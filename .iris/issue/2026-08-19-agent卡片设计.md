## 理解与结论（2026-08-19）

这次整顿的重点不是把现在的 `read`、`edit`、`write`、`terminal` 小框换一套颜色，而是改变 Agent 时间线的叙事单位：界面不再逐条暴露底层工具调用，而是把它们投影成用户真正关心的几种活动。

长期看共有四类工具活动：

1. 本地获取；
2. 上网搜索；
3. 文件写入；
4. 操作终端。

最终输出不是工具活动，而是一个 turn 的回答。因此视觉上长期共有五种内容卡片；第一批暂不实现上网搜索，恰好是“本地获取、文件写入、操作终端、最终输出”四种。用户输入继续是时间线中的提问块，不再算一种卡片；错误也不是独立业务卡片，而是上述卡片的失败状态。

这里还有三个关键判断：

* **卡片是只读投影，不是真相源。** 真正发生过什么仍以 main 持有的 tool event、file effect、terminal output 和 provider message 为准。Renderer 不自行猜测副作用，也不持久化卡片。

* **连续信息获取必须聚合。** 连续读取多个文件、执行 `git status`、`rg`、`Get-ChildItem` 等信息型终端命令，应增长同一张“本地获取”卡片，而不是让每个 access/readFile/terminal operation 各占一张卡片。

* **有副作用的动作必须保留独立审计边界。** 一次文件修改和一次操作型终端命令各自形成卡片，不与前后动作合并。这样 diff、命令、失败和重试都能准确对应到真实动作。

## 第一批产品范围

### 纳入

* 终端工具要求模型填写 `intent: information | operation`。

* `read` 与 `intent: information` 的终端调用聚合为本地获取卡片。

* `edit`、`write` 投影为文件写入卡片，并展示真实 unified diff。

* `intent: operation` 的终端调用投影为操作终端卡片，并展示实际执行的完整命令。

* assistant 的用户可见回答投影为最终输出卡片。

* 运行中、成功、失败、停止和无变更状态统一进入对应卡片，不再产生通用 Tool 卡片或额外 Error 卡片。

* 为旧 Session 做兼容迁移；旧终端记录因没有声明，保守按 `operation` 展示，并标明“旧记录，未声明类型”。

### 暂不纳入

* 独立上网搜索工具及其数据源、引用协议；只预留投影类型。

* 通过解析 PowerShell/Bash 文本来判断命令是否真的有副作用。

* 根据终端声明自动授权、拦截、回滚命令。`intent` 只影响叙事与展示，不是安全边界。

* 在聊天卡片内复制一个完整终端。完整 scrollback 仍应由真实 Terminal/输出详情承载。

* 思考过程卡片、token 卡片、内部重试卡片和 provider 原始消息卡片。

## 终端 `intent` 语义

终端工具参数改为：

```ts
type AgentTerminalIntent = 'information' | 'operation';

interface IrisTerminalToolInput {
  command: string;
  intent: AgentTerminalIntent;
  timeout?: number;
}
```

`intent` 必须是模型每次显式填写的必填字段，不设置默认值。缺失或使用其他值时由工具 schema 直接拒绝，不能由 Renderer 或 main 猜测。

### `information`

模型预期命令只读取、查询或解释现有状态，不产生需要用户审计的持久变化。例如：

* `git status`、`git diff`、`git log`、`git show`、`git rev-parse`；

* `rg`、`Get-ChildItem`、`Get-Content`、查看进程或版本；

* 只读的项目检查与元数据查询。

### `operation`

命令会或可能改变文件、Git 状态、依赖、进程、服务、系统配置或外部系统，或是否有副作用无法可靠确定。例如：

* 安装依赖、运行测试、生成代码、启动服务；

* `git add`、`git commit`、`git push`；

* 删除、移动、复制、重命名文件；

* 下载、上传、写数据库或调用会改变远端状态的接口；

* 任何混合管道中只要有一个步骤可能产生副作用。

测试命令虽然通常不修改源代码，但可能创建 cache、coverage、临时文件并消耗显著资源，因此归为 `operation`。无法确定时也必须选择 `operation`。

这个字段表达的是“模型在执行前声明的意图”，不是系统对零副作用的证明。卡片可以显示“信息型”或“操作型”，但不能写成“已验证只读”。未来若引入命令策略或权限系统，应使用独立的静态规则和运行时能力，不能复用此字段做安全判断。

## 从工具调用到卡片的投影

### 先补齐 provider tool-call 关联

当前 `IrisAgentToolEvent` 记录的是 ToolHost 的低层 operation。一次 Pi `edit` 可能先触发 `access`、`readFile`，最后才触发 `writeFile`；一次 `write` 也可能包含 `mkdir` 和 `writeFile`。这些低层 operation 现在各有随机 `toolCallId`，无法稳定知道它们来自同一个模型工具调用。

卡片整顿前需要区分两个 ID：

```ts
interface AgentToolOperationCorrelation {
  toolCallId: string;  // Pi/provider 给一次模型工具调用的 ID
  operationId: string; // Iris 为一次低层 main ToolHost 请求生成的 ID
}
```

Worker 在每个工具 definition 的 `execute(toolCallId, ...)` 边界建立上下文，低层 `requestTool()` 同时携带两者。并发时使用显式参数或 `AsyncLocalStorage`，不能用一个可被下一次调用覆盖的模块级变量。

这样一次 `edit` 的预读不会错误显示成“本地获取”，而是作为该文件写入动作的内部准备步骤；卡片的成功/失败也能以整个 provider tool call 为单位结算。

### 确定性分类规则

| Provider 工具调用              | 卡片类型 | 说明                               |
| -------------------------- | ---- | -------------------------------- |
| `read`                     | 本地获取 | `access` 与 `readFile` 合并成一个读取项   |
| `terminal` + `information` | 本地获取 | 保留命令、cwd、退出码和 terminalId，但进入获取聚合 |
| 未来 `web_search`            | 上网搜索 | 只由专用网络工具产生，不解析终端命令猜测             |
| `edit` / `write`           | 文件写入 | 内部 access/read/mkdir 不单独出卡       |
| `terminal` + `operation`   | 操作终端 | 每个模型工具调用独立一张卡                    |
| 用户可见 assistant message     | 最终输出 | 每个 turn 至多一张；流式内容原位增长            |

分类必须由 main/shared 的纯投影函数完成。React 只消费 discriminated union，不能再根据 `tool.name`、`inputSummary` 或文本启发式临场判断。

### 连续聚合算法

按 main 分配的单调 `sequence` 排序，逐个投影 provider 工具调用：

1. 遇到 `read` 或信息型 terminal：如果上一张卡也是本地获取，则追加 item；否则创建新的本地获取卡。
2. 遇到未来的 `web_search`：只与紧邻的上网搜索卡合并，不与本地获取混合。
3. 遇到 `edit`、`write` 或操作型 terminal：始终新建独立卡，并中断本地获取聚合。
4. 操作之后再次读取时，新建下一张本地获取卡。这样能表达“先检查 -> 修改 -> 再验证”的真实阶段。
5. turn 结束时追加最终输出卡；不同 turn 永不跨界合并。

不使用“相隔 N 秒以内”之类时间阈值。时间阈值会令同一事件历史在重放时得到不同分组；最大连续同类活动是稳定、可测试的规则。

示例：

```text
read package.json
read src/a.ts
terminal(information): git status
edit src/a.ts
terminal(operation): npm test -- --run src/a.test.ts
read src/a.test.ts
assistant final
```

投影为：

```text
[本地获取：2 个文件 + 1 条查询]
[文件写入：src/a.ts + diff]
[操作终端：npm test -- --run src/a.test.ts]
[本地获取：1 个文件]
[最终输出]
```

## 统一卡片骨架

所有内容卡片共享同一个紧凑骨架，但不做“卡片套卡片”：

* 圆角使用项目现有 `rounded-md`，不超过 6 px；单层边框和语义背景，不做浮夸阴影。

* Header 固定包含 Lucide 图标、类型标题、核心摘要和状态图标。状态使用图标与可访问文本，不增加大量彩色胶囊。

* Body 承载该类型最重要的事实：获取项、diff、命令或 Markdown 回答。

* Footer 只放确实可执行的动作，如展开、打开文件、打开终端输出、重试。熟悉动作使用图标按钮并带 tooltip。

* `running` 时保持尺寸稳定，内容原位增长；完成时不能替换成另一张卡或造成时间线跳动。

* 默认密度适合右栏：标题 12 px、正文 13 px、代码 12 px。长路径与长命令允许换行或横向滚动，不能挤出卡片。

* 类型依靠图标、标题和内容结构区分，颜色只做状态辅助。diff 使用标准增删色，失败使用 destructive，其余沿用 Iris 语义 token，避免整栏被单一强调色占据。

建议图标：

| 类型   | Lucide 图标          |
| ---- | ------------------ |
| 本地获取 | `FolderSearch`     |
| 上网搜索 | `Globe2`           |
| 文件写入 | `FileDiff`         |
| 操作终端 | `SquareTerminal`   |
| 最终输出 | `BotMessageSquare` |

## 卡片详细设计

### 1. 本地获取

目标是让用户知道 Agent 查了什么、查询是否成功，而不是在时间线里重看文件正文或终端 scrollback。

Header：

* 运行中显示“正在获取本地信息”；完成后显示“获取了 6 个文件，执行了 3 条查询”。

* 部分失败显示 warning 图标和“8 项中 1 项失败”，整张卡不因单项失败变成 turn 失败。

* 右侧提供展开/折叠图标。默认在项目设置层面统一，不为每项创建按钮。

Body：

* 按真实发生顺序列出 item，item 只有一行或两行，不是内嵌卡片。

* 文件项显示文件图标、项目相对路径、读取字节数；重复的 access/readFile 归并为一个文件项。

* 信息终端项显示终端图标、实际命令首行、cwd、退出码。命令多行时展开后完整显示。

* 默认最多展示最近 5 项；其余以“另有 N 项”单行入口展开。聚合数据本身不能被截断。

* 点击文件路径使用现有受控文档/文件打开能力；点击终端项打开对应输出详情。不存在可用入口时只显示事实，不渲染无效按钮。

状态：

* 新 item 到达时追加到同一张卡，卡片 ID 使用第一项 activity ID 派生，保证 React 不 remount。

* 失败 item 显示错误摘要；完整错误可在行内展开。

* 空结果仍算成功，例如 `rg` 无匹配应显示“无匹配”，不能让卡片消失。

### 2. 上网搜索（第二批预留）

该卡只由未来专用 `web_search`/`web_fetch` 工具产生。第一批不通过识别 `curl`、`Invoke-WebRequest` 等命令来伪造网络卡片。

Header 显示查询次数与来源数；Body 以查询为主线，列出标题、域名、发布时间和引用编号。连续搜索可聚合在一张卡中，网页正文抓取作为对应查询下的 source row，而不是新卡。

最终回答中的引用编号必须能定位到这里的 source。搜索失败、页面抓取失败和来源失效是 item 状态，不生成新的错误卡。未来实现时还需单独设计 URL 安全、内容污染标记、引用持久化与离线重放，本批只保留 union 分支，不能先存一套不完整的 URL 结构。

### 3. 文件写入

每次 provider `edit` 或 `write` 调用独立一张卡。最重要内容就是路径和真实 diff，而不是 `updated at line 12` 之类摘要。

Header：

* 显示 `修改 src/a.ts`、`创建 src/b.ts` 或 `未改变 src/a.ts`。

* 显示 `+N -M` 统计、运行状态和失败状态。

* 多文件能力未来若加入，一个工具调用仍是一张卡，Header 显示文件数，Body 按文件分区；当前 edit/write 单文件无需提前复杂化。

Body：

* diff 必须由 main 根据 `IrisAgentFileEffect.beforeContent/afterContent` 生成标准 unified diff，不能展示当前 `summarizeDiff()` 生成的一行文字冒充 diff。

* 建议直接依赖成熟的文本 diff 实现，输出文件头、hunk header、上下文行、增加行和删除行；不要自己维护一个只能找首个变化行的算法。

* diff 行带旧/新行号，增加与删除使用语义化绿色/红色背景；保留空白并使用等宽字体。

* 小 diff 默认完整展开。超过 120 行或 32 KiB 时内联明确标注“已显示前 N 行，共 M 行”，提供展开完整 diff；不能静默截断。

* 完整 diff 由 main 按 `sessionId + fileEffectId` 校验后按需返回。Renderer 不接收或缓存完整 `beforeContent/afterContent`。

* 创建文件时 old side 是 `/dev/null` 语义；无变化时不制造空 diff，显示“内容与现有文件一致”。

Footer：

* “打开文件”和“打开完整 diff”使用图标按钮与 tooltip。

* 第一批不在卡片上增加局部回滚按钮。现有 Undo 明确保留外部副作用，贸然放一个回滚图标会造成错误预期。

失败处理：

* 写入失败时显示目标路径、失败 operation 和错误；不显示 diff，也不能产生 file effect。

* 如果写入已经成功、后续低层步骤失败，卡片必须根据 effect ledger 显示“文件已改变，同时操作失败”，不能只显示红色失败而隐藏已发生副作用。

### 4. 操作终端

每个 `intent: operation` 的 terminal provider call 独立一张卡，绝不与相邻操作合并。命令是必须常驻可见的首要证据。

Header：

* 运行中显示“正在执行命令”；完成后显示成功/失败、exit code 和耗时。

* 显示项目相对 cwd。默认 cwd 为项目根时显示 `.`，不重复绝对项目路径。

Body：

* 使用等宽代码区展示实际送入 shell 的完整命令，保留换行和 quoting。

* 命令超过 6 行时默认限制高度并提供展开；数据不能只保存当前 `inputSummary` 的 220 字符截断值。

* 不默认把 stdout/stderr 全塞进卡片。显示输出字节数和“打开输出”动作，通过 `terminalId` 进入真实 Terminal/只读输出详情。

* 短小错误可以在命令下方显示 stderr 摘要，但必须同时保留访问完整输出的入口。

* 未来长命令转入可交互 Terminal 时，卡片仍是同一张审计入口，不再额外生成一种“运行任务卡”。

安全与真实性：

* canonical event 保存实际执行命令，而不是模型原始参数经过截断后的摘要；若 Iris 日后重写命令，必须同时记录 requested command 与 executed command，并优先展示“实际执行”。

* 命令可能含敏感值，因此不能进入日志 telemetry 或错误上报；本地 Session artifact 的访问仍由 main 校验。不能为了脱敏而在 UI 中悄悄把实际命令改成另一条命令。

### 5. 最终输出

每个 turn 最多一张最终输出卡。它承载 assistant 给用户的可见结论，工具循环中的 provider-only assistant envelope 不渲染。

* 流式开始时先建立稳定卡片，正文原位追加；不要用独立“Thinking…”卡片占位。

* 正文使用与文档一致的安全 Markdown 渲染，支持代码块、列表、表格和项目相对文件链接。

* Header 显示“Iris Agent”与生成/完成/停止状态，不重复大标题。

* turn 在有部分文本时被 Stop，保留部分文本并标记“已停止”。

* provider 在没有可见正文前失败，仍投影一张失败态最终输出卡，在 Body 显示 turn error，Footer 放唯一的重试按钮。

* provider 在已有正文后失败，保留正文，在末尾显示失败区与重试按钮。

* 现有独立 `AgentErrorCard` 并入此失败状态；工具错误则留在对应工具卡中。这样错误不会成为第六种卡片。

## 用户输入与 turn 操作

用户输入保留为靠右的提问块或无边框段落，不套用上述卡片骨架。一个 turn 的视觉顺序固定为：

```text
用户输入
活动卡片 0..N
最终输出卡片
turn 操作栏
```

Fork、Undo 等 turn 级动作放在 turn 末尾的紧凑操作栏，不塞进某一张工具卡。Retry 只出现在失败态最终输出中；Stop 仍属于当前 Session/turn 控制。这样动作所有权清楚，也不会出现顶部和错误卡两个重试入口。

## 建议的数据模型

### Canonical 事实

不持久化 `cards[]`。现有 canonical state 补充足以重建投影的事实：

```ts
interface IrisAgentToolActivity {
  id: string;             // provider tool-call ID
  turnId: string;
  requestId: string;
  sequence: number;       // main 分配，turn 内单调递增
  tool: 'read' | 'edit' | 'write' | 'terminal';
  terminalIntent?: 'information' | 'operation' | 'unknown';
  state: 'running' | 'completed' | 'failed';
  startedAt: number;
  completedAt?: number;
  input: {
    path?: string;
    command?: string;
    cwd?: string;
  };
  operationIds: string[];
  fileEffectIds: string[];
  terminalId?: string;
  result?: {
    exitCode?: number | null;
    outputBytes?: number;
    readBytes?: number;
    noMatches?: boolean;
  };
  error?: string;
}
```

低层 operation 仍可保留作诊断，但不直接进入正常 Renderer projection。`fileEffects` 与 terminal output 继续是副作用和完整输出的真相源。

### Renderer projection

定义独立的 discriminated union：

```ts
type IrisAgentCardView =
  | LocalRetrievalCardView
  | WebSearchCardView
  | FileChangeCardView
  | TerminalOperationCardView
  | FinalResponseCardView;

interface IrisAgentTurnView {
  id: string;
  userMessage: UserMessageView;
  cards: IrisAgentCardView[];
  actions: TurnActionCapabilities;
}
```

`projectIrisAgentSession()` 由 main 或 shared 的纯模块实现并有专项测试。短期 IPC 仍可发送完整 Session，但 `IrisAgentView` 必须改为只消费 projection；完成稳定后再让 main 只下发 DTO，移除 Renderer 中的 `providerMessage`、完整 file content、request fingerprint 和 cleanup queue。

大 diff、完整终端输出与 provider context 走受控的按需读取 action。流式 token 到达时，理想形态是只 patch 当前 final card，而不是跨 IPC 重发不断增长的完整 Session；这可放在 projection 稳定后的性能批次，不阻塞第一批卡片语义落地。

## 协议与持久化迁移

1. Iris 自己实现 terminal tool definition，使用 TypeBox 声明必填 `intent`。现有 Pi `createBashToolDefinition()` 的 schema 只有 `command/timeout`，仅修改 description 不能让模型真正填写并校验新字段。
2. 自定义 definition 可以复用 Pi 的输出截断工具和结果形状，但 terminal operations 接口要由 Iris 拥有，确保 `intent` 从 provider 参数完整传入 Worker request，不能藏在可变闭包中。
3. `AgentToolOperationInput` 的 terminal 分支增加 `intent`；Worker protocol version 递增。validator、worker-check 和 protocol fixtures 同步更新。
4. Session store schema version 递增。旧 terminal event 迁移为 `terminalIntent: 'unknown'`，projection 将其作为操作终端展示；旧 `inputSummary` 只能作为旧记录的命令文本，明确显示“历史命令可能已截断”。

6. 现有 `IrisAgentFileEffect` 不丢弃；它正好提供真实 diff 的 before/after 依据。卡片只引用 effect ID，不复制一份可能漂移的 diff 真相。

## 最终输出语义追问（2026-08-19）

### 现状语义

* 每个 turn 恰好一张最终输出卡，ID 固定为 `final:{turnId}`，绑定该 turn 唯一一条用户可见 assistant message（`assistantMessageId`，过滤 `providerOnly` 信封）。

* 卡片内容 = 该 message 的当前 `content`，即 main 在每次 `text_delta` 时通过 `updateAssistantMessage` 原位追加的那个缓冲，不是 turn 完成后才生成的快照。

* 卡片状态 = turn 状态（`running` / `completed` / `failed` / `stopped` / `rewound`→`stopped`），与流式正文是两个独立维度。

### 为什么运行中会变化

* 这张卡本质是“正在生成的回答”的实时视图：turn 一开始就建卡（正文为空时显示占位“正在生成最终输出…”），每个 token delta 追加进同一个缓冲，正文随之增长。这正是方案既定行为——“流式开始时先建立稳定卡片，正文原位追加”——不是 bug。

* 变化发生在三层的叠加：main 每次 delta 追加 content 并 bump revision → 完整 Session 快照跨 IPC 重发 → Renderer 全量重投影并对累计全文重新跑 ReactMarkdown。长回答下接近 O(n²)，这也是批次 C“只 patch 当前 final card、不再重发完整 Session”要解决的问题。

### 语义张力与结论

1. “最终输出”承诺的是终态产物，但生成期间正文就在变。它实际是“本轮回答”，running 时是“生成中的回答前缀”。卡片类型名可以保留，但要靠状态与占位文案传达“生成中”。
2. 卡片同时承载 turn 级结果状态与流式正文，两者本来就是两个维度，当前实现是对的；张力只在命名与全量重发。
3. 与工具卡不同，最终输出没有审计语义、不做聚合，是唯一允许“内容可变”的卡片；工具卡必须等事实落定。这个不对称是刻意的。
4. 可选小改进：running 且有部分正文时在正文前显式标注“正在生成”，消除“最终”歧义；渲染层对 final card 的 markdown 做增量/记忆化，避免每次 delta 全量重解析。

## 回复卡片定调与实测（2026-08-19）

### 定调

* “最终输出”泛化为“agent 回复”：文本回复 = 用户可见正文 **+ providerOnly 中间絮语**，每段文本一张回复卡，回复卡中断本地获取聚合；不再承诺“每 turn 一张且固定在最后”。

* 与 Claude Code 对照：其主时间线 inline 展示工具间的 assistant 短评，无文本的纯工具轮不产生文本块，方向一致。

### 存量实测

对 `%APPDATA%\Iris-dev\iris-agent-sessions\82d34fc308d28f11.json`（本项目真实 Session，24 个 turn）做了统计：

* 54 个 providerOnly 信封，其中仅 14 个非空（26%）；其余是纯 toolUse 信封、正文为空。

* 非空絮语文本 28–291 字符，均值约 143 字符（一两句话，如“我先定位消息输入区…”“The status doc reflects …, let me check current HEAD”）。

* **空文本信封必须抑制，不能成卡**：否则工具密集 turn 凭空多出 10+ 张空卡，纯粹是噪声。

## Agent 回复卡完整方案（2026-08-19）

### 方案结论

将“最终输出”从卡片类型中移除，统一改为 **Agent 回复**。Agent 回复不是 turn 的终态产物，而是 Agent 在时间线中实际发出的一段文本。

首批卡片类型调整为：

1. 本地获取；
2. 文件写入；
3. 操作终端；
4. Agent 回复。

上网搜索继续作为未来预留类型，不在本批实现。用户输入仍是独立的提问块，不属于 Agent 回复卡。

一个 turn 不再强制以某张“最终输出”卡结尾，而是按事实发生顺序显示：

```text
用户输入
本地获取
Agent 回复
本地获取
文件写入
Agent 回复
操作终端
Agent 回复
turn 操作栏
```

### Agent 回复的定义

一张 Agent 回复卡表示一段连续的、非空的、允许面向用户展示的 assistant 文本。

回复来源包括：

* 工具调用前的非空 `providerOnly` assistant 短评；

* turn 结束后的普通 assistant 回复；

* 未来其他明确声明为用户可见的 assistant 文本事件。

以下内容不生成回复卡：

* 空的 `providerOnly` 信封；

* 只有 tool call、没有文本的 assistant envelope；

* provider 原始上下文中的重复快照；

* 未被标记为可展示的内部推理文本。

这里的“空文本不成卡”不是一般性的优化，而是语义规则：没有发出文本，就没有 Agent 回复，也不应该打断本地获取聚合。

### 统一时间线

当前工具事件和 assistant message 分开投影，无法可靠表达“读取 -> 回复 -> 再读取”的顺序。需要为两者建立同一条 turn 内时间线。

建议新增统一的 canonical activity：

```ts
interface IrisAgentReplyActivity {
  id: string;                 // 稳定的 provider message/reply ID
  turnId: string;
  sequence: number;           // main 分配，turn 内严格单调递增
  state: 'running' | 'completed' | 'failed' | 'stopped';
  source: 'providerOnly' | 'assistant' | 'fallback';
  content: string;
  providerMessageId?: string;
  createdAt: number;
  completedAt?: number;
  error?: string;
}
```

工具活动与回复活动共同使用 `sequence`。Renderer 不再根据 `createdAt`、数组位置或文本内容猜测顺序。

短期可以把回复活动嵌入现有 `IrisAgentMessage`，增加 `sequence`、`displayable` 和稳定的 provider message correlation；长期再统一成 `IrisAgentTimelineActivity`。不需要持久化 `cards[]`，卡片仍然是 canonical activity 的纯投影。

### 回复生命周期

#### 1. 创建

收到一段可展示文本的第一个 delta 时创建回复活动：

* 空文本不创建活动；

* 回复 ID 在首次创建时确定；

* 同一 provider message 的后续 delta 只能更新该回复，不能创建新卡；

* 回复首次创建时分配 `sequence`，后续内容变化不改变顺序。

当前普通 assistant message 只有一个累积缓冲，需要改为支持多个回复活动。`providerOnly` 消息已经按 provider assistant message 独立保存，可以直接作为历史回复活动的基础。

#### 2. 流式更新

回复卡保持稳定的 DOM identity，正文原位追加：

```text
创建 Agent 回复卡
-> 追加文本 delta
-> 继续追加到同一张卡
-> assistant message 结束
-> 状态变为 completed
```

卡片不显示“Thinking”占位卡。只有在已经确认存在可展示回复、但正文仍在增长时，才显示 running 状态。

#### 3. 完成、停止与失败

* 正常完成：回复卡显示 `completed`；

* Stop：保留已有部分正文，回复卡显示 `stopped`；

* 回复已经有正文后 provider 失败：保留正文，在卡片末尾显示错误区；

* turn 在没有任何回复文本前失败：创建一张 `source: fallback` 的失败态 Agent 回复卡，显示 turn error 和唯一重试入口；

* 工具调用失败：错误仍归属本地获取、文件写入或操作终端卡，不创建回复卡；

* 普通空 providerOnly message：不创建卡，也不显示错误。

`fallback` 是“失败时用户需要看到一个回复落点”的例外，不改变“正常空文本不成卡”的规则。

### 投影与聚合规则

按 turn 内 `sequence` 遍历 canonical activities：

1. `read` 与 `terminal(information)`：如果上一张卡是本地获取，则追加 item，否则创建本地获取卡；
2. 非空 Agent 回复：始终创建独立回复卡，并中断本地获取聚合；
3. `edit` 与 `write`：始终创建独立文件写入卡，并中断本地获取聚合；
4. `terminal(operation)`：始终创建独立操作终端卡，并中断本地获取聚合；
5. 空回复活动不存在于投影输入中，因此不会中断任何聚合；
6. 同一 turn 可以有任意数量的 Agent 回复卡；不同 turn 永不合并；
7. 不再在 turn 末尾强制追加“最终输出”卡。

示例：

```text
read package.json
assistant(providerOnly): 我先确认项目入口
read src/main.ts
edit src/main.ts
assistant: 修改完成，我接下来运行定向检查
terminal(operation): npm test -- agent
assistant: 定向检查通过
```

投影为：

```text
[本地获取: package.json]
[Agent 回复: 我先确认项目入口]
[本地获取: src/main.ts]
[文件写入: src/main.ts + diff]
[Agent 回复: 修改完成，我接下来运行定向检查]
[操作终端: npm test -- agent]
[Agent 回复: 定向检查通过]
```

### ProviderOnly 展示边界

`providerOnly` 不再等同于“永远隐藏”，但也不等同于“所有原始 provider 文本直接展示”。main 需要在记录 provider message 时确定它是否属于可展示的 Agent 短评。

第一批采用以下规则：

* `providerOnly` 且 `content.trim() !== ''`：作为 Agent 回复候选；

* `providerOnly` 且正文为空：忽略；

* provider message 是纯 tool call：忽略文本卡；

* provider 返回明确的内部 reasoning 字段：不投影为 Agent 回复；

* 普通 assistant message：非空时作为 Agent 回复；

* 不把原始 provider message、完整上下文和重复快照直接传给 Renderer。

如果当前 provider 无法区分 commentary 与 reasoning，第一批只展示已有 `providerOnly` 中实际存储的短文本，并保留后续增加 `displayable` 标记的扩展位；不能通过字符串启发式识别推理内容。

### 卡片设计

Agent 回复卡使用现有 `CardFrame`，但替换最终输出专属语义：

* 图标：`BotMessageSquare`；

* 标题：`Agent 回复`；

* running：显示“正在回复”；

* completed：显示“已回复”；

* stopped：显示“已停止”；

* failed：显示“回复失败”；

* 正文：安全 Markdown，支持代码、列表、表格和项目相对文件链接；

* 回复很短时完整显示，不额外套内层卡片；

* 长回复保留现有文本换行、代码块和滚动约束；

* 卡片 ID 使用 reply activity ID，流式更新不能 remount；

* 失败态只有一个重试入口；

* Agent 回复卡不显示工具输出，不复制 terminal scrollback，不展示 provider context。

Header 不应再写“最终输出”。回复卡只表达“Agent 在这里说了一段话”，不暗示这一定是 turn 的最后结论。

### 错误与操作栏

Fork、Undo、Stop 等 turn 级动作仍然放在 turn 操作栏，不放进某一张回复卡。

Retry 规则改为：

* 回复失败或 fallback 失败态 Agent 回复卡提供 Retry；

* 同一失败 turn 只允许一个 Retry 入口；

* 工具失败不额外生成 Retry，除非现有 turn 级 retry 能力明确适用于整个 turn；

* 已有正文后失败，Retry 仍位于该回复卡错误区；

* 没有正文但 turn 失败，Retry 位于 fallback 回复卡。

### 旧 Session 迁移

旧 Session 不丢失任何 message 或 tool event：

* 旧的非空 `providerOnly` message 投影为 Agent 回复卡；

* 旧的空 `providerOnly` message 保留在 canonical history，但不生成卡；

* 旧的普通 assistant message 非空时投影为 Agent 回复卡；

* 旧 terminal event 没有统一 `sequence` 时使用确定性的 legacy 顺序迁移，标记为旧记录；

* 新 Session 从创建活动开始写入 sequence，不在 Renderer 临时推导；

* schema version 递增，迁移后重启和再次投影结果必须稳定；

* 旧的 `final-response` projection 名称只作为代码兼容过渡，正常 UI 不再渲染该类型。

历史 Session 的顺序如果缺少跨 message/tool event 的准确事实，不能伪造精确顺序。迁移应保持现有持久化数组中的相对顺序，并标记 legacy；新 Session 则必须使用 main sequence。

### 实现批次

#### 批次 A：统一事实与投影

* 定义 `IrisAgentReplyActivity` 或等价 timeline activity；

* 为回复与工具活动增加 turn 内单调 `sequence`；

* 为 provider message 建立稳定 correlation；

* 过滤空回复，投影非空 `providerOnly`；

* 将 projection 类型从 `final-response` 改为 `agent-reply`；

* 删除“每 turn 强制追加最终输出卡”的规则；

* 完成旧 Session 迁移。

#### 批次 B：回复生命周期与 UI

* 实现 Agent 回复卡组件；

* 支持 providerOnly、普通 assistant、fallback 三种 source；

* 支持多回复卡和回复中断本地获取聚合；

* 保持流式回复的稳定 ID 和原位更新；

* 保留 Stop、Retry、Fork、Undo 的现有 turn 级所有权；

* 删除最终输出卡的专属文案和分支。

#### 批次 C：传输与性能

* 回复 delta 只 patch 当前 reply activity，不重发完整 Session；

* main 只向 Renderer 发送最小卡片 DTO；

* Markdown 渲染避免每个 delta 对全部历史回复重新解析；

* 处理大量回复、超长回复和历史 Session 的数据预算；

* 继续让完整 provider context 由 main 控制、按需读取。

### 测试与验收

#### 投影测试

* `read + providerOnly(text) + read` 得到“本地获取、Agent 回复、本地获取”；

* `read + providerOnly(empty) + read` 仍得到一张本地获取卡；

* 空文本不创建卡；

* Stop 保留部分正文并显示 stopped；

* 有正文的 provider 失败保留正文并显示错误；

* 工具失败只显示在对应工具卡；

* Retry、Fork、Undo 不会删除或伪造已经发生的回复活动。

#### 迁移与稳定性测试

* 旧非空 providerOnly message 能迁移为回复卡；

* 旧空 providerOnly message 不生成空卡；

* 旧 Session 重启后回复卡顺序稳定；

* 新 Session 的 sequence 在并发工具和回复事件中不串线；

### 最终决策

本方案采用以下不可变口径：

* 不再使用“最终输出”作为正常卡片类型；

* Agent 的每段非空、可展示文本都是一张 Agent 回复卡；

* providerOnly 中间短评纳入回复来源；

* 空文本、纯 tool call 和不可展示内部文本不成卡；

* Agent 回复会中断本地获取聚合；

* 回复和工具活动必须共享 main 分配的 turn 内 sequence；

* 卡片是 canonical timeline activity 的只读投影，不持久化第二份 `cards[]` 真相；

* turn 失败但没有任何文本时，用 fallback 失败态回复卡承载错误和 Retry；

* 旧 Session 保守迁移，新 Session 必须按统一时间线记录事实。

## Agent 回复卡实现结果（2026-08-19）

已实现“Agent 回复卡完整方案”的第一版代码：

* `IrisAgentMessage` 增加 `displayable`，main 在首次可见文本到达时为 assistant/providerOnly 分配稳定的 turn-local `sequence`；工具事件创建时使用同一序列空间，避免 Renderer 依据数组位置猜测“读取 -> 回复 -> 修改”的顺序。

* Session store 在加载旧记录时为缺少 sequence 的 message/tool event 进行确定性补齐，并校验新字段；旧 terminal intent 兼容逻辑保持不变。
