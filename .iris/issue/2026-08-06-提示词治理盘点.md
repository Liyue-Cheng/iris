## 2026-08-06 盘点

### 真相之源清单

代码中共有四份模板正文和两份生成器，全部集中在三个文件里：

- `SOFTWARE_PROMPT_TEMPLATE`（`src/main/iris-templates.ts`）——软件层正文。
  版本属性由 `PROTOCOL_VERSION`（=2）、`app.getVersion()` 和
  `software-prompt.ts` 计算的 12 位 SHA（当前 `e24e98a5b8d2`）拼成。
- `CONSTITUTION_TEMPLATE`（同上）——项目层出厂默认，另有
  `LEGACY_CONSTITUTION_DEFAULTS` 两份历史版本用于升级识别。
- `MACHINE_CONVENTIONS_TEMPLATE`（同上）——用户层模板，一次性安装。
- `FOCUS_CONTEXT_SCRIPT`（`src/main/agent-injection.ts:57-108`）——
  SessionStart hook 的 PowerShell 脚本正文，含中文引导语。
- `jsonClis()` + `hookCommand()`（同上）——五家 CLI 的 hook JSON 配置生成器。
- `docSkeleton()`（`src/main/software-prompt.ts`）——新建文档 frontmatter
  骨架，与软件层提示词中的范例同源，由测试锁定一致。

### 副本链：一段正文实际落在多少地方

以软件层为例，同一段正文的完整副本链是：

1. 模板常量（真相之源）。
2. `AGENTS.md` 的 `<iris-software>` 块——`syncEntryFile()` 写入，SHA 校验。
3. `CLAUDE.md` 的同名块——同机制，仅在文件已存在时维护。
4. 其他 vendor 入口（`GEMINI.md`、`.cursorrules` 等六种）——同机制，
   本仓库当前没有。
5. **运行时第二次交付**：`focus-context.ps1` 从 `AGENTS.md` 正则抽取该块，
   经 hook stdout 再发一遍。Claude 会话中模型实际收到两份 software——
   静态入口一份、hook 一份；而正是这份 ~5KB 的重复把 hook 输出顶过了
   Claude Code 的 10,000 字符上限，把真正动态的 project/focus 层挤出了
   可见范围（见前置 issue 调研）。
6. `.bak` 备份（`AGENTS.md.bak`、`CLAUDE.md.bak`）——首次写入时生成，
   之后永不更新，是天然过期的死副本。
7. `.iris/status/默认提示词与提示词管理.md` 中的**完整正文引用**——
   手工维护的第四类副本，只靠 `reflects:` 戳弱保证，无任何机制校验它
   与模板一致。
8. 设置页预览（`assembleContextPreview()`）——即时渲染，不落盘，无副本
   问题，但它模拟的拼接顺序与真实 hook 输出是两套代码，可能漂移。

项目层与用户层的链条短一些，但性质相同：模板 → 落盘文件（所有权移交给
人）→ 状态文档中的完整正文引用。hook 脚本的链条是：模板常量 →
`~/.iris/focus-context.ps1`（逐字节比较判新旧）。hook JSON 的链条是：
生成器 → 五份用户级 CLI 配置（命令字符串相等判 configured）。

### 一致性机制矩阵

现存机制是三套异构方案，各管一段：

- 软件层/项目层：SHA-256 前 12 位 + 历史哈希档案 + 测试守护
  （`software-prompt.test.ts`）。这套最完善。
- hook 脚本：BOM+正文逐字节相等。无版本握手——`~/.iris/focus-context.ps1`
  被所有 Iris 版本、所有项目共享，last-writer-wins，且只在设置页手工触发
  安装，不随启动自动刷新。
- hook JSON：命令字符串相等。只证明配置文件写对了，不证明 CLI 执行了、
  更不证明模型收到了（Claude 截断即在此盲区）。
- 状态文档中的正文引用：**无机制**，纯靠人。
- 运行时交付（hook stdout → 模型上下文）：**无机制**，无预算、无 vendor
  适配、无端到端验证。

### 结构性问题

1. **副本数量本身不是问题，问题是第 5、6、7 类副本没有存在的理由。**
   运行时重复交付 software 是纯浪费且直接引发 Claude 截断故障；`.bak`
   永久滞留在仓库根目录（当前 git status 里三个 .bak 全是未跟踪/已修改
   噪音）；状态文档引用完整正文注定漂移。
2. **三套一致性机制没有共同的抽象。** 每新增一类落盘物就要发明一套新的
   "怎么判断它过期"的逻辑，这是"不可扩展"的直接原因。
3. **交付层与内容层耦合。** 五家 CLI 共享一份无预算的 stdout，内容多少、
   什么顺序、超限怎么办，对每家 CLI 都应该不同（Claude 10K 上限已证明），
   但当前架构里没有 vendor renderer 这一层。
4. **全局脚本跨版本共享。** 不同版本的 Iris 写同一个
   `~/.iris/focus-context.ps1`，行为由最后安装者决定，没有版本标记可校验。
5. **健康检查停在文件层。** `configured`/`current` 只说明字节正确，
   设置页对"Claude 实际只收到前 2KB"这种确定性失败显示全绿。

### 方向建议（待决策，未实施）

核心原则：**每段内容只有一个真相之源，所有副本都是机器渲染的产物，任何
副本不再被手工编辑或二次转发。**

- **静态与动态分工**：静态入口文件（AGENTS.md/CLAUDE.md）负责交付
  software 层；hook 只交付动态层——project/user conventions、workspace
  元数据、focus 指针或快照。消除运行时重复副本，同时让 hook 输出稳定
  落在 Claude 10K 预算内。对无静态入口文件的 CLI，hook 以条件判断兜底
  输出 software 层（检测入口文件中是否已有 `<iris-software>`）。
- **vendor renderer 层**：主进程先产出结构化的会话上下文模型（会话标记、
  项目根、workspace 路径、focus 路径），各 CLI 的 renderer 按自家格式与
  预算渲染输出。预算超限的降级策略（截 focus、退化为指针）显式写在
  renderer 里，而不是被 CLI 悄悄截断。
- **统一的新旧判据**：给 hook 脚本加版本头（如首行注释带 app version +
  sha），使脚本与软件块共用同一套 SHA+历史档案机制；`injectionState`
  据此判断，必要时随 App 启动自动刷新，替代手工安装。
- **消灭无理由副本**：状态文档改为引用 sha + 源文件指针，不再粘贴完整
  正文；`.bak` 改进为写入 `.iris/` 外的临时目录或带清理机制。
- **运行时验证**：把"文件已配置"和"最近一次真实交付"分开呈现（前置
  issue 已列，归属本治理框架）。

## 2026-08-07 项目层必要性复核

### 结论

**当前“必需的项目级提示词”没有独立存在的必要。** 内置
`CONSTITUTION_TEMPLATE` 的全部有效内容都属于 Iris 产品协议，应合并到
`<iris-software>`。项目级上下文仍有价值，但它只能是**可选的项目自定义说明**，
用于语言、测试命令、发布限制、领域约定等真正随项目变化的事实和偏好；它不应再
定义 UI 已经硬编码的状态机，也不应再作为项目是否正确初始化的协议门禁。

这里要区分两件事：

- 可以取消的是“每个 Iris 项目必须有一份出厂项目宪法，agent 必须读取它才能正确
  使用 Iris”的产品设计。
- 可以保留的是“项目作者有地方写额外 agent 指令”的扩展点。现有自定义
  `.iris/CONVENTIONS.md` 可继续兼容并按存在性注入，但应降级为 optional guidance；
  也可以由入口文件中 `<iris-software>` 块外的人类内容承担。两者都不属于协议真相
  之源。

### 为什么当前项目层并不真的可配置

当前模板只剩两项：状态机和 Markdown 风格。二者都不是项目策略。

1. **状态机是产品数据模型。** `ISSUE_STATUSES` / `REPORT_STATUSES` 固定了菜单；
   `docSkeleton()` 固定新建 issue 为 `Todo`、report 为 `Active`；默认样式表固定八个
   状态的视觉样式；issue 面板用固定六态排序、筛选和批量修改；活动 lens、报告
   timeline 以及切换关闭态时回收关联终端，都直接解释具体字符串。修改项目提示词
   不会改变这些行为。
2. **所谓 soft value 只是容错，不是配置能力。** 自定义值能被保存和原样显示，但
   不会进入标准菜单和排序。issue 只有一组额外硬编码的关闭同义词
   (`resolved` / `closed` / `wontfix` 等)；report timeline 对 `backlog` 做不区分大小写
   判断，左侧 lens 却只按精确的 `Backlog` 隐藏。同一个自定义值甚至可能在两个视图
   中得到不同结果。
3. **Markdown 风格由编辑器实现决定。** “使用 CommonMark、匹配固定 remark
   defaults”描述的是 Iris 的序列化行为，不是项目可以选择的写作策略。
4. **App 从未解析项目层策略。** scanner 对 `.iris/CONVENTIONS.md` 只读取
   `protocol` 和存在性；正文仅透传给 agent。于是它一面宣称状态值由项目文件定义，
   一面没有任何机制让 UI 服从该定义。

因此当前架构的真实关系是：

```text
产品代码中的固定语义 ──驱动──> 创建 / 菜单 / 排序 / 筛选 / 样式 / 终端生命周期
          │
          └──人工抄写──> CONSTITUTION_TEMPLATE ──告知──> agent
```

项目文件不是配置源，只是产品固定语义的一份人类可编辑副本。允许编辑反而制造了
“文字已经改了、产品行为没有改”的伪配置。

### 必需项目层带来的实际成本

这份默认文件当前只有约 1.1 KB，字符预算不是主要矛盾；主要成本是为维持它的
“独立且必需”身份，产品已经增加了整条生命周期：

- 初始化时创建文件，并支持 `~/.iris/templates/CONVENTIONS.md` 覆盖出厂种子。
- scanner 检查存在性和 `protocol`，左栏为缺失或版本不符显示协议告警。
- 维护当前模板、两份历史默认、哈希分类、升级动作和 `.bak`。
- 设置页展示 current/stale/customized、出厂正文、升级确认和合成预览。
- hook 每次会话读取并再次传输该文件。

这些复杂度没有换来真正的项目级状态机能力，只维护了一个默认内容副本。

### 建议的目标模型

1. 将六态 issue、两态 report、关闭态的用户授权规则、Markdown 序列化约束全部移入
   `<iris-software>`，并删除“状态值定义在 `.iris/CONVENTIONS.md`”的说法。
2. 状态机应有一个结构化的代码真相之源，由 UI 常量、默认样式、文档骨架和软件
   提示词共同引用或由测试锁定；不能只是把同一段英文从项目模板复制到软件模板。
3. 新项目不再生成必需的 `.iris/CONVENTIONS.md`，缺失文件不再触发补全或 protocol
   告警。删除项目默认识别、历史正文档案和默认升级链。
4. 对已有项目采取兼容迁移：不删除、不覆盖自定义 `.iris/CONVENTIONS.md`；存在时
   仍作为可选 `<iris-project>` 注入。未修改的出厂默认可以停止注入，或在一次明确的
   迁移中移除，避免与新软件层重复。
5. 若未来确实要支持“每项目自定义状态机”，应先设计 App 可解析、可验证的结构化
   配置，并让创建默认值、菜单、顺序、active/resolved 分类、终端关闭语义、样式和
   agent 提示全部由它生成。在这条链打通前，状态机必须明确归类为软件不变量。

### 对前述方向建议的修正

“静态入口管 software、hook 管动态层”仍成立，但动态层不应等同于“必有项目提示
词”。更准确的分工是：静态入口交付完整 Iris 产品协议；hook 交付 workspace/focus
等会话动态信息、用户机器事实，以及**存在时才交付**的项目自定义说明。

- [x] 确认取消必需的项目级协议提示词，将当前项目模板内容全部并入软件层。
- [x] 确认不兼容 `.iris/CONVENTIONS.md` 项目层，改由入口文件 `<iris-project>` 块托管。

## 2026-08-09 显式参与列表与双投影重构

根据最终业务决策，项目提示词不再以入口文件正文为真相，也不再自动维护所有已存在的
vendor 文件。`.iris/settings.json` 现在同时承载两个项目级真相：

- `prompts.project` 是用户编辑的项目指令。
- `agentContext.entries` 是明确参与同步的入口文件列表，`AGENTS.md` 必须始终在列。

每个参与入口都是两个并行投影的共同目标：`<iris-software>` 必须逐字等于 App 内置模板，
`<iris-project>` 必须等于 `prompts.project`；项目指令为空时项目块应不存在。项目打开只做
审计，不再把入口文件的外部修改静默导回 JSON，也不自动修复漂移；发现缺失、漂移、重复
块或写入失败时提示用户重新同步。任一参与入口的任一层不健康时，Agent 终端拒绝启动。

参与列表的修改具有明确顺序：添加入口时先用 revision CAS 更新设置，再原子写入双块；
停止同步时先从目标文件删除两个托管块并保留其他正文，再将入口移出列表，设置更新失败
则尝试恢复投影。列表外文件从此不受 watcher、保存或初始化写入。旧设置缺少显式列表时，
仅在一次迁移中收编当时已存在的受支持入口；之后新出现的 vendor 文件保持未参与状态。

协议初始化会创建或修复列表中的全部入口，包括已被删除的可选入口；不会因发现一个列表外
vendor 文件而自动收编。设置页已经重做为项目指令编辑器、参与入口列表、软件层/项目层
独立健康状态、单项或全部重同步、添加入口、停止同步和只读软件协议正文，不再提供模拟
拼接预览或从副本反向导入 canonical 的动作。
