有的时候会弹出 session is outside project scope

你全部检查一下，这是怎么回事？

## 检查结论（2026-09-12）

报错来自主进程的项目范围保护，不是 agent 自己生成的普通提示。当前有两条完全相同语义的拒绝路径：

- `src/main/ipc.ts:208-220` 的 `requireSessionInScope()` 校验终端会话的 `projectRoot` 和 `projectGeneration`；不匹配时抛出 `session is outside the active project scope`。
- `src/main/agent/session-manager.ts:2628-2636` 的 `requireSession()` 校验 Iris Agent 会话的 `projectRoot`；不匹配时抛出 `Iris Agent session is outside the active project scope.`。

项目范围由 `{ root, generation }` 标识。每次同一窗口切换项目，`src/main/project-switch.ts` 会先把旧项目的终端和 Iris Agent 会话关闭，再激活新项目并把 generation 加一。旧右栏、旧终端组件或切换期间发出的异步 IPC 如果仍携带旧的 `sessionId` 或旧 `expectedScope`，主进程就会拒绝请求。这是保护数据和输入不串项目的设计行为。

最常见的触发时序是：

1. 项目 A 中打开会话 A，renderer 保存了 A 的 `{root, generation}`。
2. 用户切换到项目 B；切换队列先关闭 A 的会话，然后提交 B 的新 scope。
3. 旧终端的输入、resize、scrollback、output attach/ack，或旧 Iris Agent 的发送/停止/重试请求，在清理完成前后抵达主进程。
4. 主进程发现会话已被销毁，或会话/请求的 root 或 generation 不再等于当前 scope，于是弹出该报错。

代码里已有几层防护：项目切换串行化并设置 `projectSwitching`；所有 project-scoped IPC 比较 `expectedScope`；renderer 的 session store 按 root + generation 过滤；旧项目会话在切换时通过 `closeProject()` 回收；终端 I/O 失败会进入断开状态并重新 hydrate。因而这个提示本身通常表示“旧请求被正确拦截”，不表示当前项目文件越界。

仍值得修的体验问题是：旧组件的异步请求在切换后仍会到达主进程，用户看到的是底层保护错误，而不是“项目已切换，会话已关闭”；另外 `session-manager.ts` 的 Iris Agent `requireSession()` 当前只比较 root，没有比较 generation，虽然 IPC 外层已经比较 expectedScope，但内部调用仍缺少同样的代际约束。

建议后续按以下顺序处理：

- [ ] 为切换项目期间及切换完成后的旧终端输入、resize、scrollback、output attach/ack 增加集成测试，确认旧请求被静默取消或转换为会话已关闭状态。
- [ ] 为旧 Iris Agent 的 send/stop/retry/rewind/branch 等异步动作增加切换后的竞态测试，并让内部会话校验同时比较 `projectGeneration`。
- [ ] renderer 在 project scope 变化时主动卸载/失效旧 TerminalView 和 agent action，避免继续发送旧 session 的请求。
- [ ] 将该错误映射为一次性、用户可理解的提示（例如“项目已切换，旧会话已关闭”），避免把预期的隔离保护显示成随机故障。
- [ ] 只有在上述竞态测试确认仍有“当前项目、当前 generation 的会话”被误判时，再继续追查路径大小写、junction/symlink 或重复窗口上下文问题。

当前判断：如果报错总是在切换项目、关闭文档、快速切换右栏会话或窗口恢复后出现，根因就是旧会话请求的竞态；如果在未切换项目、同一会话持续操作时也出现，则需要补充发生时的操作步骤和对应 IPC channel 日志。

## 补充判断：未切换项目时也会出现（2026-09-12）

用户反馈说明“项目切换竞态”不是唯一原因。更准确地说，报错的直接条件是：请求到达时，`sessionId` 在当前窗口的 session manager 中已经不存在，或者它的 session 元数据与当前 `{root, generation}` 不一致。项目切换只是其中一种制造条件。

在不切换项目的情况下，最可能的路径有两类：

1. **PTY/Agent 会话已结束或被清理，但 renderer 仍持有旧 session。** 终端进程退出、用户关闭会话、Agent 会话归档/销毁、窗口恢复或 renderer 热重载时，右栏组件可能在生命周期事件到达前仍发出 resize、scrollback、output attach/ack、输入或 Agent 操作。`requireSessionInScope()` 对“找不到 session”统一报成 outside scope，所以错误文字会掩盖真正原因“session 已经结束/不存在”。
2. **同一项目的 renderer scope 与 main scope 代际不一致。** `generation` 是窗口级项目绑定的代数，不是文件变化版本。renderer 从 `projectScopeState` 捕获旧 scope 后，异步 TerminalView/Agent action 可以在会话仍显示期间继续发送旧 expectedScope。即使 root 没变，只要 main 曾重建/恢复过窗口项目绑定，generation 不同也会被拒绝。

代码证据：

- `src/main/ipc.ts:216-220` 把“不存在”和“root/generation 不匹配”合并成同一条错误。
- `src/renderer/terminal/replay-controller.ts` 在 replay、输出队列和历史恢复中会异步发送 acknowledge；`TerminalView.tsx` 也会异步发送 resize/input。会话在这些 await 期间结束时，旧请求仍可能抵达 main。
- `src/renderer/terminal/terminal-transport.ts` 的 attach、acknowledge、replay 没有在 IPC 前再次确认 session 仍在当前 projection 中；它只绑定创建时的不可变 scope。
- `src/renderer/lib/iris-agent-actions.ts` 多个动作先读取 store 中的 session，再跨异步边界调用 IPC；会话被后台结束或归档后，旧动作仍可能使用原 sessionId。
- main 在 `TerminalSessionManager.destroySessionNow()` 删除 session 后才广播 `sessionDestroyed`；因此删除与 renderer 收到事件之间存在明确窗口。

因此，当前错误文案过于宽泛，不能仅凭这条消息判断发生过项目切换。需要在日志中区分三种原因：`session-not-found`、`project-root-mismatch`、`project-generation-mismatch`，并记录 channel、sessionId、请求 scope、当前 scope、session scope。这样才能确认用户遇到的是会话自然结束后的迟到请求，还是 scope 状态真的漂移。

建议优先级已调整：

- [ ] 先把 `requireSessionInScope()` 拆成可诊断的三类原因，并在用户提示中把“会话已关闭/进程已退出”与“项目范围已变化”分开。
- [ ] 为 `SESSION_OUTPUT_ATTACH`、`SESSION_OUTPUT_ACK`、`SESSION_SCROLLBACK`、`SESSION_INPUT`、`SESSION_RESIZE` 增加“会话刚刚退出/销毁”的测试；特别覆盖 PTY exit 与 `sessionDestroyed` 广播之间的窗口。
- [ ] 为 Agent 的 terminal attach/replay/input/resize 及 send/stop/retry 等动作增加 session 被后台销毁后的测试。
- [ ] renderer 收到 `sessionDestroyed` 或 Agent destroyed 后，立即使对应 TerminalView/Agent action 的 transport 失效；迟到请求应静默丢弃或显示“会话已关闭”。
- [ ] 增加同 root、不同 generation 的恢复/窗口重建测试，确认 renderer 不会长期持有旧 scope。

在没有日志前，无法断言是哪一类占主导；但“未切换项目也出现”已经足以排除“只由项目切换造成”的结论，首要怀疑应转为会话退出/销毁后的迟到请求，以及错误分类过粗。
