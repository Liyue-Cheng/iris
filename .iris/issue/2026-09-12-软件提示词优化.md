## 2026-09-12 检查结果

检查范围：

- `src/main/iris-templates.ts`：软件层 canonical prompt。
- `src/main/agent/prompt.ts`：Agent 基础工具提示词。
- `src/main/agent-injection.ts`：外部 CLI 的动态上下文注入脚本及预览文本。
- 本 issue 当前收到的 `<iris-agent-base>`、`<iris-software>`、`<iris-project>`、`<iris-anchor>` 注入内容。

### 结论摘要

当前提示词不是简单地“太长”，主要问题是**边界层重复、禁止项过多且缺少触发条件、规则之间存在优先级冲突**。其中最值得优先处理的是：

1. 软件层把大量资产治理细节、文件命名和生命周期规则放在每个 Agent 每次任务都要阅读的协议中，认知成本偏高。
2. 软件层与项目层、基础 Agent 层分别重复描述“不要新建文件”“不要重读上下文”“不要触碰某些内容”等限制，但没有统一“何时适用”的条件。
3. 一些 `Do not ...` 是为了防止历史上曾经发生过的具体错误，却没有在提示词中说明触发背景，模型容易把它们理解成普遍禁令。
4. 注入层把“没有焦点”也编码成多句指令式文本；这在 hub 会话中有价值，但不应让 Agent 把“等待用户指令”误解为禁止主动完成用户随后明确提出的任务。
5. 基础 prompt 的工具契约整体清楚，但把实现细节、平台约束和版本迁移背景混在同一层；其中部分内容更适合工具 schema 或运行时错误，而不是模型提示词。

### 具体发现

#### P1：上下文读取规则重复且有潜在冲突

`<iris-software>` 同时包含：

- “如果收到 focused document/workspace snapshot，使用它作为初始上下文”；
- “如果没有 snapshot 且 `FOCUS_DOC` 存在，先读取文件”；
- 工作规则又说“如果没有上下文则等待用户指令”。

当前注入链在嵌入 Agent 中提供 `<iris-anchor>`，外部 CLI 通过 hook 提供 `<iris-focus>`；基础 Agent prompt 还告诉模型使用工具读取文件。规则虽然可以推导出正确行为，但没有明确写出优先级：**已注入快照优先；没有快照时才读取 `FOCUS_DOC`；没有焦点时不主动猜测焦点文档**。建议合并成一条条件规则，避免模型因为看到“read it first”而重复读取已经注入的全文。

#### P1：`不要新建文件`类限制应改为对象和条件，而不是笼统否定

当前软件层已经比旧版本好，限制对象是“新的 Iris 管理文档/资产”，并允许实现任务所需的源码、测试和配置文件。但仍有多处相近表达：

- 不要创建新的 workspace；
- 不要创建新的 `.iris/` 文档或资产；
- 不要写出 typed folders；
- 未经请求不要创建 vendor entry；
- 不要触碰 code directories，除非明确要求。

这些规则分别出现在不同场景，模型很难判断它们是互相独立的边界还是一个总原则。建议统一为：**未经用户请求，不创建新的 Iris 管理文档、workspace 或 companion asset；实现任务所需的代码、测试和配置文件不受此限制；写回结果时使用当前 focused document 所在 workspace。** 只有在确实存在特殊例外时，再单独说明。

这也是本次最典型的“不要 A、不要 B，但用户没有暗示 A/B”问题：禁止创建 workspace、vendor entry、asset manifest、hash registry 等，很多任务根本不会涉及这些对象。将其改成“当任务涉及 X 时，遵守 Y”比继续增加否定清单可靠。

#### P1：项目层的“方案和结果写回 issue”没有进入通用软件协议

本项目 `<iris-project>` 明确要求围绕 issue 工作时把详细方案和结果写回 issue，而软件层只规定了 issue 的历史保留方式。对于其他项目，Agent 只会把结果写在对话中。

如果这是 Iris 的产品核心行为，建议提升为软件层的一条条件规则：当 focused document 是 issue，或任务明确由某个 issue 驱动时，优先将方案、实施结果和验证证据追加到该 issue；纯咨询、用户明确要求只在聊天中回答时除外。这样比“所有结果都写回文档”更准确，也不会扩大写回范围。

#### P1：缺少“已验证 / 未验证 / 假设”的输出约束

基础 Agent prompt 规定了如何执行工具，但没有要求在最终回答中区分：

- 已经通过命令、测试或读取文件确认的事实；
- 根据代码推断但尚未验证的判断；
- 因环境、权限或用户要求没有执行的检查。

软件层也没有这一条。它会导致 Agent 很容易把“代码已修改”说成“功能已完成”。建议加入正向规则，而不是再加一个宽泛的 `Do not claim success`：**报告结果时分别列出完成内容、实际验证内容和未验证/假设内容；不要把推断写成验证事实。**

#### P2：软件层混入了过多资产治理实现细节

资产章节中的以下内容比较像实现规范或数据治理文档，而不是每次任务都必须加载的 Agent 行为规则：

- 文件名必须使用 `<sanitized-name>--<sha256-prefix>.<ext>`；
- 资产应视为 immutable，更新时写新文件；
- 一个资产只能由一个文档拥有；
- 不要增加 manifest、registry、deduplication、adoption workflow 等具体机制。

这些规则并非错误，但粒度不一致：同一提示词既规定 Agent 工作边界，又规定资产系统的内部数据模型。建议保留 Agent 必须遵守的两三条行为规则，把具体命名、索引和所有权约束移到资产工具说明、项目文档或运行时校验中。否则每次普通 issue 任务都要承担与任务无关的上下文成本。

#### P2：若干禁止项是历史补丁，缺少适用条件

例如：

- 不要添加 hash、manifest、registry、deduplication 等；
- 不要删除内部文件，即使 Markdown 引用被移除；
- 不要修改 `<iris-software>` 或 `<iris-project>`；
- 不要使用 unified patch markers；
- 不要运行交互式命令（目前主要出现在项目层/工具 guideline 中）。

其中后两类分别属于工具调用契约和当前项目工程偏好，不应与通用 PM 协议混在一起。建议按“文档协议 / 工具契约 / 当前项目偏好”分层；只有真正跨项目、跨 Agent 都成立的约束才进入软件层。

#### P2：基础 Agent prompt 中有可下沉到工具契约的内容

`src/main/agent/prompt.ts` 对 `read`、`edit`、`write`、`terminal` 的参数形状说明是必要的；但以下内容可以考虑由工具 schema、工具错误和执行器直接保证：

- `oldText` 必须唯一；
- 多个 edit 以原文件为基准匹配，不能重叠；
- terminal 的 information/operation 分类；
- timeout 上限和后台任务使用场景。

模型提示词仍可保留简短原则，但详细的失败条件由工具返回会更可靠。当前 prompt 反复使用 “must / never / do not”，如果运行时已经能校验，就无需让模型承担完整的静态校验清单。

#### P3：措辞和层级上的冗余

- Agent 基础层已说明“visible terminal command”，软件层又多次强调读取文件、项目边界和等待指令；建议基础层只负责工具契约，软件层只负责 Iris 文档协议。
- `<iris-anchor>` 的焦点文档快照由注入层提供，`FOCUS_DOC` 仍同时作为 fallback；应明确这是同一信息的两种传输方式，而不是两个需要分别处理的上下文来源。
- `report/` 的“历史文档”规则和“报告可以编辑/替换”的描述需要一个时间条件；目前模型可能只记住其中一个否定句。
- `status/` 文档的“保持与现实同步”是结果要求，但没有说明何时应该主动更新 status 文档，容易变成所有代码任务的额外扫描负担。

### 建议的修改顺序

1. **先做低风险措辞收敛**：合并上下文读取规则，统一新建文件/写回范围的条件表达，补充验证事实与未验证事项的输出规则。
2. **再做分层整理**：把工具调用细节留在 Agent/tool schema，把资产内部治理细节移出通用软件 prompt；保留跨项目真正需要的行为边界。
3. **最后再决定产品规则**：是否将“issue 方案和结果写回 issue”提升到软件层，以及是否保留资产 immutable/单一所有权等规范。两者都属于产品策略，不宜仅按“提示词冗余”直接删除。

### 当前不建议直接改动的内容

- 不建议因为看到多个 `Do not` 就机械删除。涉及删除、全局配置、用户文件和 Iris 管理文档的限制，确实承担安全与数据保留职责；应先改成带对象、条件和例外的正向表达。
- 不建议改动 `IRIS_AGENT_PROMPT_METADATA` 的 upstream 指纹或 adaptation 语义来解决软件层问题；基础 prompt 与软件 prompt 是独立层，混改会扩大兼容性风险。
- 不建议在本轮直接修改代码或同步入口文件。当前 issue 的任务是审阅和记录问题；若确认方案，再单独实施 prompt 文案及对应测试。

````
<iris-software>
This project is managed with Iris — an AI-native, document-centric PM tool.
All PM artifacts are plain markdown files under `.iris/`, in typed folders.
The rules below are Iris's invariant protocol: they ship with the app and do
not vary per project. Optional user-authored project guidance lives in the
entry files' `<iris-project>` block.

## Folder semantics

Iris documents live in `.iris/status/`, `.iris/issue/`, `.iris/report/`, or
`.iris/misc/` folders. Work in the workspace containing the focused document.
Treat documents under `report/` as historical unless the user asks to change them.

- `status/` — Current state of the codebase — keep it in sync with reality.
- `issue/` — Things to do, bugs, and open questions. Preserve issue history by
  default and append updates; if the user explicitly asks to reorganize,
  rewrite, or remove content, follow that request. Mark resolved via `status:`;
  never delete the file without the user's request.
- `report/` — Dated analyses, reviews, and summaries. Edit or replace them as
  the user requests.
- `misc/` — Human scratch space. Do not touch unless asked.

## Document assets

Each Markdown document may have a sibling `<name>.assets/` directory. Files
inside that directory are internal document files and may be referenced with
ordinary relative Markdown links such as `./<name>.assets/image.png`.

The same directory may contain a `links.txt` file. Each non-empty line is an
external file or directory associated with the document; these paths are shown
separately from internal files and are not copied or deleted by Iris.

That is the complete asset model. Do not add hashes, manifests, registries,
deduplication, managed/unmanaged labels, orphan cleanup, adoption workflows,
or other asset governance. Do not delete an internal file merely because its
Markdown reference was removed. When a document is deleted, its companion
directory goes with it; external association targets remain untouched.

## What the app parses

Frontmatter keys are read literally — use exactly these (unknown keys are
ignored, and a misspelled key silently drops the field):

- `title:` — display title; falls back to the filename when absent.
- `status:` — drives the issue/report lenses and uses the state machine below.

The `labels:` frontmatter field is reserved and is not currently enabled.
Do not add, populate, edit, normalize, or remove it unless the user explicitly
asks to repair or migrate existing label metadata. Preserve an existing valid
`labels:` field verbatim.

A new issue starts as (a report starts with `status: Active`; a status doc
does not require a status field):

```
---
title: <short title>
status: Todo
---
```

The stored `status:` value is also the displayed value; write canonical values
exactly as shown unless reality requires an exceptional value.

- Issues normally move from `Todo` to `In Progress` and then
  `In Review`. `Blocked`, `On Hold`,
  `Done`, and `Canceled` are also supported states.
- Reports: `Active` / `Backlog`.

Do not mark an issue `Done`, `Canceled`, or `On Hold` unless the user asks.
You may move an issue to `In Review` when the work is ready for review.

The app also collects every GFM task checkbox (`- [ ] …`) across `.iris/`
docs into a todo panel, where the user tracks open items and checks them
off. Anything that awaits someone's action — acceptance checks, things for
the user to verify or decide, follow-ups — must be written as task
checkboxes, one per discrete item, never as prose or plain bullets: a
pending item written as prose is invisible to the panel.

## How context reaches you

If Iris provides a focused document or workspace snapshot, use it as the
initial context. If no snapshot is provided and `FOCUS_DOC` is available, read
that document first. Do not reread unchanged injected context.

## Working rules (invariant)

1. **Focus protocol.** Use the provided focused document or workspace context.
   If none is provided and `$FOCUS_DOC` is set, read that document first.
   Loading context is not a task; wait for the user's instruction.
2. **Write-back scope.** Write results beside the focused document, within its
   existing `.iris/` workspace. Do not create a new workspace unless asked.
3. **No unsolicited Iris-managed files.** Do not create new `.iris/` documents
   or assets unless the user asks. For an explicitly requested implementation
   task, you may create the required source, test, and configuration files.
   You may edit the focused document and its frontmatter.
4. **Naming.** New files in `issue/` and `report/` use a `YYYY-MM-DD-<slug>`
   prefix.
5. **Off-limits.** Never modify the `<iris-software>` or `<iris-project>`
   blocks. Never write outside typed
   folders. Never touch code directories unless explicitly asked.

Write standard Markdown and preserve the document's existing formatting where
practical. Follow the entry file's `<iris-project>` block when it contains
user guidance, unless it conflicts with this software protocol.
</iris-software>
````

### 4. 动态注入（hook 腿）

canonical：`src/main/agent-injection.ts` → `FOCUS_CONTEXT_SCRIPT`，2519 字符。写成 `~/.iris/focus-context.ps1`（UTF-8 BOM），作为 SessionStart hook 的文本 payload 交给外部 CLI。

````
# Iris focus-context (machine layer, generated by Iris — editing is fine)
# SessionStart-hook payload: reads FOCUS_DOC or IRIS_WORKSPACE_PATH (set by
# Iris when spawning a terminal) and inlines dynamic context.
[Console]::OutputEncoding = [System.Text.Encoding]::UTF8
$focus = $env:FOCUS_DOC
$workspace = $env:IRIS_WORKSPACE_PATH
if (-not $focus -and -not $workspace) { exit 0 }
$root = (Get-Location).Path

# Keep the first character non-JSON: Codex otherwise treats a leading '[' as
# a JSON array and reports "invalid session start JSON" instead of using text.
if ($focus) {
  Write-Output ('Iris: This terminal was started by Iris; project root: ' + $root + '; focused document: ' + $focus)
} else {
  Write-Output ('Iris: This terminal was started by Iris; project root: ' + $root + '; workspace: ' + $workspace)
  Write-Output ('<iris-workspace path="' + $workspace + '">')
  if ($workspace -eq '.iris') {
    Write-Output 'This is a project-root hub session. It was opened from the project root and is not focused on any document. FOCUS_DOC is unset, and no actual <iris-focus> block is injected. Do not read or infer a focused document; wait for the user''s instruction.'
  } else {
    Write-Output ('This is a workspace hub session opened from ' + $workspace + '. It is not focused on any document. FOCUS_DOC is unset, and no actual <iris-focus> block is injected. Do not read or infer a focused document; wait for the user''s instruction.')
  }
  Write-Output '</iris-workspace>'
}
````

### 11. `IRIS_WORKSPACE_PATH` 是否可以由 `FOCUS_DOC` 替代

结论：在当前模型下不能完全替代，但它只对 workspace hub 会话有必要。

- 文档会话设置 `FOCUS_DOC`，值为文档路径；
- workspace hub 会话清除 `FOCUS_DOC`，改设置 `IRIS_WORKSPACE_PATH`，值可能是 `.iris` 或 `.iris/areas/<name>`；
- hub 没有被选中的文档，因此不存在可供 `FOCUS_DOC` 表达的路径。

如果强行只保留 `FOCUS_DOC`，需要约定特殊哨兵值（例如 `.iris`），或者让 Agent 从当前工作目录推断 workspace。这两种方式都会把“文档路径”和“workspace 路径”混成一个字段，增加歧义，也无法清楚表达“当前 workspace 下没有焦点文档”。
