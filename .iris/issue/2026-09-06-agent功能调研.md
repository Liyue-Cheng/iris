现在agent的功能，是否还有明显的缺口？，你全部检查一遍

## 全面检查结论（2026-09-06）

有，而且不只是后续增强项。当前 Agent 已具备 Session 持久化、严格串行执行、Stop/Continue、
Provider/Profile、四类工具、可见 PTY、长命令监督、Fork、文件 Rewind、Context artifact 和
基础 compaction 等主体骨架，但还不能视为功能闭环或具备自举准入资格。

本轮检查覆盖：

* `src/main/agent/` 全部运行时模块及其测试；
* Worker 协议、Worker host 与 `agent-worker.ts`；
* Provider/Profile、模型目录、Prompt/Context、compaction；
* ToolHost、PTY、终端监督与输出回放；
* Session store、事件日志、重启恢复、Fork、Rewind；
* Renderer store、IPC/action、Agent 页面、设置页和右栏 Session 投影；
* 现有 Agent 产品规范、架构 issue、compact issue 与当前未完成项；
* 类型检查、Agent 定向测试、全量单线程测试、Worker 检查和 diff 检查。

结论按优先级如下。

| 优先级 | 结论 | 性质 |
| --- | --- | --- |
| P0 | 当前工作树不能通过类型检查，Agent 页面本身有重复 JSX 属性、缺失必填属性和未使用参数 | 交付阻断 |
| P0 | ToolHost 可通过“项目内目录符号链接的后代路径”读取项目外文件，并可把 terminal cwd / mkdir 引到项目外 | 安全边界 |
| P0 | 自定义 Provider API Key 被完整返回 Renderer，且输入框使用明文 `type="text"` | 凭据泄露 |
| P1 | 模型级 compact 配置没有真正接入运行时，现有 compaction 回归已有 2 项稳定失败 | 核心语义失效 |
| P1 | 模型目录的自动加载与显式刷新语义相反：空目录会被 Agent 页面隐式请求，已有目录又无法真正远端刷新 | 配置链路断裂 |
| P1 | 上下文预算漏算 system/software/project/anchor/tool schema，且没有 overflow 后自动 compact 重试 | 长会话可靠性 |
| P1 | Agent Terminal 没有输出配额和背压，“完整输出”实际上只回放最后 5000 行 | 资源与审计风险 |
| P1 | Rewind 只有“最新 Intent + 文件”一种操作，中途写入失败后不能按设计继续剩余恢复 | 数据一致性 |
| P1 | `agent:worker-check` 已落后于 protocol v14，当前固定等待 60 秒后超时 | 发布门禁失效 |
| P2 | Stop、终止命令、结束运行仍被合并；缺少重命名、归档、搜索和 lineage 详情 | 生命周期缺口 |
| P2 | Context Inspector、usage/cost/retry/correlation、compaction 状态与摘要边界未形成 UI 闭环 | 可观测性缺口 |
| P2 | ToolHost 没有表达“用户已明确授权创建新 `.iris` 文档”的能力，实际上一律拒绝创建 | PM 工作流缺口 |
| P2 | Agent 页面和右栏入口大量硬编码中文，英文界面不会完整切换 | 国际化缺口 |

## 确定性问题与证据

### 1. 当前代码门禁失败

`npm run typecheck` 失败。Agent 页面至少包含以下确定性错误：

* `IrisAgentView.tsx` 多处重复 `aria-label`；
* `CardFrame` 已要求 `title`，四类调用方仍传 `aria-label`，导致必填属性缺失；
* `CompactRowStateIcon.detail` 声明后未使用；
* 同一工作树中的 Terminal、通知、Tooltip 等 UI 改动还有额外类型错误。

Agent 定向单线程测试执行 15 个文件、117 项，115 项通过、2 项失败；失败均在
`session-manager.test.ts` 的 context compaction，摘要器从未被调用。

全量单线程测试还确认：

* 上述 2 项 compaction 失败稳定复现；
* `no-native-title.test.ts` 发现设置页新增 3 处原生 `title`；
* `session-viewport.test.ts` 仍有 1 项既有 window mock 失败。

`git diff --check` 通过。按项目约束没有运行 build、dist、开发服务器或截图。

### 2. ToolHost 的祖先符号链接逃逸

`tool-host.ts:298-305` 只对最终路径执行 `lstat`；当 `project/link` 是指向项目外的目录链接，
`project/link/file` 本身不是 symlink，因而只通过词法路径检查后直接访问。影响范围包括：

* `read/access` 可读取或探测项目外文件；
* terminal 的 cwd 可以落到项目外；
* `mkdir({ recursive: true })` 可以在项目外创建目录；
* 现有 ToolHost 测试没有目录链接后代、junction 和 terminal cwd 逃逸用例。

普通文档读写已经有对应目录链接回归测试，Agent ToolHost 没有复用同一真实路径边界。

### 3. Provider 凭据进入 Renderer

这不是潜在风险，而是当前显式契约：

* `IrisAgentProviderProfileInfo` 暴露 `apiKey: string`；
* `profilesForRenderer()` 原样返回 `profile.apiKey`；
* `pi-adapter.test.ts` 明确断言 catalog 中包含完整 secret；
* 设置页新建 Profile 使用 `type="text"`，密钥在屏幕上明文展示；
* Profile 文件也以明文 JSON 保存于 app data，尚无系统凭据存储或威胁模型结论。

这与产品规范“凭据不进入 Renderer、Context Inspector 和普通日志”的边界直接冲突。

### 4. 模型级 context/compact 配置只是存下来了，没有生效

`IrisAgentConfiguredModel` 保存了 `reserveOutputTokens`、`keepRecentTokens` 和
`compactTrigger`，但模型目录投影从未构造 `IrisAgentModelOption.contextPolicy`；全仓只有类型、
Agent 页面读取点和 Session manager 读取点，没有任何赋值点。

另外：

* `session-manager.ts:1663-1673` 完全没有读取 `compactTrigger`；
* runtime 最多把 `maxOutputTokens` 当成 reserve，用户设置的 reserve/keep/trigger 均丢失；
* 一旦 catalog 找到当前模型，测试注入的 `compactionThresholds` 也被忽略，导致现有 2 项回归失败；
* Agent 顶部展示的整理水位是重新推导的默认值，不一定是用户保存值。

因此 compact issue 中“当前模型策略已接入”的实现记录与当前代码事实不一致。

### 5. 模型目录发现流程方向反了

`loadIrisModelCatalog()` 对 Profile 的规则是：有已保存 models 就直接使用，只有空 models 才请求
远端目录。设置页“从供应商获取模型”按钮又调用同一个函数，造成：

* 新建空 Profile 后，Agent 页面自动刷新模型时会隐式请求远端目录，违背“仅设置页显式请求”；
* Profile 一旦保存过模型，点击“从供应商获取模型”不会请求远端，只会重新导入旧列表；
* 对已有列表执行该操作还会把手工 source、reserve、keepRecent 等策略重置为默认值；
* 远端目录固定 1 秒超时，对真实公网和代理环境过于激进。

当前缺少“目录 fetch”与“运行时 catalog projection”两个独立 API，因此无法可靠刷新或合并。

### 6. Context 预算与 compaction 仍不闭环

阈值预检 `session-manager.ts:424-435` 只计算历史消息和待发送文本，漏掉：

* Pi system prompt；
* Iris software prompt 与 project prompt；
* 当前 anchor 内容及 diff；
* tools schema 和 Provider 固定开销。

长 Issue、长项目规则或工具 schema 本身就可能使请求超窗，但当前预检仍会判断“不需要整理”。
Provider 真正返回 context overflow 后只会进入 paused；`overflow` 虽然存在于类型中，没有任何调用点。

其余已确认缺口：

* `compact()` 已在 manager 实现，但没有 IPC channel、Renderer action 或 UI 入口；
* Context bundle 仍把 `compaction` 固定写成 `disabled`，即使实际请求使用了摘要；
* 没有 compaction artifact、timeline divider、进度/失败恢复或真实用量水位；
* Agent 基础提示词既作为 Pi system prompt 注入，又完整包含在每次 `<iris-agent-base>` 用户消息中，
  仍存在方法层重复注入和 token 浪费；
* 摘要调用本身没有超长历史分块策略，最需要 compact 时也可能先因摘要请求超窗而失败。

### 7. Terminal 的“完整真实输出”与资源边界未实现

`AgentCommandPty` 将每个 chunk 无上限追加到文件，同时为每个 chunk 直接广播 Renderer；没有
高/低水位 ACK、软配额、硬上限或 `OutputLimitExceeded`。磁盘较慢时，`outputChain` 还会持续持有
等待写入的 Buffer。

回放也不是完整输出：

* live replay 只序列化 `TerminalMirror(..., 5000)` 的最后 5000 行；
* completed replay 先把整个 artifact 一次性读入内存，再同样只序列化最后 5000 行；
* 大文件既有主进程内存峰值，又无法从第一个字节查看。

因此高输出命令既可能压垮 IPC/内存/磁盘，也无法满足当前产品规范的事实审计承诺。

### 8. Rewind 交互和部分失败恢复不足

当前顶部按钮只能回退最新 Intent，并固定尝试回滚文件。没有“仅对话 / 对话和文件”选择、目标节点、
消息范围、文件清单、冲突预览和不支持副作用说明。

Store 会先预检全部文件再逐个写回，这是好的；但逐个写回中途失败时没有持久化进度。重试时，已经恢复的
第一个文件不再匹配 `afterSha256`，会立即被当成外部冲突，无法识别“已恢复”并继续剩余文件。这与既定的
可重试部分恢复语义不一致。

### 9. Worker 发布检查脚本已经失真

`npm run agent:worker-check` 当前等待 60 秒后报 `agent worker check timed out`。脚本仍把 model 与
providerProxy 放入 initialize runtime，并仍期待 ready 事件返回 model；protocol v14 已把两者移到
run/resume。因此 Worker 拒绝旧 initialize，脚本又忽略非 ready 消息，直到超时。

这意味着当前发布门禁不能证明编译后的 Worker 与源码协议一致，也会无意义地拖慢失败反馈。

## 尚未形成产品闭环的能力

### Session 与运行控制

* 关闭 Agent Session 直接删除本地历史和 artifacts；尚无重命名、结束运行、归档/取消归档和搜索；
* 页面只有一个 Stop，监督警报中的“终止命令”也调用同一个 Session Stop；provider 生成取消、PTY
  interrupt、结束本轮和删除 Session 还没有独立语义；
* Fork 输入按钮的投影仍固定 `canForkFromInput: true`，运行中也显示，点击后才被后端 quiescent
  校验拒绝；
* lineage 只保存 parent/forkedFrom 字段，没有用户可见详情。

### 可观测性

* 当前“查看上下文”只是打开本地 artifact 文件，不是 Context Inspector；
* Provider response usage/cost 没有作为一等事实持久化，Attempt 只保存状态、时间和错误；
* supervision usage 只保存在 manager 内存数组，没有落盘或诊断入口；
* 默认 UI 看不到 retry 链、实际模型/API、token、裁剪、摘要来源、工具 correlation ID；
* `selfHostingEligible` 仍硬编码为 `false`。

### Iris 文档工作流与多语言

ToolHost 遇到新 `.iris` 文件一律抛出“没有明确用户请求”，但协议和 correlation 中没有任何字段可以
表示“本次确有用户明确授权”。所以即使用户明确要求创建 issue/report，Agent 也做不到。反方向上，
对已有 `misc/` 等路径也没有 ToolHost 级授权区分，仍主要依赖提示词自律。

Agent 页面、错误标题、状态、按钮、终端卡片和右栏“用 Iris Agent 打开”等仍大量硬编码中文，未接入
现有 i18n catalog；英文模式只能翻译设置页的一部分。

## 已确认可用的底座

本轮没有否定已经落地的主体结构。以下能力有实现和较完整自动化覆盖：

* main 持有 canonical Session aggregate，Renderer 使用 revisioned snapshot/patch 投影；
* 单 Session 命令队列、Worker epoch、durable event ACK 和崩溃/重启暂停恢复；
* Tool call 与已提交 assistant、Invoke、Turn 的 correlation 门禁；
* Provider/Profile 多实例和模型切换基本路径；
* read/edit/write/terminal 四工具、文件 Effect artifact 和 CAS 预检；
* 3 秒 Terminal reveal、PTY 输入事实、终端监督、Stop/Continue；
* Reply Fork、Input Fork、artifact 复制和当前 Trace/Context 分离；
* 文档空输入“直接开始”的主进程规则与自动化测试。

这些底座说明下一步应以补齐边界和闭环为主，不需要推倒重做现有 Session 架构。

## 本轮边界

本轮是调研与代码审查，没有修改产品源码。没有真实 API 凭据，因此没有发起真实 Provider 请求；也没有

## 需求调整（2026-09-06）

用户确认第一版暂不为任何 Agent 工具提供项目边界、symlink/junction 或 `.iris` 文档创建防护，允许
`read`、`edit`、`write`、`terminal` 读取、写入和启动任意绝对路径。因此本轮原先针对 ToolHost 的
路径逃逸修复已按产品约束撤回；对应测试改为验证所有工具均可跟随 junction 后代。后续安全范围需
单独变更协议、提示词和验收标准。

眼睛按钮需求已落地：新增 Profile Key 与已有 Profile 的替换 Key 默认以密码框显示，用户点击眼睛按钮后
才切换为明文，且 Renderer DTO 仍只携带 `hasCredential`，不会回显已保存 Key。

## P1 实施结果：请求预算与 overflow 重试（2026-09-06）

* `compactForThreshold` 现在基于组装后的完整 prompt、持久化历史以及四类工具 schema 的保守固定预算进行预检；模型的 `contextWindow`、`reserveTokens` 和 `compactTrigger` 仍决定触发水位。预检不会把 prompt 内容写入 Session Trace。
* 新增 `estimateAgentRequestTokens` 和 `isAgentContextOverflowError` 纯函数及回归测试。只有明确的 context length/window、maximum context、token limit、prompt too long 等 provider 错误才进入自动恢复，网络、认证和普通运行时错误不会误触发。
* `AgentIntent.contextOverflowRetries` 持久化记录自动恢复次数并兼容旧聚合。第一次 overflow 会先关闭旧 Worker，压缩已完成 Intent，保留同一 Intent 和请求内容，重建 prompt/history 后重新发送一次；旧 Worker 的迟到事件因 worker epoch 变化被丢弃。第二次 overflow 或没有可压缩边界时按普通暂停处理，不会创建新 Intent 或无限重试。
