有的时候会出现一个很奇怪的问题：\
整个软件的IME 焦点都会有问题，就是，粘贴一段文字到终端之后，终端就无法接受任何IME事件了，只能输入英文，然后我点击新建issue的之后，文本框也是无法点击、无法打字，你现在进行全面检查

---

## 检查结论（IME 全局卡死，2026-06-25）

排查范围：终端粘贴链路、xterm IME workaround、焦点协调器、Radix 弹窗。
未改代码，先出结论待裁决。下面每条带 `文件:行` 证据。

### 一句话根因

这**不是**应用层把 `document.body` 设成 `pointer-events:none` 那类问题——
你能点开"新建 issue"按钮，说明 body 没被整体锁死。真正的现象是
**Chromium / Windows 的窗口级 IME 输入上下文（IMM32/TSF）被弄到了非法状态**：
一旦它在终端的 helper-textarea 上"卡住"，整个 BrowserWindow 的 IME 就全废，
直到窗口失焦再获焦（Alt-Tab 切走再切回）才恢复。新开的 React `<input autoFocus>`
拿到了 DOM 焦点却得不到可用的输入法上下文，于是表现为"点不动、打不了字"。
所以症状是**全局**的，不是终端局部的。

触发它的，是终端这边三个**可证的代码缺陷**——按嫌疑排序：

### 缺陷 A（最可疑）— compositionend 清理器与下一次输入竞态

`ime-textarea-workaround.ts` 在每次 `compositionend` 后延迟 16ms 执行
`textarea.value = ''`（`ime-textarea-workaround.ts:53-61`）。它**只在新的
`compositionend` 到来时取消上一个待定清空**（`:54-55`），却**不监听
`compositionstart`**——只挂了 compositionend（`:63`）。

- 后果：用户快速连续打字（中文 IME 自动上屏后立刻接着拼下一个词）时，
  下一次 `compositionstart` 会落在这 16ms 窗口内，但待定的清空**不会被取消**。
  16ms 一到，`textarea.value=''` 就在**一次正在进行的合成中途**执行。
- 在 Windows 上，**合成期间程序化改写 textarea.value 会让 IMM/TSF 失同步**：
  当前合成被静默中止、**不再触发 `compositionend`**，输入法上下文进入坏态。
- xterm 自身状态机也跟着坏：`_isComposing` / `_isSendingComposition`
  停在错误值后，`keydown` 分支会持续吞掉 IME 相关键（xterm `compositionHelper`
  在 `_isComposing||_isSendingComposition` 时对 keyCode 229/20/16/17/18 一律
  return false）——这正对应"只能输入英文"。

### 缺陷 B — 位置锁 `locked` 永不复位（放大 A 的后果）

`ime-composition-position-lock.ts` 在 `compositionstart` 置 `locked`、**只在
`compositionend` 清 `locked`**（`:54-59`，监听器只有 start/end 两个 `:61-62`）。

- 一旦发生缺陷 A（合成被 `value=''` 中止、没有 compositionend），`locked`
  **永远停留为非 null**。
- 此后每次 `updateCompositionElements()`(xterm 在每帧 `onRender` 和每次
  compositionstart 都会调用它) 都走"锁定"分支，把 `bufferService.buffer.x/y`
  替换成早已过期的快照（`:68-84`）。候选框/合成框被钉死在过期单元格，
  叠加已经坏掉的 IMM 上下文，候选窗根本起不来 → "无法接受任何 IME 事件"。
- 且**不会自愈**：直到切会话把整个终端重挂（`term.dispose`）才清。

### 缺陷 C — 粘贴路径用原生 `window.confirm`（次要触发点）

`TerminalView.pasteText` 在三种情况弹**原生** `window.confirm`：>1MB
（`TerminalView.tsx:162`）、含 ESC 控制符（`:171`）、非 bracketed 多行
（`:185`）。原生模态会**阻塞渲染进程事件循环**；在 Windows Electron 上，
原生弹窗夺取/归还焦点时，**IME 上下文常常不会正确还给原元素**，关掉弹窗后
textarea 看似 focused 却失去输入法上下文。

- 这正好解释"粘贴**一段**文字后 IME 死"——当这段文字是粘进非 bracketed
  shell 的多行、或含 ESC 时，必弹这个原生框。
- 终端复制粘贴 issue 自己也标注过这是临时手段（"Iris 还没有 Modal 基建，
  等有了再换"，见 `2026-06-12-终端复制粘贴.md` 末「有意偏差 2」）。
  现在 `CreateDocDialog` 已经用上 Radix `Dialog`，Modal 基建其实已具备。

### 为什么会蔓延到"新建 issue 的文本框"

见"一句话根因"：A/B/C 任一把窗口级 IMM/TSF 上下文弄坏后，坏态是**整个
BrowserWindow 级**的，与你之后点哪个 DOM 元素无关。`CreateDocDialog` 的
`<Input autoFocus>`（`CreateDocDialog.tsx:93-99`）拿到 DOM 焦点但没有可用
输入法——于是"点不动、打不了字"。它只是受害者，不是第二个 bug。

### 建议修复（待你拍板，未实现）

- **A**：清理器同时监听 `compositionstart`，并在"当前正在合成"时**不执行/
  改期**那次 `value=''`——绝不在合成进行中改写 value。低风险、最高收益。
- **B**：`locked` 增加兜底复位——监听 textarea `blur` 时清 `locked`；
  并让 patchedUpdate 以"是否真的在合成"为准（与 A 共享一个 composing 标志），
  而非仅靠 compositionend 这一条出路。低风险。
- **C**：把粘贴路径三处 `window.confirm` 换成应用内 Radix `Dialog`
  （基建已就绪），消除原生模态对 IME 上下文的破坏。中等工作量。
- **诊断**：先加一行日志（compositionstart/end 配对计数 + 每次 `value=''`
  时是否 `isComposing`），在你机器上**实锤**到底是 A 还是 C 先发——因为这个
  卡死只在 Windows + 真实 IME 下复现，我无法在此环境重放。

## 缺陷 C 修复记录（2026-06-25）

用户反馈：目前**只有 C 稳定复现**，先修 C。已实现，门禁全过
（typecheck + 65 单测 + build），代码未提交，待手工验收。A/B 暂未动。

### 改动

- **新增** `src/renderer/components/ui/confirm-dialog.tsx` —— 基于 Promise 的
  应用内确认弹窗：`confirmDialog(opts): Promise<boolean>` + 单例 `<ConfirmDialog/>`。
  走 Radix `Dialog`（in-DOM React），不再触碰原生模态，从根上消除"原生
  confirm 阻塞渲染进程 + 不归还 IME 上下文"的隐患。
- **改** `src/renderer/App.tsx` —— 在 `CreateDocDialog`/`DeleteDocDialog` 旁
  挂载一个 `<ConfirmDialog/>`。
- **改** `src/renderer/components/terminal/TerminalView.tsx` —— 把粘贴路径
  三处 `window.confirm`（>1MB / 含 ESC / 非 bracketed 多行）改为
  `await confirmDialog(...)`；**顺带**把同属一类隐患的文件拖入确认
  （shell 元字符）也一并换掉——这是终端内最后一个原生 confirm。
  另加一处守卫：确认弹窗打开期间若发生切会话（term 被 dispose），
  `termRef.current !== term` 时不再向过期终端 paste。

### 说明 / 边界

- 这是把"终端复制粘贴"issue 末尾标注的临时手段（"等有 Modal 基建再换"）
  正式还掉。基建用的就是 `CreateDocDialog` 同款 Radix `Dialog`。
- C 修掉后，由"粘贴多行/含 ESC/大粘贴/拖入危险路径"触发的那条 IME 卡死路径
  应当消失。**但 A/B（终端内 IME 合成竞态）仍在**——若你不经粘贴、纯靠中文
  连续快打也能复现卡死，那是 A/B，需另修。
