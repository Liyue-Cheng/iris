title: 开发版与安装版实例隔离
status: Done
---

要在安装版 Iris 照常运行的同时，用 `npm run dev` 调开发版，两者完全隔离、互不影响（独立的单实例锁 + 独立的 userData / 配置 / 会话 / Chromium cache）。

**这不止是开发便利问题。** 它是《2026-06-21-终端切换偶发空白未加载》那一长串「零负载也固定卡几秒」排查始终查不出的**隐藏根因**：dev 进程从没活下来，`npm run dev` 看到的一直是安装版旧构建，于是历轮针对终端的修复**改了源码却从没被执行**——每次都像「修了还卡」，被反复证伪、推翻、回退。修好隔离、dev 真正跑上当前源码后，卡顿全部消失（见下文「结论」）。

## 现象

安装版 Iris 在运行时，`npm run dev` 起的开发版窗口不出现，看到的仍是安装版（旧构建，性能监视器只有 4 个 tab，缺「终端事件」）。在运行窗口的 DevTools 里：

```js
location.href
// → 'file:///C:/Users/liyue/AppData/Local/Programs/Iris/resources/app.asar/out/renderer/index.html'
```

即这个窗口是**安装版**（`AppData\Local\Programs\Iris` 安装目录、`file://` 加载 asar 内的压缩 bundle）。结果：改了源码、反复重启 dev 也看不到新代码——因为 dev 进程根本没活下来。

## 根因：锁与 userData 的时序错配

- `index.ts:28` 在进程极早期调用 `app.requestSingleInstanceLock()` 抢锁。Electron 的单实例锁按 **userData 目录**派生。
- 给 dev 独立 userData 的代码 `app.setPath('userData', '${userData}-dev')` 却在 `app-main.ts:53-55`，而 `app-main.ts` **只有抢到锁的赢家才会动态 import**（`index.ts:41`）。
- 于是抢锁发生在 `-dev` 覆盖**之前**，用的是共享的默认 userData。dev 与安装版共用同一把锁：安装版在跑时，`npm run dev` 抢锁失败 → 把 argv 转发给安装版（触发其 `second-instance` → 开新窗口）→ dev 进程 `app.exit(0)` 自己退出。用户看到的「dev 窗口」其实是安装版开出来的窗口。
- `app-main.ts` 原注释里「independent locks」的说法因此不成立——userData 最终是分开了，但**锁**没分开（锁早在覆盖前就抢了）。

## 修复

把 dev 的 userData 覆盖提前到 `index.ts` 抢锁**之前**：

- `index.ts`：在 `requestSingleInstanceLock()` 之前，若 `process.env.ELECTRON_RENDERER_URL`（electron-vite 注入的 dev 标志）则 `app.setPath('userData', '${userData}-dev')`。入口仍只依赖 `electron`，保持轻量（不破坏 loser 不加载 native backend 的设计）。
- `app-main.ts`：删除原来过晚、且会与 index.ts 叠加成 `-dev-dev` 的 `if (isDev) setPath` 块，留指针注释。

效果：dev 的锁、配置、会话、Chromium cache 全部走 `…-dev` 独立 profile，安装版与开发版可同时各开各的、互不影响。

## 结论：卡顿消失，反证此前的终端修复本就有效

dev 与安装版隔离后，`npm run dev` 第一次真正运行当前源码。用户实测：**之前所有的终端卡顿 / 切换空白全部消失。**

这反过来说明：

- 《2026-06-21》里历轮被「实测仍卡」证伪、随后回退的终端修复（保活脚手架、empty-string fence 回调修复、failsafe 调参……）**本身大概率是有效的**——它们「没生效」只是因为**代码根本没在跑**，dev 一直加载安装版 asar 里的旧 bundle。
- 「零负载也固定卡几秒」之所以诡异、所有性能 / 并发 / 负载方向都对不上，是因为现象根本不来自被排查的那份源码，而来自一个**谁都没在跑的旧构建**——典型的「在错的二进制上 debug」。

教训：**改完先确认跑的是改后的码**（dev 窗口 `location.href` 应为 `http://localhost:...`，而非 `file://...app.asar`），再谈现象是否复现。否则一切排查都建立在未被执行的源码上。
