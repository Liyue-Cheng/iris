## 2026-08-08 代码核查结论

结论：用户的判断成立。当前页面把三类不同性质的东西混在了一起：

1. “用 X 打开”的启动器清单，是用户拥有的有序偏好。
2. Iris 对已知 CLI 的 hook 适配能力，是 App 拥有的机器级能力目录。
3. 某台机器上 hook 是否已经配置，是探测得出的运行环境状态。

其中只有第一类应该让用户增删改排；第二类应由代码定义；第三类只能展示和执行
“配置 / 更新”动作。现在逐个 agent 暴露的 `hook / flag / none` 选择跨越了这三层，
但并不控制实际运行，所以应该删除。

### 现状证据

- `AgentConfig.injection` 在类型注释中已经明确标为 `informational`。它只在设置页显示、
  保存和校验，没有进入会话启动决策。
- `SessionManager.createSession()` 实际只按 `agentId` 找到配置，再消费 `command` 和
  `onExit`。所有文档会话都会设置 `FOCUS_DOC`，所有 hub 会话都会设置
  `IRIS_WORKSPACE_PATH`，与 `injection` 值无关。
- hook 也是独立的机器级链路：`agent-injection.ts` 固定探测 Claude、Codex、Gemini、
  Qwen、Cursor 五家配置；App 启动时自动维护 `focus-context.ps1`，用户确认后才写各家
  CLI 配置。这条链路不读取 `settings.agents`。
- 因此把某一行从 `hook` 切到 `none` 不会卸载 hook，也不会阻止 CLI 执行已经配置的
  hook；反过来选择 `hook` 也不会自动安装 hook。当前控件给出了错误的因果暗示。
- `flag` 同样没有独立语义。Aider 和 Goose 是否带上下文，只由预设写入的命令字符串
  决定；把字段从 `flag` 改成 `none` 不会改变命令。
- 出厂设置只保存 Claude、Codex、Gemini、Terminal 四项。设置页另有 8 个快捷预设，
  但没有“自定义添加”，`id` 也不可编辑，所以用户只能添加代码预先认识的工具。
- 设置合并会整数组替换 `agents`。这是保存用户显式清单的正确语义，却意味着升级版本
  新增默认项永远不会进入老用户配置；仓库里的 `migrate-agents.mjs` 只是一次性补丁，
  不能作为长期产品机制。
- 快捷预设和 hook 适配目录目前是两份硬编码清单，数量分别是 8 和 5；默认清单又是
  第三份。Pi 已有调研结论但尚未进入预设。继续这样扩展必然反复漂移。
- “用 X 打开”当前主要出现在右栏空态、右栏新会话菜单和 workspace 的 `+` 菜单。
  它们都直接遍历完整数组。启动器一多，空态会变成很长的按钮墙，菜单也没有搜索、
  高度上限或统一的长列表行为。

## 治理目标

建立一个简单且可解释的产品契约：

> 用户只管理“我要用哪些命令打开”；Iris 负责判断“这个 CLI 有没有可用的零轮次
> hook”；无 hook 或 hook 未配置时，始终按同一套静态入口文件加环境变量协议回退。

hook 是可选加速器，不是正确性的开关。启动器配置不声称能够启用或禁用 CLI 自己的
hook，也不为同一事实保存第二份状态。

## 目标数据模型

### 1. 用户层：Launchers

沿用 `settings.agents` 可减少迁移面，但在产品和代码命名中把它解释为 launcher list。
每项只保留真正参与启动的字段：

```ts
interface AgentLauncher {
  id: string; // Iris 生成的稳定内部 ID，不要求等于 CLI 名
  label: string;
  command: string; // 空字符串表示普通终端
  onExit?: 'keep-shell' | 'close';
}
```

- 删除 `injection`，不增加等价的 `contextMode`、`provider` 或布尔开关。
- `id` 对用户隐藏，由 Iris 生成并保持稳定；同一 CLI 可以有多个启动器，例如两个
  Codex profile，而不会发生 ID 冲突。
- 清单有顺序，所有启动入口使用同一顺序。至少保留一项，避免新会话入口完全失效。
- preset 只是创建启动器的模板，不是白名单，也不在保存后持续接管用户字段。
- CLI 特有 flag 直接属于 `command`。如果预设需要 flag，由预设填入命令；Iris 不再
  额外保存一个不会执行的“flag 注入”状态。

### 2. App 层：Preset catalog

维护一个代码拥有的预设目录，首批包含 Claude、Codex、Gemini、Qwen、Cursor、Pi、
Aider、Goose 和 Terminal。每个预设只提供展示名、默认命令和退出行为，可附带命令
探测信息，但不进入用户设置 schema。

新增预设会自然出现在所有版本用户的“添加启动器”面板中，不再修改已有清单，也不再
需要一次性迁移脚本。用户删除过的项不会在升级时被偷偷加回。

### 3. App 层：Context adapter registry

单独维护 hook adapter registry。每个 adapter 明确定义 vendor ID、CLI 探测方式、配置
路径、配置读写器、SessionStart 事件形状、确认文案和验证能力。它不从 launcher 清单
生成，也不要求用户先添加对应启动器。

当前五家看似共享 JSON 结构，仍应以独立 adapter 表达各自契约，避免以后继续把配置
路径不同误认为运行时行为相同。Pi、Aider、Goose 等没有受支持 SessionStart hook 的
工具不进入 registry；这不影响它们成为一等启动器。

## 统一运行契约

每次从 Iris 启动会话都执行同一条基础流程：

```text
选择 launcher
  -> cwd 固定为项目根
  -> 文档会话设置 FOCUS_DOC
     或 hub 会话设置 IRIS_WORKSPACE_PATH
  -> 执行 launcher.command
  -> CLI 若已有受支持的 SessionStart hook，则预加载动态上下文
  -> 否则由静态 AGENTS.md / CLAUDE.md 规则在首条指令后读取环境指针
```

这条流程没有用户可选的 injection 分支。两种交付路径的区别只在时机：

- hook 已配置：模型调用前获得 `<iris-focus>` 或 `<iris-workspace>` 动态快照。
- hook 不支持、未安装、失效或未获信任：模型仍从入口协议获知如何读取
  `FOCUS_DOC` / `IRIS_WORKSPACE_PATH`，正确性不变，只少了零轮次预展开。

对于命令行自带 `--read` 一类参数的工具，该行为就是 launcher 命令本身的一部分，
不是第三种全局注入机制。

## 设置页重构

### 启动器

页面上半部只回答“‘用 X 打开’里出现什么”：

- 当前启动器使用紧凑列表，显示名称、命令和退出后行为，并支持拖动或上下按钮排序。
- 提供唯一主动作“添加启动器”。打开后先展示本机已检测到的推荐预设，再展示其他
  预设，并始终提供“自定义命令”。
- 自定义表单只要求名称和命令；内部 ID 自动生成。保存前校验名称非空、命令类型和
  ID 唯一性，不限制 CLI 品牌。
- 每项支持编辑、复制和删除。复制用于同一 CLI 的不同 profile / flags。
- 提供显式“恢复推荐项”动作，但必须预览将新增的项并经确认；绝不覆盖现有命令、
  排序或自动复活已删除项。
- 可显示“命令已检测到 / 未检测到”的派生提示，但这只是诊断，不阻止保存远程脚本、
  alias 或尚未安装的命令。

首次安装时建议以“探测到的预设 + Terminal”生成初始清单；如果探测失败，至少生成
Terminal。默认清单不再承担“Iris 支持哪些 agent”的宣传职责，完整能力由添加面板
展示。

### 上下文接入

页面下半部改名为“上下文接入”，与每一行 launcher 脱钩：

- 仅展示 adapter registry 中 Iris 真正能管理的 CLI。
- 状态用事实措辞：`未检测到 CLI`、`未配置 Iris hook`、`配置文件已写入`、
  `配置需更新`。当前代码只能检查文件，不能把 `configured` 翻译成“运行正常”。
- 每个 CLI 最多只有“配置 hook”或“更新 hook”动作，保持目标路径预览、用户确认和
  非法 JSON 拒绝覆盖。
- 同时固定展示回退说明：“未配置 hook 时使用标准入口协议，启动器无需额外设置。”
- `focus-context.ps1` 是 App 拥有的实现细节，继续在 App 启动时自动维护；正常状态下
  不给用户一个需要决策的脚本选项。仅在维护失败时显示诊断和重试。
- 后续若增加真实 smoke test，应把“配置文件已写入”和“最近运行已验证”分开显示；
  在此之前不制造绿色的端到端健康结论。

## “用 X 打开”入口治理

抽出一个共享的 launcher selector，右栏空态、新会话菜单和 workspace `+` 菜单都从
它渲染，避免三个入口逐渐出现不同排序、文案和溢出行为。

- 6 项以内直接展示全部；超过 6 项时提供搜索并限制弹层 / 空态列表高度，内部滚动。
- 空态仍以启动为主，不把十几个 agent 全部铺成无限按钮墙。
- 所有入口展示同一名称和顺序，点击始终只传稳定 `launcher.id`。
- 设置变更后通过现有 settings 广播即时生效，已运行会话继续保留创建时的 agent
  标签和命令语义，不因启动器被编辑或删除而被关闭。
- 文档右键菜单继续只做文件操作。会话属于当前文档 / workspace 的右栏锚点，避免
  同一动作在多个位置重复且产生不可见会话。

## 迁移与兼容

这是一次可无损迁移：

1. 读取旧 `settings.agents` 时保留 `id`、`label`、`command`、`onExit` 和顺序，丢弃
   `injection`。已有 session 只依赖 `agentId`，因此稳定 ID 不应重生成。
2. 新增启动器一律使用生成 ID；旧的品牌 ID 可以继续存在，不要求统一改名。
3. 老配置不补齐新预设；预设目录独立展示，解决“数组替换后新默认永远进不来”的问题。
4. 删除 `migrate-agents.mjs` 这类一次性默认补丁，并增加一次 schema 迁移测试。
5. hook 配置和 `focus-context.ps1` 不因删除 `injection` 而卸载或改写，现有用户级配置
   保持原样。

如果暂时不升级 settings `version`，可在加载时容忍并规范化旧字段；若希望落盘立即
清除历史字段，则应升 schema 版本并做显式迁移，不能依赖 TypeScript 类型变化自动
删除 JSON 属性。

## 明确不做

- 不为每个 agent 接入 RPC / SDK，不解析 agent 输出，不新增聊天 UI。
- 不把 launchers 变成 Iris 认可 agent 的白名单。
- 不按项目维护另一份 launcher 清单；第一阶段保持机器级用户偏好。
- 不因用户添加某个启动器就擅自修改该 CLI 的全局配置。
- 不自动卸载已经存在的 Iris hook；卸载若未来需要，应作为独立、明确确认的机器级动作。
- 不用“hook / none”开关模拟不受 Iris 控制的 CLI 生命周期。

## 2026-08-08 二次收口：删除退出行为选项

用户进一步确认“退出后回落 / 关闭”同样不构成有价值的 launcher 偏好。`AgentConfig`

该字段。主进程测试同时断言自定义 launcher 进入固定回落路径；main、preload、renderer

## 2026-08-08 Hook 移除能力

用户指出 hook 只有安装 / 更新而不能移除，不符合对用户配置文件的基本可逆性要求。
现在 `configured` 和 `stale` 状态均提供“移除 hook...”动作，并在真正写盘前再次确认。

新增的 `agent.remove-hook` 指令与 IPC 只删除命令中包含 Iris
`focus-context.ps1` 的 handler。它逐个 SessionStart group 过滤，保留同组其他 handler、
其他 hook 事件和配置文件顶层字段；空的 Iris 专属 group / event 会清理，但配置文件本身
不会删除。配置无法解析或 hook event 不是预期数组时继续拒绝写盘，不用覆盖来“修复”。

机器级 `~/.iris/focus-context.ps1` 不随单个 CLI 的移除动作删除，因为其他 CLI 可能仍在
引用它，而且该脚本由 Iris 拥有、在无 Iris 会话环境变量时不会输出内容。

自动测试新增两项纯配置变换用例，覆盖“只删除 Iris handler”和“无 Iris handler 时零
写入”；类型检查与定向测试 17 项通过。
