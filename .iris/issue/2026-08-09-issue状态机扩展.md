# Issue 状态机扩展

## 讨论结论

Iris 的 issue 反馈环很短：新问题被记录后通常就应进入可行动的 `Todo`，没有必要为了分拣而默认增加一层 `Backlog`。当前真正缺少的是一种“暂时退出行动队列，重新考虑是否还要做”的状态。

该状态使用官方存盘值 `On Hold`。它不是“做到一半暂停”，也不承诺未来一定恢复；它表达的是 issue 尚未解决，但当前不再推进，是否继续仍未决定。

状态间的核心区别：

* `Blocked`：已经确定要做，但受客观条件阻碍。
* `On Hold`：是否还要做尚无结论，当前主动退出执行与注意力队列。
* `Canceled`：已经决定不做。
* `Done`：已经完成。

`Paused` 隐含“之后会从原位置继续”，`Deferred` 隐含“已经决定以后再做”，`Suspended` 则偏正式、偏系统或资格停用语境；三者都不如 `On Hold` 贴合这里的未决语义。

## 产品语义

`On Hold` 是 **inactive 但 unresolved** 的状态。进入该状态时，应采用与 issue 进入 `Done` 相同的注意力和会话收尾行为：

* 从左栏活动 issue lens 中移除，不再占用当前注意力。
* 关闭所有锚定到该 issue 的 Iris 托管终端，避免已经退出执行闭环的任务继续保留活动会话。
* 不把 issue 视为已解决或已归档；它仍须能在 Issue 面板、状态筛选或搜索中找到，以便重新评估。
* 不触发只属于完成态的副作用，例如“切到 `Done` 时自动勾选正文任务”。
* 由活动 issue 派生的投影应采用同一套 inactive 判断；否则左栏已经隐藏，待办面板却仍持续暴露其任务，会产生相互矛盾的注意力信号。

这要求实现中不要把“是否活跃”“是否解决”和“进入时是否关闭终端”合并成一个 `terminal status` 判断。三个维度应分别表达：

| 状态 | Active | Resolved | 进入时关闭锚定终端 |
| --- | --- | --- | --- |
| `Todo` / `In Progress` / `In Review` / `Blocked` | 是 | 否 | 否 |
| `On Hold` | 否 | 否 | 是 |
| `Done` / `Canceled` | 否 | 是 | 是 |

从 `On Hold` 重新决定继续时，回到 `Todo`，重新进入可行动队列；决定不再处理时转到 `Canceled`。由于进入 `On Hold` 会让 issue 从活动 lens 消失并关闭相关终端，它和 `Done`、`Canceled` 一样应由用户决定，Agent 不应未经明确要求自行切换。

## 现状审计

当前实现并非完全散乱，但只完成了“状态词汇与写入入口统一”，尚未形成统一的状态语义模型：

* `src/shared/document-status.ts` 集中维护官方状态名称，编辑器、Issue 面板、内置协议和样式都从这里取值。
* renderer 的 `isActiveIssue` 将 active 定义为 `!resolved`，Issue 面板也只有 active / resolved / all 二分。这一捷径无法表达 `On Hold` 的 inactive + unresolved 组合。
* `statusClosesDocument` 复用 resolved 判断来决定是否关闭终端，混合了“是否解决”和“进入状态时是否收尾会话”两个维度。
* 左栏、待办和 Issue 面板虽然共享 `isActiveIssue`，但报告状态仍有局部字面量判断，状态样式也独立按字符串维护。
* 状态值有官方集合，但磁盘协议允许 exceptional soft value；当前没有统一的 fallback 分类，也没有状态转换规划器。
* 关闭终端和自动勾选任务只发生在 UI 的 `setDocsStatus` 写入路径。源码编辑、Agent 或其他外部写入可以改变 frontmatter，却不会执行同样的转换副作用。
* 当前没有直接覆盖 active / resolved 分类、待办投影、关闭终端和完成副作用组合的回归测试。

治理目标不是禁止 soft value，也不是强制所有转换路径，而是建立两个明确层次：共享的纯状态分类负责所有读侧投影；统一的转换计划负责 Iris 主动发起状态变化时的一次性副作用。未知值继续安全降级为 active + unresolved + 不关闭终端。

## 2026-08-09 实现结果

状态真相源已从“字符串清单”升级为带语义的官方定义。`Todo`、`In Progress`、`In Review`、`Blocked` 归为 active + open；`On Hold` 归为 inactive + open；`Done`、`Canceled` 归为 inactive + resolved。关闭终端和完成 issue 是独立字段，`Done` 是唯一带完成副作用的状态。旧的 `Resolved`、`Closed`、`Cancelled`、`Wontfix` soft value 继续兼容为 resolved，其他未知值继续显示在活动视图中。

左栏、待办、Issue 面板和 report lens 已改为消费共享分类。Issue 面板提供活动中、挂起、已解决、全部四个视图；挂起 issue 不进入左栏或待办聚合，但可从“挂起”或“全部”重新找到。`On Hold` 使用独立的弱强调样式，并进入官方状态菜单和排序。

Iris UI 发起状态切换时统一生成副作用计划。进入 `On Hold`、`Done`、`Canceled` 或 report `Backlog` 都会先确认并关闭关联终端；只有 `Done` 在设置启用时勾选正文任务。源码模式、Agent 或外部工具直接改 Markdown 时，读侧会立即按新状态投影，但不会把文件监听解释成新的用户手势并强制杀掉正在写该文件的 Agent；若仍有关联会话，左栏沿用现有 `Done` 保护行为，保留文档直到会话关闭。
