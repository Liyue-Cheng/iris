## 诊断结论

这三条报错是同一条故障链的三个阶段，根因是工具结果事件丢失了 Provider Call 关联，不是 Provider 自身报了这三种错。

1. Provider 返回工具调用后，worker 会把当前 `providerCallId` / `attemptId` 暂存到 `toolProviderCallId` / `toolProviderAttemptId`，然后清空当前 ID。
2. 工具结果的 `message_end` 到来时，`correlationForProviderMessage()` 只读取已被清空的当前 ID，没有使用上述工具备用 ID。
3. 主进程因此收到一个没有 `providerCallId` 的 `toolResult` provider message。`providerFrame()` 会为它生成一个从未创建过的后备 ID `provider-call:<runId>`。
4. Session 提交时的引用完整性检查发现 transcript frame 指向不存在的 Provider Call，于是抛出 `Provider Transcript Call correlation is invalid.`

第一条错误后，主进程在 worker 仍执行原 run 时就把 session 标记为 `paused`，并立即向界面开放“继续”操作。这导致后两条次生错误：

* 点得早时，同一 worker 里的 agent `activeRun` 还未清理，`continue()` 抛出 `Agent is already processing. Wait for completion before continuing.`

* 点得晚时，原 run 已经在 worker 内继续到了一条正常 assistant 消息。当前清理逻辑只会删除 `error` / `aborted` assistant，末尾的正常 assistant 仍在，所以 `continue()` 抛出 `Cannot continue from message role: assistant`。

## 当前代码位置

* `src/main/agent-worker.ts:548`：`correlationForProviderMessage()` 没有为 tool result 使用 `toolProviderCallId` / `toolProviderAttemptId`。

* `src/main/agent/session-manager.ts:1254`：缺失关联时生成了并不存在的后备 Provider Call ID。

* `src/main/agent/session-events.ts:259`：transcript 引用完整性检查在这里正确拦下了坏数据。

* `src/main/agent/session-manager.ts:575`：消费事件异常后只暂停了聚合状态，没有先让 worker 真正停止或隔离。

* `src/main/agent-worker.ts:626`：继续前只清理失败/中止的 assistant，无法处理上述竞态中后续产生的正常 assistant。

## 验证

当前 `session-manager` / `worker-host` / `pi-adapter` 的 30 个定向测试全部通过，说明现有测试没有覆盖“assistant 发起工具 -> toolResult 回写 -> 主进程提交 -> 立即继续”这条端到端时序。

## 为什么会变复杂

业务流程是串行的，但当前实现把它拆成了多个并行的异步边界：Provider 流式回调、worker 内 agent 状态、主进程持久化队列、工具执行 Promise、renderer 投影更新。每一层都保存了一份“正在调用谁”的状态，再用 `sessionId` / `turnId` / `runId` / `providerCallId` / `attemptId` 互相校验。

这些复杂度中，工具执行、取消、崩溃恢复、重试和日志持久化是必要的；但将一个串行流程用多个可独立迁移的 ID 和异步事件重新组装，属于当前设计带来的额外复杂度。这也是本次 bug 的根本原因：同一次操作在不同层被认为“已暂停”和“仍在运行”。

理想的形式应该是一个明确的串行执行器：一次只有一个活动步骤，步骤完成后才进入下一步；主进程只接收最终状态和可持久化事件，不应该自己推断 worker 是否已经结束。

## 当前架构

```text
Renderer
  │  IPC 命令 / Session 投影更新
  ▼
SessionManager（主进程，持久状态的协调者）
  ├── IrisAgentSessionStore（日志、快照、上下文产物）
  ├── IrisAgentToolHost（文件/终端副作用）
  └── AgentWorkerHost（每个 session 的 worker 生命周期）
          │  postMessage 事件/命令
          ▼
      agent-worker（短期运行时适配层）
          │
          ▼
      Pi Agent（真正推进 Provider -> Tool -> Provider 循环）
          │
          ▼
       Provider
```

### 各层职责

* Renderer 只发送 `send` / `stop` / `resume` 等命令，使用 `expectedRevision` 防止用过期界面状态覆盖新状态。它不直接控制 worker。

* `SessionManager` 保有持久化领域模型，为每个 session 用 `sessionMutationChains` 串行化命令和 worker 事件，并将最新投影推给 Renderer。

* `IrisAgentSessionStore` 将每次聚合变更写成带 hash 链的 domain transaction journal，在静止状态写 snapshot。每次 commit 都会检查引用完整性和状态迁移。

* `AgentWorkerHost` 管理 worker 启动、初始化、协议版本、空闲回收和崩溃通知。`post()` 只保证命令发进 worker，不等待整个 run 完成。

* `agent-worker` 在内存中创建 Pi session，把持久化 transcript 恢复为 SDK history，将 SDK 事件转成 Iris 事件，并用一组可变的“当前 ID”给事件补关联。

* Pi Agent 是真正的串行执行器：接收 prompt，调 Provider，如有 tool call 则等待工具结果，将 tool result 加回上下文，再调一次 Provider，直到最终回复或失败。

* `IrisAgentToolHost` 在主进程执行真正的文件/终端操作，因此 worker 中的 Pi tool 实际是 RPC 代理。

## 领域模型

```text
Session
└─ Turn（一次用户语义请求）
   ├─ Run 1（首次 send 的物理执行）
   │  ├─ Provider Call 1（一次 assistant 生成）
   │  │  ├─ Attempt 1
   │  │  └─ Attempt 2（Provider 自动重试）
   │  ├─ Tool Operation 1
   │  └─ Provider Call 2（带 tool result 继续生成）
   └─ Run 2（失败/暂停后的 continue）
```

* `Turn` 是用户眼里的一轮。它从一条用户消息开始，成功后变成 `fulfilled`。暂停时 Turn 仍然是 `open`，因为用户的这个请求还没完成。

* `Run` 是对该 Turn 的一次物理执行。首次是 `trigger: send`，暂停后继续会在同一 Turn 下创建新 Run，标记为 `trigger: continue`。因此一个 Turn 可以有多个 Run。

* `ProviderCall` 对应一轮 LLM assistant 生成。如果 assistant 要求工具，工具结果返回后会再有一个 ProviderCall。

* `ProviderAttempt` 对应一次实际 Provider 请求尝试。自动重试会保持 ProviderCall 不变，但新建 Attempt。

* `ToolActivity` 是 Timeline/UI 上的工具卡片；`ToolOperation` 是实际执行和结果；`Effect` 记录文件写入、目录创建和终端输出等副作用。

* `Timeline` 是给 UI 看的用户/回复/工具活动序列；`Transcript` 是下次启动 worker 时恢复给 Pi SDK 的 Provider 历史。它们是两份相关但用途不同的记录。

## 一个 Turn 的实际编排

### 1. 创建 Turn 和首个 Run

1. Renderer 发送 `send(sessionId, message, expectedRevision)`。
2. `SessionManager` 校验 revision、model 和 session 忙闲状态。
3. 主进程组装 software prompt、project prompt、当前 anchor 文档和用户请求，生成 `turnId` 和 `runId`。
4. 先持久化 Turn、用户 Timeline Activity、Provider user transcript、Run 和 request facts，再把 session 设为 `running`。
5. `AgentWorkerHost.post(run)` 把命令发给 worker。这里的 `await` 只等到“已投递”，不等到 Turn 执行完成。

### 2. Worker 和 Provider 循环

1. worker 调用 `PiSession.prompt()`，Pi Agent 将该 run 标为 `activeRun`。
2. Provider payload 发出前，worker 创建/复用 `providerCallId`，并为本次网络尝试创建 `attemptId`。
3. worker 先发 `provider-attempt: started`，再发 `provider-context`。主进程分别写 journal 和 Provider 上下文产物。
4. 流式 text delta 被 worker 按字符数/时间批量合并，主进程通过 `ensureReply()` 创建或追加 Timeline 回复。
5. assistant `message_end` 时，worker 发 `provider-message` 和 `provider-attempt: completed`。主进程把完整 assistant 写入 Transcript，并把 Timeline 回复标为完成。

### 3. 有工具调用时

1. Pi Agent 从 assistant 消息中发现 tool call，调用 Iris 注册的 custom tool。
2. worker 不直接碰文件或终端，而是发送 `tool-request`，并用 Promise 等待 `tool-result`。
3. `SessionManager` 先创建 ToolActivity 和 ToolOperation，把 session 设为 `waiting-tool`，然后调用 `IrisAgentToolHost`。
4. 工具完成后，主进程持久化结果和 Effects，再把 `tool-result` 发回 worker。
5. Pi Agent 将 tool result 加到内存上下文，开始下一个 ProviderCall。这个循环可以重复多次。

### 4. 结束、暂停与继续

* 正常结束：Pi Agent 的 `prompt()` 完成，worker 发 `execution-settled`，主进程将 Run 标为 `completed`、Turn 标为 `fulfilled`，清空 `currentRunId/currentTurnId`，Session 回到 `idle`。

* Provider/运行时失败：worker 应在 Pi Agent 真正退出 `activeRun` 后发 `execution-paused`。主进程将 Run 标为 `failed`，但保留 Turn `open`，Session 变成 `paused`。

* 用户继续：主进程在原 Turn 下创建新 Run，worker 调用 Pi Agent `continue()`。这不会再添加一条用户消息，所以 SDK history 末尾必须是 `user` 或 `toolResult`。

* worker 如果被回收/崩溃，重建时会从 Store 的 Transcript 恢复 Pi history。失败或中止的 assistant 只保留在 Timeline 用于 UI 展示，不应该进入 Transcript。

## 为什么明明串行还会失配

Pi Agent 内部的 Provider -> Tool -> Provider 确实是串行的，`SessionManager` 对同一 session 的本地 mutation 也是串行的。但这是两条独立的串行链，中间通过无提交确认的 worker 事件连接：

```text
Worker 执行链： Provider -> assistant -> tool -> toolResult -> Provider -> settled
                         │          │                    │
                         └── postMessage 事件──────────┘
                                      ▼
主进程提交链： attempt -> reply -> tool operation -> transcript -> completed
```

worker 发完大多数观测事件后不等待 Store commit 确认，会继续下一步。而主进程一旦在消费某个事件时失败，会独立把持久状态改成 `paused`，却没有同步终止 worker 执行链。因此两边可以同时各自“串行且正确”，整体状态仍然矛盾。

本次 bug 的具体触发点是：worker 用多个可变的全局槽位为事件补 ID，assistant 结束时已清空“当前 Provider Call”，tool result 事件又没有使用“工具所属 Provider Call”的备用槽位。执行顺序没乱，丢的是跨层事件的身份。

## Run 抽象评估

### 它当前在做什么

`Run` 现在不是一次 Provider 请求，而是“同一 Turn 的一段连续执行”。首次发送创建 `trigger: send` 的 Run；失败/停止后恢复，在原 Turn 下再创建 `trigger: continue` 的 Run。

它承担了以下职责：

* 记录每段执行的 `running/completed/failed/stopped` 状态、失败原因和起止时间。

* 将 ProviderCall、ProviderAttempt、ToolOperation、Effect 和 RequestFacts 归属到具体的恢复段。

* 通过 `currentRunId` 标记当前活动执行，拒绝旧 Run 延迟到达的 worker 事件。

* Stop 命令用 `expectedRunId` 确保不会停掉已经更换的执行。

* 让 Turn 可以在一次 Run 失败后仍保持 `open`，之后继续而不创建新的用户消息。

### 能否去掉

可以去掉 `Run` 作为一级持久化实体，但不能去掉“当前是哪一段执行”这个最小概念。否则无法区分恢复前后的延迟事件，Stop 也可能作用到错误执行。

当前 Renderer 不展示 Run 列表，只使用 `currentRunId`、当前暂停信息和按 Turn 聚合后的卡片。如果产品不要求“查看每次恢复的独立审计/计费/耗时”，完整的 `runs[]` 属于过度建模。

### 建议简化模型

```text
Session
└─ Turn
   ├─ state: running | paused | fulfilled | abandoned
   ├─ executionEpoch: number
   ├─ pauseReason / error / startedAt / completedAt
   ├─ ProviderCalls
   ├─ ToolOperations
   └─ Effects
```

* 删除 `runs[]`、`runIds[]`和 `currentRunId`。

* 将运行状态和暂停信息放到 Turn。

* 每次 send/continue 递增 `executionEpoch`，worker 事件携带 `{ turnId, executionEpoch }`。这是一个轻量 fencing token，只用于拒绝旧事件，不再是独立领域实体。

* ProviderCall、ToolOperation 和 Effect 直接归属 Turn；如确实要查看它们由哪次恢复产生，保留一个 `executionEpoch` 数值即可。

* Stop 的预条件由 `expectedRunId` 改为 `expectedExecutionEpoch`。

* RequestFacts 改为归属 Turn；继续时如没有重新组装 prompt，不需要新的 facts 实体。

如果未来要求逐次恢复审计、每次执行成本或单独回放，那么 Run 是合理的；否则建议删除它的实体身份，只保留 `executionEpoch`。这会减少一层父子引用、一套状态迁移和大量 `runId` 关联校验，但不牺牲并发安全。

## 进一步简化：去掉执行段概念

如果产品语义明确为“一个 Turn 只有一条连贯的串行执行链，Provider 错误或用户操作只是将这条链暂停，恢复后继续同一条链”，那么 `Run` 和 `executionEpoch` 都可以去掉。

此时不应再将恢复理解为“新的执行尝试”，而只是 Turn 的状态迁移：

```text
open/running
   ├─ Provider 错误 ──────────────────┐
   └─ 用户暂停 -> pausing -> worker idle ─├─> paused
                                             │
paused -> 用户恢复 -> running <-------------┘
running -> 最终回复 -> fulfilled
```

Provider 错误和人工暂停的区别只是 `pauseReason`，不是不同的生命周期：

* Provider 错误：Pi Agent 已经因错误退出，等待 `activeRun` 真正清空后，Turn 进入 `paused(reason: provider)`。

* 人工暂停：先进入 `pausing`，向 worker 发 abort，等待 `activeRun` 真正清空后，Turn 进入 `paused(reason: user)`。

* 主进程消费 worker 事件失败：不能直接把 Turn 改成 paused；必须先 abort/终止 worker，等到执行已隔离，再进入 paused。

### 删除所有执行身份的必要不变式

1. 一个 Session 同时最多只有一个 active Turn。
2. 同一 Session 的 send/pause/resume 命令由同一个串行 mailbox 处理。
3. `paused` 必须表示 worker/Pi Agent 已经静止，不能只表示主进程认为它失败。
4. Turn 进入 paused 后，旧 worker 不能再产生任何业务事件。最简单可靠的实现是暂停收口时关闭 worker，恢复时从持久化 Transcript 重建。
5. 恢复只能从 paused 进入 running，并且必须等新 worker 完成历史恢复后才开放执行。
6. 失败/中止的 assistant 可以留在 Timeline 中展示，但不能进入恢复用 Transcript；Transcript 末尾必须保持为可继续的 user 或 tool result。

在这组不变式下，迟到事件不是靠 `runId` 或 epoch 过滤，而是在暂停屏障处从源头消除。worker 实例替换仍可以在 `WorkerHost` 内部使用实例身份防止旧端口事件泄漏，但这是基础设施生命周期，不需要进入 Turn 领域模型。

### 最简领域模型

```text
Session
└─ Turn
   ├─ state: running | pausing | paused | fulfilled | abandoned
   ├─ pauseReason / error
   ├─ ProviderCalls -> ProviderAttempts
   ├─ Timeline
   ├─ Transcript
   ├─ ToolOperations
   └─ Effects
```

ProviderCall 和 ProviderAttempt 仍有独立价值：它们描述真实发生的 Provider 交互和自动重试，不是控制 Turn 生命周期的中间层。

因此更准确的结论是：如果暂停被实现为真正的执行屏障，而不是一个可以和 worker 真实状态分离的持久化标签，则“当前是哪一段执行”可以完全移出领域模型。

## 新架构与当前 bug 的关系

删除 `Run` 本身不会自动修复第一个错误。`Provider Transcript Call correlation is invalid` 的直接原因仍然是 tool result 事件没有携带正确的 Provider Call 关联。如果只删除 Run，但保留当前 worker 中的全局可变关联槽位和无确认事件协议，同类 bug 仍会出现。

但这三个错误对应的两类架构问题，都可以在新架构中从根上消除：

| 当前错误                                              | 当前根因                                                             | 新架构的消除方式                                                                             |
| ------------------------------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `Provider Transcript Call correlation is invalid` | tool result 的归属依赖 worker 的可变“当前 ID”，清空时机和事件时机失配                  | tool result 直接归属 `toolCallId`；ToolCall 在 assistant 提交时已显式归属 ProviderCall，不再从“当前调用”推断 |
| `Agent is already processing`                     | 主进程提前将 Turn 标记为 paused，Pi Agent `activeRun` 仍存在                  | `paused` 只能在 Pi Agent idle 且旧 worker 已关闭/隔离后提交，恢复不可能和旧执行重叠                           |
| `Cannot continue from message role: assistant`    | paused 之后旧 worker 仍继续追加了 assistant，SDK 内存历史和 Store Transcript 分叉 | 恢复始终从 Store 中的已提交 Transcript 重建 worker；失败/中止 assistant 只在 Timeline 展示，不进入 Transcript |

## 建议的 Turn 执行架构

### 单一所有者

引入一个每 Session 唯一的 `TurnController`（可以由现有 `SessionManager` 内部承担，不必是新类），它是 send/pause/resume 和 worker 事件的唯一 mailbox。对外只暴露一个 Turn 状态机，不允许主进程和 worker 各自独立决定 paused/running。

```text
send/resume/pause command
          │
          ▼
   TurnController mailbox
          │
          ├── durable event -> Store commit -> ACK
          │
          ├── tool request -> ToolHost -> Store commit -> result
          │
          └── lifecycle barrier -> worker idle/closed -> paused
```

### 显式事件归属

不再用 `currentProviderCallId` / `toolProviderCallId` 等跨回调全局槽位推断归属。事件在创建时就带有结构性父子关系：

```text
ProviderCall(callId)
├─ AssistantMessage(callId)
└─ ToolCall(toolCallId, callId)
   └─ ToolResult(toolCallId)
```

`ToolResult` 不需要再携带或推断 `providerCallId`：它通过 `toolCallId` 唯一归属 ToolCall，ToolCall 已经归属 ProviderCall。Transcript schema 也应与消息角色匹配：

* user frame 归属 Turn，不伪造 `run-input:<runId>` Provider Call。

* assistant frame 显式归属 ProviderCall。

* tool result frame 显式归属 ToolCall。

### 持久化边界确认

不要对每个文本 delta 做强一致 ACK，否则会增加无必要延迟。将事件分为两类：

* 瞬时 UI 事件：assistant delta，可批量合并，不作为可恢复事实。

* 持久化边界：ProviderCall started、完整 assistant、ToolCall、ToolResult、paused、fulfilled。worker 在依赖该事实进入下一步前，必须收到 Store commit ACK。

特别是 assistant 中含 tool call 时，应先将 assistant 和 ToolCall 归属提交成功，再允许 ToolHost 执行。这样 ToolResult 永远有已存在的父对象。

### 统一暂停屏障

所有异常和人工暂停都进入同一个收口：

```text
requestPause(reason)
  -> 禁止新命令
  -> 如仍运行则 abort
  -> await Pi Agent idle
  -> flush/exclude partial reply
  -> close or detach worker
  -> commit Turn.paused(reason)
  -> 向 Renderer 开放 Resume
```

任何 Store commit/协议处理错误也必须走这条路径，不能在 worker 仍运行时直接投影为 paused。

### 恢复

Resume 不是创建新 Run，而是：

```text
assert Turn.state === paused
  -> 从已提交 Transcript 创建 worker
  -> 校验 transcript 末尾为 user/toolResult
  -> worker ready
  -> continue same Turn
  -> Turn.running
```

## 建议实施顺序

* [x] 先补端到端回归测试：assistant tool call -> ToolResult -> 第二次 ProviderCall -> 最终回复。

* [x] 将 paused 改成必须经过 worker idle/closed 的统一暂停屏障，先消除后两个竞态报错。

* [x] 将 ProviderCall -> ToolCall -> ToolResult 改为显式结构性归属，删除 tool result 对“当前 Provider Call”的推断。

* [x] 为持久化边界增加 ACK，worker 只在父事实已提交后进入工具或下一次 Provider 调用。

* [x] 将 Run 状态合并到 Turn，删除 `runs[]`、`runIds[]`、`currentRunId` 和协议中的 `runId`。

* [x] 将 Resume 改为从已提交 Transcript 重建 worker 并继续同一 Turn。

* [x] 补充 Provider 失败恢复、人工暂停立即恢复、Store commit 失败、旧 worker 迟到事件和应用重启恢复测试。

## 关于取消 correlation 的补充判断

可以取消当前这种“每条 transcript frame 都必须通过 `providerCallId` 引用一条独立 Provider Call 记录”的设计。对一个严格串行的 Agent 执行器来说，Provider 开始、assistant 输出、工具请求、工具结果和下一次 Provider 请求本来就可以按追加顺序组成事件流，不需要 SessionManager 再用一组外键把它们重新拼装起来。

但需要区分两种关联：

* Provider 请求与 transcript frame 的持久化关联可以取消。一次请求的边界可由 `ProviderStarted` / `ProviderFinished` 等顺序事件表达，重试也可以作为新的顺序事件记录。
* 工具结果与具体工具请求的语义关联不能在所有情况下取消。OpenAI、Anthropic 等协议要求结果携带原始 `tool_call_id`；一次 assistant 输出也可能同时请求多个工具，执行完成顺序未必等于请求顺序。只看结果到达时间会无法判断结果属于哪个工具请求。

如果 Iris 明确收紧为“一次只允许一个待执行工具，工具完成并持久化后才能进入下一步”，内部恢复逻辑可以主要依赖时序：当前唯一未完成的 `ToolRequested` 后面出现的 `ToolCompleted` 就属于它。Provider 协议需要的 `tool_call_id` 仍保存在该工具请求/结果事件中，但只作为发回 Provider 的协议字段，不再作为跨层协调 Session 状态的通用 correlation。

建议的数据流是：

```text
TurnStarted
ProviderStarted
AssistantOutput / ToolRequested(toolCallId)
ToolCompleted(toolCallId)
ProviderStarted
AssistantOutput
TurnCompleted
```

这个方案以日志顺序和明确的步骤边界作为真实状态，删除 `providerCallId` 外键、后备 Call ID 和跨层 Call 引用完整性检查。恢复时扫描最后一个未闭合步骤即可决定续跑位置，不再根据最后一条消息的 `role` 直接拒绝。

因此，“取消 correlation”可行的准确含义应当是：取消 Provider Call 作为独立领域实体以及它和 transcript 之间的跨层关联；保留 Provider 协议要求的 `tool_call_id`，并在允许多个工具同时在途时继续用它区分工具结果。如果连 `tool_call_id` 也完全取消，就必须同时禁止并行/批量工具调用，并在适配 Provider 时临时恢复协议所需的 ID，否则无法可靠工作。

## 保留 correlation 时的修复方案

不一致并不是多个事件真的没有先后顺序，而是同一个关联被分散保存在三个状态副本中：worker 的可变全局变量、Pi Agent 的消息历史和主进程的持久化聚合。三者迁移状态的边界不同。

正常工具回合的顺序是：

```text
Provider Call A started
assistant message_end（包含 toolCallId）
Provider Call A completed
执行工具
toolResult message_end
Provider Call B started（把 toolResult 作为下一次输入）
```

worker 在 assistant `message_end` 后立即把 `currentProviderCallId` / `currentAttemptId` 清空，但 toolResult 是之后才由 Pi Agent 发出的。因此 toolResult 到达时，worker 的“当前 Provider 调用”已经不存在。旧实现又要求主进程为这条消息提供 Provider Call 关联，并在缺失时构造一个从未创建过的后备 Call ID；持久化校验随后正确发现 transcript 引用了不存在的 Call。

修复时需要先固定语义：

* `providerCallId` 表示一次逻辑模型响应。
* `attemptId` 表示该响应的一次实际网络尝试；自动重试创建新 attempt，但仍属于同一个 call。
* assistant 消息属于产生它的 attempt/call。
* toolResult 通过 `toolCallId` 关联到发起工具的 assistant 消息。若数据模型仍要求它携带 `providerCallId`，该 ID 必须从 `toolCallId -> assistant frame -> providerCallId` 推导，不能读取当时的 `currentProviderCallId`，也不能生成后备 ID。

具体实现边界如下：

1. `onProviderPayload` 创建不可变的活动 Call/Attempt 上下文，先持久化 `provider-attempt started`，收到主进程成功 ACK 后才允许后续消息提交。
2. Provider 流事件捕获这份上下文的快照，不在事件稍后消费时读取可能已经变化的全局 ID。
3. assistant 最终消息先持久化并成功 ACK；其中的每个 `toolCallId` 同时登记到所属 Call。之后才能提交 attempt completed 并释放活动上下文。
4. tool request 和 toolResult 只携带 `toolCallId` / `operationId`；主进程从已经提交的 assistant frame 查找所属 Call。找不到时直接拒绝该事件，绝不伪造关联。
5. 下一次 Provider payload 创建新的 Call。toolResult 是新请求的输入，但其因果来源仍由 `toolCallId` 指向上一条 assistant 工具请求。
6. 任一 durable 事件提交失败时，主进程先返回失败 ACK，再终止并等待对应 worker 退出，最后才把 session 标为 paused 并开放恢复。旧 worker 的后续事件通过 `workerEpoch` 作废。
7. 恢复始终启动新 worker，并从最后一次通过完整性校验的持久化 transcript 重建 Pi 历史，不复用已经比持久状态多跑了一段的内存历史。

恢复时还必须分类处理最后一个可靠状态：末尾是 user 或 toolResult 才调用 Provider 继续；assistant 含未完成工具调用时先恢复/补交该工具结果；完整 assistant 且没有待处理工具时应把回合判定为已经完成，而不是调用 Pi 的 `continue()`。这样 `Cannot continue from message role: assistant` 可以保留为内部不变量，但不会再作为用户可见的恢复失败。

当前工作树已经出现了两项朝正确方向的改动：durable worker 事件增加了 ACK，`pauseSessionExecution()` 也会在标记 paused 前关闭 host；同时当前 `applyProviderMessage()` 不再为 toolResult 生成后备 Provider Call。不过 worker 仍通过可变的 `currentProviderCallId` / `currentAttemptId` 组织关联，toolResult 分支也明确不携带 Provider ID。因此最初那条具体坏引用路径可能已经被局部移除，但上述 ID 生命周期、失败后截断点和恢复分类仍需用端到端时序测试一起确认，不能只以原报错不再出现作为完成标准。

## 本轮处理结果

本轮在保留 correlation 的前提下继续检查了相邻时序，确认并修复两个同类问题：

1. 连续多个 toolResult 原来会复用 worker 的 `currentProviderMessageId`。主进程按 frame ID 去重时，第二个及后续工具结果可能被当作重复事件丢弃。现在每条 toolResult 使用 Provider 显式消息 ID，缺失时独立生成新 ID；它仍只通过 `toolCallId` 关联工具请求，不伪造 Provider Call。

同时补齐了更早的中断点：assistant 的 toolCall 已提交、tool request 尚未到达时，暂停逻辑会创建 canceled Tool Activity 和明确的中断 toolResult。新 worker 从合法的 toolResult 边界恢复，不会从 assistant 角色直接调用 `continue()`。工具已经执行但结果尚未提交时也不会重放副作用，而是补一条要求重新检查当前状态的错误结果。
