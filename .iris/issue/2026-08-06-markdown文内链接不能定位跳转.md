title: Markdown 文内链接不能定位跳转
status: Todo
---
现在 Markdown 文档里的链接没有 Iris 自己的导航语义。像 [跳到某一节](#某一节) 或 ./另一个文档.md#某一节 这种链接，应用没有统一解析，也没有把 fragment 定位到标题或块。

用户看到的是 Markdown 编辑器，但点击链接时最多只能依赖编辑器或浏览器默认行为；Iris 不知道这是当前文档内跳转、项目内文档跳转，还是外部链接。这样目录链接、跨文档引用、从待办跳到具体条目，都只能打开整篇文档，不能稳定落到目标位置。

当前代码证据：

* renderer 里没有 Markdown link resolver、heading slug 生成、hash 解析或 fragment 定位逻辑。

* 项目内跳转入口基本都直接调用 projectStore.selectDoc(path)，没有携带 fragment。

* 兼容性文档已经包含 #heading 风格链接，但应用层没有接住它。

需要处理：

* [ ] 定义统一 Markdown link resolver：外部 http(s)、当前文档 #fragment、相对 .md\[#fragment] 分开处理。

* [ ] 固定 heading slug 规则，覆盖中文、重复标题、标点和显式锚点。

* [ ] projectStore.selectDoc 或新的 navigate 命令要能携带 fragment，并在编辑器 ready 后消费。

* [ ] 非法路径或越界相对路径必须拒绝，不能让 Electron 默认导航接管。

* [ ] 补文内标题跳转、跨文档 fragment 跳转和非法链接测试。

## 2026-08-06 分析补充

整体属于中等工作量，不需要修改 Milkdown 内核。核心逻辑并不复杂，主要集成难点是把链接解析、异步文档读取、编辑器挂载和 fragment 定位串成一条不会串目标的导航链路。

建议将“选择文档”和“带目标导航”分开：保留 `projectStore.selectDoc(path)` 处理普通选择，新增类似 `navigateDoc({ path, fragment })` 的入口。当前文档 fragment 可直接定位；跨文档 fragment 先加载文档，再由 `CrepeEditor` 的 `onCreated` 生命周期消费待处理目标；外部链接交给系统浏览器；非法目标在 renderer 拦截，并由 main 的项目根路径校验再次兜底。

现有基础：

* `projectStore.selectDoc` 已集中管理文档切换，但同文档重选会直接返回，因此 fragment 导航不宜只靠扩展现有重选行为。

* `CrepeEditor` 已有明确的 `onCreated` 回调，可以在编辑器 ready 后执行定位。

* Milkdown 会为 heading 节点维护 DOM `id`，无需自行遍历和改写渲染后的标题节点。

* `ProjectManager.resolveInside` 已提供项目根目录防逃逸校验，可作为内部链接路径校验的第二道防线。

* 待办数据已经记录源文件行号，但 `TodoPanel` 当前点击待办时只调用 `selectDoc(path)`，尚未传递行或块目标。

需要提前固定的兼容性约定：

* 不能直接把 Milkdown 当前的 heading ID 行为当成 Iris 的长期协议。其默认规则主要是转小写、裁剪和将空白替换为连字符；中文会保留，但标点也会保留，重复标题使用 `-#2` 一类后缀。应提取 Iris 自己的共享 slug 函数并用测试锁定中文、标点、空标题和重复标题行为。

* CommonMark 没有统一的显式 heading ID 语法。实现前需明确“显式锚点”具体支持 `{#anchor}`、`<a id="anchor">`，还是只支持自动 heading slug。

* 待消费导航目标必须绑定文档路径及请求代次或 editor generation。快速连续跳转时，旧文档的异步读取或旧 fragment 不能在较晚时刻落到新编辑器上。

* renderer 应拒绝绝对路径、越出项目根的相对路径、非目标 Markdown 文件及危险协议。主进程当前的 `setWindowOpenHandler` 只覆盖新窗口请求，还应防止链接触发当前 Electron 窗口的默认导航。

* heading 定位和待办定位应视为两种目标。heading 适合稳定 slug；待办已经有行号，可先用行或块目标定位，但需要考虑正文编辑后行号漂移。

测试策略：resolver、slug、重复标题和路径归一化适合写成纯函数并用现有 Vitest 覆盖。当前测试环境是 Node，尚无现成的 React/jsdom 编辑器集成测试层；编辑器 ready 后的滚动与选区行为可尽量拆成可单测逻辑，并补少量应用内交互验收，或后续单独建设 DOM 集成测试。

工作量粗估：只完成标题的文内跳转、跨文档跳转、安全解析和纯函数测试约需 1 天；若同时覆盖显式锚点、待办具体条目、源码模式定位及完整交互验证，约需 1.5 至 2 天。
