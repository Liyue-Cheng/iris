谈谈你对现在issue标题和文件名之间关系和张力的理解，你认为有没有更好的实践

## 调研：标题与文件名（2026-11-23）

**结论先行。** 现在这套设计的内核是对的：`title:` 是名字，文件名是地址。可变名 + 不可变身份，这是 GitHub/Linear/Jira、git（hash + subject）、邮件（Message-ID + Subject）共同的解法，不是缺陷。真正的张力来自两个更具体的地方：

1. 文件名里的 slug 长得像「名字」（可读的人类语言），但它的职责是「出生地址」。它从创建那一刻起就会过时，而系统里没有任何地方——协议、UI、文档——告诉人（或 agent）「它过时是正常的、它不是名字」。
2. 「文件名由标题派生」这条规则只在应用内创建对话框里成立。协议给 agent 的规则只说 `YYYY-MM-DD-<slug>`，`<slug>` 从未被定义。于是 agent 直接落盘时按自己的习惯起 slug（常常是英文缩写、去标点、全半角归一），标题另写一句中文——分叉出生在创建那一刻，而不是标题演化之后。

数据可以验证第二点：根工作区 177 篇有标题的文档里 47 篇（26.6%）的文件名无法由当前标题重新 slugify 得到；其中 46 篇在 git 的第一个版本里就已经是现在这个标题，只有 1 篇是创建之后改了标题。全仓库（含 `.iris/iris-agent` 嵌套工作区）249 篇中 64 篇不一致。所以在本仓库里，「标题和文件名的张力」主要不是「标题会变」，而是「存在两条创建路径、两套命名方言」。

### 一、现状机制（代码事实）

- **创建**：新建文档对话框只收一个 title；主进程用 `slugify(title)` 生成文件名，issue/report 加 `YYYY-MM-DD-` 前缀，同名追加 `-2`、`-3`，frontmatter 原样写入 title（`src/main/project-manager.ts:407`）。
- **编辑**：文档头部的标题输入框只改 frontmatter `title:`，不碰文件名（`src/renderer/components/doc/TypedHeader.tsx:219`）。整个应用没有「重命名文件」的命令（grep 全仓，`rename` 只出现在原子写入和 agent 会话管理里）。
- **展示**：左栏、四个集合页、待办、右栏锚点标题全部用 `docDisplayTitle = title ?? 去扩展名的文件名`（`src/renderer/lib/doc-utils.ts:23`）。用户在常规界面看到的都是标题；文件名只在 tooltip、右键菜单、删除确认框、raw tree、复制路径里出现。
- **搜索**：左栏过滤和集合搜索都同时匹配标题与文件名（`LensTree.tsx:121`、`IssuePanel.tsx:432`）——用旧名或新名都能搜到。这是现在做得对的地方，应该保留。
- **排序与日期**：左栏按标题排序（或 mtime）；issue/report 集合默认按文件名里的日期前缀排序，缺失时退 mtime（`src/renderer/lib/collect-docs.ts:67`）。日期前缀承载的是「出生日期 + 并发去重」，不是更新时间。
- **身份**：path 是主键。会话锚点（`docPath`）、删除时的会话 re-anchor、`FOCUS_DOC` 注入、`.assets/` 伴生目录都以文件名为键。文档被移走/删除后，会话列表会挂 orphaned 警告——说明系统把路径变化当事故处理。
- **兜底**：无 title 时显示文件名；frontmatter 损坏时降级显示并标警告。
- **一个边界 bug**：`title: ""`（显式空串）会让标题显示为空白——`docDisplayTitle` 用的是 `??`，空串不算缺失。按「空白即缺失」处理更稳。

### 二、真实数据（本仓库审计）

- 全库 249 篇 Markdown（含嵌套工作区）：64 篇（约 26%）文件名与标题不一致；根工作区 178 篇中 47 篇（26.6%），`.iris/iris-agent` 工作区 71 篇中 17 篇。
- 根工作区 47 篇漂移里，约 19 篇是标点/空格/全半角层面的差异（`第三轮批次1：` 写成文件名时成了 `第三轮批次1-`；拉丁词两侧的空格被吃掉；`Markdown` 大小写），28 篇是语义级差异：`终端复制粘贴 → 终端各类bug`、`状态机 → Agent设置状态机`、`MD → md编辑器的块笔记手柄`、`issue面板的反返回按钮 → issue面板的返回按钮`（标题改正了错字，文件名保留错字）。
- 出生 vs 后天：47 篇里 46 篇的首个 git 版本就带着现在的标题（`2026-06-12-terminal-clipboard-and-fixes.md` 首提交就是 `title: 块手柄设置重做…`），唯一例外是 `实现git图形化功能 → 实现 Git 图形化功能`。历史上 title 行被移除的记录只有 18 条（其中还包含删除文档的整文件 diff）；`.iris` 目录里发生过的 70 次重命名全部是整篇迁入 `.iris/iris-agent/` 工作区，同目录内改文件名 0 次。
- 6 月 12 日的 8 篇 report（`block-edit-toggle-redo`、`scrollbar-issue-analysis`、`todo-panel-labels-research` 等）是「英文文件名 + 中文标题」同时出生，属于 agent 直接落盘的典型证据。
- 标题天然不唯一：现存两篇 `报错信息`。标题不能当主键，path 才是不二之选。

### 三、为什么这是结构性张力

三个角色压在两个载体上：**身份**（必须稳定、唯一、机器可寻址）、**出生证明**（何时开题、以什么名义开题）、**名字**（当前人怎么称呼它）。Iris 把前两者给了文件名，把名字给了 title。日期前缀承担出生证明，这是好设计；问题在 slug——它是「出生那一刻的名字」的投影，却长得和「名字」一模一样。

这不是 Iris 独有的问题。文件系统世界里有两个成熟答案：Obsidian 式「文件名即名字」（改名级联改链接，没有独立 title 概念）；和 GitHub/Linear/git/email 式「不可变 ID + 可变名字」（编号/hash/Message-ID 是身份，标题随内容走）。Notion 最接近 Iris 的理想态：页面标题是属性，页面 ID 不透明，URL 里挂一段可过期的 slug——没人因为 URL 里的 slug 过时而困惑，因为没人把它当名字。Iris 本质上是「Notion 模型落在 git 的路径上」。

这也解释了为什么「标题编辑自动同步改名」是错误答案：`FOCUS_DOC` 在终端启动时写进环境变量，改名之后运行中的 agent 永远拿着旧地址；会话锚点、`.assets/`、删除语义全部以 path 为键。每次改标题都动地址，会把一次命名动作放大成一次全局身份变更——git 噪音、会话孤儿、旧窗口失效。

反过来看，漂移也不全是噪音：`终端复制粘贴 → 终端各类bug` 记录了「开题名 → 现状名」的演化，是这篇文档的档案。如果文件名永远追着标题改，「它以什么名义开题」在 plain-files 的世界里就丢了。所以更准确的表述是：**文件名不该隐藏这个差异，而应该被明确宣称为地址**。UI 侧其实已经做到了（处处显示标题）；漏掉的只是文件系统、git、删除确认框，以及 agent 的认知。

### 四、更好的实践

**方案 A（建议先做，低成本）：把分工制度化。**

- 在软件协议（`<iris-software>` 模板）里给文件名定性：文件名是地址，`YYYY-MM-DD-` 是开题日期，slug 是开题时的短别名，不承诺与标题一致；不要为了「对齐」重命名或移动 `.iris` 文档（会孤儿化会话、让运行中终端的 `FOCUS_DOC` 失效）；正文里用标题指代文档，写回与操作时用路径。
- 同时收窄协议里 `<slug>` 的语义，二选一：C1，slug 必须由标题派生（与对话框同规则）；C2，slug 是创建者自选的短别名，允许与标题不同（本仓库现状，也是分支名/邮箱别名的惯例）。我倾向 C2——中文长标题进路径有长度、编码、跨平台问题，而现状早已如此；C1 只能保证出生时一致，标题一改仍会漂移。
- 修两处「文件名冒充名字」的用户可见点：删除确认框用标题做主标题、路径做副文（现在主标题就是文件名，`DeleteDocDialog.tsx:119`）；右键菜单 label 可同时显示两者。再修 `title: ""` 的空串兜底。

**方案 B（可选，中成本）：显式「重命名文件以匹配标题」命令。**

只做人工触发的逃生舱，绝不自动。规则：保留原 `YYYY-MM-DD-` 前缀（日期是出生证明，重新生成会让按时间排列的档案说谎）；slug 部分取 `slugify(title)`；冲突追加 `-2`；文档与 `.assets/` 目录作为一个聚合原子移动（删除流程已有 staging 模式可复用）；运行中会话用 `session.reanchor` 指到新路径（机制已有）；`.iris` 内的相对链接没有反向索引，重命名需要扫描改写（或明确接受断链）；`FOCUS_DOC` 无法热更新，UI 需提示「该文档的终端要重开才拿到新路径」。鉴于 46/47 的漂移是出生即分叉，这个命令主要服务「分享/归档前让地址可读」的人类场景，不是治理漂移的主力。

**方案 C（可选，治本）：统一创建入口。**

未来若给 agent 提供 `doc.create` 的 CLI/工具入口（由主进程统一 slugify + 日期前缀 + 冲突处理），agent 就不再手写文件名，两条创建路径合并。这是消除「出生即分叉」的唯一根治办法，但不必须——只要协议说清楚文件名不是名字，C2 口径下的分叉就是无害的。

**已否决的方向**：标题编辑自动同步改名（地址漂移对 agent-native 工具是高危操作）；去掉 title 字段、文件名即名（Obsidian 模式）——`title:` 是协议接口，HTML 文档的 `<title>` 本身就是 title，标题允许含 `/`（本仓库就有「多窗口/多项目」）、允许中英切换，status/misc 也没有日期前缀，文件名承担不了名字的全部表达。

## 追问：slug 是否必要？纯时间戳命名可行吗？（2026-11-23）

**结论：slug 不是必要的；纯时间戳是一种自洽的选择，但它的本质是用「文件名的语义索引」换「文件名永不撒谎」。对 AI 检索的影响没有想象中大，因为在本协议里 AI 的主要上下文通道不经过文件名；真正的代价落在人和文件系统这一侧。想两全可选「身份 + 装饰」分离：时间戳（精确到分，或加短 id）是身份，slug 降级为装饰。**

### 纯时间戳换来了什么

- 张力从根上消失。方案 A 的协议声明、方案 B 的改名命令，都是在「管理」张力；时间戳命名是「消解」张力——文件名不再冒充名字，也就无所谓过时，不需要任何治理。
- 引用、会话锚点、外部分享天然稳定：不存在「该不该同步改名」的问题。
- 排序天然：按文件名即按时间，`docDate` 的日期前缀解析依然成立。
- 唯一性可控：日期精确到分钟（`YYYY-MM-DD-HHMM`）足以覆盖人类节奏；同一分钟内的并发仍保留现有 `-2` 兜底即可。只到日期则同日多次新建会频繁撞后缀，观感较差。

### 对 AI 检索的影响，按通道拆开看

1. **应用内注入：不受影响。** 文档会话注入的是整篇文档（title 就在 frontmatter 第一行）；工作区会话本来就不注入文档清单。
2. **内容检索（grep / 读文件）：不受影响。** AI 找文档的主通道本来就是正文：`rg` 在中文正文里照常工作，agent 拿到焦点文档时也是全文。
3. **「文件名即索引」这条通道：受损。**
   - `ls .iris/issue` 从一张「主题地图」变成一列时间戳。agent 可以一条命令重建映射（`rg -n '^title:' .iris --glob '*.md'`，约 250 行、一次工具调用），所以信息没丢、只是从「被动可见」变成「主动查询」；对人是持续的摩擦：Finder、git log、编辑器 quick-open 都失去主题提示。
   - 跨文档引用变差：本仓库大量以路径互引（「对应 issue：`issue/2026-06-12-MD.md`」），时间戳路径让每一条引用都变成「必须打开才知道是什么」。
   - 唯一无标题的文档（现存 1 篇）会直接显示成一串时间戳，兜底名彻底失去意义。
4. **检索质量本身：不下降。** 下降的是「不打开文件就大概知道它是什么」的能力。

一句话：对 AI 是「轻微、可补偿」的影响；对人是「持续、每次多一步」的影响。Iris 的立身之本是 plain files（删掉应用后项目仍然可读），评估时要把这层损失算进去。

### 三种落点

- **纯时间戳**：`2026-06-12-1403-终端复制粘贴.md` 去掉后半段，即 `2026-06-12-1403.md`。最自洽，代价如上。建议精确到分钟（秒级可选），保留 `-2` 冲突后缀。
- **搭配短 id 的装饰名**：`2026-06-12-a3f9-终端复制粘贴.md`。身份 = 日期 + id（稳定、唯一、可引用），slug = 装饰（允许过时、允许随时改，甚至删掉）。这正是 GitHub issue URL 的结构（`/issues/123/可选-slug`）：没人会因为 URL 里的 slug 过时而困惑，因为它不是身份。既消解张力，又保留索引。
- **维持现状（日期 + 出生 slug，C2 口径）**：把 slug 定义为创建时装饰、不承诺与标题一致；用协议一句话 + 少量 UI 修补吸收掉「文件名撒谎」的观感。成本最低，索引最完整。

### 我的取向

不建议直接跳到纯时间戳：它换掉的正是本仓库最常用的「一眼可读」，而张力的实际伤害已被数据证明很低（26% 漂移、0 次改名事故，UI 从不把文件名当名字）。若你对「文件名绝不撒谎」有强偏好，时间戳命名是合理选择；若想两全，选「日期 + 短 id + 装饰 slug」——把身份和装饰分开后，slug 是否过时就只是审美问题，不再是协议问题。

- [ ] 命名方案定夺：维持「日期 + 出生 slug」（C2）/ 改为「日期 + 短 id + 装饰 slug」/ 改为「纯时间戳」

### 验证范围（本次追问）

- 结论基于既有调研的代码与数据，未额外跑新审计；`rg -n '^title:' .iris` 可作为「文件名索引」的替代通道（Markdown 专用；HTML 文档需另匹配 `<title>`）。

## 追问二：先建空壳、让 AI 后补标题，会不会退化成类时间戳？（2026-11-23）

**结论：会，但退化的形态比时间戳更差——是 `日期 + untitled + 序号`。这不是「AI 后补标题」的错，而是「名字晚到」与「文件名出生即定型」没有对齐。两个自洽的出口：名字晚到时把地址同步一次（首题改名），或者出生即承认文件名不是名字（时间戳身份）。如果空壳创建会成为常态，我建议后者加可选的装饰性改名。**

### 机械上会发生什么（代码事实）

- 现在对话框让填的其实是 title，文件名是派生的；「不填文件名」实际是「不填标题创建」。主进程 `createDoc` 其实接受空标题（校验只查 `typeof title === 'string'`），拦住它的是对话框按钮的 `!title.trim()` 禁用（`CreateDocDialog.tsx:135`）。所以解锁「空壳创建」是一个很小的 UI 开关。
- 若今天直接放行：`slugify('')` 返回 `untitled`，同目录碰撞追加 `-2/-3`，文件名变成 `2026-11-23-untitled.md`、`2026-11-23-untitled-2.md`……语义部分归零，等于「日期 + 序号」——一种带占位符的时间戳，而且比纯时间戳更难读。
- 并且 `docSkeleton` 会给空标题写 `title: ''`（`yamlScalar('')` 返回引号空串）；`docDisplayTitle` 用 `??`，空串不算缺失，于是列表里显示空白行，直到 AI 填标题。这条路径必须先处理「空标题 = 缺失」的兜底，或干脆空标题时不写 `title:` 行（更省事，显示自动退到文件名）。
- 目前没有官方重命名入口，AI 只能改 frontmatter 的 title；它不碰文件名，`untitled` 就永久留下。

### 为什么「退化」只对了一半

- 身份层的退化不存在：path 依然稳定唯一，会话锚点和引用不受影响。
- 退化的是「文件名即索引」这一层：26% 的漂移会被「100% 占位名」取代，`ls`、git log、跨文档引用彻底失去信息量。
- 最糟的不是「类时间戳」，而是 `untitled-7`：时间戳是诚实的地址，`untitled-7` 是「打算起名但没起」的残骸，而且每篇长得一样、互相无法区分。

### 两个自洽的出口

**出口 1：首题时同步地址（只此一次）。** 空标题创建的文档先叫 `YYYY-MM-DD-HHMM.md`（时间戳占位）；第一次获得标题时，把地址同步成 `YYYY-MM-DD-HHMM-<slug>.md`。这与之前否决的「每次改标题都自动改名」不矛盾：危险在于一篇文档生命周期里的反复改名（会话锚点、资产目录、互引、FOCUS_DOC），而「首次命名」是唯一一次改名成本近乎为零的时刻——通常无资产、无互引，会话可以 reanchor。之后标题怎么演化都不再动文件名。需要两个小机制：官方 rename 入口（app 内或 agent 命令）+「仅从无标题变为有标题时触发」的规则。AI 在自己的会话里补标题并触发改名也安全：会话锚点由 app 管理可重挂；`FOCUS_DOC` 环境变量只影响旧进程重读，启动时快照已注入过全文。

**出口 2：出生即承认文件名不是名字。** 空标题创建直接用 `YYYY-MM-DD-HHMM.md`，AI 补标题只写 frontmatter，永不改名。代价就是上一节分析的「文件名索引」损失（应用内无感；文件系统里只剩时间索引，`rg '^title:'` 一条命令可重建映射）。好处是零新增机制、零张力。这就是上一问里的「纯时间戳」——在这个工作流下，它不是退化，而是被工作流合法化的选择。

**混合（我倾向的）。** 出生名 = 时间戳（身份永远诚实）；首次填标题时可选追加 `-slug` 装饰（有索引更好，没有也不丢身份）。因为身份已经住在时间戳里，slug 过时与否从此只是审美问题；不回填也永远不会出现 `untitled-N`。GitHub 的 `/issues/123/可选-slug` 就是这个结构。

### 在这个工作流下，对 AI 检索的实际影响

- 切题、内容检索、焦点注入都不变。
- 变的是「给一批新文档命名/分组」这类检索：以前文件名直接就是主题地图，以后要先读标题行。空壳阶段本来没有内容可索引，所以损失集中在「刚建、还没标题」的短暂阶段；标题回填后照旧。
- 真正要防的是习惯性退化：如果「不填标题」成为默认且永远不回填，文件名索引就永久消失——那时它已经不是「可以接受的退化」，而是应该正式切换到出口 2 的决策时刻。

### 建议

现在按已定方针维持现状，不动代码。将来若真的把「空标题创建」做成常规入口，建议同时做三件事，否则会得到 `untitled-N` 残骸：

1. 空标题时文件名叫 `YYYY-MM-DD-HHMM`，不叫 `untitled`；
2. 空标题时省略 `title:` 行（或修正空串兜底），避免空白行；
3. 决定是否在「首次获得标题」时做一次可选（可自动）的地址同步（出口 1）；我建议标成可选，不强制。

- [ ] 未来启用「空标题创建」时，出生名用时间戳（`YYYY-MM-DD-HHMM`）而非 `untitled`，并处理空标题兜底

### 决策记录

- 2026-11-23：用户决定维持现状——命名模型保持「日期 + 出生 slug」（即 C2 口径），不实施协议修改、改名命令与 UI 修补。本节为未来工作流的预研，不产生代码变更。

## 追问三：人直接进文件夹手工翻阅文档，必要性大不大？（2026-11-23）

**结论：作为日常导航几乎不必要；作为兜底和交接能力必须存在，但它是低频、突发的「逃生口」，不是工作流。产品自己的设计已经表明了这个立场。顺带修正上一节的理由：slug 之争真正保护的不是「人进 Explorer 翻文件」，而是路径作为文本标记的可读性——出现在 git log、agent 日志、报错、文档互引、拖进终端后的命令里，这些文本表面被读的频率远高于文件夹图标。**

- 应用内已有 Raw 文件树（`LeftPane.tsx:517`，`RawTree`），定位就是逃逸口；右键菜单的「在默认应用打开 / 在文件管理器中定位 / 复制路径」把 OS 级浏览做成按需一键桥接。Iris 的姿态是「应用是驾驶舱，文件系统是底座」，不是两套并列的浏览界面。
- plain files 的主要受益者不是人的文件夹浏览，而是：agent（`FOCUS_DOC`、`rg`、直接读写）、git（diff/历史/PR review）、以及应用失效或缺功能时的恢复能力。这个仓库 249 篇文档（顶层 issue 160、iris-agent 工作区 69、report 15、其余 5）在 Explorer 里已经不具备导航效率，且 Explorer 不渲染 frontmatter、不显示状态徽章、不做分组排序过滤。
- Explorer 只看字节、不懂语义：会话锚点、`.assets/` 伴生目录的聚合迁移、删除时的会话 reanchor 都只在应用内处理。手工在文件夹里移动 `.md` 会留下孤立的 `.assets/`，绕过应用的重锚定——这是「逃生口而非工作流」的又一理由。
- 真正让手工翻阅变得必要/频繁的场景有三类：新项目初始化时理解结构（一次性）、应用缺少某操作时的逃逸（低频突发）、把项目交给不用 Iris 的人（对方多数在 GitHub 网页上看，GitHub 渲染 Markdown 与 frontmatter 表，路径可读性同样重要——进一步支持保留 slug）。
- 若未来出现「用户在应用外频繁移动/改名文档」的信号，那说明应用缺功能，应补应用，而非为文件树做专门优化。
