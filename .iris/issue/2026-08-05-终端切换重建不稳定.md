现在在不同的页面之间切换的时候，有的TUI工作不是很稳定，就像codex，切过去居然是乱码，然后要缩放一下才能恢复正常，你现在把这个问题调研一下，现在开始

## 调研结论（2026-08-05）

这不是普通的字体乱码，也不像 PTY 字节丢失。现象与当前的“销毁可见 xterm，再从主进程 headless xterm 的序列化快照重建”机制高度吻合：切页后先看到的是重建画面；缩放改变终端行列数，ConPTY 向 Codex 发送真实 resize，Codex 随即全量重绘，所以画面恢复。

当前最明确的缺陷是：代码本来试图在每次重挂载时用一次 resize 唤醒 TUI 重绘，但这个 poke 实际被 main 进程吞掉了。

* `TerminalView.tsx:732-740` 首次 `fit()` 后无条件调用 `SESSION_RESIZE`，注释明确写着即使尺寸不变，也要让 TUI 知道“重新显示”。

* `session-manager.ts:390-393` 在新尺寸等于会话记录尺寸时立即返回，发生在 `pty.resize()` 之前。因此大多数同布局页面之间切换时，Codex 根本收不到 resize，也不会重绘。

* 用户缩放会令 cols/rows 真正变化，越过上述 early return，执行 `pty.resize()`；“一缩放立即正常”正是这一分支差异的直接外部证据。

### 为什么序列化重建本身可能出现乱屏

当前每次页面/会话切换都会卸载旧 `TerminalView`，新建 renderer xterm，然后调用 `SerializeAddon.serialize()` 把 main 进程的 headless xterm 状态编码成 ANSI，再喂给新 xterm。它恢复的是“终端缓冲区的近似可重放表示”，不是 Codex 自己的界面状态。Codex 这类 alternate-screen TUI 使用光标定位、滚动区、宽字符和频繁局部刷新，正是对序列化完整性最敏感的一类程序。

仓库已经为 serializer 漏掉 cursor visibility 和 DECSTBM 做了私有 polyfill，这本身说明该快照不能被视为无损状态迁移。只要仍有未覆盖的模式、宽字符边界或 resize/reflow 状态，重建画面就可能错位；真实 resize 让 TUI 从自身模型重新绘制后，自然会恢复。

另有一个需要实测区分的竞态：如果切页时 `fit()` 得出不同尺寸，main 进程会先同步 resize PTY 与 headless mirror，随后 renderer 马上请求 replay。Codex 响应 resize 的重绘字节是异步返回的，因此 snapshot 可能取在“headless 已 reflow、Codex 新画面尚未到达”的中间态。之后 live 输出理论上会补齐，但首帧仍可能短暂混乱。

### 已排除/降级的方向

* 旧问题中的 `display:none` + WebGL texture atlas 损坏不是当前主路径：现实现切换时直接 dispose/remount，不再保活隐藏 xterm。

* 单纯调用 renderer `refresh()` 或 `clearTextureAtlas()` 只能重画当前 buffer；若错误已经写进重建后的 buffer，它不能让 Codex 重新生成界面。

* 编码错误的可能性低：同一份内容仅通过 resize 就恢复，说明 UTF-8 传输和字体通常仍然有效。

## 建议修复方向

优先不要把复杂 TUI 的正确性建立在 serializer 快照完全等价于原终端上。

1. 给切换链路增加可观测点：记录 mount 前后的 renderer/headless/PTY cols×rows、no-op resize 是否被吞、replay 字节数，以及从切换到第一批 resize 后 PTY 输出的时间。先用一次 Codex 复现确认是“同尺寸 snapshot 失真”还是“变尺寸 snapshot 竞态”。
2. 做最小验证补丁：仅在 remount/replay 完成后，对 PTY 执行一次可辨识的强制 redraw 探针。如果必须用 resize，可临时做一次相邻尺寸再恢复原尺寸来验证机制，但不宜直接作为最终方案，因为它会造成两次 reflow、额外输出和界面闪动。
3. 最终方案优先考虑稳定挂载 terminal，并让隐藏实例保持有效布局尺寸（不能回到 `display:none`）；这样切回不需要 serializer 重建，也不会复发旧 WebGL atlas 问题。若资源占用不可接受，再设计“冻结 live 渲染 + 切回恢复 atlas/尺寸后继续”的生命周期，而不是每次从 ANSI snapshot 猜回 TUI 状态。
4. 若短期继续使用 replay，应把“resize 完成并收到 TUI redraw”与“取 snapshot”建立明确顺序；现在的同步 IPC 返回只表示 `pty.resize()` 被调用，不表示 Codex 已重绘完成。

## 首轮实现（2026-08-05）

已实现一个最小修复实验：

* `SESSION_RESIZE` 增加可选 `forceRedraw`。

* 终端 remount 的 replay 路径传入 `forceRedraw: true`；若尺寸未变，main 进程先把行数临时调整一格，再恢复目标行数，绕过 ConPTY 的同尺寸 early return，触发 Codex 的真实 resize/redraw。

* 等待 50ms 后再请求 headless scrollback snapshot；普通拖拽 resize、窗口调整和字体调整不使用该标志，不会额外双重 reflow。

验证：`npm run typecheck` 通过。`npm test -- --run` 中 65 个测试通过，另有既存的 `src/renderer/lib/editor-store.test.ts` mock 初始化错误导致测试套件失败，与本次改动无关。

* [ ] 使用当前开发版实际切换 Codex 页面，确认不再需要手动缩放恢复。

* [ ] 若仍出现乱码，抓取 trace，重点看 50ms 后是否有 Codex redraw 输出；再决定是否需要把“等待重绘”从固定延迟升级为基于 PTY 输出的确认。

## 第二轮实现（2026-08-05）

已将首轮的固定 50ms 延迟升级为一次由 main 进程负责的 replay 准备事务：

* renderer 通过 `SESSION_SCROLLBACK` 一次性提交目标 cols×rows；main 在同一事务内完成 resize/redraw、等待、headless parser fence 和 serialize，返回快照及其明确尺寸。

* 只对当前处于 alternate buffer 的 TUI 执行 redraw 等待；普通 shell 和已退出会话直接由 headless xterm 按目标尺寸重排，不承担额外等待。

* 同尺寸 TUI 先执行一行 nudge，等待其输出短暂安静后再恢复目标尺寸，避免 ConPTY 合并连续 resize。目标尺寸后的 PTY 输出需连续安静 50ms 才取快照，整个 redraw 阶段最多等待 500ms；超时会告警并降级取当前快照，不会卡住切页。

* 同一 session 的 replay 准备请求在 main 进程串行执行，快速来回切换不会让两个 resize 事务互相穿插。

* renderer 从首次测量到 replay fence 完成期间冻结 `ResizeObserver`、字体加载和设置变更触发的后续 `fit()`。若首份快照返回后应用一次待处理 fit 导致网格变化，会丢弃旧尺寸快照并按新尺寸重试一次；分块写入期间到达的 fit 继续延后到 fence 之后。

* 首轮的 `forceRedraw` IPC 参数和固定 50ms renderer 计时器已移除。

验证：`npm run typecheck` 通过；`npm test -- --run` 全部通过，共 7 个测试文件、67 个测试。
