vscode，左下角是有一个轻量级的git图形化界面的，现在iris要复刻他，你先去调研代码理解功能边界，然后将进度追加到issue下面

## 2026-08-05 调研进度

### 当前代码基础

- Iris 是 Electron + React 三进程结构，主界面由 `ThreePane` 维持稳定的左右分栏；左栏实现集中在 `src/renderer/components/layout/LeftPane.tsx`，当前只有文档透镜树/裸文件树和项目工具栏，没有底部状态栏或 Git 面板。
- 当前 Git 能力只有只读的 `project:git-head` IPC：主进程在项目根目录执行 `git rev-parse HEAD`，供 Status 列表比较 `reflects:` 新鲜度。执行封装、错误降级和每窗口项目根隔离可以复用，但目前没有通用 Git service、共享类型或 renderer store。
- `ProjectManager` 只监听 `.iris/`，其文件事件只用于文档树重投影。Git 面板需要观察整个仓库的索引、HEAD 和工作区变化，不能直接塞进现有 `.iris/` watcher，否则会混淆文档协议事件与仓库状态事件。
- 项目目前没有 `simple-git`/libgit2 依赖；已有实现通过 `execFile('git', args)` 调系统 Git。首版继续使用参数数组调用 Git 最符合现有依赖和安全边界，同时必须保持 3 秒级超时、`windowsHide`、项目根目录限定和失败可降级。

### 建议的首版功能边界

复刻 VS Code Source Control 的轻量工作流，不做完整 Git 客户端：

1. 左栏底部增加可折叠的 Source Control 区域；收起时显示当前分支和变更数，展开后占用左栏内部空间，不改变 `ThreePane` 的稳定外层分栏。
2. 展示仓库状态、当前分支，以及 `Changes` / `Staged Changes` 两组文件；状态解析使用 `git status --porcelain=v2 -z --branch`，避免依赖本地化文本并正确处理空格、重命名和非 ASCII 路径。
3. 支持刷新、单文件/全部暂存、单文件/全部取消暂存、填写提交信息并提交。提交后主动刷新；外部终端操作通过窗口重新聚焦和轻量轮询/失效刷新同步 UI。
4. 非 Git 仓库、Git 不可用、初始仓库无提交、merge/rebase 冲突和 detached HEAD 都作为明确状态展示，不能把它们统一吞成“无变更”。
5. 首版暂不包含 diff 编辑器、提交历史图、分支创建/切换、stash、pull/push/sync、远端认证和冲突解决器。这些依赖更重、交互风险更高，可在基础状态与暂存提交闭环稳定后拆分追加。

### 实现落点

- `src/shared/types.ts`：增加仓库快照、文件状态、分组和 Git 操作结果类型。
- `src/shared/protocol.ts`：增加 Git 状态查询与 stage/unstage/commit 指令通道，以及仓库状态失效事件。
- `src/main/`：新增独立 `GitManager`，负责受限命令白名单、porcelain 解析、仓库状态刷新和 watcher/失效节流；继续通过窗口上下文取得并约束当前项目根。
- `src/renderer/stores/`：新增 `git-store`，管理 idle/loading/ready/error、刷新合并和操作中的禁用状态；不要把 Git 投影混入 `project-store`。
- `src/renderer/components/git/`：拆出折叠入口、提交框、变更分组和文件行；`LeftPane` 只负责挂载，避免继续膨胀。
- 测试重点放在 porcelain v2 `-z` 解析（修改、删除、新增、重命名、冲突、特殊路径）、命令参数白名单/路径约束，以及临时仓库中的 stage → unstage → commit 集成闭环。

### 待确认

- [ ] “左下角”目标是否就是左栏底部的 Source Control 折叠区；若指 VS Code 最底部状态栏的分支/同步入口，布局和首版范围需要相应收窄。
- [ ] 首版提交是否允许直接调用用户现有 Git hooks 与签名配置；默认建议遵循原生 `git commit` 行为，失败信息原样摘要展示，不自动绕过 hooks 或签名。

## VS Code SCM 源码对照与实现方案（2026-08-05）

以下结论已按 Microsoft VS Code 官方仓库 commit `3e63ea8facbd2c415f456953e136c19305dee97d` 核对。

### 源码中的关键分层

- `src/vs/workbench/contrib/scm/common/scm.ts` 定义 SCM provider、resource group、resource state、输入框和 command 的通用契约。视图不解析 Git 输出，只消费 provider 的投影。
- `src/vs/workbench/contrib/scm/common/scmService.ts` 管理多个 provider、激活 provider 和 repository 生命周期；仓库变化通过 provider 的 change event 触发重投影。
- `src/vs/workbench/contrib/scm/browser/scmViewPane.ts` 负责 Source Control 视图：提交输入框、资源组标题、资源行、空状态、刷新和操作菜单；资源行的上下文菜单来自 SCM menu service，而不是把 Git 命令硬编码在组件中。
- `src/vs/workbench/contrib/scm/browser/scmViewPaneContainer.ts` 和 `scmViewService.ts` 负责视图容器、可见仓库、焦点仓库和 provider 切换；视图布局与仓库模型解耦。
- `src/vs/workbench/contrib/scm/browser/menus.ts` 与 `scm.contribution.ts` 把动作注册为 command/context key，再由菜单和快捷键复用。
- `extensions/git/src/commands.ts`、`extensions/git/src/repository.ts`、`extensions/git/src/model.ts` 是 Git 实现层：repository 通过 Git CLI 读取状态，model 把 porcelain 状态转换为资源组/资源状态，并以事件通知 SCM provider；UI 不直接执行 `git`。

### 对 Iris 的具体方案

1. **领域模型**：新增 `GitRepositorySnapshot`（root、branch、head、ahead/behind、detached、hasCommits、error）和 `GitResource`（path、originalPath、indexStatus、worktreeStatus、conflicted）。固定两个资源组 `changes` 与 `staged`，额外保留 `conflicts` 标记，不把 Git 文本直接暴露给 React。
2. **主进程 repository/model**：新增 `src/main/git-manager.ts`，按 VS Code `Repository`/`Model` 的职责拆分：`GitRepository` 只负责执行白名单命令和解析 `--porcelain=v2 -z`；`GitModel` 缓存快照、计算分组并发出 `changed`。所有命令都使用 `execFile` 参数数组、项目根 `cwd`、超时和取消/串行队列。
3. **IPC provider 边界**：在 `protocol.ts` 增加 `GIT_STATUS`、`GIT_STAGE`、`GIT_UNSTAGE`、`GIT_COMMIT`、`GIT_REFRESH`；增加 `evt:git:changed`。renderer 只通过 IPC 取得快照和发起动作，不能自行拼接 shell 命令。路径参数必须是仓库根内的相对路径，提交信息必须是非空字符串。
4. **事件与刷新**：VS Code 的核心是 provider change event。Iris 保留现有 `.iris/` watcher，同时在 `GitManager` 对仓库工作树、`.git/index`、`HEAD`、refs 做 debounced watcher；watcher 只发送失效事件，随后由 renderer store 拉取完整快照，避免 IPC 广播大对象和竞态覆盖。
5. **renderer store/view**：新增 `git-store`，状态机为 `idle → loading → ready/error`，动作期间记录 `pendingOperation` 并串行化；新增 `components/git/SourceControlPanel.tsx`、`GitResourceGroup.tsx`、`GitResourceRow.tsx`。`LeftPane` 只挂载面板和折叠状态，面板内部用 VS Code 类似的 resource group/header/resource row 结构。
6. **命令菜单**：不在每个行组件里散落按钮逻辑；集中定义 Git command descriptors（refresh、stage、unstage、stage all、unstage all、commit），由行和组标题按上下文显示。这样后续接入键盘快捷键、右键菜单和命令面板时不改领域层。
7. **提交与错误语义**：提交直接执行原生 `git commit`，保留 hooks、签名和用户配置；返回 stdout/stderr 摘要。无仓库、无 HEAD、冲突、锁文件、hook 失败分别建模，UI 显示可操作错误并保留刷新入口，不降级成空列表。
8. **测试顺序**：先写纯函数 porcelain 解析测试，再写 GitManager 临时仓库测试（status、stage、unstage、commit、重命名和冲突），最后补 store 的事件重拉取/过期响应测试与左栏面板渲染测试。实现前应锁定一个 VS Code commit，逐项核对上述源码路径的实际 API 名称。

### 已读取源码后的修正（VS Code `3e63ea8`）

这次已从 Microsoft 官方仓库浅克隆并实际读取以下文件：
`src/vs/workbench/contrib/scm/common/scm.ts`、
`src/vs/workbench/contrib/scm/common/scmService.ts`、
`src/vs/workbench/contrib/scm/browser/scmViewPane.ts`、
`extensions/git/src/model.ts`、`extensions/git/src/repository.ts`、
`extensions/git/src/watch.ts`。

- VS Code 的基础契约不是“文件状态数组”，而是 `ISCMProvider → ISCMResourceGroup → ISCMResource` 三层对象；provider 暴露 `inputBoxTextModel`、`count`、`acceptInputCommand`、`statusBarCommands`，并通过 `onDidChangeResourceGroups` / `onDidChangeResources` 通知视图。
- `SCMViewPane` 订阅 repository/provider/group 的变化事件，资源行只负责渲染 URI、装饰和菜单 action；因此 Iris 也应让 `git-store` 输出稳定的 provider/group/resource 投影，React 行组件不能直接解析 Git 命令结果。
- Git `Repository` 实际创建四个 group：`merge`（Merge Changes）、`index`（Staged Changes）、`workingTree`（Changes）、`untracked`（Untracked Changes）；其中 index/workingTree 开启多文件 diff。Iris 的模型应保留四组，不能把 untracked 混入普通 changes，也不能只用冲突布尔字段替代 merge 组。
- `repository.ts` 在初始化时为仓库工作树和 `.git` 关键文件安装 watcher；注释明确要求工作树变化、`.git` 第一层变化触发 `git status`，但忽略 `index.lock` 和 fsmonitor cookie。Iris 的 watcher 方案应采用同样的过滤规则，watcher 只触发重新取状态，不直接修改快照。
- Git model 用 `onDidChangeRepository`、`onDidRunGitStatus`、`onDidChangeState` 和 operation 事件区分“仓库状态变化”“状态命令完成”“生命周期变化”“提交进行中”。Iris 应至少拆分 `snapshotChanged` 与 `operationChanged`，提交期间禁用输入框和重复操作，不能只靠一个 loading 标志。
- `SCMViewPane` 的 resource/group action 通过 repository menus 获取，资源行还支持 folder menu 和多选操作。首版 Iris 可先实现组标题和单行菜单，但 command descriptor 必须集中注册，后续才能自然补齐多选、目录折叠和右键菜单。

据此调整首版实现顺序：先落地四组资源模型、watcher 失效与提交输入框，再接入 stage/unstage 命令；分支状态栏、diff、历史图和远端操作继续排在后续阶段。
