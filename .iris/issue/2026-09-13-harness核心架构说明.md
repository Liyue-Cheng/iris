## 调研结论（2026-09-13）

Iris 的 harness 核心不是一个“聊天窗口”，而是一套以项目文件为长期事实、以 Agent Session 为执行边界、以 Worker + Provider + JTP 工具为运行时的受控执行系统。它把一次用户请求拆成可追踪的 Intent/Turn/Invoke/Attempt，并通过事件协议、持久化 Trace 和投影层把运行态还原到 UI。

### 分层架构

1. **项目与上下文层（长期记忆）**

   * `.iris/issue|status|report|misc` 是事实载体；代码、测试和 Git 也是可验证状态。

   * `prompt.ts` 将固定 Agent 指令、`AGENTS.md` 软件规则、项目规则和当前锚定文档组装成分层 prompt，并记录 fingerprint。

   * `trace-context.ts` 从 Session Trace 纯函数投影 provider history；支持显式 compaction summary，避免上下文只存在于聊天记录。

2. **Session 聚合与状态机层（控制平面）**

   * `AgentSessionAggregate` 是核心领域对象：包含 anchor、revision、workerEpoch、Intent 链、Turn、Invoke/Attempt、工具操作、mailbox、compaction、任务摘要等。

   * `session-domain.ts` 只通过状态转换函数完成 pause/resume/complete/supersede/rewind/close，利用 revision 和 correlation 丢弃过期事件。

   * Session 是锚定的、可暂停和可恢复的工作单元；关闭只归档实例，Trace/History 保留。

3. **Mailbox/Intent 调度层（并发边界）**

   * 用户请求和 task-terminal 回调进入持久化 mailbox，由单一 Intent consumer 顺序消费；同一 Session 的 mutation chain 串行化。

   * 这使“多来源输入”不会并发改写同一个聚合，同时保留 dedupe、supersede 和 rewind 语义。

4. **执行隔离层（Worker Host）**

   * `AgentWorkerHost` 按 Session 懒加载 `worker_threads`，启动时加载 history/runtime，并用 protocol version、workerEpoch、history digest、shell identity 做握手校验。

   * `agent-worker.ts` 在 Worker 内驱动 Pi session：处理 run/resume/abort/tool-result，串行 provider event chain，发出 state、delta、tool-call、pause/settled 等事件；空闲超时回收 Worker。

   * 因此主进程负责生命周期与持久化，模型调用和流式事件在隔离线程执行，避免阻塞 Electron 主循环。

5. **模型适配层（Provider/PI）**

   * `pi-adapter.ts` 把 Pi 当作 API transport 和模型元数据库；可配置 provider profile、代理、模型参数，Iris 自己拥有可选模型目录。

   * provider 调用分为逻辑 Invoke 与具体 Attempt，支持失败重试、暂停后续跑和 provider replay；请求 payload 经过脱敏并写入审计 artifact。

6. **工具执行层（JTP）**

   * 工具由 JTP descriptors/registry/runtime 组成，内建 `read/edit/write/terminal` 和 `task_*`；MCP 工具可发现并注册。

   * Worker 发起 tool call，主进程通过 correlation 将其路由到 JTP provider；文件工具、终端 PTY、后台任务由各自 provider 执行，结果再以 `tool-result` 回传 Worker。

   * 长任务由 `AgentTaskManager` 管理，拥有独立 JSON 元数据、日志、取消和恢复语义，并把摘要回写 Session。

7. **持久化与投影层（事实→视图）**

   * Session store 以 append-only journal + snapshot 保存聚合；`session-model` 负责 clone、projection 和 diff，Renderer 只消费投影状态。

   * 终端输出采用镜像、日志、批量 IPC 和 ack backpressure；挂载时 replay，避免 UI 重连造成重复输出或无界队列。

   * provider context artifact 做 secret/image 脱敏，保留可审计的调用证据。

### 我对这套架构的理解

这是一种“项目中心、事件驱动、可恢复执行”的 harness。核心抽象不是模型或对话，而是 **Session 作为聚合根，Intent 作为用户意图，Invoke/Attempt 作为可重试的执行账本，Trace 作为上下文事实，文件系统作为跨工具合同**。模型只是可替换的推理资源；Worker、PTY、MCP、Provider 都是边界清晰的执行适配器。

它解决的主要问题有三类：

* **连续性**：Agent 或 CLI 会消失，但 issue、Trace、快照和代码留下来，下一次执行可从持久化事实恢复。

* **可控并发**：mailbox、session mutation chain、correlation 和 epoch 让迟到事件、重复回调、停止/恢复不会污染新状态。

* **可审计安全**：每次请求有 fingerprint、Invoke/Attempt 记录，provider payload 脱敏，工具和终端都有独立结果与生命周期。

代价是领域模型和协议较重：一次简单请求也要经过 Session、Intent、Turn、Invoke、Attempt、JTP 和 projection 多层；调试需要同时看 journal、worker 事件和 provider artifact。这个复杂度是为了获得可恢复性与证据链，而不是追求最短调用路径。

从演进角度看，当前 harness 更像“单 Session 内的可靠执行内核”，已经具备暂停、恢复、重试、压缩、后台任务和监督能力，但仍不是通用的 headless orchestration 平台；README 也明确没有自治调度队列。未来若扩展，应优先保持 Session 聚合边界、文件合同和显式并发规则，再增加队列或多 Agent 协作。

### 依据代码

* `src/main/agent/session-manager.ts`：Session 生命周期、mailbox、JTP/PTY 绑定与投影聚合。

* `src/main/agent/session-model.ts`、`session-domain.ts`：聚合数据结构和状态转换。

* `src/main/agent/worker-host.ts`、`agent-worker.ts`、`src/shared/agent-protocol.ts`：Worker 隔离与版本化事件协议。

* `src/main/agent/pi-adapter.ts`：Provider/模型适配、Invoke/Attempt 和请求审计。

* `src/main/agent/trace-context.ts`、`compaction.ts`：Trace 到 provider context 的确定性投影与压缩。

* `src/main/agent/task-manager.ts`、`src/main/jtp/*`：后台任务、终端和工具执行。

## Agent 与 Iris 的耦合度及独立 Benchmark 可行性

### 结论

当前耦合度是**中高**：Agent 的模型执行内核已经有清晰边界，但完整 Agent 产品运行时仍深度依赖 Iris 的 Session Manager、Store、项目作用域、Settings、JTP Provider、PTY 和 Electron Worker 生命周期。直接把 `src/main/agent` 目录拷走做独立 benchmark，成本较高；抽取其中的“执行内核”做 benchmark，则可行，预计属于中等规模重构。

### 耦合分布

**相对独立的部分**：

* `pi-adapter.ts`：Provider profile、模型选择、代理和 Pi transport，输入输出主要是显式 options。

* `agent-worker.ts` + `worker-host.ts`：已经通过 `agent-protocol.ts` 定义了版本化消息边界，理论上可由 CLI 或 benchmark runner 驱动。

* `session-domain.ts`、`trace-context.ts`、`compaction.ts`：大部分是纯领域函数，适合离线回放和确定性测试。

* `jtp/runtime.ts`、`registry.ts`：工具描述、校验、幂等和取消语义本身也具备独立性。

**与 Iris 强耦合的部分**：

* `session-manager.ts` 是最大耦合点：同时协调 ProjectManager、SettingsManager、SessionStore、JTP、PTY、TaskManager、MCP、窗口 scope 和 renderer projection。

* Session Store 的目录、snapshot/journal、`.iris` anchor 和项目 root 假设，使持久化格式带有 Iris 产品语义。

* JTP 内建 provider 直接依赖 Iris 文件系统、终端和后台任务实现；脱离 Iris 后必须提供替身 runtime。

* Worker 的初始化 runtime 需要 Iris 的 cwd、agentDir、providerProfileRoot、shell，以及与 Session revision/history digest 对齐。

* compaction、prompt injection 和 issue 状态规则来自 Iris 的软件协议，不是通用 Agent 能力。

### 做 Benchmark 的难度

如果 benchmark 只测试“模型在固定上下文下选择工具并完成任务”，并不难：可以绕开 SessionManager，直接构造 `AgentHistorySnapshot`，启动 Worker，注入内存 JTP providers，记录 protocol events 和最终文件 diff。

如果 benchmark 要测试真实产品行为——跨多轮、暂停恢复、重试、上下文压缩、后台任务、终端监督、崩溃恢复和持久化一致性——难度明显上升，因为这些能力由 SessionManager + Store + TaskManager 的组合实现，不能只测 Pi adapter。

### 建议的拆分方式

将 harness 拆成三层契约：

1. **Agent Core**：protocol、worker loop、provider adapter、trace/context projection、invoke/attempt 状态机。
2. **Execution Ports**：抽象 `ToolExecutor`、`TerminalExecutor`、`TaskExecutor`、`ArtifactStore`、`Clock`、`EventSink`、`ModelProvider`。
3. **Iris Runtime Adapter**：SessionStore、ProjectManager、JTP 内建工具、Electron IPC、PTY、`.iris` prompt injection。

Benchmark runner 只实现第二层 ports，并使用内存或临时目录适配器；Iris 继续使用同一 Core，通过自己的 Runtime Adapter 接入产品能力。这样 benchmark 测的是同一执行内核，而不是另写一套“近似 harness”。

### 最值得先做的抽取

优先把 `session-manager.ts` 中的三类逻辑移出：

* Intent mailbox 消费和 Invoke/Attempt 调度；

* Worker/JTP 事件到领域事件的归约；

* Context 构造、compaction 和恢复决策。

保留项目路径、Electron、Settings、PTY 和 renderer projection 在 Iris adapter 中。第一阶段甚至不必移动文件，只需定义 port 接口并为 benchmark 提供 fake 实现，即可验证边界。

### 风险判断

最大的风险不是技术上无法拆分，而是 benchmark 逐渐依赖 Iris 特有的 prompt、`.iris` 文档和工具结果格式，最后测成“某个 Iris 工作流”而非 Agent 能力。应明确区分：通用 harness 指标（工具选择、恢复正确性、重试行为、上下文利用率）与 Iris 产品指标（issue 回写、文件冲突处理、窗口生命周期、PTY replay）。

## 独立 Agent Core 与 Benchmark 准备度

这项工作总体是**中等难度、风险可控**，但不适合直接把现有目录复制出去。最稳妥的顺序是先建立独立 Core 的协议测试和最小 runner，再接入 DeepSWE/Pier 与 Terminal-Bench/Harbor。

### 推荐分阶段

**阶段 0：冻结 Core 契约**

明确 benchmark 只依赖以下接口：

* `run(instruction, workspace, runtimeConfig)`

* `ToolExecutor.invoke(request)`

* `EventSink.onEvent(event)`

* `ModelProvider.stream(...)`

* `ArtifactStore`、`Clock`、`CancellationSignal`

Iris 的 ProjectManager、Settings、Electron IPC、Renderer projection、`.iris` 文档语义不得出现在 Core 接口中。

**阶段 1：独立最小执行器**

在临时目录中运行 Worker + Provider + 内存 JTP，至少支持：文本请求、工具调用、连续多轮、失败返回、abort、事件顺序和最终 settled 状态。此阶段不接真实 Iris Session Store，也不接 UI。

**阶段 2：确定性回放测试**

加入 fake model 和 fake tools，用固定事件流验证：

* 相同 history 得到相同请求上下文；

* tool call 必须 exactly-once 或明确返回 duplicate；

* provider failure、暂停、resume、retry 的状态可重放；

* 迟到 worker event 不会写入新 intent；

* context compaction 后仍保留当前 system/project/anchor 优先级；

* abort 和 worker crash 不会留下“假完成”。

**阶段 3：真实模型 smoke test**

只使用少量人工任务验证 Provider、shell、文件工具和超时行为。先跑 3 个 DeepSWE 任务和 3 个 Terminal-Bench 任务，确认 verifier 能看到修改，再扩大到 10/30 题。

**阶段 4：Benchmark adapter**

* DeepSWE：实现 Pier 的 agent adapter，优先把现有 CLI 包成单进程 runner。

* Terminal-Bench：优先实现 Harbor Installed Agent；只有当 orchestration 必须控制容器生命周期时才采用 External Agent。

* benchmark adapter 只负责 instruction、cwd、环境变量、退出码和日志映射，不复制评分逻辑。

### 什么时候算“可以放心接入”

至少满足以下门槛：

1. Core 可以在没有 Electron、ProjectManager 和 `.iris` 目录的临时 workspace 中启动。
2. 协议测试覆盖 run/resume/abort/tool-result/shutdown 和 worker 重启。
3. fake model 测试能稳定重放关键状态转换，连续运行结果无随机漂移。
4. 工具执行有明确的超时、取消、幂等和错误语义。
5. benchmark verifier 在 smoke test 中能观察到 Core 产生的文件修改。
6. Core 指标与 Iris 产品指标分开记录：模型调用、工具选择、恢复行为属于 Core；Issue 回写、PTY replay、窗口生命周期属于 Iris。

### 难度判断

* **只做独立 Core harness + fake 测试：较好做，约中等重构。** 主要工作是从 `session-manager.ts` 抽出 ports 和调度逻辑。

* **接入真实 Provider 并跑小规模 benchmark：可做，集成工作中等。** 主要风险是 shell、网络、凭据、容器和日志边界。

* **同时复现 Iris 全部持久化、compaction、后台任务和终端监督：不适合作为第一阶段。** 这会把 benchmark 变成 Iris runtime 的移植项目。

因此，答案是“好干，但必须先做 Core 隔离和契约测试”。只要阶段 1/2 通过，接 Pier/Harbor 本身不会是主要风险；如果跳过它们，跑出的失败无法区分是 Agent 能力、Iris 耦合还是 benchmark adapter 错误。

## 彻底解耦为通用 Agent Core 的工作量评估

### 总体判断

如果目标是“Agent 核心可以被另一款软件直接集成”，不是只做 benchmark adapter，那么这是一次**中大型架构重构**。现有代码已经具备可抽取的执行内核，但产品编排、持久化、工具实现和 Electron 生命周期目前集中在 `session-manager.ts` 周围，不能通过简单移动文件完成。

粗略估算（1 名熟悉现有代码的工程师）：

- **最小可用 SDK（能被另一软件启动、调用工具、接收事件）**：4–8 周。
- **可用于 benchmark 和内部集成的稳定 Core**：8–14 周。
- **生产级通用运行时（版本兼容、持久化迁移、插件 API、文档、跨平台和完整测试）**：4–8 个月。

以上不包含新 UI；若还要把现有 Iris Agent 全量迁移到新 Core 并保持行为一致，通常要在上述基础上增加 30–50% 的回归和迁移工作。

### 必须拆开的边界

1. **领域内核**：Session/Intent/Turn/Invoke/Attempt、暂停恢复、重试和取消。这里要去掉 Iris 类型名和 `.iris` 语义，改成通用 workspace/anchor/context 模型。
2. **执行端口**：ModelProvider、ToolExecutor、TerminalExecutor、TaskExecutor、ArtifactStore、EventSink、Clock、Cancellation。
3. **运行时编排器**：Mailbox、单 Session 串行化、事件归约、worker 生命周期和崩溃恢复。
4. **存储接口**：把当前 JSON journal/snapshot 从领域代码中抽成可替换 Store；另提供内存 Store、文件 Store 和 Iris Store。
5. **Prompt/Context 接口**：Core 只接受已组装的系统指令、项目规则和 anchor material；Iris 的 `AGENTS.md`、Issue 状态规则和 prompt injection 放在适配层。
6. **工具插件 API**：JTP descriptor/registry 可以保留思想，但协议要稳定、文档化，不能要求调用方导入 Iris 的 FileProvider/TaskManager。
7. **观测与安全接口**：日志、provider payload 审计、secret redaction、指标和 trace exporter 都通过接口注入。

### 主要工作包

- **依赖反转与包拆分（2–4 周）**：建立 `agent-core`、`agent-runtime`、`agent-adapters/iris`、`agent-cli` 四个包；清理 Core 对 Electron、ProjectManager、SettingsManager 和 `.iris` 的直接 import。
- **Session 编排抽取（2–4 周）**：从 `session-manager.ts` 抽出 mailbox、调度、状态归约和恢复逻辑；保留 Iris manager 作为 facade。
- **通用 Store 与迁移（2–4 周）**：定义 journal/snapshot/attachment/artifact 接口，实现内存和文件实现，并让现有 Iris 数据格式通过 adapter 继续可读。
- **工具和终端端口化（2–3 周）**：把 read/edit/write/terminal/task 拆成插件；明确沙箱、超时、取消、幂等和权限模型。
- **独立 CLI/Runner（1–2 周）**：不依赖 Electron 启动 worker，提供 JSONL 或 SDK 接口，供 Pier/Harbor 和其他软件调用。
- **契约测试与回归（3–6 周）**：fake provider/tool、事件回放、崩溃恢复、并发、版本握手、上下文压缩、迁移和跨平台 shell 测试。
- **Iris 迁移（2–4 周）**：让 Iris 通过 adapter 使用新 Core，确保现有 session projection、PTY replay、issue 工作流和设置行为不回归。

这些工作包存在并行空间，但测试和 Iris 迁移依赖前面的接口稳定，因此总工期不能简单相加。

### 最危险的部分

- **Session 模型泛化**：当前 aggregate 混合了通用执行状态和 Iris 产品字段，拆分时最容易破坏恢复语义。
- **工具语义**：文件编辑、终端和后台任务的结果格式目前带有 Iris 假设；若只抽类型、不抽语义，其他软件仍然无法真正接入。
- **持久化兼容**：journal/snapshot 的 schema、attachment 和 compaction 必须有版本化迁移，否则现有会话无法平滑升级。
- **Provider 与安全**：凭据、代理、脱敏和 artifact 逻辑必须从 Iris 用户目录中脱离，同时保持审计能力。
- **行为一致性**：新 Core 必须由同一组契约测试证明与现有 Iris 行为一致，不能以“编译通过”作为迁移完成标准。

### 推荐目标形态

```text
agent-core                # 纯 TypeScript，可在 Node/其他宿主运行
  ├─ domain                # 状态机、Trace、Context、compaction
  ├─ protocol              # worker/runtime/事件协议
  ├─ runtime               # mailbox、调度、恢复
  └─ ports                # model/tool/store/clock/observability

agent-adapters-iris       # Iris Store、JTP、PTY、.iris prompt、Electron
agent-adapters-harbor     # Harbor/Pier workspace 与日志适配
agent-cli                 # JSONL/stdio runner，供外部软件调用
```

核心验收标准是：在没有 Electron、`.iris`、ProjectManager 和 Iris SessionStore 的环境中，另一个宿主能够通过 SDK/JSONL 启动一次或多次执行；替换 Store、ToolExecutor 和 ModelProvider 后，状态和事件语义保持一致；Iris 本身再作为一个 adapter 使用它。

### 投资建议

如果当前目标只是验证 agent 能力，先做 4–8 周的最小 Core，不要立即承诺完整通用 SDK。如果确定未来要服务多个产品，应尽早建立独立 package 和 ports，即使第一版仍复用现有实现；最忌讳继续向 `session-manager.ts` 添加 Iris 特有逻辑，否则后续解耦成本会按功能数量增长。

## 彻底解耦目标的收敛版评估（仅 Core + JTP tools + 薄 CLI）

用户已明确范围：不迁移 Iris UI，不包含 TUI，不把终端交互界面做成通用产品；交付物是一个可被其他软件引用的 Agent Core（内含 JTP 内建 tools）、一个很薄的 `myagent run --prompt ...` CLI，以及 Iris 对该 Core 的直接引用。

### 工作量重新估算

在这个范围下，工作量低于“通用 Agent 平台”估算：

- **可运行的最小版本：3–5 周**（一名熟悉代码的工程师）。
- **能先用于 benchmark 的可靠版本：6–10 周**。
- **生产级可发布 SDK：10–16 周**，主要增加 API 稳定、schema 迁移、跨平台和文档，而不是增加新 Agent 能力。

这里假定继续使用当前 Pi provider 适配、Node.js 运行时和现有文件/终端工具实现；不包含重新设计模型供应商体系，也不包含 Harbor/Pier 本身的维护。

### 建议的目标包

```text
packages/agent-core
  domain/       # session、intent、turn、invoke、attempt、trace、compaction
  runtime/      # mailbox、调度、worker host、恢复、事件归约
  protocol/     # Worker/JTP/事件协议
  tools/        # JTP descriptor、registry、runtime + read/edit/write/terminal
  provider/     # Pi transport、provider profile、stream/retry
  storage/      # memory store、file journal/snapshot、attachment/artifact
  ports/        # workspace、model、clock、event、artifact 等接口

packages/agent-cli
  myagent run --prompt ... --cwd ...

packages/agent-iris-adapter
  Iris prompt、SessionStore、ProjectManager、Settings、Electron 生命周期
```

Core 内可以保留 terminal **工具**（通过子进程或 PTY 执行命令并返回结果），但不保留 Iris 的 terminal **UI/TUI/replay projection**。长任务 `task_*` 也应保留为可选 Core tool provider；其进程监控和日志存储通过 `TaskExecutor`/`ArtifactStore` port 注入。

### 必须重构的关键点

1. **从 `session-manager.ts` 拆出无 UI 的 orchestrator**：保留 mailbox、单 Session 串行、事件归约、暂停/恢复和重试；移除 Renderer projection、window scope 和 Electron 事件。
2. **把 JTP Native Execution 改成 Core tool provider**：文件工具只依赖 workspace root；terminal 只依赖 Shell/Process port；task 工具只依赖 Task port。
3. **把 `IrisAgentSessionStore` 抽象成 `SessionStore`**：Core 提供文件实现和内存实现，Iris 可继续用同一格式或包一层 adapter。
4. **把 prompt 组装改为输入**：Core 接受 system prompt、workspace instructions 和 anchor material；Iris 负责读取 `AGENTS.md`、`.iris` 和 issue。
5. **建立 CLI 进程边界**：CLI 负责参数解析、stdio/JSONL 事件输出、退出码和信号转发；Core 不读取 argv，也不打印面向用户的文本。
6. **共享一套契约测试**：Iris facade、CLI 和 benchmark runner 都调用同一 Core API，避免三套行为分叉。

### 不应带入 Core 的 Iris 依赖

- `ProjectManager`、`SettingsManager`、Electron `app`/IPC/window。
- `.iris` 文档类型、Issue 状态流转、Iris prompt 模板和 focus injection。
- Renderer projection、终端 replay、output batcher、窗口 generation。
- Iris 专用日志目录和用户数据路径约定。

### 交付验收

- 在干净 Node 进程和临时目录中，执行 `myagent run --prompt ... --cwd ...`，无需 Electron 或 `.iris` 即可完成一次工具任务。
- `read/edit/write/terminal/task_*` 通过同一个 JTP 协议工作，支持超时、取消、错误和幂等。
- Core 可由 Iris 以库方式启动；Iris 的 prompt、持久化和 UI 只是 adapter。
- fake provider/tool 契约测试与真实 provider smoke test 均通过；benchmark adapter 只做环境映射。
- CLI 的 JSONL 日志可以被 Pier/Harbor 收集，退出码能准确反映 Core settled/failed/aborted 状态。

### 判断

这不是“重写一个 Agent”，而是把现有 Agent 的**编排层和工具层从 Iris 外壳中反转依赖**。如果严格保持上述范围，6–10 周可以得到值得跑 benchmark 的独立 Core；最大风险集中在 `session-manager.ts` 的拆分和持久化兼容，而不是 CLI 本身。

## 设置归属：哪些属于 Agent Core，哪些留在 Iris

在“Core + JTP + 薄 CLI，Iris 直接引用 Core”的目标下，当前 `Settings.experimental` 不能整体继续叫 Iris 设置。应把**可影响 Agent 执行语义的配置**迁移到 Core 配置，把**是否在 Iris 中展示和如何与 Iris 集成的配置**留在 Iris。

### 应迁移到 Agent Core 的设置

- **Provider profiles、API Key、base URL、代理和模型目录**：这是模型运行时配置，CLI、Iris、benchmark 都需要一致读取。凭据应由 Core 的 `CredentialStore` 管理；Iris 设置页只是一个管理界面。
- **默认模型**：应成为 Core 的 default model/profile 配置。Iris 可以保存“本窗口/本项目最后选择的模型”作为 UI 偏好，但不要再把它定义成 Iris Agent 专属设置。
- **JTP 内置工具启用开关**：`read/edit/write/terminal/task_*` 直接决定 Core 的能力集合，应由 Core runtime config 提供。Iris 可在设置页编辑并持久化这份配置。
- **MCP server 配置**：属于工具运行时，应迁移到 Core 的 tool provider 配置。Iris 只负责编辑、启停和展示连接状态。
- **执行策略**：未来应统一放入 Core，例如最大并发、单命令超时、上下文预算、compaction 阈值、重试次数、日志/审计级别、网络代理和 shell 选择。当前部分阈值散落在代码或 manager options，应在解耦时收拢成版本化 `CoreConfig`。
- **凭据和 Provider 安全策略**：secret redaction、artifact 保留策略、允许的 provider host 等应是 Core 的安全配置；Iris 不应拥有一套不同语义。

建议 Core 配置最少包含：

```ts
interface AgentCoreConfig {
  model?: ModelRef;
  providers: ProviderProfileConfig[];
  tools: Record<string, boolean>;
  mcpServers: McpServerConfig[];
  execution: {
    context?: ContextBudgetConfig;
    compaction?: CompactionConfig;
    retry?: RetryConfig;
    terminal?: TerminalPolicy;
  };
}
```

### 应继续留在 Iris 的设置

- **`experimental.irisAgent`**：短期保留为 Iris 的功能开关，控制是否在 Iris UI 暴露 Agent 入口。Core 本身不应知道“experimental”或“启用 Iris Agent”。稳定后可改名为 `features.agent`。
- **`agents: AgentConfig[]`**：这些是外部 CLI 启动器（Claude/Codex/Gemini/shell）的菜单和命令行配置，属于 Iris 的“open with”产品功能，不属于 Core。
- **Iris prompt 与项目规则相关选项**：`.iris` 文档、`AGENTS.md`、Issue 状态流转和 focus injection 是 Iris adapter 的上下文组装策略。Core 只接收已经组装好的 prompt/context。
- **Session UI 偏好**：默认打开位置、面板布局、是否显示历史、Renderer projection、终端 replay 和窗口生命周期都留在 Iris。Core 只提供事件和状态。
- **项目与窗口设置**：`project.openRoots`、`recentRoots`、`commandTrust`、窗口恢复等仍由 Iris 管理。`commandTrust` 若未来成为通用沙箱策略，再通过 Core 的 `WorkspacePolicy` port 注入，而不是直接让 Core 读 Iris settings。
- **外观、编辑器、终端字体、语言、确认行为**：全部是 Iris UI/工作区偏好。

### 需要拆成“Core 配置 + Iris 映射”的项目

- **`irisAgentDefaultModel`**：Core 保存全局默认模型；Iris 额外保存最近选择的模型或按项目覆盖，但通过 Core API 写入。
- **`jtpTools`**：Core 定义稳定工具 ID 和默认值；Iris 保存用户选择并在创建 runtime 时传入。其他宿主可用自己的配置文件。
- **`mcpServers`**：Core 定义 schema 和生命周期；Iris 只负责 UI、加密存储入口和事件展示。
- **终端 shell/超时**：Core 需要 shell 与 timeout port；Iris 的平台能力负责提供实现和默认值。

### 设置架构建议

不要让 `agent-core` 直接依赖 Iris 的 `SettingsManager`。改为：

```text
CoreConfigSchema + CoreConfigStore      # agent-core 提供
IrisAgentConfigAdapter                  # Iris 把 ~/.iris/settings 映射进去
CliConfigAdapter                        # CLI 使用 ~/.config/myagent 或项目配置
BenchmarkConfigAdapter                  # benchmark 固定实验参数
```

Iris 设置页仍可以显示“Agent Core”分组，但保存动作应调用 Core config service，而不是直接修改 `experimental` 任意字段。这样 CLI、Iris 和 benchmark 才能保证 provider、工具和执行策略一致。

### 迁移顺序

1. 先定义 `CoreConfig` schema 和默认值，给出 memory/file store。
2. 把 provider profile、credentials、JTP、MCP 从 `Settings` 读写改到 Core config service。
3. Iris 设置页改为调用该 service；保留 `irisAgent` feature flag 和外部 CLI agents。
4. CLI 复用同一 service，支持 `--config`/环境变量覆盖，但不读取 Iris settings。
5. 为旧 `~/.iris/settings.json` 做一次性迁移，保留兼容读取，避免用户重新录入 API Key。

判断标准是：删除 Iris 后，Core 仍能仅凭自己的 config store 启动；删除 Core 后，Iris 的 UI 和外部 CLI 管理仍然可用。符合这个标准的设置才算真正完成了解耦。

## 设置边界修订：Provider 配置应移出 Agent Core

上一节把 Provider profile、API Key、Base URL、代理列为应迁移到 Core 的配置，这对“通用 Agent Core”目标来说过于宽泛，需要修正。

### 正确边界

Agent Core 面对的应是抽象 LLM/Model Provider 能力，而不是具体供应商：

```ts
interface ModelProvider {
  stream(request: ModelRequest, signal?: AbortSignal): AsyncIterable<ModelEvent>;
  complete?(request: ModelRequest, signal?: AbortSignal): Promise<ModelResponse>;
  capabilities(): ModelCapabilities;
}
```

Core 只关心：

- 如何构造规范化的 `ModelRequest`；
- 如何消费流式事件；
- 如何处理 tool call、错误、取消、重试和 Invoke/Attempt 生命周期；
- 模型能力声明（文本/图片、上下文窗口、tool calling、reasoning 等）。

Core 不应知道：

- OpenAI、Anthropic、DeepSeek 等供应商 ID；
- API Key 的格式和存储位置；
- Base URL、HTTP headers、代理 URL；
- 供应商 SDK、Pi builtin provider 或具体认证流程。

### Provider 配置应放在哪里

这些配置属于**业务层/宿主层的 Model Adapter**：

```text
agent-core
  └─ ModelProvider interface

agent-provider-pi / agent-provider-openai / ...
  └─ 具体 API transport、认证、模型目录、代理

iris-agent-adapter
  └─ Iris 设置页、凭据存储、Provider profile 管理

cli-config-adapter
  └─ CLI 配置文件、环境变量、命令行参数
```

Iris、CLI 和 benchmark 可以各自决定如何管理 Provider profile，但都把最终得到的 `ModelProvider` 实例注入 Core。这样不同宿主可以使用不同模型供应商，Core 仍保持不变。

### 对现有代码的判断

当前 `pi-adapter.ts` 已经是一个相对清晰的边界：`createIrisPiSession` 接收 model、proxy、custom parameters，并负责把 Pi transport 接到 Worker。真正解耦时，应把它拆成 Core 无关的 provider package；Core Worker 不再直接 import Pi，而是接收 provider factory 或 `ModelProvider` port。

换句话说，当前 Agent 已经在事实上接近“抽象 LLM + 工具执行”的架构，主要残留耦合集中在 provider profile/config 的拥有权和 `session-manager.ts` 的装配逻辑，而不在模型调用协议本身。

### 哪些模型相关设置仍属于 Core

只有影响通用执行语义的参数才属于 Core，例如：

- 是否允许 tool calls、图片输入、reasoning 等能力要求；
- 请求级 token/上下文预算；
- Core 的重试、取消和超时策略；
- 对模型能力的校验和降级策略。

“选择哪个供应商、用哪个模型、API Key 放哪里、是否走代理”属于宿主层；Core 只接收已经解析好的 provider 实例和能力声明。

### 修订后的结论

因此，Provider profile、API Key、Base URL、代理**不应放进 Agent Core 的设置**。它们应由 Iris、CLI 或其他业务宿主管理，通过 `ModelProvider` 接口注入。Agent Core 的配置应保持供应商无关，只包含执行策略和模型能力约束。这会进一步降低拆分成本，也使同一 Core 更容易用于 benchmark、IDE、CI 或其他 Agent 产品。
