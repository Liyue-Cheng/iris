## 调研报告（2026-09-06）

> 本报告中的“工具”特指模型可发起的 tool/function call，不把斜杠命令、快捷键、
> prompt、Skill 文本本身、普通 CLI 子命令都混算为工具。各产品都在快速迭代；凡是
> 能固定到源码的结论均固定到 2026-09-06 的提交，运行时清单则以当前会话实际暴露
> 的 schema 为准。

### 结论摘要

这些产品表面上都有“读文件、改文件、跑命令”三件套，真正不同的不是有没有某个
工具，而是**谁拥有工具目录、目录何时变化、权限在哪一层执行，以及用户能否替换
整套工作流**。

| 产品 | 默认核心取向 | 工具集是否固定 | 最有辨识度的设计 |
| --- | --- | --- | --- |
| Iris Agent | 文档锚定 + 可审计本地执行 | 是，当前固定 4 个 | Pi 负责模型循环，Iris 接管工具执行，并把调用、diff、终端日志和关联关系持久化 |
| Claude Code | 完整、产品化、强交互 | 否，随平台、套餐、模型和设置变化 | 大量一等工具，权限、Hook、MCP、subagent、远程协作均由产品统一治理 |
| Codex | 本地执行内核 + 宿主扩展 | 否，按模型、功能开关、宿主、MCP、插件和权限组装 | Rust 工具路由器、沙箱与审批分离、支持 namespace/deferred/code mode |
| DeepSeek Harness | 组合式 Agent 运行时 | 完全不固定，由 preset 和 Cordis 插件组合 | “Everything is a Plugin”；甚至默认工具集和呈现方式都是可替换插件 |
| Pi | 极小核心、用户自组装 | 默认仅 4 个，另有 8 个一方实现 | 明确拒绝内置 MCP、subagent、plan、todo、权限弹窗，把这些留给扩展或外部环境 |
| OpenCode | 开源、多模型、客户端/服务端产品 | 否，按模型、provider、实验开关和插件变化 | 统一 registry，模型适配时在 `edit/write` 与 `apply_patch` 间动态切换 |
| Kimi Code | batteries-included 的现代 CLI | 否，按宿主能力和功能开关变化 | 内置后台任务、视频、subagent/swarm、定时任务，工具结果带资源访问声明以支持并行 |

最简短的选型结论：

- 想让 Agent 围绕 Iris 文档工作，并保留可回放的执行证据，Iris Agent 是项目内原生方案。
- 想要成熟的端到端产品治理，Claude Code 最完整。
- 想要 OpenAI 模型、本地沙箱、可审计执行和宿主级扩展，Codex 最自然。
- 想研究或搭建“Agent 操作系统”，DeepSeek Harness 的组合模型最激进。
- 想要可读、可改、几乎不替用户决定工作流的最小内核，Pi 最纯粹。
- 想要多模型、开源产品和较完整的默认体验，OpenCode 平衡最好。
- 想要开箱即用的并行 Agent、后台任务、视频和中文生态，Kimi Code 最积极。

### 一、先统一“工具”的定义

一个可执行工具通常至少有六层：

1. **模型契约**：`name`、`description`、输入 JSON Schema；模型只看到这一层。
2. **执行器**：接收参数、取消信号和会话上下文，执行文件、进程、网络或业务操作。
3. **结果契约**：文本、多模态内容、结构化值、错误、截断/溢写位置等。
4. **策略层**：allow/ask/deny、沙箱、路径和网络边界、审批规则、并发冲突判断。
5. **呈现层**：TUI/GUI 中如何显示调用、进度、diff、终端输出和结果。
6. **生命周期层**：工具从内置代码、插件、MCP、Skill、宿主或动态发现中注册，何时
   对某个 Agent 可见，何时卸载。

因此，“源码里实现了多少工具”“文档列了多少工具”“当前模型实际看到多少工具”是
三个不同数字。可靠盘点应分为：

- **实现集**：仓库中存在的工具实现。
- **候选集**：当前产品配置可注册的工具。
- **暴露集**：本轮请求真正发送给模型的工具 schema。
- **获批集**：策略层最终允许执行的调用。

Skill 也不一定等于工具。Claude Code 的 Skill 通过单一 `Skill` 工具执行；OpenCode 的
`skill` 工具把 `SKILL.md` 内容载入上下文；Pi 的 Skill 更接近 prompt/resource；MCP
则通常会真的增加独立工具名。把它们混在一起会显著夸大工具数量。

当前会话采用 Codex 的 code-mode 宿主：顶层模型主要看到 JavaScript 编排入口，入口
内部再调用具体工具。当前实际目录如下。

这里盘点的是**启动本次调研终端的外部 Codex 会话**，不是 Iris 应用内置的
**Iris Agent**。后者是另一套运行时，当前固定暴露 4 个工具，详见文末补充章节。

#### 顶层编排与长任务

| 工具 | 作用 |
| --- | --- |
| `functions.exec` | 在隔离的 V8 中编排一个或多个具体工具调用，可并行、裁剪和组合结果 |
| `functions.wait` | 等待仍在运行的 `exec` cell，或终止该 cell |

`functions.request_user_input` 有定义，但只在 Plan mode 可用；本次 Default mode 不计入
当前可调用集。

#### `functions.exec` 内可调用的 15 个端点

| 类别 | 工具 |
| --- | --- |
| 文件/进程 | `apply_patch`、`exec_command`、`write_stdin`、`view_image` |
| MCP 资源 | `list_mcp_resources`、`list_mcp_resource_templates`、`read_mcp_resource` |
| OpenAI Docs MCP | `search_openai_docs`、`fetch_openai_doc`、`list_openai_docs`、`list_api_endpoints`、`get_openapi_spec` |
| 持久目标 | `create_goal`、`get_goal`、`update_goal` |

其中 `apply_patch` 是结构化补丁工具；`exec_command` 是 PTY/命令执行入口；
`write_stdin` 继续与正在运行的统一执行会话交互；OpenAI Docs 五个工具来自当前连接的
MCP server，并非所有 Codex 安装都有；Goal 三个工具来自当前宿主扩展，也不是 Codex
CLI 永久内核。

#### 当前协作 namespace 的 6 个端点

`spawn_agent`、`send_message`、`followup_task`、`interrupt_agent`、`list_agents`、
`wait_agent`。它们由当前宿主的 multi-agent v2 提供，且本会话开发指令明确限制：只有
用户或项目指令授权 delegation 时才可派生 subagent。

所以，本会话当前有 **23 个可调用端点**（2 个顶层运行控制、15 个 code-mode 内部端点、
6 个协作端点）。这只是当前 Iris 启动配置的快照，不等于“Codex 永远有 23 个”。

### 三、Claude Code

#### 3.1 当前官方工具目录

Claude Code 官方 Tools reference 在调研时列出 45 个精确工具名：

| 类别 | 工具 |
| --- | --- |
| 文件与代码 | `Read`、`Edit`、`Write`、`Glob`、`Grep`、`NotebookEdit`、`LSP` |
| 命令与长进程 | `Bash`、`PowerShell`、`Monitor` |
| Web | `WebFetch`、`WebSearch` |
| 计划/工作区 | `EnterPlanMode`、`ExitPlanMode`、`EnterWorktree`、`ExitWorktree` |
| 用户交互 | `AskUserQuestion`、`EndConversation` |
| Agent 与消息 | `Agent`、`ListAgents`、`SendMessage`、`Workflow` |
| 任务状态 | `TaskCreate`、`TaskGet`、`TaskList`、`TaskUpdate`、`TaskOutput`、`TaskStop`、`TodoWrite` |
| MCP/动态发现 | `ListMcpResourcesTool`、`ReadMcpResourceTool`、`WaitForMcpServers`、`ToolSearch` |
| Skill | `Skill` |
| 调度 | `CronCreate`、`CronList`、`CronDelete`、`ScheduleWakeup`、`RemoteTrigger` |
| 交付与产品能力 | `Artifact`、`PushNotification`、`SendUserFile`、`ShareOnboardingGuide`、`SendFeedback`、`ReportFindings` |

这 45 个是“参考目录”，不是每个会话都同时出现。官方明确说明实际集合取决于 provider、
平台和 settings。例如 `PowerShell`、云端交付、手机通知、Artifact、Routine、LSP、团队
消息都有环境或套餐条件；新模型默认可能省略 `TodoWrite` 和 Task 系列；禁用一个裸工具
名会让它从模型上下文中完全消失。

#### 3.2 如何定义和扩展

Claude Code 本体不是完整开源实现，因此无法像其余五项一样从公开源码审计内部
`ToolDefinition` 类型；官方对外稳定的是：

- 工具名及输入字段由 Tools reference 和 Agent SDK 类型定义。
- 权限规则以 `Tool` 或 `Tool(specifier)` 表达，例如 `Bash(git status)`、
  `Read(./src/**)`、`WebFetch(domain:example.com)`。
- 策略顺序是 `deny` → `ask` → `allow`；裸 `deny` 会把工具从上下文移除，带参数的规则
  则保留工具但拦截匹配调用。
- `PreToolUse`、`PermissionRequest`、`PostToolUse` 等 Hook 可以在执行前后检查、拒绝、
  改写或审计调用。
- MCP server 通过协议注册新的工具/资源；名称通常带 `mcp__<server>__<tool>` 前缀。
- Skill 不创建任意新函数名，而是由已有 `Skill` 工具载入/执行，减小目录膨胀。
- subagent frontmatter 可声明 `tools`，从父会话拥有的工具集中继续收窄。

#### 3.3 设计哲学

Claude Code 是“**完整产品平台**”路线。它把本地编码、计划、问答、后台监控、
worktree、任务、团队通信、远程控制、文件交付、定时唤醒都做成一等工具，再用统一
权限、Hook 和组织策略治理。优点是交互一致、企业控制面完整；代价是目录较大、条件
工具多，而且闭源部分使具体调度和实现只能依赖官方行为契约。

### 四、Codex

#### 4.1 工具不是一个静态数组

Codex CLI 的核心能力是检查文件、编辑代码和运行本机工具，但请求级目录由多种来源
合成：

- 核心执行工具：shell/unified exec、`apply_patch`、计划、图片读取。
- Hosted tool：例如 Web search。
- MCP 工具和 MCP resources。
- Codex Apps、插件和 extension contributor。
- Dynamic tools。
- multi-agent、Goal、Memory、Image generation 等功能扩展。
- code mode 下的 `execute`/`wait` 以及 deferred tool search。

常见核心/可选名称包括：

| 类别 | 常见工具 |
| --- | --- |
| 进程 | `exec_command`、`write_stdin`；旧配置/不同宿主可能表现为 `shell` 或 `shell_command` |
| 编辑 | `apply_patch` |
| 计划/交互 | `update_plan`、`request_user_input` |
| 本地媒体 | `view_image` |
| Web | `web_search`，可配置 cached/indexed/live/disabled |
| MCP 资源 | `list_mcp_resources`、`list_mcp_resource_templates`、`read_mcp_resource` |
| multi-agent v2 | `spawn_agent`、`send_message`、`followup_task`、`interrupt_agent`、`list_agents`、`wait_agent` |
| 延迟发现/code mode | `tool_search`、`execute`、`wait` |
| 其他按需能力 | 权限申请、环境等待、当前时间、sleep、插件安装、Goal、Memory、Image generation |

具体模型可能要求 freeform `apply_patch`，也可能使用 JSON function；统一执行是否可续写、
是否有多个环境、当前模型是否支持图片、是否启用 multi-agent，都影响最终 schema。

#### 4.2 如何定义

Codex 的公开实现以 Rust registry/router 为中心。可以概括为：

1. 每个 handler 同时提供工具身份、模型可见 spec 和执行逻辑。
2. spec 支持 function、freeform、namespace、Web search、tool search 等形态，不局限于
   普通 JSON function。
3. Registry 汇入 core、hosted、MCP、extension 和 dynamic runtime。
4. Exposure 再决定 `Hidden`、仅直接暴露、仅 deferred、仅 code mode，或多种界面均可见。
5. Router 在每轮根据 model info、feature flags、环境、permission profile 和宿主扩展
   生成最终目录。
6. 沙箱决定进程实际能访问什么；approval policy 决定何时向用户提权。两者相互关联
   但不是同一个概念。

官方配置显示 `shell_tool`、`unified_exec`、`multi_agent`、`apps` 等均为独立 feature；
MCP 支持 stdio 与 streamable HTTP、Bearer/OAuth，并读取 server instructions。Codex CLI、
IDE 和桌面宿主共享分层 `config.toml`，项目配置仅在项目受信任时加载。

#### 4.3 设计哲学

Codex 是“**受控的本地执行内核 + 可变宿主能力**”。它不像 Pi 那样追求固定四工具，
也不像 Claude Code 那样把所有产品功能固定成一个显眼目录，而是在每轮构造适合当前
模型和宿主的工具表。code mode/deferred disclosure 的目标是避免把数十或数百个工具
schema 一次性塞进上下文；namespace 则保留来源和所有权边界。其优势是扩展面大、
安全层清晰、适合 CLI/IDE/App/CI 多宿主；代价是“Codex 有哪些工具”必须带配置快照
回答，单看仓库文件名无法得到真实目录。

### 五、DeepSeek Harness

#### 5.1 默认不是一个工具集，而是四个 preset

DeepSeek Harness 仍处于 developer preview，官方明确警告会有破坏性变化。它提供的
四个 shipped preset 是理解其工具设计的入口：

| Preset | 模型看到的形态 |
| --- | --- |
| `minimal` | POSIX 为 `bash`、Windows 为 `pwsh`，再加 `str_replace_editor`，严格双工具 |
| `standard` | 完整文件、Shell、搜索、Web、Skill、计划、Goal、subagent、workflow 工具 |
| `ptc` | 能力接近 standard，但多数原生工具通过生成的 TypeScript SDK 由 `run_code` 组合，默认不暴露 `workflow` |
| `cordis`/创造模式 | 在 standard 能力上增加运行时检查、插件实验和 preset 创作能力 |

#### 5.2 Standard preset 的一方工具族

| 类别 | 工具/来源 |
| --- | --- |
| Shell | `bash` 或 `pwsh`，支持后台 job 与沙箱升级参数 |
| 文件 | `read`、`read_image`、`write`、`edit` |
| 搜索 | `glob`、`grep`，内置打包的 ripgrep |
| 后台任务 | `job_output`、`job_list`、`job_kill` |
| Skill | `skill` |
| Goal | `get_goal`、`create_goal`、`update_goal` |
| Plan | `/plan` 由 command 进入；模型用稳定存在的 `exit_plan_mode` 提交审批 |
| subagent | `subagent`、`subagent_fork`、`list_subagent_models`，以及 `send_message`、`interrupt_agent`、`list_agents` |
| 工作流 | `workflow`、`ralph` |
| 交互/状态 | `ask_user_question`、`todo_write` |
| Web | `web_search`、`web_fetch` |

Codex/Claude Code 外部 subagent provider 在 shipped standard preset 中有示例行，但默认
`disabled: true`；仅仅安装 provider 不会自动授权相应工具。

#### 5.3 如何定义

它的核心 `ToolDefinition` 是本次调研中契约最显式的一种：

- 模型字段：`name`、`description`、`parameters`。
- 必需输出声明：`output.schema`、`output.render()`，可选 presentation metadata。
- 执行：`execute(args, ToolRunContext)`，上下文携带 call identity、取消信号、延迟上下文
  和结束当前 turn 的能力。
- 调度元数据：`timeoutMs`、`isConcurrencySafe()`。
- UI：`presentCall()`、`presentResult()`，要求纯函数以支持日志重放。
- `defineTool()` 用一套 TypeScript schema DSL 同时推导参数/输出类型、生成 JSON Schema、
  运行时校验输入和输出。
- `ToolRestriction` 在 scope 上对继承工具做 allow/deny 交集；本 scope 自己注册的工具不
  受继承过滤影响。
- 执行流水线是可扩展 waterfall：pre-execute 策略 → 单调 guard → execute wrappers →
  post-execute → finalize → immutable result。

工具本身也是 Cordis 插件。`agent.cordis.yml` 决定哪些插件挂到哪个 scope/realm；文件
provider、Shell executor、沙箱、工具 schema、UI 和 preset 都能分别替换。这正是
“Everything is a Plugin”的具体含义，不只是营销口号。

#### 5.4 设计哲学

DeepSeek Harness 追求“**时空可组合性**”：服务和插件不仅按依赖组合，还按 Host、
Preset、Agent、Session 等生命周期与作用域隔离。PTC 又把工具调用从“模型每次挑一个
函数”提升为“模型写一个小程序组合多个函数”，减少往返并允许程序级控制流。优点是
研究、定制和替换能力极强；代价是架构认知成本最高，developer preview 阶段的兼容性
风险也明显高于其他产品。

### 六、Pi

#### 6.1 默认四工具与完整一方目录

Pi 默认只给模型四个工具：

| 工具 | 作用 |
| --- | --- |
| `read` | 分页读取文本/图片等内容 |
| `write` | 创建或完整写入文件 |
| `edit` | 精确字符串替换 |
| `bash` | 执行 Shell 命令 |

源码中完整 `ToolName` 联合还有 `powershell`、`grep`、`find`、`ls`，因此一方实现总计
8 个。`createCodingTools()` 仍只返回四工具；`createReadOnlyTools()` 返回
`read/grep/find/ls`。这说明“存在 8 个实现”和“默认暴露 4 个”是刻意区分的。

#### 6.2 如何定义

Pi 的 `ToolDefinition` 包含 `name`、`label`、`description`、TypeBox `parameters`、
可选参数预处理/执行模式，以及 `execute()`；包装器把定义转成 agent-core 的
`AgentTool`。扩展可以随时调用 `pi.registerTool()` 注册工具，并立即通过
`getAllTools()`、`setActiveTools()` 查询或切换，无需重启。扩展还能拦截 `tool_call`
和 `tool_result`、改变 system prompt、实现审批、修改压缩和自定义 TUI。

Pi 没有内置权限系统，默认继承启动进程的文件、网络、进程和凭据权限；官方建议需要
强边界时使用 micro-VM、Docker 或 OpenShell。项目级扩展仍有 trust gate，但这不是
逐调用权限弹窗。

#### 6.3 设计哲学

Pi 对自己的取舍写得最直白：

- No MCP：优先让 CLI + README/Skill 暴露能力，或由扩展自行加 MCP。
- No sub-agents：用 tmux 启动多个 Pi，或安装/编写自己认可的实现。
- No permission popups：在容器做隔离，或扩展自己的确认流。
- No plan mode：把计划写文件，或扩展。
- No built-in todos：作者认为它容易干扰模型。
- No background bash：用 tmux 获得完整可观察和直接交互。

这是“**机制优先、策略后置**”的 Unix 式设计。Pi 不是能力弱，而是拒绝把某一种工作流
升格为产品唯一答案。优点是核心小、prompt/tool schema 成本低、行为容易理解；代价是
团队治理、审批、并行编排和 MCP 互操作都需要用户自己选型与维护。

### 七、OpenCode

#### 7.1 官方列出的内置工具

| 稳定类别 | 工具 |
| --- | --- |
| 命令/编辑 | `bash`、`edit`、`write`、`apply_patch` |
| 读取/搜索 | `read`、`grep`、`glob` |
| 工作流 | `skill`、`todowrite`、`question` |
| 网络 | `webfetch`、条件可用的 `websearch` |
| 代码智能 | 实验性的 `lsp` |

源码 registry 还注册 `task`（subagent）、内部 `invalid`，并可按实验开关加入 plan
exit 和 code-mode `execute`。官方工具页没有把这些内部/条件项都算进稳定列表。

最值得注意的是模型适配：对合适的 GPT 模型，registry 暴露 `apply_patch` 并隐藏
`edit/write`；对其他模型反过来。这避免要求每个模型都擅长同一种编辑协议。Web search
也只在 OpenCode/OpenCode Go provider 或相应 Exa/Parallel 开关下出现。

#### 7.2 如何定义

OpenCode 当前内部 `Tool.Def` 使用 Effect Schema：

- `id`、`description`、`parameters`，可另给原始 JSON Schema。
- `execute(args, context)` 返回带 `title`、`metadata`、`output` 和附件的结果。
- wrapper 先做 schema decode，参数错误转成模型可修复的结构化错误，再统一做 tracing
  与超长结果截断/落盘。
- context 提供 session/message/agent/call ID、取消信号、历史消息、UI metadata 和
  permission request。
- registry 合并内置工具、`.opencode/tool(s)/*.ts`、插件工具和 MCP 工具，再按模型、
  provider、agent permissions 和 feature flags 过滤。

自定义工具使用 `@opencode-ai/plugin` 的 `tool()` helper，以 TypeScript/JavaScript 文件
定义 description、参数 schema 和执行函数；执行函数本身可以调用任何语言写的脚本。
权限统一是 `allow`、`ask`、`deny`，支持工具名通配符，MCP 工具也进入同一规则空间。

#### 7.3 设计哲学

OpenCode 是“**多模型开源产品**”路线：既不保持 Pi 那样的极小主义，也不绑定单一模型
供应商。它接受不同模型对工具格式和编辑方式的偏好差异，在 registry 的最后一步适配；
同时提供 TUI、桌面端、server/SDK、插件、MCP、LSP 和 agent。优势是开放、provider
选择广、默认能力完整；代价是条件分支较多，文档稳定列表与源码候选列表并不完全相同。

### 八、Kimi Code

#### 8.1 当前文档中的 23 个基线工具

| 类别 | 工具 |
| --- | --- |
| 文件 | `Read`、`Write`、`Edit`、`Grep`、`Glob`、`ReadMediaFile` |
| Shell | `Bash` |
| 网络 | `WebSearch`、`FetchURL` |
| Plan | `EnterPlanMode`、`ExitPlanMode` |
| 状态 | `TodoList` |
| 协作 | `Agent`、`AgentSwarm`、`AskUserQuestion`、`Skill` |
| 后台任务 | `TaskList`、`TaskOutput`、`TaskStop`、`WaitFor` |
| 定时任务 | `CronCreate`、`CronList`、`CronDelete` |

源码还有按功能装配的 Goal 工具（`CreateGoal`、`GetGoal`、`SetGoalBudget`、
`UpdateGoal`）、`SelectTools`、Tower/Swarm 等工具族；它们不应混进所有安装都有的 23 个
基线工具。`WebSearch`/`FetchURL` 也要求宿主注入 provider，未注入就不出现在目录中。

Kimi Code 的细节约束较丰富：`Read` 单次上限 1000 行或 100 KB；`Write/Edit` 对已有
文件执行 read-before-write 并检测读取后的磁盘变化；`ReadMediaFile` 支持图片与视频；
`Bash` 超时可自动转后台；`AgentSwarm` 可按 item 模板展开最多 128 个 subagent；Cron
任务与会话一起持久化并有抖动、合并错过触发和过期机制。

#### 8.2 如何定义

Kimi Code v2 的 `ToolContract` 把模型定义和执行阶段分开：

- `ToolDefinition`：`name`、`description`、`parameters`、`source`（builtin/user/mcp）、
  `disclosure`（inline/deferred）和附加信息。
- `ExecutableTool.resolveExecution(input)` 先把模型输入解析为一项待执行操作。
- 待执行操作声明 `approvalRule`、`matchesRule`、资源访问 `accesses`、输入展示、是否阻断
  同批后续工具，再提供真正的 `execute()`。
- 结果可含文本/多模态、错误、流式 update、turn stop、截断、spill 文件和 steer delivery。
- `ToolAccesses` 显式描述 read/write/readwrite/search 的路径与递归范围，并能判断两个调用
  是否冲突。这为“互不冲突的读可以并行、写冲突则串行”提供运行时依据。
- 每个内置工具作为 DI contribution 注册，assembly service 在 App scope 汇总；MCP 和
  user tool 进入同一 registry 与审批体系。

默认审批策略是只读自动放行，写入和执行类需审批；“Ask When Needed”可跳过普通调用
审批，但 Plan 退出审批仍保留。项目提供 hooks、MCP、插件市场、ACP 和多类 subagent。

#### 8.3 设计哲学

Kimi Code 是“**开箱即用的高并发工作台**”。它不要求用户先用 tmux、脚本或第三方包
拼出后台任务、结构化问答、计划、swarm 和定时任务，而是把这些直接纳入统一工具协议；
同时用访问声明、审批规则、后台任务 ID 和结果 spill 控制复杂性。优势是现代能力覆盖
广、图片/视频和中文场景突出；代价是核心目录和状态机明显比 Pi/OpenCode 更重，部分
能力又依赖 Kimi 宿主或市场生态。

### 九、横向设计对比

#### 9.1 工具粒度

| 取向 | 产品 | 影响 |
| --- | --- | --- |
| 少量通用工具 | Iris Agent、Pi、DeepSeek minimal | schema 短、模型选择简单；复杂流程主要靠 shell 或扩展 |
| 中等编码工具集 | OpenCode、Codex CLI 基础配置 | 文件/命令/搜索职责清楚，并可按模型裁剪 |
| 大量领域一等工具 | Claude Code、Kimi Code、DeepSeek standard | UI 和策略可精确治理，但目录、状态与条件可用性更复杂 |
| 程序化工具组合 | Codex code mode、DeepSeek PTC | 一次模型输出可编排多个调用，减少 round trip；需要额外运行时和安全边界 |

#### 9.2 扩展模型

| 产品 | 主要扩展方式 | 工具所有权 |
| --- | --- | --- |
| Iris Agent | 当前没有模型侧工具扩展入口 | 模型循环来自 Pi，固定四工具由 Iris 定义并托管执行 |
| Claude Code | MCP、Plugin、Hook、Skill | 产品内置目录 + 外部 MCP；Skill 复用统一入口 |
| Codex | MCP、Apps、Plugin、Extension、Skill | Registry 记录 core/host/MCP/extension 来源和 exposure |
| DeepSeek Harness | Cordis plugin、preset、provider | 一切均是插件，可按 scope/realm 重组 |
| Pi | TypeScript extension、Pi package、Skill、CLI | 用户扩展最自由，但 MCP 不是核心协议 |
| OpenCode | 本地 tool 文件、plugin、MCP | 统一 registry，工具名进入统一权限规则 |
| Kimi Code | Plugin marketplace、MCP、Skill、Hook、ACP | builtin/user/mcp 显式标源，支持 deferred disclosure |

#### 9.3 权限和安全边界

| 产品 | 默认安全观 |
| --- | --- |
| Iris Agent | 第一版明确允许四工具访问用户要求的任意路径；当前无逐调用审批、项目根限制或工具沙箱 |
| Claude Code | 细粒度 allow/ask/deny + Hook + managed policy + sandbox；产品负责逐调用治理 |
| Codex | sandbox 与 approval policy 两层；project trust、permission profile、网络策略和提权前缀分开 |
| DeepSeek Harness | policy waterfall + 单调 guard + sandbox/provider 插件；部署者可替换整条策略链 |
| Pi | 核心无逐调用权限，继承进程权限；边界应由容器/VM或扩展提供 |
| OpenCode | 工具通配 permission；默认文档称工具启用且无需批准，用户可改为 ask/deny |
| Kimi Code | 只读默认放行、写/执行默认审批；工具先声明 approval rule 与资源访问范围 |

Pi 与其他产品不是“少做了一个安全功能”，而是安全责任归属不同：Pi 把强隔离交给
进程外环境。Iris Agent 当前也没有逐调用审批或沙箱，但这是第一版显式延后的统一安全
模型，不应误读为已经提供项目级隔离；其他产品多倾向在 Agent 宿主内同时做策略和交互。

#### 9.4 并行和 subagent

- Iris Agent 当前按一个 Provider 回复中的顺序执行工具调用，没有模型侧 subagent 工具；
  长时间运行的终端另有隔离的监督调用，它不进入正式对话，也不能调用工具。
- Claude Code 把 `Agent`、Workflow、共享任务和跨会话消息做成产品能力。
- Codex multi-agent v2 使用独立 namespace，并可按 developer/project policy 整体禁止
  自主派生；当前会话就是这种策略。
- DeepSeek Harness 把 subagent backend 也抽象为 provider，可用 spawn、fork、Codex、
  Claude Code 等实现；preset 决定哪一个真正授权。
- Pi 有意不内置 subagent，建议 tmux 或扩展。
- OpenCode 的 `task` 工具调用不同 agent profile，plan/build/general 由 agent 配置控制。
- Kimi Code 同时提供单 Agent、后台 Agent 和 `AgentSwarm`，并把任务输出/停止/等待做成
  独立工具。

#### 9.5 工具目录膨胀的处理

- Iris Agent 当前直接固定为四工具，没有动态目录、deferred disclosure 或工具搜索。
- Claude Code 用 `ToolSearch`、条件工具和 Skill 单入口控制目录。
- Codex 用 namespace、deferred exposure、tool search 和 code mode。
- DeepSeek Harness 用 preset；PTC 进一步把目录投影成 SDK。
- Pi 直接保持四工具默认核心。
- OpenCode 按模型/provider/agent 过滤，并在编辑协议间二选一。
- Kimi Code 的 contract 已提供 inline/deferred disclosure，复杂功能按 contribution 装配。

### 十、如何选，不宜只按工具数量

| 需求 | 更合适的首选 | 原因 |
| --- | --- | --- |
| Iris 文档锚定、执行记录、diff 与终端证据持久化 | Iris Agent | 会话直接绑定文档/工作区，工具效果进入统一 Trace 和 artifact |
| 企业权限、审计、远程协作和成熟 UX | Claude Code | 完整控制面与大量产品级工具 |
| OpenAI/Codex 模型、本地仓库、CI 和强沙箱 | Codex | 执行/审批分层，CLI/IDE/App 配置一致 |
| 自研 Agent 平台、替换工具管线、研究 PTC | DeepSeek Harness | preset、scope、realm、waterfall 都开放组合 |
| 个人黑客式工作流、最小 prompt、完全自己搭 | Pi | 默认四工具，扩展 API 极强，不规定工作流 |
| 多供应商、开源、TUI/桌面/服务端兼顾 | OpenCode | provider 中立且产品面较完整 |
| 中文团队、视频输入、后台任务和大规模 swarm | Kimi Code | 多媒体与并行/调度能力开箱即用 |

不建议形成一个跨产品“最大工具并集”再强行统一。更合理的抽象是：

1. 定义稳定的能力类别：read/search/mutate/execute/web/interact/delegate/state。
2. 保存每次会话的真实 tool schema 快照，而不是只保存产品名和版本。
3. 权限规则绑定“工具来源 + 工具名 + 参数范围”，避免同名工具越权。
4. Skill、MCP、command、agent profile 分类型展示，不把所有扩展都叫工具。
5. 对大目录优先采用 deferred discovery 或 code/PTC mode，而不是无条件注入全部 schema。
6. 对并行调用要求工具声明资源访问或并发安全性；仅凭“只读名称”推断并不可靠。

### 十二、补充调研：Iris Agent（我们自己的）

前文“当前 Iris/Codex 会话”盘点的是运行本次任务的外部 Codex 宿主，遗漏了 Iris
产品里真正面向用户的内置 Agent。根据当前工作树源码，Iris Agent 的模型侧工具目录
**固定且只有 4 个**：`read`、`edit`、`write`、`terminal`。类型层也用
`AgentToolName = 'read' | 'edit' | 'write' | 'terminal'` 封闭了这个集合。

#### 12.1 模型实际看到的四个工具

| 工具 | 模型输入 schema | 当前真实行为 |
| --- | --- | --- |
| `read` | `{ path: string }` | 读取一个文件；主进程先读原始字节，经 worker 协议以 base64 传输，再按 UTF-8 文本返回模型 |
| `edit` | `{ path: string, content: string }` | 用完整 `content` 原子替换文件；记录为 `edit` 效果，并生成 before/after hash 与 unified diff |
| `write` | `{ path: string, content: string }` | 创建或完整覆盖文件；原子写入会递归准备父目录，并记录为 `write` 效果 |
| `terminal` | `{ command, intent, successExitCodes? }` | 在项目选择的 PowerShell/POSIX shell 中运行可见命令；`intent` 必须是 `information` 或 `operation`，成功码默认 `[0]` |

这里有三个容易混淆的点：

1. `edit` 当前不是 patch 或 exact-replacement 工具。它和 `write` 在执行层最终都是整文件
   原子写入，主要区别是模型语义和审计记录中的 operation 名称。
2. `read` 没有分页参数；文件工具层也没有观察到截断逻辑。大文件会整体进入工具结果。
3. `terminal.intent` 当前是声明和审计信息，不是审批开关；标为 `operation` 不会自动弹出
   确认框，标为 `information` 也不会额外限制命令副作用。

#### 12.2 定义和执行链

Iris 没有直接采用 Pi 自带的文件/命令实现，而是只复用 Pi 的模型、消息流和 tool-call
循环，再把四个 schema 替换为 Iris 自己的定义。完整链路是：

```text
模型 tool call
-> Pi ToolDefinition
-> Node worker 发出 tool-request
-> 主进程 IrisAgentToolHost
-> 文件系统或 AgentCommandPty
-> 结构化 result + effects
-> worker 生成 tool result
-> 继续 Provider 对话
```

每次请求都带 session、intent、turn、provider message、tool call、operation 等关联 ID。
`session-manager` 会先确认 tool call 属于一个已经持久化的 assistant Provider message，
再记录 waiting/running/completed/failed 状态并执行；重复的已完成 operation 可以直接回放
既有结果。这使“模型说了什么、调用了什么、产生了什么效果”能落到同一条可恢复 Trace，
而不只是留在一次性的终端输出里。

#### 12.3 文件效果与终端证据

`edit`/`write` 在内容真正变化时会：

- 计算写入前后的 SHA-256；
- 生成 unified diff 供活动卡展示；
- 原子写入目标文件；
- 在会话 artifact 中保存 path、operation、完整 before/after content 和两侧 hash；
- 创建 `file-write` effect，并关联回 intent、turn 和 tool activity。

内容相同会返回 `unchanged`，不产生 effect。worker/host 内部协议还预留了显式 `mkdir`
operation；只有该 operation 首次创建目录时才产生独立的 `directory-create` effect，
普通模型侧 `write` 自动准备父目录时不会额外记录这个 effect。

`terminal` 通过 `AgentCommandPty` 执行，每次分配独立 terminal ID：

- 完整输出持久化到 `terminal/<id>.log`；
- 返回模型的是末尾最多 64 KiB，并标记是否截断；
- Timeline 元数据保存末尾 8 KiB 预览、退出码、成功码集合、总字节数和 artifact 引用；
- 默认运行超过 3 秒会在 UI 中显露为可见终端；
- 默认每 20 秒对新增输出做一次隔离监督，监督调用没有工具、不会续写正式会话，只在
  发现可疑行为时形成提示。

所以 Iris Agent 的辨识度不在于工具多，而在于**工具效果是一等持久化对象**：文件可
追溯 before/after，终端有完整 transcript，Provider 调用和工具状态都可关联、恢复和展示。

#### 12.4 当前权限边界：不要把“当前项目”理解成沙箱

工具描述把终端称为“在当前项目执行”，但当前 host 的实际解析逻辑是
`normalize(resolve(projectRoot, path))`，方法名也明确叫 `resolveUnrestrictedPath`。这意味着：

- 绝对路径和包含 `..` 的路径可以落到项目外；
- junction/symlink 指向项目外时，四个工具仍可跟随访问；
- terminal 的 `cwd` 使用同一套不受限解析；
- terminal 环境以 Iris 主进程 `process.env` 为底，再合并调用方传入值；
- 在这条 Iris Agent 工具执行链中，没有发现逐调用 allow/ask/deny、项目根 containment
  检查或独立 sandbox。

这不是从方法名猜出的偶然漏洞：base prompt、适配元数据和测试都明确把它定义为
“第一版允许所有工具访问用户明确要求的任意路径，统一安全模型以后再做”。因此准确
结论是：**当前能力边界等于 Iris 进程本身的文件和命令权限**。审计记录增强了可追溯性，
但审计不等于执行前隔离或授权。

#### 12.5 当前实现中应注意的契约缺口

当前 `IRIS_AGENT_PROMPT` 告诉模型：`edit` 是 exact text replacement，支持
`edits[].oldText` 和多段不重叠编辑；但发送给模型的真实 schema 只有 `{ path, content }`，
执行器也只支持整文件写入。这是 prompt、schema 与 executor 三层之间的明确不一致。
在它被修正前，应以真实 schema 和执行器为准，不能把 `edit` 当成精确补丁能力。

此外，Iris Agent 当前没有独立的 glob/search、Web、MCP、Skill、todo、plan 或 subagent
模型工具；搜索和项目命令都通过 `terminal` 完成，也没有当前会话 Codex 所拥有的
namespace/deferred/code-mode 工具目录。这个小目录降低了模型选错工具和 schema 占用，
但也把更多能力集中进了权限较宽的 shell。

#### 12.6 设计哲学与其他产品的关系

Iris Agent 可以概括为“**Pi 的最小模型循环 + Iris 的文档锚定和可审计执行宿主**”：

- 像 Pi 一样保持四工具小核心，不把大量工作流能力做成模型工具；
- 与 Pi 不同，工具执行、活动状态、diff、终端日志、会话恢复都由 Iris 产品层接管；
- 与 Claude Code/Codex/Kimi Code 不同，当前没有成熟的逐调用审批和沙箱控制面；
- 与 DeepSeek Harness/OpenCode 不同，当前工具目录不是插件 registry，也不按 provider 动态装配；
- Iris 自己最独特的部分，是 Agent 会话锚定文档/工作区，并让工具效果进入可持久化、
  可关联、可回放的项目工作记录。

因此，前一版报告漏掉 Iris Agent 的后果不只是少列四个名字，而是漏掉了一条不同的
设计路线：**工具目录极小，但执行证据和项目文档的结合比通用 CLI Agent 更深。**
