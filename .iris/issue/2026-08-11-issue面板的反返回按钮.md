我现在想在issue面板中加入返回按钮，你认为安装在哪里好呢？

## 问题理解

这个需求表面上是“在哪里放一个返回按钮”，实际上需要先确定 issue 面板在导航层级中的位置，以及“返回”的准确语义。

如果用户的路径是“issue 列表 -> issue 详情面板”，那么详情就是一个比列表更深的层级。返回按钮应放在面板顶部标题栏的最左侧，位于 issue 标题之前。这符合常见的“左侧返回、中间标题、右侧操作”结构，用户也最容易理解。

这个返回不应只是“关闭面板”的另一种写法。它应尽量恢复用户进入 issue 之前的上下文，包括原工作区、视图、筛选条件、选中项和滚动位置。如果无法恢复这些状态，用户虽然“返回”了，仍然会丢失工作进度。

另一个需要区分的是返回、关闭和浏览器后退：

- 返回：回到 Iris 内部的上一层内容。
- 关闭：收起临时面板，并不一定表示存在层级跳转。
- 浏览器后退：按历史记录离开当前 URL，可能跳出 Iris 当前工作流。

因此，我对该问题的初步判断是：如果 issue 面板已经形成明确的二级详情页，推荐在标题栏左侧放置箭头返回按钮，并让它恢复来源视图的状态。如果它只是覆盖在当前内容上的临时抽屉，则应先评估现有关闭按钮是否已经满足需求，避免同时出现两个语义近似的控件。

- [x] 确认 issue 面板当前是独立导航层级还是临时抽屉，以及现有关闭操作的语义。

## 根据现有代码确认

前面把这个问题理解成“列表 -> 详情”并不准确。实际上 issue 面板是一个独立的 issue 浏览器：左侧是 `IssuePanel`，右侧是选中 issue 的 `DocView`，它会整体替换常规的“全局树 + 编辑器 + 终端”布局。

从 issue 浏览器外部进入它的唯一代码入口，是主界面左侧 `LensTree` 中的 issue 分组标题。根工作区和子工作区都会渲染同一个入口：点击根工作区的 issue 标题会打开全局 issue 集合，点击子工作区的 issue 标题会打开该工作区范围的 issue 集合。

因此，返回按钮不是“从 issue 详情返回 issue 列表”，而是“退出 issue 浏览器”。返回后应重新显示包含该入口的常规主界面，并恢复用户进入前的准确视图：

- 如果进入前正在查看某篇文档，返回后仍显示该文档及其终端。
- 如果进入前是根工作区或子工作区 hub，返回后恢复该 hub。
- 如果进入前是其他集合或 todo 视图，返回后恢复该视图。

不应固定跳到项目根节点，也不应把当前 issue 的右侧详情简单清空；这两种行为都不是回到入口所在的上下文。实现上需要在进入 issue 浏览器前保存一份返回目标，因为当前 `projectStore.openCollection` 会直接替换 `view`，并没有保留上一个视图。

## 位置决定

按钮放在 issue 列表面板左下角，相对该面板绝对定位。它属于 issue 浏览器的退出控件，不随列表滚动。列表滚动区需要预留底部空间，避免按钮遮住最后一行 issue。

## 完整方案：统一集合浏览器

### 前提与边界

未来 issue、status、report、misc 以及其他需要的管理面板，都使用与当前 issue 浏览器一致的独立布局。它们只能从主页面进入，集合浏览器之间不相互跳转，也不从文档详情再打开另一层浏览器。

这里的“主页面”指非集合浏览器状态下的常规三栏工作台，而不是强制指项目根 hub。主页面中间当时可能是一篇文档、根 hub 或子工作区 hub；这份状态在进入浏览器时保留，退出时原样恢复。

由于入口和出口都是单一层级，本方案不引入通用导航历史栈，也不借用浏览器的 `window.history`。只保存一份“返回主页面”目标，语义更清楚，也避免出现集合面板嵌套。

### 交互规格

所有集合浏览器的左侧列表 viewport 左下角都放置同一个返回控件：

- 使用 Lucide `ArrowLeft` 图标，图标按钮保持固定尺寸，不因列表内容变化。
- 按钮的 tooltip 和 `aria-label` 统一为“返回主页面”，不使用“关闭”或“返回列表”。
- 按钮相对左侧 viewport 绝对定位，不放进列表的滚动内容，不随滚动移动。
- 按钮使用有实底和边界的常规表面，保证在各种行背景上都可识别；层级高于列表行，但不高于对话框和菜单。
- 左侧列表滚动区预留与按钮高度和底部间距匹配的 padding，最后一行可以完整滚动到按钮上方。
- 点击返回后，键盘焦点恢复到主页面中原来用于进入该浏览器的分组标题，便于键盘用户继续导航。

首版只提供明确的屏幕按钮，不把 `Escape` 设为全局退出快捷键，因为它与搜索框、下拉菜单、对话框和编辑器的现有取消语义冲突。

### 导航状态设计

在 `project-store` 中把当前视图与集合浏览器的来源分开建模。概念上增加一个临时的 `collectionOrigin`：

```ts
interface CollectionOrigin {
  returnView: MainView;
  entry: {
    type: DocType | 'todos';
    workspacePath: string | null;
  };
}
```

`MainView` 只允许常规主页面中可以恢复的视图，即文档、根 hub 和子工作区 hub，不包含任何集合浏览器。这会在类型层面禁止集合面板嵌套和循环返回。

导航规则如下：

1. 从主页面调用 `openCollection` 时，先完成当前编辑器的离开检查和保存。
2. 只有检查成功且本次导航意图仍有效时，才记录 `collectionOrigin` 并进入集合浏览器；保存被拒绝时不留下错误的返回目标。
3. 在同一集合浏览器内切换范围、筛选、选中文档或右侧详情时，不覆盖 `collectionOrigin`。
4. 点击左下角按钮时调用专用的异步 `returnToMainView()`，先保存集合右侧正在编辑的文档，再恢复 `returnView`。
5. 返回成功后清除 `collectionOrigin`；如果保存失败、冲突策略拒绝离开或导航意图已过期，保持当前浏览器和返回目标不变。
6. 切换项目或项目重新打开时清除 `collectionOrigin`，不跨项目恢复导航状态。

返回目标只保存在当前窗口的内存中，不写入项目文件或用户设置。集合面板自身的筛选、分组、选中项和滚动位置继续由各自的 panel memory 保留；退出浏览器不清空这些状态，下次进入时可以继续。

### 异常与回退

在集合浏览器停留期间，原来的主页面文档可能被外部删除。返回前应根据最新 scan 验证 `returnView`：

- 原文档仍存在时，重新读取并显示它。
- 原文档已不存在时，返回该入口所属的工作区 hub；全局入口则回到根 hub。
- 原子工作区也已不存在时，最终回退到根 hub。
- 返回过程中发生普通读取错误时，沿用现有 `docError` 界面，不静默改变目标。

在没有 `collectionOrigin` 的异常状态下渲染集合浏览器时，返回按钮仍可用，但目标固定回退为根 hub。这只是容错路径，正常入口不应到达该状态。

### 组件与布局收敛

返回控件不应分别写进 `IssuePanel`、`StatusList`、`ReportTimeline` 等业务组件。应抽到共享的集合浏览器外壳中，由外壳统一提供：

```text
CollectionBrowserShell
├─ CollectionListViewport
│  ├─ 当前类型的列表面板
│  └─ ReturnToMainButton
├─ ResizableHandle
└─ CollectionDetailViewport
   └─ DocView / 未选中空状态
```

外壳负责分栏、viewport 溢出边界、返回按钮与右侧详情空状态；各面板只负责列表的数据、工具栏、筛选和行交互。这样新增面板时不会再复制一套返回逻辑。

当 status、report、misc 迁移到双栏浏览器后，它们的行点击统一改为在当前浏览器右侧选中文档，不再通过 `selectDoc` 离开浏览器。`selectedPath` 从 issue 专用状态推广为集合浏览器的通用状态，`ThreePane` 也从 issue 特判改为统一渲染 `CollectionBrowserShell`。

Todo 面板可以使用同一外壳，但它的列表行指向 issue 文档而不是 `todos` 文档类型。因此应将“浏览器种类”与“右侧文档类型”分开，不为了统一布局而伪造 `todos` 文档类型。

## 架构理解：从 issue 特例收敛为集合工作台

### 现状的真实分界

当前代码中，只有 issue 是真正的集合浏览器：它在 `MiddleView` 中保存 `selectedPath`，列表点击调用 `selectCollectionDoc`，`ThreePane` 为它渲染独立双栏，`DocView` 也只识别 issue 集合详情。

status、report、misc 和 Todo 目前只是全宽列表页。它们的行点击直接调用 `selectDoc`，会离开集合视图回到常规文档布局。创建文档对话框成功后也固定调用 `selectDoc`。因此，“改为和 issue 一套代码”的本质不是共享几个 CSS class，而是把被 issue 特例化的导航、布局、选中详情和生命周期提升为通用集合能力。

同时，各列表的领域差异是真实的：

- issue 有状态过滤、分组、排序、搜索、响应式列宽和内联状态编辑。
- status 有 `reflects` 与 Git HEAD 的新鲜度比对。
- report 按日期桶分组，并区分 Active 与 Backlog。
- misc 是刻意保持简单的文档列表。
- Todo 展示的不是一种文档，而是 issue 正文中任务项的跨文档投影，且拥有独立的勾选写回行为。

所以最优雅的边界是：**共享工作台机制，保留领域列表组件**。不把它们改成一个带几十个配置项和 render callback 的“万能集合面板”。

### 一、用类型表达导航状态机

比起在 `ProjectState` 旁边单独放一个可能与 `view` 失配的 `collectionOrigin`，更稳固的建模是让主工作台和集合工作台成为顶层判别联合，并把返回目标放进集合状态本身：

```ts
type MainPage =
  | { kind: 'document'; path: string | null }
  | { kind: 'root' }
  | { kind: 'workspace'; path: string };

type CollectionKind =
  | { kind: 'documents'; docType: DocType }
  | { kind: 'todos' };

type ProjectView =
  | { mode: 'main'; page: MainPage }
  | {
      mode: 'collection';
      browser: {
        kind: CollectionKind;
        workspacePath: string | null;
        selectedPath: string | null;
      };
      returnTo: MainPage;
    };
```

这个模型有三个重要好处：

- 集合工作台天然必须携带 `returnTo`，不会出现“界面在集合模式，但 origin 恰好是 null”的非法组合。
- `returnTo` 的类型不能是另一个 collection，从结构上禁止集合浏览器嵌套。
- Todo 作为浏览器种类被正式建模，但不被伪造成 `DocType`；它的 `selectedPath` 仍然可以指向来源 issue。

Store 对外不再暴露“先随便改 view，然后由组件补操作”的细粒度 API，而是提供完整的用户意图：

```ts
enterCollection(kind, workspacePath)
changeCollectionScope(workspacePath)
selectCollectionDetail(path)
leaveCollection()
openCollectionDetailInMain()
```

每个导航命令都经过现有的 navigation intent 和 `flushBeforeSwitch`，只在保存成功、项目 scope 仍一致、意图仍是最新时提交整个状态迁移。`changeCollectionScope` 与 `enterCollection` 必须分开，避免在集合内清除工作区过滤时意外覆盖 `returnTo`。

`openCollectionDetailInMain` 是一个明确的“提升为主页面文档”动作：它与返回不同，会把当前集合详情变成新的主页面，并结束本次集合会话。现有右键菜单和 `TypedHeader` 中的“在默认视图中打开”可以统一调用它。

### 二、一个工作台外壳，两个明确槽位

`ThreePane` 只判断顶层 `mode`，不再判断 issue、status 或其他类型：

```text
ProjectShell
├─ mode = main       -> MainWorkspaceShell
└─ mode = collection -> CollectionWorkspaceShell
                              ├─ CollectionListViewport
                              │  ├─ CollectionPanelSlot
                              │  └─ ReturnToMainButton
                              ├─ ResizableHandle
                              └─ CollectionDetailViewport
                                 └─ DocView
```

`CollectionWorkspaceShell` 只负责以下与领域无关的事情：

- 双栏尺寸、最小宽度、viewport 溢出隔离和持久化分隔位置。
- 左下角返回按钮、列表底部 inset 和返回后的焦点恢复。
- 右侧无选中、加载中、读取失败和文档编辑视图。
- 右侧 `DocView` 的 fluid 布局与“在主页面打开”命令。

左侧槽位通过一个小型、穷尽的 registry 选择领域面板：

```ts
const documentPanels: Record<DocType, CollectionPanelComponent> = {
  issue: IssuePanel,
  status: StatusPanel,
  report: ReportPanel,
  misc: MiscPanel,
};
```

Todo 由 `CollectionKind` 的独立分支渲染 `TodoPanel`。registry 只解决“当前用哪个面板”，不承载列定义、排序函数、筛选函数和业务写操作，因此不会演变成难以理解的配置引擎。

### 三、通用列表能力做成原语，不做成大组件

各领域面板统一接收清晰的容器协议，而不直接读取和改写整个 project store：

```ts
interface CollectionPanelProps {
  root: IrisWorkspace;
  workspacePath: string | null;
  selectedPath: string | null;
  onSelect: (path: string) => Promise<boolean>;
  onChangeScope: (workspacePath: string | null) => Promise<boolean>;
  onOpenInMain: (path: string) => Promise<boolean>;
}
```

只有容器知道导航状态机；面板只知道投影数据和用户回调。这会让各列表可以在测试中直接传入数据与 spy，不需要伪造全局 store。

真正值得共享的列表能力拆成小原语和 hook：

- `CollectionPanelHeader`：标题、范围 chip、数量与工具栏 actions 槽位。
- `CollectionScrollArea`：统一滚动、底部 inset 和 scroll memory。
- `CollectionRow`：统一高度、选中态、活动行、拖拽、右键菜单与单行截断规则。
- `GroupHeader` 和 `CollectionEmptyState`：统一分组与空状态的布局语汇。
- `useCollectionListNavigation`：统一 `j/k`、方向键、`Enter/o` 与活动行滚动。

列宽、单元格内容、分组规则和行内编辑仍属于各面板。例如 issue 的测量式四列布局不应强加给 Todo，status 的 Freshness 也不应被包装成一个所有面板都必须理解的通用 cell type。

键盘活动行应由当前的数字索引升级为文档路径或 Todo 稳定 key。当筛选、分组折叠或 watcher rescan 使列表长度改变时，稳定 key 不会像 `activeIdx` 一样悠然指向另一篇文档。

### 四、明确分离四类状态

集合整改后有四类容易混在一起的状态，应该分开归属：

1. **导航状态**：当前集合种类、工作区范围、`selectedPath` 和 `returnTo`，属于 `project-store`。
2. **持久显示偏好**：分组字段、排序字段和顺序，属于已有 `view-prefs`/localStorage，按面板种类保存。
3. **会话级列表记忆**：搜索词、折叠组、活动 key 和滚动位置，由通用 panel-memory hook 按 `projectRoot + collectionKind + workspacePath` 保存，不写进项目。
4. **领域暂态**：Todo 正在勾选的行、status 正在读取的 HEAD、issue 的状态下拉菜单，留在各领域面板内部。

这个分层可以避免两种极端：既不会把所有东西都塞进全局 store，也不会因为组件卸载而丢失用户刚才的列表位置。

### 五、创建、删除和 watcher 回声也要进入统一语义

现有 `CreateDocDialog` 在成功后固定 `selectDoc`，会破坏新的集合语义。创建请求需要携带明确的成功去向：从主页面创建就在主页面打开，从集合工作台创建就在当前右侧详情中选中，不离开集合。去向应该是可判别的数据，而不是让对话框根据打开时的全局 view 自行猜测。

文档被删除时，store 对所有集合类型统一清空失效的 `selectedPath` 和 selection memory，右侧回到未选中状态，而不退出集合。Todo 来源 issue 被删除后，同样由 scan 投影自然移除相关任务组。

当 watcher rescan 使当前文档不再符合列表过滤条件时，右侧详情不应立即被关闭：“当前选中”是导航状态，“当前在过滤后列表可见”是列表投影，两者不应被强制绑定。列表可以显示选中项已不在当前筛选中的轻量提示，但用户正在编辑的详情应保持稳定。

### 六、迁移时保持可验证的小步骤

整改不适合一次把所有面板重写完再测。最稳定的分割方式是先收敛状态机和外壳，然后一个面板一个面板地接入。Issue 先做等价迁移，用它证明共享架构没有丢掉现有能力；再按 misc、status、report、Todo 的复杂度从低到高迁移。

每个面板接入时都应同时完成行选中、右侧详情、创建后选中、删除后清理、返回主页面和对应测试。不留下“看起来已是双栏，但某个操作又偷偷退回主页面”的半迁移状态。

### 最终判断

这次整改的理想结果不是“五个面板长得一样”，而是“五个面板遵守同一套工作台协议”：

- 进入和返回的导航语义一样。
- 左列表、右详情和分隔线的几何边界一样。
- 选中、加载、保存、冲突、删除和焦点恢复的生命周期一样。
- 工具栏、行、分组、空状态和键盘操作使用同一套原语。
- 每个面板仍然可以保留它的信息架构和领域操作。

这样共享的是稳定机制，而不是偶然相似的界面代码。未来新增一种集合面板时，它只需实现左侧领域列表并注册到工作台，无需再复制导航、双栏、编辑器和返回逻辑。

## 范围修正：Todo 不属于文档集合浏览器

上述方案中将 Todo 作为一种 `CollectionKind` 纳入双栏工作台的部分作废，以本节为准。

Todo 与 issue/status/report/misc 的根本区别不是“页面样式不同”，而是数据模型和主从关系不同：

| 维度 | 文档集合浏览器 | Todo 面板 |
| --- | --- | --- |
| 数据单元 | 某一 `DocType` 下的文档 | issue 正文中未勾选任务的跨文档投影 |
| 主操作 | 选中文档并在右侧持续编辑 | 扫描待办、就地勾选、进入来源 issue |
| 布局 | 左侧同类文档列表 + 右侧选中详情 | 全宽按来源 issue 分组的任务列表 |
| 选中语义 | `selectedPath` 是当前浏览器内的详情 | 点击来源就是离开 Todo 并打开 issue |
| 返回控件 | 需要左下角返回主页面 | 不需要集合浏览器的返回控件 |

因此 Todo 应该保持在常规主工作台内，继续由 `view.kind === 'todos'` 表示，由现有 `RightArea` 以全宽 manager 渲染。`openTodos` 是主页面内的视图切换，不进入文档集合状态，不创建 `returnTo`。Todo 行继续调用主页面文档导航，打开来源 issue 是它的正常交互，不是需要修复的“意外退出”。

### 修正后的顶层状态

主页面需要包含 Todo，文档集合浏览器则只接受真实 `DocType`：

```ts
type MainPage =
  | { kind: 'document'; path: string | null }
  | { kind: 'root' }
  | { kind: 'workspace'; path: string }
  | { kind: 'todos'; workspacePath: string | null };

type ProjectView =
  | { mode: 'main'; page: MainPage }
  | {
      mode: 'document-collection';
      browser: {
        docType: DocType;
        workspacePath: string | null;
        selectedPath: string | null;
      };
      returnTo: MainPage;
    };
```

这个模型表达了一个重要行为：用户可以在 Todo 面板显示时，通过仍然存在的左侧类型入口进入 issue/status/report/misc 浏览器；点击左下角返回后，应当能恢复之前的 Todo 主页面视图。Todo 是可恢复的来源页，但不是被统一的集合浏览器。

Store 命令也因此收窄为：

```ts
enterDocumentCollection(docType, workspacePath)
changeDocumentCollectionScope(workspacePath)
selectCollectionDocument(path)
leaveDocumentCollection()
openCollectionDocumentInMain()
```

`selectCollectionDocument` 可以验证目标文档确实与当前 `docType` 一致，Todo 来源 issue 导航则继续走 `selectDoc`。两条路径不共用“选中集合详情”命令。

### 修正后的组件边界

共享外壳应使用更明确的 `DocumentCollectionShell` 命名，而不是似乎可以容纳任意投影页的泛化 `CollectionWorkspaceShell`。它的 registry 只有四个成员：

```ts
const documentCollectionPanels: Record<DocType, DocumentCollectionPanel> = {
  issue: IssuePanel,
  status: StatusPanel,
  report: ReportPanel,
  misc: MiscPanel,
};
```

Todo 不注册到这个 registry，不渲染 `DocumentCollectionShell`，不使用右侧 `DocView` 槽位，不参与 document collection selection memory。它仍可以在真正有收益时复用像空状态、视觉 token 这样的底层 UI 原语，但这不等于复用文档浏览器架构。

### 修正后的迁移范围

本次全面整改只包含 issue、status、report 和 misc：

1. Issue 先等价迁移到 `DocumentCollectionShell`，验证双栏、详情、返回、记忆和“在主页面打开”不回归。
2. Misc 作为最简单的新接入面板，验证通用协议不只是 issue 换名。
3. Status 接入双栏，保留 Git HEAD 新鲜度查询和行展示。
4. Report 接入双栏，保留日期桶、折叠与 Active/Backlog 过滤。

Todo 不改布局、不增加左下角返回按钮、不改成双栏、不迁移行点击语义。只有在顶层 `ProjectView` 类型调整导致编译修复时，才对 Todo 的调度代码做最小适配，不借机重构 `TodoPanel`。

### 修正后的验收边界

- [x] Issue、status、report 和 misc 都使用同一 `DocumentCollectionShell`，并在右侧编辑当前选中的同类文档。
- [x] 四种文档集合都显示统一的左下角返回按钮，Todo 面板不显示该按钮。
- [x] 从 Todo 主页面视图进入任一文档集合后返回，能恢复 Todo 视图及其工作区范围。
- [x] Todo 继续使用全宽分组任务布局，勾选写回和打开来源 issue 的行为不发生回归。
- [x] 代码中的集合工作台类型、registry、selection memory 和布局分支均无 `todos` 成员或特判。

## 实现结果（2026-08-12）

软件打不开的直接原因是前一次修改停在不可编译的中间态：`DocView` 仍调用已删除的
`openIssueInDefaultView`，新集合导航方法存在变量重名，`IssuePanel` 又向尚未扩展的创建目标
传入 `destination`。渲染端 TypeScript 因此无法通过编译，Electron 无法正常加载界面。

本次已完成以下修复和整改：

- 将主页面与文档集合状态分开，集合状态保留准确的 `returnTo` 和来源 workspace；返回可恢复
  文档、根 hub、子工作区 hub 或 Todo，来源文档被删除时按来源 workspace 稳定回退。
- 抽出唯一的 `DocumentCollectionShell`，通过四成员 `DocType` registry 渲染 Issue、status、
  report 和 misc；Todo 不进入 registry，也不显示返回按钮。
- 四类列表统一在左下角显示固定 `ArrowLeft` 返回按钮，并为滚动区预留底部空间。按钮提供
  tooltip、`aria-label`，返回后按类型和 workspace 把焦点恢复到原集合入口。
- 四类集合都在右侧使用 fluid `DocView` 编辑同类文档。store 会拒绝类型或 workspace 不匹配的
  选择；右键和详情 Header 的“在默认界面打开”使用统一事务。
- 集合内新建文档会刷新扫描投影并在当前右侧选中新文档。当前详情删除后清空选择和记忆，
  不退出集合。
- 选择记忆按项目、类型和 scope 隔离；Issue 保留原有筛选/分组/排序/折叠/活动行/滚动记忆，
  Report 补齐 Active/全部、折叠和滚动记忆，status 与 misc 补齐滚动记忆。
- 同步更新异步边界门禁和中英文返回文案。
