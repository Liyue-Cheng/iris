参考设计立场：.iris/issue/2026-09-03-Iris-Agent-架构设计与本质建模.md

背景：在新架构(trace → context 纯函数投影)已落地后，设计一个真正可靠的 compact 功能。
本 issue 只做调研与方案设计，不落地代码。以下设计结论基于对当前代码的逐点核对。

## 现状核对（2026-09-04）

### 新架构已落地的部分（compact 的底座）

* `buildAgentTrace(session)` 从 aggregate 推导 turn 级 trace；`buildAgentContext(trace, policy)` 是
  纯函数投影——这正是 compact 的天然落点。见 `src/main/agent/trace-context.ts`。
* `store.history()` = `buildAgentContextFromSession(session)`，通过协议 v14 的 `run`/`resume`
  请求的 `history` 字段发送给 worker，worker 端 `restoreIrisPiHistory` 逐条恢复进 Pi session。
* `intent.content` 存的是**原始用户消息**，不是每轮重复的完整组装 prompt（本轮对比旧 issue 的
  重大改进）。完整 envelope（agent-base + software + project + anchor + user-request）只在
  当次请求经 `run.prompt` 一次性发送，不进 trace。

### 尚未实现的空白

1. **compact 的 policy 是悬空的。** `AgentContextPolicy = { maxIntents?: number }` 是唯一的
   `buildAgentContext` 缩减机制，但 `store.history()` 从不传 policy——`maxIntents` 从未被实际触发。
   它没有摘要、没有 token 水位、没有持久化边界、没有审计。
2. **聚合没有 token usage 账本。** `session-model.ts` 的 aggregate 无 `usage`/`tokens`/
   `contextWindow` 字段。系统不知道“当前上下文多大”。
3. **没有 compaction 领域实体。** 无 summary、无 active pointer、无 compaction artifact、无
   trigger 状态机。
4. **Pi 的 compact 仍关闭。** `pi-adapter.ts` 显式 `SettingsManager.inMemory({ compaction: { enabled: false } })`。
5. **真实 token 数据已存在但未用于水位。** 终端监督和 provider-attempt 有 usage 上报
   （`requestTerminalSupervision` 返回 `usageTokens`），但未汇入聚合用于 compact 决策。

## 设计立场

在新架构下，compact 的语义应当严格遵循「trace 不变、context = pure(trace, policy)」：

* **trace 永远完整可审计**，compact 不删除、不改写任何 turn 级事实。
* **compact 改变的是 context 呈现**——即 `buildAgentContext` 的 policy 参数，外加一份可持久化、
  可溯源的「压缩契约」，告诉每次投影“哪些旧 turn 被摘要替代、从哪开始保留原文”。
* **压缩边界只落在完整 intent 之间**，不拆 intent/turn 的原子组。

因此 compact 的落点分两层：

**第一层（纯函数，无副作用）：`AgentContextPolicy` 成型。** 把当前悬空的 `maxIntents` 扩展为
真正的策略对象，使其能在 `buildAgentContext` 内把 trace 投影成「最新摘要 + 保留的最近 N 个
完整 intent 原文」。

**第二层（持久化领域事实）：压缩契约。** 因为 `store.history()` 每次调用都重新投影，
若每次结果不同（依赖某个可变状态），就破坏了 `context = pure(trace)` 的不变式。所以压缩契约
必须是**可持久化的不可变事实**，而不是临时算出来的水位。这样同一个 trace + 同一契约，永远
投影出同一个 context。

## 详细方案

### 1. 领域模型增量（`session-model.ts`）

新增两类字段到 `AgentSessionAggregate`：

```ts
interface AgentCompaction {
  id: string;
  state: 'running' | 'completed' | 'failed' | 'canceled';
  trigger: 'threshold' | 'overflow' | 'manual';
  sourceRevision: number;            // 创建时的 session revision，供 CAS 校验
  coveredThroughIntentId: string;    // 摘要覆盖到哪个完整 intent
  firstRetainedIntentId: string;     // 从哪个 intent 开始保留原文
  summary?: string;                   // 脱敏后实际进入 context 的摘要文本
  summarySha256?: string;
  model: IrisAgentModelRef;           // 生成摘要所用模型
  tokensBefore: number;
  estimatedTokensAfter?: number;
  measurement: 'reported' | 'estimated';
  providerUsage?: AgentUsage;         // 摘要调用的真实 usage，若可用
  error?: string;
  createdAt: number;
  completedAt?: number;
}
```

外加聚合字段：

```ts
compactions: AgentCompaction[];          // 全部压缩记录（追加，不删除）
activeCompactionId: string | null;       // 当前生效的 completed 压缩契约
```

不新增 `compacting` 运行时状态——它属于临时执行状态，可用现有 `session.state` 的
`starting`/`running` 表达；也可在需要区分时扩展 runtime state，但不引入单独的领域实体。

### 2. Context 投影升级（`trace-context.ts`）

`buildAgentContext(trace, policy)` 的 policy 扩展为：

```ts
interface AgentContextPolicy {
  maxIntents?: number;              // 保留的最近完整 intent 原文数量
  summary?: {
    text: string;                   // 已持久化的摘要
    coveredThroughIntentId: string; // 摘要覆盖到哪个 intent
    firstRetainedIntentId: string;  // 保留原文的起点
    sha256: string;
  };
}
```

语义：当 `summary` 存在时，把 `coveredThroughIntentId`（含）之前的所有 intent 折叠成一条
摘要 message（provider 侧带固定边界，说明“这是历史摘要，仅作背景；当前 system/project 规则
优先”）；`firstRetainedIntentId` 之后的 intent 保留完整原文；两者之间不允许存在半个 intent。
`maxIntents` 作为兜底策略，用于无摘要时只关注最近 N 条。

关键不变式：**同一个 trace + 同一份已持久化摘要，永远投影出同一个 context。** 摘要文本
`summary.text` 必须作为不可变事实持久化，不能每次重新生成。

### 3. 摘要生成与触发（`session-manager.ts`）

**触发分三类：**

* **threshold**：每次发送新请求前，对「当前投影 + 本轮输入」做 token 预检，命中水位则先 compact
  再发业务请求。token 估算优先用 provider 最近一次真实 usage，其次用保守估算，并在 UI 标“估算”。
* **overflow**：provider 明确拒绝上下文后，在同一 turn 里 compact 并自动重试一次，不再循环。
* **manual**：session 静止时用户主动触发，不创建伪 user turn。

**threshold 流程（对应发送一条新消息）：**

```text
创建 intent 并持久化（含本轮 user message）
  → preflight 投影 + 本轮输入的 token 估算
  → 命中水位？
      → 创建 running compaction 并提交（含 sourceRevision、coveredThrough、firstRetained）
      → 用当前模型生成摘要（provider-neutral，可取消）
      → 校验 sourceRevision 与 sourceDigest 未变
      → 提交 completed compaction（含 summary、summarySha256、tokensBefore/After、measurement）
      → 原子切换 activeCompactionId
      → 重建 worker，校验 projection digest
      → 发送原业务请求
  → 未命中水位？
      → 直接发送业务请求
```

**overflow 恢复流程：** 当前 attempt 失败但 turn 保持可恢复 → 按 overflow 触发 compact →
成功后从新投影重建 worker → 同一 turn 自动重试一次 → 再次 overflow 则 pause，不循环。

**摘要内容要求（provider-neutral，固定 prompt 版本）：** 保留用户目标与验收口径、已确认的决定/
约束/被否决方案、当前实现状态与重要文件符号、已执行操作与仍存在的外部副作用、测试结果与未解
问题、继续工作所需的确切名称/数值/错误信息。**不重复** software/project prompt 或当前 anchor
正文（这些每次请求都会重新读取）。文件 effects/边界/hash 由系统确定性记录，不依赖模型复述。

### 4. 注入层去重（前置）

当前 `preparePrompt` 每次现读盘、现组装完整 envelope，且 `assembleAgentPrompt` 的 `<iris-agent-base>`、
`<iris-software>`、`<iris-project>`、`<iris-anchor>` 每轮都会重复。虽然这些不进 trace 了，但它们
仍在**每次请求的 `run.prompt`** 里重复发送。compact 不解决这个重复——它只解决 context 投影。
建议作为 compact 的前置（低风险、独立可验证）：

* 方法层（agent/software/project）走符号链接：每次运行时现读当前版本，不复制进 trace。
* 材料层（anchor）走锚点+diff：创建时锚定基准，当前注入 diff。
* 这条建议与紧凑 issue 正交，可单独先做，也可与 compact 一起做。

### 5. 边界语义

* **Continue/Rewind/Branch/模型切换** 都明确理解同一套边界：
  * **Rewind** 若越过 `coveredThroughIntentId`，回退到更早的 completed compaction，找不到则回退
    full history。active pointer 回退与 turn 移除在同一 journal transaction。
  * **Branch** 从 intent `T` 分支时，选择 `coveredThroughIntentId <= T` 的最新 completed compaction，
    自包含复制（记录 originCompactionId），不跨 session 依赖父 artifact。
  * **模型切换** 后摘要仍 provider-neutral 可继续用；切小窗口重新算水位，切大窗口不自动“解压”。
* **Stop** 在 compact 阶段应可取消摘要调用；自动 compact 被 Stop 后该 turn 进入 paused，旧投影
  保持有效。

### 6. 审计与 artifact

每个 compaction 一个独立目录，`summary.txt` 存进入未来 context 的脱敏文本，`source-index.json`
只记录 frame id/边界/hash/前一个 compaction id/prompt version，不重复保存完整 transcript。
摘要 provider payload 与普通 provider context 用同一 allowlist 和 secret redaction。

### 7. UI

* 模型选择器旁加稳定的 Context 指示器（图标 + 水位），tooltip 显示“87k / 128k（估算/报告）”，
  点击 popover 展示 active context 组成与“立即整理上下文”。
* compact 进行中显示“正在整理上下文… [停止]”；overflow 恢复时显示“上下文已满，正在整理并重试… [停止]”。
* timeline 在覆盖边界与保留边界之间插入非卡片式 divider（“已整理 18 轮 · 96k → 22k [展开]”），
  展开显示摘要原文、范围、trigger、模型、前后 token。
* 自动 compact 失败时保留原历史与旧投影，提供 [重试整理] [切换模型] [展开技术详情]。

## 与旧紧凑 issue 的关系

旧 issue（`2026-08-20-iris-agent-compact.md`）在设计时基于旧模型（provider-frame transcript
兼任 trace 与 context）。新架构落地后，其中「compact 需要持久化投影、不能关 Pi compact 只靠
临时状态」的**核心判断仍然成立**，但许多具体设计的落点已经变化：

* 旧 issue 的「先做输入去重：把历史 user request 与每轮 assembled envelope 分离」——新架构
  已通过 `intent.content` 存原始请求、envelope 只作单次 `run.prompt` 实现。**这一项已完成。**
* 旧 issue 的 `history()` 直接过滤全部 transcript——新架构已是 `buildAgentContext` 纯函数投影。
  **底座已具备。**
* 旧 issue 的「provider-frame 有注入合成帧（turn-input:、interrupted-tool-result:）污染 trace」——
  新架构已在 context 投影时合成 interrupted tool result，不写回 trace。**这一项也已解决。**

因此本 issue 的设计是新架构下 compact 语法的**重述与收窄**，不是从零开始。剩余真正要做的：
把悬空的 `maxIntents` 升级为完整的持久化压缩契约 + 摘要生成 + token 水位 + UI。
