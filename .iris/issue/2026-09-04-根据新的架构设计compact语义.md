参考设计立场：.iris/issue/2026-09-03-Iris-Agent-架构设计与本质建模.md

背景：在新架构(trace → context 纯函数投影)已落地后，设计一个真正可靠的 compact 功能。
本 issue 只做调研与方案设计，不落地代码。以下设计结论基于对当前代码的逐点核对。

## 现状核对（2026-09-04）

### 新架构已落地的部分（compact 的底座）

* `buildAgentTrace(session)` 从 aggregate 推导 turn 级 trace；`buildAgentContext(trace, policy)` 是
  纯函数投影——这正是 compact 的天然落点。见 `src/main/agent/trace-context.ts`。
* `store.history()` = `buildAgentContextFromSession(session)`，通过协议 v14 的 `run`/`resume`
  请求的 `history` 字段发送给 worker，worker 端 `restoreIrisPiHistory` 逐条恢复进 Pi session。
* `intent.content` 存的是**原始用户消息**，不是每轮重复的完整组装 prompt（本轮对比旧 issue 的
  重大改进）。完整 envelope（agent-base + software + project + anchor + user-request）只在
  当次请求经 `run.prompt` 一次性发送，不进 trace。

### 尚未实现的空白

1. **compact 的 policy 是悬空的。** `AgentContextPolicy = { maxIntents?: number }` 是唯一的
   `buildAgentContext` 缩减机制，但 `store.history()` 从不传 policy——`maxIntents` 从未被实际触发。
   它没有摘要、没有 token 水位、没有持久化边界、没有审计。
2. **聚合没有 token usage 账本。** `session-model.ts` 的 aggregate 无 `usage`/`tokens`/
   `contextWindow` 字段。系统不知道“当前上下文多大”。
3. **没有 compaction 领域实体。** 无 summary、无 active pointer、无 compaction artifact、无
   trigger 状态机。
4. **Pi 的 compact 仍关闭。** `pi-adapter.ts` 显式 `SettingsManager.inMemory({ compaction: { enabled: false } })`。
5. **真实 token 数据已存在但未用于水位。** 终端监督和 provider-attempt 有 usage 上报
   （`requestTerminalSupervision` 返回 `usageTokens`），但未汇入聚合用于 compact 决策。

## 设计立场

在新架构下，compact 的语义应当严格遵循「trace 不变、context = pure(trace, policy)」：

* **trace 永远完整可审计**，compact 不删除、不改写任何 turn 级事实。
* **compact 改变的是 context 呈现**——即 `buildAgentContext` 的 policy 参数，外加一份可持久化、
  可溯源的「压缩契约」，告诉每次投影“哪些旧 turn 被摘要替代、从哪开始保留原文”。
* **压缩边界只落在完整 intent 之间**，不拆 intent/turn 的原子组。

因此 compact 的落点分两层：

**第一层（纯函数，无副作用）：`AgentContextPolicy` 成型。** 把当前悬空的 `maxIntents` 扩展为
真正的策略对象，使其能在 `buildAgentContext` 内把 trace 投影成「最新摘要 + 保留的最近 N 个
完整 intent 原文」。

**第二层（持久化领域事实）：压缩契约。** 因为 `store.history()` 每次调用都重新投影，
若每次结果不同（依赖某个可变状态），就破坏了 `context = pure(trace)` 的不变式。所以压缩契约
必须是**可持久化的不可变事实**，而不是临时算出来的水位。这样同一个 trace + 同一契约，永远
投影出同一个 context。

## 详细方案

### 1. 领域模型增量（`session-model.ts`）

新增两类字段到 `AgentSessionAggregate`：

```ts
interface AgentCompaction {
  id: string;
  state: 'running' | 'completed' | 'failed' | 'canceled';
  trigger: 'threshold' | 'overflow' | 'manual';
  sourceRevision: number;            // 创建时的 session revision，供 CAS 校验
  coveredThroughIntentId: string;    // 摘要覆盖到哪个完整 intent
  firstRetainedIntentId: string;     // 从哪个 intent 开始保留原文
  summary?: string;                   // 脱敏后实际进入 context 的摘要文本
  summarySha256?: string;
  model: IrisAgentModelRef;           // 生成摘要所用模型
  tokensBefore: number;
  estimatedTokensAfter?: number;
  measurement: 'reported' | 'estimated';
  providerUsage?: AgentUsage;         // 摘要调用的真实 usage，若可用
  error?: string;
  createdAt: number;
  completedAt?: number;
}
```

外加聚合字段：

```ts
compactions: AgentCompaction[];          // 全部压缩记录（追加，不删除）
activeCompactionId: string | null;       // 当前生效的 completed 压缩契约
```

不新增 `compacting` 运行时状态——它属于临时执行状态，可用现有 `session.state` 的
`starting`/`running` 表达；也可在需要区分时扩展 runtime state，但不引入单独的领域实体。

### 2. Context 投影升级（`trace-context.ts`）

`buildAgentContext(trace, policy)` 的 policy 扩展为：

```ts
interface AgentContextPolicy {
  maxIntents?: number;              // 保留的最近完整 intent 原文数量
  summary?: {
    text: string;                   // 已持久化的摘要
    coveredThroughIntentId: string; // 摘要覆盖到哪个 intent
    firstRetainedIntentId: string;  // 保留原文的起点
    sha256: string;
  };
}
```

语义：当 `summary` 存在时，把 `coveredThroughIntentId`（含）之前的所有 intent 折叠成一条
摘要 message（provider 侧带固定边界，说明“这是历史摘要，仅作背景；当前 system/project 规则
优先”）；`firstRetainedIntentId` 之后的 intent 保留完整原文；两者之间不允许存在半个 intent。
`maxIntents` 作为兜底策略，用于无摘要时只关注最近 N 条。

关键不变式：**同一个 trace + 同一份已持久化摘要，永远投影出同一个 context。** 摘要文本
`summary.text` 必须作为不可变事实持久化，不能每次重新生成。

### 3. 摘要生成与触发（`session-manager.ts`）

**触发分三类：**

* **threshold**：每次发送新请求前，对「当前投影 + 本轮输入」做 token 预检，命中水位则先 compact
  再发业务请求。token 估算优先用 provider 最近一次真实 usage，其次用保守估算，并在 UI 标“估算”。
* **overflow**：provider 明确拒绝上下文后，在同一 turn 里 compact 并自动重试一次，不再循环。
* **manual**：session 静止时用户主动触发，不创建伪 user turn。

**threshold 流程（对应发送一条新消息）：**

```text
创建 intent 并持久化（含本轮 user message）
  → preflight 投影 + 本轮输入的 token 估算
  → 命中水位？
      → 创建 running compaction 并提交（含 sourceRevision、coveredThrough、firstRetained）
      → 用当前模型生成摘要（provider-neutral，可取消）
      → 校验 sourceRevision 与 sourceDigest 未变
      → 提交 completed compaction（含 summary、summarySha256、tokensBefore/After、measurement）
      → 原子切换 activeCompactionId
      → 重建 worker，校验 projection digest
      → 发送原业务请求
  → 未命中水位？
      → 直接发送业务请求
```

**overflow 恢复流程：** 当前 attempt 失败但 turn 保持可恢复 → 按 overflow 触发 compact →
成功后从新投影重建 worker → 同一 turn 自动重试一次 → 再次 overflow 则 pause，不循环。

**摘要内容要求（provider-neutral，固定 prompt 版本）：** 保留用户目标与验收口径、已确认的决定/
约束/被否决方案、当前实现状态与重要文件符号、已执行操作与仍存在的外部副作用、测试结果与未解
问题、继续工作所需的确切名称/数值/错误信息。**不重复** software/project prompt 或当前 anchor
正文（这些每次请求都会重新读取）。文件 effects/边界/hash 由系统确定性记录，不依赖模型复述。

### 4. 注入层去重（前置）

当前 `preparePrompt` 每次现读盘、现组装完整 envelope，且 `assembleAgentPrompt` 的 `<iris-agent-base>`、
`<iris-software>`、`<iris-project>`、`<iris-anchor>` 每轮都会重复。虽然这些不进 trace 了，但它们
仍在**每次请求的 `run.prompt`** 里重复发送。compact 不解决这个重复——它只解决 context 投影。
建议作为 compact 的前置（低风险、独立可验证）：

* 方法层（agent/software/project）走符号链接：每次运行时现读当前版本，不复制进 trace。
* 材料层（anchor）走锚点+diff：创建时锚定基准，当前注入 diff。
* 这条建议与紧凑 issue 正交，可单独先做，也可与 compact 一起做。

### 5. 边界语义

* **Continue/Rewind/Branch/模型切换** 都明确理解同一套边界：
  * **Rewind** 若越过 `coveredThroughIntentId`，回退到更早的 completed compaction，找不到则回退
    full history。active pointer 回退与 turn 移除在同一 journal transaction。
  * **Branch** 从 intent `T` 分支时，选择 `coveredThroughIntentId <= T` 的最新 completed compaction，
    自包含复制（记录 originCompactionId），不跨 session 依赖父 artifact。
  * **模型切换** 后摘要仍 provider-neutral 可继续用；切小窗口重新算水位，切大窗口不自动“解压”。
* **Stop** 在 compact 阶段应可取消摘要调用；自动 compact 被 Stop 后该 turn 进入 paused，旧投影
  保持有效。

### 6. 审计与 artifact

每个 compaction 一个独立目录，`summary.txt` 存进入未来 context 的脱敏文本，`source-index.json`
只记录 frame id/边界/hash/前一个 compaction id/prompt version，不重复保存完整 transcript。
摘要 provider payload 与普通 provider context 用同一 allowlist 和 secret redaction。

### 7. UI

* 模型选择器旁加稳定的 Context 指示器（图标 + 水位），tooltip 显示“87k / 128k（估算/报告）”，
  点击 popover 展示 active context 组成与“立即整理上下文”。
* compact 进行中显示“正在整理上下文… [停止]”；overflow 恢复时显示“上下文已满，正在整理并重试… [停止]”。
* timeline 在覆盖边界与保留边界之间插入非卡片式 divider（“已整理 18 轮 · 96k → 22k [展开]”），
  展开显示摘要原文、范围、trigger、模型、前后 token。
* 自动 compact 失败时保留原历史与旧投影，提供 [重试整理] [切换模型] [展开技术详情]。

## 与旧紧凑 issue 的关系

旧 issue（`2026-08-20-iris-agent-compact.md`）在设计时基于旧模型（provider-frame transcript
兼任 trace 与 context）。新架构落地后，其中「compact 需要持久化投影、不能关 Pi compact 只靠
临时状态」的**核心判断仍然成立**，但许多具体设计的落点已经变化：

* 旧 issue 的「先做输入去重：把历史 user request 与每轮 assembled envelope 分离」——新架构
  已通过 `intent.content` 存原始请求、envelope 只作单次 `run.prompt` 实现。**这一项已完成。**
* 旧 issue 的 `history()` 直接过滤全部 transcript——新架构已是 `buildAgentContext` 纯函数投影。
  **底座已具备。**
* 旧 issue 的「provider-frame 有注入合成帧（turn-input:、interrupted-tool-result:）污染 trace」——
  新架构已在 context 投影时合成 interrupted tool result，不写回 trace。**这一项也已解决。**

因此本 issue 的设计是新架构下 compact 语法的**重述与收窄**，不是从零开始。剩余真正要做的：
把悬空的 `maxIntents` 升级为完整的持久化压缩契约 + 摘要生成 + token 水位 + UI。

## 实现结果（2026-09-04）

本轮落地了 compact 的核心闭环：领域模型、纯函数投影、触发状态机和边界语义。
`src/main/agent/compaction.ts` 是新的领域模块，`compaction.test.ts` 与
`session-manager.test.ts` 的新 describe 块覆盖它。

### 核心不变式

**压缩契约是持久化的领域事实，不是临时算出的水位。** 这是「可靠」的关键：
`store.history()` 每次调用都重新投影，如果折叠依赖任何可变状态，`context = pure(trace)`
就被破坏了。因此摘要文本 `summary` 与 `summarySha256` 内嵌在 `AgentCompaction` 里随
journal 持久化；`activeAgentContextPolicy(session)` 从 `activeCompactionId` 推导策略，
同一 trace 加同一契约永远投影出同一 context。摘要不会在投影时被重新生成。

**Trace 永不改写。** compact 只改变 `buildAgentContext` 的产物，`intents` / `turns` /
`timeline` / `effects` 全部原样保留。测试「keeps the full Trace on disk after Context folds」
断言这一点。

### 领域模型

`AgentSessionAggregate` 新增 `compactions: AgentCompaction[]` 与
`activeCompactionId: string | null`。`compactions` 进入 `session-events.ts` 的
`COLLECTIONS`，因此走既有的 journal 序列化、append-order 与状态机校验：
`running → completed | failed | canceled`，终态不可再变。引用校验要求两个边界 Intent
都存在，且 `activeCompactionId` 只能指向 `completed` 契约。

磁盘上已存在的 v3 会话没有这两个字段，`normalizeAgentSessionAggregate()` 在
snapshot 读取与 journal 重放两条加载路径上补齐它们，因此旧数据不会触发新不变式。
v2 迁移器输出空契约。

### 边界选择

`planAgentCompaction()` 从后向前累计要保留的原文尾部，再把边界退到最近一个
`completed` Intent，因此边界只落在完整 Intent 之间，且永不覆盖 `running` /
`paused` Intent。至少保留一个完整 Intent 原文。已被上一个契约覆盖的前缀不再重复
摘要——新摘要的输入是「上一次 summary + 此后新增的完整 Intent」。

当边界无法前进时（尾部已经是唯一可保留的 Intent）返回 `null`，调用方原样发送。
测试「declines a second compaction until new settled history arrives」锁定这一点。

### 摘要生成

摘要是一次**独立的 provider 调用，不属于任何 Intent**：`pi-adapter.ts` 的
`summarizeIrisAgentHistory()` 用 `modelRuntime.completeSimple()` 发起，无工具、
不建 Pi Session、不 append 任何会话历史，因此不可能产生 Trace 事实。它复用现有
provider profile、代理与 secret 脱敏管线，不需要升级 worker 协议。

它以 `summarizeContext` 选项注入 `IrisAgentSessionManager`，`app-main.ts` 接上真实
实现。没有注入时 compact 不可用而不是伪造摘要——测试
「rejects a manual compaction when no runtime summarizer is available」锁定该行为。

摘要提交是两段式：先 commit `running` 契约，生成成功后校验 `sourceRevision` 未变，
再用第二次 commit 写入摘要并原子切换 `activeCompactionId`。历史在摘要期间变动时
契约标记 `failed`，旧投影继续有效。空摘要被拒绝而不是激活一个无用契约。

### 触发与失败

threshold 触发在 `sendSession()` 组装请求前、创建新 Intent 前执行，因此计划只会
看到已完成的 Intent。摘要失败或不可用时**不阻塞用户请求**：send 继续用旧投影发出。
测试「sends the request uncompacted when summarizing fails」锁定这一点。

Stop 在进入 per-session 命令队列**之前**触发 abort——否则 Stop 会排在正在运行的
摘要请求后面，永远无法取消它。

### Rewind / Branch

`realignActiveCompaction()` 在 rewind 提交时同批执行：摘要只在其边界仍在 active path
上时有效，否则回退到仍被覆盖的更早契约，找不到就回到全量历史。
`buildAgentContext` 里 `resolveSummaryFold()` 也做同样的降级——找不到边界 Intent 就
不折叠，因此 context 永不声称摘要了它看不见的 Intent。

`inheritAgentCompactionInto()` 在 `copyBranchFacts()` 中被两条 fork 路径共用：只复制
两个边界 Intent 都存在于分支内的契约，自包含复制，不依赖父 Session artifact。

### 模型切换

摘要文本是 provider-neutral 的，模型切换后继续有效。`AgentCompaction.model` 只记录
生成它的模型作为审计事实，不参与投影。

### token 估算

`estimateAgentTokens()` 分别计数 CJK 与拉丁字符（CJK 约 1 字 1 token，拉丁约 4 字符
1 token），避免中文会话被严重低估。`measurement` 当前恒为 `estimated`——本轮没有接入
provider 真实 usage，UI 展示时必须标注为估算。

一个实测结论：**摘要有固定开销，只有被覆盖的历史足够大时折叠才划算。** 四个短
Intent 的场景下摘要框架比它替代的历史更贵。这是 `keepRecentTokens` 与触发水位需要
保持保守的原因。

### 验证

`npm run typecheck`（含 async boundary 门禁）通过。全量单 fork Vitest：83 个文件、
496 项全部通过，包含 `compaction.test.ts` 19 项与 session-manager 的 5 项 compaction
测试。此前 `session-viewport.test.ts` 的既有失败在本轮已不复现。未运行 build、dist、
开发服务器或截图。

### 本轮未做（诚实边界）

* **没有任何 UI。** Context 水位指示器、compacting 状态栏、timeline divider、失败恢复
  操作都未实现。用户目前看不到压缩发生，只能从 provider context artifact 观察。
* **手动 compact 无入口。** `manager.compact()` 已实现并有测试，但没有 IPC 通道，
  renderer 无法调用。自动 threshold 压缩已经在应用中生效。
* **overflow 触发未接线。** `trigger: 'overflow'` 在类型与状态机中已定义，但没有调用点；
  provider 明确拒绝上下文后不会自动 compact 并重试。
* **没有 compaction artifact 目录。** 摘要只存在聚合内，没有独立的 `summary.txt` /
  `source-index.json` 审计目录。
* **provider-context bundle 仍写 `compaction: 'disabled'`。** 该字段没有升级为可解释
  投影的 schema，因此还不能从某次 provider 调用追溯到具体契约。
* **Pi 自身的 compact 保持关闭**（设计如此，避免两套互不知情的压缩状态）。

## 2026-09-05 重新界定问题：多供应商上下文治理优先于 UI

本轮调研确认，问题本质不是“Agent 页面缺少水位指示器”，而是模型运行配置的所有权错误：当前 Agent 顶部同时承担供应商发现、模型选择和请求级状态展示，导致模型目录查询、端点兼容性、上下文窗口和 compact 阈值都变成了会话界面的临时行为。这样做会把不同供应商的协议差异伪装成一个统一下拉框，也无法保证下一次请求使用的上下文策略与上一次一致。

治理原则如下：

* **设置页是配置事实源。** 供应商凭据、端点、模型目录来源、手工模型、每个模型的上下文窗口和 compact 水位都在设置页管理；Agent 页面只消费已保存的可用模型配置。
* **模型选择与模型发现分离。** Agent 页面只选择“已启用且配置完整”的模型，不在发送消息时查询供应商端点，也不允许通过页面临时改变上下文窗口。
* **供应商能力显式建模。** “支持模型目录查询”不是默认假设；每个供应商 profile 必须声明目录模式：自动发现、手工维护或自动发现后手工补充。目录失败不能阻塞手工模型。
* **上下文策略属于 `(providerProfile, modelId)`。** 不能只按 provider 设置，也不能只按当前 session 设置；切换模型时应切换到该模型自己的窗口、保留尾部和压缩水位。
* **运行时只读快照。** 发送请求前解析设置页生成的不可变模型运行快照，并把快照版本写入 provider-context artifact；设置修改不追溯改变已经完成的调用。

## 设置页：模型与供应商治理方案

### 1. 供应商 profile 编辑流程

在“设置 → Iris Agent → 供应商与模型”中，新增/编辑 profile 使用同一表单，不在 Agent 页面提供供应商管理入口。表单分为三段：

1. **连接**：名称、协议模板、Base URL、API key/凭据引用、代理选项、连通性测试。
2. **模型目录**：目录模式切换为“自动发现 / 手工维护 / 自动发现 + 手工补充”；自动发现支持刷新、显示最近成功时间和错误原因；手工维护提供模型 ID、显示名、API 类型等字段。供应商不支持模型目录时，默认进入手工维护，不显示误导性的“加载模型”按钮。
3. **模型策略**：每个模型展开后独立编辑上下文窗口和 compact 参数。保存 profile 时只保存配置，不因一次目录失败删除已有模型。

目录查询必须是显式设置操作或后台低频刷新，不能由 Agent 页面挂载触发。新增或修改 profile 后，只有设置页完成校验并产生新配置版本，Agent 页面才收到 `providers-changed` 事件并刷新本地只读目录。

### 2. 模型条目契约

每个已启用模型至少包含以下字段（名称可按现有类型风格落地）：

* `providerProfileId`、`modelId`、`displayName`、`api`、`enabled`；
* `contextWindowTokens`：供应商文档或用户确认的完整上下文窗口；
* `maxOutputTokens`：输出上限，不能大于上下文窗口；
* `contextPolicy`: `reserveOutputTokens`、`keepRecentTokens`、`compactTrigger`；
* `capabilities`: `listModels`、`streaming`、`toolCalls`、`vision`、`reasoning` 等，未知能力必须标为 `unknown` 而非 `true`；
* `source`: `discovered` / `manual`，以及 `lastVerifiedAt`、`verificationError`。

上下文窗口下拉框提供常用值 **128K、256K、512K、1M**，同时保留“自定义”输入（正整数，单位 token）。不预置 112K、700K 等少见值；目录返回的非标准值仍可原样显示并允许用户改成标准值。保存时校验 `maxOutputTokens + reserveOutputTokens < contextWindowTokens`，并给出实际 token 数而不是模糊的“长上下文”标签。

### 3. compact 水位设置

设置页按模型展示“上下文预算”预览条，而不是让用户直接填写一个难以理解的百分比。推荐默认值：

* `reserveOutputTokens`：16K；
* `keepRecentTokens`：20K；
* `compactTrigger`：上下文窗口减去 reserve，即 128K 模型默认约 112K、256K 模型默认约 240K；
* 高级模式允许改为绝对 token 数或窗口百分比，但最终持久化为绝对 token 数，避免窗口变化后语义漂移。

设置页必须实时显示：`窗口 / 输出预留 / 触发水位 / 保留尾部`，并提示“当前估算来自字符计数，实际 provider usage 可用后优先采用报告值”。模型切换不自动解压已经完成的 compaction；只改变后续投影使用的阈值。

### 4. 可用性与保存规则

模型只有在 profile、端点、凭据、模型 ID、上下文窗口和 API 类型均有效时才进入 Agent 可选目录。验证失败保留草稿和旧版本，显示可修复字段；不因端点不支持目录而阻止手工模型保存。删除 profile 前列出引用它的 session，并要求用户选择迁移模型或保留不可用状态。

## Agent 页面 UI 方案（在治理完成后实施）

Agent 顶部不再承担供应商模型查询和配置编辑，只保留一个紧凑的“当前模型”选择器，选项来自设置页的已启用模型快照。选择器旁显示上下文水位指示器：环形或细条进度、当前 token、窗口上限、数据来源（报告/估算）和 compact 状态。示例 tooltip：`87K / 128K · 估算 · 将在 112K 前整理`。

点击水位指示器打开 context popover，内容按固定顺序展示：

1. system/project/user/tool 各组成部分的 token 估算；
2. 当前 active compaction 的摘要范围、摘要模型、触发原因、前后 token；
3. 最近一次 provider usage、估算误差和配置版本；
4. 操作：`立即整理上下文`、`打开设置中的模型策略`、`查看调用详情`。

会话时间线增加轻量 divider 表示摘要边界；默认只显示“已整理 N 个 intent”，展开后才显示摘要正文和 source-index。自动 compact 失败时保留原投影，顶部显示可关闭的错误状态，并提供“重试整理”“切换到已配置模型”“查看技术详情”；失败不能阻塞普通发送。

模型选择器、context popover 和时间线都不得发起供应商目录请求或修改模型策略。所有修改回到设置页完成，成功保存后通过配置版本事件让 Agent 页面重新计算水位。

## 实施顺序与验收边界

1. 先扩展 provider profile 与 model entry 持久化 schema、迁移旧配置，并为每个模型补齐上下文窗口和 compact policy。
2. 再把目录发现改为设置页显式流程，支持不提供目录的供应商手工模型，Agent 页面改读配置快照。
3. 接入按模型的 `contextWindowTokens`、`reserveOutputTokens`、`keepRecentTokens`，将当前运行时默认值降为迁移兜底。
4. 最后实现 Agent 页水位、context popover、摘要边界和失败恢复 UI。

验收必须覆盖：目录不支持时手工添加模型；目录部分失败不丢失旧模型；128K/256K/512K/1M 默认值与自定义值校验；切换模型使用各自水位；配置版本写入调用审计；自动 compact 失败仍可发送；设置页之外不发生模型目录请求。

### 设置页流程重做（2026-09-05）

原先的“模型与上下文策略”区块存在业务断裂：它只渲染已保存模型，却没有模型导入或手工添加入口，因此用户永远只能看到空状态和保存按钮。现已改为按业务顺序组织：

1. 先展示供应商连接信息和凭据状态。
2. 在供应商卡片内直接输入模型 ID 手工添加，适用于不支持模型目录的端点。
3. 添加模型后，逐行编辑显示名、上下文窗口（128K/256K/512K/1M）、输出预留，并可删除模型。
4. 最后统一保存该供应商的模型配置；空状态明确提示手工添加，不再显示“刷新目录后可维护”的死路径。

随后补充了显式目录操作：供应商卡片提供“从供应商获取模型”按钮，只有用户点击时才请求目录；成功结果导入当前 profile，失败不覆盖已有模型，并保留手工添加路径。
