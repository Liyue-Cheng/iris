# 背景

Iris 的终端实现继承自 Marina。在 Codex TUI 持续输出时，输入区附近的光标会短暂出现在绘制中的错误位置，随后跳回正确位置，形成明显闪动。VS Code 集成终端在此前的人工对照中没有同样的可见闪动。

旧调查记录：`E:\projects\terminal\docs\issues\cursor-2-codex-tui-jitter-vs-vscode.md`

# 当前结论

根因链已经闭合并由修复复测确认：**Codex 每帧末尾先显示光标，随后才移动光标；Windows 系统 ConPTY 又把最终移动重编码成稍后到达的“隐藏、移动、显示”序列。** Iris 并没有凭空计算出第二个光标位置，但会忠实渲染 Codex/ConPTY 暴露出来的中间状态，因此用户能看到闪动。

Iris 改用 `node-pty` 随包携带的 ConPTY DLL 后，原始 synchronized-output 边界得到保留，xterm 不再呈现中间光标位置。用户已使用当前 Codex 版本复测，确认闪动消失。

# 已确认的证据

## 1. 旧探针已经捕获到两个可见光标状态

旧调查记录的关键输出大致为：

```text
同一原子帧：... ESC[33;2H ... ESC[?25h ESC[?2026l
约 12 ms 后：ESC[?25l ESC[32;3H ESC[?25h
```

第一段在绘制末端位置显示光标，并结束 synchronized update；约 12 ms 后，第二段才隐藏光标、移动到输入位置并重新显示。xterm 若逐段处理这些合法控制序列，就会先画出错误位置，再画正确位置。

## 2. Codex 源码确实先 Show、后 MoveTo

本机版本：

```text
codex-cli 0.146.0
```

OpenAI 官方 tag `rust-v0.146.0` 中，`codex-rs/tui/src/custom_terminal.rs` 的帧尾逻辑为：

```rust
self.flush()?;

match cursor_position {
    None => self.hide_cursor()?,
    Some(position) => {
        self.set_cursor_style(cursor_style)?;
        self.show_cursor()?;
        self.set_cursor_position(position)?;
    }
}
```

也就是：

```text
绘制帧 -> flush -> 设置样式 -> Show -> MoveTo
```

这个顺序允许光标在 `Show` 与 `MoveTo` 之间出现在前一个位置或当前绘制位置。

## 3. flush 边界真实存在，不只是源码书写顺序

Codex 在 `tui.rs` 中通过 `stdout().sync_update(...)` 包裹 `terminal.draw(...)`。其固定 ratatui fork 中：

```rust
fn show_cursor(&mut self) {
    execute!(self.writer, Show)
}

fn set_cursor_position(...) {
    execute!(self.writer, MoveTo(x, y))
}
```

`execute!` 会 flush，因此 `Show` 与后续 `MoveTo` 不只是同一内存缓冲区中的相邻字节，而是两个实际 flush 边界。synchronized update 只能要求终端原子呈现收到的序列，不能保证 Windows ConPTY 不在中间转换或延迟光标状态。

## 4. Windows ConPTY 的转换与探针吻合

Codex 发出最终光标移动后，系统 ConPTY 对外表现为延迟到达的：

```text
Hide -> MoveTo -> Show
```

这正是旧探针第二包的字节形态。由此可见，第二个位置不是 Iris/xterm 自行生成，而是 ConPTY 对应用侧光标状态更新的 VT 重编码结果。

# Iris 修复前链路

当前实现与依赖：

```text
Codex 0.146.0
  -> Windows ConPTY（useConpty: true）
  -> node-pty 1.1.0
  -> SessionManager 固定 8 ms 合批
  -> @xterm/xterm 6.1.0-beta.256
  -> @xterm/addon-webgl 0.20.0-beta.255
```

Iris 的 `node-pty` 预构建包中已经包含 `conpty.dll` 和 `OpenConsole.exe`，但修复前创建 PTY 时只显式设置了 `useConpty: true`，没有显式设置 `useConptyDll: true`。

# 已排除或显著降级的方向

## xterm 光标闪烁设置

Iris 没有显式启用 `cursorBlink: true`，而 xterm 默认不闪烁。观察到的现象也对应两个位置之间的状态变化，不是常规定时光标 blink。

## WebGL 光标使用独立画布

源码核对表明，当前 xterm WebGL renderer 的正文与光标在同一个 WebGL canvas/渲染帧中提交。旧调查中“独立 2D cursor canvas 产生异步错位”的推测不成立。

## Iris 与 VS Code 使用完全相同的 xterm

旧调查的这个前提不准确。相关时期的 VS Code 约使用 xterm `beta.197` 到 `beta.213`，Iris 当前为 `beta.256`。不过进一步比对发现 `.213 -> .256` 的 `RenderDebouncer` 完全相同，相关 WebGL 差异主要是资源清理和纹理图集修复，没有发现能解释本问题的光标提交时序变化。因此版本不同是真实差异，但目前不像根因。

## node-pty 1.1 与 VS Code 的 1.2 beta

VS Code 当时约使用 `node-pty 1.2.0-beta.12/13`，Iris 使用 `1.1.0`。两版持续输出读取的 JavaScript 路径基本相同，主要改动集中在启动握手。

受控双写实验中，两版都会把相隔约 15 ms 的两次子进程写入作为独立 `onData` 交付，行为近乎相同。node-pty 版本本身因此基本排除；ConPTY 后端选择仍需单独验证。

## 5 ms 与 8 ms 合批差异

VS Code 的 `TerminalDataBufferer` 做固定 5 ms 拼接，没有发现 Codex 特判；Iris 对 PTY 数据做固定 8 ms 合批。较长窗口可能改变闪动的可见概率，但无法解释“第一包已显示错误位置、第二包稍后才纠正”的源头，也不能单独解释 VS Code 稳定不闪。

# 对旧调查结论的修正

以下说法不应再作为前提：

- “Iris 与 VS Code 使用同一个 xterm 版本”：实际版本不同。
- “WebGL 正文和光标由两张独立画布异步提交”：当前源码不支持。
- “synchronized update 意味着整条 PTY 链路一定只交付一个原子包”：它约束终端呈现语义，但 Codex 自身有多个 flush，ConPTY 也会转换并延迟光标状态。
- “第二个光标位置由 Iris 产生”：原始 PTY 字节已经包含该状态变化。

# VS Code 对照

## 本轮调查：实际开关已经确认

本机已安装的 VS Code ptyHost 源码（`3c631b164c` / `0958016b2a`）中，Windows
PTY 选项明确构造成：

```text
useConpty:      process.platform === 'win32' && build >= 18309
useConptyDll:   windowsUseConptyDll
```

其配置 schema 的默认值仍是 `false`，但本机
`%APPDATA%\\Code\\User\\globalStorage\\state.vscdb` 的实验服务记录了：

```text
config.terminal.integrated.windowsUseConptyDll = true
assignmentContext ... conptydll_true:31498968 ...
```

因此当前 VS Code 实例实际使用的是它随包携带的 ConPTY DLL，而不是 Windows
系统内置的 ConPTY。该 DLL 的文件版本为 `1.25.2603.03002-preview`。

Iris 当前 `node-pty 1.1.0` 随包携带的 DLL 为 `1.23.2510.08001`，但
`SessionManager.createSession()` 只传 `useConpty: true`，没有传
`useConptyDll`，因此 node-pty 按默认值 `false` 走系统 ConPTY（该默认值在
`node-pty/typings/node-pty.d.ts` 中有明确说明）。

## 同机字节级 A/B

使用本项目的 `node-pty 1.1.0`，同一 `node.exe` 子进程、同一 `80x24` 尺寸和
同一组两次相隔约 12ms 的写入进行对照：

```text
写入 1: ESC[?2026h ... ESC[?25h
写入 2: ESC[32;3H ESC[?2026l
```

- `useConptyDll: false`：系统 ConPTY 把第一帧重编码成已经结束
  synchronized update 的屏幕重绘；约 12ms 后再发出隐藏/移动/显示光标的
  修正包。xterm 会先有一次可见的中间光标位置，再显示最终位置。
- `useConptyDll: true`：两次 `onData` 保留原始边界，第二包才包含
  `MoveTo + synchronized-output 结束`。xterm 的 2026 同步输出在此期间保持
  渲染冻结，不会显示第一包的中间位置。

这与 Codex 的 `Show -> MoveTo` 帧尾顺序以及现场约 12ms 的第二包完全吻合。
它也解释了为什么 Windows Terminal 没有该现象：它是最终终端渲染器，不会把
Codex 的 VT 输出再经过一次系统 ConPTY 重编码。

# 修复与验收

`SessionManager.createSession()` 的 PTY spawn 选项现已加入：

```ts
useConptyDll: process.platform === 'win32'
```

`PtySpawnFn` 的本地 options 类型也同步声明了 `useConptyDll?: boolean`。Windows 因而使用 `node-pty` bundled ConPTY DLL；其他平台保持原路径。用户已在原问题场景中复测，确认 Codex 输入区光标闪动消失。

# 最终判断

根因链已经闭合：**Codex 帧尾的 `Show -> MoveTo` 顺序本身提供了一个短暂
中间态；Iris 使用系统 ConPTY 时，该中间态被重编码为先结束 synchronized
update、再延迟发送最终光标移动的两包输出，xterm 因而可见地渲染两次。当前
VS Code 实例通过实验开关使用 bundled ConPTY DLL，保留原始同步边界，所以
没有闪动；Windows Terminal 不经过该 ConPTY 中间层。**

最终修复是在 Iris 的 Windows node-pty spawn 选项中启用
`useConptyDll: true`。该方案已经复测通过，不需要在 xterm 侧吞掉特定光标
序列。若未来遇到旧 Windows 或 bundled DLL 加载失败，再基于真实兼容性故障
设计显式回退。
