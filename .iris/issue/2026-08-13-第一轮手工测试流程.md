## Issue 定义

本 Issue 定义 Iris Agent 第二阶段之后的第一轮手工测试流程。目标不是扩大功能范围，而是在当前自动化骨架基础上，用真实产品入口验证最小可用链路、记录证据，并把不能通过的环节转化为后续修复 Issue。

本轮测试只证明“入口、Session、真实 provider、短任务工具链和消息 Rewind 的第一轮可观察性”。它不代表 Iris Agent 可自举，也不代表关键里程碑二完成。

## 测试边界

本轮覆盖：

* 右栏空状态入口和 `iris-agent` Session 选择。

* 固定 Issue/document anchor 与发送前最新内容读取。

* Pi TUI 登录结果复用和一次真实 provider 流式对话。

* main-owned `read`、`edit`、`write`、`terminal` 副作用链路。

* 非交互短命令、交互命令拒绝、provider/tool 错误展示。

* 消息-only Rewind 的确认文案和实际行为。

* 普通 PTY 与外部 Agent CLI 的基本回归。

本轮不覆盖：

* 多 provider 全矩阵。

* 长命令 Terminal 标签、20 秒监督、用户 PTY 输入。

* Fork、文件 Rewind、Context Inspector。

* 安装包发布验收。

* 自举开发准入确认。

### 2026-08-13：隔离确认 - Git watcher 导致项目打开后无响应

用户确认：在当前 Agent 支线保持其他代码不变、仅临时禁用 Git watcher 后，同一项目可以正常打开并保持响应。

隔离结果：

* 启用 watcher：Electron 主进程约 19,626 个 handles，窗口无响应。

* 禁用 watcher：Electron 主进程约 1,389 个 handles，窗口响应正常。

* 项目目录约 6,456 个，其中 `node_modules` 约 5,244 个；Git tracked 文件实际只涉及约 179 个目录。

* `GitManager` 把整个 worktree 交给 Chokidar。当前 `ignored` 回调只过滤 `.git` 内部噪声，不读取 `.gitignore`，因此 `node_modules`、构建输出和其他未跟踪目录也会被递归遍历并建立目录级 `fs.watch`。

* 当前开发版使用 Electron 43.4.0 / Node 24.18.1；正常的 beta.7 打包版使用 Electron 31.7.7 / Node 20.18.0。两边 Chokidar 都是 5.0.0，因此不是 Chokidar 包版本变化，而是原有的无界 worktree 监听设计在新版运行时和开发工作区中暴露为严重退化。

* 开发环境还会持续改写 `out` 等项目内文件，进一步制造 watcher 事件；日志已出现 `EPERM: operation not permitted, watch`。

根因结论：

Git 自动刷新错误地以“递归监听整个 worktree”近似 Git 变更来源。Chokidar 在 Windows 上为递归发现的目录建立 `fs.watch`，而当前过滤规则不等同于 Git ignore 规则，导致依赖树也进入监听。大量 Windows watcher handles 和事件处理压在 Electron main 进程上，最终阻塞窗口消息循环。Electron 43/Node 24 是触发或放大条件，不是单独根因；缺少有界监听范围才是设计缺陷。

* `src/main/git-manager.ts` 中 `GIT_WATCHER_ENABLED = false`；Git status、stage、unstage、commit 和 branch 命令仍可用，但外部文件变化不再自动刷新 Source Control。

* `npm run typecheck`、`npm run build` 通过；关闭 watcher 后 4 个不依赖 watcher 的 GitManager 集成测试通过。

### 2026-08-15：修复记录 - 首轮请求早于 Worker ready

范围：

本次只处理用例 B 的第一个明确失败 `Iris Agent Worker has not been initialized`；“模型最终回复出现在工具调用条目之前”仍作为独立问题保留，不在本次改动中混修。

根因：

`AgentWorkerHost.ensureStarted()` 在向 Worker 投递 `initialize` 后立即完成，随后 `post()` 立刻投递首个 `run`。Worker 的消息监听使用异步处理，`initialize` 尚在等待 Pi Session 创建时，`run` 已开始读取 `runtime`，因此命中未初始化错误。协议虽然已有 `ready` 事件，但 Host 原先没有把它作为业务消息的启动屏障。

修复：

* Host 现在并行读取持久历史和运行参数，创建 Worker 后等待该 Worker 的 `ready` 事件，再允许首个 `run` 或其他业务消息通过。

* 初始化期间的并发发送共享同一个启动 Promise，不会因 Worker 对象已经存在而绕过 ready 屏障。

* 初始化若返回 failure、触发 error 或在 ready 前退出，Host 会拒绝发送并清理半初始化 Worker，使后续重试重新创建实例。

验证：

* `npm test -- --run src/main/agent/worker-host.test.ts`：通过，1 个测试文件、3 项测试；新增覆盖确认首个 `run` 在 `ready` 前不会被投递。

* `npm test -- --run`：通过，74 个测试文件、386 项测试。

* `npm run typecheck`：通过，包含 node、preload、web TypeScript 检查和异步边界检查。

### 2026-08-15：修复记录 - 最终回答早于工具事件

现象：

一次包含多次 `read`、`terminal`、`edit`、`write` 调用的真实 turn 完成后，Iris Agent 的整段最终回答显示在所有紧凑工具事件之前。用户先看到结论，再看到产生结论的工具事实，违反默认历史“用户消息 -> 必要工具事件 -> Agent 最终回答”的产品顺序。

根因：
