## 结论

问题成立，并且在满足条件时是确定性的状态覆盖，不是仅依赖 watcher 或磁盘
时序的推测。

修改语言的窗口在打开设置页前会执行 `flushBeforeSwitch`，所以通常不会丢失
自己的草稿。风险发生在其他窗口：全局设置广播会改变这些窗口的 i18n
language，进而重建仍在使用的 Crepe 编辑器。

## 触发条件

同时满足以下条件时可以触发：

1. 至少打开两个 Iris 窗口，项目是否相同不影响触发。
2. 窗口 A 在设置页切换到不同的实际显示语言。
3. 窗口 B 正在使用 WYSIWYG 模式编辑文档正文。
4. 窗口 B 存在尚未成功写入磁盘的正文草稿。

默认自动保存延迟为 1.5 秒，但持续输入会不断重新开始计时，因此风险窗口不只
是一次固定的 1.5 秒间隔。关闭自动保存、保存失败或存在外部冲突时，风险窗口
会持续更久。source 模式不挂载 Crepe，不受这条链路影响；已经成功保存的正文也
不会丢失。

## 状态覆盖链

1. `SettingsManager` 将语言设置变化广播给所有窗口。
2. 其他窗口执行 `changeLanguage`，`useTranslation` 更新
   `i18n.resolvedLanguage`。
3. `CrepeEditor` 的 effect 把 `i18n.resolvedLanguage` 作为依赖，因此销毁并
   重建 Crepe。
4. 新 Crepe 的 `defaultValue` 来自 `session.originalBody`，即最近一次磁盘
   baseline 的正文，不是当前 `bodyCurrent` 草稿。
5. 这次重建没有增加 editor generation，也没有重新进入独立的 hydration
   状态。新 Crepe 的更新回调可以把旧正文写回 editor store。
6. `finishBodyHydration` 随后把旧正文同时写入 `bodyBaseline` 和
   `bodyCurrent`，dirty 状态和未保存正文一起消失。

## 推荐方案

当前合适的修复是让语言变化不再重建 Crepe：从生命周期 effect 的依赖中移除
`i18n.resolvedLanguage`。

React 渲染的上下文菜单等文字仍会随语言立即更新。Crepe 初始化配置中的少量
固定文案可以在切换文档、切换编辑模式或其他自然 remount 后更新。相比为了这些
文案即时变化而重建一个持有草稿的编辑器，这是更合理的数据安全取舍。

不建议仅把 `defaultValue` 改为 `bodyCurrent`。当前 hydration 会把传入正文同时
设为 baseline/current，这样虽然画面可能保留草稿，dirty 状态仍会被清除，并且
后续保存可能把草稿判断成无需写入。

如果未来要求 Crepe 内部固定文案也必须即时切换，应单独实现 presentation
remount 协议：以当前 composed draft 初始化、增加 generation、屏蔽旧实例回调，
并在 hydration 完成时保留原持久化 baseline、draft revision 和 dirty 语义。

* [ ] 增加回归测试：dirty WYSIWYG 会话经历语言变化后，正文、revision 和
  dirty 状态保持不变。

* [ ] 执行双窗口验证：窗口 A 切换语言时，窗口 B 持续输入且不发生正文回退。

* [ ] 验证上下文菜单立即翻译，Crepe 内部固定文案在自然 remount 后使用新语言。
