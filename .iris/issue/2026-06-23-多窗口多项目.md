## 背景

再次启动 Iris 时第二个窗口会叠在已有窗口上、不稳定、偶发崩溃，崩溃后 node-pty/ConPTY 的 agent CLI 子进程不退出，要任务管理器全杀才恢复。根因是 `src/main/index.ts` 单实例锁失败后**没有 guard**，`app.quit()` 异步，第二个进程继续 bootstrap、抢同一份 Chromium userData 缓存锁。

产品决策（产品负责人拍板）：v1 功能已收口，把 VS Code 式多窗口/多项目提前作为 v1.1 开篇，边用边改。这与定义书 §「v1 不做多项目管理」冲突，已在 `software-definition.md` 同步范围。

## 架构

每窗口一套 `ProjectManager` + `SessionManager`；`SettingsManager` 全局共享（机器级）。IPC 按 `event.sender` 路由到该窗口的 manager（`src/main/window-context.ts` 注册表 + `requireContext`）。渲染层 store 是模块级单例、每窗口独立 JS 上下文，天然隔离。审计确认 `style-maps-store`/`agent-injection`/`software-prompt`/`perf-runtime` 无隐藏单项目状态，下游零改。

## 已实现（typecheck + build + smoke + 65 单测全过）

* 单实例锁失败 → `app.exit(0)` 同步终止，杜绝穿透；主进程加 `uncaughtException`/`unhandledRejection`/`child-process-gone` 兜底，崩溃前杀全部 PTY。

* `window-context.ts`：per-window 上下文注册表（create/dispose/lookup/all/persist）。

* `ipc.ts`：`registerIpcHandlers(settingsManager)` 单参，project/session/doc/styles/software-prompt/shell handler 按窗口路由。

* 新频道 `window:bootstrap`（渲染层问本窗口绑哪个项目）、`window:open-project`（在新窗口打开）。

* `second-instance` 改为开新窗口（解析 argv 路径）；左栏新增「在新窗口打开项目」按钮。

* per-window flush 握手、confirmOnQuit 用本窗会话、before-quit 遍历所有窗口、dialog 改窗口 modal。

* 启动恢复：`settings.project.openRoots`，退出时快照、启动每个 root 开一窗；`lastRoot` 保留向后兼容。

* `render-process-gone` 崩溃时 destroy 该窗口、回收其 PTY。

## 评审中发现并修复：portable 双开崩溃（ESM `package.json` ENOENT）

复现：打包 portable 单窗口终端完全正常；**第二次双击 exe** 弹「主进程 Uncaught
Exception」，报 `ENOENT … open '…\Temp\<随机>\…\package.json'`（栈为纯 Node ESM
解析器 `packageResolve`），之后两窗口终端都开不出。

根因（非「锁穿透」，是更前一步）：portable 每次启动把 app 解压到全新的
`%TEMP%\<随机>`，进程退出时该目录被 portable 壳清理。原 `index.ts` 在顶部就静态
`import` 了被 externalize 的原生后端（`node-pty`/`@xterm`/`chokidar`/`gray-matter`），
ESM 规范要求这些导入在模块体执行前全部求值——**早于**单实例锁检查。抢锁失败的第二
实例于是先把整套后端从临时目录解析一遍（读各包 `package.json`），才走到
`app.exit(0)`；退出时 portable 壳删临时目录，与在途的 `package.json` 读竞争 →
ENOENT → 未捕获 → 崩溃框。崩在「向主进程转发开窗请求」的半路上，于是新窗口没能干净
开出，看着像「多开坏了」。`app.exit(0)` 本身没问题，问题是它排在重型 import 之后。

> 排除：曾疑 node-pty conout Worker 的 asar 路径 bug——单窗口终端正常已证伪，未动
> `node_modules`。

修复（架构方向：产品确认走 VS Code 式「一个主进程 + 多窗口」，非完全隔离，避免重新
引入 userData 缓存锁互抢）：把 main 入口拆成**瘦壳 + 懒加载实现**。

* `src/main/index.ts` 只 `import electron`，先做单实例锁：输家
  `app.exit(0)`（此时只加载了 electron，无任何后端 `package.json` 待解析，杜绝临时
  目录竞争）；赢家 `void import('./app-main.js')` 才加载后端。`requestSingleInstanceLock`
  仍由输家调用——触发赢家 `second-instance` 开新窗的机制不变，多开架构原样保留。

* 新增 `src/main/app-main.ts`：原 `index.ts` 除单实例守卫外的全部实现，外加加固的
  `parseProjectRootFromArgv`（解析出的目录若在 `PORTABLE_EXECUTABLE_DIR` 或系统临时
  目录下则跳过、回退 `lastRoot`，防新窗误绑到会被删的临时路径）。

* `electron.vite.config.ts`：main 加第二 input `app-main`，使其落在
  `out/main/app-main.js`（而非 `chunks/` 子目录），`__dirname` 仍是 `out/main`，
  `../preload`/`../renderer` 相对路径才正确（构建首跑因落在 `chunks/` 偏一级、
  smoke 报 preload/renderer 找不到，已据此修正）。

验证：`build` 后 `out/main/index.js` 仅 0.24kB、只 import electron、无任何 node-pty/
@xterm/chokidar 静态导入；smoke 过；65 单测过；portable exe 重新打包+签名成功，asar 内
`out/main/index.js`、`out/main/app-main.js` 层级正确。

## 仍复现：同时开两个打包 exe → 窗口1 终端起不来 + devtools 被搞坏（诊断中）

用户实测（2026-06-25）：上面的瘦壳修复后**仍不行**。场景是**同时启动两个打包
exe**（非「在新窗口打开」按钮）。一旦开第二个 exe，第一个窗口的终端就起不来，且第一
个窗口的 devtools 也被搞坏。

关键复盘：第二个 exe 是**独立进程**，抢锁失败后 `app.exit(0)`，但它先触发第一个进程
的 `second-instance` → 在同一主进程里开窗口2（VS Code 式）。两个 exe 共享同一份
`%APPDATA%\iris-app` 的 userData / GPUCache。两个并行嫌疑：

* **A.** **`createWindow`** **抛错 → uncaughtException →** **`process.exit(1)`** **拖垮整进程。**
  `process.on('uncaughtException')` 的兜底是 `process.exit(1)`；而 `second-instance` →
  `createWindow`（开窗口2 入口）**原先没有 try/catch**。开窗口2 半路抛错就会冒泡到
  uncaughtException，把整个 app 连同窗口1 一起带走——正好解释「开窗口2 把窗口1 搞坏」。

* **B. 共享 GPUCache / GPU 进程被扰动 → 窗口1 WebGL 上下文丢失。** xterm 用
  `WebglAddon`（GPU），devtools 渲染也吃 GPU；exe#2 启动碰 `%APPDATA%\iris-app\GPUCache`
  使第一个进程的 GPU 进程崩溃/重启 → 窗口1 所有终端 + devtools 同时失效。终端与 devtools
  **同时**坏，强烈指向共享 GPU 这条线。

**根因未坐实——之前全在猜，因为打包版没有任何文件日志**（`logger.ts` 原来只写
console，packed build 看不到）。本轮先补观测、再堵已知漏洞：

* `src/main/logger.ts`：console 之外新增**文件落盘** `~/.iris/logs/main-debug.log`（dev
  为 `~/.iris-dev/logs/`），每行带 ISO 时间戳 + **PID**。两个 exe 进程写同一文件、PID 不
  同——这正是看清两进程交错（谁抢锁、winner 何时开窗口2、那一刻有没有 GPU/渲染/子进程死）
  的依据。依赖只 electron + Node 内建，瘦壳 `index.js`（645B）未回归 node-pty/@xterm。

* `src/main/index.ts`：抢锁输赢两路都打 `boot` 日志（pid + argv + 锁结果）。

* `src/main/app-main.ts`：`second-instance` 整体 **try/catch 兜住**（堵假设 A——出错只记
  日志、保住窗口1），并打 argv→root；`createWindow` 加 start/done 日志（含 win id、现有窗
  口数）；app-main 模块加载打 build/userData。`render-process-gone`/`child-process-gone`/
  `uncaughtException` 探针原已存在，现在都落盘可见。

验证：typecheck + build + smoke（日志链路实测打出 `won lock → app-main loaded →
createWindow start/done`）+ 65 单测全过；`out/main/index.js` 仍只 import electron + Node
内建。

**下一步（待用户复现取证）**：用本轮新打的 portable exe，清空/记录
`~/.iris/logs/main-debug.log` → 双击起窗口1 → 再双击触发故障 → 回传整份日志。按 PID 交错
与探针定位是 A 还是 B：A 已基本堵住（若日志显示 `second-instance handler failed` 即坐
实并已不再拖垮窗口1）；若是 B（`child-process-gone: type=GPU` / `render-process-gone`），
下一步把 GPUCache 隔离/禁用或加 GPU 崩溃恢复。

## 取证坐实：A 证伪、B 修正为「GPU 合成层」（fix=关硬件加速，0.0.2-alpha.4 待验）

用户回传 `~/.iris/logs/main-debug.log`（2026-06-25，pid 交错清晰）。第二个 exe 起来
那一刻的链路：`[loser] boot starting` → `[winner] second-instance → root` →
`[winner] createWindow start existingWindows=1` → `[winner] createWindow done id=2` →
`[loser] lost lock — forwarded argv, exiting` → `[winner] project opened`。**整份日志
零异常**：没有 `second-instance handler failed`、没有 `render-process-gone`、没有
`child-process-gone: type=GPU`、没有 `uncaughtException`。

据此定论：

* **假设 A 证伪**。`second-instance` 的 try/catch 没触发，主进程一路健康、窗口2 干净
  开出。不是「开窗口2 抛错拖垮整进程」。

* **第二个 exe 无辜**。它抢锁失败后只 import 了 electron 就 `app.exit(0)`，**没走到
  `whenReady`、根本没起 Chromium/GPU 子进程**。所以「两个进程抢同一份
  `%APPDATA%\iris-app\GPUCache` 磁盘锁」也排除——全程只有一个 Chromium 进程。

剩下唯一活着的解释是**假设 B 的精确版**：单个 Chromium 进程内，窗口2 一开，窗口1 的
终端 + devtools 同时坏、且无任何崩溃日志——GPU 资源层被搅动，不是进程崩溃（所以
`child-process-gone` 不打）。

**关键证伪 WebGL-上下文理论**：用户实测说明 `advanced.terminalRenderer` 早已是
`dom`——终端**根本不创建 WebGL 上下文**；且**devtools 在第二个进程一开就当场花屏，
早于任何终端起来**。两点合起来排除「WebGL 上下文翻动（超 16 上限丢最老）」，把根因压到
**整个 GPU 合成层**：仅仅 `new BrowserWindow()` 创建窗口2 这个动作，就让窗口1 的
detached devtools 当场花屏——典型的**多 HWND 表面 +** **`frame:false`** **+ detached devtools
的 GPU 驱动/合成 bug**。`dom` 渲染器只去掉终端 WebGL，UI 与 devtools 仍吃 GPU 合成，
故无效。

修复（`src/main/app-main.ts`，模块顶部、`whenReady` 前）：
`app.disableHardwareAcceleration()`——整个 app 落到软件合成，同时干掉终端 WebGL 与
UI/devtools 的 GPU 合成，把「共享 GPU 被搅动」整类故障连根拔。终端是最不吃 GPU 的界面，
软件合成代价基本无感；一行、可逆。这步本身即决定性实验：装上若好 → GPU 合成坐实；若仍
坏 → 整个 GPU 类排除，转查渲染进程共享等方向。

版本号 `0.0.2-alpha.3 → 0.0.2-alpha.4`（不提号打包有壳缓存 bug）。typecheck + build 过；
portable exe **未在本轮打包**（用户自行出包验证）。

**待用户验**：出 alpha.4 portable → 清 `~/.iris/logs/main-debug.log` → 双击起窗口1
（开着 devtools）→ 再双击 → 看窗口1 devtools 是否还花、终端是否还起不来。

## alpha.4 回归坐实 + 推翻 GPU 结论 + 真相（alpha.5 已解决）

用户实测 alpha.4 portable：**窗口完全打不开，后台有进程、窗口弹不出来**。这是
`disableHardwareAcceleration` 修复自身引入的**回归**，而循因这条回归，反手把整个 GPU
结论也推翻了。

### 回归根因：`disableHardwareAcceleration()` 在懒加载模块里「太晚」执行

Electron 规定 `app.disableHardwareAcceleration()` **必须在 app ready 之前调用，否则
抛错**（`can only be called before app is ready`）。alpha.3 的瘦壳重构把它放进了**懒加载
的** **`app-main.ts`**——该模块静态 import 了原生后端（node-pty/@xterm/chokidar）。三种构建
的 app-main 加载速度不同：

* **dev / unpacked(=installed)**：从正常磁盘加载，快 → 第 53 行 `disableHardwareAcceleration()`
  赶在 app ready **之前**跑完 → 生效，窗口正常。

* **portable**：每次解压到临时目录再走 asar，app-main 加载**最慢**，与 `app.whenReady()`
  形成竞态 → 调用落在 ready **之后** → **抛错**。

抛错发生在 `app-main.ts` 模块求值途中（第 53 行），**早于** `app.whenReady().then(...)`
注册（第 347 行）、更早于 `unhandledRejection` 处理器注册（第 433 行）。后果三连：
①`whenReady().then` 那段根本没注册 → 永不建窗；②`void import('./app-main.js')` 的 promise
rejection 无人捕获也无人记录（handler 还没装）→ **日志里连报错都没有**；③app 因「从没建过
窗口 → `window-all-closed` 从没触发」而一直活着 → 正是「后台有进程、窗口弹不出来」。日志
零 06-25 记录，与此完全吻合。这也解释了为何 alpha.3 portable 没事：alpha.3 在 app-main 里
只有 `appendSwitch('disable-gpu-shader-disk-cache')`——`appendSwitch` 晚于 ready 只是**静默
失效、不抛错**；alpha.4 新加的 `disableHardwareAcceleration()` 晚于 ready 是**抛错**。

### 关键反证：原始多窗口崩坏 bug 本身就「仅 portable」

用户澄清（2026-06-25）：**`npm run dev`** **和 unpacked 开好几个 Iris 窗口都没事，且 HW 加速
开着**。这把上一节「多 HWND 表面 + `frame:false` + detached devtools 的 GPU 合成 bug」结论
**直接证伪**：installed 与 portable 是**同一份代码、同一份 asar、同一个** **`frame:false`、
同一套多窗口逻辑、同一块 GPU、同一个驱动、同一个系统**——若真是多窗口合成 bug，installed
必然一模一样复现。它没有。

**故根因绝不在「窗口代码 / 多窗口合成」**（那部分 portable 与 installed 逐字节相同），只能
在 **portable 与 installed 之间的环境/配置 delta**。前几轮一直把它当 GPU API 层的代码 bug、
不停往上叠 GPU 缓解（`dom` 渲染器 → `disableHardwareAcceleration`），方向从一开始就偏了。
portable 与 installed 的差异只有三处：① 跑在每次随机的 `%TEMP%\<random>\`；② portable 壳
注入 `PORTABLE_EXECUTABLE_DIR`、退出删临时目录；③ **`disable-gpu-shader-disk-cache`** **这个
命令行开关 portable 独有**（`app-main.ts`，`getBuildType()==='portable'` 才加，2026-06-13
为另一个「GPUCache 创建失败」问题、同样靠消去法加进去的未证实旧改动）。第 ③ 条是 portable
与 installed 之间**唯一的 GPU 配置差异**——头号嫌疑。

### 修复（alpha.5）：把 portable 的 GPU 配置对齐到 installed（决定性实验）

`src/main/app-main.ts` 同时**撤掉两处 GPU 干预**，使 portable 与已知良好的 installed 在 GPU
层逐字节一致：

* 撤 `app.disableHardwareAcceleration()`（alpha.4，作用于所有构建；建立在被证伪理论上的
  workaround，且自带上述「窗口打不开」回归）；

* 撤 portable 独有的 `disable-gpu-shader-disk-cache` 开关。

二选一判据：portable 多窗口若恢复正常 → 根因就是这两个开关之一；若仍坏 → 根因是 portable
临时目录执行那条线（GPU 驱动按 exe 路径分配 profile），与代码开关无关。

### 结论：根因坐实为 portable 独有 GPU 开关，多窗口代码与 `disableHardwareAcceleration` 均无辜

用户实测 **alpha.5 portable 已解决**（多窗口不再花屏、终端正常）。据此定论：

* 原始多窗口崩坏的**真实根因**是那两处 portable-only GPU 干预（极可能是
  `disable-gpu-shader-disk-cache` 与多表面合成的交互），**不在多窗口/`frame:false`** **代码**。

* `disableHardwareAcceleration` 是站在错误层级的 workaround——既非必要，又因放进慢加载的
  app-main 而制造了 alpha.4 的窗口回归。已彻底移除。

* 「仅 portable」这条事实是破案关键：同代码的 installed 健康，证明问题在构建环境而非窗口逻辑。

版本 `0.0.2-alpha.4 → 0.0.2-alpha.5`（不提号打包有壳缓存 bug）。typecheck + build 过；
portable exe 本轮已打包+签名：`dist/release/0.0.2-alpha.5/Iris-0.0.2-alpha.5-portable.exe`
（73.7 MB，exit 0）。`out/main/index.js` 仍 645B 瘦壳、`app-main.js` 两个 GPU 开关已清零。

**遗留/下一步**：

* 对照实验 B（坐实是哪一个开关）：给 installed/unpacked **单独加回** `disable-gpu-shader-disk-cache`
  看是否复现——若复现即坐实就是它。（非阻塞，bug 已解，可择机做。）

* 2026-06-13 的「Unable to create cache」GPUCache 问题现已无该开关兜底，需复核 portable 是否
  复发；若复发，改用**非 GPU-config** 的解法（如把 GPUCache/userData 指到稳定非临时路径），
  不再重新引入会触发本 bug 的 GPU 开关。

## 善后清理（alpha.5 后，2026-06-25）

bug 解决后审计排障期间留下的脚手架，确认运行时已无有害 workaround，并清掉诊断残留：

  `disable-gpu-shader-disk-cache` 只剩注释与本 issue 文档，无任何执行调用；且**没有**被

  抢锁输赢/`second-instance` 路由等**每进程一次**的低频 boot 日志保留——正是它们当初坐实了真相。
