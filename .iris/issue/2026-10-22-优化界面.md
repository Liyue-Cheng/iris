## 调研报告（2026-10-24）

> **更正：** 这一版偏到了业务逻辑上，方向不对。用户的意思是只看三栏的视觉效果，见下方「视觉调研（第二版）」。本版留作记录，其中的待决事项已作废。

> 本节只有调研和理解，没有改代码。资料来源见文末。说明：assets 里的三张 jpg 是同一张截图（小红书转载）。官方页面上的截图我没法直接拿到（抓取工具只返回文字，官方配图也没有 alt 文本），所以下面的画面拆解基于你附的这张图，功能语义来自官方文档。

### 1. 截图里到底是什么

这张图**不是** 4 月那次「并行会话」改版，而是 **Claude Code Projects（Beta，2026-09-17 发布）**，位于桌面版 Code 标签页里。判断依据如下：

- 左栏有 `Projects Beta` 入口。
- 中栏顶部有 `Overview` 按钮。
- 右栏面包屑是 `Threads > Claim 邮箱 onboarding 设计稿`。
- 右栏底部有线程分支 `claude/project-thread-e56jy1`，输入框占位文字是 `Steer this thread...`。
- 中栏用 `Opus 5.5 · Medium`，右栏用 `Fable 5.1 · High`。官方文档里协调者模型和线程模型正是分开设置的。

Claude Code 桌面版今年有两次界面变化，需要分开看：

| 时间 | 变化 | 核心 |
|---|---|---|
| 2026-04-14 | Claude Code 桌面版重做 | 左栏是所有会话的列表，可按项目、状态、环境分组过滤。面板（聊天、终端、文件、diff、浏览器、计划、任务）可以拖拽排布成网格。另有侧聊（Ctrl+;）和视图模式（Normal / Thinking / Verbose）。 |
| 2026-09-17 | Projects（Beta） | 一个项目就是**一条长期对话**。Claude 在其中当协调者，把任务拆成多个 **thread**（每个都是独立会话，通常在云端，各有分支和 PR）。`Overview` 面板按状态汇总所有 thread。 |

### 2. 布局拆解

```
┌────────────┬───────────────────────────────┬───────────────────────────────┐
│ ○○○  ⊞ ←→ │ Mailly ⌂               Overview│ Threads › Claim 邮箱…  ⟲5  ⊘ ✕ │
│ [Home|Code]│                               │                               │
│ + New      │  我：长段需求（浅粉气泡）        │  thread 的完整对话记录         │
│ Projects β │       ── 18 replies           │  · 预览链接                    │
│ Artifacts  │  Claude：好的，这个任务开始做    │  · ⚠ Usage limit reached      │
│ Customize  │  ┌ thread 卡片 ────────────┐   │  · 图片附件（4-live.png …）   │
│ More       │  │ 标题 · PR #46 · linear  │   │  · 完成清单 ✔✔✔✔○            │
│            │  │ 状态一句话              │   │                               │
│ Pinned     │  │ [Review PR][View thread]│   │                               │
│ · Mailly ● │  └─────────────────────────┘   │                               │
│ · Pulse    │  ──── Today ────              │ #46 claude/project-thread-…    │
│ This comp. │ [Ask Claude a question or…]   │ [Steer this thread…]          │
│ 👤 user    │ + ⚙        Opus 5.5 · Medium  │ +            Fable 5.1 · High │
└────────────┴───────────────────────────────┴───────────────────────────────┘
   导航（窄）        主线：协调对话                   详情：选中的 thread
```

要点：

1. **三栏的分工是「导航 / 主线 / 详情」**。
   - 左栏很窄，只做跨项目导航：几个一级入口、Pinned 项目，以及按「This computer」分组的会话。
   - 中栏是项目的主线对话，你和协调者在这里交流。
   - 右栏是**按需打开的详情**：点 thread 卡片或 Overview 里的某一行，右栏就显示那个 thread 的完整记录，也能直接在里面给它发消息。
2. **主线里的「对象卡片」**：协调者每开一个 thread，就在对话里插一张卡片，上面有标题、PR 号、外链、一句话状态和下一步按钮（Review PR / View thread / Fix CI / Merge it）。对话本身就是看板。
3. **Overview 是注意力面板**。它的 Threads 标签按状态分组：`Ready for review / Waiting on you / Working / Landing / Idle / Resolved`。另有 Library（文件与产物）、Pull requests、Scheduled tasks 三个标签。有 thread 在等你时，Overview 按钮上会出现小圆点。
4. **每个面板自成一体**：顶部是面包屑和少量图标，底部是上下文信息（分支、模型、effort）和输入框。界面上几乎没有分隔线，靠留白和圆角卡片区分层级。
5. **视觉**：暖白/米色底，用户气泡是淡粉，强调色很克制。正文列宽有上限（约 700px），窗口大圆角，几乎没有多余的界面装饰。

### 3. 背后的设计思路（官方说法）

- 「Projects have threads that do the work and a coordinator that directs them.」你像给幕僚长布置工作一样说需求，Claude 决定开新 thread 还是交给已有的 thread。
- **上下文只设一次**：项目指令加项目记忆（`MEMORY.md`）。每个新 thread 都从这里起步，用户纠正过一次的规则会被记进记忆。
- **离开再回来**：回来后打开 Overview，就能看到哪些做完了、哪些等你、哪些有 PR 待审。
- 4 月改版的思路是「人自己管理多个并行会话」，9 月 Projects 的思路是「让 Claude 替你管理会话」。

### 4. 和 Iris 对照：概念上惊人地相似

| Claude Projects | Iris 现状 |
|---|---|
| Project（一条长期主线） | 工作区 / 项目根 |
| 协调对话（project conversation） | hub 会话（工作区根会话，`ws:<path>` 锚点） |
| Thread（一件事 + 一个会话 + 一个分支） | issue 文档 + 挂在它上面的会话（`FOCUS_DOC`） |
| Overview › Threads 按状态分组 | 左栏每篇文档旁的状态点（工作中 / 空闲 / 已退出），但**散在树里，没有汇总视图** |
| Library | `.iris/` 下的文档 + `.assets/` |
| 项目指令 + 项目记忆 | `CLAUDE.md` 的 `<iris-project>` 块 + `status/` 文档 |
| thread 结果留在 thread 里 | 会话产出写回 issue（文档是长期记忆，会话是工作记忆） |

我的理解是：**Claude 走到了「以对话为中心」，Iris 是「以文档为中心」，但两边解决的是同一个问题——一个人同时盯多件 agent 在做的事，并且知道哪件在等自己。** 定义书 §5 里「左栏即注意力调度面板，告诉人哪件事在等你」，和 Overview 的定位完全一致。Claude 的答案更直白：把注意力信息**单独做成一个面板**，而不是摊在导航树上。

### 5. 哪些该学，哪些不该照搬

**值得学（主要是布局和视觉，与 Iris 的原则不冲突）：**

1. **注意力面板（最有价值）**：把全项目所有活着的会话按状态汇总成一个视图（工作中 / 等你 / 空闲 / 已退出 / 孤儿），点一行就跳到对应文档和会话。数据现成：状态点用的就是 PTY 活动启发式，不需要解析 agent 输出。
2. **「主线 + 按需详情」的右栏**：右栏顶部用面包屑（如 `会话 › claude · 优化界面`），右上角放一个带圆点的开关按钮（对应 Overview），可以收起，把空间让给中栏。
3. **面板头和面板底的统一约定**：头部放标题、面包屑和少量图标。终端面板底部加一条上下文条，显示 agent、`FOCUS_DOC`、状态和运行时长。现在 Iris 的会话信息全挤在头部下拉里。
4. **卡片化的关联对象**：在 issue 文档的头部（TypedHeader 下方），把挂在这篇文档上的会话显示成小卡片（agent 名、状态、最后活动时间、[打开] [新建]），相当于对话里的 thread 卡片，只是放到了文档上。
5. **视觉减重**：
   - 左栏头部现在一排 8 个左右的图标，可以收进「更多」菜单或分组。
   - 正文限宽，面板间少用分隔线，多用留白。
   - 新增一个接近截图的暖白主题（米色底、淡粉强调）。现有 14 套主题里没有这种风格。Iris 已经是「深色衬底 + 圆角卡片」结构，换皮成本不高。

**不该照搬（与 Iris 定位冲突，或代价过大）：**

1. **协调者派发 thread、对话里渲染卡片和回复数**：这依赖 Claude 自己的结构化对话。Iris 的会话是第三方 CLI 跑在 PTY 里，按原则「不解析 agent 输出」「detach 不 dispatch」「不做会话编排看板」（定义书 §4、§7），这一层不能照抄。我们能做的「卡片」只能来自文件和 PTY 状态，不能来自对话内容。
2. **跨项目左栏（Pinned 项目列表）**：Claude 的左栏是跨项目的，Iris 是一个窗口一个项目。要加就得动窗口模型，需要你拍板。也可以做个折中：只在左栏顶部放「最近项目」切换器。
3. **任意拖拽的面板网格**：成本高、收益低。Iris 的固定三栏已经够用。
4. 云端 thread、PR 自动修复、用量计费等：与 Iris 无关。

### 6. 方案草图（供讨论，未实施）

**A. 只换皮（低风险，1～2 天量级）**
- 新增暖白主题并考虑设为默认浅色。
- 收紧左栏头部图标，统一面板头高度和间距，正文限宽。
- 布局不动。

**B. 布局对齐（推荐作为「做一版看效果」的版本）**

```
┌──────────────┬──────────────────────────────┬──────────────────────────┐
│ 项目 ▾  + 新建│ 优化界面  [In Progress]  ⧉ ◉ │ 关注 ▸ 会话              │
│ ── 关注 (2) ─│                              │ ── 等你 ────────────     │
│ ◐ 优化界面   │  文档正文（限宽，所见即所得） │ ◐ claude · 优化界面 2m   │
│ ◐ 终端bug    │                              │ ── 工作中 ──────────     │
│ ── 工作区 ───│  ┌ 挂在本文档的会话 ───────┐ │ ● codex · 终端bug        │
│ status / …   │  │ ● claude  工作中  [打开]│ │ ── 空闲 ────────────     │
│ issue  / …   │  └─────────────────────────┘ │ ○ hub · 根               │
│ report / …   │                              │——点一行 → 右栏变成终端，  │
│ misc   / …   │                              │  面包屑可返回——           │
└──────────────┴──────────────────────────────┴──────────────────────────┘
   导航+关注            主线：文档                详情：关注面板 / 终端
```

- 左栏：顶部放项目切换和新建。下面一个「关注」小节，只列有活会话的文档，按「等你优先」排序。再往下才是透镜树。
- 中栏：保持文档为主角（这是 Iris 的身份）。头部下方加「本文档会话卡片」。
- 右栏：有两种状态，用面包屑切换。一种是**关注面板**（全项目会话按状态分组），一种是**某个会话的终端**。头部开关按钮带「等你」圆点，可以收起整个右栏。
- hub 视图：中栏放 hub 终端（相当于 Claude 的主线对话），右栏照旧。

**C. 对话为中心（最像截图，但不推荐）**：中栏换成 hub 终端，issue 作为 thread 在右栏打开。这会把「文档中心」改成「终端中心」，而且 hub 终端无法像协调者那样插卡片、汇总回复，形似但神不似。

### 7. 需要你决定的事（已作废）

- 方向选 A、B 还是 C（我建议先做 B，同时带上 A 的视觉）
- 中栏主角是否保持「文档」（B）还是改成「hub 终端」（C）
- 左栏是否需要跨项目的 Pinned / 最近项目（会影响「一窗口一项目」模型）
- 是否新增暖白主题并设为默认浅色主题
- 关注面板的状态口径：是否在现有「工作中 / 空闲 / 已退出」之外，区分出「等你输入」（现在空闲和等输入混在一起，只靠 2s 静默判断）

## 视觉调研（第二版，2026-10-24）：只看三栏的视觉层次

> 范围：只讨论分栏的视觉处理，包括底色、分隔、浮层和圆角，不涉及任何功能或业务逻辑。
>
> 方法：对附图原图（1440×1178，窗口占 x 71–1368）逐像素取色和扫描边界。下文的「px」都是这张图的像素。图是转载缩放过的，换算到 CSS 像素大约要除以 1.5～2，所以只看比例，不要当绝对值。另外 JPEG 压缩会让极淡的线条略有失真。

### 1. 结论：两层，而不是三张卡片

```
 截图（Claude）                                Iris 现状
┌───────────┬──────────────────┬╭─────────╮┐  ┌──────────────── TitleBar ────────────────┐
│ ●●●       │ 标题  Overview   ││ 面包屑   ││  ├──────────────────────────────────────────┤
│           │                  ││          ││  │╭───────╮ ╭──────────────╮ ╭───────────╮│
│  左栏     │     中栏          ││  右栏    ││  ││ 左栏   │ │    中栏       │ │  右栏      ││
│ （底面）  │   （底面）        ││ （浮层） ││  ││ 卡片   │ │    卡片       │ │  卡片      ││
│           │                  ││          ││  │╰───────╯ ╰──────────────╯ ╰───────────╯│
└───────────┴──────────────────┴╰─────────╯┘  └──────────────────────────────────────────┘
      ↑ 1px 极淡竖线             ↑ 右栏四周留边、细边框、淡阴影          ↑ 三张平级圆角卡片
```

- **截图**：左栏和中栏是**同一张「纸」**，只用一根竖线隔开。右栏是**放在这张纸上的一块浮起面板**。视觉上分成「底面层」和「浮层」两个层级，右栏因此被突出。
- **Iris 现状**：外面一圈 `bg-card` 衬底，里面放三张一样的 `rounded-lg bg-background shadow-sm` 卡片，卡片之间是 4px 宽的拖拽条，中间有一根淡线。三栏地位相同，没有主次。见 `src/renderer/components/layout/ThreePane.tsx:159-177` 和 `src/renderer/components/ui/resizable.tsx:31`。

### 2. 逐项测量

| 部位 | 测量结果 | 说明 |
|---|---|---|
| 左栏底色 | `#fbfbf9` | 中性略暖的白 |
| 中栏底色 | `#fcfcfa` | 和左栏只差 1 个色阶，肉眼看是同一种颜色 |
| 左/中分隔 | 1 根 1px 竖线 `#f3f3f1`，只比底色暗约 3% | 从窗口顶端贯穿到底端，没有间隙、圆角或阴影；在 y=150…1080 各处取样，颜色一致 |
| 标题行 | 没有独立的标题栏色带，标题行下方也**没有横向分隔线** | 红绿灯、侧栏按钮、项目名、Overview 按钮直接放在底面上 |
| 右栏外边距 | 上、右、下各约 5px，左侧不留明显间隙 | 卡片顶边在 y≈77（窗口顶在 y=71），底边在 y≈1100（窗口底在 y=1106），右边在 x≈1362（窗口右边在 x=1368） |
| 右栏边框 | 1px，`#e5e6e1`～`#eff0eb`，比底色暗 5～8% | 比左/中那根分隔线明显一档 |
| 右栏阴影 | 边框外侧 2～3px 很淡的过渡（`#f1f2ed` → `#f9faf5`） | 小半径的柔和阴影，不是投影感很强的那种 |
| 右栏填充 | `#fefffa` / `#ffffff` | **比底面更白一点**。浅色模式下「越高越亮」 |
| 右栏圆角 | 约 8～10px | 明显小于窗口外圆角（约 20px） |
| 右栏高度 | 一直顶到窗口顶部 | 右栏占用了标题栏那一行，自己的头部（面包屑 + 图标）就是它的标题行 |
| 右栏头部 | 头部和正文之间**没有分隔线** | 靠留白区分 |
| 中栏内容 | 正文限宽，大约 x 270–790 | 两侧留白很宽 |
| 中栏用户消息 | 淡暖色块 `#f6eeec`，圆角 | 这是层次表达的第三种手段：在底面上用浅色块区分，而不是用卡片 |

### 3. 这种做法为什么显得「有层次」

1. **只有一处被抬起**：三张卡片平均用力，等于没有重点。截图只抬起右栏，层次差别就出来了。
2. **分隔用最轻的手段**：左/中之间只有一根约 3% 对比度的线，标题行下没有线，面板头部下也没有线。线越少，那块浮层的边缘就越显眼。
3. **浮层的三个要素同时出现，而且每个都很弱**：四周留一点边、一根细边框、一层很淡的阴影，再加上「填充略亮」。单看哪一项都不明显，叠在一起就有了清晰的前后关系。
4. **没有衬底**：Iris 现在的 `bg-card` 衬底让所有面板都像嵌在凹槽里。截图里底面本身就是左栏和中栏的背景，没有凹槽。
5. **圆角分级**：窗口约 20px，浮层约 8～10px，内容卡片和按钮更小。圆角随层级递减，显得规整。

### 4. 映射到 Iris 时需要注意的地方（只谈视觉）

- **Windows 标题栏冲突**：截图是 macOS，窗口按钮（红绿灯）在左上角，所以右栏可以一直顶到窗口顶部。Iris 在 Windows 上把最小化、最大化、关闭放在右上角（`TitleBar.tsx:60-119`），右栏顶到顶部会和它们打架。有三种处理：
  - 保留 40px 的标题行，但标题行与底面同色、不加分隔线，右栏浮层从标题行下方开始；
  - 把窗口按钮挪进右栏浮层的头部；
  - 右栏浮层顶部让出窗口按钮那一块。
  
  第一种最稳。
- **单栏情况**：hub 视图（终端全宽）、todos 视图、collection 视图，目前都不是「左 + 中 + 右」的结构。要分别决定谁当浮层。一个自然的规则是：**终端或详情面板永远是浮层，文档、列表和导航永远在底面**。
- **深色主题的层级**：浅色模式下浮层「更白」。深色模式的惯例是浮层「更亮一点」，阴影基本看不见，主要靠边框。14 套主题都需要补一个「浮层底色」token（比如 `--surface-raised`），以及一个比现有 `--border` 稍重的浮层边框。现有的 `--border` 和 `--border-subtle` 两档可以直接对应左/中分隔线。
- **终端背景**：右栏浮层里是 xterm，它的背景色在 `src/renderer/theme/xterm-themes.ts` 里单独维护。浮层底色变了，这里也要同步，否则浮层里会出现一块颜色不一样的终端区域。
- **拖拽条**：左/中之间的拖拽条可以继续用现有的 1px 线（`resizable.tsx` 的 `after:` 伪元素），只把颜色调到更淡。中/右之间不再画线，浮层的边框本身就是边界，拖拽热区放在浮层左边缘附近即可。

### 5. 可以做的视觉改动清单（供选择，未实施）

1. 去掉 `ThreePane` 的 `bg-card` 衬底，以及左、中两栏的卡片外壳，让它们直接铺在 `bg-background` 上。
2. 左/中之间只保留 1px 极淡竖线。
3. 右栏改成浮层：上、右、下留约 6px 边距，左侧 0～2px；1px 浮层边框；很淡的阴影；填充用新的 `--surface-raised`；圆角约 8px。
4. 标题栏与底面同色，去掉下分隔线。右栏浮层从标题栏下方开始（Windows 方案一）。
5. 文档正文继续限宽（现在是 48rem），左右留白保持宽松。
6. 先在一套浅色主题和一套深色主题上做出效果，确认后再铺到其余主题。

## 上游版本兼容性调研（2026-10-24）

用户要求上网研究版本是否能更好配合。本轮只调查和隔离验证，未修改项目 package.json、锁文件、node_modules 或运行代码，也未打包／启动开发服务器。实验依赖与测试均放在系统临时目录 `iris-milkdown-compat-20261024/trial-7.22.3`。

### 结论

**建议把 Milkdown/Crepe 整套从 7.21.2 升到 7.22.3，保留当前 ProseMirror Model 1.25.12。** 首轮可以保留当前 View 1.42.6，减少同时变化的层数；最新 View 1.42.7 也已通过相同的隔离测试，可以作为后续同步更新候选。长期应使用上游已经修复的 schema，移除这次新增的列表和图片兼容层，而不是一直在 Iris 中覆盖上游行为。

需要修正此前调查的完整性：上轮确认了本地根因并提供了应急兼容修复，但尚未查询上游修复发布情况。此次确认，在 10 月 22 日那次更新底层依赖之前，Milkdown 7.22.3 已于 10 月 10 日发布，而且包含这两类修复。因此，当时只更新底层、保持 Milkdown 7.21.2 的选择没有充分利用已有的上游兼容修复。

### 已查到的官方证据

1. **列表类型问题有明确的上游 issue 和修复。** [Issue #2419](https://github.com/Milkdown/milkdown/issues/2419) 描述了 spread 存储为字符串导致校验失败和紧凑列表变宽松的问题；[PR #2423](https://github.com/Milkdown/milkdown/pull/2423) 在解析、DOM 转换、序列化和列表重编号中统一使用布尔值。修复收录于 [7.22.0 发布记录](https://github.com/Milkdown/milkdown/pull/2421)。
2. **图片消失也已被上游修复。** [PR #2478](https://github.com/Milkdown/milkdown/pull/2478) 明确指出 prosemirror-model 1.25.12 的新校验会拒绝 null 图片标题，而 Milkdown 会吞掉错误并丢弃图片。修复同时覆盖行内图片和块图片，已纳入 [7.22.3 发布记录](https://github.com/Milkdown/milkdown/pull/2488)。本轮解包 npm 正式发布包，确认源码实际包含这些修改，未仅依赖 PR 的关闭状态。
3. **Model 的行为改变是有记录的。** npm 发布包内 [prosemirror-model 1.25.12 CHANGELOG](https://unpkg.com/prosemirror-model@1.25.12/CHANGELOG.md) 明确写明，在 NodeType/MarkType.create 中执行属性校验，使不同创建路径都受到检查。根本问题是旧 Milkdown 生成了不符合自己 schema 的值；回退 Model 只能隐藏这个问题。
4. **回退旧 View 会撤回安全修复。** 官方 [GHSA-c8x8-7fp4-3x9w](https://github.com/ProseMirror/prosemirror-view/security/advisories/GHSA-c8x8-7fp4-3x9w) 披露粘贴处理 XSS，影响 `<1.42.3`，修复版本为 `1.42.3`。本项目升级前的 `1.41.9` 落在范围内。这证明升级 View 有实际依据，但不代表当时所有间接依赖更新都分别有安全必要。
5. **View 的依赖约束不支持简单只降 Model。** 当前 View 1.42.6 和最新 1.42.7 均要求 Model `^1.25.12`。只通过 override 把 Model 强制改成 1.25.8／1.25.11，会违反它声明的依赖范围；不作为推荐组合。

查询 npm registry 当时：Milkdown/Crepe 最新稳定版为 7.22.3（10 月 10 日发布），Model 最新为 1.25.12，View 最新为 1.42.7（10 月 22 日发布）。所有 Milkdown 内部包应保持同一版本；ProseMirror 的各包采用独立版本号，不需要把 model、view、state 等改成相同数字。
