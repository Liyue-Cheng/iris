我让agent生成一些东西，然后将其停止，然后让agent继续生成，然后再停止，然后我rewind，结果一次rewind掉了两条消息，这是怎么回事？

而且参见.iris/issue/2026-08-16-Iris-Agent-Stop与上下文恢复.md

我们之前已经修过很多轮了，但是我发现现在的会话模型还是有很多缺口，这是怎么回事？你要给我讲一下现在的架构是怎么设计的，我审核一下，我认为这么简单的一个功能，不应该反复返修这么多次

## 调查结论（2026-08-17）

这次不是偶发竞态，而是现行 Rewind 语义必然产生的结果。

Renderer 不是让 main 执行“撤销最后一轮”，而是先在本地只筛选
`status === completed` 的 turn：

```text
latest turn 是 completed -> 选倒数第二个 completed turn
latest turn 不是 completed -> 选最后一个 completed turn
```

然后 Renderer 把这个 turn ID 发给 main。main 的 reducer 又规定目标必须是
`completed`，并删除目标之后的所有 turn 及其 messages、tool events、file effects 和
request facts。因此它实际上不是“Rewind 一条消息”，而是“截断到某个 completed
checkpoint”。

你的复现中，末尾是连续的 stopped turn。stopped turn 明明已经被上一个 issue
定义为需要保留 user message 和 assistant partial 的合法历史，但 Rewind 又不把它视为
checkpoint。所以 Rewind 会跨过这些 stopped turn，一次退到更早的 completed turn。

### 现场证据

受影响 Session 为 `c0618ff0-e262-4238-ba23-13489b406df1`，anchor 是关联 issue。Rewind 后的
canonical store 现在只剩 1 个 completed turn：

```text
这个文章讲了什么？ -> assistant 回答
```

但 Rewind 不删除 context artifact，因此同一 Session 的磁盘目录仍能看到 4 个不同 turn
的 provider context。按时间排序，后三个是：

```text
d2640298...  编写一篇5000字的小说
491e3855...  编写一篇5000字的小说
98cec09e...  继续
```

这说明这次 Rewind 实际一次截掉了 3 个尾部 turn。用户看到的“两条消息”只是其中可见的
assistant 输出；按 canonical data 计算，被截掉的还包括每轮 user message 及相关内部事实。

## 现行架构

现在的会话链路可以分为五层：

```text
Renderer
  IrisAgentView + iris-agent-actions
  显示 Session 投影，发送 send/stop/retry/rewind
          |
          v
Main / IrisAgentSessionManager
  每个 Session 的命令串行化
  拥有 active turn、stop intent、turn 终态和 Rewind 事务
          |
          +------> IrisAgentSessionStore
          |        app-owned canonical store，持久化 Session 整个物化视图
          |        messages / turns / tools / effects / request facts
          |
          v
AgentWorkerHost
  每个 Session 一个短生命 Worker，管理启动、generation、空闲回收和终止
          |
          v
agent-worker + Pi session
  拥有当前活的模型上下文和 provider/tool 循环
  Worker 重建时由 store.history() 恢复
          |
          v
pi-adapter
  把 Iris canonical messages 转成 Pi messages
  在 provider 边界清理 aborted/tool 序列并捕获实际 payload
```

### 一轮请求如何运行

1. `send` 重新读取 anchor 并组装本轮 prompt。
2. main 先在 store 中新建一个 running turn，同时新建 user message 和空 assistant
   message。
3. Worker 若不存在，Host 用当前 store history 创建 Pi Session；活动 turn 不进入初始历史，
   避免当前 user message 重复。
4. Worker 把 Pi 的 stream、provider message、tool request 和 provider context 都带上
   `sessionId + requestId + turnId` 发回 main。
5. main 把中间 tool-call assistant 保存为 `providerOnly` message，把可见文本追加到主
   assistant message，最后以 compare-and-set 方式结算 turn。

### Stop 现在如何运行

main 先把 `stopRequestedTurnId` 和 `stopping` 持久化并 flush，然后才给 Worker 发 abort。
对应 turn 一旦有 stop intent，晚到的 `agent_end`、failure 或 Worker 退出都不能再把它变成
completed。已显示的 partial 会保留，并在下一个 Worker 重建时恢复给 Pi。这部分的方向是对的。

### Rewind 现在如何运行

Rewind 先校验 Session 不在运行，然后关闭旧 Worker、排空旧事件，再次读取最新
Session，最后保留到指定 completed turn 为止的前缀并 flush。下一次 send 会从这个前缀
重建 Worker。

这条事务的并发和持久化顺序已经比最初安全，但它安全地执行了一个错误的产品语义：
把“completed checkpoint”当成了“用户想撤销的上一轮”。

## 为什么反复返修

根本原因不是功能本身复杂，而是先前没有先封闭会话领域模型，而是围绕每次现象补局部不变量。

### 1. `message`、`turn`、`checkpoint` 没有统一语义

UI 显示的是 message card，Stop 和 Retry 操作的是 turn，Rewind 操作的是 completed
checkpoint，provider 需要的又是 user/assistant/tool 协议序列。对外只有一个含糊的
“Rewind”按钮，内部却有四种不同的操作单位。

### 2. `messages` 同时承担 UI 投影和 provider 恢复

为了修复 tool history，现在又在同一个 messages 数组中增加了 `providerOnly` 和
`providerMessage`。这能修复当前协议序列，但说明这个数组不是稳定的领域真相，而是 UI 和 Pi
两个投影的混合物。一个投影的修复容易破坏另一个投影。

### 3. 同时存在两套 Rewind 模型

`src/main/agent/history.ts` 定义了 message completion node 和 linear history，但生产路径完全不使用它，
只有这个 helper 自己的单测在跑。生产 Rewind 是 `session-manager.ts` 里另一套基于 turn
status 的 reducer。这是明确的架构漂移：测试中的“完成节点”并不是产品实际使用的节点。

### 4. 测试证明了实现，没有证明产品语义

现有 Rewind 单测明确断言“保留指定 completed target，删除后缀”，manager 集成测试也是主动
选第一个 completed turn。这些测试会稳定地保护当前错误语义。没有一条验收用例覆盖：

```text
stopped turn A -> stopped turn B -> 点击一次 Rewind -> 只撤销 B
```

### 5. 源码、运行产物和验收没有同一个版本身份

当前 Git `HEAD` 仍是 `805620e09c930fadb0c06140fdf98115995a786f`，Stop/history/Rewind 修复都还在
未提交工作区。关联 issue 也明确保留了“真实产品入口复测”未完成，并记录过旧
Worker 产物没有更新。因此“测试通过的源码”不能自动等于“用户刚才操作的版本”。

但这不是本次问题的借口：就算只审查最新工作区源码，Rewind 对 stopped turn 的处理也仍然是错的。

## 建议的产品语义

建议先把顶部全局按钮明确定义为“撤销上一轮”，不再使用没有边界定义的“Rewind”：

* 一轮是最小原子单位，包含该轮 user、assistant、tool-call/result 和内部事实。协议层不应只删
  assistant 而留下孤立 user 或 tool result。
* 点击一次只从 active branch 移除最后一个 terminal turn。`completed`、`stopped` 和 `failed`
  都是可撤销的 terminal turn，不能跨过 stopped/failed 去猜一个更早目标。
* 你这次的序列应当是：第一次撤销只移除“继续”这一轮；再点一次才移除前一个小说 turn。
* 对外 API 应叫 `undoLatestTurn(expectedRevision)`，不再由 Renderer 计算 target turn。具体截断点必须由
  main 基于最新 canonical revision 决定。
* 如果未来要支持点选历史中某一轮，API 要把语义写在名称里，例如 `truncateBeforeTurn`
  或 `keepThroughTurn`，不能再用一个含糊的 `turnId` 让两边各自推断。
* 仍然只撤销模型历史，不倒放已发生的文件、终端或外部副作用；确认框必须明确显示这个边界。

## 建议的架构收口

不建议再在现有 Renderer 目标计算上打一个条件补丁。需要按以下边界收口：

1. 定义唯一的 `Turn` aggregate，其中明确包含 user input、可见 assistant output、provider protocol
   messages、tools、effects 和 terminal status。
2. Session 显式保存 active branch 的有序 turn IDs 和独立的单调 revision；不再用 `updatedAt`
   同时客串时间戳和版本号。
3. UI messages 和 Pi/provider history 都从 Turn aggregate 独立投影，不再共用一个带
   `providerOnly` 开关的 messages 数组充当两份真相。
4. 删除未接入生产的 `history.ts` 双轨模型，或者让生产 reducer 和测试都只依赖同一个
   domain module。
5. Rewind/undo 命令返回 `removedTurnIds`、新 revision 和副作用未回滚标记，让 UI 显示的结果
   可核验，而不是只接收一份新 Session 快照。

## 修复前必须锁定的验收矩阵

* [ ] `completed A -> undo` 只移除 A，Session 回到空历史。
* [ ] `completed A -> completed B -> undo` 只移除 B。
* [ ] `stopped A -> stopped B -> undo` 只移除 B，再次 undo 才移除 A。
* [ ] `completed A -> stopped B -> undo` 只移除 B。
* [ ] `completed A -> failed B -> undo` 只移除 B。
* [ ] 包含多次 tool call/result 的最后一轮被整体移除，保留前缀仍是合法 provider 序列。
* [ ] undo 与 send/stop/Worker startup 并发时仍由 main Session 命令链串行化。
* [ ] Worker 重建、应用重启后只恢复 undo 后的 active branch。
* [ ] 真实产品入口显示可核验的 protocol/build identity，并手工复现本 issue 的精确序列。

## 当前判断

Stop 状态机、Worker 历史恢复和 provider 序列清理是必要且各自有效的修复，不应推倒。
真正需要重做的是上层会话领域边界，尤其是 Turn、active branch 和 undo 语义。本 issue 在语义经审核确认前，
不继续改代码，避免再增加一轮局部补丁。

## 基于第一性原理的完整整改方案

下面的方案不以现有字段和函数为起点，而是先回答“一个可以 Stop、继续、Retry、Undo 和重启恢复的
Agent 会话，最少需要哪些不可破坏的事实”，然后再推导数据模型、命令边界和运行时。

### 一、六条基本原理

#### 1. Turn 是最小的因果单位

一次 user input 引发一次 Agent 执行，该执行可能产生多次 provider call、assistant partial、tool
call/result 和外部副作用。这些事实共同属于一个 Turn，不能被 UI 上的几张 message card 反过来
定义。

Undo、Retry、Stop 操作的都应该是 Turn，而不是一条孤立 message。

#### 2. 持久化的 canonical state 是唯一真相

Renderer store、Worker、Pi Session 和 provider payload 都只是 canonical state 的投影或短生命运行时。
任何 Worker 都必须可以被随时销毁，然后仅凭 canonical state 重建出等价的模型上下文。

不允许用 Renderer 当前显示了什么、Worker 还记得什么、或某个 Pi SDK 对象的内部状态反推
会话真相。

#### 3. 执行状态与历史成员资格是两个维度

`completed/stopped/failed` 回答“这轮是如何结束的”。“这轮是否仍在当前对话时间线中”是另一个
问题。

因此不能继续用 `status === completed` 同时表示“正常完成”和“可作为 Rewind 边界”；也不应该把
`rewound` 塞进执行终态。

#### 4. UI 对话、模型协议和外部副作用是三个独立投影

* UI 对话需要 user text、可见 assistant text、turn status 和 tool 摘要。
* 模型协议需要严格有序的 user/assistant/tool-call/tool-result frames。
* 外部副作用需要审计“曾经发生过什么”，即使对话 Turn 后来被 Undo，事实也不能随之消失。

这三者可以共享 Turn ID 和 Tool Call ID，但不能继续共用同一个 `messages[]` 数组并依赖
`providerOnly`、`compact` 等开关解释其含义。

#### 5. 每个用户命令只能有一个原子提交点

Send、Stop、Retry、Undo、Close 都必须经过 main-owned Session actor 串行执行，并带上
`commandId + expectedRevision`。命令要么在 canonical store 中完整提交并返回新 revision，要么没有生效。

Renderer disabled、IPC 返回顺序和 Worker 事件时序都不能充当一致性保证。

#### 6. Undo 不等于倒放现实世界

Undo 只改变当前模型对话时间线。已写入的文件、已执行的终端命令和已调用的外部系统不会被默认回滚。

因此当前 reducer 在 Rewind 时删除 suffix `fileEffects` 是概念上错误的：它没有回滚文件，却删掉了
文件曾被改动的证据。

### 二、目标领域模型

#### Session aggregate

```ts
interface AgentSession {
  schemaVersion: 3;
  id: string;
  anchor: AgentAnchor;

  // 专用的单调乐观锁，与时间戳分离。
  revision: number;
  createdAt: number;
  updatedAt: number;

  // 仅列出当前对话时间线中的 Turn。
  timeline: string[];
  turns: Record<string, AgentTurn>;

  runtime: {
    phase: 'idle' | 'starting' | 'running' | 'waiting-tool' | 'stopping';
    activeTurnId: string | null;
    workerEpoch: number;
    stopIntent: null | {
      turnId: string;
      requestId: string;
      requestedAt: number;
    };
    lastError?: AgentError;
  };

  // 不随 Undo 删除的现实世界审计事实。
  effects: ExternalEffectFact[];

  // 只保留不可恢复的操作回执，不保留被删对话正文。
  undoReceipts: UndoReceipt[];
}
```

`timeline` 是当前会话的唯一顺序真相。第一阶段不引入用户可见的 branch/redo，避免为未定义的产品能力
增加复杂度。如果未来要做分支，可以把 timeline 升级为 branch，但不影响 Turn 本身的语义。

#### Turn aggregate

```ts
interface AgentTurn {
  id: string;
  ordinal: number;
  requestId: string;
  retryOfTurnId?: string;

  input: {
    text: string;
    acceptedAt: number;
    assembledInputArtifact?: ArtifactRef;
  };

  execution: {
    status: 'running' | 'completed' | 'stopped' | 'failed';
    startedAt: number;
    endedAt?: number;
    error?: AgentError;
  };

  display: {
    assistantText: string;
  };

  // provider-neutral 的严格协议序列，不是 UI card。
  transcript: ModelFrame[];
  tools: ToolExecution[];
  providerCalls: ProviderCallRef[];
}
```

Turn 的执行终态一旦写入就不再修改。Undo 不把 status 改为 `rewound`，而是把 Turn 从
`timeline` 移除。提交后可以删除 Turn 正文，只保留一条不含正文的 Undo receipt：

```ts
interface UndoReceipt {
  commandId: string;
  removedTurnId: string;
  removedAt: number;
  resultingRevision: number;
  externalEffectsRetained: boolean;
}
```

#### ModelFrame

`ModelFrame` 只表达跨 provider 共有的协议事实：

```text
user(text)
assistant(text blocks, tool calls, stop reason)
tool-result(toolCallId, content, isError)
```

其中本轮 user frame 保存实际交给 Agent 运行时的 assembled input，而 `Turn.input.text` 单独保存用户原始输入。
两者不得再混为一个含义不明的 message content。

思考签名、provider response ID 等专有信息可以放入带 schema version 的 adapter metadata，但不能成为 UI 恢复或基本
历史正确性的必要条件。Pi 升级时只迁移 adapter，不迁移会话领域语义。

### 三、唯一的状态机

#### Turn 执行状态

```text
accepted/running ---- normal settle ----------------> completed
       |--------------- provider/tool failure ------> failed
       |
       +-- Stop committed --> stopping --> ack/exit -> stopped
```

不可破坏的规则：

* 同一 Session 最多只有一个 active Turn。
* `stopping` 是 Session runtime phase，不是 Turn 终态。
* stop intent 一旦持久化，该 Turn 只能结算为 `stopped`。
* terminal status 只能从 running 写入一次。所有重复、晚到或旧 Worker epoch 事件无副作用。
* Session runtime 可以在 Worker 销毁后回到 idle，Turn 历史不依赖 Worker 是否存活。

#### Timeline 操作

```text
send  -> append a new running Turn
stop  -> settle active Turn as stopped
retry -> replace the failed/stopped tail with a linked new attempt
undo  -> remove exactly timeline[-1]
```

Undo 的先决条件只是 Session 已静止、末尾 Turn 已终结、没有未结算 tool。末尾 Turn 是
completed、stopped 还是 failed 不影响它能否被 Undo。

### 四、五个命令的精确语义

#### Send

1. Renderer 发送 raw user text、`commandId` 和 `expectedRevision`。
2. main Session actor 校验当前无 active Turn。
3. main 重新读取 anchor，组装本轮 input，新建 Turn 并递增 revision。
4. running Turn 先原子持久化，再将 run 发给特定 `workerEpoch`。
5. Worker 启动失败时，main 通过同一结算入口把 Turn 结算为 failed。

#### Stop

1. main 验证 active Turn 和 request correlation。
2. stop intent 先持久化并 flush，再发 abort。
3. `agent_end`、provider failure、abort ack、Worker crash 都经同一 reducer；只要 stop intent 存在，最终就是 stopped。
4. 结算前已接收的 display text、ModelFrame 和 tool facts 保留。

#### Continue

Continue 不是隐式命令，就是一次普通 Send，user text 为“继续”。provider history projection 必须把当前 timeline
中前一个 stopped Turn 的 user frame 和已显示 assistant partial 投影进新请求。

#### Retry

Retry 不应该在整个历史里搜索“最近的 failed/stopped Turn”。现在 Renderer 和 main 都这样搜索，所以即使
后面已经有成功 Turn，仍可能重试一个旧请求。

新语义是：Retry 只允许作用于 `timeline[-1]`，且该 Turn 必须是 stopped 或 failed。Retry 表示“从该轮之前的
对话前缀，重新执行同一份 raw user input”，因此旧 stopped partial 和失败 transcript 不能进入新 attempt 的
provider history，否则这不是 Retry，而是又发了一次 Continue。

Retry 应当是一个原子的 `replaceLatestTurn` 事务：从 active timeline 移除旧末尾 Turn，保留它已产生的外部
effects 审计，然后在同一次 commit 中放入一个带 `retryOfTurnId` 的新 running Turn。旧 Turn 正文按 Undo 相同策略
逻辑删除和清理，但 replacement receipt 保留这次重试的因果链。

#### Undo latest turn

对外不再提供含糊的 `rewind(sessionId, turnId)`，改为：

```ts
undoLatestTurn({ sessionId, commandId, expectedRevision })
  -> { removedTurnId, revision, externalEffectsRetained }
```

事务顺序：

1. 进入 Session actor 队列，读取最新 revision。
2. 校验 Session 静止、末尾 Turn 终结且 tools 已结算。
3. 递增 `workerEpoch`，使当前或启动中 Worker 的所有后续事件立即逻辑失效。
4. 关闭 Worker，排空已入队事件，再次校验末尾 Turn 和 revision。
5. 从 timeline 中只移除最后一个 Turn，清除该 Turn 的对话正文和 provider transcript。
6. 保留 effects ledger 原记录不变；UI 投影通过 Undo receipt 派生 `sourceTurnRemoved: true`，不回写或篡改
   已发生的 effect fact。
7. 追加不含正文的 Undo receipt，递增 revision，原子 flush。
8. 只在 commit 成功后 emit 新 Session 投影，并异步执行 artifact 清理。

如果在关闭 Worker 后、canonical commit 前崩溃，重启后会话仍保留原末尾 Turn，只是 Worker 需要重建；
不会出现“UI 说已撤销，磁盘还没撤销”的中间态。

### 五、投影与运行时边界

#### UI projection

Renderer 只接收以 Turn 为单位的 view model：

```ts
interface TurnView {
  id: string;
  userText: string;
  assistantText: string;
  status: 'running' | 'completed' | 'stopped' | 'failed';
  tools: ToolSummary[];
  canRetry: boolean;
  artifacts: ArtifactCapability[];
}
```

Renderer 不再根据 status 数组推导 Undo 目标，不再拼接 provider-only messages，也不判断哪个历史 Turn 可 Retry。
main 直接投影 `canUndoLatestTurn` 和每轮 `canRetry`。

#### Provider history projection

Pi adapter 只读取 `timeline` 中的 Turn，按 ordinal 展开每轮 transcript，生成严格合法的 provider frames。
投影后必须执行一次总体结构校验：

* 每个 tool result 必须对应先前未结算的 tool call。
* tool call/result 组必须原子保留或原子降级。
* stopped/aborted assistant 只恢复已显示文本和已完整结算的 tool 组。
* failed Turn 只恢复 provider 真实已看到且协议合法的 frames。
* 任何降级都产生可观测 diagnostic，不能静默改变历史。

Worker `ready` 回执必须包含：

```text
protocolVersion
appBuildId
sessionRevision
workerEpoch
historyDigest
historyFrameCount
```

main 只在这六项与预期完全一致时允许投递 run。这样才能区分“源码已修”、“Worker 产物已更新”和
“这个请求实际跑的版本”。

#### External effects projection

effect ledger 是 append-only 审计事实，不从 timeline 派生。UI 可以在 Undo 确认框显示该 Turn 曾产生的文件和终端
副作用数量，但本轮不实现自动回滚。如果未来要加“回滚文件”，它必须是一个独立、显式的命令，
不得暗含在 Undo conversation 中。

### 六、持久化和崩溃一致性

可以继续使用 userData 中的 versioned JSON store，但必须从“150 ms 后尽量落盘的快照”升级为有明确 commit
边界的存储层：

* Send accepted、Stop intent、Turn settlement、Undo、Close 是必须原子替换并 flush 的转换。
* 流式 partial 可以 debounce，但 Stop ack 或 terminal settlement 前必须 flush 最后一份 partial。
* revision 是独立整数，每次 canonical mutation 严格 `+1`；`updatedAt` 只是展示时间。
* 所有写入使用 temp file + fsync/close + atomic replace。启动时只读取最后一份完整 schema。
* 如果工具可以改写文件，应先持久化 tool intent，执行后再持久化 outcome；崩溃恢复时把未知结果标为
  `outcome: unknown`，不猜测“没有执行”。

如果后续性能或会话体积证明单 JSON 快照不够，再把同一 repository 接口迁移到 SQLite/WAL。本轮不应把换数据库
当成修复领域语义的前置条件。

### 七、Undo 后数据与 artifact 策略

建议采用“立即逻辑删除 + 可重试物理清理”：

1. canonical commit 中立即移除 Turn 正文和 transcript，新 Worker 永远无法恢复被 Undo 内容。
2. assembled input 和 provider context 在 commit 后进入清理队列。
3. 启动时 GC 扫描未被 canonical Turn 引用的 artifact，补做因崩溃中断的删除。
4. Undo receipt 只保留 Turn ID、时间、revision 和“副作用未回滚”，不保留 user/assistant 正文。
5. 清理失败只产生可观测警告，不能让已提交的 Undo 在 UI 上复活。

这个策略与当前“后缀不可恢复”的产品语义一致，也解决当前 provider-context artifact 永久成为孤儿的隐私缺口。

### 八、存量数据迁移

迁移必须独立于 Renderer 和 Worker，在 store load 边界一次完成：

1. 保留原始 store 的可恢复备份，然后用 temp + atomic replace 写入 schema v3。
2. 按现有 `turns[]` 顺序生成 timeline 和 ordinal。
3. 使用 `userMessageId/assistantMessageId` 生成 Turn display，使用 `providerMessage/providerOnly/tool`
   生成 transcript。
4. 对 transcript 做结构校验。无法无损恢复的旧 Turn 标记 `historyQuality: degraded`，保留可见文本，
   但不伪造 tool call/result。
5. 把现有 file effects 迁入独立 effects ledger，不再随 timeline 截断。
6. 新 revision 从 1 开始，原 `updatedAt` 仅保留为时间字段。
7. 索引现有 artifacts，对无对应 active Turn 的孤儿执行同一 GC 策略。
8. 迁移是幂等的：任何一步失败都继续使用原 store，不输出一半 v2、一半 v3 的会话。

### 九、测试战略

测试不再按每个现场 bug 追加一条 fixture，而是分四层证明不变量。

#### A. 纯领域 reducer 测试

* 用表驱动测试覆盖所有命令与状态组合。
* 用 property-based/model-based 测试生成 Send/Stop/Settle/Retry/Undo 事件序列。
* 每一步都断言：最多一个 active Turn、revision 严格递增、terminal 不可改写、timeline 无悬空 ID、
  Undo 每次只减少一个 Turn。

#### B. Store 和崩溃测试

* 在每个 commit 边界注入写入失败、rename 失败和进程重启。
* 断言重启后只能看到命令前或命令后状态，不存在半提交。
* 覆盖 v1/v2 迁移、损坏 provider message、孤立 tool result 和孤儿 artifact GC。

#### C. Worker/provider 合同测试

* 所有 Worker 事件带 session/revision/epoch/request/turn correlation。
* 覆盖旧 epoch 的 ready、stream、tool result、provider context、crash 在任意时序晚到。
* 从 canonical Turn 构建真实 Pi/provider payload，验证 stopped partial、failed、multi-tool、Undo 前缀和 Retry。
* 直接断言 provider-bound frames 的 role/tool-call 协议，不以 adapter mock 被调用代替。

#### D. 产品验收测试

* 按用户看到的 Turn 数量断言 Undo 结果，不使用内部 checkpoint 术语。
* 固定复现：生成 -> Stop -> 继续 -> Stop -> Undo，只减少最后一轮。
* 固定复现：Stop -> 应用重启 -> 继续，provider payload 包含 stopped partial。
* 固定复现：Undo -> 应用重启 -> Send，provider payload 不含被删 Turn。
* UI 显示的 build/protocol/revision 与 context artifact 中的身份一致。

### 已落地语义

* 顶部操作已改为“撤销上一轮”，每次只删除 timeline 最后一个 terminal Turn；
  `completed`、`stopped`、`failed` 都可撤销，running Turn 和未结算 tool 会被拒绝。
* Retry 只接受末尾 stopped/failed Turn，从该轮之前的 canonical 前缀启动新 Worker；旧 partial、
  provider transcript 和 artifact 不进入新 attempt，新 Turn 记录 `retryOfTurnId`。
* Undo/Retry 不删除 `fileEffects`。真实副作用继续作为 audit facts 保存，并通过 `undoReceipts`
  记录“对话已撤销、外部效果未回滚”。
* Renderer 不再推导 completed checkpoint；Send、Stop、Retry、Undo、Close 都携带
  `commandId + expectedRevision`，迟到命令不能作用到更新后的 Session。

### 一致性与持久化

* 新增唯一生产 domain module，`history.ts` 改为兼容导出，生产与测试共用 Turn reducer。
* Session store 升为 schema v3；v1/v2 加载时补齐 `revision` 和 `workerEpoch`，运行中 Turn
  按 stop intent 恢复为 stopped 或 failed。
* revision 对同一 Session 严格单调；Renderer 以 revision 拒绝旧投影。每次 Worker 替换增加
  epoch，main 忽略旧 epoch 的 ready、stream、tool、provider context、failure 和 crash 事实。
* Worker protocol 升为 v3。ready 屏障同时验证 protocol、epoch、history revision、消息数和
  deterministic history digest；独立 Worker probe 已同步验证这些字段。
* Undo/Retry 先提交逻辑状态，再清理 assembled input 和 provider context。失败的删除进入
  `pendingArtifactCleanupTurnIds`，下次列出 Session 时继续重试，清理失败不会让已撤销 Turn 复活。
* provider context index 记录 app version、protocol、Session revision 和 Worker epoch，实际 payload
  仍经过字段 allowlist、credential 删除和已知 secret 替换。
