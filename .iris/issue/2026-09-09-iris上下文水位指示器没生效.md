> 原始诉求：你看看现在这是怎么回事，好像1M显示出来了，但是随着运行没有任何效果，不知道自己的上下文用了多少，你调研一下，然后看看怎么解决

## 结论速览

那个「1M」原来是一个**窗口容量标签**，不是用量指示器：它只读模型配置里的 `contextWindowTokens` / `compactTrigger` 两个静态字段，跟运行时真实消耗无关，所以怎么跑都不会变。

根因有三层，缺一不可：领域模型里没有用量字段；`compactForThreshold` 其实已经算出请求的 token 估算，但算完即弃；provider 每次回包都带 `usage`，但 `applyProviderMessage` 直接把它丢掉了。

现在的方案：**主进程把读数算出来、存进会话、投影给渲染端；渲染端画一个环 + 严格百分比，绝对量放在悬浮里。**

## 现在的方案

### 显示

顶栏右侧、模型选择器之后的一个 `shrink-0` 小盒子：

* **左：环形进度条。** D=20 的 SVG（`r=9`、`stroke-width=2`、12 点起点、`linecap: butt`），弧长 = 占用比例。环是静止的，只在读数变化时过渡 `stroke-dashoffset`，避免和头像上那个旋转的活动环同族。

* **右：严格百分比。** `round(used / window * 100)`，**不封顶**——超过窗口就显示 `120%`。

* **环外一条刻度线**，角度 = `trigger / window * 360`，标出自动压缩会在哪里动手。

* **悬浮出细节。** `已用 372,000 / 1,000,000 tokens（37%），整理水位 983,616，来源：provider 上报 / 本地估算`；只有窗口、还没有读数时是 `上下文窗口 …, 整理水位 …, 尚无读数`。

* **颜色分三档**，但只改颜色不改数字：达到 trigger 的 80% 为警示，达到或超过 trigger、或达到窗口为危险。

唯一被夹逼的是**环的弧长**（一个圆转不了两圈，几何上限），数字完全如实。

### 数据

「窗口」和「读数」是两件事，所以拆成两个字段。窗口是模型属性，读数是一次观测——分开之后，「换了模型但窗口没变」这种错误在类型上就不可能发生。

```ts
// src/shared/types.ts
// 窗口：切模型时重算
interface IrisAgentContextBudget { windowTokens: number; triggerTokens: number; }
// 读数：永远与它被测量时的那套窗口配对
interface IrisAgentContextUsage { usedTokens: number; measurement: 'reported' | 'estimated'; updatedAt: number; }
```

两个都是可选会话标量，挂在 `IrisAgentSessionInfo` 上，复用现有 `session.updated` 差分投影——没有新增领域事件，也不用升 store 版本。

`normalizeAgentSessionAggregate` 负责容错：非整数的预算丢弃；**没有预算的读数也丢弃**（不知道分母的百分比没法显示）。旧快照读到就是 undefined。

### 采集

读数由主进程写，只有四个写入点：

| 时机                        | 口径                                           | 标记              |
| ------------------------- | -------------------------------------------- | --------------- |
| 创建会话 / 切模型                | 只解析窗口，不写读数                                   | —               |
| 发车前（prompt 组好、`run` 未发）   | 工具 schema 预算 2048 + 方法层 + 锚点 + 全历史 + 本次输入    | `estimated`     |
| provider 回包（assistant 消息） | provider 自报 `input + cacheRead + cacheWrite` | `reported`，覆盖估算 |
| 压缩落地                      | 工具 schema 预算 + 压缩后历史（不含方法层）                  | `estimated`     |

两个关键选择：

* **reported 用** **`input + cacheRead + cacheWrite`，不用** **`totalTokens`。** 后者还含 output。`@earendil-works/pi-ai` 已把 OpenAI / Gemini / Anthropic 三家的 `input` 都归一化成「不含缓存命中」，所以三项相加才是 prompt 总量。上报为 0 或缺失时返回 null，**绝不覆盖已有读数**。

* **窗口口径与自动压缩预检同源**（同一个 `estimateAgentRequestTokens`、同一个 `agentContextBudget`），所以指示器上那条线就是系统实际动手的线。

## 实现

### 主进程

**`src/shared/types.ts`** — 上面两个接口。

**`src/main/agent/compaction.ts`** — `AgentContextBudget` 改为 `IrisAgentContextBudget` 的类型别名（原来是重复定义，是两处默认值漂移的根）；新增 `agentContextBudget()`（集中解析窗口 / trigger 的默认值）与 `reportedContextTokens(usage)`（按上面的口径取数）。

**`src/main/agent/session-model.ts`** — `AgentSessionAggregate` 挂两个标量；`normalizeAgentSessionAggregate` 做校验与丢弃；`projectAgentSession` 投影出去。

**`src/main/agent/session-manager.ts`** — 三个私有助手 + 各写入点：

* `applyContextMeasurement(session, prompt, history)` 是唯一的读写入入口，同时重写窗口和读数，保证两者永远配对提交。

* `contextBudgetFor(session)` → `agentContextBudget(await compactionThresholdsFor(session))`。

* `compactionThresholdsFor` 改为 `async`，内部走 `await this.loadModelCatalog()` 而不是直接读 `this.modelCatalogCache`（理由见下面「硬 bug」）。受影响的四个调用点 `compact` / `compactForThreshold` / `retryAfterContextOverflow` / `contextBudgetFor` 一并改 await。

* 写入点：`sendSession`（发车前）、`retry`、`retryAfterContextOverflow`、`runCompaction`（压缩落地）。

* `applyProviderMessage` 解析 `message.usage` 写 `reported`，只对 `stopReason !== 'error'` 的 assistant 消息生效——失败的请求没有可用的占用量。

### 渲染端

**`src/renderer/lib/agent-context-usage.ts`** — 纯函数层，只负责「怎么画」，不重算占用：环的几何常量、`contextUsagePercent`（不封顶）、`contextRingOffset`（封顶）、`contextTriggerAngle`、`contextUsageTone`、`contextUsageLabel`、`contextUsageTitle` / `contextBudgetTitle`、`formatTokenCount`。

**`src/renderer/components/agent/AgentContextRing.tsx`** — 纯 SVG 环，几何全部来自上面的纯函数。

**`src/renderer/components/agent/IrisAgentView.tsx`** — 顶栏接线。预算优先取会话自己持久化的 `session.contextBudget`，只有会话还没有预算时才退回模型目录；读数只在「会话自己有预算」时才与之配对显示。悬浮用仓库的 `Tooltip` 组件（`no-native-title.test.ts` 禁止渲染端出现原生 `title` 属性）。

**`src/renderer/styles/global.css`** — `.iris-agent-context-ring*` 样式；颜色通过一个 `--iris-agent-context-accent` 变量下发，环和文字从同一处取色；三套主题家族都覆盖；`prefers-reduced-motion` 下关掉过渡。

## 一起修的硬 bug

**切模型不清读数（真数据错误）。** 旧实现里 `setModel` 只改 `session.model`，不动读数；而渲染端优先用读数里的窗口。于是从 1M 切到 128K 后，界面会拿旧窗口的读数去配新窗口，显示一个错的百分比，甚至偏乐观。

修法：`setModel` 按新模型重算 `contextBudget`，并**删掉** **`contextUsage`**。宁可暂时不显示百分比（回落成窗口标签 `128K`），也不显示错的；下一次发送即用新窗口重新测量。

**窗口解析依赖目录缓存是否热。** `compactionThresholdsFor` 原来直接读 `this.modelCatalogCache`。缓存冷（没走过 `listModels`）时回落到默认 128K，同一个 1M 模型会被先记成 128K。改为走 `loadModelCatalog()`。

途中差点引入一个真错误：我一度把 `createSession` 也改成走 loader，被仓库既有的 `creates a session without starting model discovery` 测试拦住——**创建会话不触发模型发现**是一条有意为之的不变量（创建必须保持离线快速）。已回退：创建仍只从上一次列出的缓存里选模型，选不到就没有模型，也就没有窗口。

**首次发送前可能整块消失（部分修复）。** 窗口现在随会话持久化（创建时、切模型时、每次发送 / 压缩时都重写），所以指示器不再依赖模型目录。只有在「会话根本没有模型」或「旧快照」时才退回目录，两者都退回不了就不渲染；没有模型时不再显示一个猜出来的默认窗口。

## 明确没做的

* **读数在估算与上报之间来回跳。** 纯上报无法在首次发送前和压缩后立刻给出读数，纯估算又拿不到 provider 的真实计数，所以两种都要保留；来源已标在悬浮里。未动。

* **压缩后先下陷再弹回。** 压缩落地时的重算不含方法层（软件 / 项目提示词 + 锚点，几千到上万 token），所以是下限，下一次发送才补正。未动。

* **上报滞后一轮。** 它是「刚跑完那次调用的输入」，不含该次自己的输出，误差约等于上一次回复长度。未动。

* **估算态没有视觉区分。** 只在悬浮文案里写「本地估算」。未动。

* **分辨率。** 1M 窗口下每 1% 只有约 0.5px 弧长，环同样要 1 万 token 才挪动半个像素。这是几何事实而非实现问题，所以由严格的百分比数字承担读数职责（已按用户裁决执行）。

* **让模型感知自己的用量。** 另一个话题，不在本 issue 范围。

## 2026-09-10 代码复审

评价：主链路实现合理，已经把静态容量标签变成有数据来源的指示器；没有发现需要推倒重做或会直接造成数据损坏的严重缺陷。但还不能认定为可靠的当前上下文水位，存在影响核心诉求的刷新遗漏。本次只审查并追加记录，未修改代码，状态保留 In Review。

### 已确认的问题

1. **P2：缺失 usage 时，长任务仍可能一直不动。** `session-manager.ts:1967` 的估算发生在发送、部分继续路径、溢出重试及压缩落地时；`pi-adapter.ts:473` 内部的工具调用循环会持续追加 assistant 和 toolResult，却不会逐次重算指示器。`session-manager.ts:2346` 收到空／零 usage 直接保留旧读数。因此，provider 持续不提供有效 usage 时，同一次任务即使读了大量文件，也可能一直显示任务开始时的数字。已有 missing-usage 测试只验证旧数不被清零，没有覆盖历史增长后的刷新。

2. **P2：回退历史后保留了失效读数。** `session-manager.ts:864` 回退仅截断活动 Intent 并对齐压缩；`session-domain.ts:43` 从完整会话克隆，保留 contextUsage，后续没有重算或清除。回退掉大段历史、甚至回退到空历史后，界面仍显示原百分比，直到后续测量才恢复。这是生命周期遗漏。

3. **P2：一个“已用”混合了不同测量对象。** provider 上报是上次调用的输入，不含该次输出和后续工具结果；发送前估算包含组装的 prompt；压缩后估算明确传入空 prompt，缺少方法层。区分 reported / estimated 只解释数据来源，没有说明测量时点和内容范围。现有偏差已在上文记录，但不宜一概当作纯视觉优化：用户会把百分比理解为当前占用。保持严格百分比没有问题，问题是分子代表什么。

### 次要问题与边界

渲染端的目录回退路径（`IrisAgentView.tsx:317`）仍用固定 16,384 计算整理水位，主进程却考虑 reserveOutputTokens / maxOutputTokens，因此旧会话尚无预算时，刻度可能与实际策略不一致。

“刻度就是系统实际动手的线”表述过强：阈值预检使用本地估算，正常回包后显示 provider 实测，两者并不完全相等；工具循环也没有每次经过主进程阈值预检，且无可压缩边界时不会执行压缩。这是现有压缩机制的边界，不应归因于环形 UI 新增了压缩故障。

做得好的部分：主进程持有并持久化读数、复用会话投影、切模型清除旧读数、百分比不封顶而几何封顶，方向均合理。核对了本地安装依赖的 Anthropic、OpenAI Responses、Google 适配实现，input 与缓存分项的归一化支持当前加总方式，没有发现这里重复计算缓存的依据。

## 2026-09-10 复审收尾

四条全部落地。其中前两条是真实缺陷，不是打磨；第三条定了口径；第四条只是消除两套规则的漂移。验证：全量 `npx vitest run` 89 个文件 554 个用例通过；`npm run typecheck`（含 `check:async`）通过。

### 接手时的现场

上一轮只落到一半：`session-manager.test.ts` 那条 missing-usage 用例是红的（`expected 2059 to be greater than 4571`），第 3、4 条一行没动，也没有写收尾记录。那条红灯和被修掉的是同一个根因——旧代码重测时读的是上一次提交的快照，量到的值比发送前的估算还小。

### 1. 长任务不再冻结

provider 不给 usage 时，工具循环里每追加一条 assistant / toolResult 都重测一次，读数随历史增长。

途中挖出一个隐藏的错位：原来的重测读的是 `store.history(id)`，而 `store.get()` 交回的**是上一次提交的快照** —— 刚应用的那条消息还不在里面，所以读数永远慢一拍（第一次重测量到的其实是“还没有这条 assistant”的上一个状态）。改用 `buildAgentContextFromSession(latest)`（即刚改完的那份投影）之后，量到的才是将要发送的请求。同一个 bug 也让测试里 4500 字符的工具结果只被计成 76 字符的未落库占位文本——这类偏差会系统性低估读数，且随工具结果变大而放大。

### 2. 回退后的读数作废

`rewind` 清掉 `contextUsage`，保留 `contextBudget`（模型没变）。测试覆盖“回退一条”和“回退到空历史”，并验证下一次发送会重新测量。

### 3. 「已用」的口径写死了

指标定义为：**一次请求 prompt 侧的 token 数 = 工具 schema + 方法层 + 历史**。两个来源是同一个对象的两次测量，差别只在时点：

* `reported`：provider 对“刚答完那次请求”的计数（不含该次回复与之后的工具结果）；

* `estimated`：对“下一次请求”的同一份投影。

为此会话上多了一个主进程私有标量 `contextPromptTokens`（最后一次组装请求里非历史部分的 token 数）。工具循环里方法层是固定的——pi 的循环每次调用都用同一个 `systemPrompt`——所以复用它不是近似。压缩落地同样复用它，于是「压缩后先下陷再弹回」那条已经不成立（至少不再凭空丢掉方法层那一块）。

悬浮文案改为 `已用（prompt 侧） …，来源：provider 上报（上次请求输入）` / `本地估算（下次请求）`，两个来源都写清了度量对象和时点。

### 4. 目录回退与主进程同源

窗口 / 整理水位的解析规则上移到 `src/shared/agent-context-budget.ts`，主进程的 `agentCompactionTrigger` 与渲染端的目录回退都调它。渲染端不再写死 16,384，而是按 `reserveOutputTokens → maxOutputTokens → 默认 16,384` 取预留，解析不出窗口就不画。目录回退仍然只在“会话还没有持久化预算”时生效（新建分支、旧快照）。

### 顺带纠正一句说法

「刻度就是系统实际动手的线」只在一半意义上成立：预检用本地估算，读数为 reported 时是 provider 实测，两者不会完全相等；工具循环也不逐次经过阈值预检，且没有可压缩边界时不会压缩。刻度标的是**策略起点**，不是“这一刻就会压缩”。
