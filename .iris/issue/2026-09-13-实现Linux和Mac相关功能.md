## 调研结果（2026-09-13）

### 结论摘要

当前不是“所有代码都绑在 Windows 上”，而是核心产品路径仍按 Windows 设计：编辑器、项目扫描、Markdown、Git 数据处理、IPC 协议、绝大多数 renderer 逻辑本身没有明显平台硬编码；但终端、Agent 上下文注入、外部终端、窗口 chrome、进程树清理和发行流水线决定了 Linux/macOS 目前还不能作为完整产品交付。

按文件粗略统计：

- `src/` 中 234 个非测试源码文件，38 个直接出现平台/Windows 相关分支或命名（约 **16%**）。
- `src + scripts` 中 244 个非测试源码/脚本文件，约 44 个出现平台相关引用（约 **18%**，包含测试、构建和诊断脚本时约 20% 左右）。
- 这个数字低估了实际工作量：被命中的文件集中在主进程关键路径，尤其是终端和 Agent；按“用户能否启动并完成主要工作”加权，当前 Windows 绑定程度更接近 **30–40%**，不能把 16% 当作完成度指标。

### 已确认的 Windows 绑定点

#### 1. 发行与 CI：目前实际上只有 Windows 产品

- `electron-builder.yml` 只有 `win` 配置，产物仅 `portable` 和 `nsis`，且只构建 x64；没有 `mac`（dmg/zip、签名、公证）或 `linux`（AppImage/deb/rpm）配置。
- `package.json` 的 `dist` 脚本固定执行 `electron-builder --win --x64`。
- `.github/workflows/ci.yml` 名为 Windows CI，runner 固定 `windows-2022`；没有 Linux/macOS 矩阵，也没有跨平台 smoke/build 验证。
- 资源中有 `build/icon.ico`，尚未看到 macOS 所需 `.icns` 或 Linux 多尺寸图标/桌面文件的发行配置。
- README 明确写着当前“Windows-first、仅提供 Windows x64”，运行要求包含 Windows 10/11、PowerShell，构建说明也是 Windows 发行包。

#### 2. Agent 上下文注入：整条 hook 适配器是 PowerShell 专用

- `src/main/agent-injection.ts` 生成 `~/.iris/focus-context.ps1`，hook 命令固定为 `powershell -NoProfile -ExecutionPolicy Bypass -File ...`。
- 文件编码、BOM、`[Console]::OutputEncoding`、`$env:*`、`Join-Path` 等均针对 Windows PowerShell 5.1；注释明确写着 POSIX 版本是后续里程碑。
- 识别 Iris 自有 handler 也只检查 `focus-context.ps1`，因此未来需要同时支持 `.sh`/`.zsh`（或直接调用 Node helper）并兼容已有配置迁移。
- `src/shared/types.ts` 的 goose 默认命令直接内嵌 PowerShell 和 `$env:USERPROFILE`，在 Linux/macOS 上不能运行。

#### 3. 终端与 Agent shell：虽有 POSIX 分支，但 Windows 语义仍是默认设计中心

- `src/main/terminal-session-manager.ts`：Windows 依次探测 `pwsh.exe`/`powershell.exe`，再退回 `cmd.exe`；POSIX 使用 `$SHELL`/`/bin/bash`。
- `src/main/agent/command-pty.ts` 已有 POSIX `-lc` 分支，这是可复用基础，但 Windows 路径探测使用分号分隔、反斜杠和 `.exe`，需要补齐 Linux/macOS 的 shell、登录参数、环境变量和失败提示测试。
- `src/main/terminal-session-manager.ts` 无条件传 `useConpty: true`（node-pty 在非 Windows 上通常忽略，但应明确按平台生成选项），并仅在 Windows 启用 bundled ConPTY DLL。
- `src/preload/index.ts` 和 `src/renderer/terminal/xterm-adapter.ts` 为 Windows ConPTY 暴露 `windowsBuild`；非 Windows 虽可得到 `null`，仍需要真实 Linux/macOS PTY 回归验证。
- `src/shared/terminal/shell-quoting.ts`、`input-policy.ts` 的命名和实现是 Windows shell quoting；拖拽路径、复制换行、shell 元字符等需要拆成平台无关层 + shell-specific 层。
- `src/main/terminal/process-tree.ts` 只实现 `taskkill.exe /T /F`，非 Windows 返回 `null`。Linux/macOS 需要进程组/session 设计（例如 signal group、`setsid`/pgid、macOS 子进程树清理），否则 Agent/PTY 可能残留。

#### 4. 外部系统终端：目前明确拒绝 Linux/macOS

- `src/main/system-terminal.ts` 只调用 `wt.exe`，并在 `platform !== 'win32'` 时直接抛出“不支持”。
- 需要分别适配 macOS `open -a Terminal`/`osascript`（或 iTerm2）和 Linux 的 `xdg-terminal`/发行版终端检测；还要定义命令、cwd、环境变量和失败回退策略。

#### 5. 窗口与桌面集成：当前是 Windows 风格 frameless 窗口

- `src/main/app-main.ts` 使用 `frame: false`；`src/renderer/components/layout/TitleBar.tsx` 自绘最小化/最大化/关闭按钮，注释和布局均称为 Windows caption buttons。
- macOS 需要处理 traffic-light 按钮、标题栏安全区、全屏/最大化语义和菜单栏；Linux 需要适配不同窗口管理器的 frameless/装饰策略。建议先按平台决定是否保留自绘标题栏，而不是简单复用 Windows 控件。
- `window-all-closed` 当前无条件 `app.quit()`，注释写明 macOS 行为只是暂时沿用 Windows 逻辑；macOS 通常应保留应用菜单并在关闭最后一个窗口后继续运行。

#### 6. 路径、环境和数据目录：底层 API 可跨平台，但周边假设很多

- `homedir()`、`path.join()`、Electron 路径 API 已被正确使用，这是可复用部分；但 `USERPROFILE`、`AppData`、Windows 盘符/反斜杠、大小写不敏感比较、PowerShell 路径拼接仍散落在 Agent、测试和文档中。
- `settings-manager.ts` 的 Windows 大小写折叠逻辑是合理的，需要确认 macOS 默认大小写不敏感磁盘与 Linux 大小写敏感磁盘的产品语义，不应简单按 `darwin` 复制 Windows 行为。
- Git 子进程已使用通用 `git` 命令，主要缺口是 shell/环境/进程终止方式，不是 Git 数据协议本身。

#### 7. 测试、诊断和文档覆盖不均

- 大量测试 fixture 使用 `C:\...`，并有 Windows-only `runIf`；已有少量 Linux 分支单测（如 shell 解析和外部终端拒绝），但没有真正 Linux/macOS Electron 启动矩阵。
- `scripts/smoke-launch.mjs` 已有跨平台终止分支（Windows 用 taskkill，其他平台用 SIGTERM），这是可沿用的模式；但 CI 没有在 Linux/macOS 执行它。
- `electron.vite.config.ts` 的端口探测和注释主要针对 Windows 保留端口，逻辑本身可跨平台，但应验证 macOS/Linux 网络权限和 IPv6 场景。

### 建议的实现拆分

#### P0：先让 Linux/macOS 能启动并完成基本项目工作

- [ ] 设计平台化标题栏：macOS traffic lights/菜单栏、Linux 原生装饰或可配置 frameless、Windows 保留现有控件。

### 建议的完成度口径

不要以“改动了多少文件”作为完成标准。建议定义三档：

1. **可启动**：三平台均能启动、创建/打开项目、编辑 Markdown、运行 Git，且无 native module 崩溃。
2. **功能等价**：内置终端、Agent 命令、上下文注入、进程清理、外部终端均有平台实现，并通过 CI + 手工验收。
3. **可发布**：三平台安装包、图标/元数据、签名（macOS 尤其是公证）、升级/卸载和回滚流程完整。

本轮调研未执行 `npm run build`、`npm run dist`、开发服务器或截图；结论来自源码、配置、CI 和文档静态检查。当前 issue 仍保持 `Todo`，待确认目标平台/架构和发布优先级后再拆成实施 issue。

## 兼容层放置建议（2026-09-13）

推荐在主进程建立 `src/main/platform/`，由这里统一承接所有真正依赖操作系统的能力。Electron 主进程已经拥有 `process.platform`、`os.homedir()`、`child_process`、`node-pty`、窗口和系统终端权限；把适配集中在这里，可以让 renderer 不需要知道 Windows、macOS、Linux 的命令和路径差异，也可以让单元测试用注入的 adapter 替换真实 OS。

建议的目录边界：

```text
src/main/platform/
  index.ts              # 根据 process.platform 创建 PlatformServices
  types.ts              # 所有能力的接口和平台类型
  shell.ts              # shell 探测、登录/非交互命令参数、环境变量
  process-tree.ts       # Windows taskkill；POSIX process group/signal 清理
  system-terminal.ts    # wt.exe；macOS open/osascript；Linux xdg-terminal 等
  agent-hook.ts         # PowerShell、sh/zsh 或平台无关 Node hook 生成
  paths.ts              # home、配置目录、脚本路径和规范化规则
  window-chrome.ts      # 标题栏、关闭行为、macOS menu/traffic-light 能力
  packaging.ts          # target、arch、图标和发行元数据
  windows.ts
  macos.ts
  linux.ts
```

`PlatformServices` 可以按能力拆成窄接口，而不是一个包含所有方法的巨型接口。例如 `shell.resolve(env)`、`processTree.kill(pid)`、`systemTerminal.launch(input)`、`agentHook.render(context)`、`windowChrome.policy()`。平台文件只负责系统调用和平台语义；上层业务负责会话生命周期、错误展示和协议，不把业务逻辑复制三份。

现有代码的迁移方向：

- `src/main/terminal-session-manager.ts` 和 `src/main/agent/command-pty.ts` 只调用 `platform.shell`，删除各自的 PowerShell/cmd/POSIX 探测。
- `src/main/terminal/process-tree.ts` 移入 `platform/process-tree.ts`；保留现有 `ProcessTreeKillFn` 作为接口，增加 POSIX process group 实现。
- `src/main/system-terminal.ts` 移入 `platform/system-terminal.ts`；IPC handler 只调用 provider，不再暴露 `wt.exe` 语义。
- `src/main/agent-injection.ts` 移入 `platform/agent-hook.ts` 的生成部分；配置读写、确认和状态模型留在现有业务模块。
- `src/main/settings-manager.ts`、`src/main/agent/pi-adapter.ts` 中的路径规则集中到 `platform/paths.ts`，业务层只接收规范化后的路径。
- `src/main/app-main.ts` 的 `window-all-closed`、frameless 标题栏和窗口选项通过 `platform.windowChrome` 提供策略；renderer 的 `TitleBar` 只渲染能力层声明支持的控件。

`src/shared/` 不适合放 `child_process`、`node-pty`、Electron 或 `process.platform` 适配。这里适合保留三类内容：跨平台协议（如 `AgentCommandShell`、IPC payload）、纯数据模型、与 OS 无关的算法。现有 `shell-quoting.ts` 是例外中的问题点：应改成纯的 shell quoting contract，具体 PowerShell/POSIX 实现放到 `src/main/platform/shell.ts`；renderer 的粘贴确认只消费平台无关的风险结果。

renderer 侧只保留用户交互差异，例如 Cmd/Ctrl 快捷键、macOS 菜单提示和路径展示。平台信息通过已有 IPC 能力（可扩展 `app-info`）下发，避免在组件中散落 `navigator.platform`。所有外部命令、脚本路径、进程信号和窗口 API 都应从 renderer 隔离。

推荐依赖关系：

```text
renderer ──IPC──> main business services ──> PlatformServices
                                      └────> shared protocols / pure algorithms
PlatformServices ──> Windows | macOS | Linux implementations
```

这样拆分的收益是：平台差异只有一个入口；核心业务可以在任意系统上复用；每个平台实现可以单独做 contract test；将来增加 FreeBSD、WSL 或远程终端时，不需要把平台判断重新散落到会话、Agent 和 UI 中。

## 完整实施方案

### 目标与范围

目标是让 Windows、macOS、Linux 在以下路径达到功能等价：启动和多窗口、项目选择与文件夹对话框、Markdown 编辑和资源管理、Git、内置 PTY、外部 Agent CLI、Iris 上下文 hook、剪贴板/拖拽、外部终端、设置持久化和安装包。

目标平台先固定为：Windows 10/11 x64；macOS 12+ x64/arm64；Linux x64（Ubuntu 22.04+，AppImage 优先，deb 作为补充）。Linux arm64 和更多发行版作为第二阶段扩展，避免第一轮同时处理桌面环境、架构和发行格式三个变量。

非目标：把各平台的 shell 行为伪装成完全相同；支持没有 POSIX shell 或没有桌面会话的服务器；在第一阶段实现自动更新、代码签名服务和所有 Linux 桌面环境的原生标题栏。

### 分层设计

```text
renderer components/stores
        │ typed IPC (protocol.ts)
main IPC adapters
        │ business services
        ├── project / git / session / injection / settings
        │       │
        │       └── PlatformServices
        │              ├── shell
        │              ├── pty
        │              ├── processTree
        │              ├── systemTerminal
        │              ├── agentHook
        │              ├── paths
        │              ├── windowChrome
        │              └── packaging (build time)
        └── shared protocols and pure algorithms
```

规则如下：

1. `process.platform` 只允许出现在 `src/main/platform/`、平台入口和少量 Electron 启动代码中；业务模块不能自行分支。
2. renderer 不调用 `child_process`、Electron shell、文件系统或平台命令。需要系统能力时新增 typed IPC。
3. `src/shared` 不导入 Node/Electron；只放 payload、状态机、路径显示规则、风险分析和序列化协议。
4. 平台实现返回结构化错误码，不把 `wt.exe`、`taskkill.exe`、`open`、`xdg-open` 等命令名泄漏到 UI。
5. 所有外部命令都接受显式 `cwd`、环境变量白名单和取消信号；禁止拼接未经校验的 shell 命令作为唯一执行方式。

### 核心接口

新增 `src/main/platform/types.ts`，定义以下窄接口（名称可调整，但边界固定）：

```ts
interface ShellService {
  resolveInteractive(env: Record<string, string>): ShellSpec;
  resolveCommand(env: Record<string, string>, requested?: ShellSpec): ShellSpec;
  buildInteractiveArgs(command?: string): string[];
  buildCommandArgs(command: string): string[];
  quotePath(path: string): string;
  pathListSeparator: ':' | ';';
}

interface PtyService {
  spawn(spec: PtySpawnSpec): IPty;
  options(): { useConpty?: boolean; useConptyDll?: boolean };
}

interface ProcessTreeService {
  kill(pid: number, signal?: string): Promise<void>;
}

interface SystemTerminalService {
  isAvailable(): Promise<boolean>;
  launch(input: { command: string; cwd: string; env: Record<string, string> }): Promise<LaunchResult>;
}

interface AgentHookService {
  scriptPath(): string;
  render(context: HookContext): RenderedHook;
  command(): string;
  install(cli: CliDescriptor): Promise<HookInstallResult>;
}

interface PathService {
  homeDir(): string;
  appDataDir(buildType: BuildType): string;
  configDir(tool: string): string;
  normalizeProjectRoot(path: string): string;
  equalProjectRoot(a: string, b: string): boolean;
}

interface WindowChromeService {
  createOptions(): BrowserWindowConstructorOptions;
  capabilities(): WindowChromeCapabilities;
  shouldQuitWhenLastWindowCloses(): boolean;
}
```

`PlatformServices` 在 `app-main.ts` 启动时创建一次并注入 `SettingsManager`、`TerminalSessionManager`、IPC 注册器和 Agent injection service。不要让这些服务在方法内部再次读取全局 `process.platform`。

### Shell 与 PTY 方案

Windows 实现顺序为 `pwsh.exe`、`powershell.exe`、`cmd.exe`；PATH 使用 `;`，PowerShell 命令使用 `-NoLogo -NoProfile -Command`，交互会话使用 `-NoExit`。POSIX 实现从 `SHELL` 读取，验证路径可执行；为空或不可执行时依次尝试 `/bin/bash`、`/bin/sh`，macOS 默认优先 `/bin/zsh`。交互 shell 使用 `-l`，Agent 命令使用 `-lc`，不把用户命令直接放进登录 shell 的二次拼接字符串，必要时通过 stdin 写入命令。

PTY 层保持 node-pty API 不变，平台服务只负责生成 shell 和选项：Windows 设置 ConPTY；Linux/macOS 不传 Windows 专用选项，并记录真实 backend。启动失败时返回 `ShellUnavailable`、`PtyBackendUnavailable`、`CwdNotAccessible` 等稳定错误码。

进程清理必须在 spawn 时建立所有权：Windows 记录根 PID并调用 taskkill；POSIX 以独立 process group/session 启动，先发送 SIGTERM，等待有限时间后 SIGKILL，最后关闭 PTY。超时、用户 abort、窗口关闭、renderer 崩溃和 app before-quit 走同一清理流程。

### Agent hook 方案

保持 `FOCUS_DOC`、`IRIS_WORKSPACE_PATH` 和注入文本协议不变。每个平台只改变脚本载体：Windows 生成带 BOM 的 `.ps1`；macOS/Linux 生成 UTF-8 `.sh`，使用 `printf`、`dirname`、`pwd` 和受控路径读取；脚本只负责读取环境变量和输出上下文，不执行项目命令。

hook 检测不再通过文件名判断“是否是 Iris handler”，而是写入版本化 marker（例如 `irisManaged: { version, platform }`）并兼容旧的 `focus-context.ps1` 字符串识别。升级时保留用户其他 handlers；删除时只删除 marker 对应的 Iris handler。默认 Agent 命令通过 `AgentHookService.command()` 生成，不再在 `shared/types.ts` 中内嵌 PowerShell。

### 路径、文件和 shell quoting

内部协议统一使用绝对路径或 `/` 分隔的 project-relative 文档路径。Windows 盘符、UNC、大小写折叠只在 `PathService` 处理；macOS 是否大小写折叠由 `realpath`/文件系统结果决定，Linux 保持大小写敏感。项目根比较统一使用 realpath 预检加平台规则，避免在业务层使用 `toLowerCase()`。

将 quoting 拆为两个结果：`analyzeDroppedPaths(paths)` 只判断是否含 shell 风险；`ShellService.quotePath(path)` 负责 PowerShell、POSIX shell、命令参数的实际编码。拖拽、粘贴确认、Git 参数和 Agent 命令分别测试空格、引号、换行、Unicode、`$`、反引号、反斜杠、通配符和换行。

### 外部终端与窗口

外部终端采用 provider 注册表：Windows `wt.exe`，macOS 先尝试 `open -a Terminal`，可选 iTerm2；Linux 依次检测 `x-terminal-emulator`、`gnome-terminal`、`konsole`、`xfce4-terminal`，最后使用 `xdg-open` 仅打开目录而不执行命令。provider 返回可用性和失败原因，设置页面可以显示检测结果。

窗口先分三种策略：Windows 保留现有自绘 caption；macOS 默认使用系统标题栏和 traffic lights，菜单通过 Electron application menu 提供；Linux 默认使用原生装饰，保留 frameless 作为显式实验开关。`window-all-closed` 改为由 `WindowChromeService.shouldQuitWhenLastWindowCloses()` 决定，macOS 默认不退出，`activate` 时重新创建窗口。

### IPC 与 renderer 改造

在 `APP_INFO` 或新增 `PLATFORM_CAPABILITIES` 返回：`platform`、`arch`、`shellDisplayName`、`externalTerminalProviders`、`windowChrome`、`supportsConpty`、`supportsAgentHooks`。所有字段是只读快照，启动时缓存。

新增或调整的 IPC 只表达意图：`SYSTEM_TERMINAL_LAUNCH`、`PLATFORM_CAPABILITIES`、`WINDOW_CHROME_POLICY`。renderer 不接收 executable path、脚本完整路径或 taskkill 等实现细节。现有 `SHELL_REVEAL`、`SHELL_OPEN_PROJECT_ITEM` 继续由 main 调用 Electron `shell`，并统一错误映射。

快捷键策略使用 `event.metaKey` 与 `event.ctrlKey` 的平台映射；Cmd+W、Cmd+Q、Windows/Linux 的 Ctrl 快捷键和 AltGr 单独测试。复制换行、标题栏、右键菜单和拖拽路径都以能力快照驱动，不在组件中散落 `navigator.platform`。

### 测试与验证矩阵

第一层是纯 contract tests：shell 解析、参数、quoting、路径比较、hook 输出、进程清理状态机、窗口能力。每个平台实现至少一组 fixture，不依赖实际桌面。

第二层是主进程集成测试：真实 `git`、真实 shell、node-pty 创建/输入/resize/退出、Agent 子进程超时和树清理。Linux/macOS runner 必须实际执行，不能只传入伪造 platform 字符串。

第三层是 Electron smoke：启动、preload、renderer、创建窗口、创建 PTY、打开项目、关闭窗口。Linux CI 使用 `xvfb-run`，macOS/Windows 使用原生 runner。截图不作为唯一验证手段。

验收场景固定为：首次启动、打开含中文路径的项目、创建 `.iris`、Markdown 编辑和图片、Git status/stage/commit、内置 terminal、Claude/Codex hook、Agent 超时、外部终端、剪贴板、拖拽、窗口恢复、最后窗口关闭、应用重启和升级后设置迁移。

### 发布与 CI

将 `electron-builder.yml` 拆为通用配置加平台 target：Windows `nsis/portable`；macOS `dmg/zip`，预留 hardened runtime、entitlements、签名和公证；Linux `AppImage/deb`，补齐 `.desktop`、AppStream 元数据和多尺寸 PNG。`asarUnpack` 保持 node-pty 原生模块规则，改为在每个平台 runner 验证加载。

把 `dist` 改成显式参数，例如 `npm run dist -- --platform=mac --arch=arm64`，禁止脚本固定 `--win --x64`。CI 矩阵至少包含 `windows-2022`、`ubuntu-22.04`、`macos-13`，Node 版本保持项目要求；步骤统一为 npm ci、license/metadata、test、typecheck、build、agent worker check、smoke。发行任务另行执行签名、公证和 artifact 上传。

### 风险和决策点

- `node-pty` 的 Electron ABI 和预构建包必须先在目标 runner 验证；失败时要选择 electron-rebuild、源码构建或锁定可用 Electron 版本。
- Linux 外部终端没有统一标准，必须接受“检测到的 provider 不同”这一产品事实，并提供复制命令的回退。
- macOS 签名、公证和 hardened runtime 会影响子进程、文件访问和原生模块加载，应在 M3 单独验证，不要与业务迁移混在一起。
- 自绘标题栏跨窗口管理器成本高；Linux 默认原生装饰可以显著降低风险。
- hook 配置属于用户文件，迁移必须保留未知字段和非 Iris handler，任何解析失败都应停止写入并提示用户。
