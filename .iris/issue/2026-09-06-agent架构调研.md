## 调研报告（截至 2026-09-06）

### 0. 口径、范围与证据等级

本报告比较的是“编码 Agent / Agent Harness 的架构哲学”，不是模型排行榜，也不是对各产品实际成功率的测评。比较对象的层级并不相同：

* Claude Code、Codex、Pi、OpenCode、Kimi Code 是可以直接工作的编码代理产品。
* DeepSeek 是模型与 API 平台；官方没有把 DeepSeek API 本身定义成一个完整的本地编码 Agent。
* “Harness”不是一个唯一产品名。DeepSeek 官方 API 文档的 Agent Integrations 链接指向 `deepseek-harness`，因此本文把 Harness 解释为 DeepSeek Harness（DSH），同时说明通用 harness 的含义。

证据优先级如下：官方产品文档 > 官方 GitHub 仓库/源码说明 > 官方博客或发布说明。文档描述的是产品的设计契约，不能替代源码审计和实际运行测试；开源项目的源码结构可以进一步验证其持久化和扩展边界，闭源产品则只能把未公开部分标为未知。

### 1. 统一比较坐标

为了避免把“模型、代理、工具、UI”混为一谈，使用以下十个坐标：

| 坐标 | 要回答的问题 |
| --- | --- |
| 本体边界 | 一等实体是 Session、Intent、Turn、Step、Task，还是一个不断循环的 Agent？ |
| 控制循环 | 谁驱动下一步：模型自行决定、固定 driver、工作流引擎，还是用户显式推进？ |
| 事实与投影 | 是否有 append-only 事实日志？上下文、UI、状态是否由事实纯投影得到？ |
| 执行身份 | 模型/Provider 是任务身份的一部分，还是每次 Invoke 可替换的运行参数？ |
| 工具与副作用 | 工具调用如何记录、重试、审批、回滚和审计？ |
| 安全边界 | sandbox、权限、网络、审批由谁强制执行，是否依赖模型遵守提示？ |
| 多代理 | 是 subagent（结果返回主代理）、agent team（横向通信），还是同一 Agent 的并发任务？ |
| 上下文与记忆 | 项目指令、自动记忆、压缩、分支、恢复如何实现？ |
| 扩展协议 | MCP、ACP、插件、Hooks、Skills 的责任边界是什么？ |
| 目标取舍 | 极简可组合、企业安全、模型能力、长任务并行，哪个是第一优先级？ |

### 2. Claude Code：以“可控的模型工作台”包住 Agent Loop

#### 2.1 产品边界

Anthropic 官方将 Claude Code 定义为能读取代码库、编辑文件、运行命令并集成开发工具的 agentic coding tool；它同时覆盖终端、IDE、桌面、浏览器和云端。核心不是一个公开的领域模型，而是一个跨表面的工作台：同一个会话可以在本地、IDE 或 Web 上继续，差异主要落在执行环境和授权面。

#### 2.2 状态与上下文哲学

Claude Code 的持久上下文由两部分组成：

1. 用户维护的 `CLAUDE.md`，用于项目、用户和组织级规则；
2. Claude 自动写入的 auto memory，用于偏好、纠错和项目经验。

两者都作为上下文加载，并不是强制执行的安全配置。官方明确建议：真正要阻止动作，应使用 `PreToolUse` hook 或权限系统，而不是把禁止写在提示词里。这是“软指导”和“硬边界”分离的设计。

它的上下文层级是文件作用域层级，而不是 Iris 式的 Trace/Context 领域分离：组织策略、用户规则、项目规则、局部规则按优先级合并；子目录中的规则按需加载。自动记忆默认只加载有限行数，以控制启动 token。

#### 2.3 执行、权限与 Hooks

Claude Code 的权限是工具级的 `allow / ask / deny` 规则，并有 `default`、`acceptEdits`、`plan`、`auto`、`dontAsk`、`bypassPermissions` 等模式。规则由运行时强制，模型提示不能绕过；命令、文件编辑、网络抓取、搜索和 MCP 工具都可以分别设定规则。审批规则可写入项目的 `.claude/settings.local.json`，从而跨会话复用。

Hooks 覆盖 `SessionStart`、`UserPromptSubmit`、`PreToolUse`、`PermissionRequest`、`PostToolUse`、`PostToolUseFailure`、`PreCompact`、`PostCompact`、`SubagentStart/Stop`、`Stop` 等生命周期节点。Hook 可以是 shell、HTTP、MCP 工具、提示词或 subagent。它是执行控制面，不是对话内容；可以在工具真正运行前拒绝操作，也可以在失败后提供修正信息。

#### 2.4 多代理哲学

Claude Code 区分两种并行模型：

* **Subagent**：有自己的上下文、工具权限和结果摘要，由主代理负责协调；适合隔离搜索、代码审查等局部任务，token 成本较低。
* **Agent team**：每个 teammate 是独立 Claude 实例，可直接相互通信并共享任务列表；适合需要讨论、互相挑战的复杂任务，成本更高。

这与“主循环里临时调用工具”不同：Claude 把上下文隔离、通信方式和协调责任作为一等运行时选择。

#### 2.5 设计取舍

Claude Code 的核心信念是：模型很强，但不能直接拥有不受约束的世界权限；代理能力必须包在权限、Hooks、配置和多种运行表面之内。它的优势是产品完整度和治理能力，代价是领域模型对用户不可见、内部事件日志和撤销语义不是公开稳定契约。

### 3. Codex：以 Sandbox/Approval 为中心的本地与云端执行系统

#### 3.1 产品边界

OpenAI 官方文档把 Codex 分成 CLI、IDE extension、Cloud 等表面。Codex CLI 可以在本地仓库中检查文件、编辑、运行命令、调用脚本和 CI；Codex Cloud 在隔离云环境中并行执行任务，并返回可审查的摘要、diff 或 pull request。模型、推理强度、权限、网络和运行环境是用户可选的执行参数。

#### 3.2 核心哲学：Sandbox 与 Approval 是两层控制

Codex 明确区分：

* **Sandbox** 决定技术上能做什么，例如可写目录、网络是否可达、是否能触碰宿主机。
* **Approval policy** 决定什么时候必须停下来问人，例如越出工作区、访问网络或调用有副作用的工具。

本地默认是 workspace-write、网络关闭、工作区内可写；常见权限模式为 `read-only`、`workspace-write`、`danger-full-access`，审批模式为 `untrusted`、`on-request`、`never`。这不是模型提示词，而是操作系统或云容器施加的边界。Codex Cloud 还采用两阶段环境：setup 阶段可以联网安装依赖，agent 阶段默认离线，setup 中的 secrets 不带入 agent 阶段。

#### 3.3 方法注入与扩展

Codex 的项目指导文件是 `AGENTS.md`；可叠加 Skills、MCP、Rules、Memories 和 Subagents。它把“项目应该怎么做”与“代理可以做什么”拆开：`AGENTS.md` 提供持久规则，Skills 封装可复用工作流，MCP 提供外部能力，Rules 管理命令许可，Subagents 分担上下文。

CLI 支持 `codex exec` 非交互运行，便于 CI 和脚本；CLI、IDE、Cloud 之间共享恢复、审查和委派概念，但不是同一进程或同一权限边界。

#### 3.4 设计取舍

Codex 的中心问题是“如何让 Agent 在真实机器上自主运行而不把机器交给模型”。它把安全边界做成显式运行时状态，把本地快速循环和云端并行作为同一产品的两种执行面。与 Iris 最接近的地方是“执行身份可替换、任务可以挂起等待审批、结果需要可审查”；不同之处是 Codex 文档更强调运行环境和审批，较少公开 Trace 领域的不可变性、事件重放或副作用回滚模型。

### 4. DeepSeek：模型/API，而不是完整 Agent 本体

#### 4.1 证据结论

DeepSeek 官方 API 文档将 API 描述为 OpenAI/Anthropic 兼容格式，提供 chat completion、tool calls、Responses API、上下文缓存等能力。DeepSeek-Coder-V2 仓库描述的是开源代码模型、推理方式和 benchmark，并没有定义 Session、Agent、权限、文件修改或终端执行的产品级领域模型。

因此不能把“DeepSeek 的设计哲学”直接与 Claude Code 或 Codex 并列：DeepSeek 主要把能力放在模型和 API 兼容层，Agent loop、工具执行、沙箱和会话持久化交给调用方或第三方 harness。

#### 4.2 对 Agent 架构的实际影响

DeepSeek API 的工具调用是一个协议事实：模型返回 tool call，客户端执行工具，再把 tool result 送回模型。重试、幂等、审批、失败归属和历史压缩都不由 API 自动替调用方决定。由此得到三个结论：

* DeepSeek 可以作为 Iris 的 Provider/Model adapter，而不应成为 Iris Intent 或 Turn 的身份。
* DeepSeek 兼容 OpenAI/Anthropic 风格接口，适合放在“可横向替换的 Invoke 执行主体”位置。
* 使用 DeepSeek 时，Iris 必须自己承担安全和持久化责任，不能把模型返回的 tool call 当作已发生的世界事实。

### 5. Harness：DeepSeek Harness（DSH）的事件溯源与可组合 SDK

#### 5.1 为什么单独列出

DeepSeek API 文档的 Agent Integrations 菜单直接链接 `deepseek-harness.github.io/deepseek-harness`。DSH 是用于构建 Agent Harness 的插件化 SDK，不是 DeepSeek 模型的别名。它比一般编码 CLI 更接近“可复用的运行时内核”。

#### 5.2 核心领域模型

DSH 的核心包由 `session`、`system-prompt`、`tools`、`agent`、`agent-loop` 和 `scope` 组成：

* `session` 是 append-only 的 `SessionEvent` 日志和内存存储，文档称其为 single source of truth。
* `agent-loop` 是具体 driver：从 inbox 领取 prompt，开启 turn，组装 system prompt，派生 history，请求 LLM，分派工具，再把模型可见事实追加回日志。
* `agent` 是对外的可编程句柄，暴露 `send/followup/steer/inject/cancel/whenIdle/runMaintenance`。
* `system-prompt` 和 `tools` 是可插拔注册表，按 agent scope 组合。
* `scope` 用于把服务、监听器和资源限制在一个 Agent 的生命周期内。

这是一种“事件日志记录事实，live API 管理协调”的明确分离。DSH 文档还特别区分：可重放的 `session/event` 与只用于实时控制的 `agent/*` 事件。

#### 5.3 Turn/Step、Inbox 与失败

DSH 的运行时层级是 Session -> Turn -> Step：一个 Turn 可以包含多个模型 Step；每个 Step 有 prompt assembly、LLM stream、tool calls 和 `step/end`。用户可以把消息送到普通 next-turn、steering（下一步）或 inject（下一步模型可见上下文）三个 inbox 边界。

请求错误通过 `agent/request-error` hook 进入重试、压缩或保留原错误的决策；工具调用支持 pre/execute/post，允许受控并发，但结果按模型顺序回写。它没有把所有错误都抽象成“Intent 挂起”：请求重试属于 driver/step 维护，永久错误和终止条件由上层处理。

#### 5.4 审批、持久化与扩展

DSH 的 user-approval seam 使用 `allowed-once/rejected/cancelled/unavailable` 的封闭结果集，并且 fail-closed；`approval/asked` 与 `approval/decided` 成对写入会话日志，但不进入模型 transcript。它的插件生命周期负责资源释放、MCP 重连、服务作用域和 agent dispose。

会话支持 seed、精确 inherited event count、fork lineage、JSONL/event catalog 和版本拒绝策略；文档要求无法忠实读取的新版本日志显式拒绝，而不是静默跳过未知事件。这个“可重放事实 + 明确格式边界 + 运行时投影”的取舍非常接近 Iris 的目标。

#### 5.5 与 Iris 的异同

相同点：

* 都把 Trace/Session 视为事实源，把上下文视为派生物。
* 都把模型/Provider 放在执行边界，而不是用户意图身份中。
* 都有工具调用的独立管线、审批边界、MCP 扩展和会话分支/恢复。
* 都把运行时失败和可重放历史分开，避免把网络噪声写入用户语义历史。

不同点：

* DSH 的公开主模型是 `Session -> Turn -> Step`，Iris 额外引入了不失败的 Intent，并把暂停/覆盖放在 Intent 生命周期。
* DSH 允许一个 open Turn 内继续领取 inbox 和重试 Step；Iris 更强调 Invoke/ToolCall/Turn 的失败归属与 Intent 挂起。
* DSH 的事件日志记录粒度较细（assistant chunk、tool call、approval 等），Iris 的目标是持久化 turn 级 Trace，provider runtime frame 留在 artifact/adapter 边界。
* DSH 的副作用回滚不是核心通用语义；Iris 对文件 effect 有 before/after hash 与 CAS rewind，终端 effect 明确不可逆。

### 6. Pi：极简、可嵌入、由用户塑形的 Harness

#### 6.1 核心定位

Pi 官方仓库把自己称为 minimal terminal coding harness，并由 `pi-agent-core`、`pi-coding-agent`、`pi-ai`、`pi-tui` 等包组成。默认只给模型四个工具：`read`、`write`、`edit`、`bash`。Pi 明确选择不内置 subagents 和 plan mode，建议用户通过扩展、Skills、Prompt Templates、Themes 和 Pi Packages 自己组合需要的工作流。

这是有意识的“反平台化”立场：核心保持小，用户适应 Pi，而不是 Pi 预设一套强工作流。

#### 6.2 Session、分支与压缩

Pi 的会话是 JSONL 文件树，每条记录有 `id` 和 `parentId`；`/tree` 可以在同一文件中切换分支，`/fork` 从历史用户消息创建新会话，`/clone` 复制当前分支。完整历史保留在 JSONL，compact 只是有损地生成上下文摘要，用户仍可通过 tree 回到原始历史。

这和 Iris 的“Trace 不变、Context 可变”高度相似，但 Pi 的 tree 是产品级交互功能，并不等价于 Iris 的 Intent path + effect rewind：Pi 主要分叉认知历史，文件副作用的通用 CAS 恢复不是其核心承诺。

#### 6.3 安全与扩展取舍

Pi 官方明确声明没有内置权限系统；默认以启动进程的用户权限运行，若需要边界，应该使用容器或 sandbox。这是极简哲学的直接代价：Pi 把安全交给外部部署层，把创新空间留给扩展。

Pi 的扩展是 TypeScript，能改变工具、UI、事件和命令；同时支持交互、print/JSON、RPC 和 SDK 嵌入。它还维护统一多 Provider API，可使用 DeepSeek、Kimi For Coding、OpenAI、Anthropic 等多种后端。这种“Provider 中立 + Harness 极薄”的结构很适合作为 Iris adapter 的参考。

### 7. OpenCode：开放模型市场 + 显式 Agent Profile

#### 7.1 产品定位

OpenCode 官方文档和仓库把它定义为开源 AI coding agent，提供终端 TUI、桌面应用和 IDE 扩展。它通过 AI SDK/Models.dev 支持 75+ Provider，也支持本地模型；项目初始化会生成 `AGENTS.md`，并建议提交到 Git。

#### 7.2 Agent 类型与权限

OpenCode 把 Agent 明确分为：

* Primary agent：用户直接交互的主代理。内置 `Build`（全工具）和 `Plan`（编辑与 bash 默认 ask/受限）。
* Subagent：主代理按需调用的专用代理。内置 `General`、`Explore`、`Scout`，也可用 JSON 或 Markdown 文件定义自定义 agent。

每个 agent 可以设置 description、model、prompt、temperature、steps、permission。Permission 的结果是 `allow / ask / deny`，并支持 `--auto`；配置按 remote、global、project、`.opencode`、managed 等层级合并，组织级配置可强制覆盖用户配置。

OpenCode 的重要哲学是“模型和工作流可配置，而执行面保持统一”：计划模式不是另一种产品，而是一个权限更小、模型可不同的 Agent profile；Subagent 可以继承调用者模型，也可以指定更快或更便宜的模型。

#### 7.3 交互、撤销与可观察性

官方入门文档要求先用 Plan mode 生成方案，再切换 Build；支持 `/undo`、`/redo`、`/share`。这些是用户可见的工作流控制，但文档没有把 undo 定义为可逆文件 effect ledger 或 event-log prefix truncate，因此不能直接推断它具备 Iris 的 CAS 语义。

OpenCode 的 provider registry、agent profile 和 config merge 设计很适合产品化；风险是大量配置优先级与第三方 Provider 兼容性会成为运行时复杂度。

### 8. Kimi Code：产品化 TUI + 子代理/插件/生命周期 Hooks

#### 8.1 产品与模型关系

Kimi Code CLI 官方仓库把它定义为运行在终端的 AI coding agent：读写代码、执行 shell、搜索文件、抓取网页，并根据反馈选择下一步。它以 Moonshot 的 Kimi 模型开箱即用，也支持兼容 Provider；官方产品页强调 Kimi K3 和最高 1M 上下文，但不能把模型上下文长度等同于 Agent 的持久化语义。

Kimi Code 采用单二进制安装、快速启动和专用 TUI；同时通过 ACP 接入 Zed/JetBrains，通过 MCP、插件市场和 Skills 扩展。

#### 8.2 Subagent 与 Agent 配置

官方文档定义三种内置 subagent：

* `coder`：可读写和执行命令的通用工程代理。
* `explore`：只读的快速代码探索代理。
* `plan`：只读的实现规划代理。

Subagent 在隔离上下文中运行，不允许再嵌套 `Agent`，结果返回主代理。自定义 Agent 用 YAML 定义，可以继承默认 Agent、替换 system prompt、增删工具并声明子代理。这种设计和 OpenCode/Claude 的“隔离上下文 + 角色权限”相似，但 Kimi 还把它做成了强产品默认值。

#### 8.3 Hooks 与持久化

Kimi Code 的 Hooks（当前标为 Beta）覆盖 13 类事件，包括 `PreToolUse`、`PostToolUse`、`UserPromptSubmit`、`Stop`、`SessionStart/End`、`SubagentStart/Stop`、`PreCompact/PostCompact` 和 `Notification`。Hook 命令接收 JSON stdin；退出码 2 可以阻止工具并把 stderr 反馈给模型，其他失败默认 fail-open。这个 fail-open 选择偏向可用性，与 DSH 的审批 fail-closed 和 Codex 的 sandbox enforcement 是明显差异。

Kimi 会话恢复的不只是聊天文本，还恢复审批决定、Plan mode、Subagent 状态和额外工作目录；`/compact` 用摘要替换上下文，原会话仍可通过 session id 恢复。旧 `kimi-cli` 已在迁移到新的 `kimi-code` 仓库，不能把旧文档中的实现状态直接套到新 CLI。

### 10. 设计哲学的分组结论

#### 10.1 “安全包裹模型”派：Claude Code 与 Codex

两者都不把模型的自然语言约束当成安全边界，但重心不同：Claude Code 通过权限规则、Hooks、项目记忆和多代理工作台治理模型；Codex 通过 OS/cloud sandbox、网络隔离、审批策略和环境复现治理执行。Iris 应吸收二者的“硬边界不依赖模型”原则，但不应把其 UI 权限模式直接复制成领域状态。

#### 10.2 “Harness 内核”派：DeepSeek Harness 与 Iris

DSH 与 Iris 都在回答：如何把一次不可靠的模型循环，变成可持久化、可恢复、可扩展的系统。append-only 日志、运行时事件与可重放事件分离、作用域资源、审批闭集和精确 fork cut 都可以直接互相校验。Iris 比 DSH 更进一步地把 Intent 定义为价值层实体，把 Turn 限定为执行事实，并为可控副作用定义 CAS 回滚。

#### 10.3 “极简可塑”派：Pi

Pi 认为核心越小越容易被真正理解和改造，因此不内置计划、多代理和权限。它提醒 Iris：不要因为产品竞争而把每个工作流都硬编码到领域内；Skills、Hooks、MCP 和 Agent profile 应尽量停留在扩展层。与此同时，Iris 面向项目文件和长期任务，不能照搬 Pi 的默认无权限模型。

#### 10.4 “开放平台产品化”派：OpenCode 与 Kimi Code

OpenCode 选择 Provider/Agent/Permission 全配置化，Kimi Code 选择单二进制、专用 TUI、内置 subagent、MCP/ACP 和生命周期 Hooks。两者都把 Agent profile 当成用户可切换的工作模式，而不是把每个模式写死在核心循环里。Iris 可以借鉴 profile 化和协议适配，但必须保留 Provider-neutral Trace，否则切换模型会污染历史语义。

#### 10.5 “模型供给层”派：DeepSeek

DeepSeek 说明了一个边界：模型厂商提供能力和协议兼容，不必拥有 Agent 的领域模型。Iris 应把 DeepSeek、Kimi、Claude、OpenAI 都放在 Provider adapter 之下，用统一 Invoke 契约吸收限流、超时和响应格式差异。

### 11. 对 Iris 的具体启示

#### 11.1 已经正确、应保持的决策

1. **Intent 不等于模型会话。** Intent 表达用户价值和生命周期；Provider、模型和 API 是每次执行可替换的临时身份。
2. **Trace 是唯一事实源。** Provider 原始帧、流式重试和网络错误属于运行 artifact，不应写入用户可见 Trace。
3. **Context 必须是纯投影。** compact、anchor diff、UI projection 都可以变化，但不改写历史事实。
4. **失败按可替换性归层。** Invoke 可换 Provider，适合层内重试；ToolCall 是世界操作，只有可重试部分在层内消化。
5. **副作用需要独立 effect ledger。** 文件使用 before/after hash 和 CAS 保护回滚；终端、网络发送等不可逆操作只审计不伪造撤销。
6. **方法与材料分开。** agent-base/software/project 用当前符号引用，anchor 用快照加 diff，避免旧协议污染新执行和全量材料膨胀。

#### 11.2 应从外部项目吸收的能力

* 借鉴 DSH 的 `session/event` 与 `agent/*` 双平面：持久化事实和 live control 不共用一个 transcript。
* 借鉴 Codex 的 sandbox/approval 二层模型：在 ToolCall 进入业务错误处理前先做技术边界判断。
* 借鉴 Claude Code 的 `CLAUDE.md` 分层和 Hook 事件：指导、硬拒绝、审计和自动化分别建模。
* 借鉴 Pi 的最小核心：把 plan、review、research 等工作流优先做成 Skills/Agent profiles，而不是继续扩大 Intent/Turn 本体。
* 借鉴 OpenCode 的 Agent profile 和 Provider registry：允许同一 Intent 在不同 Invoke 使用不同模型，但把选择存于 Session 当前配置而非历史实体。
* 借鉴 Kimi Code 的 ACP/MCP 边界和 session state 恢复：协议连接、审批状态、subagent runtime 必须有明确的恢复/失效策略。

#### 11.3 不应直接复制的设计

* 不复制 Pi 的默认全权限；Iris 的“可恢复文件副作用”要求更严格的 sandbox 和审批。
* 不复制 Kimi Hooks 的 fail-open 作为唯一策略；安全门禁应能选择 fail-closed，至少 PreTool/权限类 Hook 必须闭合。
* 不把 Claude auto memory 或 Kimi compact 摘要当作 Trace；它们只能是可丢弃的 Context artifact。
* 不把 OpenCode `/undo` 或一般 Git checkpoint 宣称为领域级 rewind；只有 effect ledger + CAS 才能安全恢复文件。
* 不把 DeepSeek API 的 tool call 当作工具已经执行；执行事实必须由 ToolCall runtime 提交。

### 12. 建议的 Iris 目标架构（按优先级）

#### P0：稳定语义边界

* 保持 `Session -> Intent -> Turn -> Invoke/ToolCall`，禁止将 Provider、Model、Attempt、UI card 重新塞回 Intent。
* 为每一层定义闭集状态和错误归属，并在类型层拒绝跨层泄漏。
* 将 Trace、Context、runtime frame、effect ledger、approval audit 作为五种不同的数据类型。

#### P1：安全与恢复

* 在 ToolCall 执行前增加 sandbox/approval decision；模型提示只影响意图，不授予权限。
* 对文件、目录、命令、网络请求分别定义 effect kind、可逆性、幂等键和 CAS 条件。
* 审批采用 DSH 式闭集结果：`allowed-once / rejected / cancelled / unavailable`，`unavailable` 必须 fail-closed。
* 设计统一的 `suspend(reason)` 控制信号；网络、Provider、worker 暂时不可用不生成失败 Turn。

#### P2：可组合 Agent

* Agent profile 只选择 prompt、工具集合、权限 preset、模型偏好和 Skills，不改变 Trace 语义。
* Subagent 继承父 Intent 的只读 Context 快照，产生独立 Intent/Session 或带 lineage 的 child path；禁止隐式共享可变 runtime。
* Hooks/MCP/ACP 都通过 typed adapter 接入，不能直接写入 Trace；必须由领域命令提交事实。

#### P3：产品能力

* 支持 plan/review/explore/build 等 profile；Plan 只能产生方案 artifact，Build 才能提交 ToolCall effect。
* 支持本地、云端、IDE 三种 execution surface，统一使用同一个 Trace/Context 协议。
* 对 context compact 提供可验证摘要和来源指针，允许从原始 Trace 重建，而不是把摘要当作唯一历史。

### 13. 最终判断

市场上没有一个项目完整实现了 Iris 的全部立场：

* Claude Code 最强的是产品治理、权限和 Hooks。
* Codex 最强的是 sandbox、审批、网络隔离和本地/云端统一执行边界。
* DeepSeek 提供的是可替换模型/API，不是 Agent 领域模型。
* DeepSeek Harness 最接近可重放、可组合的 Agent 运行时内核。
* Pi 最强的是极简、Provider 中立和扩展性，同时主动放弃内置安全与工作流。
* OpenCode 最强的是开放 Provider、Agent profile 和配置化权限。
* Kimi Code 最强的是产品化 TUI、长上下文、内置 subagent、MCP/ACP 和生命周期自动化。

Iris 的差异化不应是“再做一个会写代码的 CLI”，而应是把这些系统隐含的正确性问题显式化：用户意图不失败、执行失败可恢复、事实与上下文分离、Provider 可替换、副作用可审计且可选择性回滚。就架构方向而言，最值得继续坚持的是 Iris 自己的 Intent/Trace/Context/effect 语义；最值得吸收的是 DSH 的事件溯源与作用域、Codex 的 sandbox/approval、Claude/Kimi 的生命周期 Hooks，以及 Pi/OpenCode 的可组合扩展边界。

## 架构思想的先进性判断（2026-09-06）

结论：**有，而且先进性主要体现在语义边界和失败本体论上，不只是功能数量上。** 如果把“先进”定义为“比别人多几个工具、支持更多模型或有更漂亮的 UI”，Iris 并不天然领先；如果定义为“能否把不可靠的模型调用变成可恢复、可审计、不会污染用户意图的长期系统”，Iris 的思想处于行业中比较靠前的位置。

### 为什么说它先进

1. **把 Intent 从执行过程里分离出来。**

   多数编码 Agent 的公开产品模型是 Session + transcript + agent loop。Iris 进一步区分“用户想完成什么”（Intent）和“这次如何执行”（Turn/Invoke/ToolCall），因此 Provider 暂时不可用、worker 崩溃或网络抖动不会被误写成用户意图失败。这是面向长期任务的正确抽象，而不是 UI 命名变化。

2. **失败按可替换执行主体分层。**

   “能横向替换执行主体的层，错误通常是可重试噪声；不能替换的世界操作，才有不可重试事实”是很有价值的判别器。它比“所有错误统一向上抛”或“所有错误都让模型自行修复”更接近真实系统的本体结构。

3. **明确 Trace 是事实、Context 是投影。**

   许多产品有 transcript、summary、memory 和 UI history，但没有把它们之间的真相关系说清楚。Iris 把 `Context = f(Trace)` 作为不变式，并要求 compact 改变 Context 而不改写 Trace，这为重放、审计、分支、恢复和跨 Provider 迁移提供了统一基础。

4. **不把模型当作领域身份。**

   同一 Intent 可以在不同 Invoke 使用不同 Provider/模型，模型切换不会制造一个新的用户意图，也不会污染 Provider-neutral Trace。这比把“某个模型的会话”当作 Agent 身份更适合真实生产环境中的故障切换和成本路由。

5. **把副作用可逆性单独建模。**

   文件 effect 用 `beforeSha256` / `afterSha256` 和 CAS 条件恢复，终端等不可逆副作用只做审计，不假装能够撤销。这比通用的 `/undo`、Git checkpoint 或“重新让模型改回去”更严谨，尤其适合文档和代码会被长期保留的 PM 工具。

6. **方法与材料使用不同的注入策略。**

   方法层跟随当前协议，材料层保留锚点并注入 diff。这同时处理了“旧规则继续操作当前文件”的风险和“每次全量注入导致上下文膨胀”的问题，属于针对长期运行 Agent 的工程化推导。

### 先进性不是“完全原创”

Iris 的每个零件都不是市场上首次出现：DSH 已经有 append-only session event、live agent control 与 scope；Pi 有 JSONL tree、fork 和 compact；Codex 有 sandbox/approval；Claude Code 与 Kimi Code 有分层指令、Hooks 和 subagents。Iris 的价值在于把这些分散的实践统一成一套更严格的领域不变式，尤其是：

`Intent 不失败`、`Invoke 可替换`、`ToolCall 记录世界事实`、`Trace 不因 compact 改写`、`副作用按可逆性处理`。

因此它的创新更接近**语义整合和边界清晰度**，而不是发明了一个完全没有先例的新组件。

### 仍然需要保持警惕的地方

* **“Invoke 没有永久错误”不能无限泛化。** 认证失效、计费关闭、模型不存在、策略拒绝等错误未必能靠换 Provider 解决。更稳妥的表述是：Invoke 不把这些错误写成 Intent 的失败事实，但可以向 Intent 上浮一个受限的暂停/阻塞原因。
* **纯 Context 需要严格输入闭集。** 如果 Context builder 偷偷读取当前文件、当前模型配置或 UI 临时状态，`Context = f(Trace)` 就会失效。所有外部材料都应进入带版本/指纹的 injection 或 artifact 输入。
* **Trace 级别越粗，恢复成本越高。** turn 级 Trace 很干净，但 worker 恢复、Provider 特殊格式重建和中断 tool result 合成会更依赖 artifact。这个取舍必须由协议测试覆盖，而不能只靠类型设计。
* **文件 rewind 的 CAS 不是万能撤销。** 文件被用户或其他进程改动后应拒绝恢复；目录、权限、生成物、外部服务和终端输出不能被伪装成可逆。拒绝路径本身需要成为用户可理解的产品状态。
* **模型切换和并发需要明确屏障。** 运行中的请求不能原地换模型；切换应在 Invoke/Turn 边界生效。多个 Intent 并行时还需要定义 artifact、文件锁和 active path 的冲突策略。
* **抽象复杂度必须由验证兑现。** Intent、Trace、Context、Effect、Approval 五套结构如果没有重启恢复、分支、失败重试和旧数据迁移测试，先进思想会退化成维护负担。

### 综合评级

* 语义和第一性原理：**8.5/10**。失败归层、Provider 非身份、Trace/Context 分离和 effect 可逆性都很扎实。
* 与行业实践的差异化：**7.5/10**。单点并非全新，但组合后的边界比大多数编码 Agent 的公开模型更清晰。
* 当前可证明的工程成熟度：**取决于持续验证，暂评 6.5-7.5/10**。设计先进不等于已经解决分布式并发、迁移、异常中断和用户理解成本。

一句话判断：**Iris 最值得坚持的不是“Agent 能做更多事”，而是“Agent 做错或暂时做不到时，不会把执行噪声伪装成用户意图，也不会把不可逆世界状态伪装成可撤销”。** 这是一条有长期价值的架构路线；下一阶段的重点应是用故障注入、重启恢复、并发分支和 CAS 冲突测试证明它，而不是继续增加表面能力。
