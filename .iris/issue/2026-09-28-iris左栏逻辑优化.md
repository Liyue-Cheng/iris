## 2026-10-25 第二轮：现状复核、同类软件调研与优化建议

本轮只做调研和出方案，没有改业务代码。依据是当前工作副本，包含尚未提交的改动：工作区右键菜单（见 `2026-10-25-根工作区右键菜单`）和卡片/分层两种布局风格（见 `2026-10-22-优化界面`）。9-28 那一轮的研究记录在工作副本里已被移除，这次重新核对了一遍；其中仍然成立的结论，下文标注「（上轮已提，仍在）」。

### 一、当前左栏的实际结构

```text
[项目菜单][新建工作区][排序][搜索][文件树][待办 12][Git 3]      [自定义命令…]
[搜索输入行]                                   ← 打开搜索后才出现
▾ 📁 iris                                [+]   ← 箭头=折叠文档区  名称=会话中心  +=新会话
    ● Claude Code · xxx                        ← 工作区会话，没有分区头
    STATUS 2                             [+]   ← 名称=集合页  +=新文档
      ● 文档标题                      Backlog
    ISSUE 8 / REPORT 5 / MISC 1 / External
▸ 子工作区A                              [+]   ← 非根默认折叠（9-28 改动），不缩进
▸ 子工作区B
```

### 二、同类软件调研摘要

调研范围有三类。AI agent 工作台：Conductor、Claude Code Desktop、Codex app、Cursor 3、Zed、Warp、Superset、Vibe Kanban、Nimbalyst、JetBrains Air。文档/项目管理工具：Linear、Notion、Jira、Plane、Obsidian、Craft。IDE 和设计规范：VS Code、JetBrains、Apple HIG、Fluent。和 Iris 最相关的结论如下。

| 模式 | 典型产品 | Iris 现状 |
| --- | --- | --- |
| 工作项状态和 agent 状态各占一个位置，不共用颜色 | Conductor 用 PR 彩条表示工作项，用动画/未读点表示 agent | ✅ 已做到：左侧会话点，右侧文档状态徽章 |
| 行首状态槽宽度固定，空闲时也留位，标题不跳 | Codex #49984 提案、Zed、Vibe Kanban | ✅ 已做到（`SessionDot` 固定占位） |
| 「等你输入/审批」是最醒目的一档，单独成类 | Vibe Kanban 举手图标、Nimbalyst 的 Awaiting input、Warp 的 request 通知、Air 的 Input required | ❌ 黄点混合了空闲和等输入；聚合时工作中优先 |
| 折叠后在父节点显示子项状态汇总 | Nimbalyst 导航徽章、VS Code Activity Bar 计数、Linear 的数字/圆点 | ❌ 折叠后只剩文档数 |
| 用「跳到下一个需要关注的」代替按活动重排 | Conductor 的 ⌘⌥L；T3 Code 坚持「永不重排」；Conductor 曾修过列表乱跳 | ⚠️ 没有跳转；按 mtime 排序时可能跳动 |
| `+` 放在离内容最近的容器上，行内操作不超过 3 个，其余进右键菜单 | Zed 项目标题、Notion、Superset；VS Code UX 准则 | ✅ 基本符合（工作区 +=会话，分区 +=文档，右键菜单已补） |
| 左栏模式用互斥切换器，切换器图标带徽标 | VS Code Activity Bar、JetBrains 工具窗、Obsidian 侧栏 tab | ⚠️ 有徽标，但模式是散开的开关，Git 模式会丢 |
| 切换模式或布局时，列表状态和位置不能丢 | Cursor 3 用户最集中的抱怨；Vibe Kanban 按工作区保存布局 | ❌ 进出集合页会丢折叠和 Git 视图 |
| 全局功能放到导航树之外 | Plane 2.0 把搜索和 Inbox 移到顶栏 | ⚠️ 待办（全项目）和左栏模式按钮放在同一排 |
| 侧栏层级不超过两级，更深的内容交给内容列 | Apple HIG、Fluent NavigationView | ⚠️ 工作区 → 类型 → 文档共三级，靠平铺加集合页缓解 |
| 空区段不占位，用到时才出现 | Linear 的 Favorites | ⚠️ 每个空类型都占一行「空」 |
| 会话行显示 agent 类型图标 | Zed、Warp | ❌ 只有 Iris Agent 有标识 |
| 置顶、最近使用 | Superset、Cursor、Codex、Linear、Notion | 没有；当前规模下不急 |

**不建议照搬的做法**（符合 `优化界面` 中「业务逻辑不可能抄他们的」这一原则）：

- 会话做一级列表的侧栏，例如 Claude Code Desktop、Codex、Zed Threads。Iris 以文档为一级对象，会话依附于文档和工作区，这正是它与这些工具的区别。
- 按状态分组的看板式侧栏，例如 Conductor、Superset、Vibe Kanban。issue 状态分组已经由集合页承担，再放进主树会让同一篇文档出现两次。
- 用缩进和层级线表达嵌套，例如 Zed、VS Code 的文件树。你在 06-16 已经定了平铺，这里改用其他手段表达归属（见 V2）。文件树本身已经有层级线，保持不变。

### 三、我的判断

有优化空间，但重点不在推翻结构。Iris 现在的骨架，即工作区分组、文档为一级、会话依附、状态双槽、平铺，和调研中做得好的产品方向一致，有几处甚至做得更好，比如固定状态槽。值得做的集中在三件事：

1. **可达性（P0）**：搜索、根分类、新建工作区这三处的结果和用户的预期不一致，属于逻辑 bug。
2. **注意力调度（P1）**：§5 把左栏定为「注意力调度面板」，但目前「等你」这一档既不突出也不汇总，折叠后还会消失。这是和同类工具差距最大的地方，也是 Iris 的核心卖点。
3. **模式与记忆（P1）**：工具栏的语义分组、左栏模式的单一状态、折叠状态的持久化。

### 四、业务逻辑建议

- **B1 搜索穿透折叠（P0）。** 搜索框有内容时，临时展开含匹配项的工作区和类型分区；没有匹配的工作区整体隐藏，工作区会话不计入文档结果；显示「N 个结果」和真正的无结果状态；清空后恢复原来的折叠状态。可选：在搜索行加一个「含已完成/Backlog」开关，默认仍只搜活动文档，并在占位文字里写明。
- **B2 根工作区只看本层（P0）。** 去掉 `.iris → null` 的转换，让根和子工作区的分类范围一致。全项目聚合有两个入口：工具栏的待办（本来就是全项目），以及集合页内新增的「全项目 / 本工作区」范围切换。
- **B3 工作区模板（P0）。** 去掉「空白」模板，或者改成「自选类型、至少选一种」，这样新建结果一定能被扫描到。创建成功后自动展开并定位到新工作区。
- **B4 按注意力优先聚合（P1）。** 聚合顺序改成「等你 > 工作中 > 已退出」。前提是要有可信的「等你」信号：终端的 idle 是基于输出的启发式判断，不能直接当作「需要审批」。建议优先接入现有的 hook 链路（Claude Code 的 Notification/Stop hook、Codex hook）拿到明确的等待状态，拿不到时继续显示「空闲」，不冒充「等你」。hook 能否稳定提供这个状态，本轮没有核实。
- **B5 折叠后汇总（P1）。** 折叠的类型行和工作区标题行在右侧显示会话汇总，例如「● 2」，颜色取最需要关注的那一档。点击汇总会展开对应分区并滚动到相关文档。这样折叠时也满足「挂终端的文档不能丢」。
- **B6 左栏模式改成单一状态并保存（P1）。** 用一个 `documents | files | git` 状态替换 `rawMode` 和 `gitOpen`，放进 store。工作区和类型的折叠状态按「项目 + 工作区路径」保存在 store 中，不再放在组件局部 state。最低要求是同一窗口里进出集合页、切换模式后都能恢复；重启后是否保留可以以后再定。切换项目时清空，避免把旧项目的状态带进来。
- **B7 「下一个需要关注」（P2）。** 加一个快捷键，在挂有「等你」会话的文档和工作区之间循环跳转。不改排序，只负责跳转。
- **B8 排序防跳（P2，先观察）。** 如果实际使用中确实出现 #12 的跳动，再考虑「选中项和正在交互的行不因 mtime 变化即时移位」，或者合并排序更新。这一条先观察，不立刻实施。

### 五、视觉建议

- **V1 工具栏分区（P1）。** 只调整分组和顺序，不增减功能：

  ```text
  [📁项目▾]  [文档|文件|Git 3]              [待办 12] [自定义…]
  [🔍 筛选文档…                       ] [排序] [新建工作区]
  ```

  - 第一行：「文档 / 文件 / Git」做成一个互斥的分段控件，带明显的选中态，Git 的数字徽标保留在分段上；待办和自定义命令放在右侧。
  - 第二行：放当前模式的视图工具。在 Git 模式下换成 Git 自己的操作，或者保持占位，保证宽度不跳。
  - 想保持一行也可以：只要把模式切换做成分段控件，并让视图工具在各模式下位置固定，大部分问题就解决了。图标顺序以你的审美为准。
- **V2 不缩进也看得出归属（P1）。** 工作区之间加组间距或细分隔线，让每个工作区读起来是一组。只有嵌套或同名时，才在子工作区标题后面用灰色小字显示父路径，例如「后端 / 支付」。不加缩进，也不加层级线。
- **V3 空分区瘦身（P2）。** 去掉「空」占位行，空类型只保留标题行，计数 0 淡化显示。整个工作区一篇文档都没有时，显示一行空状态：「暂无文档 · 新建」。External 维持现在常显的约定。
- **V4 会话行补一个 agent 图标（P2）。** 在状态点后加一个 Claude / Codex / 终端的小图标，宽度固定，保证对齐。悬停时显示「最后活动时间」。仍然保持一行。
- **V5 「等你」的视觉（随 B4 一起做）。** 保持现在的点尺寸和槽位不变（遵守对齐原则），只让「等你」档醒目一些，比如更饱和的颜色或轻微的呼吸动画。「工作中」保持静态，避免满屏都在动。
- **V6 文案（P2，可以马上做）。** 把内部术语换成用户语言：「新建工作区」「打开项目根会话」「打开工作区会话」。

## 2026-10-25 补充：B4「等你输入/审批」在现有架构下的可行性

用户追问：现有架构是否做不到这一点。核对代码后的结论是：**现有架构确实做不到可信地区分，上文 B4 写的「接入现有 hook 链路」不准确，需要更正。** 不过这个状态可以通过新增链路得到，并非结构性的不可能。

### 现状（代码依据）

- **终端会话的状态全部来自输出时序。** `src/main/terminal/session-activity.ts` 的 `SessionActivityController` 在有输出时标记 active，静默超过阈值后回到 idle，另有启动、resize、输入的静默窗口。它对 agent 的语义一无所知：「思考间隙」「跑完了」「弹出审批」「等用户输入」都表现为一段时间没有输出，全部落成 idle。
- **现有 hook 是单向的。** `src/main/agent-injection.ts` 只为各 CLI 安装 `SessionStart` hook。hook 执行 `~/.iris/focus-context.ps1`，把上下文注入给 agent。没有从 agent 回到 Iris 的通道：hook 无法通知 Iris，主进程也没有监听端口或 named pipe。
- **主进程能看到全部终端字节。** 每个会话都有一个 headless xterm 镜像（`terminal-mirror.ts`），目前只订阅了 OSC 0/2 标题变化（`terminal-session-manager.ts` `handleTitle`），没有处理 OSC 9 / OSC 777 通知或 BEL。
- **Iris Agent 是进程内实现，状态完全可控。** 但现有状态枚举里没有「等待用户审批」。`waiting-tool` 的含义是工具正在执行（`session-manager.ts` 设置这个状态时，tool operation 处于 `running`），不是等人确认。

### 可以走的路

| 方案 | 做法 | 能得到什么 | 代价与风险 |
| --- | --- | --- | --- |
| A. 反向 hook 通道 | 主进程开一个本地 IPC 端点（Windows 用 named pipe，其他平台用 Unix socket），每个会话注入 `IRIS_SESSION_ID` 和一次性 token。为 Claude Code 额外安装事件 hook，hook 脚本把事件报给 Iris。事件包括：Notification（权限请求、空闲等待等类型）、Stop、UserPromptSubmit；如有 PermissionRequest 也一并接入。 | 最可信：明确区分「等审批 / 等输入 / 本轮完成 / 正在处理」 | 新增 IPC 面，需要 token 鉴权和会话归属校验；hook 安装和治理面扩大，历史上 hook 有过多次损坏（`2026-08-06-hook功能已经完全损坏`、`codex-hook的问题`）；脚本目前只有 PowerShell 版；每种 CLI 支持哪些事件需要逐个核实。Codex hook 是否有审批类事件未核实。 |
| B. 终端通知协议 | 在镜像上注册 OSC 9 / OSC 777 处理器，可选也处理 BEL。把 agent 自带的「需要注意」通知转成会话状态。 | 不需要 hook，不需要新开端口 | 依赖用户在 CLI 中开启终端通知，例如 Claude Code 的通知渠道设置、Codex 的 TUI 通知（两者的具体配置名和事件覆盖范围未核实）。语义通常比 hook 粗，可能只能得到「需要注意」，分不清审批和输入；区分时往往要解析通知文本，比较脆弱。 |
| C. 识别屏幕内容 | 匹配「Do you want to proceed?」之类的 TUI 文本 | 不推荐 | 随 CLI 版本、语言、主题变化而失效，误报风险高 |
| D. Iris Agent 原生支持 | 如果 Iris Agent 以后增加工具审批门，就新增一个 `awaiting-approval` 运行态 | 自有会话完全准确 | 只覆盖 Iris Agent，覆盖不了 Claude Code / Codex 终端 |

### 修正后的建议

1. **B4 先做不依赖新信号的部分。** 聚合时不再让「工作中」掩盖「空闲」；同一锚点下如果有空闲会话，在汇总里单独计数。UI 上仍然只叫「空闲」，不冒充「等你」。

## 2026-10-25 补充二：OSC 9 / 777 是否比静默可靠？

用户追问 OSC 9 / 777 是否真的比静默可靠。查阅官方文档后的结论是：**不能作为主信号。上一节方案 B 需要更正，首选改为 OSC 7501。**

### OSC 9 / 777 的问题

两者都是**一次性的提醒事件**，不是持续的状态：

- **依赖终端识别。** Claude Code 默认只在 Ghostty、Kitty、iTerm2 中发桌面通知。在其他终端（Iris 属于这一类）里，用户必须手动设置 `preferredNotifChannel`；即使设置了，可选的 `terminal_bell` 也只是一个不带语义的 BEL。
- **依赖焦点。** Claude Code 文档写的是「and you appear to be away from the terminal」时才触发。Codex 的 `tui.notification_condition` 默认 `unfocused`，可选 `osc9` / `bel`。用户正看着某个终端时它不会发；Iris 里多个隐藏终端的焦点语义也不清楚。
- **只有开始，没有结束。** 提醒只表示「开始等你了」，不会告诉 Iris 什么时候「不等了」。清除状态还得靠输入或新输出来推断，又回到了启发式。
- **类型靠文本区分。** 审批、提问、本轮完成要从通知文案里解析，不稳定。

所以它误报少，但漏报多，清除也不可靠。和静默启发式相比，只是失效方式不同，整体并不更可靠。

### 更合适的是 OSC 7501（Program Status Protocol）

- **持续状态，语义完整。** 状态有 `idle` / `working` / `done` / `blocked` / `error`。`blocked` 还带 `kind=permission|question|auth`，正好区分「等审批」和「等输入」。每条报告完整替换上一条；进程退出时终端必须丢弃 `working` / `blocked`，`done` / `error` 保留。
- **Claude Code 不需要用户做任何配置。** 官方 terminal-config 文档写着「There is nothing to turn on」，要求 v2.1.295 及以上。前提是终端声明支持：程序发 `OSC 7501 ; ?` 探测，终端回 `OSC 7501 ; ? ST`。在支持的终端里，Claude Code 会去掉标题前面的状态字形。
- **和 Iris 现有架构贴合。** 主进程的 headless 镜像本来就负责协议应答（`terminal-protocol.ts` 的 `reply` 通道，已经在应答颜色查询和配色方案查询），`terminal-mirror.ts` 也已经暴露了 `registerOscHandler`。实现只需四步：注册 7501 处理器，应答探测，按会话保存记录，把记录映射成会话状态（新增 `blocked`、`done`）。不需要 hook，不需要新开端口，也没有焦点问题。
- **不支持 7501 的 agent 继续走现有的输出静默启发式**，UI 上只叫「工作中 / 空闲」，不冒充「等你」。

### 风险

以下多数来自二手资料，未逐项核实：

- **协议非常新。** 规范于 2026-10-06 发布，当前修订 0.4，不是标准组织的文档。
- **有版本门槛。** Claude Code 2.1.295 以上才支持，有资料称 npm stable 标签当时还停在 2.1.292。Codex 据称 10-09 已合入 main，但稳定版尚未包含。
- **存在误报先例。** 发送方可能报错状态，有资料提到其他 agent 在仍有工作时报了 `done`。
- **没有持久的会话 ID。** 跨 `/clear`、`/resume` 无法关联。这一点对 Iris 影响不大，因为 Iris 按 PTY 会话归属状态。
- **探测应答的时机需要验证。** 主进程镜像和渲染端 xterm 并存时，应答必须只来自主进程一处，并且要赶在 Claude Code 的探测超时之前。
- **另有一种做法：从 OSC 0/2 标题里识别 Claude Code 的状态字形。** Iris 已经能收到标题，但这正是 7501 想取代的脆弱做法，而且 Iris 一旦声明支持 7501，Claude Code 就不再加这个字形。不推荐。

### 修正后的顺序

1. **先做 7501 原型。** 用 Claude Code 2.1.295+ 实测，确认能收到 `blocked` / `done`，对误报和漏报做手工记录，再决定是否上 UI。
2. **hook 反向通道（上一节方案 A）作为补充。** 只在需要覆盖旧版本、或需要 PermissionRequest 这类精确事件时再做。
3. **不采用 OSC 9 / 777 作为状态来源。**

## 2026-10-25 补充四：状态徽章里的圆点是否需要

用户问：状态徽章（如 `Done`）左侧的小圆点是否必要，还是只占空间、不提供信息。

### 现状

`StatusBadge` 的所有官方状态都使用 `soft` 模板（`status-badge.tsx`）。`badge.tsx` 中 `hasDot()` 对 `soft` 返回 true，所以每个徽章都会渲染一个 6px 实心圆点，圆点和文字之间有 `gap-1`（4px）。圆点、背景（14% 着色）和文字（72% 着色）用的是同一个 `--badge-color`。这是 `2026-08-11-状态徽章的视觉效果不统一` 中明确定下的样式：「每个状态都带 6px 实心圆点」。

### 判断：建议去掉，至少在左栏去掉

1. **不提供新信息。** 圆点的颜色与胶囊底色、文字颜色完全相同，也不随状态改变形状。状态已经由文字和底色两路表达，圆点是第三次重复同一种颜色。08-11 那轮本身也要求「圆点和色相不作为唯一信息通道」。
2. **它原本的作用已经消失。** 08-11 之前，状态混用 `solid`、`outline`、`dot`、`soft` 四种结构，圆点是区分结构的手段之一。统一成单一的 soft pill 之后，所有徽章都有圆点，它就不再区分任何东西。
3. **和左栏的会话圆点冲突，这是最主要的理由。** 文档行最左侧的 `SessionDot` 是 8px 圆点，蓝（foam）表示工作中，黄（gold）表示空闲。徽章里的圆点也是圆点，而且颜色撞车：`In Progress` 用 foam，与「会话工作中」同色；`On Hold` 用 gold，与「会话空闲」同色。于是同一行出现两个同形、同色、含义不同的点，正好违背调研中「工作项状态和 agent 状态分槽、不共用视觉语言」的原则。在 Iris 里，「圆点」这个形状应该留给会话状态。
4. **占空间。** 每个徽章多出约 10px（6px 圆点加 4px 间距）。左栏 `sm` 徽章本来就挤占标题宽度，例如 `In Review` 和 `In Progress`，去掉圆点后标题能多显示一到两个字。

它目前唯一的作用，是让胶囊看起来更「像状态」（Notion 的状态属性用的就是这种样式）。但 Iris 的这些位置上，除了状态之外没有别的胶囊，不需要靠圆点来区分。

### 方案（未实施）

- **推荐：全局去掉状态徽章的圆点。** 只改 `badge.tsx` 中的 `hasDot`，让 `soft` 不再带点，或者新增一个不带点的 `pill` 变体，由 `StatusBadge` 使用。左栏、Issue 面板、文档头部、报告时间线会同步变化，保持 08-11 定下的「同一结构」约定。固定高度、内边距、hover 和 focus 规则都不变。
- **备选：只在左栏的 `sm` 尺寸去掉。** 能保留其他位置的现状，但同一组件在不同位置结构不同，违背 08-11 的统一原则，不推荐。
- **不建议：换成 Linear 那样随状态变形的图标**（空心圆、半圆、对勾等）。它确实能提供形状信息，但又在左栏多加了一种图形语言，会和会话圆点竞争。和 Iris「克制、去冗余」的方向不一致。

- **几何上确实有问题。** 胶囊两端是半圆，半径等于高度的一半：`sm` 为 19px 高、半径约 9.5px，`md` 为 22px 高、半径 11px。但当前左侧内边距只有 6px（`sm`，`px-1.5`）和 8px（`md`，`px-2`），都小于半径，文字的起点落在半圆弧以内。原来圆点正好填在这段弧里，把问题遮住了；去掉圆点后，首字母会贴着弧线，视觉上偏挤、偏左。
- **如果保留胶囊，内边距至少要接近半径**，`sm` 约 10px、`md` 约 12px。这样每个徽章两侧会多出 8px 左右，去掉圆点省下的宽度又被吃回去了。
- **圆角矩形可以保持现在的内边距**，文字不再落进弧区。去掉圆点省下的宽度也能完整留给标题。

**和 Iris 现有元素的一致性：**

- 左栏文档行的选中和 hover 底色是 `rounded-sm`（`calc(var(--radius) - 4px)`，即 4px）。工具栏上待办和 Git 的计数小徽标也是 `rounded-sm`。徽章用同样的半径，嵌在行里会更协调：内层圆角不大于外层。
- 圆角矩形和会话圆点形状差异更明显，进一步区分「文档状态」和「会话状态」两套视觉语言，和上面去掉圆点的理由一致。
- 这种紧凑的圆角矩形状态标签，在信息密集的界面里很常见，比如 Jira 的 lozenge、VS Code 的计数徽标。

**方案（未实施）：**

- 高度、字号、内边距、hover 加深和 focus 外轮廓保持 08-11 定下的数值不变。改动后需要在窄左栏和 Issue 面板里看一眼，确认 6px / 8px 内边距在圆角矩形下是否合适，必要时 `md` 可以微调到 `px-2.5`。

## 2026-10-25 补充五：子工作区平铺还是切换

用户问：子工作区是平铺好，还是切换好。

### 判断：保持平铺，不改成切换器

1. **切换器会让其他工作区的会话从左栏消失。** 左栏定位为注意力调度面板，「挂终端的文档不能丢」是用户反复坚持的原则。改成切换后，当前工作区以外的会话只能靠切换器上的汇总徽标提示，看不到具体是哪篇文档、哪个会话在等，用户要切过去才能找到。
2. **切换层已经有了。** 项目级切换有项目菜单、最近项目和多窗口。在同类产品里，切换器一般用于真正隔离的上下文，例如 Slack 的 workspace、Craft 的 Space、Linear 的 workspace（组织级）。同一项目内的分组则普遍平铺、可折叠，例如 Linear 的 teams、Notion 的 teamspaces、Conductor/Superset/Codex 按 repo/项目分节。Iris 的子工作区对应后一类。再加一层切换，会形成「项目切换 + 工作区切换」两级。
3. **切换会引入新的全局状态，耦合面变大。** 「当前工作区」会和焦点文档、会话归属、集合范围、新建文档的默认位置互相纠缠。例如：打开的文档不属于当前工作区时怎么显示？从待办跳到别的工作区的文档时，要不要自动切换？平铺没有这些问题。
4. **跨工作区操作需要同时看到多个工作区**，比如待办（全项目）、搜索、拖拽文档路径，以及同时盯几个工作区的会话。
5. **规模不需要切换。** 本项目实际只有 3 个工作区：根、`iris-agent`、`private`。

### 平铺需要补上的部分

切换器的好处是专注和不拥挤。平铺可以用轻量方式拿到这两点：

- **折叠后的工作区标题行就是「切换器条目」。** 非根默认折叠已经实现。再加上 B5 的折叠汇总（文档数加会话状态），折叠状态下就是一个带状态的工作区列表，点开即进入。
- **B1 搜索穿透折叠是前提**，否则默认折叠会让子工作区的内容搜不到。
- **V2 嵌套归属的表达**：用组间距或细分隔线，同名或嵌套时显示父路径，继续不缩进。
- **B6 折叠状态持久化**：用户手动展开、收起的结果要保留下来。

### 什么时候再考虑

工作区数量明显增长（比如超过 8 到 10 个），或者实际使用中频繁滚动寻找时，优先加下面两种轻量手段，而不是改成硬切换器：

- **聚焦模式**：在工作区右键菜单里加「只看此工作区」，左栏顶部显示「聚焦：xxx ✕」。这只是临时的视图过滤，不改变数据，不影响会话。其他工作区的会话汇总显示在这条提示上，保证不丢。
- **快速跳转**：用快捷键打开工作区模糊搜索，跳到对应分组并展开。

## 2026-10-25 补充六：左栏展开状态是否需要持久化

用户问：左栏的展开状态需不需要持久化。

### 现状

- 工作区的文档区折叠由 `WorkspaceSection` 的 `useState(depth === 0)` 管理，类型分区折叠由 `TypeSection` 的 `useState(true)` 管理，两者都是组件局部状态。文件树用的是 `RawTree` 局部的 `expandedPaths: Map<path, boolean>`，没有记录的路径回落到默认值。
- 因此，进出集合页（`DocumentCollectionShell` 会换掉整棵组件树）、切换项目或重启后，这些状态都会恢复默认。Git 视图开关（`gitOpen`）也是局部状态，同样会丢。
- 项目里已有一套持久化机制：`src/renderer/lib/view-prefs.ts`。它把面板显示偏好存到 localStorage，明确不写进 `.iris/`，集合面板的分组折叠已经在用它。

### 判断：需要持久化，但要分层，并且只保存用户偏离默认值的部分

| 状态 | 同一会话内保留 | 重启后保留 | 说明 |
| --- | --- | --- | --- |
| 工作区文档区展开/折叠 | 必须 | 建议 | 默认折叠子工作区以后，用户手动展开的那个工作区就是常用工作区；每次重启都要重新点开，体验很差 |
| 类型分区展开/折叠 | 必须 | 建议 | 例如长期折叠 `misc`、`report`，属于稳定偏好 |
| 文件树目录展开 | 必须 | 可选 | VS Code 的 Explorer 会按工作区恢复展开状态。可以以后再做，需要限制条数 |
| 左栏模式（文档/文件/Git） | 必须 | 可选 | 这一项的成本很低 |
| 搜索词、搜索框开关 | 可以保留 | 不保存 | 属于临时操作 |
| 搜索时的临时展开（B1） | 不写入 | 不写入 | 必须和持久化状态隔离，清空搜索后恢复原状 |
| 滚动位置 | 建议 | 不保存 | 重启后内容会变化，恢复滚动位置不可靠，意义也不大 |

「同一会话内必须保留」这一列本身就是一个 bug 修复，即前文 #6 / B6。「重启后保留」是体验增强。

### 设计要点

1. **只存覆盖值，不存完整状态。** 键为路径，值为 `true` 或 `false`；没有记录的路径使用默认规则（根工作区展开，非根折叠，类型分区展开）。这和 `RawTree` 现有的 `expandedPaths` 语义一致。新出现的工作区自动按默认显示；路径改名或被删除后，旧记录自然失效，写入时再顺带清理不在当前 scan 中的键。
2. **存在本机，不进 `.iris/`。** 这是个人的界面状态，不是项目数据。写进 `.iris/` 会污染 git，还会同步给协作者。复用 `view-prefs`，或者同类的 localStorage store。
3. **键名带上项目绝对路径。** 例如 `项目根 + 工作区相对路径 + 类型`，避免把 A 项目的状态带进 B 项目。多窗口打开同一项目时互相覆盖，以最后一次写入为准，这可以接受。
4. **状态不放在组件里，提到 store。** 这样组件卸载（进出集合页、切换模式）就不会丢失状态。这是同一会话内保留的前提。
5. **「定位到文档」时展开并持久化。** 从待办、集合页或文内链接打开一篇文档时，如果它所在的分区是折叠的，就自动展开以露出这一行，并把展开结果记下来，和 VS Code 的 reveal 行为一致。搜索造成的展开只是临时的，两者不同。
6. **持久化的折叠不能挡住注意力。** 即使某个分区长期折叠，B5 的折叠汇总也要显示其中的会话状态，保证「挂终端的文档不能丢」。
7. **右键菜单里已有的「折叠文档区 / 展开文档区」**，同样写入覆盖值。

### 实施顺序

1. 把工作区和类型的折叠状态提到 store，保证同一会话内不丢，并和 B6（左栏模式单一状态）一起做。
2. 接入 `view-prefs`，实现跨重启持久化，并清理失效键。
3. 文件树展开状态的持久化，按需再做。
