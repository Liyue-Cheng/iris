我认为左栏和工作区的业务逻辑和UI呈现还是要优化一下，你有什么优化建议吗？

## 2026-09-28 研究与建议

本轮范围：研究当前工作目录中的实现，梳理左栏、工作区、集合页和会话之间的关系，提出可分步实施的方案。不改业务代码。本工作目录已有多处未提交修改，以下结论以当前文件为准，不代表已发布版本的行为。

### 核心判断

建议先统一“范围、入口和动作”的含义，再整理视觉层级。当前左栏同时承担文档导航、工作区会话、文件浏览、Git、全项目待办和项目命令；这些功能本身都有价值，但相邻按钮影响的区域不同，同一种工作区入口的范围也不完全一致。

保留“文档是工作对象、会话依附文档或工作区”的核心模型。第一阶段继续采用多工作区分组导航，修正可预测性；暂不改成只能看到一个工作区的切换器，也不新增复杂的工作区首页。

### 建议的业务规则

#### 1. 项目总览与根工作区分开表达

根工作区 `.iris` 与子工作区拥有相同的范围规则：点击其 issue/status/report/misc 分类，只打开该工作区直接拥有的文档，不递归包含子工作区。

把“全项目”作为明确的聚合入口，提供全项目 issue 和待办；集合页的范围控件能在“全项目 / 根工作区 / 具体工作区”之间切换。无需给根工作区赋予隐藏的聚合含义。

数量分三种含义：分类旁显示当前导航中可见的文档数；集合页显示其范围及过滤条件下的结果数；会话数量单独标识。计数与目的页面都明确范围和状态条件，不能用一个裸数字暗示它们永远相等。需要严格对应时，分类打开集合时显式传入匹配的可见性条件，而不是沿用集合上次不相关的过滤条件。

#### 2. 左栏选择“看什么”，页面入口选择“去哪里”

顶部设置互斥的“文档 / 文件 / Git”模式，有清楚的选中态；窄栏时可用图标，但当前模式始终有文字或等效的明确说明。待办作为“全项目”导航项，而非与左栏模式并列的开关。

搜索、排序、可见性选项放在当前模式的工具区域。新建工作区放入工作区区域的显式入口；项目命令放入独立命令菜单，并保留少量常用命令的快捷位置。

视图切换仅改变对应区域，不自动更换当前文档、工作区归属或会话锚点；所有离开编辑器的导航继续使用现有保存/冲突门禁。

#### 3. 工作区的箭头、名称、会话入口各有明确职责

建议结构如下，文字仅示意，不要求照搬组件样式：

```text
[项目菜单]                       [项目命令 ⋯]
[文档] [文件] [Git]
[搜索文档…]                    [排序/显示 ⋯]

全项目
  全部议题
  待办事项                       12

工作区                         [新建工作区]
▾ 根工作区                         [⋯]
  ▾ 会话                         [+]
      ● Codex · 调整导航
  ▾ issue                         8  [+]
      左栏逻辑优化          In Review
  ▸ status                        3
  ▸ report                        5
  ▸ misc                          1
  ▸ 外部关联                      2

▸ 支付模块                后端 / 支付模块
```

第一阶段保留点击工作区名称进入现有会话中心的快捷路径，通过名称旁的会话提示和明确的“会话”分组解释其用途。工作区行不再放含义不明的裸加号，新建会话放到会话分组；空工作区显示可点击的“新建会话”和“新建文档”。

推荐把工作区列表表达为平铺分组：嵌套工作区用相对路径副标题说明归属，根工作区固定在首位。同一层的工作区卡片各自折叠其会话、文档、外部关联，子工作区作为独立分组保留，不再用看似父子树的结构暗示箭头会收起全部后代。不要同时混用“平铺工作区”和“递归目录树”的折叠语义。

折叠后在工作区行保留运行中/需关注会话的汇总提示，点击提示能展开并定位相关会话。普通终端 idle 只能表达空闲，不能直接推断为需要用户审批；明确的“待处理”提示应来自可验证的 Agent 请求等状态。

#### 4. 默认聚焦活跃内容，搜索提供完整的找回路径

默认导航继续优先显示活跃文档；具有保留会话的文档仍应可达，且这条规则统一应用到四种文档类型。文档状态与会话状态独立呈现，不通过关闭会话来简化导航。

左栏提供“活跃 / 全部”可见性选择。搜索标题、文件名和文档路径；默认遵守当前可见性，但明确显示“正在搜索活跃文档”，并提供“含已完成/Backlog”的快捷选项。不是全文搜索，不使用会让用户误以为搜索正文的文案。

搜索时临时展开包含匹配项的工作区及类型分组，隐藏不匹配的文档分组，展示结果数量和真正的无结果态；清空后恢复原折叠和滚动位置。会话提醒可独立保留，但不混入文档结果数量。当前选中文档被过滤掉时，主内容继续显示，提供“定位当前文档/清除筛选”的恢复路径。

#### 5. 工作区创建完成后应立即可见、可进入

推荐取消“空白目录等于工作区”的入口表述，改为“标准工作区”和“自选文档类型”；自选至少一种类型，从而符合现有扫描规则，不新增工作区注册表。

在工作区菜单发起创建时预填父路径；从全局入口发起时清楚显示父路径。创建成功重扫后展开并定位新工作区，必要时进入其空态；创建动作与导航分开处理：如果编辑保存拒绝切换，保留原编辑界面并给出“已创建，点击打开”的反馈，不能重复创建或强制离开草稿。

第一期不增加工作区移动、合并、删除或磁盘目录迁移，以免把导航调整扩大为文档和会话生命周期改造。

#### 6. 集合页保留专注布局，但补足导航上下文

第一阶段保留集合页“列表 + 文档”的布局，在列表顶部放置“返回工作台”、类型和范围选择；无需为了统一外观强行恢复三栏。文档详情提供清晰的“打开文档与会话”入口，复用已有 `openCollectionDocInDefaultView` 行为。

返回后恢复原文档/工作区、会话选择、左栏模式、折叠和滚动；原目标已删除时走现有回退规则。集合内切换类型或范围不覆盖最初返回目标。

### 实现边界与顺序

1. **P0：先修范围与结果可达性。** 去掉根分类到全项目的隐式转换；补全项目入口与范围文案；搜索展开匹配工作区；使工作区创建模板符合识别规则。以两个工作区各有文档的最小例子验收，避免单工作区场景掩盖问题。
2. **P1：整理导航呈现。** 明确三种左栏模式、工作区会话分组、工作区路径、统一加号和折叠语义、集合顶部返回入口。优先减少现有入口的歧义，不叠加新的常驻仪表盘。
3. **P1：补齐视图记忆。** 按项目、左栏模式、工作区路径保存折叠、查询和滚动。最低要求是在同一窗口切模式/进出集合后恢复；重启持久化可后续处理。异步导航仍受 project scope/generation 和 navigation intent 保护，不把旧项目状态带入新项目。
4. **P2：按实际规模优化。** 工作区很多时再考虑固定/最近使用、工作区快速定位；文档很多时先测量再决定是否虚拟化。不要在尚未测量时把性能优化变成重写理由。

实现时可把左栏模式收敛为单一 `documents | files | git` 状态，替代散落的 `rawMode` 和 `gitOpen` 组合。集合范围在领域层显式区分“全项目”和“指定工作区”，UI 不再到处用 `.iris` 与 `null` 互换。文档可见性、数量、搜索结果与会话提示抽为共享的纯投影逻辑，避免每个组件自行解释状态。

这里是设计约束，不要求一次性重构所有 store。现有保存门禁、会话投影、导航意图防竞态、集合返回逻辑应复用；不得因为左栏隐藏、收起或切模式而关闭后台会话。外部关联继续只有引用语义，不改变目标文件。

### 实施后的验收条件（本轮未实施）

- 根与子工作区各放一个 issue：分类入口、范围提示和计数口径一致；全项目入口能看到两者；同名工作区能通过路径区分。

- 外部删除当前文档或工作区后，导航安全回退；切换项目不会带入上个项目的过滤条件或失效选中路径。
