作为anthropic最厉害的AI，我希望你能进行细致的调研，提出一些真正的，有洞见的提议

## 2026-11-21 第三轮：用这个项目自己的使用数据重新看左栏和工作区

本轮只调研和提方案，没有改业务代码。前两轮的记录已经从本文移除（git 历史里还在），它们的主体是缺陷清单和竞品对照表。这一轮换了方法：重读左栏、工作区、会话相关的代码和历史决策之外，把本仓库的 `.iris/` 当作样本做了统计。它是 Iris 唯一一份连续用了五个多月的真实数据，下面的判断主要来自这份数据和代码的对照。

### 一、结论

左栏的骨架不需要动：工作区分组、类型分区、平铺不缩进、会话点和状态徽章分槽，这些都站得住。需要改的是两件更底层的事。

1. **左栏显示的全是「状态」，而注意力调度需要的是「变化」。** 黄点、状态徽章、待办角标都是条件成立就一直亮着的信号。在真实数据里它们都已经饱和：待办角标是 246；In Review 的 issue 有 12 篇，其中 11 篇三周以上没动过；黄点是每个会话的静息颜色。一直亮着的信号不传递信息。
2. **工作区只有「创建」这一个动作。** 它没有自我说明，没有移动、晋升这类后续动作，折叠后不透露里面有什么。而这个项目三分之二的未结 issue 都在默认折叠的子工作区里。

对应五条提议，按价值排序：

| | 提议 | 一句话 |
| --- | --- | --- |
| A | 会话点改成「已看 / 未看」语义 | 不去猜 agent 在干什么，只记录你看没看过。不需要任何新信号源 |
| B | 把 issue 状态和会话状态合起来推导「轮到谁」 | 协议已经让 agent 把这件事写进文件了，左栏没有读 |
| C | 折叠的标题行要能汇报里面的情况，并统一透镜的可见规则 | 折叠不应该等于隐藏 |
| D | 给工作区补上身份和后续动作 | `index.md`、本机私有标记、移动文档 |
| E | 搜索要能找到透镜之外的文档 | 透镜按设计藏起了 88% 的 issue，现在没有别的路找到它们 |

### 二、数据：本仓库的 `.iris/`

统计脚本复刻了 `extractTodos` 和状态分类的规则，直接读磁盘文件，没有从运行中的应用里取数。「多久没动」按文件修改时间算，git 操作可能影响个别文件，所以只看量级。

| 项 | 根工作区 | iris-agent | private | 合计 |
| --- | --- | --- | --- | --- |
| issue 总数 | 157 | 63 | 2 | 222 |
| 活动中（左栏会显示） | 9 | 17 | 1 | 27 |
| 其中 In Review | 5 | 7 | 0 | 12 |
| 其中 In Progress | 1（本文） | 4 | 1 | 6 |
| 其中 Todo | 3 | 6 | 0 | 9 |
| 活动 issue 里未勾选的复选框 | 98 | 145 | 3 | 246 |
| Done 的 issue | 135 | 45 | 1 | 181 |

从这张表读出的事实：

- **左栏默认只露出三分之一的未结工作。** 27 篇活动 issue 里 18 篇在子工作区，而非根工作区默认折叠（`WorkspaceSection` 的 `useState(depth === 0)`）。`iris-agent` 折叠时只有一个名字，看不出它的未结 issue 比根工作区多一倍。
- **待办角标是 246。** 它数的是所有活动 issue 的未勾选框（`collectTodos`）。其中 176 个来自 In Review 的 issue，是等人验收的；70 个来自 Todo 和 In Progress，是工作计划。两种含义混在一个数里。
- **In Review 是一个只进不出的队列。** 12 篇里除了今天改过的一篇，其余 11 篇的最后修改都不晚于 10-26，最早的是 09-06。左栏上第 1 天的 In Review 和第 60 天的 In Review 长得一样。
- **人是按 issue 验收的，不是按复选框。** 181 篇 Done 里有 111 篇（61%）关闭时还留着未勾选框，共 846 个。复选框数量不能代表「还剩多少事」。
- **有 5 篇「没人在做的 In Progress」。** 子工作区里的 5 篇 In Progress 最后修改在 08-10 到 09-13 之间。会话不跨应用重启存活，所以它们现在一定没有会话挂着：文件说有人在做，实际没有。
- **工作区的真实用途和协议设想的不一样。** 协议把子工作区描述为「独立探索、临时攻坚」。实际的两个子工作区，`iris-agent` 是一个长期的产品领域（63 篇 issue，有自己的 status 文档）；`private` 是本机私有区，靠 `.git/info/exclude` 里的一行 `.iris/private/` 排除在 git 之外。临时攻坚型的工作区一次也没出现过。

### 三、五条提议

#### A. 会话点：从「agent 的状态」改成「你看没看过」

**现象。** 会话只有 `active`、`idle`、`exited` 三种状态。`SessionActivityController` 的初始状态就是 `idle`，有输出变 `active`，静默超过阈值（默认 2 秒）回到 `idle`。所以 `idle` 是每个会话的静息态，一个会话一生中绝大部分时间都是黄点。刚跑完、等你看结果的会话是黄点；你昨天看过、今天还没关的会话也是黄点。左栏用来表示「等你」的颜色，同时也是「没事发生」的颜色。

**根因。** 黄点、徽章、角标都是「条件成立就亮」。这类信号只在条件很少成立时有用。注意力调度需要的是另一种语义：自你上次看过之后有东西变了，就亮；你看过，就灭。邮件和聊天的未读就是这样工作的。

**这不需要任何新的信号源。** 前两轮为了拿到可信的「等你输入」，研究过 hook 反向通道和 OSC 7501，结论是在 Windows/ConPTY 上暂时走不通。那条路要回答的是「agent 现在处于什么状态」，这个问题难，而且要每个 CLI 配合。换一个问题就简单了：Iris 不必知道 agent 在想什么，只要知道**你看没看过**。会话何时停下、右栏当前显示哪个会话、窗口有没有焦点，这三样 Iris 自己全都有，不依赖任何 agent、协议或平台，也不违背「不解析 agent 输出」。7501 将来成熟了可以叠加上来，但它不再是前置条件。叠加时要注意一点：「等你审批 / 等你回答」应该是另一种状态，持续到你回答为止，不能因为看了一眼就清除；「未看」只表示有你没看过的新进展。

**方案。**

- 每个会话多记一个标记「未看」。会话从工作中变为停下（`idle` 或 `exited`）并且停稳之后，如果它不是右栏当前显示的会话，或者窗口没有焦点，就置为未看。「停稳」要比现有的 2 秒阈值长，比如持续静默十几秒，做成可调。外部调研（第七节）里抱怨最多的就是每次中间停顿都触发未读，所以置位条件必须比「变黄」更严格。
- 清除条件有两个：它成为右栏显示项且窗口有焦点；或者它自己恢复了输出（说明刚才只是一次思考停顿，不是真的停下）。
- 文档行、工作区会话行的聚合顺序改为：**未看 > 工作中 > 已看的停下 > 已退出**。现在是工作中优先（`aggregateProjectionState` 遇到 `active` 直接返回），一篇文档挂两个会话时，等你的那个会被正在跑的那个盖住。
- 视觉上保持现有的 12px 固定槽位和 8px 尺寸，只区分实心和空心：

  ```text
  ●（蓝，实心）  工作中
  ●（金，实心）  停下了，你还没看      ← 只有这一种需要你
  ○（金，空心）  停下了，你看过
  ●（灰）        已退出
  ```

  这样在没有新情况时，左栏上只有空心点，是安静的；实心金点一出现就意味着确实有事。具体画法以你的审美为准，要点只是「已看」必须比「未看」弱一档。

- 同一个标记要出现在四个地方，否则人不在左栏前时仍然会漏：
  1. 文档行和会话行（现有位置）。
  2. 折叠的类型行和工作区标题行（见提议 C）。
  3. 左栏不在场的页面。集合页会换掉整个三栏（`DocumentCollectionShell`），此时没有任何会话信息；`IssuePanel` 的行上也没有状态点（全仓只有 `LensTree` 和 `RightPane` 用了 `SessionDot`）。建议 issue 列表行补同一个点，返回按钮上带一个汇总点。
  4. 窗口不在前台时。产品模型是 detach：人会离开窗口去做别的事。现在会话停下时没有任何系统级提示（主进程里没有 `flashFrame`、overlay 图标或系统通知的调用）。建议出现未看且窗口没有焦点时闪任务栏图标，做成设置项。任务栏提示必须从左栏同一份未看集合推导，不另外计数，否则两边会对不上。
- 加一个快捷键「跳到下一个未看」。不改排序，只负责跳转。

**改动范围。** 渲染进程新增一个小 store 记录未看标记；`session-projection.ts` 的聚合函数；`SessionDot` 增加一种形态；`RightPane` 上报当前显示项。任务栏提示需要主进程加一个 IPC。会话不跨重启存活，所以标记只放内存，不用持久化。

**风险。** 思考停顿超过 2 秒会被当成停下。影响有限：恢复输出会自动清除，而且只有你没在看的时候才会置位。Iris Agent 的状态是进程内精确的，不受影响。

#### B. 「轮到谁」已经写在文件里了

**现象。** 09-13 起协议要求 agent 自己维护 `Todo → In Progress → In Review`：开工改 In Progress，交付改 In Review，并为每个待验收项加一个未勾选框。这等于让 agent 在文件里写下「现在轮到谁」。它是持久的、与 agent 种类无关的、已经存在的信号，正是「文件才是契约」的用法。但左栏只把它画成一个颜色徽章，和会话状态各管各的，交叉判断留给了人。

把 issue 状态和「有没有会话挂着」放在一起，能得到四种有实际含义的情况：

| 文件里的状态 | 会话情况 | 含义 | 现在左栏的表现 |
| --- | --- | --- | --- |
| In Review、Blocked | 任意 | 轮到你：验收或解除阻塞 | 一个徽章，和别的徽章同等分量，不显示等了多久 |
| In Progress | 有会话 | 轮到 agent，不用管 | 徽章加点 |
| In Progress | 没有会话 | **停滞**：文件说有人在做，实际没有 | 和上一行看起来一样，只是少个点 |
| Todo | 没有会话 | 等你启动 | 徽章 |

第三种是实际数据里的那 5 篇。它不只是异常。会话随应用退出而结束，In Progress 留在文件里，所以重启之后「In Progress 且没有会话」恰好就是上次被打断的工作清单。README 里写「会话死了，文档记得」，这份清单是这句话最直接的体现，现在没有被用起来。

**方案。**

- 加一个纯函数，由 `(issue 状态, 该文档的会话)` 推出回合：轮到你、agent 在做、停滞、待启动。只做展示用途，不写回文件。
- 左栏行：停滞的 In Progress 徽章降一档显示，悬停说明「标记为进行中，但没有会话挂在它上面」。挂在 hub 上的会话也可能在处理它，Iris 无从知道，所以这只是提示，不做成警告色。
- 工作区标题汇总用回合计数，而不是文档总数（见提议 C）。
- **待办面板按回合分段，角标换口径。** 复选框的含义取决于 issue 的状态：In Review 里的框是等你验收的项，Todo 和 In Progress 里的框是工作计划。建议面板分成「待你验收」和「计划项」两段，各组标题显示等了多少天；角标从 246 个框改成「轮到你的 issue 数」，现在是 12。06-12 设计待办时把它定位为「横切的注意力视图」，这个改动是让它回到这个定位。
- 既然 61% 的 issue 是带着未勾选框关闭的，验收的实际单位是 issue。「待你验收」一段里每组可以直接提供「完成」，沿用现有的转 Done 流程（关闭会话确认、按设置勾选待办）。
- 可选：issue 分区增加「按回合」排序，轮到你的排前面。根工作区只有 9 篇时意义不大，`iris-agent` 的 17 篇会明显受益。现有的排序开关是全局一个（`lens-prefs` 的 `sort`），四种类型共用；report 在左栏里也按修改时间排，而它「出生即冻结」，应当按文件名里的日期排。排序规则按类型分开会更合理。

**改动范围。** 一个纯函数加测试；`LensTree` 的行渲染；`TodoPanel` 的分组；`LeftPane` 的角标计算。不涉及协议和主进程。

#### C. 折叠不应该等于隐藏；透镜的可见规则缺一个统一说法

**现象一。** 折叠工作区的文档区后，标题行只剩名字；折叠类型分区后只剩文档数。里面挂着会话的文档、等你验收的 issue 都不留痕迹。08-06 你定过一条规则：有终端挂着的 issue 必须留在左栏，「要不然容易丢终端」。这条规则在折叠状态下是失效的，而子工作区默认就是折叠的。

**现象二。** 「什么文档出现在透镜里」现在是三段各自写的条件：issue 是「活动，或挂着会话」；其余三类只看 Active，没有会话例外；当前打开的文档不保证在树里。后两点的后果：

- report、status、misc 如果被外部改成 Backlog（比如 agent 改了 frontmatter），而它还挂着会话，这篇文档会从左栏消失，会话跟着找不到。界面上改状态会先确认关闭会话，所以只有外部修改会触发，但它正是 08-06 那条规则要防的情况（`TypeSection` 里非 issue 分支只有 `isActiveDocumentStatus`）。
- 从集合页用「在默认视图打开」打开一篇 Done 的 issue 后，左栏里没有任何一行对应它，看不出自己在哪。

**方案。**

- **一条规则管四种类型：透镜可见 = 活动 ∪ 挂着会话 ∪ 正在打开。** 后两种是「被占用」的文档，占用结束后自然离开透镜。
- **折叠的标题行继承子项的汇总。** 类型行折叠时，在右侧放一个聚合后的会话点。工作区标题折叠时，放聚合点加回合计数。示意：

  ```text
  ▾ iris                                 +
      ● Claude Code · 左栏调研
    STATUS 2
    ISSUE 9
      ● MD 问答标准              In Review     ← 金色实心：停下了，还没看
      ○ 根工作区右键菜单          In Review     ← 空心：看过了
        软件质量检查              In Review
    ▸ REPORT 5                          ●     ← 折叠的分区里有会话在跑
  ▸ iris-agent                 7 待验收 · 4 停滞
  ▸ private                             1 停滞
  ```

  文字形式可以再收：只留数字、把说明放进悬停提示也行。要点是折叠后的一行能回答「这里面有没有我的事」。
- **不建议按活跃度自动展开工作区。** 展开状态应该只由人改变并记住（`2026-10-25-左栏展开状态持久化` 已经在跟踪）。自动展开会让树在你没动的时候变形，违背渲染层要确定的原则。把信息放到折叠行上，人自己决定要不要展开。汇总做好之后，持久化的折叠才是安全的，两件事适合一起做。
- **没用过的类型分区不画。** 每个展开的工作区固定渲染四个类型标题（`TYPE_ORDER.map`），不管对应的文件夹存不存在。`private` 只有 `issue/`，却会显示三个空分区。协议说工作区的形状从文件系统读出，那么没有的类型就不该画。以前空标题行还承担「新建文档」入口，10-25 加了右键菜单的「新建文档 ▸ 四种类型」之后，这个职责已经有了替代。External 维持常显的约定不变。
- **点工作区名称时顺带展开。** 现在名称（大热区）是跳到 hub，箭头（14px）才是展开。子工作区默认折叠，人最先想做的是展开，却容易点到名称而离开当前文档。建议点名称在进入 hub 的同时展开文档区，但不负责折叠；折叠仍然只由箭头触发。

**改动范围。** 都在 `LensTree.tsx` 内，加上提议 A、B 的两个纯函数。

#### D. 工作区：有出生，没有一生

**现象。** 应用对工作区只支持创建。协议写了完整的生命周期（「探索失败，删掉整个工作区文件夹；成功，把有价值的文档晋升到父级」）和元数据位置（「工作区级元数据用一篇普通 `index.md` 放在工作区根上」），应用都没有对应的东西：

- **没有身份。** 左栏上一个工作区只有文件夹名。hub 会话启动时动态注入的内容也只有路径：除了入口文件里的静态提示词，`focus-context` 脚本对 hub 会话输出的全部内容是「这是从某路径打开的工作区 hub 会话，没有焦点文档」。在 `iris-agent` 的 hub 里开一个 agent，它不知道 iris-agent 是什么。`index.md` 在代码里只出现在扫描器的一行注释里，被明确排除在透镜之外。
- **没有后续动作。** 文档级的指令只有 `doc.create`、`doc.save`、`doc.delete`。没有重命名，也没有移动。而在 Iris 的协议里，类型就是文件夹名，作用域也是文件夹，所以「改类型」「换工作区」「晋升到父级」本质上都是同一个动作：移动文件。现在只能去资源管理器里拖，拖完会话会被当作文档删除处理，变成 hub 上的孤儿会话。
- **真实用途没有被承认。** `private` 这种本机私有区是你自己用 git exclude 拼出来的，左栏上看不出它不进 git。

**方案。**

- **D1 `index.md` 作为工作区的自我说明（可选存在）。** 有这个文件时：左栏悬停工作区名显示它的 `title` 或首段；hub 会话的注入内容带上它，规则和焦点文档一样（超过 32 KiB 降级为指针）；hub 没有会话时的启动页显示它。没有这个文件时，一切和现在相同。这是把协议里已经写了的一句话实现出来，符合「每一层都可降级」。它会改动注入内容，属于提示词治理的范围，需要你单独点头。
- **D2 本机私有标记。** 扫描时判断工作区目录是否被 git 忽略，是的话在标题上加一个小标记，悬停说明「未纳入 git，仅在本机」。新建工作区的对话框可以加一个「仅本机」选项，代写 `.git/info/exclude`。协议里机器层和项目层的区分是有的，但只覆盖了规约文件，没有覆盖「不想进 git 的 PM 文档」，这个缺口你已经用工作区补上了，应用应该认它。
- **D3 「移动到…」作为统一动词。** 文档右键菜单加「移动到 ▸ 工作区 / 类型」，主进程新增一条 `doc.move`：文档和它的 `.assets/` 一起移动，挂着的会话随之改锚（主进程已有 `reanchor`）。它同时解决改类型、换工作区和晋升。左栏的文档行本来就可拖拽，以后可以让拖到类型标题或工作区标题上等于移动，但第一版用菜单就够。移动后指向这篇文档的相对链接会失效，第一版可以只提示、不改写。
- **D4 修掉空白模板。** `createWorkspace` 的 `empty` 模板只建一个空目录，扫描器不认，新工作区不会出现在任何地方。改成至少选一种类型，或者去掉这个模板。
- **不建议在左栏提供删除工作区。** 它会连带删掉整棵文档树，风险和收益不成比例，留给资源管理器。

**根工作区的双重身份。** 根节点现在同时是「项目」和「根工作区」：布局上它和子工作区平权，但点它的类型标题打开的是全项目集合（`LensTree.tsx:211` 把 `.iris` 换成 `null`），旁边的计数却只算根这一层；右键「查看待办」也是全项目。建议统一成一种说法：平权指的是能力（hub、会话、菜单），范围上根工作区就是它自己这一层；全项目的入口只留工具栏的待办和集合页里的范围切换。

#### E. 透镜藏起 88% 之后，缺一条不经过透镜的检索路径

**现象。** 222 篇 issue 里左栏只显示 27 篇，这是设计意图，是对的。但左栏的搜索框只在透镜可见的文档里过滤（`lensDocs.filter(matchesFilter)`），而且会被工作区折叠挡住。想找一篇已完成的 issue，路径是：点 ISSUE 标题进集合页，切到「全部」，再搜。应用里没有快速打开，也没有命令面板。

对一个以文档为长期记忆的工具，「我记得写过这个」是高频需求。被藏起来的 195 篇正是记忆的主体。

**方案。** 搜索框有内容时结果分两段：

1. 透镜内的匹配，穿透折叠（临时展开，清空后恢复，不写入持久化的折叠状态）。
2. 「不在透镜中」的匹配：Done、Canceled、On Hold、Backlog 的文档，弱化显示并带状态徽章，限制条数。点击就打开；按提议 C 的可见规则，它打开期间会留在树里。

这样左栏的搜索就从「过滤眼前的东西」变成「找到任何一篇文档」，不需要新增入口。

**改动范围。** `LensTree.tsx` 的过滤逻辑，数据已经全部在 scan 结果里。

### 四、考虑过但不建议的做法

- **在左栏顶部加一条「待你处理」的动态区域。** 它能跨工作区汇总，但条目出现和消失会把下面的树整体上下推，正在点的行会跑；同一篇文档还会出现两次。折叠行汇总、角标和「下一个未看」快捷键能达到同样的目的，而树不动。
- **把会话做成一级列表，或在树里按状态分组。** 文档是一级对象、会话依附文档，这是 Iris 和别的 agent 工作台的区别。按状态分组的职责已经在集合页。
- **工作区切换器，或恢复缩进。** 理由和你之前的决定一致。汇总做好之后，折叠的标题行本身就是一个带状态的工作区列表。
- **现在就投入 OSC 7501 或 hook 反向通道。** 有了「已看 / 未看」之后，它们从前置条件降为锦上添花，可以等生态成熟。
- **用更多复选框表达待验收。** 数据显示复选框没有被逐个维护。

### 五、建议的顺序

1. **A（已看 / 未看）加 C 里的折叠汇总。** 纯渲染进程，改动集中，立刻改变左栏的信息量。和 `2026-10-25-左栏展开状态持久化` 一起做，因为都要把折叠状态从组件里提出来。
2. **B（回合）。** 纯函数加待办面板和角标的口径调整。
3. **C 的其余部分和 E。** 可见规则统一、不画空类型、搜索两段。都在 `LensTree` 里。
4. **D。** D4 随时可做；D2、D3 需要主进程配合；D1 涉及注入内容，等你确认方向。
5. 任务栏提示和「下一个未看」快捷键可以跟在第 1 步后面单独做。

这些证据大体支持提议 A：tmux 几十年来用的就是「不是当前窗口才置位，选中即清除」，Zed 的源码实现的是同一条规则。同时它带来三点修正，前两点已经写进提议 A：

1. **「等你输入」在所有产品里都是持续状态，回答了才消失。** 它和「未看」是两回事。Iris 现在拿不到可信的「等输入」信号，所以先只做「未看」；以后接入 7501 时不要把两者合并成一个标记。
2. **未读标记自己也会饱和。** 抱怨最集中的是每次中间停顿、每次例行运行都触发未读（[#87351](https://github.com/anthropics/claude-code/issues/87351)、[#103688](https://github.com/anthropics/claude-code/issues/103688)，均为用户报告）。Iris 靠输出静默判断停下，比这些产品更容易误触发，所以置位要等「停稳」。
3. **这一类功能最常见的缺陷是任务栏徽标和侧栏对不上，以及未读状态丢失。** 前者靠单一数据源避免；后者在 Iris 里不存在，因为会话本身不跨重启。

反例也有：Claude Code CLI 的 agent view 完全按状态分组（工作中、需要输入、空闲、已完成），没有已看和未看的区分（[agent-view 文档](https://code.claude.com/docs/en/agent-view)，已核实）。它能这样做是因为它有精确的结构化状态，Iris 对外部 CLI 没有。

## 2026-11-22 第四轮：把工作区从「树的分组」改成「可切换的工作上下文」

第三轮的主判断错了。它把问题解释成「左栏缺少注意力信号」，所以一路推到了未读点、任务栏闪烁、回合计数。这些机制即使全部做完，也不会让人更容易从根工作区切到 `iris-agent`、回到刚才工作的文档，或看清另一个工作区正在做什么，反而会继续往左栏里堆状态。本轮明确撤回这条路线：**不做已读/未读，不新增红点，不做任务栏提醒，也不把待办改造夹带进来。**

真正的问题是：Iris 在文件模型里有工作区，在界面里却没有「当前工作区」。`WorkspaceSection` 只是把所有工作区依次画在同一棵树上；点工作区名称只会打开它的 hub，点一篇文档后工作区本身不再是选中态；`project-store` 只记当前 `view`，没有每个工作区的上次位置。于是「切工作区」实际等于：在一棵平铺长树中找到标题、展开、再找文档。跨区协调也只能靠人扫完整棵树。

顶部按钮拥挤和排序粗糙是同一个根因的外显：所有动作都被提升成项目级全局动作，而真正应该作为作用域的「当前工作区」缺席了。

### 一、代码和历史决策暴露出的结构问题

1. **工作区只有 hub 视图，没有导航上下文。** `MainView` 有 `root`、`workspace`、`doc`、`todos`，但没有 `activeWorkspacePath` 或 `lastViewByWorkspace`。`selectWorkspace(path)` 只把主区域换成全宽终端；从工作区里点开文档后，系统不会记住「这是当前工作区」，也没有下次一键返回的位置。
2. **平铺和平权解决了层级视觉，却牺牲了切换。** 2026-06-16 的决定是所有工作区无缩进、根和子工作区平权。这个决定适合表达文件模型，但真实使用后暴露出另一面：工作区多起来以后，它们不是一个个可切换的上下文，而是重复的 `status / issue / report / misc` 区块。当前项目 27 篇活动 issue 中 18 篇在子工作区，这已经不是边缘场景。
3. **折叠状态代替不了当前工作区。** 子工作区默认折叠（`useState(depth === 0)`），展开状态还会因组件卸载而丢失。即使把折叠持久化做好，也只是记住树形 UI，并不会记住「我离开 `iris-agent` 前正在看哪篇文档、哪个集合或哪个 hub 会话」。
4. **根工作区和全项目范围混在一起。** 根工作区类型行显示的是根这一层的计数，但点击后传 `null`，打开全项目集合；根工作区待办也是全项目待办。这会让人无法建立稳定的作用域直觉：`iris` 有时指根工作区，有时又指所有工作区。
5. **顶部是一排没有层级的动作。** 当前常驻系统入口是项目菜单、新建工作区、排序、搜索、文件树、待办、Git；本项目又配置了「启动开发服务器」「编译版本」两个自定义命令。低频结构动作、视图切换、列表设置和高频项目命令全在同一排竞争空间。
6. **排序只有一个全局二选一。** `lens-prefs` 只有 `mtime | alpha`，同时驱动 Lens 和文件树；Lens 内四种文档共用同一个规则。issue、report、status 的使用语义完全不同，却被迫一起按标题或 mtime 排。工作区本身则永远按路径字母序，和最近使用、正在工作的上下文无关。

### 二、核心方案：一个明确的「当前工作区」

左栏仍然保留所有工作区，不改磁盘结构，也不恢复缩进；但任意时刻有且只有一个**当前工作区**。它是导航作用域，不是新的 PM 数据，不写入 `.iris/`。

#### 1. 切换要回到上次工作的地方

为每个工作区记一份本机导航记忆：

```text
workspace path -> 上次主视图
               -> doc(path)
               -> collection(type, workspace scope, selected doc)
               -> todos(workspace scope)
               -> hub(selected session)
```

- 点工作区名称是「切换到这个工作区」，默认恢复它的上次位置，而不是一律打开 hub。
- 第一次进入、记忆目标已删除，或记忆无效时才回到该工作区 hub。
- 从全项目集合、搜索结果或文内链接打开一篇文档时，当前工作区自动跟随到文档所属工作区，并更新该工作区的上次位置。
- 切换工作区只切导航，不关闭、重建或搬动任何会话。会话选择已经按 anchor 记忆，可以直接复用。
- 第一版先保证同一应用会话内记忆；稳定后再写入 `view-prefs` 跨重启保存。删除或重命名工作区时清理失效键，并回退到仍存在的父工作区或根工作区。

这才是「切换」应有的手感：`根工作区 → iris-agent → private → iris-agent`，最后一步直接回到离开前的文档和会话，而不是重新走一遍树。

#### 2. 当前工作区展开，其他工作区退成紧凑入口

左栏正文改成工作区手风琴，而不是让所有工作区的四类文档同时争夺纵向空间：

- 当前工作区默认展开其文档区，名称有稳定的选中态。
- 其他工作区保留一行标题，默认收起。点名称会切换；chevron 只做临时预览，不改变当前工作区。
- 切换后旧工作区自动收起，新工作区展开。用户手动预览的展开状态可以保留到下一次切换，但不会被误认为当前作用域。
- hub 会话仍属于各自工作区；文档会话仍属于文档。此处只改投影和导航，不改 session anchor 模型。

示意不是最终视觉稿，重点是作用域关系：

```text
iris / iris-agent  ▾                         搜索  视图  命令

▸ 根工作区
▼ iris-agent                                  当前
    Claude Code · 左栏逻辑优化
  STATUS  2
  ISSUE   17
    iris 左栏逻辑优化             In Progress
    软件质量检查                  In Review
  REPORT  5
▸ private
```

#### 3. 跨工作区协调放进切换器，不放进红点系统

工作区切换器不是只有名字的下拉框，它同时承担跨区协调：

```text
正在进行
  iris-agent    左栏逻辑优化 · Claude Code
  根工作区      软件质量检查 · Codex

最近使用
  private       上次：私有提示词
  根工作区      上次：开发与构建

全部工作区
  ...
```

- 「正在进行」只使用已有事实：工作区里存在尚未关闭的会话。显示会话或锚定文档名称，不引入已读/未读，也不猜测 agent 是否在等人。
- 点击工作区名恢复上次位置；点击具体会话直接跳到该会话。
- 没有会话的工作区仍可从「最近使用 / 全部工作区」进入。
- 非当前工作区标题最多显示朴素文本 `2 个会话`，不画新的告警色和角标。跨区协调需要的是「哪里正在做什么」，不是「哪里有东西亮了」。

#### 4. 根工作区和「全部工作区」彻底分开

- 根工作区就是 `.iris` 这一层，点它的 ISSUE 只打开根工作区 issue，计数与结果一致。
- 「全部工作区」是一个显式的虚拟范围，放在工作区切换器里，用于进入全项目 Issue、Todo、Status 等集合视图。
- 集合页已有 workspace 过滤能力，可以继续在其中切换范围；左栏不再用一个看似根工作区的入口偷偷打开全项目。

这样工作区切换与全局协调成为两种明确动作：**切到一个地方继续工作**，或**打开全局视图横向管理**。

### 三、顶部工具栏：按「导航 / 视图 / 命令」收拢

建议把当前单行九类入口收成四个区域：

```text
[ 项目 / 当前工作区 ▾ ]   [搜索]   [视图 ▾]   [命令 ▾]
```

| 现有入口 | 新位置 | 原因 |
| --- | --- | --- |
| 项目菜单 | 面包屑的「项目」段 | 它是项目级导航，不是普通工具按钮 |
| 新建工作区 | 工作区切换器底部 + 工作区右键菜单 | 低频结构动作，且必须有明确父工作区 |
| 搜索 | 保留直接入口 | 高频、进入后有明确输入态 |
| 排序 | 「视图」菜单内，按当前模式/类型显示 | 它是展示偏好，不值得永久占一个按钮 |
| Lens / 文件树 | 「视图」菜单 | 两者是同一左栏区域的模式切换 |
| Todo | 「视图」菜单中的当前工作区 / 全部工作区入口 | 必须显式带作用域，不再只有一个全局按钮 |
| Git | 「视图」菜单 | 是另一种项目视图；变更数在菜单项内显示即可 |
| 自定义开发命令 | 单独的「命令」菜单 | 和导航、排序分槽；菜单直接显示「启动开发服务器」「编译版本」文字 |

项目 / 工作区用一个复合面包屑最清楚：点项目名打开「切换项目 / 最近项目 / 新窗口」；点工作区名打开工作区切换器。窄栏时优先保留当前工作区名，项目名可缩成图标。顶部从「一排用途不明的图标」变成三个清楚问题：**我在哪、我要看什么、我要执行什么。**

自定义命令不建议继续按配置数量无限平铺。第一版全部收进命令菜单；如果实际使用证明多一次点击太慢，再给动作增加 `pinned`，最多允许固定一个常用命令。不要预先恢复一排按钮。

### 四、排序：按对象语义排序，不再全局切换 `mtime / alpha`

排序要拆成三层，且各自稳定：

#### 1. 工作区顺序

- 切换器先列「正在进行」，再列「最近使用」，最后列完整的字母序清单。
- 最近使用是本机导航历史，不写入项目；完整清单始终提供稳定字母序，避免 MRU 让人找不到东西。
- 左栏正文不跟着活跃输出频繁重排：当前工作区固定在展开位置，其他标题保持扫描器的稳定顺序。

#### 2. Lens 文档顺序

不同类型使用不同默认规则：

| 类型 | 默认顺序 | 理由 |
| --- | --- | --- |
| issue | 有未关闭会话的在前；其余按 `In Progress → Blocked → In Review → Todo → 未知`，组内按日期/mtime 倒序 | 先保留正在发生的工作，再按工作流事实排序；不引入 priority 字段 |
| status | 标题字母序 | status 是长期入口，位置稳定比最近修改更重要 |
| report | 文件名日期倒序，无法解析日期时退回 mtime | report 是时间序列，mtime 可能被 git 或修订扰动 |
| misc | mtime 倒序 | scratch 内容通常按最近使用找 |

- 「有会话」只在会话创建或关闭时改变，不根据 `active / idle` 输出状态实时重排，避免点击目标跳动。
- 每种类型的标题菜单可切换「默认 / 最近修改 / 标题」，偏好按 `项目 + 工作区 + 类型` 保存；不再用一个全局开关同时改变四种类型。
- 相同条件用标题、最后用路径做稳定 tie-breaker，确保重扫不随机换位。

#### 3. 文件树顺序

文件树保留自己的「名称 / 修改时间」规则和搜索语义，与 Lens 偏好彻底解耦。当前两者共用 `lens-prefs.sort`，属于实现复用泄漏到产品语义，应该拆开。

不建议第一版加入任意拖拽排序或 `priority:`。前者需要处理跨设备、重命名和失效项，后者违背 2026-06-14 已经确立的「不为个人工作引入常驻优先级管理」原则。先用工作区记忆、会话事实、状态和日期解决 90% 的定位问题。

### 五、交互边界

- **打开跨区文档：** 当前工作区跟随文档切换；返回原工作区时恢复原位置。
- **全项目集合：** 当前工作区不被改写；从集合打开某篇文档进入默认视图时才跟随到所属工作区。
- **当前文档有未保存内容：** 沿用 `flushBeforeSwitch()`，保存冲突或失败就不提交工作区切换。
- **会话：** 切换、折叠、改变视图都不能关闭或重建会话。
- **删除工作区：** 清理导航记忆；当前工作区被删时回退到存活父级或根。
- **新建工作区：** 默认父级就是当前工作区；创建后切到新工作区的 hub。
- **搜索：** 默认搜索当前工作区；结果页提供一次显式的「全部工作区」扩展，不靠搜索悄悄改变作用域。

### 六、建议实施顺序

1. **先做导航模型。** 增加当前工作区推导和 `lastViewByWorkspace`，覆盖文档、hub、集合、Todo 的往返；修正根工作区与全项目 scope。此步不大改视觉，但决定后面不会继续在错误模型上堆 UI。
2. **再做工作区切换器与当前工作区手风琴。** 接入已有 session projection 形成「正在进行」列表；不增加新状态源。
3. **收拢顶部工具栏。** 上线面包屑、视图菜单和命令菜单，移走新建工作区、排序、Todo、文件树、Git 的常驻图标。
4. **最后拆排序偏好。** Lens 按类型给默认规则，文件树独立保存；排序入口进入类型标题或视图菜单。

每一步都可以独立验收。不要把四步做成一次大重构，也不要顺带实现第三轮的待办、搜索和工作区生命周期提议。
