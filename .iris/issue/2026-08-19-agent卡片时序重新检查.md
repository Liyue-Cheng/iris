## 全面调研结论（2026-08-19）

结论先说：**新 Session 中，工具活动与已提交回复的静态排列顺序基本正确；当前真正没有收口的是回复卡的生命周期。**

main 已经用共享单调序号解决了最初的“最终回答固定跑到工具前面”问题，也能表达“读取 -> 中间短评 -> 再读取”。但现有实现仍把“逻辑 Turn”“物理 Provider Attempt”“一段可见回复”和“流式草稿”混在不同对象里。结果是：历史回复会跟着整个 Turn 一起转圈或变成已暂停；流式回复提交时更换卡片 ID；Stop 后 Continue 会覆盖停止前已展示的回复；旧 Session 迁移则会把跨数组的未知顺序强行写成“所有回复在前、所有工具在后”。

因此，这不是再调整一次 `.sort()` 就能彻底解决的问题。目标模型必须明确：**位置属于 timeline activity，运行状态属于单个 activity，Turn/Execution 状态只控制会话操作，不反向改写已经发生的卡片事实。**

本轮只做调研和方案收口，没有修改代码。

## 我对当前时序的理解

### 1. Turn 外壳

发送用户消息时，main 一次创建：

```text
user message
Turn(open)
Execution(running)
预留的空 assistant message
```

用户消息始终由 Renderer 固定放在该 Turn 最前，不参与活动 `sequence`。这部分直观，也符合“一轮先有用户请求”的事实。

### 2. 流式文本

Provider 的 `text_delta` 暂时只追加到 `Execution.draftContent`。Renderer 把它临时投影为：

```text
id = draft:<executionId>
state = running
位置 = 当前所有已提交活动之后
```

它此时没有 canonical `sequence`，也没有独立的 provider message/reply identity。

当 assistant `message_end` 到达后：

* 工具调用前的 assistant envelope 会保存为独立 `providerOnly` message；
* 普通 assistant 回复会写入 Turn 预留的唯一 `assistantMessageId`；
* 非空正文首次提交时才由 main 分配 `sequence`；
* `draftContent` 清空，Renderer 改为投影持久 message。

因此视觉位置通常不会错，因为同一 Worker `MessagePort` 的事件按 Session 串行归约，工具请求要在对应 assistant envelope 结束后才发生。但卡片身份会从 `draft:<executionId>` 变成 `reply:<messageId>`。

### 3. 工具活动

Worker 在 provider tool definition 边界取得 provider `toolCallId`。同一工具内部的 access/read/write/exec operation 共享这个 ID；main 收到该 tool call 的第一个低层请求时创建 `IrisAgentToolEvent` 并分配 `sequence`。

后续 operation 和完成结果 upsert 同一事件，并保留首次分配的 `sequence`。所以工具卡的位置表达的是“这次工具活动开始于哪里”，不会因为慢命令最后完成而跳到时间线末尾。这个选择是正确的。

### 4. Renderer 投影

每个 Turn 内，Renderer 合并：

```text
displayable non-empty assistant messages
+ tool events
-> 按 sequence 排序
-> 连续 read / information terminal 聚合成本地获取
-> 回复、写文件、operation terminal 中断聚合
```

空 provider envelope 虽然可能占用一个序号，但不生成卡，也不会中断本地获取聚合。该规则确定、可重放，方向正确。

## 已经合理的部分

1. **新记录不再依赖两个数组的 JSX 遍历顺序。** 回复和工具共同排序，已经修复“先显示最终结论、后显示取证过程”的原始问题。

2. **工具卡创建位置稳定。** 运行中和完成态更新同一个事件，长命令不会在结束时移动。

3. **连续聚合是语义连续，不是时间阈值。** 回复或有副作用动作会明确打断本地获取；空 envelope 不会制造虚假断点。

4. **provider tool call 与低层 operation 已分开。** edit 的预读不会再额外冒出“本地获取”卡。

5. **异步事件有 Session 级串行边界。** `workerEventChains` 让同一 Session 的 Worker 事件顺序归约；revision/epoch/attempt correlation 负责拒绝旧快照和迟到事件。这使 main 分配序号具备可靠基础。

## 发现的问题

### P0：Stop 后 Continue 会覆盖已经展示的回复

这是当前最严重的语义问题。

Stop 时，安全的 interrupted assistant 文本会通过普通 assistant 分支写入 Turn 唯一的 `assistantMessageId`。Continue 仍复用同一 Turn/Execution；下一次非 `toolUse` assistant `message_end` 又进入同一分支，并把同一个 message 的 `content` 和 `providerMessage` 替换为新值。

确定的结果是：

```text
停止前：reply:<assistantMessageId> = "已经输出的前半段"
继续后：reply:<assistantMessageId> = "继续请求产生的新一段"
```

前半段不是新增一张已停止回复，而是从 UI 与 Session canonical message 中消失。随后新 Turn 恢复历史时，也只会看到被覆盖后的 provider message。这个行为同时破坏三件事：

* 用户已经看见的时间线事实不再 append-like；
* Stop checkpoint 与 Continue 新回复不能同时表达；
* UI 历史和 Provider 实际经历过的多条 assistant message 不再同构。

现有 Stop 测试只断言 checkpoint 在暂停时存在；Continue 测试只覆盖空 checkpoint，未覆盖“非空 checkpoint -> Continue -> 新回复结束”的完整链路，所以没有抓住覆盖问题。

相关实现：`src/main/agent/session-manager.ts:1395`、`src/main/agent/session-manager.ts:1403`；相关测试缺口位于 `src/main/agent/session-manager.test.ts:696` 与 `src/main/agent/session-manager.test.ts:790` 附近。

### P1：所有回复卡错误地继承整个 Turn 的状态

`projectIrisAgentCards()` 对每一张已提交回复都调用同一个 `turnState(turn, execution)`。因此：

* Agent 已经说完“我先检查入口”，开始执行工具时，这张历史回复仍显示 spinner 和“正在回复”；
* Turn 自动重试等待时，前面的已完成回复仍被视作 running；
* 用户 Stop 后，Turn 内所有早已完成的回复都会一起变成“已暂停”；
* Continue 后，它们又一起回到“正在回复”；
* Turn 最终 fulfilled 时，所有卡才一起变成 completed。

这把“当前 Turn 还没结束”误写成“Turn 中每段话都还没说完”。用户会看到状态逆流，尤其在多段中间短评的长任务里很不直观。

正确口径应是：已收到 `message_end` 的回复就是 completed；只有当前 draft reply 是 running；Stop 提交的 interrupted reply 是 stopped；以后 Continue 创建的新回复拥有自己的状态。Turn/Execution 状态不应覆盖这些既成事实。

相关实现：`src/renderer/components/agent/IrisAgentView.tsx:378`、`src/renderer/components/agent/IrisAgentView.tsx:797`。

### P1：流式卡片在提交时换 ID、换事实来源

设计要求“首个可见 delta 建立稳定回复活动，后续原位追加，message_end 只结算状态”。当前实现却是：

```text
流式阶段：draft:<executionId>，无 sequence
提交阶段：reply:<messageId>，首次获得 sequence
```

React 会把它当作旧卡删除、新卡创建，卡片内部状态和 DOM identity 都不能保持。视觉上可能出现 remount、展开状态丢失或滚动锚点轻微跳动。更重要的是，统一时间线在回复流式期间并不真实存在，只是在 `message_end` 后补写了一个通常正确的位置。

目前事件顺序使它暂时不容易排错：工具请求不会早于该 assistant message 结束。但它仍然违背“活动在首次可见时进入时间线”的契约，也无法支撑 Stop/Continue 的多回复模型。

相关实现：`src/renderer/components/agent/IrisAgentView.tsx:414`、`src/main/agent/session-manager.ts:978`、`src/main/agent/session-manager.ts:1397`。

### P1：旧 Session 迁移会伪造跨 message/tool 的顺序

`normalizeTimeline()` 先遍历全部 `messages`，为缺序号项依次补号；然后再遍历全部 `toolEvents` 补号。Renderer 只显示其中的 assistant message 与 tool event，所以一个旧 Turn 很容易被迁移成：

```text
全部 assistant 回复
全部 tool event
```

这会把旧版最典型的“工具 -> 最终回答”重新迁移成“最终回答 -> 工具”，正是最初要修复的问题。迁移结果虽然确定，却不是保守：它把未知事实永久盖章为精确顺序，而且没有 `legacyOrder` 标记。

Renderer 中按 `createdAt` 计算的 `legacySequence()` 基本不会拯救从 store 加载的记录，因为 store 已先给缺失项补齐正式 `sequence`。

相关实现：`src/main/agent/session-store.ts:628`、`src/renderer/components/agent/IrisAgentView.tsx:360`。

### P1：卡片设计文档与新的暂停模型互相冲突

卡片设计仍定义：失败 Turn 没有文本时生成 fallback 失败回复卡；已有文本时把错误附在最后一张回复卡；Retry 只出现在该卡中。

当前会话领域模型已经取消 failed Turn：provider/Worker/auth 错误使 Execution paused，错误显示在时间线外的顶部暂停条，并提供“继续”。Renderer 实际上始终传 `canRetry={false}`，`AgentReplyCard.error` 正常链路也没有来源。

两套口径不能同时成立：

* **暂停/继续模型**：失败是当前执行控制状态，顶部条是唯一恢复入口；时间线只记已提交活动。
* **失败回复模型**：失败在时间线形成一张 receipt，并在回复卡上 Retry。

就当前 Stop/Continue 设计而言，我倾向保留第一种：provider failure draft 本来就没有提交为可恢复历史，把它伪装成一段 Agent 回复并不准确。但应正式废止卡片文档中的 fallback/Retry 规则，并删除 Renderer 的死分支；否则后续开发会继续按相反契约补功能。

### P2：失败 Attempt 的可见草稿会突然消失，时间线没有解释

Provider 失败或自动重试时，`draftContent` 被清空。这样可以避免把失败 Attempt 的不完整输出写入 canonical provider history，是正确的领域选择；但用户刚刚看到的流式文字会瞬间消失，只剩页面顶部的“请求已暂停”或“等待重试”。

这不是历史顺序错误，却是明显的时间体验断裂。至少需要明确产品口径：running draft 是可撤销预览，不是已提交回复；进入 retry-wait 时应有稳定的状态反馈，避免看起来像应用吞掉了一段历史。不要简单把失败 draft 提交成回复来掩盖，因为它可能包含 provider 判定无效的半截输出。

### P2：所谓 turn-local `sequence` 实际是 Session 全局计数器

`timelineSequence` 保存在 Session 根上，新 Turn 不归零；user/tool-result/空 envelope 等不显示项目也可能占号。Renderer 只在单个 Turn 内比较，因此当前不会排错，但类型注释和设计反复称其为“turn-local”，与实际契约不符。

建议二选一：

* 保留 Session 全局单调序号，并改名/注释为 `activitySequence`；
* 真正把计数器归属到 Turn。

前者更简单，也有利于调试整段 Session 的事件顺序。序号有空洞没有问题，不应为了连续美观重排历史。

### P2：投影仍在 React 文件中理解 canonical 内部结构

`projectIrisAgentCards()` 虽然是纯函数，但仍位于 `IrisAgentView.tsx`，直接 join `messages`、`toolEvents`、`turns`、`executions`，并在组件文件里决定 legacy fallback 与状态语义。它与既有架构调研提出的 `canonical aggregate -> pure projection builder -> view model` 仍有距离。

这不是当前排序 bug 的直接原因，但正是“Turn 状态被误用为 Reply 状态”能够进入 UI 的结构性原因。投影应迁到独立 shared/renderer lib，并输出不再需要理解 domain 归一化方式的 view model。

## 推荐的目标语义

### 1. 把回复升级为真正的 timeline activity

不再用 `Execution.draftContent` 加 Turn 唯一 assistant 占位消息拼出回复卡。至少需要等价于：

```ts
interface IrisAgentReplyActivity {
  id: string;
  turnId: string;
  providerCallId: string;
  attemptId: string;
  sequence: number;
  source: 'providerOnly' | 'assistant' | 'interrupted';
  state: 'running' | 'completed' | 'stopped';
  content: string;
  createdAt: number;
  completedAt?: number;
}
```

Provider transcript message 与用户可见 reply activity 可以关联，但不应再假设“一条 Turn 只有一个普通 assistant message”。两者服务不同目的：前者保证 provider history 合法，后者保证用户已经看见的叙事不会被覆盖。

### 2. 首个可见 delta 就创建稳定回复

main 在某个物理 assistant message 的第一个非空可展示 delta 到达时：

1. 生成稳定 reply ID；
2. 分配 activity sequence；
3. 写入 running reply；
4. 后续 delta 只原位追加；
5. `message_end` 只将该 activity 结算为 completed/stopped，并关联完整 provider message。

如果业务坚持“失败 Attempt 的 draft 不能进入 canonical state”，也应把 `draftContent` 升级成带稳定 `id/sequence/providerCallId/attemptId` 的 `draftReply` 对象，并在成功时以同一 ID 提交，避免 Renderer 换卡。

### 3. Stop 与 Continue 各自产生事实，不互相覆盖

```text
回复 A（stopped，保留停止前正文）
点击继续
回复 B（running -> completed）
```

两张卡都属于同一 Turn/Execution，但属于不同物理 assistant message/Attempt。后续 provider history 恢复也必须同时包含安全的 interrupted message 与 Continue 后的新 message。

### 4. 工具序号策略保持不变

工具 activity 仍在首次 main-owned operation 请求到达时分配序号，后续低层 operation 和完成结果更新原 activity。这部分不需要为了回复重构而改动。

### 5. 旧 Session 只做诚实的兼容投影

迁移不能简单“messages 先、tools 后”。建议按每个 Turn 重建候选活动：

* 优先使用已有 sequence；
* 缺 sequence 时，利用 provider transcript 中 assistant tool-call / tool-result 的关联，把对应工具放在正确 envelope 之后；
* 其余项目按 `createdAt` 加稳定 tie-breaker 保守排序；
* 无法确定的记录标记 `legacyOrder: true`，不要宣称是精确事实；
* 迁移一旦持久化，重启后顺序必须稳定。

- [ ] P0：增加“非空 interrupted checkpoint -> Continue -> 新 assistant 完成”的领域测试，先固定两段回复都必须保留、provider history 不丢失的契约。

- [ ] P0：取消 Turn 唯一普通 assistant 槽位的覆盖语义，让 Stop 前回复与 Continue 后回复成为两个稳定 activity/message。

- [ ] P1：为回复建立独立 lifecycle；已提交中间回复保持 completed，不再继承 Turn/Execution 的 running/paused 状态。

- [ ] P1：在首个可见 delta 创建稳定 reply ID 与 sequence，提交时不换 React key、不重建卡片。

- [ ] P1：重写 legacy timeline 迁移，增加“旧工具在最终回答之前”“providerOnly 短评夹在两次读取之间”和部分已有 sequence 三类用例。

- [ ] P1：在卡片设计文档中正式选择“暂停条 + Continue”或“失败回复卡 + Retry”之一；按当前领域模型建议保留前者，并清理 fallback/error/retry 死分支。

- [ ] P2：定义失败 Attempt draft 的 UI 口径，确保自动重试/暂停时内容消失有明确状态反馈，但不把无效 draft 冒充 canonical reply。

- [ ] P2：统一 `timelineSequence` 的真实作用域与命名，补充唯一性/迟到事件/重启稳定性断言。

- [ ] P2：把 projection builder 移出 React 组件，输出显式 `AgentTurnView` / `AgentActivityView`，让 JSX 不再解释 domain 状态。

## 必须补齐的验收场景

- [ ] `reply(text) -> read(running)`：前一张回复显示已完成，只有 read 卡运行中。

- [ ] `reply(text) -> Stop`：只把当前被中断回复标为 stopped，较早回复不发生状态回流。

- [ ] `Stop(partial A) -> Continue -> reply B`：A 与 B 同时保留，顺序稳定，重启后仍一致。

- [ ] `delta -> message_end`：卡片 ID、sequence、DOM identity 和展开状态均不改变。

- [ ] `read -> providerOnly(text) -> read`：得到本地获取、Agent 回复、本地获取，前一张回复完成后不转圈。

- [ ] `read -> providerOnly(empty) -> read`：仍只有一张本地获取卡。

- [ ] Provider 自动重试：失败 Attempt draft 不进入 canonical history，旧 Attempt 的迟到 delta 不创建/移动卡片，UI 明确显示等待重试。

- [ ] Provider 暂停：时间线不伪造失败回复；顶部暂停条是唯一 Continue 入口，历史已完成卡片状态不变化。

- [ ] 旧 Session：工具仍在最终回答之前；无法精确恢复的顺序有 legacy 标识，二次加载不再变化。

## 最终判断

目前这套实现可以说“**静态排序第一版可用**”，不能说“Agent 卡片时序已经完整成立”。

最需要避免的是继续在 Renderer 上补条件，例如“如果不是最后一张回复就 completed”或“Stop 时只改最后一张”。这些规则仍然是在用数组位置猜物理事件，遇到 Continue、多 Attempt 和旧 Session 就会再次失真。正确的收口点在 main canonical activity：每段可见回复从首次出现起就有稳定身份、稳定位置和自己的生命周期，Renderer 只负责确定性聚合与展示。

## 根因与全面治理方案（2026-08-19）

### 根本原因

一句话概括：**Iris 已经有 Provider 上下文真相、执行控制真相和工具副作用真相，但没有“用户实际看见了什么、按什么顺序看见”的 canonical timeline 真相。**

当前卡片时间线由 Renderer 临时 join 四类不同生命周期的数据：

```text
messages             Provider 历史和最终 assistant 占位
toolEvents           main-owned 工具审计事实
Execution.draftContent  当前物理 Attempt 的瞬态流
Turn/Execution state 整轮意图与执行控制状态
```

这些对象各自合理，但它们不是同一种东西。Renderer 为了画一条时间线，被迫做以下错误替代：

* 用 Turn 状态代替每段 Reply 的状态；
* 用 Execution 唯一 draft 代替当前 Provider message；
* 用 Turn 唯一 assistant message 代替同一 Turn 内多次可见回复；
* 用 message/tool 两个数组的迁移遍历顺序代替历史真实顺序；
* 用“是否非空”同时承担 Provider 合法性、用户可见性和卡片存在性。

`sequence` 只是后来补上的排序坐标。它解决了“两个已提交对象谁在前”，却没有回答“对象何时诞生、是否还是同一个对象、属于哪个 Attempt、什么时候结束、失败后是否仍是用户已经看见的事实”。所以继续修 `.sort()` 或 JSX 条件只能缓解表象。

### 五个结构性成因

#### 1. 最初的“一轮一答”假设已经失效

Turn 创建时预留唯一 `assistantMessageId`，适合传统聊天的“用户一句、助手最终答一句”。工具型 Agent 的真实行为却是：

```text
短评 -> 工具 -> 短评 -> 工具 -> Stop -> Continue -> 新短评 -> 最终回复
```

同一 Turn 天然包含多条物理 assistant message 和多段用户可见文本。继续保留唯一可见 assistant 槽位，覆盖只是必然结果。

#### 2. Provider transcript 与用户时间线被当成同一份数据

Provider transcript 只允许保存能合法回放给模型的 committed frames。用户时间线则必须诚实记录已经展示过的内容，包括可能因 Provider 失败而不能重新注入上下文的不完整片段。

两者不是谁派生谁的简单关系：

* failed draft 可以是“用户确实看见过”，但不能进入下次 Provider context；
* interrupted partial 经过安全清理后，既是用户可见事实，也可以成为 Continue checkpoint；
* 空 tool-use envelope 是 Provider transcript 事实，但不是用户可见活动；
* tool result 是 Provider transcript 与工具审计事实，但不直接成为回复卡。

当前用一个 `IrisAgentMessage` 同时承担这些职责，导致“为了上下文合法而删除 draft”在 UI 上表现为历史消失。

#### 3. 状态归属层级错误

Turn 表达逻辑意图是否仍 open；Execution 表达该意图当前能否继续；Attempt 表达一次物理 Provider 请求；Reply 表达一段可见输出。四者状态应当单向汇总，不能从外层反向覆盖内层历史：

```text
Attempt 状态 -> 当前 Reply 如何结算
Execution 状态 -> 输入区、Stop、Continue 如何展示
Turn 状态 -> Fork、Undo 和下一轮边界
Reply 自身状态 -> 这张回复卡显示什么
```

当前 `turnState()` 反向把 Turn/Execution 状态批量投到所有 Reply，破坏了历史事实的单调性。

#### 4. 确定性迁移被误当成真实迁移

迁移确实需要结果稳定，但“稳定地给 messages 全部排在 tools 前面”不等于“恢复了真实顺序”。这里混淆了两个目标：

* deterministic：每次加载结果相同；
* truthful：结果尽可能符合已知因果关系，并诚实标记未知部分。

旧数据无法完全恢复时应表达不确定性，而不是写入一个看似精确的新 `sequence`。

#### 5. 产品状态机演进后，卡片契约没有同步退役

失败重试已经演进为 paused Execution + Continue，卡片方案中仍保留 failed Turn、fallback reply 和 Retry。代码为了兼容两套设计留下 `error/canRetry` 死分支。领域、投影、文档和测试各自正确了一部分，却没有一次统一的契约切换。

## 治理目标：四类真相分层

全面治理不应把所有数据塞进一个 event log，也不需要持久化 `cards[]`。建议明确四个边界：

| 层 | 真相 | 主要消费者 | 是否进入 Provider context |
| --- | --- | --- | --- |
| Conversation transcript | 合法的 user/assistant/tool provider frames | Pi adapter、Worker 恢复 | 是 |
| Activity timeline | 用户已经看见的 reply/tool 活动及顺序 | Renderer、重启恢复 | 不直接进入 |
| Execution control | Turn/Execution/Attempt、暂停、重试、Stop | main reducer、操作栏 | 否 |
| Effect ledger | 文件、终端和外部副作用事实 | 审计、详情、Undo 提示 | 否 |

Activity timeline 不是完整事件溯源，只是一份很小的 canonical 叙事读模型。卡片仍然由 activity 纯投影生成，不保存第二份 `cards[]`。

## 建议的数据模型

### 1. 新增独立 Reply Activity

建议把普通回复、providerOnly 短评和 interrupted partial 从“Turn 唯一 assistant 槽位”中解放出来：

```ts
interface IrisAgentReplyActivity {
  id: string;
  turnId: string;
  executionId: string;
  providerCallId: string;
  attemptId: string;
  sequence: number;
  source: 'assistant' | 'providerOnly' | 'interrupted';
  state: 'running' | 'completed' | 'stopped' | 'failed';
  contextDisposition: 'pending' | 'committed' | 'excluded';
  content: string;
  createdAt: number;
  completedAt?: number;
  error?: string;
  providerMessageId?: string;
  legacyOrder?: true;
}
```

其中最关键的不是字段数量，而是两个正交维度：

* `state` 回答“用户看到的这段回复后来怎样了”；
* `contextDisposition` 回答“这段内容能不能进入下一次 Provider context”。

这样 failed partial 可以保留为用户已经看见的失败片段，同时明确 `excluded`，不会污染模型历史。Stop 的安全 partial 则是 `stopped + committed`；Continue 后的新回复是另一个 activity。

### 2. Provider transcript 保持独立

`messages` 只保存合法的 Provider history frame，不再作为 Renderer 回复卡输入。它可以通过 `providerMessageId` 与 Reply Activity 关联，但允许以下关系：

```text
一个 transcript assistant frame -> 一个 Reply Activity
一个空 tool-use frame          -> 零个 Reply Activity
一个 failed visible draft      -> 一个 Reply Activity，零个 committed frame
```

Turn 不再需要把唯一 `assistantMessageId` 当作用户可见回答容器。若出于迁移兼容暂时保留，也只能是 deprecated provider-history 关联，不能继续承担 UI identity。

### 3. 工具活动沿用现有事实

`IrisAgentToolEvent` 已经接近合格的 timeline activity：有稳定 provider `toolCallId`、main-owned 状态和首次发生位置。只需与 Reply Activity 共用同一 Session activity sequence 分配器，不需要再造一份 Tool Card 数据。

### 4. 明确 sequence 是 Session activity sequence

建议保留 Session 全局严格递增，而不是每 Turn 归零，并改名为 `activitySequence`。理由：

* 全 Session 调试和日志关联更直接；
* Fork/Undo 前后的活动仍有唯一坐标；
* Renderer 虽按 Turn 分组，但不必依赖 Turn 局部计数器；
* 空洞合法，删除或隐藏活动时不重排。

必须保证 ID 与 sequence 一经分配永不改变。

## 完整生命周期规则

| 输入事件 | Timeline 行为 | Provider transcript 行为 |
| --- | --- | --- |
| 首个 user-visible text delta | 立即创建 running Reply，分配稳定 ID/sequence | 暂不提交 |
| 后续 delta | 原位追加同一 Reply | 暂不提交 |
| 正常 assistant message_end | Reply -> completed | 保存合法 assistant frame |
| toolUse envelope 有可见短评 | Reply -> completed | 保存 assistant tool-call frame |
| toolUse envelope 无文本 | 不创建 Reply | 仍保存 assistant tool-call frame |
| 用户 Stop，partial 可安全提交 | Reply -> stopped + committed | 保存清理后的 interrupted frame |
| Provider 失败且已有可见 partial | Reply -> failed + excluded | 不提交失败 frame |
| Provider 失败且无可见文本 | 不伪造 Reply；暂停条显示原因 | 不提交 |
| 自动重试 | 新 Attempt 后创建新的 Reply | 只提交成功 Attempt |
| Continue | 同一 Turn/Execution 下创建新的 Reply | 从 committed checkpoint 继续 |

这个表同时解决当前 fallback reply 争议：**无文本失败不伪造“Agent 说过一句话”；有文本失败则保留用户确实看见的片段，但明确不进入模型上下文。** Continue 仍由 Execution 暂停条拥有，回复卡不再放第二个恢复按钮。

## main 归约方式

### 1. Worker 提供稳定的物理消息关联

不要让 Renderer 或 main 根据文本猜一段 delta 属于哪条回复。Worker 应为每个 assistant message 提供稳定 `providerMessageId`，或使用可证明一一对应的 `attemptId + messageOrdinal`。

main 收到首个 displayable delta 时，在同一次 reducer 事务中：

1. 校验 session/epoch/turn/execution/providerCall/attempt correlation；
2. 创建 Reply Activity；
3. 分配 activity sequence；
4. 更新 Session revision；
5. 发出 projection patch 或新 snapshot。

后续 delta 只能命中该 Reply ID；迟到的旧 epoch/Attempt delta 必须在 reducer 边界丢弃，不能创建新 activity。

### 2. 状态转换必须单调

Reply 只允许：

```text
running -> completed
running -> stopped
running -> failed
```

terminal Reply 不得重新 running，不得被 Continue 改写，不得因 Turn 最终 closed 批量变状态。Continue 总是创建新 Reply。

Tool Event 同样保持现有的稳定位置与状态结算；如果未来需要取消态，应显式增加，不能借用 Turn 状态。

### 3. 控制状态与历史状态分开投影

Session/Execution presentation state 只控制：

* 顶部当前状态；
* 输入框可用性；
* Stop / Continue；
* Undo / Fork 是否可用。

Activity state 只控制对应卡片图标、摘要和错误区。两者不能在 React 中再次合并推导。

## Projection 与 UI 收口

新增独立纯模块，例如 `src/renderer/lib/iris-agent-projection.ts`，输入 canonical aggregate，输出：

```ts
interface AgentTurnView {
  id: string;
  userMessage: UserMessageView;
  activities: AgentActivityView[];
  actions: TurnActionsView;
}
```

投影规则只做：

1. 合并 Reply Activity 与 Tool Event；
2. 按 activity sequence 排序；
3. 连续本地获取聚合；
4. 生成卡片 view model；
5. 不读取 Provider transcript，不调用 `turnState()`，不猜 Attempt。

React 只渲染 view model。running spinner 只可能出现在 state=running 的单个活动；暂停条来自单独的 Session presentation state。

完成语义收口后，再把 IPC 从完整 Session snapshot 优化为 projection snapshot + 当前活动 patch。性能优化不能先于真相模型，否则只是更高效地传播错误语义。

## 旧数据迁移

### 迁移原则

1. 有现成 sequence 的新记录直接保留，绝不重排。
2. 没有 sequence 的记录按 Turn 重建，而不是先扫完整 messages 再扫完整 tools。
3. 优先利用 provider transcript 的 toolCall/toolResult 关系恢复因果边。
4. 其余记录用 `createdAt` 与稳定 tie-breaker 排序。
5. 无法确定精确顺序的 Reply 标记 `legacyOrder: true`。
6. migration 只运行一次；再次加载不得改变 ID、sequence 或分组。

### 建议的 legacy 因果规则

```text
assistant(toolUse) 必须早于其 tool event/toolResult
匹配的 toolResult 必须早于下一条 assistant frame
普通 final assistant 默认晚于该 Turn 已知工具链
同时间戳且无关联时保留源数组稳定次序，并标记 legacy
```

不能把“不知道”迁移成未经标记的精确事实。

### 领域不变量

- [ ] 每个可见 Activity 在 Session 内具有唯一 ID 与唯一 sequence。

- [ ] ID/sequence 创建后不可修改；内容只允许在 running 阶段追加。

- [ ] terminal Reply 不可重新 running，也不可被后续 Attempt 覆盖。

- [ ] `delta A -> message_end -> tool -> delta B -> message_end` 产生两个 Reply，A 在工具前、B 在工具后。

- [ ] 为每个旧 schema 建立 golden fixture，迁移后 snapshot 固定。

- [ ] 覆盖旧版“用户 -> 工具 -> 最终回答”，不得迁移回“回答 -> 工具”。

- [ ] 覆盖 providerOnly 短评、空 envelope、同时间戳、部分已有 sequence 和 Stop partial。

- [ ] 迁移后 flush、重启、再次加载，ID/sequence/card grouping 完全一致。

## 治理完成的退出条件

- [ ] Stop/Continue、自动重试、Provider 暂停、Worker 重建和应用重启都不会覆盖或重排已展示 Activity。

- [ ] 任意时刻最多只有当前物理 assistant message 对应的一张 Reply 显示 running。

- [ ] Timeline 与 Provider transcript 可以不同，但通过 correlation 可解释，且各自不变量成立。

- [ ] 新 Session 完全不依赖 Renderer 猜 sequence、Reply 状态或 Provider message 可见性。

### 最终定性

这次治理的核心不是“做一个更复杂的时间线”，而是承认 **Agent 对话包含两条不同但可关联的历史**：一条是模型下一次能合法看到的 Provider transcript，另一条是用户已经实际看到的 Activity timeline。

当前所有主要冲突都来自强行让前者兼任后者。把 Reply Activity 建成 main-owned canonical 事实，并让 Turn、Execution、Attempt、Reply 各自拥有正确状态边界后，排序、Stop/Continue、失败草稿、旧数据迁移和 Renderer 简化会同时得到统一解法。

## 第一性重构方案：废弃旧模型与旧数据（2026-08-19）

### 替代声明

用户已明确不接受兼容迁移和渐进妥协。本节完整替代上文“在现有 messages/toolEvents 上增加 Reply Activity、迁移 legacy sequence”的方案。

新的最终口径是：

* 不迁移任何旧 Iris Agent Session。
* 不读取任何旧 Session schema。
* 不保留 `legacySequence`、legacy order、旧 assistant 占位或 fallback 兼容分支。
* 一次性删除旧 Session、prompt/provider context artifact 和 Agent terminal output。
* 从零建立一条 main-owned canonical timeline；Renderer 不再合并平行数组。
* Provider transcript、运行控制、用户时间线和副作用账本从数据模型上彻底分离。

这次改造不是 schema v7 到 v8 的迁移，而是旧 Session 子系统退役、新 Session 子系统启用。

## 第一性原则

### 原则 1：用户看见过的事实不能消失或改写

一段文本只要已经显示给用户，就成为 Timeline 事实。以后 Provider 失败、自动重试、Stop、Continue、Worker 崩溃或应用重启，都只能结束这段 Activity，不能删除、覆盖或换 ID。

### 原则 2：时间线必须直接记录因果顺序，不能事后推断

Activity 在第一次成为用户可观察事实时进入 Timeline：

* 用户请求被 main 接受时；
* assistant 首个可展示 delta 到达时；
* provider tool call 被 main 接受并准备执行时。

进入时分配全 Session 唯一、严格递增的 `ordinal`。以后只更新内容和状态，永不移动。

### 原则 3：用户历史与模型上下文是两条不同的权威历史

Timeline 回答“用户实际看见了什么”。Provider Transcript 回答“下一次模型可以合法接收什么”。两者通过 ID 关联，但互不派生、互不冒充。

失败 partial 可以保留在 Timeline，同时不进入 Transcript。空 tool-use envelope 可以进入 Transcript，同时不进入 Timeline。

### 原则 4：控制状态不能反向污染历史状态

Turn、Run、Provider Call、Attempt 和 Activity 分别拥有自己的状态。外层对象只能决定当前可执行动作，不能批量改写已经完成的内层事实。

### 原则 5：所有用户可见变化先持久化、后广播

main 是唯一写入者。一个 Timeline Activity 或 delta 未成功写入 durable store 前，Renderer 不得先显示。这样应用崩溃后不会出现“用户刚才明明看见，重启却消失”的历史分叉。

### 原则 6：Renderer 是纯视图，不是领域解释器

Renderer 不接触 Provider 原始 message、Attempt、file effect 内容、cleanup queue 或 sequence fallback。它只消费 main 输出的 Session View 与 Activity patch。

## 全新领域模型

### 1. Session

```ts
interface AgentSession {
  id: string;
  projectRoot: string;
  anchor: IrisAgentAnchor;
  model: IrisAgentModelRef;
  revision: number;
  nextOrdinal: number;
  currentTurnId: string | null;
  currentRunId: string | null;
  turns: AgentTurn[];
  runs: AgentRun[];
  providerCalls: ProviderCall[];
  providerAttempts: ProviderAttempt[];
  timeline: TimelineActivity[];
  transcript: ProviderFrame[];
  effects: AgentEffect[];
  createdAt: number;
  updatedAt: number;
}
```

`timeline` 是唯一叙事顺序，不再存在“messages 与 toolEvents 分开保存、Renderer 再 merge”的结构。

### 2. Turn：一个用户意图

```ts
interface AgentTurn {
  id: string;
  userActivityId: string;
  state: 'open' | 'fulfilled' | 'abandoned' | 'removed';
  runIds: string[];
  createdAt: number;
  closedAt?: number;
}
```

语义固定：

* Send 创建新 Turn。
* Stop 或 Provider 失败不关闭 Turn。
* Continue 在同一 Turn 下创建新 Run。
* 暂停后发送新用户请求，把旧 Turn 标为 `abandoned`，再创建新 Turn。
* Undo 将最后一个 Turn 标为 `removed`，从活动视图隐藏；外部 Effect 继续保留。
* 只有 Agent 正常完成用户意图时才是 `fulfilled`。

### 3. Run：一次连续执行阶段

```ts
interface AgentRun {
  id: string;
  turnId: string;
  trigger: 'send' | 'continue';
  state: 'running' | 'stopping' | 'completed' | 'stopped' | 'failed' | 'abandoned';
  pauseReason?: 'user' | 'provider' | 'auth' | 'worker' | 'restart';
  error?: string;
  createdAt: number;
  completedAt?: number;
}
```

Run 取代当前长期复用的 Execution：

* 一次 Send 产生一个 Run；
* 每次 Continue 产生一个新 Run；
* Stop 结束当前 Run 为 `stopped`；
* Provider/Worker 不可恢复错误结束当前 Run 为 `failed`；
* Continue 不把旧 Run 改回 running。

因此控制状态也遵守 append-like 历史，不再让同一 Execution 在 paused/running 间来回改写。

### 4. Provider Call 与 Attempt

```ts
interface ProviderCall {
  id: string;
  runId: string;
  turnId: string;
  index: number;
  state: 'running' | 'completed' | 'failed' | 'aborted';
  attemptIds: string[];
  contextArtifactId: string;
}

interface ProviderAttempt {
  id: string;
  providerCallId: string;
  index: number;
  state: 'running' | 'completed' | 'failed' | 'aborted';
  error?: string;
  createdAt: number;
  completedAt?: number;
}
```

一个工具循环中的每次模型请求都是新 Provider Call；HTTP/SDK 自动重试是同一 Call 下的新 Attempt。Stop 后 Continue 属于新 Run，也从新 Provider Call 开始，不复活旧 Call/Attempt。

### 5. Canonical Timeline

```ts
type TimelineActivity =
  | UserActivity
  | ReplyActivity
  | ToolActivity;

interface ActivityBase {
  id: string;
  ordinal: number;
  turnId: string;
  runId?: string;
  createdAt: number;
}
```

#### User Activity

```ts
interface UserActivity extends ActivityBase {
  kind: 'user';
  content: string;
  assembledInputArtifactId: string;
}
```

用户请求也是 Timeline 一级事实，不再由 Turn 外壳特殊插到最前。main 只有在 anchor、model、assembled input 和持久化准备全部成功后，才原子追加 User Activity、Turn 与首个 Run。准备失败时不创建半个 Turn，Renderer 保留输入草稿。

#### Reply Activity

```ts
interface ReplyActivity extends ActivityBase {
  kind: 'reply';
  providerCallId: string;
  providerAttemptId: string;
  providerMessageId: string;
  state: 'streaming' | 'completed' | 'stopped' | 'failed';
  contextDisposition: 'pending' | 'committed' | 'excluded';
  content: string;
  completedAt?: number;
  error?: string;
}
```

规则固定：

* 首个 user-visible delta 创建 Reply，状态 `streaming + pending`。
* 后续 delta 只追加到同一 Reply。
* 正常 message_end 结算为 `completed + committed`。
* Stop 的 partial 一律结算为 `stopped`；能生成合法 provider-safe frame 时为 `committed`，否则为 `excluded`，原始可见文本仍保留在 Timeline。
* Provider 失败的可见 partial 结算为 `failed + excluded`。
* Provider 失败且从未产生可见文本，不创建假 Reply。
* 自动重试、Continue 和下一次 Provider Call 永远创建新 Reply。
* internal reasoning、signature、空 envelope 和纯 tool-call message 永远不创建 Reply。

#### Tool Activity

```ts
interface ToolActivity extends ActivityBase {
  kind: 'tool';
  providerCallId: string;
  providerAttemptId: string;
  toolCallId: string;
  tool: 'read' | 'edit' | 'write' | 'terminal';
  intent?: 'information' | 'operation';
  state: 'running' | 'completed' | 'failed' | 'canceled';
  input: CanonicalToolInput;
  result?: CanonicalToolResult;
  effectIds: string[];
  startedAt: number;
  completedAt?: number;
}
```

一个 provider tool call 恰好一个 Tool Activity。access/readFile/writeFile/exec 等低层 operation 只是该 Activity 的内部执行记录，不再成为 Timeline 候选。Tool Activity 被 main 接受时追加，完成时原位结算，ordinal 不变。

### 6. Provider Transcript

```ts
interface ProviderFrame {
  id: string;
  turnId: string;
  runId: string;
  providerCallId: string;
  role: 'user' | 'assistant' | 'toolResult';
  message: CanonicalProviderMessage;
  createdAt: number;
}
```

Transcript 只包含能重建合法 Provider context 的 committed frame：

* 用户 assembled input；
* 完整 assistant/tool-call frame；
* 对应 tool result；
* 正常 assistant 回复；
* 经过 provider-safe 清理的 stopped partial。

failed/excluded Reply、运行中 delta 和不完整 tool call 永不进入 Transcript。Renderer 完全拿不到该数组。

### 7. Effect Ledger

文件变更、terminal output 和未来外部副作用继续独立保存：

```ts
interface AgentEffect {
  id: string;
  turnId: string;
  runId: string;
  toolActivityId: string;
  kind: 'file-write' | 'terminal-output' | 'external';
  payloadRef: string;
  createdAt: number;
}
```

Timeline Tool Activity 只引用 Effect ID；大 diff、完整输出和文件前后内容不复制进 Session 主对象。Undo/Remove Turn 不删除 Effect，避免伪装副作用已经回滚。

## 唯一顺序模型

### Ordinal 分配

`nextOrdinal` 属于 Session，全局严格递增。追加 Activity 的 main reducer 在同一事务中：

```text
ordinal = nextOrdinal
nextOrdinal += 1
append timeline activity
revision += 1
durable commit
broadcast renderer patch
```

Activity 数组本身必须按 ordinal 追加；正常运行不调用 `.sort()`。加载时如果 ordinal 不连续、重复或数组逆序，store 直接判损坏并拒绝打开，不做猜测修复。

### 可见因果顺序

```text
user accepted
-> user activity
first visible assistant delta
-> reply activity
provider tool call accepted
-> tool activity
next visible assistant delta
-> next reply activity
```

空 assistant envelope 不进入 Timeline，因此不会制造序号或聚合断点。

## 状态机

### 正常工具 Turn

```text
Turn(open)
Run(running)
User Activity
Reply A(streaming -> completed)
Tool A(running -> completed)
Reply B(streaming -> completed)
Run(completed)
Turn(fulfilled)
```

Reply A 一旦 completed，工具运行、Run 完成或 Turn fulfilled 都不能再改变它。

### Stop 与 Continue

```text
Run 1(running)
Reply A(streaming)
Stop
Reply A(stopped + committed)
Run 1(stopped)
Turn 保持 open
Continue
Run 2(running)
Reply B(streaming -> completed)
Run 2(completed)
Turn(fulfilled)
```

时间线上 A 与 B 永久并存。Continue 不复用旧 Run、Call、Attempt 或 Reply。

### Provider 自动重试

```text
Provider Call 1
Attempt 1 -> Reply A -> failed + excluded
Attempt 2 -> Reply B -> completed + committed
```

用户看见过的 A 保留并明确标为“本次回复未完成”；模型历史只提交 B。自动重试不创建新 Run。

### Provider 失败后人工 Continue

```text
Run 1 -> failed
Turn 保持 open
顶部控制区显示失败原因与 Continue
Continue -> Run 2
```

失败时若没有可见 Reply，Timeline 不制造 fallback 卡。失败事实保存在 Run；当前 Turn 的控制区是唯一 Continue 入口。若已有 failed Reply，卡片只展示自身失败，不再放第二个 Continue/Retry。

### 暂停后发送新请求

```text
旧 Turn(open) -> abandoned
旧 Run 保持 stopped/failed
旧 Timeline Activity 全部不变
创建新 User Activity + Turn + Run
```

## 持久化架构

### 新存储根

新系统使用独立目录，完全不复用旧文件：

```text
<userData>/iris-agent-v2/
  manifest.json
  projects/<projectHash>/
    sessions/<sessionId>/
      snapshot.json
      journal.ndjson
      artifacts/
        assembled-input/
        provider-context/
        effects/
```

每个 Session 独立存储，避免一个项目所有 Session 因单文件重写互相放大。

### Journal 是持久化提交边界

main 为每个 Session 串行追加领域事件：

```ts
interface AgentJournalRecord {
  revision: number;
  previousHash: string;
  hash: string;
  event: AgentDomainEvent;
}
```

最小事件集：

```text
turn.started / turn.fulfilled / turn.abandoned / turn.removed
run.started / run.stopping / run.stopped / run.failed / run.completed
reply.started / reply.delta / reply.completed / reply.stopped / reply.failed
tool.started / tool.completed / tool.failed / tool.canceled
provider-call.started / provider-call.completed / provider-call.failed
provider-attempt.started / completed / failed / aborted
provider-frame.committed
effect.recorded
```

写入顺序：

1. reducer 验证 event 与当前 aggregate；
2. 追加带 revision/hash chain 的 journal record；
3. flush durable write；
4. 更新内存 aggregate；
5. 广播 patch。

启动时从原子 snapshot 的 `lastRevision/lastHash` 继续 replay journal。末尾半写记录可检测并截断；中间 hash/revision 断裂视为损坏，拒绝静默修复。

Snapshot 只是加速恢复，不是第二真相源。Session idle/关闭时原子写 snapshot；journal 仍保留足以验证 snapshot 之后的事件。

### 流式性能边界

Worker 将文本按有界 chunk 发送，而不是让每个 token 成为跨进程事务。每个 `reply.delta` chunk 必须先写 journal、后发 Renderer patch；一个 chunk 内文本不可再拆成 UI-only 状态。

这保证用户可见内容与 durable 内容严格一致，同时避免完整 Session snapshot 随每个 token 重发。

## Main 与 Worker 协议

Worker 必须为每个 Provider Call、Attempt 和 assistant message 提供稳定 correlation：

```ts
interface AgentCorrelation {
  sessionId: string;
  workerEpoch: number;
  turnId: string;
  runId: string;
  providerCallId: string;
  attemptId: string;
  providerMessageId?: string;
  toolCallId?: string;
}
```

协议事件直接表达领域事实，不再把原始 Pi event 整包交给 main 猜：

```text

assistant-message-completed
assistant-message-aborted
assistant-message-failed
tool-call-requested
tool-call-result

```

Pi adapter 负责识别 reasoning、text、tool call 和合法 Provider frame；main 负责权限、持久化、状态机与 Activity 创建。旧 epoch/Run/Call/Attempt 的任何迟到事件在 journal 写入前拒绝。

## Renderer 契约

main 输出唯一 `AgentSessionView`：

```ts
interface AgentSessionView {
  id: string;
  revision: number;
  state: SessionPresentationState;
  turns: AgentTurnView[];
}

interface AgentTurnView {
  id: string;
  state: 'active' | 'fulfilled' | 'abandoned';
  cards: AgentCardView[];
  actions: TurnActionsView;
}
```

`cards` 是传输时纯 projection，不持久化。main/shared projection 只遍历已经有序的 Timeline：

* User Activity -> 用户块；
* 连续 read/information Tool Activity -> 一张本地获取卡；
* Reply Activity -> 一张 Agent 回复卡；
* edit/write Tool Activity -> 文件写入卡；
* operation terminal Tool Activity -> 操作终端卡。

Renderer 接收：

```text
session.snapshot(revision)
activity.append(revision, activityView)
activity.patch(revision, id, patch)
session-state.patch(revision, state)
```

Renderer 只按 ID 更新。revision 旧则拒绝，revision 跳号则重新请求 snapshot。它不再读取 `messages`、`toolEvents`、`turns + executions` 联合状态，也不再排序。

### 已落地的模型

- main-only `AgentSessionAggregate` 成为唯一 canonical state；Turn、Run、Provider Call、Provider Attempt、Timeline Activity、Provider Transcript、Tool Operation 和 Effect Ledger 分层保存。

- Send 创建 Turn + Run，Continue 只在同一 open Turn 下创建新 Run。Stop、provider failure、Worker crash 和 restart 只终结当前 Run；已创建的 Reply/Tool Activity 不删除、不换位、不复用。

- Reply 在首个可见 delta 时创建稳定 identity。Reply terminal 后拒绝迟到 delta；无文本失败只投影 Session pause，不创建空 Reply。

- 工具以 provider toolCallId 形成一个稳定 Tool Activity，低层 operationId 进入独立幂等账本。重复 operation 返回已持久化结果，不重新执行副作用；Tool Activity 在 Provider tool result 后 terminal。

- Provider Transcript 只接收 committed provider frame。失败 Attempt 的 Reply 保留在 Timeline 并标记 excluded，但不进入下一次 Worker history。

### v2 持久化与 reset

- 新根目录为 `<userData>/iris-agent-v2/`。每个 Session 的 `journal.ndjson` 保存增量领域事务，不重复写整份 aggregate；严格递增 revision、previousHash 和 SHA-256 形成哈希链。`snapshot.json` 只在 Session 静止时作为可丢弃的恢复加速缓存。

- Renderer 可见变化均先完成 journal append、file flush 和 hash/revision 校验，再广播同 revision projection。重启从 snapshot 锚点继续重放，或删除 snapshot 后纯 journal 重放；末尾半写会在验证后截断，中段 malformed、hash 断链或 revision 断链会拒绝加载。

- 首次加载 v2 Store 时只允许删除解析后精确等于 `<userData>/iris-agent-sessions/` 与 `<userData>/iris-agent-output/` 的两个旧目录，随后写入幂等 `manifest.json`。Provider profiles/API keys、项目 `.iris/`、源码、Git 状态和既有外部副作用不在删除集合内。

### 协议与 Renderer

- Worker protocol 升至 v10，只发送有界 `assistant-text-delta`、规范化 `provider-message`、Provider Attempt/Context 和 Tool operation 事件，不再把 raw Pi event 交给 main。全部事件携带 Session、Worker epoch、Turn、Run、Provider Call、Attempt、Provider Message、toolCall 和 operation identity。

- Renderer 初始只消费 `IrisAgentSessionInfo.turns[].cards` snapshot；连续 revision 使用 Session header、Turn metadata 和按 Activity ID 的 card patch。旧 patch 被丢弃，revision 跳号会重新拉取 snapshot。Renderer 已删除领域排序、provider 可见性判断、legacy sequence、raw message/tool merge 和 fake reply fallback。

- Stop partial A -> Continue -> Reply B 的投影稳定保留 A、B 两张卡；pause/Continue 控件只出现在 Session control 区一次。
