我们现在打算实现一个新的功能：

左上角现在有一些图标，然后希望实现自定义功能

很简单：自定义图标在系统图标空一格之后出现

自定义图标属于项目，不属于软件，可以在设置中配置

只需要配置三项：图标名称（我们现在有图标库，就是库中的名称）

点击后需要执行的命令

用系统还是iris根目录终端执行这条命令

顺序可以在设置中排序

不知道现在iris文件夹有没有项目级配置文件

## 2026-08-08 方案

### 现状结论

当前没有正在生效的通用项目级配置机制。

* 机器级设置由 `SettingsManager` 保存到 `~/.iris/settings.json`，开发版保存到
  `~/.iris-dev/settings.json`，同一份配置会被所有项目共享。

* 当前仓库的 `.iris/styles.json` 是已经退出运行链路的遗留文件。项目初始化明确不再
  创建它，现有代码也不再读取或维护它，不能作为本功能的配置基础。

* `AGENTS.md` 中的 `<iris-project>` 是给 agent 阅读的项目提示词，不是 App 配置，
  不应在其中混入工具栏和可执行命令。

* 左上角目标位置是 `LeftPane` 顶部 44px 工具栏。该区域目前依次放置项目菜单、
  新建工作区、排序、筛选、Todo 和 Git 等系统动作。

因此建议新建 `.iris/settings.json`，作为 Iris 的项目级 App 配置。它与机器级
`~/.iris/settings.json` 采用相同名称、不同作用域，职责清楚，也符合 Iris 自有项目
数据放在 `.iris/` 下的约定。没有自定义动作时不主动创建该文件。

### 配置模型

```json
{
  "version": 1,
  "toolbar": {
    "actions": [
      {
        "icon": "rocket",
        "command": "npm run dev",
        "terminal": "iris"
      },
      {
        "icon": "database-backup",
        "command": "npm run backup",
        "terminal": "system"
      }
    ]
  }
}
```

每个动作只暴露需求中的三个字段：

| 字段         | 含义                                                 |
| ---------- | -------------------------------------------------- |
| `icon`     | Lucide 图标名，使用与 Lucide 官网一致的 kebab-case，例如 `rocket` |
| `command`  | 交给用户 shell 执行的完整命令                                 |
| `terminal` | `iris` 或 `system`                                  |

数组顺序就是图标显示顺序，不额外保存 `order`。内部渲染标识和配置 revision 都可以
运行时派生，不增加用户需要理解的字段。

### 两种执行语义

这里把“系统终端”定义为 Iris 外部的操作系统终端：

* `iris`：始终新建一个项目根 hub 终端，工作目录固定为项目根，执行命令并切换到
  根终端视图；命令结束后保留 shell，便于查看输出和继续操作。

* `system`：打开外部系统终端，工作目录同样固定为项目根并执行命令；Iris 只确认
  启动成功，不跟踪输出和后续生命周期。

* 不向某个已经存在的终端发送命令。现有终端可能正在运行 TUI、服务或处于子目录，
  直接注入命令会产生不可预测行为。

* Windows 复用当前的 `pwsh -> powershell -> cmd` 探测原则；其他平台使用独立的
  system-terminal adapter。找不到可用外部终端时明确报错，不静默改用 Iris 终端。

Iris 内部执行可以复用现有 `SessionManager` 的 PTY、回放和状态能力，但应新增
“按项目动作启动”的入口，不能把项目快捷命令临时写入机器级 `settings.agents`，也
不能把它伪装成 agent launcher。

### 设置页

设置页新增“项目”分类，仅在当前窗口已经打开并初始化 Iris 项目时允许编辑。分类中
增加“左栏快捷命令”区域：

* 使用紧凑的有序列表展示动作。

* 图标字段提供 Lucide 名称搜索、即时预览和合法性校验。

* 命令使用单行输入，编辑时不因配置广播丢失正在输入的内容。

* 执行位置使用 `Iris 终端 / 系统终端` 分段控件。

* 每行提供上移、下移和删除按钮，列表末尾提供添加动作。

* 保存完整 actions 数组，沿用现有设置页的即时保存交互；主进程负责最终校验和原子
  写入。

* 没有活动项目时显示不可编辑空态；项目尚未初始化时引导先初始化，不在任意项目根
  私自创建 `.iris/`。

### 左栏展示

系统图标组渲染完成后，仅在存在自定义动作时插入一个固定间距，再按配置数组顺序显示
自定义图标。

* 自定义按钮沿用现有 `h-7 w-7`、ghost button 和 tooltip 视觉规范。

* Tooltip 显示完整命令和执行位置，避免用户只能根据图案猜测行为。

* 点击 Iris 终端动作后切换到根 hub，让执行结果立即可见；点击系统终端动作时保持
  当前 Iris 视图不变。

* 工具栏保持单行、不换行。宽度不足时，尾部使用“更多”菜单收纳放不下的自定义
  动作，菜单中的顺序仍与配置一致。

* 图标加载使用 `lucide-react/dynamic` 提供的图标目录，不手工维护另一份容易漂移的
  图标白名单。未知图标在设置页报错，不进入可执行工具栏。

### 主进程与 IPC 边界

建议增加三个项目级接口：

```text
project-settings:get
project-settings:update
project-command:run
```

读写和执行都必须携带当前 `ProjectScope`，由 main 校验项目 root 和 generation，避免
项目切换期间的旧 renderer 请求作用到新项目。

项目配置查询结果同时返回一个由文件内容派生的 revision。点击图标时 renderer 只发送
动作下标和 revision；main 在当前项目配置中重新解析对应动作，revision 过期就拒绝
执行。执行接口不接受 renderer 直接传入的任意 command，从而避免旧界面、配置外部
修改和项目切换造成误执行。

配置读写可以放入独立的、每窗口拥有的 `ProjectSettingsManager`：

* 固定只访问当前项目下的 `.iris/settings.json`，复用现有项目路径越界保护。

* 缺失文件返回 `{ version: 1, toolbar: { actions: [] } }`。

* 写入采用临时文件加原子替换，完整校验通过后才提交。

* JSON 损坏时保留原文件并返回诊断，不使用默认值覆盖用户内容。

* watcher 发现外部修改后重新加载并广播；无效条目不渲染、不执行，但不影响其他
  合法条目。

### 执行安全

项目配置可能来自刚 clone 的陌生仓库，因此其中的 command 属于可执行内容，必须建立
显式信任边界：

* 打开项目、扫描配置和渲染图标都不得自动运行命令。

* 某项目第一次执行自定义动作时，确认框展示项目路径、完整命令、工作目录和终端类型。

* 确认结果按“规范化项目根 + 配置 revision”保存在机器级设置中，不写回项目文件，
  因此项目动作仍然只有三个配置字段。

* 项目配置变化后 revision 改变，需要重新确认；同一份已确认配置不必每次弹窗。

* 限制动作数量、图标名长度和命令长度，拒绝空命令、非法 terminal 值和异常大的配置。

* cwd 通过 spawn 选项单独传递，不能拼进 command；命令本身作为一个 shell 参数传递，
  避免项目路径中的空格或 shell 元字符改变命令结构。

## 2026-08-09 启动时图标缺失根治

人工验收发现，项目启动后左栏自定义图标不显示，进入设置再返回后才出现。问题不是设置页
负责加载配置，而是项目打开事务和工具栏 DOM 生命周期各有一个缺口，设置页切换造成的
重新挂载恰好掩盖了它们。

第一处问题在项目首次打开链路。`project.open` 原先先提交 `projectStore.handleOpened()`，
把项目发布为 `ready`，再通过独立 IPC 刷新项目配置。renderer 因而可能先渲染一个配置
快照为空的项目界面。恢复已经由 main 持有的 active scope 时虽然会在首帧前等待配置水合，
但首次打开、启动时 requested root 和手工切换项目走的是上述不完整提交路径，两条初始化
路径没有遵守同一个 ready 不变量。

第二处问题在 `ProjectToolbarActions`。配置快照为空时组件返回 `null`，但负责建立
`ResizeObserver` 的 effect 只在首次渲染运行一次；此时没有真实容器可观察，配置随后到达
并挂载容器时 effect 不会重跑。工具栏一直保留初始的单槽位测量结果，自定义动作被折叠；
打开设置会卸载三栏界面，返回时组件在配置已经存在的条件下重新挂载，观察器才偶然建立，
所以表象像是“进入设置才加载配置”。

根治遵守两个结构性不变量：

* 项目只有在扫描、会话和项目配置属于同一个 `ProjectScope` 且同时可用时，才能作为一次
  完整的 `ProjectOpenResult` 提交给 renderer。

* DOM 观察器的建立和释放必须绑定真实 DOM 节点的 attach/detach，而不是绑定组件第一次
  render 的时刻。

已完成整改：

* `ProjectOpenResult` 现在强制携带 `projectSettings`。main 在项目切换串行事务内读取对应
  scope 的配置和机器级信任状态，再结束 `project.open`，避免 ready 后补发配置查询。

* renderer 的 `project.open` commit 先安装同事务配置快照，再发布项目 ready 状态；首次
  打开不再调用 `projectSettingsStore.refresh()` 进行补偿。active scope 恢复仍保留显式水合，
  用于 renderer reload 时读取 main 已持有项目的当前配置。

* 工具栏改用稳定 callback ref 管理 `ResizeObserver`。容器晚于首 render 出现时立即建立
  观察，节点替换或卸载时断开旧观察器，不再依赖进入设置触发重挂载。

## 2026-08-09 移除 conhost 回退

人工验证确认 `conhost.exe` 回退只会出现一闪而过的空控制台。根因包含两层：Windows
Terminal 的 `wt.exe` 是 App Execution Alias，Node 对别名执行 `stat` 会返回 `EACCES`，
原先基于 `existsSync()` 的探测因此把已安装的 Windows Terminal 误判为不存在；回退链路又
以 `stdio: ignore` 直接启动 conhost，使交互 shell 在命令结束后读到 EOF 并退出。main 的
`spawn` 日志只证明进程创建，不能证明终端窗口持续可用。

按产品决策删除 conhost 回退和文件系统预探测。Windows 系统终端动作现在只调用
`wt.exe -w new`；操作系统无法解析或启动 `wt.exe` 时，IPC 直接返回
`SystemTerminalError`，renderer 使用现有失败弹窗展示错误，不再静默降级。

自动验证结果：
