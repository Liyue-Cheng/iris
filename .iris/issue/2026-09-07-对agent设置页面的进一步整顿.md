# Iris Agent 设置页与供应商管理全面改造方案

## 目标与范围

本次改造聚焦设置页的 `Iris Agent` 区域，目标是让用户以“连接供应商 → 获取模型 ID → 选择要使用的模型”为主线完成配置，而不是面对一张需要维护大量参数的模型表。改造包含：

* 供应商管理区域的完整视觉重做。

* 供应商连接、凭据、模型发现和模型启用关系的业务语义调整。

* 模型列表只保存“模型 ID 及必要的发现元数据”，不在设置页一次性铺开所有远端模型，也不要求用户逐个录入上下文/输出参数。

* Iris Agent 会话中的模型下拉框同时支持“已发现模型”和“手工填写模型 ID”。

* 保留现有 profile 文件和 IPC 的兼容迁移能力，避免已有用户配置失效。

## 现状问题（基于当前实现与截图）

### 视觉与信息架构

* 页面大面积留白，内容从顶部横向铺开，供应商、凭据、模型目录之间缺少清晰的层级和分组。

* “PP / OpenAI · URL / 删除”这一行像裸表格记录，供应商身份、连接状态、操作入口不够明确。

* API Key 输入、更新按钮和模型目录挤在同一水平节奏中，用户无法快速判断当前连接是否可用。

* 模型目录采用四列宽表，每一行暴露上下文窗口、预设、输出预留等内部参数；这些参数对大多数用户没有决策价值，却制造了密集、难读、易误配的表单。

* “从供应商获取模型”和“添加模型”是并列按钮，无法表达发现、筛选、启用之间的关系；获取后直接把全部模型写入 profile，造成模型列表膨胀。

* 成功态仅以“模型配置已保存”这类文字出现，缺少连接状态、最近同步时间、发现失败原因等可扫描反馈。

* 删除供应商只有图标，没有与供应商配置影响范围关联的提示；窄窗口下长 URL 和模型参数也容易挤压布局。

### 业务逻辑问题

* `IRIS_AGENT_PROVIDER_PROFILE_DISCOVER` 当前会把远端返回的所有模型写入 profile；“发现”与“用户选择”被强耦合。

* `IrisAgentConfiguredModel` 要求持久化上下文、输出、压缩等多项运行参数，导致发现结果必须先被“配置化”才能使用。

* 模型目录没有独立的“可用远端模型缓存”和“用户启用模型集合”概念，无法支持只选择少量模型。

* 会话模型选择器只消费最终 catalog；当用户知道一个模型 ID 但供应商目录没有返回它时，没有一致的手工模型 ID 输入路径。

* 发现失败时缺少按供应商隔离的状态、重试和保留上次成功结果策略。

## 新的用户心智模型

```text
添加供应商
  -> 填写 Base URL + API Key
  -> 测试连接并获取模型 ID
  -> 在发现结果中勾选/启用少量模型
  -> Iris Agent 会话下拉框选择已启用模型
  -> 也可在下拉框中切换到“手工输入”，填写任意模型 ID
```

“获取模型”是查询动作；“启用模型”才是改变用户配置的动作。查询结果不应自动全部变成启用项。

## 视觉与交互方案

### 页面骨架

* Iris Agent 页面改为窄而稳定的内容列（建议 `max-width: 920px`），左侧保留设置分类导航，右侧不再使用超宽表格。

* 顶部使用页面标题、简短说明和一个全局状态摘要：已连接供应商数、已启用模型数、最近一次发现时间/失败数。

* 供应商列表使用纵向列表项或轻量 section（每个供应商一个独立管理单元），而不是嵌套卡片套卡片。单元内部按“身份与状态 → 凭据 → 模型发现/启用”分段，使用细分隔线和留白建立层次。

* 所有按钮使用图标+短文案；刷新、显示/隐藏 Key、删除、测试连接等使用现有 Lucide 图标，并提供 aria-label/tooltip。

* 颜色以当前主题变量为准，成功/警告/错误只用于状态，不再整页使用粉色边框和浅色填充。

### 添加供应商

采用两步表单：

1. 选择供应商类型（OpenAI、Anthropic、OpenAI Compatible、Anthropic Compatible），显示类型说明和默认 Base URL。
2. 输入显示名称、Base URL、API Key；点击“添加并测试连接”。

提交后立即执行连接测试和模型发现：

* 成功：供应商进入列表，显示绿色“已连接”，同时展示发现到的模型数量；默认不启用任何模型，要求用户明确勾选。

* 失败：供应商不写入或保留为“连接失败”草稿（实现上建议先校验再写入，网络失败时保留 profile 但不影响其他供应商），展示可复制错误和“重试连接”。

* API Key 只显示掩码；更新 Key 后自动标记模型发现结果为“需要刷新”，不在界面回显密钥。

### 供应商条目

每个条目首行展示：供应商名称、类型、Base URL、连接状态、最近同步时间、启用模型数量，以及右侧的“刷新模型”“更多/删除”。

凭据区改为单行紧凑编辑：已配置时显示“已配置 · 输入新 Key 可替换”，点击更新后反馈验证结果；支持测试连接但不强制保存按钮。

模型区分为三个状态：

* 未同步：显示“获取模型”主按钮和说明。

* 同步中：按钮进入 loading，保留旧结果，显示进度/不可用原因。

* 已同步：显示发现数量、上次同步时间、筛选框和模型 ID 列表。

发现结果使用可搜索的紧凑列表：每项显示模型 ID（主文本）、名称/能力等可选元数据（次文本）、启用开关；不展示上下文窗口、输出预留等高级内部参数。提供“全选当前筛选结果”“清空启用”快捷操作，但不自动全选。

### 模型 ID 选择器

在 Iris Agent 会话顶部模型下拉框中：

* 第一组显示所有已启用模型，按供应商分组，标签为“供应商名 / 模型 ID”。

* 第二组显示“手工输入模型 ID”。选择后出现可编辑输入框；输入非空即可提交，不要求该 ID 出现在发现目录中。

* 手工模型只绑定当前 Session 的 provider + modelId，不写入供应商的启用列表，除非用户在设置页显式“保存到供应商”。

* 当前选择不可用时保留原值并标注“不可用”，允许用户切换或重新发现。

* 运行中的 Session 禁止切换模型；暂停/空闲时切换，沿用现有 `IRIS_AGENT_SET_MODEL` 语义。

## 数据模型与持久化调整

建议将现有配置拆成“发现缓存”和“启用集合”，同时保留旧字段读取：

```ts
interface IrisAgentDiscoveredModel {
  modelId: string;
  displayName?: string;
  api?: 'openai-responses' | 'anthropic-messages';
  capabilities?: { reasoning?: boolean; input?: ('text' | 'image')[] };
  contextWindowTokens?: number;
  maxOutputTokens?: number;
  discoveredAt: number;
}

interface IrisAgentProviderProfileInfo {
  // 现有身份字段
  ...
  models: IrisAgentDiscoveredModel[];      // 最近一次发现结果，仅作缓存
  enabledModelIds: string[];               // 用户明确启用的 ID
  lastDiscoveredAt?: number;
  discoveryError?: string;
}
```

实现兼容策略：

* 读取旧 `models` 时，将 `source: manual` 的模型 ID 合并进 `enabledModelIds`；旧 discovered 模型保留为发现缓存，并默认不启用，避免升级后突然增加会话选项。

* 新写入采用版本 `2` 文件格式；写入前保留 `.bak`。旧版本读取后在首次修改时迁移。

* `IrisAgentConfiguredModel` 的运行参数改为可选覆盖，只在用户明确进入“高级模型设置”时保存；正常发现/启用流程只依赖 `modelId`，运行时使用远端元数据或默认值。

* 启用列表写入时去重、保持用户排序；发现刷新不删除已启用但暂时未返回的 ID，而是标记为“目录中暂不可见”，避免网络/权限波动导致会话配置丢失。

## IPC 与后端行为调整

保留现有通道名称以降低迁移成本，但修改返回语义，并可新增查询通道：

* `IRIS_AGENT_PROVIDER_PROFILE_DISCOVER`：只刷新指定 profile 的发现缓存和 `lastDiscoveredAt`，不自动把所有结果写入启用列表；返回该 profile 的发现结果、错误和同步状态。

* 新增 `IRIS_AGENT_PROVIDER_PROFILE_ENABLED_MODELS`（或复用 MODELS 通道）：提交 `enabledModelIds` 与可选高级覆盖，服务端校验 ID 非空、去重并返回最新 profile。

* `IRIS_AGENT_MODELS`：构建会话 catalog 时只返回 `enabledModelIds` 对应模型；保留手工 session 模型的临时注入项。

* `IRIS_AGENT_PROVIDER_PROFILE_SET_KEY`：更新 Key 后将发现缓存标记为 stale，下一次进入设置页显示“需要刷新”，不静默沿用旧目录作为最新事实。

* 发现请求按 profile 串行去重；同一 profile 的并发刷新复用 Promise，避免重复网络请求。其他供应商刷新不被阻塞。

* 后端对供应商返回的模型 ID 做 trim、去重和长度限制；拒绝空 ID、控制字符和超长列表。错误按 profile 隔离，catalog 仍返回其他健康供应商。

* 删除 profile 前检查是否有 Session 正在使用；若有，先提示用户切换模型或确认删除，删除后广播 `IRIS_AGENT_PROVIDERS_CHANGED`，使会话模型选择器即时剔除失效项。

## 状态与错误处理

每个 profile 维护 `idle / loading / ready / stale / error` 投影状态。界面必须区分：

* “没有获取过模型”

* “获取成功但用户尚未启用模型”

* “上次获取失败但仍保留旧结果”

* “已启用模型不在最近目录中”

错误消息提供供应商名、HTTP 状态/网络原因和重试入口；不把原始 API Key 或完整请求头写入日志、错误文本或渲染层。

### Phase 1：数据与 IPC 契约

* 扩展 shared types，加入发现缓存、启用 ID、同步状态字段和版本迁移函数。

### Phase 2：设置页重做

* 新增供应商条目状态头、凭据行、发现 toolbar、搜索/筛选列表、启用开关和空/错/加载态。

* 增加供应商级操作反馈和删除确认文案；补充中英文 i18n key。

* 以 920px 内容列和 640px 以下断点验证布局，确保 URL、模型 ID、错误文本不溢出。

### Phase 3：会话模型选择器

* 重写 `IrisAgentView` 顶部模型选择器，加入供应商分组与“手工输入模型 ID”分支。

* 增加手工 ID 校验、不可用状态、暂停/运行态切换限制和错误反馈。

* 让 catalog 只返回启用模型，同时兼容当前 session 已选但已被禁用/删除的模型。

### Phase 4：迁移与验收

* 首次启动/首次修改时完成 v1 → v2 迁移并写 `.bak`。

* 手工验证：新增 OpenAI Compatible、错误 Key、断网刷新、恢复网络、删除正在使用的供应商、长模型 ID、窄窗口和深色主题。

* 自动测试覆盖 provider-profiles、pi-adapter、IPC handler、renderer store/selector；不运行 `npm run build`/`npm run dist`，除非另有明确要求。

## 验收标准

* 用户打开 Iris Agent 设置页，首屏能看懂“有几个供应商、连接是否正常、启用了几个模型、何时同步”。

* 点击“获取模型”不会自动启用全部远端模型；用户必须显式启用。

* 模型列表只展示模型 ID 和轻量元数据，不再要求逐行配置上下文窗口/输出预留。

* Iris Agent 会话模型下拉框只出现已启用模型，并支持手工输入任意模型 ID。

* 刷新失败不清空上次发现结果；错误可定位到具体供应商并可重试。

* 旧 profile 文件升级后 API Key、手工模型和现有会话仍可继续工作。

* 设置页在当前主题下视觉层级清晰，无超宽空白、无横向滚动、无控件重叠；按钮和图标具备可访问名称。

## 交互方案修正（2026-09-07）

上一版方案中“发现结果与启用列表拆分”“会话模型选择器独立管理”等设计过重，不符合本次需求，现以以下交互为准：

* 模型 ID 始终是普通可编辑文本框。

* 在没有获取到候选模型前，文本框右侧不显示任何下拉控件。

* 获取模型成功后，文本框最右侧出现下三角按钮；点击后打开候选模型 ID 菜单，选择项只负责替换文本框当前内容，用户仍可继续手工编辑。

* 上下文窗口使用完全相同的模式：默认普通数字文本框；获取到模型且存在上下文候选值后，右侧才显示下三角，选择候选值替换当前输入。

* 不引入独立 Combobox。项目当前已安装并封装 `@radix-ui/react-dropdown-menu`，使用 `DropdownMenu + DropdownMenuTrigger + Input` 组合即可满足需求；Radix Select 不适合，因为它不是可编辑文本框。
