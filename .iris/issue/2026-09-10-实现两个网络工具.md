### 三、核心实现逻辑

#### 1. 搜索引擎选择

**方案 A：使用公共搜索 API**
- DuckDuckGo HTML 搜索（无需 API key）
- 优点：免费、简单
- 缺点：可能被限流、结果质量一般

**方案 B：支持配置搜索引擎**
- Google Custom Search API
- Bing Search API
- 需要用户配置 API key
- 优点：结果质量高、稳定
- 缺点：需要额外配置

**推荐：方案 A 作为默认，方案 B 作为可选配置**

#### 2. SSRF 防护

```typescript
function validateUrl(url: string): void {
  const parsed = new URL(url);
  
  // 只允许 http/https
  if (!['http:', 'https:'].includes(parsed.protocol)) {
    throw new Error('Only http:// and https:// URLs are allowed');
  }
  
  // 阻止内网地址
  const hostname = parsed.hostname.toLowerCase();
  const blockedPatterns = [
    /^localhost$/i,
    /^127\./,
    /^10\./,
    /^172\.(1[6-9]|2[0-9]|3[01])\./,
    /^192\.168\./,
    /^169\.254\./,
    /^\[::1\]$/,
    /^\[fe80:/i
  ];
  
  if (blockedPatterns.some(pattern => pattern.test(hostname))) {
    throw new Error('Access to private/internal addresses is not allowed');
  }
}
```

#### 3. 内容处理流程

**web_fetch 实现伪代码**：
```typescript
async function webFetch(url: string, options: FetchOptions) {
  // 1. URL 验证
  validateUrl(url);
  
  // 2. 发起请求（带超时和大小限制）
  const response = await fetch(url, {
    signal: AbortSignal.timeout(options.timeout * 1000),
    headers: {
      'User-Agent': 'IrisAgent/0.1 (https://github.com/Liyue-Cheng/iris)'
    }
  });
  
  // 3. 检查响应状态
  if (!response.ok) {
    throw new Error(`HTTP ${response.status}: ${response.statusText}`);
  }
  
  // 4. 读取内容（流式，带大小限制）
  const contentType = response.headers.get('content-type') || '';
  let html = '';
  let totalBytes = 0;
  const maxBytes = options.maxContentLength || 1024 * 1024;
  
  for await (const chunk of response.body) {
    totalBytes += chunk.length;
    if (totalBytes > maxBytes) {
      html += chunk.toString('utf8').slice(0, maxBytes - (totalBytes - chunk.length));
      break;
    }
    html += chunk.toString('utf8');
  }
  
  // 5. 转换为 Markdown
  const markdown = htmlToMarkdown(html);
  
  // 6. 返回结果
  return {
    content: [{ type: 'text', text: markdown }],
    details: {
      url,
      finalUrl: response.url,
      statusCode: response.status,
      contentType,
      contentLength: totalBytes,
      truncated: totalBytes >= maxBytes
    }
  };
}
```

## 外部方案复核（2026-09-11）

### 结论先行

不建议把 `idefav/web-search` 或 `webfetch-llm` 原样嵌入 Iris，也不需要从零发明搜索和网页抽取算法。更合适的路线是：**复用成熟项目的协议和实现思路，优先把 Iris 做成外部 Web Search Gateway 的客户端适配层；同时保留一个轻量的本地 `web_fetch` 兜底实现。**

### 1. `idefav/web-search` 实际是什么

该项目不是一个可直接 `npm install` 后在 Electron 进程内调用的单一库，而是一个完整的自托管服务：Docker Compose + Camofox Browser + REST/MCP Gateway。它提供 `web_search`、`web_fetch` 两个只读工具，包含 Bearer 鉴权、SSRF 代理隔离、多搜索引擎回退、浏览器渲染、OpenAPI/REST 客户端和 Pi 插件。

仓库许可证为 MIT；截至本次调研 GitHub API 显示约 7 stars、1 fork、0 open issues，创建于 2026-08-02，最近推送 2026-08-09。项目很新，功能覆盖较完整，但不宜把它当作长期稳定的核心依赖。

**可复用部分**：REST/MCP API 形状、工具参数（query/count/freshness/include/exclude domains、url/max_chars）、错误模型、SSRF 和不可信网页内容边界、Pi 插件接入方式。

**不适合直接搬入 Iris 的部分**：Camofox 浏览器和 Docker 部署、Squid SSRF 网络隔离、服务端运行时、与 Iris 现有 `pi-adapter` 工具生命周期的耦合。若采用它，Iris 只需实现一个 HTTP 客户端工具，服务作为可选外部组件运行。

### 2. `webfetch-llm` 实际是什么

这是 Python 包（当前 PyPI 版本 0.1.3，MIT，要求 Python >=3.10），默认通过 DuckDuckGo，可选 Brave/Serper/Tavily，多引擎 RRF 融合；网页抽取链包括 trafilatura、readability、newspaper4k，Playwright/PDF/表格/语义重排属于可选额外依赖。它还带 MCP server、缓存和压缩/排序流水线。

仓库为 `firish/webfetch`，截至本次调研约 55 stars、6 forks、0 open issues，创建于 2026-04-20，最近推送 2026-07-23。它更像“本地 Python 搜索研究服务”，不是 Node/Electron 原生依赖。直接在 Iris 中引入会增加 Python 运行时、进程管理、依赖安装和跨平台打包成本。

**可复用部分**：搜索提供商抽象、DDG 被阻断时的 fallback/circuit breaker、页面抽取降级链、缓存和结果压缩思路。

**不适合直接搬入 Iris 的部分**：Python 服务生命周期、Playwright/ML 依赖、SQLite 语义缓存、面向长研究任务的多工具接口（`fetch_url`、`save_finding`、`status` 等超出当前两个工具范围）。

### 3. 是否“网上方案直接就可以”

分情况：

- **如果目标是尽快可用**：可以直接接入 `idefav/web-search` 的远程 REST/MCP Gateway。Iris 在 `pi-adapter` 中注册两个薄工具，把参数转发到 `/v1/search` 和 `/v1/fetch`，并处理鉴权、超时、响应截断和错误映射。这样几乎不需要自己实现搜索引擎解析、浏览器渲染和 SSRF 代理。
- **如果目标是 Iris 单机开箱即用**：不能直接依赖上述项目。`web-search` 需要 Docker/Camofox 服务；`webfetch-llm` 需要 Python 及一组较重依赖。应当自己写一个小型 Node `web_fetch`，搜索则接入外部 API/Gateway，避免在 Electron 内维护爬虫。
- **如果目标是长期产品能力**：不要复制任一项目的全部代码。采用“协议兼容 + 可插拔后端”架构，后端可以是 `idefav/web-search`、自建搜索 API，或未来的其他服务；Iris 只稳定自己的工具 schema、错误格式和安全边界。

### 4. 对当前实现方案的修正

原方案中“新增 cheerio/turndown、默认抓 DuckDuckGo HTML、在 Electron 内自行完成全部 SSRF/搜索解析”的范围偏大，且会重复维护外部项目已经解决的问题。建议改为三层：

1. **Iris 工具层**：固定 `web_search` / `web_fetch` schema 和 LLM 可读的返回格式。
2. **Gateway 客户端层（首选）**：通过配置的 endpoint + API key 调用外部 REST；支持代理、超时、最大字符数、错误归一化。
3. **本地 fallback（可选）**：仅实现受限 `web_fetch`（HTTP/HTTPS、DNS/IP 私网阻断、响应大小/超时、纯文本或简单 HTML 提取），不实现搜索引擎抓取和浏览器渲染。

### 5. 推荐决策

**推荐采用“外部 Gateway 优先，轻量本地 fetch 兜底”，暂不引入 Python 包，也不把 Docker/Camofox 打进 Iris 发布包。**

实施顺序：

- Phase 1：定义 Iris 内部 `WebClient` 接口和配置项；实现远程 Gateway 客户端及两个工具注册。
- Phase 2：加入本地 `web_fetch` fallback，明确能力降级（无 JS 渲染、无搜索）。
- Phase 3：根据真实使用量再决定是否提供一键启动 Gateway 的开发者脚本；不纳入默认生产安装。

### 6. 需要保留的风险

- 外部项目版本和 API 可能变化，应锁定 endpoint 协议版本并做响应 schema 校验。
- 网页内容必须标记为不可信输入，不能让页面指令改变 Iris 工具策略。
- Gateway 不可用时，工具应返回可理解的结构化错误，不能让 agent loop 因异常直接中断。
- 若未来分发 Gateway，需另行评估 Docker、浏览器镜像和 SSRF 隔离的运维责任。

### 关键发现

1. **“直接复用”最现实的形式是 MCP 接入，而不是复制源码。** Iris 的 agent 基于 Pi 适配层，理论上可以启动一个 stdio MCP server，或调用 Streamable HTTP MCP；这样 Fetch/Firecrawl/SearXNG 都能替换后端，Iris 只维护工具注册和配置。
2. **MCP 官方 Fetch 是最小可行起点。** 它解决 `web_fetch` 的核心难题，许可证和 Node 技术栈都友好；搜索可另接 Brave 官方 MCP、SearXNG 或 `idefav/web-search`。
3. **Firecrawl 能力最好但许可证是主要阻碍。** AGPL-3.0 项目作为独立网络服务调用通常比复制/链接其代码容易合规；如果 Iris 未来闭源分发，不应把 Firecrawl 代码或服务打包进产品。
4. **Crawl4AI/SearXNG 更像基础设施。** 它们适合部署在服务器或用户自有环境，不适合随 Iris 桌面应用自动安装。
5. **小型 MCP 项目可快速验证，但不应作为长期核心依赖。** 应优先选择有明确版本、协议稳定、可替换的后端。

### 更新后的推荐方案

**推荐路线：Iris 内置 MCP 外部服务连接器，首选组合为：**

- `web_fetch`：MCP 官方 Fetch server（Node，MIT/官方参考实现）或 `idefav/web-search` Gateway。
- `web_search`：`idefav/web-search` Gateway；若只需搜索，可接 SearXNG 或 Brave 官方 MCP。
- Firecrawl/Crawl4AI：作为高级、可选的远程后端，不进入默认安装包。

Iris 需要自己开发的部分缩小为：MCP 进程/HTTP 连接管理、配置界面、工具名称映射、超时和错误归一化、网页内容不可信提示。搜索引擎解析、HTML 抽取、浏览器渲染和 SSRF 细节交给外部项目。

### 最终判断

可以复用网上开源方案，而且应该复用；但应复用**服务和协议**，不要把大型项目源码、Python 运行时、Docker 浏览器栈塞进 Iris。下一步应先做一个最小 MCP connector spike，验证 Iris Pi runtime 能否稳定挂载官方 Fetch 或 `idefav/web-search` 的两个工具，再决定默认后端。

## Codex 内置 Web 工具实现复核（2026-09-12）

### 结论

用户的判断是对的：如果目标是像 Codex 一样安装后直接可用，就不应该要求用户部署 Docker、Camofox 或 Python 服务。Codex 的网络能力并不是本地运行一个开源搜索爬虫，而是：**客户端内置工具适配器 + OpenAI 后端托管的搜索接口**。

### 从 OpenAI Codex 开源代码确认的调用链

OpenAI 官方 `openai/codex` 仓库目前包含独立的 `codex-rs/ext/web-search` 扩展。其 `WebSearchTool` 做的事情主要是：

1. 将模型传入的命令解析成 `search_query`、`open`、`find` 等动作。
2. 读取当前 Codex provider 的认证信息和模型信息。
3. 创建 `SearchClient`。
4. 向 provider base URL 下的 `alpha/search` 发起 POST 请求。
5. 将服务端返回的 `output` 和 `results` 映射成 Codex 的 WebSearch 事件和工具输出。

源码中的关键接口是：

```text
SearchClient
  -> POST alpha/search
  -> provider auth
  -> SearchResponse { output, results }
```

Codex 本地代码没有实现 DuckDuckGo/Google/Bing 页面解析，也没有在安装包中启动浏览器。网络搜索、网页打开、页内查找和结果生成由 OpenAI 服务端完成。

### Codex 的 web_search / web_fetch 关系

Codex 对模型暴露的是一个 `web` namespace 下的 `run` 工具，而不是两个完全独立的本地程序。工具命令包括：

- `search_query`：搜索
- `open`：打开搜索结果或指定 URL
- `find`：在页面中查找文本
- 其他扩展动作

因此用户看到的 `web_search` 和 `web_fetch`，本质上是同一套托管 Web Search 能力的不同动作或产品层名称。`open` 已经承担了主要的 fetch/read page 语义，并不需要在客户端另外实现 HTML 转 Markdown 爬虫。

### 为什么安装 Codex 不需要 Docker

因为 Codex 的安装包只负责：

- 工具 schema 和 prompt 描述
- 请求构造与认证
- 流式事件、历史记录和 UI 展示
- 取消、超时和错误传递

真正昂贵和复杂的部分在 OpenAI 云端：

- 搜索引擎接入
- 网页抓取与渲染
- 内容提取和结果排序
- 网络安全和服务端资源管理

这也是它能做到“安装即用”的根本原因。`idefav/web-search` 之所以需要 Docker，是因为它是一个自托管替代品，要把这些云端能力全部搬到用户自己的机器上。

### 对 Iris 的直接启示

此前“接入 idefav/web-search Gateway”方案确实偏离了用户期望。它解决的是自托管问题，而不是 Codex 的产品形态。若 Iris 使用任意 OpenAI-compatible provider，不能假定该 provider 也提供 Codex 的 `alpha/search` 服务；这个接口不是通用 OpenAI API 能力，不能仅靠修改 URL 就获得。

因此，真正符合“安装后直接使用”的方案只有两类：

1. **使用已有的托管 Web Search provider**：Iris 内置客户端适配器，向明确支持搜索的 provider 专用 endpoint 发请求。需要把 provider 的 web capability、认证方式、endpoint 和返回 schema 配置化。
2. **Iris 自己提供统一的云端 Web 服务**：Iris 客户端只调用 Iris 的后端，搜索/抓取基础设施部署在服务端。这是产品化路线，但不是本地代码小改动。

不建议：

- 要求每个 Iris 用户安装 Docker。
- 将 Camofox、Playwright、Python 搜索栈塞入 Electron 安装包。
- 在本地复制 Codex 的 `alpha/search` 调用但没有对应服务端。
- 把 `idefav/web-search` 当作“安装即用”的本地库。

### 当前合理的技术方向

如果 Iris 的目标 provider 主要是 OpenAI/Codex-compatible 服务，应新增一个**托管 Web 工具适配层**，结构类似：

```text
Iris web tool
  -> WebSearchProvider adapter
  -> provider-specific hosted endpoint
  -> search/open/find result
```

工具层只负责：

- 统一 `web_search` / `web_fetch` 对模型的 schema
- 根据 provider 能力决定是否暴露工具
- 发送认证请求
- 将响应转换成 Iris 的事件和工具结果
- 将服务端错误返回给模型

它不负责网页抓取算法。

如果当前 provider 没有托管 Web Search endpoint，正确行为应是禁用该工具并明确提示“当前模型服务商不提供 Web Search”，而不是偷偷启动本地爬虫或要求用户部署 Docker。

### 与 Codex 的重要差异

Codex 的 `SearchClient` 使用的是 OpenAI 自己的 provider/session/auth 抽象，并将用户输入历史、模型、搜索设置和结果 token 预算一起发送给服务端。Iris 当前支持多个模型 provider，因此不能照抄 Codex 的 endpoint；需要定义 provider capability：

```text
supportsWebSearch
webSearchEndpoint
webSearchAuth
webSearchRequestFormat
webSearchResponseFormat
```

只有 capability 为真时，才把 web 工具注册给 Pi。

最终判断：**Codex 的正确复用对象不是某个 Docker 开源爬虫项目，而是它的“客户端薄适配器 + 服务端托管 Web 能力”架构。**

## 纯本地方案再调研：Pi / DeepSeek Harness / OpenCode（2026-09-12）

### 结论先行

“纯本地集成”可以实现，但需要把 `web_fetch` 和 `web_search` 分开判断：

- `web_fetch`：可以完全在 Iris/Electron 进程内实现，OpenCode 已有很接近的 Node/TypeScript 参考实现。
- `web_search`：Pi 本身不内置搜索；OpenCode 的本地工具壳仍调用 Exa/Parallel 的远程 MCP/API。也就是说，主流开源 Agent 并没有一个真正离线、零外部服务、零 API key 的高质量通用 Web Search 实现。
- 因此最合理的纯本地产品形态是：**Iris 本地实现 fetch；搜索采用本地客户端直连公开搜索源/API，必要时做可插拔 provider，不要求 Docker 或常驻外部服务。**

### Pi 的实际做法

Pi 的核心定位是极小 Agent runtime 和可扩展工具系统，默认不内置 web_search/web_fetch。它提供 TypeScript extension/tool 机制，网络工具由用户或插件自己注册。Pi 的文档明确把权限和网络边界交给宿主/扩展处理；因此不能从 Pi 本身复用一套现成的本地 Web 实现。

这对 Iris 的启示是：继续使用现有 `pi-adapter` 注册 Iris 自己的工具即可，不需要引入 MCP 或 Docker。

### OpenCode 的实际做法

OpenCode 当前源码提供两个内置工具：`packages/core/src/tool/webfetch.ts` 和 `packages/core/src/tool/websearch.ts`。

#### `webfetch`

这是一个真正的本地实现，流程是：

1. 检查 URL 只允许 `http:` / `https:`。
2. 用运行时 HTTP client 发请求。
3. 限制响应体最大 5 MiB。
4. 限制超时，默认 30 秒，最大 120 秒。
5. 拒绝图片和非文本 MIME 类型。
6. 用 `htmlparser2` 提取纯文本。
7. 用 `turndown` 将 HTML 转 Markdown。
8. 遇到 Cloudflare challenge 时重试一次不同 User-Agent。
9. 通过工具权限系统询问/允许 URL 访问。

这部分可以直接作为 Iris 的设计参考，甚至在许可证允许且完成归属声明的前提下复用对应 MIT 代码/依赖思路。Iris 已经依赖 `undici`，只需补充 HTML parser 和 Markdown converter，或者先实现轻量纯文本模式。

#### `websearch`

OpenCode 的 `websearch` 名称容易造成误解：它不是本地搜索引擎。源码注释明确写着它是 provider-independent local tool，但实际实现是本地工具壳通过 HTTP MCP 调用：

- Exa：`https://mcp.exa.ai/mcp`
- Parallel：`https://search.parallel.ai/mcp`

并从环境变量读取 `EXA_API_KEY` / `PARALLEL_API_KEY`，做 provider 选择、超时、响应大小限制和错误转换。搜索、索引和网页研究仍由远端服务完成。

因此 OpenCode 证明了“工具可以本地注册和执行”，但没有证明“搜索数据源可以完全本地”。

### DeepSeek Harness 的判断

DeepSeek 相关 Agent/Harness 项目采用的是工具/插件/MCP 扩展思路，未发现一个随安装包分发的通用本地搜索索引和网页抓取引擎。其模型或 Agent runtime 与 Web Search 数据源是分离的；要获得实时搜索仍需搜索 API、MCP provider 或用户自建服务。

这与 Pi/OpenCode 的边界一致：Agent 框架负责工具调用协议，搜索基础设施另行提供。

### 纯本地 Iris 方案应该怎么做

#### 方案 A：纯本地 `web_fetch`（推荐，第一阶段）

直接在 Iris 主进程/worker 中实现：

```text
URL 校验
→ 请求超时与 AbortSignal
→ 响应大小限制
→ Content-Type 判断
→ HTML 文本提取 / Markdown 转换
→ 截断与结构化错误
```

建议参数：

```text
url
format: markdown | text | html
timeoutSeconds: 5..120
maxBytes: 64 KiB..5 MiB
```

安全边界至少包括：协议白名单、localhost/私网地址阻断、重定向重新校验、响应大小限制和不可信网页内容提示。

#### 方案 B：纯本地 `web_search` 客户端（可行，但质量和稳定性有限）

Iris 进程直接访问公开搜索来源，不启动 Docker/服务进程：

1. 优先使用无需自建服务的搜索 API（用户提供 key，如 Brave/Bing/Serper/Exa）。
2. 无 key 时可选 DuckDuckGo HTML/轻量接口作为 best-effort fallback。
3. 将每个 provider 做成同一个 `WebSearchProvider` 接口，可配置顺序和失败回退。
4. 对返回结果做统一去重、域名过滤和数量限制。

这仍然是“纯本地集成”——所有代码和进程都在 Iris 内，只有网络请求访问搜索源；但不能承诺完全离线或永久免 key。

#### 方案 C：真正离线搜索

只有在用户自己提供本地网页/文档索引时才成立，例如 SQLite/FTS 或 Tantivy 索引。它不是互联网搜索，不能替代 `web_search`，只能作为 `local_search`。

### 不应采用的路线

- 不引入 Docker/Camofox/Playwright/Python 运行时作为安装前置条件。
- 不把 OpenCode 的 `websearch` 误认为本地搜索；它仍依赖 Exa/Parallel。
- 不直接复制 Codex 的 `alpha/search` 调用；那是 OpenAI 私有托管接口。
- 不承诺 DuckDuckGo HTML 抓取是长期稳定方案；它可能限流、返回空结果或改变页面结构。

### 最终推荐

Iris 应采用“两级本地工具”设计：

1. **第一优先级：本地 `web_fetch`**，完全内置，达到 OpenCode 同等的超时、大小限制、HTML→Markdown 和权限控制。
2. **第二优先级：本地 `web_search` 工具壳 + 可插拔远程搜索源**，默认支持用户配置 API key 的 provider，并提供无 key 的 DuckDuckGo best-effort fallback。
3. **另行提供 `local_search`**，面向 Iris 文档/项目文件的本地索引，避免把互联网搜索和本地全文检索混为一谈。

这样不需要 Docker，也不需要用户运行外部 Gateway；Iris 安装后可以直接使用 `web_fetch`，搜索能力则按 provider 配置自动启用和降级。

## 是否采用 OpenCode 方案（2026-09-12）

可以采用，但需要拆开看：

### 可以直接复用的部分：`web_fetch`

OpenCode 的 `webfetch` 是真正的本地工具，适合迁移到 Iris：

- 仅允许 HTTP/HTTPS URL
- 本地 HTTP 请求
- 默认 30 秒超时，限制最大超时
- 响应体最大 5 MiB
- 拒绝图片和非文本 MIME
- `htmlparser2` 提取纯文本
- `turndown` 将 HTML 转 Markdown
- 对 Cloudflare challenge 做一次 User-Agent 重试
- 工具权限层控制 URL 访问

Iris 可以在自己的 `pi-adapter` / `IrisToolHostOperations` 中实现同等行为，不需要 Docker、Python、Playwright 或外部 Gateway。OpenCode 的代码和整体项目采用 MIT 许可时，可以按许可要求复用代码；更稳妥的做法是参考其实现并保留归属与依赖许可证。

### 不能直接复用的部分：`web_search`

OpenCode 的 `websearch` 不是本地搜索引擎。其本地工具只是向以下远程 MCP 服务发送请求：

- Exa：`https://mcp.exa.ai/mcp`
- Parallel：`https://search.parallel.ai/mcp`

并通过 `EXA_API_KEY` / `PARALLEL_API_KEY` 认证。因此直接复制 OpenCode 的 `websearch`，仍会引入外部服务和 API key，不符合 Iris 当前要求的“安装后纯本地集成”。

### 对 Iris 的推荐取舍

采用 OpenCode 的 `web_fetch` 方案，作为 Iris 的本地第一方工具；搜索部分只复用它的工具结构、输入限制、权限和错误处理方式，另行实现 Iris 的搜索 provider 接口：

```text
web_fetch：完全本地，按 OpenCode 实现
web_search：Iris 本地工具壳 + 可插拔 HTTP 搜索 provider
```

搜索 provider 可以按顺序支持 Brave/Bing/Serper/Exa 等 API，并保留 DuckDuckGo best-effort fallback。这样 Iris 本身不启动任何外部服务，但 `web_search` 的结果质量仍取决于可用搜索源。

### 最终判断

**可以用 OpenCode 方案，但不能整体照搬。**

- 如果只需要网页读取：OpenCode 方案几乎可以直接作为 Iris 的实现基线。
- 如果需要搜索：只能复用 OpenCode 的工具封装方式，不能把它的远程 Exa/Parallel 调用当成纯本地实现。
- 如果要求搜索也完全离线：OpenCode 方案无法满足，必须另做本地索引；那应命名为 `local_search`，不应伪装成互联网 `web_search`。

## 外置 Exa/Parallel MCP 方案评估（2026-09-12）

### 判断

**可以接受，而且比 Docker/Camofox 自托管方案更适合 Iris 当前阶段；但建议把它定位为可配置的外部搜索 provider，不要把 Exa 或 Parallel 写死成 Iris 的核心能力。**

### 为什么可以接受

- 用户不需要安装 Docker、Python、Playwright 或浏览器运行时。
- Iris 只需通过 HTTP MCP 调用远程工具，安装包保持轻量。
- 搜索质量、网页抓取、索引和服务稳定性由专业服务负责。
- OpenCode 已验证这种产品形态：本地 `websearch` 工具壳通过 MCP 调用 Exa/Parallel。
- Exa 和 Parallel 都是标准化 MCP endpoint，未来可以替换其他 provider。

### 必须接受的现实

这不再是“纯本地网络能力”，而是“本地工具调用 + 云端搜索服务”：

- 查询内容会发送给第三方服务。
- 结果和部分上下文可能经过第三方处理。
- 需要用户配置 API key 或采用服务方的认证方式。
- 会产生费用、配额限制和服务可用性风险。
- 网络不可用时，`web_search` 不能工作。

这些限制应在配置界面和工具说明中明确，而不是隐藏成 Iris 自己的能力。

### Exa 与 Parallel 的取舍

建议先接入一个 provider，再抽象多 provider：

- **Exa**：OpenCode 已经有成熟调用参考，接口和参数比较容易复用；适合作为第一实现。
- **Parallel**：可以作为第二 provider 或 fallback，但需要单独验证鉴权、限流、响应格式和服务条款。
- 不建议第一版同时深度绑定两个服务，否则会增加配置、错误分类、测试和行为差异。

### Iris 应如何接入

Iris 不应把远程 MCP 工具原样暴露给模型，而应在本地注册稳定的 Iris 工具：

```text
Iris web_search
  → MCP client
  → 当前配置的 Exa 或 Parallel endpoint
```

本地适配层负责：

- MCP 初始化和 capability 协商
- `tools/call` 请求
- HTTP 超时、取消和重试
- Bearer/API key 注入
- MCP 文本结果解析
- 错误归一化
- 不向模型暴露 API key
- provider 切换和 fallback

工具 schema 可以保持 Iris 自己的 `web_search`，不要让模型依赖 Exa/Parallel 的私有参数名。

### 主要风险

1. **MCP client 是 Iris 的新基础设施**：当前 Iris 没有现成 MCP client，需要实现 Streamable HTTP 生命周期、初始化、调用、断线和错误处理。
2. **服务端协议和认证可能变化**：应锁定 provider API 版本并做响应 schema 校验。
3. **成本不可控**：需要限制结果数量、上下文字符数、并发和重试次数。
4. **隐私边界**：应明确提示“搜索查询和请求 URL 将发送给配置的 provider”。
5. **服务商锁定**：工具层必须保持 provider-neutral，不能把 Exa 的字段扩散到 Iris 的业务层。

### 推荐产品策略

接受外置 MCP，但采用以下边界：

- `web_fetch`：继续使用 Iris 本地实现，避免为了读取一个 URL 也依赖搜索服务。
- `web_search`：通过外置 MCP provider 提供，第一版只接 Exa。
- Parallel：作为后续可选 provider，不作为第一版必需依赖。
- 未配置 provider 时：不注册 `web_search`，或返回明确的配置提示。
- 配置和权限：API key 放在安全配置存储中，查询外发提示由用户确认或设置。

### 最终结论

**外置 Exa/Parallel MCP 方案是可以接受的，并且是目前复杂度、质量和安装体验之间最平衡的方案。**

但它成立的前提是 Iris 接受“搜索是云端 provider 能力”，并且实现一个真正独立的 MCP 客户端适配层。推荐顺序是：本地 `web_fetch` + Exa MCP `web_search`，之后再加入 Parallel 作为可选 fallback。
