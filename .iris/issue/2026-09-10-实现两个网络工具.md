### 三、核心实现逻辑

#### 1. 搜索引擎选择

**方案 A：使用公共搜索 API**
- DuckDuckGo HTML 搜索（无需 API key）
- 优点：免费、简单
- 缺点：可能被限流、结果质量一般

**方案 B：支持配置搜索引擎**
- Google Custom Search API
- Bing Search API
- 需要用户配置 API key
- 优点：结果质量高、稳定
- 缺点：需要额外配置

**推荐：方案 A 作为默认，方案 B 作为可选配置**

#### 2. SSRF 防护

```typescript
function validateUrl(url: string): void {
  const parsed = new URL(url);
  
  // 只允许 http/https
  if (!['http:', 'https:'].includes(parsed.protocol)) {
    throw new Error('Only http:// and https:// URLs are allowed');
  }
  
  // 阻止内网地址
  const hostname = parsed.hostname.toLowerCase();
  const blockedPatterns = [
    /^localhost$/i,
    /^127\./,
    /^10\./,
    /^172\.(1[6-9]|2[0-9]|3[01])\./,
    /^192\.168\./,
    /^169\.254\./,
    /^\[::1\]$/,
    /^\[fe80:/i
  ];
  
  if (blockedPatterns.some(pattern => pattern.test(hostname))) {
    throw new Error('Access to private/internal addresses is not allowed');
  }
}
```

#### 3. 内容处理流程

**web_fetch 实现伪代码**：
```typescript
async function webFetch(url: string, options: FetchOptions) {
  // 1. URL 验证
  validateUrl(url);
  
  // 2. 发起请求（带超时和大小限制）
  const response = await fetch(url, {
    signal: AbortSignal.timeout(options.timeout * 1000),
    headers: {
      'User-Agent': 'IrisAgent/0.1 (https://github.com/Liyue-Cheng/iris)'
    }
  });
  
  // 3. 检查响应状态
  if (!response.ok) {
    throw new Error(`HTTP ${response.status}: ${response.statusText}`);
  }
  
  // 4. 读取内容（流式，带大小限制）
  const contentType = response.headers.get('content-type') || '';
  let html = '';
  let totalBytes = 0;
  const maxBytes = options.maxContentLength || 1024 * 1024;
  
  for await (const chunk of response.body) {
    totalBytes += chunk.length;
    if (totalBytes > maxBytes) {
      html += chunk.toString('utf8').slice(0, maxBytes - (totalBytes - chunk.length));
      break;
    }
    html += chunk.toString('utf8');
  }
  
  // 5. 转换为 Markdown
  const markdown = htmlToMarkdown(html);
  
  // 6. 返回结果
  return {
    content: [{ type: 'text', text: markdown }],
    details: {
      url,
      finalUrl: response.url,
      statusCode: response.status,
      contentType,
      contentLength: totalBytes,
      truncated: totalBytes >= maxBytes
    }
  };
}
```

## 外部方案复核（2026-09-11）

### 结论先行

不建议把 `idefav/web-search` 或 `webfetch-llm` 原样嵌入 Iris，也不需要从零发明搜索和网页抽取算法。更合适的路线是：**复用成熟项目的协议和实现思路，优先把 Iris 做成外部 Web Search Gateway 的客户端适配层；同时保留一个轻量的本地 `web_fetch` 兜底实现。**

### 1. `idefav/web-search` 实际是什么

该项目不是一个可直接 `npm install` 后在 Electron 进程内调用的单一库，而是一个完整的自托管服务：Docker Compose + Camofox Browser + REST/MCP Gateway。它提供 `web_search`、`web_fetch` 两个只读工具，包含 Bearer 鉴权、SSRF 代理隔离、多搜索引擎回退、浏览器渲染、OpenAPI/REST 客户端和 Pi 插件。

仓库许可证为 MIT；截至本次调研 GitHub API 显示约 7 stars、1 fork、0 open issues，创建于 2026-08-02，最近推送 2026-08-09。项目很新，功能覆盖较完整，但不宜把它当作长期稳定的核心依赖。

**可复用部分**：REST/MCP API 形状、工具参数（query/count/freshness/include/exclude domains、url/max_chars）、错误模型、SSRF 和不可信网页内容边界、Pi 插件接入方式。

**不适合直接搬入 Iris 的部分**：Camofox 浏览器和 Docker 部署、Squid SSRF 网络隔离、服务端运行时、与 Iris 现有 `pi-adapter` 工具生命周期的耦合。若采用它，Iris 只需实现一个 HTTP 客户端工具，服务作为可选外部组件运行。

### 2. `webfetch-llm` 实际是什么

这是 Python 包（当前 PyPI 版本 0.1.3，MIT，要求 Python >=3.10），默认通过 DuckDuckGo，可选 Brave/Serper/Tavily，多引擎 RRF 融合；网页抽取链包括 trafilatura、readability、newspaper4k，Playwright/PDF/表格/语义重排属于可选额外依赖。它还带 MCP server、缓存和压缩/排序流水线。

仓库为 `firish/webfetch`，截至本次调研约 55 stars、6 forks、0 open issues，创建于 2026-04-20，最近推送 2026-07-23。它更像“本地 Python 搜索研究服务”，不是 Node/Electron 原生依赖。直接在 Iris 中引入会增加 Python 运行时、进程管理、依赖安装和跨平台打包成本。

**可复用部分**：搜索提供商抽象、DDG 被阻断时的 fallback/circuit breaker、页面抽取降级链、缓存和结果压缩思路。

**不适合直接搬入 Iris 的部分**：Python 服务生命周期、Playwright/ML 依赖、SQLite 语义缓存、面向长研究任务的多工具接口（`fetch_url`、`save_finding`、`status` 等超出当前两个工具范围）。

### 3. 是否“网上方案直接就可以”

分情况：

- **如果目标是尽快可用**：可以直接接入 `idefav/web-search` 的远程 REST/MCP Gateway。Iris 在 `pi-adapter` 中注册两个薄工具，把参数转发到 `/v1/search` 和 `/v1/fetch`，并处理鉴权、超时、响应截断和错误映射。这样几乎不需要自己实现搜索引擎解析、浏览器渲染和 SSRF 代理。
- **如果目标是 Iris 单机开箱即用**：不能直接依赖上述项目。`web-search` 需要 Docker/Camofox 服务；`webfetch-llm` 需要 Python 及一组较重依赖。应当自己写一个小型 Node `web_fetch`，搜索则接入外部 API/Gateway，避免在 Electron 内维护爬虫。
- **如果目标是长期产品能力**：不要复制任一项目的全部代码。采用“协议兼容 + 可插拔后端”架构，后端可以是 `idefav/web-search`、自建搜索 API，或未来的其他服务；Iris 只稳定自己的工具 schema、错误格式和安全边界。

### 4. 对当前实现方案的修正

原方案中“新增 cheerio/turndown、默认抓 DuckDuckGo HTML、在 Electron 内自行完成全部 SSRF/搜索解析”的范围偏大，且会重复维护外部项目已经解决的问题。建议改为三层：

1. **Iris 工具层**：固定 `web_search` / `web_fetch` schema 和 LLM 可读的返回格式。
2. **Gateway 客户端层（首选）**：通过配置的 endpoint + API key 调用外部 REST；支持代理、超时、最大字符数、错误归一化。
3. **本地 fallback（可选）**：仅实现受限 `web_fetch`（HTTP/HTTPS、DNS/IP 私网阻断、响应大小/超时、纯文本或简单 HTML 提取），不实现搜索引擎抓取和浏览器渲染。

### 5. 推荐决策

**推荐采用“外部 Gateway 优先，轻量本地 fetch 兜底”，暂不引入 Python 包，也不把 Docker/Camofox 打进 Iris 发布包。**

实施顺序：

- Phase 1：定义 Iris 内部 `WebClient` 接口和配置项；实现远程 Gateway 客户端及两个工具注册。
- Phase 2：加入本地 `web_fetch` fallback，明确能力降级（无 JS 渲染、无搜索）。
- Phase 3：根据真实使用量再决定是否提供一键启动 Gateway 的开发者脚本；不纳入默认生产安装。

### 6. 需要保留的风险

- 外部项目版本和 API 可能变化，应锁定 endpoint 协议版本并做响应 schema 校验。
- 网页内容必须标记为不可信输入，不能让页面指令改变 Iris 工具策略。
- Gateway 不可用时，工具应返回可理解的结构化错误，不能让 agent loop 因异常直接中断。
- 若未来分发 Gateway，需另行评估 Docker、浏览器镜像和 SSRF 隔离的运维责任。

### 关键发现

1. **“直接复用”最现实的形式是 MCP 接入，而不是复制源码。** Iris 的 agent 基于 Pi 适配层，理论上可以启动一个 stdio MCP server，或调用 Streamable HTTP MCP；这样 Fetch/Firecrawl/SearXNG 都能替换后端，Iris 只维护工具注册和配置。
2. **MCP 官方 Fetch 是最小可行起点。** 它解决 `web_fetch` 的核心难题，许可证和 Node 技术栈都友好；搜索可另接 Brave 官方 MCP、SearXNG 或 `idefav/web-search`。
3. **Firecrawl 能力最好但许可证是主要阻碍。** AGPL-3.0 项目作为独立网络服务调用通常比复制/链接其代码容易合规；如果 Iris 未来闭源分发，不应把 Firecrawl 代码或服务打包进产品。
4. **Crawl4AI/SearXNG 更像基础设施。** 它们适合部署在服务器或用户自有环境，不适合随 Iris 桌面应用自动安装。
5. **小型 MCP 项目可快速验证，但不应作为长期核心依赖。** 应优先选择有明确版本、协议稳定、可替换的后端。

### 更新后的推荐方案

**推荐路线：Iris 内置 MCP 外部服务连接器，首选组合为：**

- `web_fetch`：MCP 官方 Fetch server（Node，MIT/官方参考实现）或 `idefav/web-search` Gateway。
- `web_search`：`idefav/web-search` Gateway；若只需搜索，可接 SearXNG 或 Brave 官方 MCP。
- Firecrawl/Crawl4AI：作为高级、可选的远程后端，不进入默认安装包。

Iris 需要自己开发的部分缩小为：MCP 进程/HTTP 连接管理、配置界面、工具名称映射、超时和错误归一化、网页内容不可信提示。搜索引擎解析、HTML 抽取、浏览器渲染和 SSRF 细节交给外部项目。

### 最终判断

可以复用网上开源方案，而且应该复用；但应复用**服务和协议**，不要把大型项目源码、Python 运行时、Docker 浏览器栈塞进 Iris。下一步应先做一个最小 MCP connector spike，验证 Iris Pi runtime 能否稳定挂载官方 Fetch 或 `idefav/web-search` 的两个工具，再决定默认后端。
