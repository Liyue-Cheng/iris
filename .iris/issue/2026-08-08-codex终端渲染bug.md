## 2026-08-08 调查结论

这不是 Codex 版本变化导致的。根因是 Iris 的终端响应依赖可见 renderer xterm，而新会话的 PTY 比 renderer xterm 更早启动，初始挂载时的 replay 又会暂存实时输出。因此程序在启动期发出的 OSC 10/11 前景色、背景色查询，可能被错过或过晚才送到会回答它的 browser xterm。

画面中的内容是 Iris 自己的 xterm 生成的回复，不是 Codex 输出：

```text
ESC ] 10;rgb:5c5c/1d1d/3e3e ESC \
ESC ] 11;rgb:ffff/f8f8/fbfb ESC \
```

这两个色值精确对应 Iris `cutie` 主题的 `#5c1d3e` 前景色和 `#fff8fb` 背景色。xterm 源码会将 OSC 10/11 查询转成完整的 `ESC ] ... ESC \` 回复，再通过 `term.onData` 发出。Iris 当前将 `onData` 的所有内容不区分来源地经 IPC 交给 `SessionManager.sendInput()`，最后调用 `managed.pty.write()`。

如果回复在查询的等待期内到达，颜色判断正常。如果回复在超时后才到达，程序已经进入输入框：`ESC` 被当成不可打印按键消费，后续可打印字符则被当成用户输入，所以屏幕上只剩下 `]10;rgb:...`、`]11;rgb:...` 和终止符中的反斜杠。同时颜色查询已超时，输入框使用回退颜色，这解释了“文字泄漏”和“输入框颜色错误”为什么同时出现。

### 代码证据

* `src/main/session-manager.ts` 在 spawn 成功后立即运行子进程，此时 renderer 还没有收到会话并挂载 `TerminalView`。
* `src/main/session-manager.ts` 使用 `@xterm/headless` 保存会话状态。实验向该 headless terminal 写入 OSC 10/11 查询，`onData` 回复为空；headless 实现没有 browser xterm 的 theme/color 处理器，无法自己回答颜色。
* `src/renderer/components/terminal/TerminalView.tsx` 在 replay 完成前将实时 PTY 输出放入 `holdQueue`，到获取快照、必要时重试快照、分块写入后才调用 `term.write()`。该路径平时是毫秒级，alt-buffer 重绘可等待至 500 ms，replay 失败保险上限为 5 s，足以使启动查询超时。
* 快照是序列化的终端状态，不是原始字节回放。如果 OSC 10/11 查询发生在 renderer 订阅前，它既不会被 headless terminal 回答，也不会出现在序列化快照中，因而会被彻底错过。
* 当前没有覆盖 OSC 10/11、xterm 自动终端回复、renderer 未挂载或 replay 期间查询的测试。

### 为什么是最近才出现

2026-08-06 的提交 `aa34b0e` 在 Windows 上新增了 `useConptyDll: true`，改用 `node-pty` 携带的 ConPTY DLL，目的是修复同步输出帧被系统 ConPTY 拆分后的光标闪动。

使用项目当前的 `node-pty 1.1.0` 做的受控对照实验表明：

* `useConptyDll: false`：系统 ConPTY 将写入的整段 OSC 10/11 回复吞掉，raw-mode 子进程没有收到任何字节。
* `useConptyDll: true`：子进程收到的十六进制字节与写入的两段完整 OSC 回复逐字节一致，ESC 没有被 Iris 或 bundled DLL 破坏。

因此 `useConptyDll` 不是传输损坏的根因，但它是这次可见回归的直接触发点：潜伏的“终端回复依赖 renderer 时序”问题原先被系统 ConPTY 的吞字节行为遮住，现在 bundled DLL 正确传递了迟到回复，反而让它泄漏到输入框。

### 解决意见

1. 推荐由主进程会话层拥有 OSC 10/11 查询与回复。它与 PTY 同寿命，不受 renderer 是否挂载、会话是否可见、replay 是否完成的影响。主进程需要获得当前 xterm 主题的前景色和背景色，并在 headless parser 遇到查询时立即回写 PTY。
2. 主进程接管后，必须同时阻止 browser xterm 对同一查询再次回答，否则 replay 结束后仍会产生重复的迟到回复。实现时应在两端的 OSC parser 层明确分配所有权，不要用无状态字符串替换处理可跨 chunk 的控制序列。
3. 不建议将 `useConptyDll` 永久退回 `false`。这只会恢复“把合法终端回复吞掉”的旧行为，并重新引入已修复的同步输出光标闪动。它可以作为临时对照开关，不应成为最终修复。
4. 不建议只缩短 replay 或延迟启动 Codex。这只会缩小竞态窗口，不能处理 renderer 尚未订阅或会话当前不可见时发生的终端查询。

在代码修复前，可用的无代码规避方式是先打开一个空 shell 会话，等 Iris 终端完全显示后再手动运行 `codex`。此时 browser xterm 已经订阅且 replay 完成，可以在查询超时前回复。

- [x] 在主进程建立与 PTY 同寿命的 OSC 10/11 查询回复路径，并在 renderer 端抑制重复回复。
- [x] 增加 OSC 查询拆 chunk、renderer 未挂载、replay 期间和会话切换场景的自动化测试。
- [x] 在 Windows 打包版中保留 `useConptyDll: true` 复测，同时确认启动颜色和光标稳定性。
