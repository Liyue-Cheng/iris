最近一次的iris agent执行记录显然是暴露了我们工具设计的一些问题，为什么AI会生成一个删掉所有内容的补丁？是不是我们的实现有bug

## 执行记录核查（2026-09-07）

### 结论

这次不是 Git 或 UI 的 diff 展示错误，而是一次真实的整文件覆盖。当前工作树中的
`src/renderer/components/settings/SettingsView.tsx` 曾被写成两行：

```text
*** Begin Patch
*** End Patch
```

Git 因而显示原文件约 2673 行全部删除。Iris 保存的最近一次 Session artifact 位于本机
`%APPDATA%/Iris/iris-agent-v3/projects/82d34fc308d28f11bcd95fbc/sessions/686d982f53459c79f3ca21734857e1f8/`，其中的 `provider-context/call-015.json`、对应 `call-015.txt` 和 `journal.ndjson` 保留了原始调用及宿主结算。

### 原始模型调用与实际解析

关键顺序如下：

1. 模型先读取 `SettingsView.tsx`，随后发出 `edit` 调用，参数是：

   ```json
   {
     "path": "src/renderer/components/settings/SettingsView.tsx",
     "content": "*** Begin Patch\n*** Update File: ...\n@@ ...\n*** End Patch"
   }
   ```

   这不是完整文件，而是模型生成的 unified patch 文本。

2. Iris 当前暴露给模型的真实 `edit` schema 是 `{ path: string, content: string }`。`src/main/agent-worker.ts` 的 `providerToolCallInput()` 将它转换成：

   ```ts
   { tool: 'edit', operation: 'writeFile', absolutePath, content: args.content }
   ```

   `src/main/agent/pi-adapter.ts` 也把 `edit` 定义成直接传入完整 `content` 的文件工具；没有 `oldText`、patch 格式字段或补丁解析步骤。

3. `src/main/agent/tool-host.ts` 对 `edit/writeFile` 的行为是读取旧文件、生成展示用 unified diff，然后调用 `writeFileAtomic(target, content)`。因此模型给出的 patch 文本没有被应用，而是被当成整个文件内容原子写入，导致约 2673 行内容被替换掉。

4. 模型之后调用终端执行：

   ```text
   git show HEAD:src/renderer/components/settings/SettingsView.tsx > src\\renderer\\components\\settings\\SettingsView.tsx
   ```

   这一步确实恢复了 HEAD 内容，且 journal 将其记录为成功的 terminal operation。

5. 随后模型再次调用 `edit`，参数为：

   ```json
   {
     "path": "src/renderer/components/settings/SettingsView.tsx",
     "content": "*** Begin Patch\n*** End Patch"
   }
   ```

   这是一个空 patch。由于同样没有 patch 解析或空 patch 拒绝逻辑，Iris 再次把两行标记当作完整文件写入，于是文件最终留下这两行。

### 为什么模型会这样调用

Prompt 与真实工具契约不一致：`src/main/agent/prompt.ts` 仍告诉模型 `edit` 支持
`edits[].oldText`、多段精确替换；但实际发送的 schema 只有 `path/content`，执行器也只支持
整文件替换。模型因此沿用了熟悉的 patch 习惯，宿主却按 full-content writer 解释。

此外，最近一次 provider payload 中工具定义是 `strict: false` 的宽松 function schema，缺少
对内容格式和目标版本的约束。`edit` 与 `write` 在执行层几乎相同，只有审计 operation 名称不同，
使模型更容易误判 `edit` 是安全的局部编辑器。

### 是否存在实现 bug

存在，且是契约和安全边界的组合缺陷：

* **明确 bug：** prompt、schema、worker adapter、executor 对 `edit` 语义不一致。

* **明确防护缺口：** 对以 `*** Begin Patch`、`*** Update File`、`@@` 开头的内容没有格式拒绝或解析；空 patch 也没有拒绝。

* **明确风险：** `edit` 可以无条件整文件覆盖，未校验读取基线、revision 或最小变更比例；一次模型格式误判即可造成全量删除。

* **并非根因：** `generateUnifiedPatch()` 只在写入之后生成展示 diff，它没有参与文件内容解析，也没有制造删除。

* **恢复行为：** terminal 可以恢复文件，说明宿主并未阻止模型自救；但恢复后再次接受空 patch，说明执行器缺少最终写入门禁。

### 修复优先级

  【你自己看看pi agent的工具是怎么设计的，这个阶段不要搞那么多创新，直接抄过来 】

* [ ] 在执行层增加写入前门禁：拒绝 patch marker、空 patch、明显非源文件内容；对已有文件要求基于已读内容或 revision 的 CAS 校验。

  【这必须做】

* [ ] 对整文件替换增加异常变更保护：删除比例/字节比例超过阈值时暂停并要求用户确认，或至少把操作标为高风险而不自动提交。

  【我拒绝】

* [ ] 为 `edit` 增加回归测试：模型传 unified patch、空 patch、完整内容、旧文件不存在、基线变化、整文件大幅缩短时分别验证结果。

  【可以的】

* [ ] 在 artifact/journal 中同时保存原始 provider tool call、解析后的 operation input、before/after hash 和拒绝原因，并在 UI 中明确显示“模型请求内容”与“宿主解释”。

  【我拒绝，未来再设计统一log】

本次检查没有修改源码；只核对了持久化执行记录、当前工作树和相关实现。

## 实现结果（2026-09-07）

已按用户确认直接采用 Pi 0.84.1 的 `edit` 设计，没有引入新的 patch 协议：

* `edit` schema 改为 `{ path, edits: [{ oldText, newText }] }`，至少包含一个替换。
* `oldText` 必须非空、在原文件中唯一，多个编辑不得重叠；所有匹配基于同一份原始文件内容，再从后往前应用。
* 保留原文件换行风格；匹配失败、重复匹配、重叠编辑、无变化和空 edits 都返回 ToolCall 错误，不写盘。
* `providerToolCallInput()`、Pi adapter、worker operation 和 shared protocol 已统一为 `edits` 语义，不再把 `edit` 映射成整文件 `content` 覆盖。
* 对新替换文本增加补丁标记门禁，拒绝 `*** Begin/Update/End Patch` 或 `@@` 形式的误用。
* Prompt 已改为明确说明 `edit` 的 `{ path, edits: [{ oldText, newText }] }` 契约，并要求不要把 unified patch 标记放进 edit/write 内容。
* 恢复了事故中被两行补丁标记覆盖的 `SettingsView.tsx`，未改动其余既有工作树变更。

新增/更新测试覆盖：

* Pi adapter 的四工具暴露和委托测试仍通过。
* Tool Host 的精确替换、junction 路径编辑测试通过。
* 新增空 edits 和补丁标记拒绝测试，确认目标文件保持不变。
* `npm run typecheck`（含 `check:async`）通过。
* 定向 Vitest：3 个文件、26 项测试全部通过。

本次没有实现用户拒绝的“大比例删除阈值”、统一 log 设计或额外用户确认流程。

## read / write 与 Pi 0.84.1 对比实现（2026-09-07）

继续逐项核对 Pi `read`、`write`、`edit` 的提示词、schema、adapter 与执行器后，已完成以下对齐：

* `read` schema 增加可选 `offset`（1-based）与 `limit`，worker、shared protocol、Pi adapter、Tool Host 全链路传递。
* `read` 默认限制为最多 2000 行或 50KB；发生截断时返回 `Showing lines ... Use offset=... to continue.`，显式 `limit` 提前结束时也返回剩余行提示；越界 offset 返回错误。
* `read` 仍由 Iris 以 base64 在 worker/host 间传输，图片附件暂不纳入现有协议（当前协议只有文本文件结果），该差异已明确保留，不会静默伪装成图片支持。
* `write` 的 `path`、`content` 均为必填并补充 Pi 风格描述；成功结果返回 `Successfully wrote <bytes> bytes to <path>`。Iris 继续保留原子写入和审计 diff，这是产品层有意扩展。
* `edit` 成功结果返回替换块数量；此前已实现的精确唯一替换、空 edits/补丁标记拒绝、换行保持和审计 diff 保持不变。
* `terminal` 未改动，继续使用 Iris 自己的 intent、可见输出、supervision 与成功退出码语义。

### 尚未完全复制的 Pi 能力

`read` 的图片识别/缩放与 image content block、`edit` 的 NFKC/智能引号/dash/特殊空格模糊匹配、BOM 与局部原始字节保留，以及 Pi 的文件变更队列，当前 Iris 尚未全部移植。原因是现有 Iris 协议只承载文本/终端结果，且现有 session 已串行调度工具；本轮先完成不会改变协议形状的核心契约对齐，避免引入新的图片或日志架构。

## terminal 与 Pi 0.84.1 对比（2026-09-07）

对照 Pi `bash` 工具后，Iris 的 terminal 业务语义继续保持不变：仍使用 PTY、可见输出、`information/operation` intent、supervision、自定义成功退出码和完整日志文件。

### 已吸收的安全/可用性行为

* 取消 terminal 时，在关闭 PTY 前可调用平台进程树清理；Windows 复用现有 `taskkill /T /F` 适配器，避免 shell 派生的后台子进程残留。清理失败仍会回退到 `pty.kill()`，不会卡住会话关闭。
* 当返回给模型的 terminal 尾部预览因 64KB 限制被截断时，结果明确附带“仅为尾部预览，完整输出位于日志路径”的提示。之前完整日志虽已落盘，但模型不知道预览不完整，可能误判命令结果。

### Pi 能力中有意不引入的部分

* Pi 的 `timeout` 参数未加入 Iris terminal schema。Iris 当前通过会话 Stop/Abort、PTY 生命周期和 terminal supervision 管理命令，不改变既有命令语义。
* Pi 的 bash 子进程实现、shell 环境变量和 `detached` 策略不直接替换 Iris 的 PTY；Iris 需要保留 Windows ConPTY、终端镜像、可见性阈值及审计事件。
* Pi 的输出累加器会把超长输出按尾部截断并记录结构化 truncation details；Iris 已有完整输出文件、尾部预览和 `outputTruncated` 字段，本轮只补模型可见提示，不引入新的输出协议。

## Trace、日志与审计能力核查（2026-09-08）

### 结论

是的，这次事故说明当前设计还缺少真正意义上的日志层。但不需要把 Trace 推倒重来，也不应把所有内容再复制一份塞进 Trace。

当前 Trace 是 **Agent 的业务事实和上下文投影**：它适合回答“这个 Intent 当前处于什么状态、模型看到了哪些已提交消息、工具卡片如何显示”。当前 session journal 是 **状态存储的事件溯源日志**：它有 revision、`previousHash`、`journalHash` 和 `journal.sync()`，适合重启后重放 aggregate，并能检测文件被修改。两者都不能单独承担“发生过什么、哪个主体在什么时候请求了哪个副作用、宿主如何解释、结果是什么、记录是否完整”的独立审计职责。

建议采用三个相互关联但职责不同的信号：

1. **Trace**：因果关系、上下文和 UI 投影，允许压缩、裁剪和重新投影。
2. **Audit log**：副作用和安全相关事实的不可变记录，按操作写入请求、开始、结果或未知结局，不能因为 UI 投影失败而消失。
3. **Diagnostic log**：主进程、worker、IPC、窗口、文件系统和异常的结构化运行诊断，用于定位实现问题，不承担业务事实的唯一存储责任。

因此，问题的答案是“需要真正的 log，而且至少需要一条独立的 audit stream”；但“保证任何问题都能审计”不能作为绝对承诺。进程在写入前断电、操作系统或磁盘损坏、用户拥有本机文件权限时，软件无法保证零信息丢失或不可抵赖。可实现的目标是：对已接受的关键操作提供有边界的完整性、可关联性和结局记录；对未能落盘的部分明确产生 audit gap，而不是静默当作成功。

### 对当前实现的证据盘点

| 现有记录 | 已经能做什么 | 仍然不能保证什么 |
| --- | --- | --- |
| `AgentSessionAggregate`、`Trace` 和 `journal.ndjson` | 保存 Intent、Turn、Invoke、Attempt、reply、tool activity、revision；journal 使用 hash chain 并在追加后同步文件；重启时可校验和重放 | 记录的是 aggregate 变更，不是每一个运行时事实；没有统一的 actor/action/object/result 审计事件；hash chain 的根仍只在本机，能检测部分篡改，不能阻止删除、回滚或证明记录从未被删掉 |
| `provider-context/call-*.json`、`index.json`、`index.txt` | 保存模型请求的部分 provider payload、provider/model/API、调用序号和 sha256；这次事故因此能够回放“模型传入了 patch marker” | 内容先经过字段白名单和 secret 脱敏；provider stream 的中间事件、传输错误的完整上下文、某些被丢弃的运行时事件没有独立事实记录；`persistProviderContext(...).catch(() => undefined)` 会把 artifact 写入失败静默吞掉 |
| `timeline` 中的 reply/tool activity 与 `toolOperations` | 保存模型消息、工具输入摘要、工具状态、文件 diff、终端退出信息和部分输出预览 | 它在副作用执行前后由 session manager 更新，是状态投影，不是严格的 before/after 操作账本；没有统一记录“请求已接受但结果尚未记账”的中间状态；文件写入没有通用的 before/after 字节 hash、实际写入者和宿主解析版本 |
| terminal 输出文件与 `TerminalFlightRecorder` | PTY 的完整输出通常写入临时 `.log`，flight recorder 保存最近 128 个内存事件；终端 timeline 保存尾部预览、字节数和结果 | flight recorder 重启即丢失；输出文件在系统临时目录，不属于 session 的不可变 artifact 树，路径、保留期和 hash 没有进入统一审计索引；输出 append 没有像 journal 一样的每条记录同步和链式校验 |
| `src/main/logger.ts` 的 `~/.iris(-dev)/logs/main-debug.log` | 主进程有带时间、PID、等级和 tag 的 best-effort 文件 sink，并有约 5 MiB 的一次轮转 | 是纯文本拼接，缺少 JSON 事件名、session/intent/turn/tool correlation、worker epoch、结果和版本；只覆盖显式调用 logger 的主进程路径，worker 的 provider/工具生命周期不自动进入；写失败会禁用 sink，应用继续运行；一次轮转会覆盖上一代，不能作为长期审计证据 |
| worker protocol 的 `postDurable` | 带 `eventId` 的少数 provider message/attempt 事件等待主进程 ack 后才继续，降低了事件先后不明的风险 | 普通 `post` 的 state、delta、terminal event 不具备同等持久性；worker crash、IPC 中断或 host 退出时可能只有暂停状态，没有“最后收到什么、哪条事件未确认”的明确审计 gap |

这解释了这次事故的特殊性：本次 provider artifact 和 journal 恰好都存在，所以可以把错误调用、第一次覆盖、terminal 恢复、第二次空 patch 串起来。它证明现有记录“有用”，不证明所有未来失败路径都有同样的可审计性。

### 调研得到的设计约束

对照 OpenTelemetry Logs Data Model、OWASP Logging Cheat Sheet 和 NIST SP 800-92 后，得到几个直接适用于 Iris 的约束：

* 日志和 Trace 是不同信号。OpenTelemetry 的 log record 具有时间、严重级别、body、resource、attributes、`TraceId`/`SpanId` 等字段；Trace ID 应用于关联，不应替代日志事实。[OpenTelemetry Logs Data Model](https://opentelemetry.io/docs/specs/otel/logs/data-model/)
* OWASP 要求事件记录足够的“when, where, who and what”，并建议补充 action、object、result status、reason、响应和扩展错误信息；这正是当前 `timeline` 和文本 logger 缺少的公共事件字段。[OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)
* OWASP 将日志的完整性、可用性、责任归属和保留期单独视为设计问题：要有篡改检测，尽快复制到只读介质，监控日志停止和删除，并对访问、权限和 disposal 建立规则。单一本地 hash chain 只覆盖其中的篡改检测一部分。[OWASP Logging Cheat Sheet 的保护与运行章节](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)
* NIST 把 log management 定义为生成、传输、存储、访问和处置的全过程，而不是“写一个文件”。Iris 当前有生成和部分存储，缺少统一的完整性检查结果、访问/导出记录、保留策略和故障处理契约。[NIST SP 800-92 Rev. 1](https://csrc.nist.gov/pubs/sp/800/92/r1/ipd)
* OpenTelemetry 明确说明 trace sampling 会丢掉未采样的 trace；Iris 当前本地 Agent 量很小，关键操作不应采样或只保留尾部摘要。诊断日志可以限流，audit event 不应因采样而丢弃。[OpenTelemetry Sampling](https://opentelemetry.io/docs/concepts/sampling/)
* Node 的 `filehandle.sync()` 只是请求操作系统把当前文件描述符的数据刷到存储设备，不能解决写入之后的进程崩溃、目录 rename、介质故障或本机篡改；因此“调用了 fsync”不能单独被称为审计保证。[Node.js fs 文档](https://nodejs.org/api/fs.html)

### 建议的统一事件契约

不建议新增一套只给 UI 用的字符串日志。建议定义一个版本化、可导出的结构化 `IrisLogEvent`，Trace、audit 和 diagnostic 只共享 envelope，payload 按类别分别受控：

```json
{
  "schemaVersion": 1,
  "eventId": "uuid",
  "eventName": "agent.tool.operation.completed",
  "stream": "audit",
  "occurredAt": "2026-09-08T00:00:00.000Z",
  "observedAt": "2026-09-08T00:00:00.010Z",
  "severity": "info",
  "source": { "component": "tool-host", "process": "main", "pid": 1234, "workerEpoch": 7 },
  "correlation": { "sessionId": "...", "intentId": "...", "turnId": "...", "invokeId": "...", "attemptId": "...", "toolCallId": "...", "operationId": "...", "terminalId": "..." },
  "actor": "model",
  "action": "edit",
  "object": { "kind": "file", "path": "src/..." },
  "outcome": "success",
  "reason": null,
  "payload": { "inputRef": "artifact://...", "beforeSha256": "...", "afterSha256": "...", "diffSha256": "..." },
  "sequence": 42,
  "previousHash": "...",
  "eventHash": "..."
}
```

字段要求如下：

* `eventId` 是幂等键；`occurredAt` 和 `observedAt` 区分事件发生与宿主收到事件的时间。
* `correlation` 必须沿用现有 session/intent/turn/invoke/attempt/tool/operation/terminal ID；另外保留 `traceId`/`spanId` 兼容未来 OpenTelemetry，而不把 Trace 当成唯一记录。
* `actor` 至少区分 `user`、`model`、`host`、`worker`、`system`；`action`、`object`、`outcome`、`reason` 使审计者不必从自由文本猜测行为。
* 大文本和敏感值默认放入受控 artifact，以引用、长度和 sha256 进入事件；provider credential、环境变量和 token 不进入 log。为了复盘本次 patch 事故，模型原始工具参数的脱敏 canonical JSON 必须可按事件引用，而不是只保存 220 字摘要。
* 每条 stream 自己维护 `sequence` 和 hash chain；启动、恢复、导出时校验，并把 `integrity-check.completed` 或 `integrity-check.failed` 作为事件记录下来。hash chain 是篡改检测，不是不可抵赖；若未来需要证据级别的审计，应在导出时签名并把 checkpoint 送到用户控制之外的存储。

### 关键操作的写入顺序

对于会改变工作树、启动/取消进程、发送 provider 请求或改变 session 事实的操作，必须把 audit 当作操作协议的一部分：

1. 先写并确认 `requested`（包含脱敏输入引用、基线 hash、版本和 correlation）；写不进去就不执行副作用。
2. 写 `started`，再执行副作用。
3. 成功或可确定失败后写 `completed`/`failed`，包含结果、错误分类、结束时间、before/after hash、diff/output artifact 引用。
4. 如果副作用已经发生但结果事件没落盘，写不出结果也不能伪造失败；下次启动必须把它标成 `unknown`，尝试通过文件/进程状态核对，并保留 `audit-gap`。
5. 每次拒绝、取消、超时、重试、worker crash、IPC ack 超时、artifact 保存失败和日志 sink 停止都必须有明确事件。当前若干 `.catch(() => undefined)` 只适合非关键的可读投影，不能出现在 audit 路径。

对本次 `edit` 事故，最小可审计链应是：`provider.requested`（原始脱敏 tool call 引用）→ `tool.operation.requested`（宿主解析后的 edits）→ `tool.operation.started`（before hash）→ `tool.operation.completed`（after hash 和 diff）→ 第二次调用对应的另一条链；若中途恢复，则再有 terminal operation 的 command、exit code、影响文件 hash 和结果。这样不必依赖从一段最终状态反推发生过什么。

### 存储与保留建议

* session 目录下新增独立的 `audit/events-*.ndjson` 和索引；它与 `journal.ndjson` 并列，journal 继续负责 aggregate replay，audit 负责副作用账本。provider context、terminal output 等大对象作为 immutable artifacts，由 audit 事件引用并记录 hash。
* `~/.iris(-dev)/logs/` 改为结构化 diagnostic stream，至少覆盖 main、worker、IPC 和 crash/lifecycle；保留一个人类可读的 projection 供快速排查，但它不能是唯一来源。每个 worker 的启动、ready、request、event ack、exit/crash、terminate 和 epoch 都要有 correlation。
* audit 不应使用当前 main logger 的“一次轮转覆盖上一代”策略。session audit 在用户删除 session 或明确的保留策略到期前保留；diagnostic 才可按大小/时间轮转。轮转、压缩、导出和删除本身要产生日志，并记录保留边界。
* 提供一个“导出诊断包”动作：包含 manifest、版本、时间范围、session audit、journal、provider context、terminal artifact 索引、hash 校验结果和 redaction policy；导出动作本身写 audit。不要默认上传 provider prompt、文件内容或终端输出。
* 桌面应用无法让同一台机器上的本地用户无法删除文件。若产品未来需要更强的不可抵赖性，应增加可选的签名 checkpoint 和用户明确开启的远端/只读归档；在此之前，UI 必须把“hash chain verified”与“完整性有外部锚定”区分开。

### 分阶段落地顺序

以下是建议的实现顺序，不是本次调研中已经完成的代码：

* [ ] 先冻结 `IrisLogEvent` envelope、stream 分类、actor/action/outcome 枚举、脱敏规则、事件覆盖清单和保留策略；把“关键操作必须 requested→started→result/unknown”写成协议不变量。
* [ ] 增加独立 audit writer：单调序号、事件 ID 去重、hash chain、同步追加、启动校验、损坏尾部与中间损坏的不同处理，以及不可静默的 writer failure。
* [ ] 在 provider request/attempt、tool operation、文件写入、terminal 生命周期、task 生命周期、worker/IPC 生命周期和 session 恢复路径接入关键 audit 事件；保留现有 Trace/journal，不以 projection 代替 audit。
* [ ] 将 provider call 和 terminal output 迁移到带 owner、immutable hash、保留期和索引的 session artifact；对完整原始输入采用脱敏引用，不再让临时目录路径成为唯一证据。
* [ ] 将 main logger 升级为结构化 diagnostic stream，补齐 worker 和 crash/lifecycle，加入 correlation、schema/version、日志停止检测、容量保护和轮转事件。
* [ ] 实现诊断包导出与完整性报告，并为用户提供查看“模型请求、宿主解释、实际副作用、结果/未知结局”的审计视图。
* [ ] 增加故障注入测试：请求前崩溃、side effect 后崩溃、fsync/rename 失败、worker 无 ack、文件被外部修改、日志目录不可写、磁盘接近满、轮转和导出期间退出、脱敏回归以及 hash chain 篡改检测。

### 验收标准

完成后，针对任意一个已接受的 Agent 工具操作，离线拿到 session 目录和诊断包，应能回答：谁（user/model/host/worker）在何时提出了什么；宿主按哪个版本和 schema 解释；操作基于哪个文件/上下文 hash；是否真正开始执行；产生了哪个文件、进程或 provider 请求副作用；结果、错误或未知结局是什么；所有引用 artifact 是否存在且 hash 一致；中间是否发生过 crash、重试、取消、超时或 audit gap。

达不到这些问题的任意一个答案时，记录系统只能称为“有 trace 和若干 debug artifact”，不能称为完整审计系统。
