你认为，我们需不需要实现将这个软件和jira或者linear互相集成？还是没有这个必要

## 结论

**壳不长 Jira/Linear 模块；但"和它们集成"这个需求是合理的，应当被满足——
经由用户自带的智能，而非壳自带的智能。** 早先把它判成"反 Iris / 身份认同的
试金石"是过度发挥：定义书 §2/§7 本就允许用户 BYOK 驱动的自动化，这个需求落在
批准之列。详见 `2026-06-24-红线清查与去教条化.md`。

要避免的只有一件事：**壳自己变成又一个双向同步中间件**（常驻同步引擎、字段
映射、冲突对账、内嵌 API key）。集成的"重量"放在 agent / 用户脚本里，壳保持哑。

## 三级出口（从轻到重）

### ① frontmatter 存 `jira_key`（今天就能用）

在 issue 的 frontmatter 写 `jira_key: PROJ-123` 做链接。frontmatter 的键是
**自由软值**，不是 schema——这不构成红线"不做 schema 校验"的违规。零壳改动，
agent 现在就能写。

### ② 拉取 / 推送走 BYOK 自动化或 agent 层（正路）

- **拉取**：用户对 agent 说"把这个 Jira 项目拉成 md"，agent 用自带 Jira MCP/CLI
  写进 `issue/`。
- **推送**：改状态后，带 SessionStart hook 的 agent 读到 frontmatter 有 `jira_key`
  就替你推一次；或用户自带 key 的小自动化完成。

壳依然哑、依然只认文件；集成是 agent 的能力，而非应用的特性。这与"选中文档 →
召唤 agent"的核心手势完全同构。

### ③ 通用「状态迁移命令钩子」（v1.1 候选，待立项）

若想要"改状态时**自动**推"这点壳层自动性，正确形态不是 Jira 专用模块，而是一条
**通用钩子**：壳在 `status:` 变化时执行**用户自带的脚本**，壳自己不认识 Jira——
与 git hook 同理，不破任何不变量（壳只跑用户给的命令，不内嵌 SDK/key）。

## 为什么不做"壳内双向同步"

仍然成立的那部分理由：双向同步引擎是工程泥潭（冲突解决、字段映射、状态机对账、
轮询/webhook、限流重试），且会产生**双份事实来源**的悖论。Iris 已经回答过——
文件才是契约。所以集成的出口在 agent / 脚本层，而不是把同步引擎焊进壳里。
原先"留一道窄门：仅单向只读导出"的限制，据此放宽为上面的三级出口。
