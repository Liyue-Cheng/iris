## 调研结论摘要

* 这一版「聚合」完全发生在渲染层：`src/renderer/components/agent/IrisAgentView.tsx:1168` 的 `groupAgentCards()` 把主进程投影出来的**连续** `local-retrieval` / `file-change` 卡片再合并成一个组，由同文件 1145 行的 `CombinedActivityGroup` 渲染成「无卡片外框、无标题、最多 5 行」的平铺列表。

* 主进程侧的 `projectCards()`（`src/main/agent/session-model.ts:627`）已经把连续的读取类工具合并成一张带 `items[]` 的 `local-retrieval` 卡片，所以同一批操作被合并了两次：一次在领域投影层，一次在视图层。

* 聚合组目前没有任何展开/收起能力：超过 5 行的操作是**被直接丢弃**（不是折叠），摘要文案也只在超过 5 行时出现。

* 当前工作区里这个组件处于一次**未完成的图标重构**中，`IrisAgentView.tsx` 现在无法通过类型检查（证据见第七节）。

## 一、数据来源：主进程的卡片投影

### 1.1 领域活动（AgentToolActivity）

一次意图（Intent）的工具调用记录在 `AgentToolActivity`（`src/main/agent/session-model.ts:243`），关键字段：`tool`、`intent`（`information` / `operation`）、`operation`、`command`、`cwd`、`path`、`diff`、`resultSummary`、`error`、`terminalId`、`terminalOutcome`、`imageAttachment`。

### 1.2 `projectCards()` 的投影规则（session-model.ts:627-692）

按 `activities` 顺序（即调用发生顺序）逐条映射：

| 输入 activity                                                      | 输出卡片                                        | 是否合并                                                                    |
| ---------------------------------------------------------------- | ------------------------------------------- | ----------------------------------------------------------------------- |
| `kind: 'reply'`                                                  | `agent-reply`（`state: streaming → running`） | 不合并                                                                     |
| `task_start` / `task_get` / `task_list` / `task_cancel`          | **不产出卡片**（642-643 行 `continue`）             | —                                                                       |
| `tool: 'read'`，或 `tool: 'terminal'` 且 `intent === 'information'` | `local-retrieval`                           | 与**紧邻上一条** `local-retrieval` 合并进同一张卡片的 `items[]`，并重算卡片 state（644-658 行） |
| `tool: 'edit'` / `'write'`                                       | `file-change`（一次调用一张卡）                      | 主进程不合并（660-677 行）                                                       |
| 其它（执行命令类 terminal）                                               | `terminal-operation`                        | 不合并（679-689 行）                                                          |

补充事实：

* 「平凡操作」的判定在 `isLocalRetrieval()`（694 行）：`read`，或 `information` 意图的 `terminal`。`edit` / `write` 是另一种卡片，但会被视图层和检索卡片合并到同一组。

* 后台任务卡片不由 timeline 产生，而是在 `projectIntent()` 里**追加到该意图卡片列表末尾**（`session-model.ts:573-575`）。

* 合并只在「紧邻」时发生：中间出现 `edit`/`write`/执行命令/回复，就会另起一张 `local-retrieval` 卡片。

### 1.3 卡片状态枚举与推导

`IrisAgentCardState`（`src/shared/types.ts:728`）：`running | completed | failed | partial | stopped | unchanged`。

* 检索卡片：`combinedState()`（722 行）——只要有 running 就是 running；全部 failed 才是 failed，否则 failed 混在其中是 partial；有 canceled → stopped；否则 completed。

* 文件变更卡片：`state === 'failed'` → failed；`action === 'unchanged'` → unchanged；其余走 `toolCardState()`（canceled → stopped）。

* `action` 由 `fileAction()`（734 行）从 `resultSummary` 反推：`created` / `updated` / `unchanged`，识别不出来一律 `attempted`。

### 1.4 卡片如何到达渲染端

`diffAgentSessionProjection()`（session-model.ts:512）按 revision 发快照或补丁（`upsert` 带 `index`、`remove` 带 `cardId`），渲染端 `irisAgentStore.handleProjectionUpdate()`（`src/renderer/stores/iris-agent-store.ts:64`）把补丁落到 `intent.cards`。`IrisAgentView` 每次渲染都对 `intent.cards` 重新调用 `groupAgentCards()`，所以聚合组是**随会话实时增长**的（同一组会从 1 行涨到 5 行，然后开始丢行）。

## 二、渲染层的聚合规则 `groupAgentCards()`

`src/renderer/components/agent/IrisAgentView.tsx:1168-1183`，逻辑等价于：

```text
groups = []
for card of intent.cards:
  if card.kind in ('file-change', 'local-retrieval'):
    if groups 最后一项是 activity-group: 追加进它的 cards
    else: 新建 activity-group，cards = [card]
  else: 推入 single 组（原样渲染单张卡片）
```

要点：

* 分组的**唯一**依据是「连续」：`agent-reply`、`terminal-operation`、`task` 这三种卡片会打断聚合，一个意图里因此可能出现多段聚合组。

* 聚合条件只看卡片种类，不看成败、不看是否 running。失败的检索和失败的文件写入同样会被吸进组里。

* 组内顺序 = 卡片顺序 = 调用发生顺序，读取与文件变更**按时间交错平铺**，不按类型分组。

* React key 取 `group.cards[0].id`（视图 647 行）。

### 已经变成死代码的分支（重要）

因为 `file-change` 与 `local-retrieval` 永远进 `activity-group`，`AgentActivityCard`（956 行）里的这两个分支在运行时**不可能被触发**：

* `LocalRetrievalCard`（989 行）——它带有「信息检索」标题、`N 个文件 · M 条查询` 摘要、`slice(-5)` 只显示**最新** 5 条、以及「另有 N 项」＋折叠按钮（1010 行）。

* `FileChangeGroupCard`（1099 行）——它带有「文件变更」标题、`N 个文件 · +a -d` 摘要、逐文件 `创建/修改/未改变/写入失败` 文案，以及 `diffLineStats()` 算出的 `+N -M`。

连带结果：`diffLineStats()`（1185 行）与 `groupState()`（1196 行）实际上不再被任何可达路径使用 → **文件 diff 的增删行数在当前 UI 中已经完全不展示**。

## 三、聚合组内部的行投影与摘要

`CombinedActivityGroup`（1145-1159 行）把组里的卡片拍平成 `Row`：

```text
Row = { id, icon, label, state, error, terminalId }

file-change 卡片  → 1 行：icon = FileActionIcon(action)，label = path，state = card.state，
                         error = card.error，terminalId = undefined
local-retrieval   → 每个 item 1 行：icon = FileText(文件) / SquareTerminal(查询)，
                         label = item.label，state = item.state，error = item.error，
                         terminalId = item.terminalId
```

被丢弃的字段：`file-change.diff`、`file-change.detail`（resultSummary）、`local-retrieval item.errorDetail`（终端输出预览）、`item.image` 缩略图（检索到的图片在聚合组里不再显示）。

摘要计算（1150-1154 行）：

```text
files  = rows.filter(row => 'terminalId' in row === false).length
info   = 所有 local-retrieval 卡片的 items 总数
edits  = file-change 卡片数
failed = state === 'failed' 的行数
summary = `${files}读取 · ${info}信息 · ${edits}编辑 · ${failed}错误`
```

渲染条件（1156-1157 行）：

* `rows.length > 5` 时，才在列表**上方**插一行 `text-[10px] text-muted-foreground` 的摘要。

* 列表永远只渲染 `rows.slice(0, 5)`，多余的行没有任何入口可以看到。

## 五、场景化的展示效果（现状推导）

1. **只读一个文件**：底部出现单独一行 —— `FileText` + 文件路径 + 绿色勾。没有标题、没有外框、没有摘要（因为只有 1 行）。
2. **连续读 4 个文件 + 1 次信息类命令**：5 行平铺，仍无摘要（`rows.length === 5` 不满足 `> 5`）。
3. **连续 8 次操作**：列表上方出现一行小字 `0读取 · 8信息 · 0编辑 · 0错误`，列表只列出**最早**的 5 行，后 3 次操作在界面上完全消失。
4. **读取与编辑交替**：同一组内交替出现文件读行与文件编辑行；编辑行只有路径 + 一个小图标，看不到 `+N -M`，也看不到「未改变 / 写入失败」这类结果文字。
5. **出现失败**：失败行显示红色 `X`；若该失败检索带 `terminalId`，可以点开终端输出；失败原因（`error`）只进了无障碍文案，界面上没有可展开的错误详情。
6. **组被打断**：一次意图里若中间产生了 AI 回复、执行命令卡片或后台任务卡片，聚合组会被切成多段，视觉上就是若干段 1\~5 行的裸列表穿插在其它卡片之间。

## 六、发现的疑点与缺陷（仅记录，未改动）

* **F1 超过 5 行直接丢数据**：`rows.slice(0, 5)` 之外的行没有任何展开入口，与旧 `LocalRetrievalCard` 的「另有 N 项 + 展开按钮」能力不一致。

* **F2 摘要有硬 bug**：`'terminalId' in row === false` 中 `in` 的优先级高于 `===`，等价于 `('terminalId' in row) === false`；而 `Row` 始终带 `terminalId` 键，所以该条件恒为假，`files`（「N读取」）**恒为 0**。

* **F3 摘要口径重叠且显示条件苛刻**：只在 >5 行时出现；「读取」与「信息」语义重叠（`info` 已经包含文件读取的条数）；「编辑」按卡片计、「错误」按行计，三种粒度混用。

* **F4 文件变更信息丢失**：`+N -M` 与 `创建/修改/未改变/写入失败` 文案在可达路径上不再展示，`FileChangeGroupCard` / `diffLineStats` / `groupState` 成为死代码。

* **F5 无组级状态**：没有头部、没有状态图标、没有 running 动画；连续检索时用户无法从这一组判断「是否还在跑、跑到哪一步」。

* **F6 领域配色丢失**：行状态图标统一 `var(--primary)`，`--iris-card-retrievals` / `--iris-card-files` 在这里没有作用。

* **F7 截取方向不一致**：聚合组取**最早** 5 行（`slice(0, 5)`），旧检索卡片取**最新** 5 行（`slice(-5)`）。

* **F8 无障碍细节退化**：行 label 无 `aria-label`，容器 `aria-label` 用的是可能错误的 `summary`。

* **F9 字段丢弃**：`item.errorDetail`（终端输出预览）与检索到的图片缩略图在聚合行里都不再呈现。

* **F10 图标语义重构只做了一半**：见第七节；同时重构完成后「结果动作」将没有文字/图标表达，聚合行需要重新定义展示什么。

* **F11 没有测试**：仓库内没有 `groupAgentCards` / `CombinedActivityGroup` 的测试。

* **F12 文案硬编码中文**：`IrisAgentView` 整体未接入 i18n（`AgentHistoryDialog` 已接入），聚合组的摘要与状态文案都是中文常量。

## 实现结果（2026-09-14 第二轮，按你的指示改完）

改动集中在 `src/renderer/components/agent/IrisAgentView.tsx`，只动了聚合卡片的渲染层，未改主进程投影。前面「八、待确认」清单按下面方式落地，未落地项在末尾重新列出。

### 1. 截断 5 行 → 可滚动的 5 行窗口（不丢数据）

* 删除 `rows.slice(0, 5)`，现在**渲染全部行**，外层容器改为固定高度的滚动窗口：

  * `ACTIVITY_GROUP_VISIBLE_ROWS = 5`

  * `ACTIVITY_GROUP_WINDOW_HEIGHT = calc(5 * 1.75rem + 4 * 0.125rem)`（正好是 5 个 `min-h-7` 行 + 4 个 `space-y-0.5` 间隙，= 148px）

  * 容器：`className="space-y-0.5 overflow-y-auto"` + `style={{ maxHeight: ACTIVITY_GROUP_WINDOW_HEIGHT }}`

* 初始与新增行时自动停在**最新**一行（`useIsomorphicLayoutEffect` + `followTail` ref）；如果用户自己往上滚看旧行，新行到达时**不再强行拉回**底部（`onScroll` 里判断距底 ≤ 4px 才继续跟随）。

* 效果：连续 8 次操作时仍是 148px 高的一屏，显示最新 5 行，往上滚能看到前 3 行，无信息丢失（F1、F7 解决）。

### 2. 文案重做（F2、F3）

摘要改为按**行**统一计数，口径互不重叠：

```text
共 8 项操作 · 5 个文件读取 · 2 条查询 · 1 个文件变更 · 1 项失败
```

* `activityGroupRows()` 给每行加 `family: 'read' | 'query' | 'file-change'`，`activityGroupSummary()` 据此计数：读取=文件类检索行、查询=命令类检索行、文件变更=文件卡片行、失败=`failed` 或 `partial`。

* 数值为 0 的项直接省略（不再出现「0读取」这种噪声）。

* F2 根因（`'terminalId' in row === false` 恒为假）随旧统计代码一起删除；`onClick` 里的 `'terminalId' in row &&` 也一并换成直接判空。

* 摘要仍只在超过 5 行时显示（窗口固定时它就是「还有更多」的提示）；容器 `aria-label` 用的是同一份文案，现在内容准确。

### 3. 文件变更信息回填（F4）

新增 `FileChangeResult`，文件行右侧现在同时显示结果文案与增删行数：

```text
[工具图标] src/main/agent/session-model.ts   修改 +12 -3   ✓
[工具图标] .iris/issue/xxx.md                未改变        ✓
[工具图标] .iris/issue/yyy.md                写入失败      ✕
```

* 文案由新的 `fileActionLabel(action)` 统一提供：`创建` / `修改` / `未改变` / `写入失败`；写入失败用 destructive 色。

* `+N` / `-M` 只显示非零项，颜色与旧文件变更卡片一致。

* 已变为死代码的 `FileChangeGroupCard` 里的同名三元表达式也改成调用 `fileActionLabel()`，避免两处口径漂移。

* 左侧图标保持并行会话已落地的**工具类型**语义（`edit → Pencil`、`write → FileText`），结果只由文字与状态图标表达，不再复用垃圾桶语义。

### 4. 顺带处理

* 行内 label 补上 `aria-label`（与其它卡片一致，截断文本仍可被读屏读全）。

* 滚动容器未使用 `overscroll-contain`，鼠标滚轮在组内到底后仍可继续滚动整个会话，避免嵌套滚动卡住。

### 先更正上一轮方案里的一处错误

我上一轮写过「store 只在补丁到的 intent 上换数组身份，所以 `useMemo([cards])` 能命中」——**这是错的**。`iris-agent-store.ts` 原来写的是 `intents: structuredClone(existing.intents)`，每次补丁都会深拷贝**全部** intent（连带全部卡片与 items）。后果有两个：

* 基于身份（identity）的 memo 永远不可能命中；
