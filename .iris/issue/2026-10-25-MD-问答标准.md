## 2026-10-25 Agent 理解

### 问题本质：两类东西被塞进了同一种语法

agent 需要用户介入的事其实有两类：

| | 待办 / 验收项 | 待决问题 |
|---|---|---|
| 用户要做的 | 去做一件事、确认一件事 | 提供信息、做出选择 |
| 结果形态 | 二值：做了 / 没做 | 开放内容：一个答案 |
| 合适的语法 | `- [ ]` checkbox | 需要一个能写答案的位置 |

checkbox 只适合前者。拿它装问题，打勾只能表达“看过了”，答案没有落点，于是用户只能在终端里回答，答案没回到 issue——这与“详细方案、结果写回 issue”的追溯要求冲突，下次会话也看不到当时的决定。

### 为什么 agent 总用 checkbox：根源在我们自己的协议

`src/main/iris-templates.ts` 的软件协议写的是：

> When an item requires human review, verification, approval, **or follow-up**, represent it with one GFM task checkbox …

以及 In Review 规则里的 “add one unchecked task per remaining item”。“approval / follow-up” 范围太宽，agent 自然把“需要用户回答的问题”也归进去。协议目前只给了 checkbox 这一种“需要人介入”的表达方式，所以这不是 agent 不守规矩，而是协议缺了一类。

产品层面还有一个副作用：扫描器（`extractTodos`）会把未勾选项收进待办面板，`checkTodo` 可以一键勾掉——对问题来说，这等于“没回答就关闭了”。

### 对 `Q: / A:` 方向的看法

方向是对的：问题和答案都留在文档里，空 A 表示未答、非空 A 表示已答，agent 不需要额外状态就能判断。但裸写 `Q:` / `A:` 有几个细节要定：

1. **编号**：`Q1`、`Q2`……便于用户在终端里简答“Q2 选 B”，也便于 agent 回写时对应。
2. **问题要自带上下文**：为什么要问、影响什么、不回答时 agent 的默认做法。否则用户得翻上文才能回答。
3. **选项**：大量问题其实是选择题，应允许列选项并标推荐项，用户只填一个字母即可。
4. **答案边界**：多行答案到哪里结束？Markdown 里连续文本行会并成一个段落，所见即所得编辑器里也容易和下一个问题粘连。需要一个视觉和结构上都清晰的答案区（比如引用块或下一个 `Q` 前的空行约定）。
5. **位置与历史**：统一追加在一个“待确认问题”小节，符合 issue 追加历史的原则；已答的 Q/A 不删，本身就是决策记录。
6. **边界**：不是所有问题都要进 issue。只有影响方案、阻塞工作、需要留档的问题写进 issue；终端里一来一回的澄清可以留在会话。

一个可能的样式（仅示意）：

```markdown
## 待确认问题

**Q1.** 待答问题存在时 issue 状态用什么？
影响：决定 agent 提问后是否停下。不回答的默认：保持 In Progress。
- A. In Review（推荐）
- B. 保持 In Progress

> A：
```

### 需要改动的地方（仅列出，暂不实施）

- 软件协议（`iris-templates.ts`）：把“需要人做/验收的事 → checkbox”和“需要人回答的问题 → Q/A 格式”拆开；In Review 规则同步区分。对应的 `software-prompt` 测试和本仓库入口文件同步。
- 可选的产品层（后续）：扫描器识别空 A 的问题，在左栏/issue 列表显示“N 个待答问题”；待办面板不再能“勾掉”问题。V1 可以先只改协议，靠纯文本约定跑起来。

## 2026-11-21 重新思考：把「提问 + 默认」合写成一句提议

### 上一版怪在哪里

1. **默认和回答是同一种东西，却占了两个位置。** 两者都是“这个问题的答案”，区别只是谁给的、有没有被确认。上一版把默认藏在一句说明里（`不回答的默认：…`），又另开一个空的 `> A：`。于是空着的 A 有歧义：是还没看，还是接受默认？
2. **最常见的反应成本最高。** 用户多数时候的回答是“就按你说的”，但上一版要求找到答案区再打字。
3. **标签太多。** `Q1.`、`影响：`、`不回答的默认：`、选项 `A.`/`B.`、`> A：`，其中答案标签 `A：` 还和选项 `A.` 撞名。
4. **需要另起一套机制。** 协议要新增一个类别，产品层以后还要新增扫描规则，和现有待办面板是两条线。

### 核心想法

“提问、回答、默认”看起来是三个字段，其实可以不设任何字段：

- **提问 + 默认 = 一句提议。** 不写“状态用什么？默认 In Review”，而是直接写“状态用 In Review”。
- **回答 = 对提议的反应。** 同意就打勾；不同意就在下面写一行。

格式只有一行，没有 `Q:`、`A:`、`默认:` 这些标签：

```markdown
- [ ] Q3 存在待确认项时的 issue 状态：In Review —— 复用现有“等人”的状态；备选：保持 In Progress、放开 Blocked。
```

用户改判时在下面缩进写一行（多行、多段也可以，整个缩进块都算回答）：

```markdown
- [ ] Q3 存在待确认项时的 issue 状态：In Review —— 复用现有“等人”的状态；备选：保持 In Progress、放开 Blocked。
  - 保持 In Progress，In Review 留给真正做完的情况
```

agent 实在给不出提议时，照样是一行，只是冒号后面没有结论，并明说需要用户提供：

```markdown
- [ ] Q7 发布用哪个账号？—— 我没有依据判断，请写在下面。
```

### 读取规则

勾和缩进行各管一件事，互不重叠：缩进行管“答案是什么”，勾管“人确认过没有”。

| 文档里的样子 | 含义 | agent 怎么做 |
|---|---|---|
| 未勾、下面没有内容 | 还没确认 | 有提议：按提议推进，随时可被推翻。没有提议：这一点停下等 |
| 已勾、下面没有内容 | 同意提议 | 定案 |
| 下面有内容（勾不勾都算） | 用户另有回答 | 以下面的内容为准 |

“有没有提议”同时回答了“这个问题阻不阻塞”：有提议就不阻塞，没有提议才阻塞，不需要额外标记。

### 为什么我认为这比上一版好

- **一次点击完成最常见的情况。** 同意提议只需打勾，在待办面板里也能直接勾。
- **改判不覆盖原提议。** 回答是追加在下面的，“agent 提议 X，用户改成 Y”这段历史原样留在文档里，符合 issue 追加历史的原则。
- **不需要任何产品改动。** 我核对了现有实现：`extractTodos`（`src/shared/markdown-utils.ts:133`）逐行识别 checkbox 行，提议行会原样进入待办面板，缩进的普通列表行不会被当成待办；面板显示的就是 checkbox 行的全文（`TodoPanel.tsx:157`），所以用户在面板里看到的是完整提议，勾选是知情的；“置为 Done 时自动勾选全部待办”也自然等价于“接受所有剩余提议”。
- **协议只需补一句，而不是新增一类。** 现有的 “approval → checkbox” 和 In Review 的 “one unchecked task per remaining item” 都继续成立。
- **逼 agent 先给判断。** 只抛问题不给建议是偷懒；没有提议的问题会因为显眼地阻塞而变少。

这里要修正我上一版的一个判断。上一版说“待办是二值、问题是开放内容，所以 checkbox 不适合装问题”，并把“面板里一键勾掉 = 没回答就关闭”当成副作用。更准确的说法是：一个问题同时需要内容和确认两样东西，checkbox 之所以不够，是因为当时行里没有答案。只要行里已经带着提议，勾掉就不是“没回答”，而是“同意”。

### 代价和没有验证的地方

- 面板显示的是原始文本，行内的 `**加粗**` 会露出星号，所以提议行用纯文本，靠 `：` 和 `——` 分隔议题、提议、理由。
- 提议行要一行写完，理由和备选不能长。需要长篇背景时写在正文里，提议行引用即可。
- 选择题不再有 `A.`/`B.` 字母，用户改判时要写出选项的名字。我认为这是好事（答案自解释），但打字略多。
- 保留 `Q<编号>` 前缀：便于在终端里说“Q3 改成…”，也给以后区分“待答”和普通待办留了一个零成本的识别点。
- 未验证：Iris 的所见即所得编辑器（Milkdown）里，在任务项下面新增一个缩进的普通列表行是否顺手。这是标准 GFM，预期没有问题，但我没有运行应用确认。

### 协议措辞草案（未实施）

接在现有 checkbox 段落之后：

> When you need a decision or information from the user, write it as one task checkbox phrased as a proposal: the topic and your recommended answer on a single plain-text line (`- [ ] Q1 <topic>: <recommended answer> — <why, alternatives>`). The user ticks it to accept, or writes a different answer in an indented line beneath it. Treat content beneath a proposal as the answer; treat an unticked proposal as your working assumption. If you cannot recommend an answer, say so on the line and do not proceed on that point until an answer is written beneath it.
