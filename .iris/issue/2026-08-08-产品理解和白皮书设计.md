## 一句话定义

Iris ADE 是一个本地优先、文档中心、终端驱动的 Human-Agent 协作环境：它把项目事实保存在
普通文件中，把工作单元组织成可追踪的文档，把已有 agent CLI 作为交互式执行者，再用桌面
界面连接长期记忆、实时会话、注意力调度和 Git 工作区。

它不是“内置了 AI 的项目管理软件”，而是“让外部 AI agent 能在一个项目中持续、可见、
可恢复地工作的人机协作控制面”。这也是 `Agent Development Environment` 比传统 PM 工具
更准确的含义。

## 产品的三层结构

白皮书必须把以下三层分开，否则会把当前实现误写成协议本身。

### 1. 协议层：可脱离应用存在的项目记忆

协议层由项目根入口文件中的 Iris 提示词块和 `.iris/` 文件树组成。它没有数据库、服务端、
账号、工作区清单或私有二进制格式。

- `status/`、`issue/`、`report/`、`misc/` 是四个内建类型。
- 类型由最近的 typed folder 决定，不要求固定目录深度。
- 直接包含 typed folder 的目录自动成为 workspace，不需要 manifest 或注册表。
- `.iris/` 是根 workspace；子 workspace 与根 workspace 使用同一种数据模型。
- workspace 被放进上级 `report/` 后会被识别为归档整体。
- frontmatter 的键是硬接口，值是软约定。`title`、`status`、`labels`、`reflects` 会被识别，
  但异常状态值仍原样显示，而不是被 schema 拒绝。
- GFM checkbox 不是另一套任务数据库，而是从 Markdown 正文实时投影出的任务项。
- 文档资产使用同级 `<文档名>.assets/` companion 目录，Markdown 链接和磁盘文件共同充当索引。

这套设计的本质是“文件系统即共享状态，目录结构即轻量类型系统”。Iris 不接管用户数据，
只是对普通文件作确定性解释。

### 2. 应用层：协议的参考实现和操作控制面

Electron 应用负责把协议投影为可操作的产品体验：项目打开与初始化、递归扫描、文件监听、
结构化集合视图、Markdown 编辑、PTY 会话池、Git、资产管理、多窗口和机器级设置。

应用层可以被替换，协议层仍然成立；但当前 Iris 的高质量交互和可靠性主要来自这一层，不能
简单称为“一个薄查看器”。主进程中已经存在大量防并发、防陈旧响应、防写入冲突和终端恢复的
工程机制。

### 3. 适配层：把外部 agent 接入协议

Iris 不嵌入模型 SDK，也不保存 API key。用户在设置中配置 `claude`、`codex`、`gemini` 或
任意命令，Iris 在项目根启动真实 PTY。

- 文档会话设置 `FOCUS_DOC`。
- workspace hub 会话不设置 `FOCUS_DOC`，只设置 `IRIS_WORKSPACE_PATH`。
- SessionStart hook 可调用机器级 `~/.iris/focus-context.ps1`，在零额外对话轮次中注入焦点
  文档或 workspace 快照。
- 没有 hook 的 CLI 仍可退化到读取入口提示词和环境变量。
- hook 配置属于其他 CLI，只有用户明确确认后 Iris 才修改；生成的 focus script 属于 Iris，
  启动时会自动保持最新。

因此 agent agnostic 的成立条件不是“所有 agent 有统一 API”，而是“所有 agent 最终通过终端
和文件协作”。文件而不是终端输出，是跨 agent 的稳定契约。

## 核心产品对象

### 文档是工作单元，也是长期记忆

Iris 不是以聊天线程为中心。issue、status、report 等文档同时承担目标、上下文、进展记录和
写回目标。一次会话可以消失，但文档应保留工作的可交接结果。

四种类型形成一套时间语义：

- `status` 表示现在，是需要与代码和 Git HEAD 对齐的镜像；界面会比较 `reflects` 与当前 HEAD。
- `issue` 表示未来和正在发生的工作，有明确状态机，并承载可聚合 checkbox。
- `report` 表示有日期的交付物，按时间线展示，`Backlog` 后退出活动视图。
- `misc` 是人类自由空间，应用仅提供普通列表，不强加工作流。

这不是四种页面模板，而是一套围绕“现在、未来、过去、体系外”的项目记忆模型。

### 会话是短期工作记忆

会话由 `node-pty` 启动，工作目录始终是项目根。一个文档可挂多个会话，会话创建后锚点固定；
根 workspace 和子 workspace 也各自有无焦点的 hub 会话。

会话只有 `active`、`idle`、`exited` 三种状态。Iris 不解析 agent 的文字内容，只根据 PTY 字节
活动和安静窗口判断工作中或等待中。退出后的会话保留滚动历史，直到用户主动关闭。

渲染器切换或重载时，会话进程仍由主进程持有。主进程用 headless xterm 维护完整终端状态，
界面重新挂载时通过序列化快照恢复普通缓冲区、备用屏、光标和模式。这说明右栏是完整终端，
不是对 agent 输出做二次封装的聊天 UI。

### workspace 是作用域，不是团队或云租户

workspace 由文件结构推导，用于限定文档归属、集合过滤、agent 写回和 hub 会话分组。它适合
子项目、独立探索和临时攻坚。创建 workspace 被明确设计为人的手势；agent 不应自行制造新的
组织边界。

## 用户工作闭环

实际代码兑现的主闭环是：

1. 用户打开本地项目；没有 `.iris/` 时，经确认初始化 typed folders 和入口提示词块。
2. 用户从 issue、status、report 或 workspace hub 进入一个工作作用域。
3. 文档可直接编辑，也可启动一个或多个带焦点上下文的 agent 终端。
4. agent 与人通过真实终端交互，结果写回磁盘文件或代码，而不是写进 Iris 私有会话记录。
5. 文件监听触发全量重投影，集合、任务数、状态、标签和文档内容随磁盘事实更新。
6. Git 面板提供状态、暂存、取消暂存、提交和本地分支切换，形成最小本地交付闭环。
7. issue 完成或报告进入 Backlog 时，文档退出活动视图；如果仍挂着终端，界面会先要求处理。

这里最关键的不是“从 issue 启动 AI”，而是上下文、执行、写回、投影和注意力重新分配形成了
一个闭环。

## 三栏界面的真实职责

### 左栏：导航加注意力调度

左栏按 workspace 和类型组织文档，只显示活动 issue 和非 Backlog report，但仍挂着会话的已
解决 issue 会继续可见。每个文档和 hub 会话旁的状态点把左栏变成等待队列：用户可以看到哪个
agent 正在输出、哪个可能在等待输入、哪个已经退出。

左栏还承载项目切换、最近项目、新窗口、workspace 创建、排序、筛选、Todo 和 Git 入口。raw tree
作为逃生舱保留全部 `.iris/` 文件，不要求所有内容都被 lens 模型理解。

### 中栏：阅读编辑面和结构化运营面

单文档视图由 typed header 与正文编辑器组成。frontmatter 不进入 WYSIWYG 正文，标题、状态、
标签和资产由 header 管理；源码模式是精确编辑和修复异常 frontmatter 的逃生舱。

类型集合不是同一张通用表：

- Issue 是主运营面，支持活动/已解决/全部、搜索、标签过滤、workspace 过滤、分组、排序、键盘
  导航、多选和批量状态变更。
- Todo 聚合活动 issue 中所有未完成 checkbox，并用精确行级比较写回源文档。
- Status 显示 `reflects` 与 Git HEAD 的新鲜度。
- Report 按日期和时间桶展示交付物。
- Misc 保持简单，避免把体系外空间重新结构化。

集合视图独占右侧工作区，不同时显示终端；文档视图才采用编辑器加右栏终端的分割布局。

### 右栏：真实、可离开的交互式执行面

右栏只显示当前文档或 workspace 锚点下的会话。同一锚点可有多个 session，用户可切换、搜索、
复制、粘贴、拖入文件，也可把 Iris 文档直接拖入终端，形成带路径和快照声明的上下文块。

hub 视图让终端占满右侧区域，适合没有单篇文档焦点的项目级工作；文档视图则让执行面与长期
记忆并列。它实现的是 detach，而不是 headless dispatch：agent 始终是可返回、可对话的终端
进程。

## 可靠性设计不是附属细节

当前代码最成熟的部分不是 PM 表格，而是跨编辑器、文件系统、PTY 和多窗口的因果一致性。

- 所有离散副作用通过 FrontCPU 指令集进入，并按项目、文档、会话、Git 仓库等资源串行化。
- 连续终端输入、resize 和输出绕过指令流水线，避免给每次按键增加不必要开销。
- 每个窗口拥有独立 ProjectManager、GitManager 和 SessionManager；机器设置共享。
- 项目作用域使用 canonical root 加 generation，旧项目的迟到 IPC 和事件不能污染新项目。
- 项目切换先完成目标预检，再关闭旧项目会话，跨过不可逆点后只向前完成。
- 编辑器保存使用磁盘基线做 compare-and-swap，写入采用临时文件加 rename。
- 自动保存、失焦保存、视图切换、Git 动作、项目切换和退出都会走统一 flush 决策。
- 外部修改与本地草稿冲突时默认暂停写入，让用户载入外部版本或明确覆盖。
- 文件监听只负责失效通知，renderer 重新扫描磁盘，而不是猜测单个事件的业务含义。
- 文档删除会把 Markdown 与 companion assets 作为一个整体移入系统回收站；失败会尝试恢复。
- 删除有锚定会话的文档时，用户可关闭会话或把会话重新锚定到项目根。

这些机制共同支撑“文件是契约”。如果缺少它们，文件中心只会退化为多个写入者互相覆盖。

## 对产品设计的判断

### 最有价值的设计不是 AI，而是外部化协作状态

普通 agent CLI 的问题不只是缺少项目管理，而是上下文靠复制、进度藏在终端、多个会话的等待
状态不可见、结果容易停留在聊天里。Iris 用文档锚点、状态点、文件写回和结构化投影，把这些
隐形状态外部化。

因此 Iris 的“AI-native”不应解释为应用拥有模型，而应解释为产品的基本对象、导航和生命周期
从一开始就假设：大量工作由多个长时间运行、会提问、会修改文件的 agent 完成，人负责目标、
边界、审查和关键决策。

### 文档中心不是笔记中心

Iris 文档不是知识库页面的集合。类型、状态机、时间语义、workspace 作用域、任务聚合、会话
锚点和 Git 新鲜度让文档成为可执行工作协议。Markdown 只是最低耦合、可版本化、可由所有 agent
读写的载体。

### 产品刻意选择协调而不是代理

Iris 不解释 agent 输出、不替 agent 决策、不自动派单，也不拥有对话历史。它把智能留给 CLI，
把人保留在交互回路中。这降低了 agent 绑定和云依赖，也意味着产品的价值必须来自上下文组织、
并行会话管理、注意力调度与可靠写回，而不能依赖“模型能力更强”的叙事。

### 协议与 App 的张力是健康的，但要诚实表达

协议可以脱离 App 存活，这是可迁移性和信任基础；实际产品体验又依赖大量 App 工程。这两者并
不矛盾：协议保证退出权和数据寿命，App 提供操作效率和并发可靠性。白皮书不应把 App 贬低为
可有可无的薄壳，也不应把当前 Electron 实现描述成协议的唯一形态。

## 当前真实边界

- 产品是 `0.1.0-beta.1`，Windows/ConPTY 优先；自动 hook 适配脚本是 PowerShell，POSIX 不是
  当前完整能力。
- 会话在 renderer 重载和界面切换时可恢复，但应用退出、窗口关闭或项目切换会终止相应 PTY；
  它们不是跨进程重启的持久会话。
- Git 是最小本地控制面，目前有 status、stage、unstage、commit 和本地 branch switch，没有
  diff 编辑器、fetch/pull/push、远端协作或冲突解决工作台。
- Iris 没有代码编辑器。代码工作发生在 agent CLI、终端程序或外部编辑器中；中栏编辑的是
  `.iris/` Markdown 文档。
- 没有内置模型、后台 agent 调度、输出语义解析、账号、云同步、权限系统或遥测。
- 文档类型固定为四种，没有自定义类型系统；soft values 提供弹性，但视图能力仍围绕内建类型。
- Markdown 编辑支持 GFM、LaTeX、代码高亮、Mermaid、图片和源码模式，但并非通用知识库或完整
  IDE Markdown 生态。
- 资产受管范围是本地 companion aggregate；不会自动下载 HTTPS 资源，也不会自动删除孤儿。
- About 设置页仍有版本、构建形态和数据目录的占位内容。

这些不是应该隐藏的缺点，而是白皮书区分“核心承诺、当前实现、未来可能性”时必须写清的边界。

## 白皮书建议叙事

白皮书不应从四个目录或三栏 UI 开始，而应从 AI 编程后的协调问题开始：代码生成更快以后，
长期记忆、上下文交接、并行会话、等待注意力、结果落盘和人类审查成为新的瓶颈。

建议正文按以下逻辑展开：

1. 问题：聊天和终端是短期记忆，传统 PM 与真实代码和 agent 执行脱节。
2. 核心主张：项目事实必须外部化为 agent 和人共同可读、可写、可版本化的本地文件。
3. 协议：typed folders、workspace 推导、四种时间语义、hard keys/soft values、资产 aggregate。
4. 执行模型：文档锚定会话、workspace hub、FOCUS_DOC、交互式 detach、files as contract。
5. 人机分工：agent 负责执行和写回，人负责创建边界、提供指令、处理问题和验收。
6. 注意力模型：左栏会话状态、活动 lens、Todo 聚合和退出活动视图的生命周期。
7. 可靠性：文件监听、CAS 保存、冲突处理、项目 generation、终端状态重放和安全删除。
8. 开放性与退出权：本地文件、原生 Git、任意 CLI、无账号、无模型绑定、删掉协议即可退出。
9. 当前实现边界：明确 Windows-first、beta、非持久 PTY、最小 Git、无代码编辑器和无云服务。

对比章节应明确 Iris 不是什么：它不是 Jira 替代品、不是 VS Code 克隆、不是聊天机器人外壳、
不是 headless agent 编排平台、也不是个人笔记库。它占据的是这些产品之间长期缺失的一层：
以项目文档为记忆、以交互终端为执行、以人类注意力为控制的 Agent Development Environment。

## 2026-08-08 第三方许可证审计

本次以 `package-lock.json`、已安装包的许可证原文、`electron-builder.yml` 和
`0.1.0-beta.1` 的实际 `app.asar` 为依据。lockfile 中共有 968 个解析后的 npm package
条目：810 个 MIT、87 个 ISC、17 个 BSD-3-Clause、13 个 Apache-2.0、13 个 MPL-2.0，
其余为 BSD-2-Clause、BlueOak、Python-2.0、CC-BY-4.0、Unlicense、0BSD 和少量双许可证。
唯一缺失 `license` 元数据的是 Mermaid 的间接依赖 `khroma@2.1.0`，其包内 `license` 文件
明确为 MIT。

没有发现 GPL、AGPL 或 LGPL 依赖。`@resvg/resvg-js` 及其平台包使用 MPL-2.0，但只由
`scripts/gen-icons.mjs` 在构建时生成 Iris 自有图标，不进入安装包。`caniuse-lite` 的
CC-BY-4.0 数据同样只参与构建。renderer 会实际打包 `class-variance-authority`
（Apache-2.0）、`dompurify`（选择其 Apache-2.0 许可）、`robust-predicates`（Unlicense）
及大量 MIT/BSD/ISC 依赖，不需要开放 Iris 源码，但必须保留相应版权和许可证声明。

electron-builder 已自动把 `LICENSE.electron.txt` 和 `LICENSES.chromium.html` 放进解包目录；
主进程生产依赖的许可证多数仍位于 `app.asar`，但 Vite 合并后的 renderer 不会保留各 npm
包的独立许可证文件。因此发布决定为：从下一候选版本起，setup 和 portable 都必须包含
Iris 自身的 `LICENSE.txt` 与集中生成的 `THIRD_PARTY_NOTICES.txt`，不能只依赖 Electron
自带声明或 asar 内零散的许可证文件。

- [x] 根据 lockfile 生成 `THIRD_PARTY_NOTICES.txt`，通过 electron-builder `extraResources` 与 Iris 自身 `LICENSE` 一起装入 setup 和 portable，并在两种产物中核验可访问性与内容版本。

实现已加入可重复生成和防过期机制：生成器从应用源码导入与生产依赖计算分发闭包，当前覆盖
521 个包；缺失许可证文本或标识会直接失败。CI 与 `npm run dist` 都执行
`npm run licenses:check`。隔离目录中的 Windows 完整打包已通过，unpacked resources 内的
`LICENSE.txt`、`THIRD_PARTY_NOTICES.txt` 与仓库文件 SHA-256 一致，setup 和 portable 均由
该 app image 构建，NSIS setup 额外包含 Iris MIT 许可证页面；既有 `beta.1` 发布目录未覆盖。
