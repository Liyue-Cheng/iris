当前 Source Control 已打通查看状态、暂存、取消暂存和提交，但若干边界会让界面投影偏离 Git 的真实状态，或导致用户无法可靠完成已经支持的操作。本 issue 只处理现有基础闭环的正确性；diff、历史、stash、远端同步和分支生命周期等新增能力仍由原 Git 图形化 issue 跟踪。

## 已确认问题

### porcelain `-z` 重命名解析错误

`git status --porcelain=v1 -z` 的重命名记录包含新旧两个连续路径。当前实现逐段独立解析，未消费第二个路径，也未填写 `GitResource.originalPath`，会把旧路径误识别成另一条资源。资源行显示、暂存和取消暂存随后可能作用于错误或截断的路径。

### 同一文件的双层状态丢失

当 XY 状态同时包含 index 和 working tree 变化，例如 `MM`、`MD` 时，当前实现只按 X 字符把文件放入 `index` 组，Y 字符代表的未暂存变化不会显示。用户无法判断暂存内容是否已过期，也无法直接把该文件的最新工作区变化再次加入暂存区。

### 无 HEAD 仓库行为不完整

首次提交前的分支头会被解析成类似 `No commits yet on main` 的显示名称；取消暂存固定执行 `git reset HEAD -- <paths>`，在 unborn HEAD 下会失败。首次 `add` 和 `commit` 可以执行，但撤销暂存闭环不成立。

### 提交失败会丢失输入

renderer 在 `git commit` 成功前清空提交信息。Git hook、签名、用户配置或其他提交错误发生时，错误虽会显示，但用户需要重新输入提交信息。主进程统一的 5 秒 Git 超时也可能中断正常的耗时 hook 或签名流程。

### 快照可能被过期响应覆盖

刷新请求只校验项目 scope，没有同一仓库内的请求版本控制。较早发起的 status 请求如果晚于 stage、unstage 或 commit 返回，仍可能覆盖操作返回的新快照，使 UI 短暂或持续回退到旧状态。

### 状态同步覆盖不足

工作树 watcher 使用有限深度，且 `.git` 引用、锁文件和 fsmonitor 的边界尚未通过专项测试锁定。深层文件或部分 HEAD/index 变化可能无法及时触发可靠刷新。

* `2026-08-06-右键菜单功能盘点.md` 记录 Source Control 右键菜单、diff 和 discard，它们是交互扩展，不是基础稳定版 blocker。

基础稳定版建议明确限定为：可靠查看一个本地仓库的状态，暂存和取消暂存完整路径集合，提交已暂存内容，切换已有本地分支，并能从外部文件变化、命令失败和项目切换中恢复。diff、discard、历史、分支创建或删除、stash、fetch、pull、push、认证和冲突解决工作台均不进入本轮。

### 当前 issue 之外仍缺少的 blocker

#### 仓库根与项目根契约

当前 manager 在 Iris 项目根执行 Git，却没有解析并保存 `git rev-parse --show-toplevel`、`--git-dir` 和 `--git-common-dir`。当 Iris 项目只是更大仓库的子目录时，porcelain 路径、路径越界校验、watcher 范围和提交所覆盖的暂存区可能彼此不一致；linked worktree、submodule 等 `.git` 为文件的仓库也无法靠监听 `<project>/.git/**` 正确处理。

基础版必须先选择并实现一个无歧义契约。建议以 Git worktree 根为 Source Control 作用域，在 UI 明示仓库根，并以该根统一解析状态路径、操作路径和 watcher；如果不准备授权操作 Iris 项目之外的仓库文件，则应在检测到项目根不等于 worktree 根时明确禁用提交，而不能显示一个不完整列表却提交整个 index。

* [x] 探测并建模 worktree 根、Git dir 和 common dir，覆盖普通仓库、项目位于仓库子目录、linked worktree 和 submodule。

* [x] 明确项目根不等于仓库根时的产品与权限策略，保证用户看到的 staged 集合与实际 commit 的集合一致。

* [x] 所有 status、stage、unstage、commit、branch switch、路径校验和 watcher 使用同一仓库身份，仓库身份变化后旧请求和旧事件全部失效。

#### 批量路径与大仓库边界

组级暂存会把所有路径直接展开为命令行参数，在 Windows 上可能超过命令行长度；status 又受 4 MiB `maxBuffer` 和统一 5 秒超时限制。基础稳定版不能在小仓库测试通过、到真实大仓库时静默截断或部分执行。

* [x] 使用 Git 的 NUL 分隔 stdin pathspec 能力或等价的原子方案传递批量路径，避免命令行长度、前导短横线和特殊字符歧义；不要用可能只完成一部分的无状态分批操作掩盖失败。

* [x] 为只读 status、index 写操作、branch switch 和可能运行 hook 或签名的 commit 设置各自的超时与输出上限，超时错误必须指出具体操作且不能伪装成“不是 Git 仓库”。

* [ ] 定义并测试大状态输出、数千路径组操作、缓慢 hook、缓慢签名和超大提交信息的上限与失败恢复。

#### 状态模型与错误恢复

`available: false` 目前同时表示非 Git 仓库、Git 不在 `PATH`、命令超时、权限错误和仓库损坏；一次刷新失败还可能把最近的有效快照替换成空状态。稳定版需要区分“仓库不存在”和“仓库暂时不可读”，并保留可恢复的最近真相。

* [x] 建立稳定的错误分类，至少区分 Git 不可用、非仓库、权限或 ownership、index lock、超时、hook 或签名失败、分支切换冲突和未知命令失败，并提供可读但不泄露无关环境信息的消息。

* [x] 刷新失败时保留最后成功快照并标记为过期；首次读取失败才显示无快照状态，手动刷新和窗口重新聚焦可以恢复。

* [x] mutation 成功但随后 status 失败时，不得把操作误报为失败或诱导用户重复提交；操作结果和刷新结果需要可区分。

* [x] 不自动删除 `index.lock`、修改 `safe.directory`、关闭签名或绕过 hooks；只报告原因和恢复入口。

#### 并发与跨窗口一致性

FrontCPU 的 `git:repository` 串行化只覆盖当前 renderer。同一仓库被多个 Iris 窗口打开，或外部终端同时执行 Git 时，仍可能出现交错操作、旧快照和锁冲突。Git 自身的 index lock 可以防止部分数据破坏，但不能保证 UI 的因果顺序。

* [x] 快照携带仓库 generation 和单调 revision，renderer 只接受当前仓库中不早于已接收 revision 的结果；所有成功 mutation 都形成新的 revision 屏障。

* [x] 验证同窗口 refresh 与 mutation、两个窗口操作同一仓库、外部 `git add` 或 `git commit` 和项目快速切换时，不会回显旧仓库或旧 index。

* [x] 对真实 lock contention 给出可重试失败，操作失败后清除 pending、保留草稿和有效快照，随后能通过刷新恢复。

#### 提交草稿的作用域与生命周期

当前草稿保存在组件局部状态，提交前就清空；它还没有正式的项目或仓库作用域。除了修复失败丢失，还应防止切换项目后把 A 项目的提交信息带到 B 项目，或因面板卸载意外丢失。

* [x] 提交草稿按当前项目或仓库隔离，仅在 Git 明确报告 commit 成功后清空；失败、刷新和同项目视图切换均保留。

* [ ] 项目切换、窗口关闭和提交成功后的草稿策略有明确测试，任何情况下都不得把一个项目的草稿提交到另一个项目。

#### 状态语义的剩余边界

现有解析验收还需要把操作语义一并锁定，而不只是断言列表内容。尤其是 staged rename 或 copy 必须用新旧两个路径完成 stage 或 unstage；untracked 目录是否展开也应固定，否则资源计数和组级操作会随 Git 配置变化。

* [x] 明确使用不受用户 `status.relativePaths`、`status.showUntrackedFiles` 和颜色或本地化配置影响的命令参数，输出解析不依赖用户配置和当前工作目录。

* [ ] 覆盖 submodule 状态、符号链接、空格、引号、换行、非 ASCII、大小写变化、路径分隔符和超长路径；无法无损支持的文件名必须明确成为已知限制，不能误操作另一条路径。

* [ ] 对冲突资源明确只提供当前已支持且安全的操作；普通 branch switch 因脏工作树、分支被其他 worktree 占用或 detached HEAD 失败时，原快照和当前分支显示保持不变。

### watcher 的稳定版策略

简单地移除 `depth: 2` 可能修复漏报，却会让大型仓库和依赖目录的递归监听成本失控。稳定版应把 watcher 定义为失效提示器，Git status 才是唯一真相源，并设计可验证的降级路径。

* [x] 分别监听 worktree 文件变化与解析后的 Git dir/common dir 关键状态，覆盖 index、HEAD、loose refs、packed-refs、refs 目录切换和 linked worktree。

* [x] 明确 `index.lock` 和 fsmonitor 临时文件只参与防抖或完成信号，不在 Git 写入中间态反复发布错误快照。

* [x] watcher 错误、事件丢失或高频变更时进入可见 degraded 状态；手动刷新和窗口重新聚焦始终执行一次完整 reconciliation。

* [ ] 用深层目录、ignored 大目录、快速连续写入、原子 rename、外部 Git 命令和 watcher 重建测试正确性及资源消耗。

### 推荐交付顺序

1. 先冻结仓库身份、作用域、快照 revision、错误分类和命令超时契约；这些决定会影响 manager、IPC、store 和测试夹具。
2. 抽出纯 parser，修复双层状态、rename/copy、unborn/detached HEAD 和配置无关性。
3. 改造 manager 的仓库发现、stdin pathspec、命令级超时、unstage 和结构化操作结果，并补临时仓库集成测试。
4. 改造 store 的 revision 屏障、最后有效快照、失败恢复和按仓库隔离的 commit draft，并补并发测试。
5. 最后收口 watcher，因为它只负责触发 reconciliation，不应反过来决定领域模型。
6. 在干净 Windows 用户环境手工跑通普通仓库、unborn 仓库、项目位于仓库子目录、linked worktree、冲突、hook 失败和锁冲突，再执行完整自动化验证。

### 实现结果

* 新增纯 `porcelain v1 -z` parser，按 NUL 记录消费 rename/copy 的第二路径，保留 `originalPath`，并把 `MM`、`MD` 等二维状态同时投影到 index 与 working tree。unborn、detached、ahead/behind 和 upstream gone 均有独立解析覆盖。

* `GitManager` 发现并建模项目根、worktree 根、Git dir 和 common dir。Source Control 始终展示完整 worktree 状态；项目位于更大仓库子目录时明确显示实际仓库根，避免“只看到子目录却提交整个 index”。普通仓库、现场初始化仓库、linked worktree 和 submodule 均有真实仓库测试。

* stage/unstage 使用 `--literal-pathspecs` 与 NUL 分隔 stdin pathspec，不再展开到命令行。rename/copy 行和组操作均传入新旧完整路径集合；unborn HEAD 使用 `git rm --cached` 取消暂存。

* status、写 index、分支切换和 commit 使用分级超时及输出上限；commit 最长等待 5 分钟，FrontCPU 超时同步放宽，超时会终止 Git 进程树。commit message 通过 stdin 提交并保留正文中的 `#` 行。

* 错误分类覆盖 Git 不可用、非仓库、unsafe ownership、权限、index lock、超时、配置缺失、无暂存内容、hook 拒绝、普通 commit 拒绝、签名和分支冲突。Iris 不自动删 lock、改 safe.directory、关闭签名或绕过 hooks。

* 快照包含 repository identity、revision 和 stale 状态。刷新失败保留最后有效快照且禁用所有写操作；同仓库乱序 refresh、mutation 与 watcher refresh 竞态、项目切换旧响应均由 renderer 请求屏障拒绝。

* 同一进程的多个 Iris 窗口按实际 repository identity 串行 stage、unstage、commit 和 branch switch；status 等待同仓库写队列。真实双 manager 并发 stage 测试确认两个 index 更新均保留。

* 提交草稿移入 store 并按规范项目根隔离。刷新、面板重挂载、失败、切换到其他项目再返回均保留；只有 commit IPC 明确成功后清空，草稿不会串到另一项目。

* watcher 改为监听 worktree 根以及 linked worktree 的外置 Git dir/common dir，只接受 index、HEAD、packed-refs 和 refs 等权威元数据，忽略 objects、fsmonitor daemon 等噪声。`index.lock` 只在删除完成后触发 reconciliation；深层文件、外部 `git add` 和 linked worktree index 均有真实事件测试。
