### 当前结论

对“UI 消失”的最可能解释是：恢复窗口时，原生窗口已可见，而网页合成画面尚未呈现，于是先看到固定的深色底色，之后网页画面恢复。这是与现象吻合的**待验证假设**，尚不能把 Electron、GPU 驱动或某次提交认定为根因。底色不一致能解释闪出的颜色，但不能单独解释为什么出现画面空档，也不能据此宣称同步底色就能彻底修好。

## 追加调研：为何恢复会露底，是否近期性能回归（2026-09-20）

用户追问：“恢复窗口时，原生窗口已可见，而网页合成画面尚未呈现，为什么会这样？最近引入了性能问题吗？”本轮继续只读检查代码，未修改实现。

### 机制解释与结论边界

Windows 的窗口恢复／桌面合成与 Chromium 的网页绘制／提交是不同的处理链路，并非一次同步 React 更新。正常情况下可以复用已有画面，不要求最小化恢复时重新挂载整页；所以不能把肉眼明显的整窗空白当作必然且正常的恢复行为。

若恢复时旧画面暂时不可用，或 Chromium 提交的画面未及时被窗口合成接收，才可能出现“窗口已经显示，网页画面还没跟上”的间隙。画面资源的生命周期、合成时序、显示链路异常，以及页面负载导致的新帧延迟，都可能参与其中。本轮没有证据证明实际发生了纹理丢失、资源回收或 GPU 故障。

**单纯 JavaScript 很慢通常也可能只是让旧画面停住，不足以独自解释为什么旧画面消失并露出原生底色。** 因此需要同时调查“为什么没有保住旧画面”和“下一帧是否被耗时任务拖延”，而不是直接把闪屏等同于 React 性能问题。上一轮的“原生窗口先显示”是现象解释假设，不是已经测到的帧时序。

### 新找到的具体性能线索

1. **恢复聚焦确实有工作，不是完全空闲。** `settings-store` 不重新取主题，但 `git-store.ts:207` 的 `focus` 监听会触发 `gitStore.refresh()`。它立即发布 `loading: true`，等待 Git 快照后再发布结果；`LeftPane.tsx:183` 订阅了整个 Git store，因此会随这些更新重渲染，连带当前文件树和 `collectTodos()` 计算。聚焦监听在 `6cd7ab97`（2026-08-05）已存在，不是 beta.27 新引入。
2. **Git 刷新不是只读取内存。** `ipc.ts:715` 转到 `GitManager.status()`（`git-manager.ts:682`），执行仓库识别、状态、分支、HEAD 查询。Git 命令使用异步 `spawn`，所以不能将 Git 执行时间直接当成阻塞前端的时间；潜在前端开销在状态发布、快照传输与渲染。当前 refresh 只在写操作 pending 时合并请求，没有针对普通 refresh 的统一在途合并，聚焦和文件变化同时发生时有额外请求的可能。这也是既有逻辑，尚未测得它导致本次空白。
3. **beta.27 确实增加了 Raw 文件树的部分渲染工作。** `RawTree.tsx` 新增连接索引，并为文件／目录行渲染 `ItemContextMenu`；菜单 JSX 在每行执行 `workspaces.map(...)`，即使菜单没有打开也会先计算这些 React 元素。旧版目录行没有这一菜单，旧版文件菜单也没有遍历所有工作区。于是聚焦引发左栏更新时，展开节点较多、工作区较多的 Raw 视图可能比 beta.26 更贵。这里说的是元素计算，不是声称关闭的菜单 DOM 全部挂载。**这是可定位的新增成本，但没有性能采样，尚不能称为已确认的性能退化，更不能认定为闪屏根因。** 若故障发生在 Lens 视图或欢迎页，这个候选的解释力会显著下降。
4. beta.26 对 `TerminalView` 的相关变动是 External 拖放支持，未改窗口恢复／尺寸处理；终端 `ResizeObserver` 仍走防抖。beta.26 的 Agent store 还把未修改 intents 的深克隆改为保留引用，配合视图 memo 减少重复渲染，不能把这一改动描述成新增的全历史重绘。

### 定位结论

**本机已复现并定位到 Windows／Electron 的原生窗口恢复重绘间隙，叠加 Iris 原生底色写死为默认主题。没有证据表明最近的 RawTree、Git 或 Agent 业务代码性能退化是这次闪屏的根因。**

具体链路是：最小化后的原生窗口恢复可见 → 窗口系统先呈现背景／根视图 → 窗口合成器随后提交网页内容所在的画面 → UI 重新可见。Iris 的网页仍然使用 cutie，但原生底色始终是 `#191724`，因此这个间隙表现为“UI 消失，默认主题背景闪过”。这是呈现层的空档，并非已经证实 React 卸载再挂载或主题设置回退。

本轮不仅验证了颜色来源，还在不含 React、Git、编辑器、终端和业务定时器的静态 HTML 上复现了同一现象，并在窗口恢复的 Chromium trace 中观察到原生消息处理与后续合成提交的先后关系。**不能再把优化文件树当作这个故障的首要修复方向。**

### 为什么原生背景会先出来：源码与 trace 对应

1. Chromium 对应版本的 `HWNDMessageHandler::OnSize()` 在最小化／还原状态变化时调用 `HandleWindowMinimizedOrRestored()`，并请求 `RedrawWindow(... RDW_INVALIDATE | RDW_ALLCHILDREN)`；`DesktopWindowTreeHostWin::HandleWindowMinimizedOrRestored()` 对窗口树执行 Hide／Show。这条路径属于原生窗口生命周期，不以 React 是否有状态更新为前提。
2. Electron **v43.4.0** 的 `NativeWindowViews::SetBackgroundColor()` 不仅保存颜色，还设置 Windows `GCLP_HBRBACKGROUND` 画刷、网页后方 `root_view_` 的纯色背景，以及窗口 compositor 的背景。因此网页画面未覆盖的原生层确实会呈现该颜色，鲜绿色替换实验与之吻合。
3. 高精度无动画复测的 trace 中，一个原生 `WM_SYSCOMMAND` 处理耗时 **81.589 ms**（线程 CPU 时间 **17.391 ms**）；相对消息开始，窗口 `SingleThreadProxy::DoComposite` 在 **109.629 ms**，`Display::SetSurfaceId` 在 **109.722 ms**，`Display::DrawAndSwap` 在 **109.810 ms**，`FramePresented` 在 **117.051 ms**。另一个样本分别为消息耗时 **72.303 ms**、合成 **101.885 ms**、呈现 **110.947 ms**。这些是诊断窗口的真实 trace 值，不是对用户每次闪屏时长的估计。
4. 这证明即便网页没有业务负载，窗口恢复仍存在原生消息处理与随后新画面提交之间的间隔。消息的墙钟时间明显大于线程 CPU 时间，也不支持把全部延迟解释成网页 JavaScript 在忙。

查到了 Electron [#42378](https://github.com/electron/electron/issues/42378) 和修复 [#52844](https://github.com/electron/electron/pull/52844)。后者修复隐藏时 `setBackgroundThrottling(false)` 绕过 view 直接调用 `WasShown()`，导致表面 ID／可见性不同步。43.4.0 源码确实还没有该修复。
