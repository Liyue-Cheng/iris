一次对所有产品文档的清查：把"为哲学纯粹性而牺牲功能"的语句逐条揪出来，区分
**本质约束**（让产品更好，留）与**自我设限 / 措辞过硬**（挡住合理需求，改）。

## 缘起

讨论"要不要和 Jira/Linear 集成"时暴露出一个问题：红线被当成教条来挡需求，而不是
服务于"把该做的做出来"。产品负责人据此要求全面清查。详见 `2026-06-21-集成问题.md`。

## 核心发现

**定义书早就允许了被挡掉的需求，是下游文档把它写丢了。**

- 定义书 §2「哑壳 + 智能外包」与 §7 白纸黑字：智能外包"**不是禁令**……不拒绝
  **用户 BYOK 驱动的辅助功能**……禁的是壳自带智能，不是用户自带智能"。用户自带
  Jira token、自担计费的小自动化，本就在批准之列。
- `CLAUDE.md` 红线 #1 把它压成无但书的"不内嵌 agent、SDK、API key"，并扣上
  "违反 = 错误"——BYOK 豁免在搬运中丢失。
- `2026-06-21-集成问题.md` 进一步拔高成"身份认同的试金石 / 反 Iris"，而定义书 §7
  的原话恰是"不是身份认同"。该 issue 违反了定义书自己的元立场。

结论：定义书本身已被反复去教条化（"取舍，非教条""不是否决票"遍布全文）；病灶在
**下游两处的硬化措辞**，清查范围比预期小，也更好治。

## 基础方案讨论

不删红线，而是**分层**——把"真不变量"和"当前取舍"分开，并恢复被丢的豁免。

1. **真不变量**（保留强约束）：零 diff、文件即契约、渲染确定性、零账号/云/遥测、
   不执行陌生代码、agent 不改宪法。
2. **当前取舍**（标注"理由可变则重谈"，与定义书 §7 对齐）：集成方式、headless、插件。
3. **被丢的豁免**（恢复）：用户 BYOK 自带自动化。

对集成需求，给出三级出口（从轻到重）：

- **① frontmatter 存 `jira_key`**：今天就合法（键是自由软值，非 schema），零壳改动。
- **② 拉取 / 推送走 BYOK 自动化或 agent 层**：用户对 agent 说"同步到 Jira"，
  agent 用自带 MCP/CLI；或用户自带 key 的小自动化。壳依然哑。
- **③ 通用「状态迁移命令钩子」**（v1.1 候选，本轮仅写文档不实现）：壳在 `status:`
  变化时执行**用户自带的脚本**，自己不认识 Jira——与 git hook 同理，不破任何不变量。
  这是把"窄门"从"单向只读导出"放宽后的壳层触发点。
