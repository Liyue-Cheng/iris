## 调查结论

已定位，问题发生在 main 进程的 Iris Agent 会话重试流程，不是 renderer 的按钮误调用撤销，也不是 Worker 自己丢失上下文。

调用链如下：

1. [IrisAgentView.tsx](../../src/renderer/components/agent/IrisAgentView.tsx) 只在最后一个 Turn 为 `failed` 或 `stopped` 时显示重试，并调用 `retryIrisAgent(session.id)`。
2. [iris-agent-actions.ts](../../src/renderer/lib/iris-agent-actions.ts) 正确发送 `IRIS_AGENT_RETRY` IPC 命令；这里没有清理 Turn。
3. [session-manager.ts](../../src/main/agent/session-manager.ts) 的 `retrySession()` 找到最后一个失败 Turn 后，先关闭旧 Worker，然后调用 `undoLatestIrisAgentTurn()`。
4. `undoLatestIrisAgentTurn()` 会删除最后一个 Turn 的 user/assistant 消息、toolEvents、requestFacts，并加入 `pendingArtifactCleanupTurnIds`，等价于“撤销上一轮”。
5. 随后 `startTurn()` 使用原 user message 的文本创建一个新的 Turn，并写入 `retryOfTurnId`。由于旧 Turn 已被删除，新 Turn 虽然保存了旧 ID 关联，但时间线中只剩新的 running Turn，用户看到的就是整轮被重置。

因此，失败重试当前的实际语义是：`撤销失败 Turn + 用相同文本新发一轮`，而不是“保留失败 Turn 的可见记录，只重发请求”。这正是 issue 描述的严重行为错误。

## 证据

- [session-manager.ts](../../src/main/agent/session-manager.ts) 的 `retrySession()` 在 `startTurn()` 前直接执行 `undoLatestIrisAgentTurn()`。
- [session-domain.ts](../../src/main/agent/session-domain.ts) 中的 `undoLatestIrisAgentTurn()` 明确过滤掉最后一个 Turn 的 `messages`、`turns`、`toolEvents`、`requestFacts`。
- 现有 retry 测试 [session-manager.test.ts](../../src/main/agent/session-manager.test.ts) 反而断言 `retried.turns` 长度为 `1`，并断言新 Worker 的 `initialize.history.messages` 为空；测试把错误语义固化了，没有覆盖保留原失败 Turn 的要求。
- `rewindSession()` 也使用同一个 reducer，但它才是应该删除最后一轮的显式“撤销”操作。retry 复用它造成了两个不同用户动作的职责混淆。
- 该逻辑由提交 `f7d3db5`（`Implement canonical Iris Agent session remediation`）引入；当前 HEAD 为 `67c9a97b624d1dc6b3fe4037118ad46c515733d9`。调查期间未修改代码。

## 影响

- 失败 Turn 的用户消息、部分 assistant 输出、工具调用记录和请求事实从会话时间线消失。
- 失败 Turn 的 prompt/provider artifact 会进入清理流程，重试后无法再从原 Turn 直接检查失败上下文。
- 新请求虽然保留了 `retryOfTurnId` 字段，但该字段指向一个已从 `turns` 中移除的 Turn，无法提供完整的历史审计关系。
- Worker 重启本身不是根因。为重试而重新创建 Worker 可以接受，但 Worker 初始化历史必须来自保留失败 Turn 后的会话历史；当前之所以为空，是因为撤销先删掉了它。

## 修复方向

retry 应与 rewind 分离：

- 保留原失败/停止 Turn、它的消息和工具/请求记录，继续作为会话历史的一部分。
- 以原 user message 内容创建一个新的 retry Turn，保留 `retryOfTurnId` 作为显式关联；新 Turn 的 prompt 重新组装并重新请求。
- 不要在 retry 路径调用 `undoLatestIrisAgentTurn()`，也不要清理旧 Turn 的 artifacts。
- 保持当前的 quiescence、revision、worker event drain 和 correlation 校验，避免旧 Worker 事件污染新 Turn。
- 重新定义并补充测试：重试后旧 Turn 仍存在且状态仍为 `failed`/`stopped`，新 Turn 为 `running`，新 Worker history 包含旧 Turn 的非空消息；同时验证旧 Turn 的工具事件、request facts 和 artifact 仍可访问。单独的 rewind 测试继续验证删除最后 Turn。

待修复验收：

- [x] 失败 Turn 点击重试后，原 Turn 仍显示在时间线中，原有部分输出和错误信息不消失。
- [x] 重试只新增一个 retry Turn 并发出一次新的 provider 请求，不删除旧 Turn 或其审计记录。
- [x] 重试期间 Worker 初始化历史包含重试前的会话消息，且旧 Worker 的迟到事件不会改变新 Turn。
- [x] rewind 仍只在用户明确点击撤销时删除最后一轮。

## 方案否决记录

上述“保留失败 Turn，再新增 retry Turn”的方案已被否决。上面的验收项被关闭是因为方案作废，不代表已经实现。

否决原因是该方案仍然把 provider 故障泄漏到了 Turn 层：它承认存在“失败 Turn”，并把 retry 建模为 Turn 之间的关系。正确的不变量应当是：**Turn 是理想业务层，Turn 永远不会失败。**

## 新方案：Turn 与执行彻底解耦

### 核心语义

Turn 表示一次用户意图及其最终逻辑结果，不表示某次 provider 请求、某个 Worker 生命周期或某次网络尝试。

Turn 只允许以下状态：

- `active`：下层正在推进这个 Turn。
- `paused`：当前没有下层执行能够继续推进，但 Turn 本身仍然有效、未失败、可恢复。
- `completed`：用户意图已经得到逻辑结果。

Turn 不再拥有 `failed`。用户主动停止、provider 重试耗尽、Worker 崩溃、网络断开、鉴权失效等情况都只会令 Turn 进入 `paused`，不会产生失败 Turn。恢复后继续同一个 Turn；只有完成时才进入 `completed`。

`rewind` 也不应成为 Turn 的运行状态。它是用户对会话历史执行的编辑命令：从当前时间线移除目标 Turn，并保留 undo receipt 和外部副作用审计。

### 两层模型

逻辑层为 `IrisAgentTurn`：

- 只保存稳定的 `turnId`、用户消息、已提交的 assistant/tool 逻辑历史、创建时间、完成时间和 `active | paused | completed` 状态。
- 移除 `requestId`、`retryOfTurnId`、`error`、`providerCallCount` 等执行细节。
- 同一次用户意图从首次发送到多次暂停、恢复、自动重试、手工重试，始终只有一个 Turn、一个 user message，不复制 Turn。

执行层新增 `IrisAgentTurnExecution`：

- 通过 `turnId` 关联当前 Turn，但拥有独立的 `executionId`、`workerEpoch` 和运行状态。
- 状态至少包括 `running`、`waiting-tool`、`retry-wait`、`paused`、`completed`。
- `paused` 记录结构化的暂停原因，例如 `provider-exhausted`、`worker-crashed`、`auth-required`、`user-requested`，以及可展示的错误和是否可恢复。
- provider 调用进一步拆成逻辑 `providerCallId` 和物理 `attemptId`。自动重试或手工重试只新增 Attempt，不新增 Turn，也不重新发送 user message。
- provider payload、错误、调用次数和耗时进入 Attempt 审计或 context artifact，不进入 Turn 消息和 Turn 状态。

关系如下：

```text
Turn (一个用户意图，永不失败)
└── Execution (推进或暂停该 Turn)
    ├── Provider Call 1
    │   ├── Attempt 1: provider error
    │   └── Attempt 2: success
    ├── Tool execution
    └── Provider Call 2
        └── Attempt 1: success
```

### 正常失败与重试流程

1. 用户发送消息时创建一个 `active` Turn，并创建对应 Execution。
2. 每次真正调用模型时创建 Provider Call；每次 HTTP/stream 尝试创建 Attempt。
3. provider 瞬时故障由 Pi 的自动重试策略在同一 Provider Call 内处理。`auto_retry_start` / `auto_retry_end` 只更新 Execution/Attempt。
4. `message_end(stopReason=error)` 和 `agent_end(willRetry=true)` 绝不能 settle Turn。当前代码在这里把 Turn 标成 `failed`，是需要移除的核心错误。
5. 自动重试成功后提交该 Provider Call 的结果，继续推进原 Execution，Turn ID、消息 ID、工具历史均不变化。
6. 自动重试耗尽或出现需要用户修复的 provider 问题时，Execution 与 Turn 一起进入 `paused`。错误显示在会话运行状态区域，不生成失败回复卡片，不写入 Turn 的 `error`。
7. 用户点击重试后，对暂停的 Execution 创建新 Attempt，恢复同一个 Turn。不得调用 undo，不得调用 `startTurn()`，不得创建 `retryOfTurnId`，不得重新组装一条新的用户轮次。
8. provider 最终成功且 `agent_settled` 确认没有后续工作时，Execution 和 Turn 才进入 `completed`。

### 流式内容与副作用边界

provider Attempt 的流式增量必须先进入 attempt-scoped 暂存区。UI 可以实时投影暂存内容，但只有成功的 `message_end` 才把它提交为 Turn 的逻辑消息。

Attempt 失败时丢弃的只能是该 Attempt 尚未提交的增量和错误 assistant message，不能回滚同一 Turn 中此前已经成功的 Provider Call、工具结果或文件副作用。这样在“已经执行工具，下一次 provider call 失败”的场景中，重试只重发失败的 provider call，不会重复执行之前的工具。

若 Worker 已死亡，恢复流程应从同一 Turn 最近一次已提交的 Provider Call/tool result checkpoint 重建 Worker，然后继续缺失的 provider call。不得从原始用户 prompt 重新运行整个 Turn。

### 协议与持久化调整

- Worker correlation 从当前的 `workerEpoch + requestId + turnId` 扩展为 `workerEpoch + turnId + executionId + providerCallId + attemptId`。
- Worker 向 main 发送结构化的 provider retry/paused/resumed 事件；原始 provider error 不再伪装成 Turn failure。
- `activeTurnId` 的“Worker 正在运行”含义拆开：会话保留当前未完成的 Turn 引用，Execution 单独表达是否正在运行。暂停 Turn 仍然是当前 Turn，但没有活动 Attempt。
- provider context bundle 按 Provider Call/Attempt 保存 payload 和错误；Turn 只保留到该诊断资产的入口，不承载调用次数和错误状态。
- `requestFacts` 保留为 Turn 输入组装事实；provider 的每次物理请求事实进入 Attempt 记录。
- 新数据不再写 `retryOfTurnId`。旧版 `failed` Turn 在加载时迁移为 `paused` Turn 加 `paused` Execution，旧诊断信息保留，不能通过创建第二个 Turn 来迁移。

### UI 语义

- 时间线中不存在“失败 Turn”和 provider 错误回复卡片。
- Turn 暂停时，原 user message、已提交回复、工具活动保持原样。
- provider 错误在时间线之外的运行状态区展示，例如“请求暂停：Provider 暂时不可用”，并提供恢复按钮。
- 自动重试期间只显示 Execution 的重试/等待状态；不重复 user message，不新增 Turn 卡片。
- 暂停期间发送框不能悄悄开始下一个 Turn；用户必须先恢复、明确结束或 rewind 当前 Turn。

### 实施顺序

1. 先在 shared types 和 session store 引入 Execution/Provider Call/Attempt，并完成旧 `failed` Turn 的兼容迁移。
2. 调整 Worker 协议，透传 Pi 已有的 `auto_retry_start`、`auto_retry_end`、`agent_end.willRetry` 和 `agent_settled` 语义。
3. 重写 main reducer：provider error 只更新 Execution；Turn 仅在 `agent_settled` 成功时完成，在无法继续或用户停止时暂停。
4. 将 `IRIS_AGENT_RETRY` 改为恢复当前暂停 Execution，删除 retry 路径中的 undo、`startTurn()` 和 artifact cleanup。
5. 引入 Attempt 流式暂存与 checkpoint 恢复，确保失败 call 的部分增量不污染 Turn，也不重复先前工具调用。
6. 更新 renderer，将错误和重试入口从 Turn 卡片移到运行状态区，并移除基于 `turn.status === 'failed'` 的投影。
7. 最后迁移测试，删除所有“重试产生新 Turn”或“Turn 状态为 failed”的断言。

## 实施结果

已按新方案完成全面治理。Turn 现在只有 `active | paused | completed`，不再保存 `requestId`、
`retryOfTurnId`、provider error 或失败/停止状态。Session store schema 升至 v6，旧
`running/failed/stopped` 数据会迁移为 Turn + Execution；应用重启中断也恢复为同一个
`paused` Turn。暂停时 `activeTurnId` 继续指向当前未完成 Turn，是否正在运行由 Execution 表达。

Worker protocol 升至 v7，correlation 包含 `executionId(requestId) + providerCallId + attemptId`。
Pi 的 `auto_retry_start/end` 被投影为 Execution 状态，同一逻辑 Provider Call 的物理请求各自形成
Attempt。失败 assistant `message_end` 不再进入 stream；失败流式增量只存在于 Execution draft，
Attempt 失败时清空。只有最终成功消息会提交到 Turn，且只有完整执行返回后才发送
`execution-settled`；重试耗尽、异常或 Worker 故障发送 `execution-paused`。

手工“重试”已改为恢复：复用原 `turnId`、Execution、user message 和 Provider Call，通过
`agent.continue()` 从已提交的 provider/tool checkpoint 继续，不调用 undo、`startTurn()` 或 artifact
清理。Worker 重建时从暂停 Turn 的 canonical history 恢复。发送新 Turn 会被暂停 Turn 阻止；rewind
仍是唯一删除逻辑轮次的历史编辑命令。

main reducer 对 stream 和 Attempt 结束事件执行 call/attempt 精确匹配，并要求 Attempt index 单调
递增。旧 Worker 由 epoch 拒绝，旧 Attempt 的迟到 delta/failure 不能清空或污染新 Attempt。Provider
payload 仍写入不可变 context 文件；可读 `index.txt` 在打开时合并持久化 Attempt 审计，包含
provider call、attempt、状态、时间和错误。

Renderer 不再生成失败 Turn 或 provider 错误回复卡。错误位于独立的“当前 Turn 已暂停”状态条，
恢复按钮和输入区恢复动作都推进同一 Turn；自动重试显示为 `retry-wait`。失败 draft 不进入逻辑
时间线，已提交回复、工具活动和文件副作用保持原顺序。

## 审核修订：Turn 的开放与用户终止

当前实现仍有一个抽象缺口：`paused` 只能表达 Execution 暂时没有继续推进，不能表达用户已经决定
不再恢复这个意图。若暂停 Turn 阻止发送新消息，系统就无法表示以下正常流程：

```text
Provider 故障 -> 用户不重试 -> 直接发送新消息
用户按停 -> 用户不恢复 -> 发送新消息
```

这两种情况不是 Turn 失败，也不是 rewind。旧 Turn 的用户消息、已提交回复、工具活动和外部副作用
都应保留；变化只是用户宣告“这个意图到此结束”，然后开始一个新的 Turn。

### 修订后的正交模型

Turn 只表达逻辑意图是否仍开放：

```text
Turn.lifecycle = open | closed
Turn.closeReason = fulfilled | user-ended   // 仅 closed 时存在
```

- `open`：用户意图仍然有效，未来可以由 Execution 继续推进。
- `closed + fulfilled`：Agent 已经给出逻辑结果并正常 settle。
- `closed + user-ended`：用户明确不再追求本 Turn 的结果。它不是失败，也不伪装成 fulfilled。

Execution 独立表达运行能力：

```text
Execution.state = running | waiting-tool | retry-wait | paused | completed | terminated
```

- provider、网络、Worker、鉴权故障只会把 Execution 变为 `paused`，Turn 仍为 `open`。
- 用户按停只会把 Execution 变为 `paused`，Turn 仍为 `open`，所以仍可恢复。
- Turn 被用户结束时，Execution 变为 `terminated`，终止原因记为 `user-ended`；该 Execution 不可再恢复。
- Agent 正常 settle 时，Execution 变为 `completed`，Turn 关闭为 `fulfilled`。

因此不再需要 Turn 的 `active | paused | completed` 三态。`paused` 本来就是执行态；把它放在 Turn
上会混淆“暂时不能推进”和“用户已经结束意图”。Session 的 `currentTurnId` 只指向 `open` Turn，
比当前 `activeTurnId` 同时表达 current/running 更准确。

### 用户动作语义

暂停状态下必须同时提供两个互不替代的动作：

1. **恢复**：继续当前 open Turn，复用原 Execution checkpoint，只新增 Provider Attempt。
2. **发送新消息**：原子地将当前 Turn 关闭为 `user-ended`，终止旧 Execution，再创建新 Turn。

发送框在暂停时不应禁用，也不应把发送按钮变成“恢复”。用户输入文字并发送，本身就是“结束旧
意图并开始新意图”的明确表达。状态条可以保留独立恢复按钮，也可以提供显式“结束 Turn”动作，
用于用户只想结束但暂时不发新消息的情况。

运行中仍不能直接并发创建下一 Turn。用户应先按停；收到暂停结算后，发送新消息采用上述原子转换。
这避免正在执行的工具与新 Turn 并发，也使旧 Worker 的事件隔离边界清晰。

### 原子状态转换

暂停 Turn 上发送新消息应是一个 main-owned、带 `expectedRevision + commandId` 的事务：

```text
旧 Turn: open -> closed(user-ended)
旧 Execution: paused -> terminated(user-ended)
Session.currentTurnId: 旧 Turn -> 新 Turn
新 Turn: 创建为 open
新 Execution: 创建为 running；若启动失败则 paused
```

事务必须保留旧 Turn 的所有已提交消息、工具结果、request facts、Attempt 审计、provider artifact 和
外部副作用；只丢弃旧 Attempt 未提交的 draft。它不得调用 rewind，也不得把旧 user message 拼成
新 Turn 的 prompt。

为避免 Pi 内存中残留 provider error 或未完成 continuation，开始新 Turn 前应隔离旧 Worker，并用
canonical committed history 重建 Worker。新 Worker history 包含旧 Turn 的用户消息和已提交
assistant/tool checkpoint，不包含失败 Attempt 的 error assistant 或 draft。连续 user message 的
provider 兼容归一化属于 history adapter，不应改变逻辑 Turn 边界。

### 与其他操作的边界

- `resume`：同一 open Turn、同一 Execution，新增 Attempt。
- `stop`：暂停 Execution，Turn 仍 open。
- `end`：关闭 Turn 为 `user-ended`，终止 Execution，不删除历史。
- `send while paused`：`end + start new Turn` 的原子快捷路径。
- `rewind`：删除最后一个 Turn 的历史编辑；与 end、stop、resume 均不共享 reducer。
- `app restart`：未关闭 Turn 仍 open，Execution 恢复为 paused，不自动视为用户结束。

### 修订验收

- [x] Provider 故障或用户按停后，当前 Turn 保持 open，既可以恢复，也可以直接发送新消息。（方案已由下节替代，非实现完成）
- [x] 暂停时发送新消息会将旧 Turn 关闭为 `user-ended`，不会标记失败、fulfilled 或删除旧 Turn。（方案已由下节替代，非实现完成）
- [x] 关闭旧 Turn并创建新 Turn是一个具备 revision/idempotency 保护的原子状态转换。（方案已由下节替代，非实现完成）
- [x] 被用户结束的 Execution 进入不可恢复的 terminal 状态；旧 Worker/Attempt 迟到事件不能重新打开它。（方案已由下节替代，非实现完成）
- [x] 新 Turn 的 Worker 从旧 Turn 已提交 checkpoint 重建，不包含失败 draft/error，也不重复旧工具。（方案已由下节替代，非实现完成）
- [x] UI 在暂停时同时保留恢复入口和可编辑发送框；发送文字的语义是开始新 Turn，而不是恢复旧 Turn。（方案已由下节替代，非实现完成）

## 审核修订：停止可恢复，但不暴露 Turn 操作

上一节提出的显式“结束 Turn”入口被否决。Turn、Execution、`user-ended` 都是内部中间表示，
不应作为用户需要理解或操作的产品概念。界面不提供“结束 Turn”按钮，也不要求用户先执行内部
状态清理才能继续对话。

人工停止也不定义为不可恢复的意图终止。Iris 的停止语义与 Codex Esc 有意区分：

```text
停止 = 中断当前执行，在安全 checkpoint 暂停
继续 = 从 checkpoint 继续原用户意图
发送新消息 = 隐式放弃原意图，并开始新意图
```

选择可恢复停止的原因是它包含两条后续路径：用户既可继续，也可直接发新消息；不可恢复停止只能
表达后一条路径，信息损失更大。是否放弃意图由停止后的下一次用户动作决定，而不是由按下停止键
提前推断。

### 产品行为

- Agent 运行时只显示停止按钮。
- 用户按停止后先进入 `stopping`；只有 Worker 已停止、在途工具已结算且 checkpoint 可用时，界面
  才进入暂停表现。
- 暂停表现不出现 Turn、Execution、Attempt 或“结束 Turn”等术语，只显示与原因相符的状态文案和
  一个“继续”按钮。
- 暂停时输入框保持可编辑。点击“继续”不读取输入框，恢复原任务；发送非空文字则创建新请求。
- 发送新文字时，main 在内部关闭旧 open Turn 为 `user-ended` 并终止旧 Execution，然后原子创建
  新 Turn。用户只看到一条正常的新消息。
- 若用户停止后离开页面或重启应用，旧意图保持可继续的暂停状态；不会因时间或页面切换自动结束。

### 继续的精确定义

“继续”不是恢复同一条 HTTP stream，也不承诺从最后一个 token 无缝续写。它表示从最后一个安全、
已提交的 provider/tool checkpoint 对同一用户意图发起新的物理 Provider Attempt：

- 已完成工具及其副作用不重复执行。
- 已提交 assistant/tool 消息保留。
- 被用户中断的物理 Attempt 记录为 `aborted`，不是 `failed`。
- 用户停止前已经展示的文本会经过 provider-safe 清理后提交为“被中断的 assistant 片段”，成为继续
  checkpoint；未闭合 tool call、无效 reasoning/signature 和不可安全提交的尾部仍丢弃。
- provider 故障产生的未完成 draft 仍不进入 canonical history。人工停止与 provider failure 不能
  共用 draft 丢弃策略，否则继续时模型不知道用户已经看到的内容，容易重复输出。
- 新 Attempt 仍属于同一 Turn、Execution 和适用的 Provider Call。

如果停止发生在工具执行期间，不能为了尽快显示“已暂停”而假装 checkpoint 已成立。系统应先等待
工具自然结算，或由工具层明确返回可审计的取消结果；只有 main 已持久化结果后才允许继续。外部
副作用即使只完成一部分也必须记录，恢复不能盲目重放同一工具。

### 对上一节验收的替代

上一节关于显式结束入口及“五种 UI 操作”的验收作废，以以下标准替代：

- [x] 人工停止只暂停 Execution，Turn 在内部保持 open，并在安全 checkpoint 建立后显示“继续”。
- [x] 被人工中断的 Provider Attempt 记录为 `aborted`，已展示文本形成 provider-safe interrupted
  checkpoint；provider failure 的 draft 仍被丢弃。
- [x] 点击“继续”复用同一 Turn/Execution/checkpoint，只新增物理 Attempt，且不重复已结算工具。
- [x] 暂停时输入框可编辑；发送非空文字会隐式关闭旧意图并原子创建新 Turn，不需要显式结束操作。
- [x] UI 不出现 Turn、Execution、Attempt、user-ended 或“结束 Turn”等内部术语。
- [x] stop、continue、暂停后发送新消息和 rewind 分别有独立状态机测试。

## 实施结果

已按最终审核语义完成全面治理：

- Turn 只保留 `open | closed`，关闭原因仅为正常完成的 `fulfilled` 或用户发送新消息时内部使用的
  `user-ended`；provider、Worker、鉴权和人工停止都不会产生失败 Turn。
- Execution 独立表达运行、工具等待、provider 重试等待、暂停、完成和用户终止；Session 只用
  `currentTurnId` 指向仍可继续的 open Turn。
- 人工停止会等待 Worker abort 及在途工具结算。被中断 Attempt 记为 `aborted`；Pi aborted assistant
  通过 provider-safe 归一化后只提交纯文本 checkpoint，未闭合 tool call、reasoning/signature 不进入
  canonical history。provider failure draft 继续丢弃。
- “继续”复用原 Turn、Execution、Provider Call 和 checkpoint，只递增 Attempt。暂停后发送非空
  新消息先完成 prompt 准备；准备失败保持原状态，成功后隔离旧 Worker，并在一次 store 提交中将
  旧 Turn 关闭为 `user-ended`、旧 Execution 终止，同时创建新 Turn/Execution。
- Renderer 暂停条只显示“已停止”或“请求已暂停”及“继续”；输入框保持可编辑，发送按钮始终表达
  发送，不提供结束入口，也不显示内部状态机术语。
- Session store 升至 schema v7，Worker protocol 升至 v8；旧 `activeTurnId` 和
  `running/active/paused/completed/failed/stopped` Turn 数据会迁移到新模型，应用重启后的 open Turn
  保持可继续。
