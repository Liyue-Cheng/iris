## 本轮排查范围与方法（2026-10-24）

本轮按用户要求做全面排查，以当前工作区实际代码（含已有未提交修改）为准，历史 issue 的完成状态不作为通过依据。先记录问题与可复现证据，不直接修改生产实现。

## 排查结论

**仍有严重问题。** 本轮确认 10 类缺陷，建议其中 6 类按 P1 优先处理、4 类按 P2 随后处理。尤其是 F02，能够再次造成「鼠标捕获仍开启，但 SGR 编码没有恢复」的状态；上一轮补齐鼠标编码并未覆盖快照切在半条控制序列上的情形。

本轮完成的是排查与证据整理，**没有修复生产代码**。下面描述的是当前源码及已安装依赖上的复现，不代表已经定位用户当前安装版每一次异常的唯一原因。issue 的 `In Review` 表示排查结果待审阅，不表示这些 bug 已解决。

### F01：快照内容已经包含新输出，边界序号却仍停在旧输出

位置：[terminal-session-manager.ts](../../src/main/terminal-session-manager.ts) 的 `prepareReplayNow`，约 706–721 行；[terminal-mirror.ts](../../src/main/terminal/terminal-mirror.ts) 的 `fence`，约 64–81 行。Agent 的 `replayTerminal` 也采用先取边界、再等待 fence、最后序列化的相同结构，需一起修复；本项完整 `ABB` 复现在普通终端完成。

当前代码先冻结 `replayLastSeq`，然后 `await mirror.fence()`，最后 `serialize()`。但是 xterm 的 fence 回调只是 resolve Promise；同一轮 parser drain 可以继续解析 fence 后的 chunk，然后才运行 await 后的序列化。因此「fence 后字节一定不在快照里」的代码注释不成立。

实际复现顺序：

1. PTY 输出 `A`，序号为 0。
2. 请求 replay，等一个 microtask 让协调器插入 fence。
3. PTY 输出 `B`，序号为 1。
4. 返回的快照内容已经是 `AB`，但 `lastSeq` 仍为 0。
5. 恢复端按现行规则继续应用 seq 1 的 `B`，真实 xterm 最终显示 **`ABB`**。

影响包括切换终端、首次挂载、history resync 时的重复文本；若被重复应用的是控制序列，也可能破坏 TUI 状态。建议把序号边界与实际快照获取放在同一解析边界内，不通过调整等待时间掩盖问题，并覆盖 fence 超时的降级语义。

### F02：完整解析完输入 chunk，不等于处在完整控制序列边界

位置：[terminal-mirror.ts](../../src/main/terminal/terminal-mirror.ts) 的 `fence/serialize`；[terminal-session-manager.ts](../../src/main/terminal-session-manager.ts) 的 replay 边界处理。

真实 xterm 输入如下前缀，取快照后再输入后缀：

```js
const prefix = '\x1b[?1003hhello\x1b[?100';
const suffix = '6h!';
```

原终端显示 `hello!`，`DECRQM 1006` 返回已启用；恢复端显示 **`hello6h!`**，同一查询返回未启用，`1003` 鼠标捕获却仍开启。这里丢的是 parser 中尚未完成的 CSI 前缀，不是上一轮已经补齐的最终鼠标编码字段。

PTY 分片可以落在任意字节边界。当前序列化只恢复完成解析的终端状态，后续增量又继续从分片中间开始，形成永久分叉。建议定义安全的快照切点，或者保留并正确接续未完成的解析尾部；不能靠一次空写入 fence 证明 parser 已回到普通文本状态。

### F03：恢复滚动区域会重置当前光标

位置：[terminal-mirror.ts](../../src/main/terminal/terminal-mirror.ts) 约 81、100–108 行，以及已安装 `@xterm/addon-serialize` 的滚动区域序列化。

```js
const prefix = '\x1b[2;5r\x1b[4;7Hstatus';
const suffix = '!';
```

源端在第 4 行继续得到 `status!`；快照恢复后，`!` 被写到**第 1 行第 1 列**。原因是末尾的 DECSTBM（`CSI top;bottom r`）会重置光标，但之后没有恢复实际光标位置。

当前 addon 自己也会追加滚动区域指令，Iris 又追加一次。因此只删除 Iris 那次重复指令并不足以修复。需要按 origin mode、滚动区域和实际坐标，在正确顺序下恢复光标，并验证恢复后的后续写入，不能只比较静态画面。

### F04：协议回复依赖可见 renderer，隐藏或冻结时会丢查询

位置：[terminal-mirror.ts](../../src/main/terminal/terminal-mirror.ts) 构造函数未接入 headless `onData`；[terminal-protocol.ts](../../src/main/terminal/terminal-protocol.ts) 约 68–72 行只接管 OSC 10/11；[replay-controller.ts](../../src/renderer/terminal/replay-controller.ts) 约 41 行在 history-frozen 状态直接 ACK 并丢弃显示数据。

普通终端未 attach 时输入 `hello\x1b[6n`：实际 manager/mirror 不向 PTY 回复；之后生成并恢复快照也不回复，因为快照已不包含这条查询。裸 headless xterm 对照会回复 `\x1b[1;6R`。所以切回终端不能可靠补救，等待该回复的程序可能一直等候。

已补真实 Windows 验证，避免误把 ConPTY 能自动回答的查询算作 Iris 缺陷：

- 普通终端实际使用 `useConpty:true,useConptyDll:true`。用相同配置启动 Node 子进程，宿主只回答启动 DA 握手，随后 DSR、DA、DECRQM、OSC10/11、DECRQSS 六种查询都原样到达宿主；在 1800ms 的观察 sentinel 中 `replyPackets=0`，子进程随后正常退出（exitCode 0）。
- 单独 DSR 对照：100ms 发查询，1000ms 输出 `OBSERVATION_DONE replyPackets=0`，1400ms 正常退出。该结果证明观察窗口内无回复；没有用强杀或退出超时冒充「真实程序永久挂死」。与 manager 确定性丢弃查询的复现结合，说明普通终端现行 Windows 配置可以到达故障链。
- 当前 Agent PTY 没有显式启用 bundled ConPTY DLL。系统 ConPTY 对上述四种 CSI/DCS 查询能自动回答，但 OSC10/11 被吞掉且不回答；不能把两种后端当作同样的协议行为。另用实际 `AgentCommandPty` 加受控 PTY 输入 DSR/OSC，确认其宿主层和随后快照都没有回复机制；这不等于系统 ConPTY 下所有 DSR 都会失败。

建议把协议回复统一到持续工作的唯一所有者，并与画面显示解耦。**不能只把 mirror.onData 连到 PTY 而保留 renderer 对同一查询再次回复，否则会引入双回包。** Agent/普通终端的 ConPTY 配置差异也需明确处理。

### F05：普通页面重载不会执行 React 卸载，旧 attachment 无人 ACK

位置：[TerminalView.tsx](../../src/renderer/components/terminal/TerminalView.tsx) 约 316–318 行只在 runtime cleanup 时 detach；[app-main.ts](../../src/main/app-main.ts) 未在普通重载时撤销输出订阅；[project-store.ts](../../src/renderer/stores/project-store.ts) 初始为 `doc/path:null`；[RightPane.tsx](../../src/renderer/components/layout/RightPane.tsx) 对应视图不挂载终端。

刷新页面丢失旧 renderer 的监听器，但不会调用 React effect cleanup。新页面即使 hydrate 出会话列表，也不一定立即挂回原终端。main 仍向旧 attachment 发送数据并累计未确认字节；达到 384 KiB 高水位后暂停 PTY。

受控复现输出 400 KiB，等待 mirror 完全排空后诊断仍为：

```text
mirror.pendingBytes = 0
output.inFlightBytes = 409600
flow = { paused: true, blockers: ['renderer'] }
```

显式 detach 后才恢复。普通重载链路经过源码核对，尚未启动 Electron 做人工 Ctrl+R 验收。**不要扩展为所有 renderer crash 都泄露**：`app-main.ts` 已对 crashed/oom 等情况销毁窗口并清理。建议 main 管理 renderer 生命周期，在普通 reload 时撤销该 renderer 的所有订阅，同时保留会话及镜像。

### F06：Agent 右键粘贴没有经过普通终端的输入控制器

位置：[AgentTerminalDialog.tsx](../../src/renderer/components/agent/AgentTerminalDialog.tsx) 约 194–199 行。

普通终端通过 `TerminalInputController` 做多行/ESC/大文本确认、runtime 生命周期检查和 `term.paste()`。Agent 的右键菜单粘贴及右键直接粘贴却在读取剪贴板后直接调用 `writeIrisAgentTerminal(...)`。

已挂载真实 React 组件、模拟外部剪贴板与终端端口验证：

- 在 bracketed paste 已开启的端口上，粘贴 `first\nsecond\n`，实际向输入 API 直接发送原文，`term.paste()` 调用次数为 0。没有 bracketed paste 包装，也没有普通终端的确认链，程序可能把换行当作输入提交。
- 先发起剪贴板读取，再卸载面板，最后完成读取，仍实际调用输入 API 写入 `late input\n`。原 PTY 仍运行时会收到已经离开面板后的迟到输入。此子项为 P2 生命周期缺陷，不宣称已经写入另一个 session ID。

建议 Agent 复用同一输入控制器和绑定在创建时的 scope/runtime；不同粘贴入口需要具有相同的确认、包装和取消语义。本项是组件行为复现，不是系统剪贴板或真实 TUI 人工验收。

### F07：可续流状态还缺保存光标和 DEC 字符集

位置：[terminal-mirror.ts](../../src/main/terminal/terminal-mirror.ts) 的 `serialize`。

两个真实 xterm 往返用例：

| 前缀（之后取快照） | 后缀 | 预期 | 实际 |
| --- | --- | --- | --- |
| `\x1b[4;7H\x1b7\x1b[2;2Hstatus` | `\x1b8!` | 回到保存的第 4 行第 7 列写 `!` | 在左上角写 `!` |
| `\x1b(0lq` | `qk` | `┌──┐` | `┌─qk` |

源端的保存光标寄存器和字符集会影响之后的输出，快照却只保留目前可见字符与部分模式。建议与 F02/F03 一起定义完整的恢复契约，加入「快照恢复后继续输入」的回归矩阵。

### F08：OSC 取消符后面的提示符被缓存住

位置：[terminal-protocol.ts](../../src/main/terminal/terminal-protocol.ts) 约 38–46 行。当前预处理器只寻找 BEL/ST 终止符，不处理 CAN/SUB 等取消情形。

输入 `\x1b]0;unfinished\x18\x1b[2J\x1b[Hprompt> `，裸 xterm 正常显示 `prompt>`；Iris `TerminalProtocol.consume` 返回 **`display:''`**。之后没有 BEL/ST、累计长度未超过 4096 字符时，新的显示内容继续被扣住，可能表现为输入后没有响应。建议按 VT 的取消/终止规则处理流，或避免用不完整的独立扫描器阻断所有显示输出。

### F09：拖入路径没有按实际 shell 正确引用

位置：[shell-quoting.ts](../../src/shared/terminal/shell-quoting.ts) 第 2 行仅对含空白路径加双引号；[input-policy.ts](../../src/shared/terminal/input-policy.ts) 的危险字符识别；[input-controller.ts](../../src/renderer/terminal/input-controller.ts) 的 `dropPaths`。

真实 `pwsh.exe`/`cmd.exe` 复现：

1. `.iris/issue/O'Brien.md` 未触发危险确认，PowerShell 解析错误为 `TerminatorExpectedAtEndOfString`；交互输入可能进入等待补齐引号的续行状态。
2. `.iris/issue/%IRIS_AUDIT_PATH_VALUE%.md` 未触发危险确认。设置同名测试环境变量为 `expanded` 后，cmd 实际得到 `.iris/issue/expanded.md`，不再是原路径。
3. 含空格的 PowerShell 路径 `C:\tmp\$(Write-Output IRIS_PATH_EXECUTED)\file name.txt` 会执行括号内表达式。
4. cmd 路径 `C:\tmp\foo&echo.IRIS_PATH_EXECUTED&rem` 会执行额外的 echo。

后两项已有明确的「可能意外执行，仍要粘贴？」确认，**不描述为绕过告警**。但确认并没有把路径变成字面数据，且前两种合法文件名无提示就损坏。这与兼容性矩阵 T05 的要求不一致。建议按实际 shell 对路径做参数引用，并分别验证 PowerShell、cmd 和其他支持的 shell；本轮仅执行无副作用的输出与解析探针。

### F10：shutdown 已取待关闭会话快照后，仍允许创建新 PTY

位置：[terminal-session-manager.ts](../../src/main/terminal-session-manager.ts) 的 `shutdown`（约 516–521 行）与创建入口；[ipc.ts](../../src/main/ipc.ts) 的 `PROJECT_COMMAND_RUN`（约 580、584、601 行）。

`shutdown()` 只关闭调用当时的会话并永久缓存 Promise，创建入口没有 closing gate。工具栏命令在 scope 校验之后 await 读取设置，随后创建终端前没有再次验证生命周期。

两个独立受控测试已确认：

- 第一个 PTY 正在异步清理时创建第二个独立 PTY，完成 shutdown 并再调用 shutdown，第二个会话仍存活，其 kill 从未被调用。
- 调用真实注册的工具栏 IPC handler，在设置读取期间改变 scope，再完成读取，handler 仍成功创建旧 scope/generation 的会话。

主要风险是关闭窗口期间已发出的启动请求迟到，逃过清理。普通同页切项目有前端 CPU 读写锁串行化，不能宣称正常切项目每次都可触发；超时、reload 或直接 IPC 的情况需另行考虑。没有用真实 OS 孤儿进程作为本项证据。建议 manager 关闭时拒绝新的创建，并在异步 IPC 完成后重新校验 scope/closing。
