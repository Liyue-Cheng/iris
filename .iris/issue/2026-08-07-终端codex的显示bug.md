现在就是有一个非常显著的bug，就是codex长任务的时候，有的时候会有这种现象：屏幕中上半部分内容不滚动，只有下半部分内容滚动，然后这一轮全部输出完之后，终端的滚动条直接跑到最上面

不是稳定复现的问题，有的时候有，有的时候不一定有

## 调研结论（2026-08-08）

根因已经收敛到 Codex TUI 与 xterm.js 的终端协议兼容问题，不是普通 DOM 滚动、WebGL 字形贴图或 Iris 自动滚动逻辑。

Codex 0.146.1 每次绘制都包在 DEC 2026 同步输出块中，并用 DECSTBM 局部滚动区、反向索引和清屏序列维护“上方历史 + 下方活动 viewport”。本机版本的 `insert_history.rs` 仍在标准路径中发出 `CSI top;bottom r`，只对 Zellij 使用另一条安全路径。滚动区没有按预期复位或 xterm 的 viewport 状态与 buffer 状态不同步时，外观正是只有屏幕的一部分滚动。

Iris 使用 `@xterm/xterm 6.1.0-beta.256`。该版本支持 DEC 2026，并在同步块期间冻结 canvas 绘制和 DOM scrollbar 更新，结束后再一起提交。xterm 上游仍未关闭的 [#5801](https://github.com/xtermjs/xterm.js/issues/5801) 明确记录：Codex 等 CLI 在 DEC 2026 块内发出 `ED2` 清屏时，xterm 会立即改变 viewport/scrollback，导致流式重绘期间视口被拉动；相关 [#5770](https://github.com/xtermjs/xterm.js/pull/5770) 只把 DOM scrollbar 延迟到帧末，没有消除清屏对 buffer 的副作用。

Codex 上游仍未关闭的 [#14277](https://github.com/openai/codex/issues/14277) 也给出了同一组复现条件：Windows、VS Code 或自定义 Electron xterm.js 容器、长对话。其分析还指出 inline history 的 DECSTBM / reverse-index 路径会令 xterm 风格终端的全局 scrollback 丢失或陈旧。因此 `--no-alt-screen` 或 `tui.alternate_screen = "never"` 不是可靠修复；当前 Codex 源码仍保留这条路径。

“一轮结束后滚动条跑到最上面”是同一问题的另一面：Codex 的清屏/清 scrollback 序列改变了 buffer 的 `ybase/ydisp` 或总行数，xterm 在同步块结束时才把新的 canvas 与 scrollbar 一次提交，于是用户看到瞬间跳转。用当前 headless xterm 做最小实验也能观察到：默认 `scrollOnEraseInDisplay: false` 时，`DEC 2026 + ED2` 会覆盖当前 viewport 中的旧行；设为 `true` 后旧行进入 scrollback，`ybase/ydisp` 随内容一起前移，不再丢失。

### Iris 侧判断

* `TerminalView` 的 live 路径只是按原字节顺序调用 `term.write()`；main 进程的 8 ms 合批只拼接字节，没有改变控制序列顺序，不是主因。

* headless snapshot replay 只在终端挂载/切换时发生；不切换页面也能出现本 bug，因此 replay 不是触发源。但切换时 serializer 会连同 DECSTBM 状态重放，可能把已经错误的滚动区继续带到新实例，是放大器。

* `useConptyDll` 已启用，它能减少 Windows ConPTY 拆分同步帧造成的中间画面，但上游问题是平台无关的 xterm buffer 语义，不能解决清屏和局部滚动区问题。

* DOM 与 WebGL 渲染器共享同一个 xterm buffer/viewport 状态，所以切换为 DOM renderer 顶多用于排除绘制层，不能根治。

### 建议修复顺序

1. 最小兼容修复是在 renderer xterm 和 main 的 headless xterm 上同时设置 `scrollOnEraseInDisplay: true`。这是 xterm 维护者针对该问题给出的现成兼容选项，也与 macOS Terminal/iTerm2 的行为一致。两端必须同时设置，否则 live buffer 与 replay snapshot 会分叉。
2. 补一个协议级回归测试：预置多屏 scrollback，写入跨 chunk 的 `CSI ?2026h`、`ED2`、DECSTBM、内容和 `CSI ?2026l`，断言旧历史仍在、活动滚动区最终复位、renderer/headless 的 buffer 基准一致。
3. 若兼容选项仍不能消除局部滚动，可在 PTY 到两个 xterm 的共同入口做有状态过滤，仅忽略 DEC 2026 块内的 `ED2`。该方案已有下游先例，但必须跨 chunk 跟踪状态，且同时喂给 live 与 headless；风险和维护成本高于第一种。
4. 长期仍应跟进 xterm/Codex 上游。降级 xterm 5.x 或仅强制 `--no-alt-screen` 都不是可靠方案。

## 补充分析（2026-08-09）

新的高相关触发条件是：Codex 持续输出时，用户同时手动向上滚动。触发后，上半部分画面保持不动，下半部分仍被 Codex 的活动 viewport 刷新；流式内容看似越过刷新区，但在本轮结束并提交为历史后会重新出现，同时滚动条突然跳向顶部。

根本矛盾不是 Iris 丢失输出，而是两种终端模型不兼容：xterm 的用户滚动锁定假定输出主要追加在 buffer 底部；Codex inline TUI 则把终端当作可局部改写的画布，使用 DECSTBM 在已完成历史与活动 viewport 之间插入、移动和重绘内容。用户向上滚动后，xterm 固定 `ydisp`，Codex 仍在 `ybase` 附近修改局部区域，修改边界落入当前可见范围中间时，就会形成“上方冻结、下方刷新”的分裂画面。DEC 2026 又延迟 canvas 与 DOM scrollbar 的提交，使轮次结束后的恢复和跳转集中发生。

最小实验已经验证：在用户滚动锁定状态下写入 Codex 同形的 DECSTBM 历史插入序列，会保持可见区域上方旧行不变，只移动和重画插入点以下的行。另一个测试还发现，`scrollOnEraseInDisplay: true` 遇到尚未复位的局部滚动区时，会让 ED2 服从该滚动区，只清空局部区域。现有回归测试在 ED2 前先复位 DECSTBM，且只测试 headless mirror，因此没有覆盖这两个交叉条件。

### 候选方案及风险

Iris 侧较完整的规避方案是：用户离开终端底部查看历史时，可见 xterm 暂停应用 Codex 的 live 重绘，但 main 的 headless mirror 和 PTY 继续实时接收全部输出；用户回到底部后，从 mirror 恢复最新完整状态。这样暂停的是可见画面，不是 Codex 进程，也不会丢失输出。

该方案有明显产品和实现风险，暂不直接实施：轻微向上滚动也可能让用户感觉终端“停止输出”；需要可靠区分仍在底部、主动查看历史和滚轮误触；恢复时不能高速补播全部中间动画；还要处理 DEC 2026 控制序列跨 chunk、冻结发生在同步帧中间、缓存上限，以及 renderer 与 headless 的短暂状态分叉。仅过滤同步帧内 ED2 也不足以解决 DECSTBM 历史插入与用户滚动的冲突。
