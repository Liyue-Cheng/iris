现在有实现模型的思考吗？你调研看看

## 调研结论（2026-09-10）

**没有实现。** `@earendil-works/pi-ai` 0.84.1 这一层完整支持 thinking / reasoning，但 Iris 只在三处「认识」这个概念：事件类型枚举、请求 payload 审计白名单、模型目录里的一个布尔字段。真正跑起来时链路是断的——**请求不申请思考，流式的思考被丢掉，切片后的思考不进 Session，UI 也没有任何入口**。

| 环节 | 现状 | 关键位置 |
| --- | --- | --- |
| 请求 | 不传 `reasoning`，pi 端退化成「关闭」 | `pi-adapter.ts:535`、`pi-adapter.ts:605` |
| 传输 | `thinking_delta` 在 worker 被丢弃 | `agent-worker.ts:663`、`agent-worker.ts:848` |
| 持久化 | 只取 `type === 'text'` 的块 | `session-manager.ts:2807` |
| 卡片 | `agent-reply` 只有 `content: string` | `session-model.ts:619`、`types.ts:886` |
| 配置 | 没有 thinking level 字段或设置项 | `types.ts:667`、`provider-profiles.ts:177` |
| 展示 | 只有会话级「生成中」粗状态 | `IrisAgentView.tsx:1610` |

### 1. 请求侧：思考被显式关闭

- Agent 主循环调用 `streamSimple` 时只传了 `signal`（`src/main/agent/pi-adapter.ts:535`）。
- 压缩摘要的 `completeSimple` 同样只传 `fetch` / `signal`（`src/main/agent/pi-adapter.ts:605`）。
- pi-ai 在缺少 `reasoning` 选项时的行为是确定的：
  - Anthropic：直接 `thinkingEnabled: false`（`node_modules/@earendil-works/pi-ai/dist/api/anthropic-messages.js:616`）。Claude 的 extended thinking 一定不会开。
  - OpenAI Responses：`params.reasoning = { effort: model.thinkingLevelMap?.off ?? 'none' }`（`node_modules/@earendil-works/pi-ai/dist/api/openai-responses.js:243`），即显式请求「不推理」。
- 结论：当前模型不会因为 Iris 的请求而思考，也不会产生任何 thinking 事件。某些模型的「惯性推理」无法从这条链路观察到，但那不是 Iris 的功能。

### 2. 适配层认得出 thinking，但 worker 把它丢掉

- pi-adapter 的流循环把 `thinking_delta` 和文本增量一起包装成 `message_update` 发出（`src/main/agent/pi-adapter.ts:538`）。
- worker 只把 `text_delta` 转成 `assistant-text-delta`，其它 `message_update` 落到空分支（`src/main/agent-worker.ts:663`、`assistantTextDelta()` 在 `src/main/agent-worker.ts:848`）。
- 兜底路径也救不回来：`message_end` 的完整 assistant message 会作为 `provider-message` 上报，里面确实带 thinking block，但下一步就被丢弃。

### 3. 持久化与卡片：只取正文

- `providerMessageText()` 只拼接 `type === 'text'` 的块（`src/main/agent/session-manager.ts:2807`），所以 Turn 的 `assistant.content`、Reply Activity 的 `content` 都只有正文。
- `projectCards()` 产出的 `agent-reply` 卡片只有 `content: string`（`src/main/agent/session-model.ts:619`、`src/shared/types.ts:886`），没有承载思考的字段。
- 跨进程恢复用的 history 是 `text + toolCalls` 重建的（`src/main/agent/pi-adapter.ts:1106`），`providerSafeAssistantText()`（`src/main/agent/pi-adapter.ts:1078`）明确丢掉 thinking 与 signature。这在当前无害，但一旦打开 Anthropic extended thinking，这条重建路径必须按 provider 要求重做——`.iris/issue/2026-08-16-Iris-Agent-Stop与上下文恢复.md` 里已记录过「重放不完整的 reasoning 会造成 provider API 错误」。

### 4. 配置侧：没有任何 thinking 开关

- 模型目录里带了 `reasoning: boolean`（`src/shared/types.ts:639`，由 `src/main/agent/pi-adapter.ts:817` 从 pi 目录映射），但渲染端没有任何代码读它，是个未使用的字段。
- `IrisAgentConfiguredModel`（`src/shared/types.ts:667`）只有上下文窗口 / 输出上限 / 保留量 / 压缩阈值，没有 thinking level；`normalizeConfiguredModel()`（`src/main/agent/provider-profiles.ts:177`）也不会保留这类配置。
- 设置页的模型行只编辑 `contextWindowTokens` / `maxOutputTokens` / `reserveOutputTokens`（`src/renderer/components/settings/SettingsView.tsx:1270` 起），没有思考强度这一栏。
- 附带事实：请求 payload 审计的白名单里已经包含 `thinking` / `reasoning` 键（`src/main/agent/context-artifact.ts:6`）。所以一旦开始发送这些参数，context inspector 不需要改动就能看到它们——这对验证很有用。

### 5. 现在用户看到的「思考」是什么

- 只有会话级粗状态：`statusLabel()` 返回的「生成中」（`src/renderer/components/agent/IrisAgentView.tsx:1610`）和头像旁的三点动画（`src/renderer/components/agent/IrisAgentView.tsx:349` 起）。
- 回复卡片的「正在回复…」占位（`src/renderer/components/agent/IrisAgentView.tsx:1263`）只有在正文增量到达、卡片已建立之后才会出现；纯思考阶段没有任何独立表达。
- 这与既有设计取向一致：`.iris/misc/agent开发探讨.md` 与 `.iris/issue/2026-08-19-agent卡片设计.md` 都主张「内部 reasoning 不投影为回复或卡片，思考是模型的瞬时状态而非历史」。也就是说，**「显示实时思考状态」这条在 `2026-08-13-Iris-Agent产品设计与开发.md` 里被勾掉，实际交付的是会话级 running 指示，不是模型思考内容**。
- 该文档里还留着两条相关的未完成项：模型选择 + thinking level、对 thinking/tool call 图片/上下文窗口/usage 做显式 capability 降级。

### 如果要做，需要动哪些地方（草案，未开工）

建议分三层，按 A → B → C 推进，可以只做 A。

**A. 让模型真的思考（最小改动）**

1. `IrisAgentConfiguredModel` 增加 thinking level 字段（`off | minimal | low | medium | high | xhigh | max`），随模型持久化，并在设置页模型行暴露。
2. `createIrisPiSession` 与 `summarizeIrisAgentHistory` 增加 `reasoning` 入参，两处调用点改为 `{ signal, reasoning }`。
3. 能力门禁：`model.reasoning === false` 或 profile 不支持时不传该选项（pi 会静默忽略，但 UI 应当说明而不是假装生效）。
4. 注意语义差异：Anthropic 是「开关 + budget token」，OpenAI 是 effort 档位；`thinkingLevelMap` 目前只能来自 pi 内置目录，Iris 自己的模型配置无法覆盖它，若遇到不认某档位的兼容端点需要单独考虑。

**B. 把思考送出来（不改历史语义）**

1. worker 增加 `assistant-thinking-delta`（或给 `assistant-text-delta` 加 kind），沿用现有的 8ms / 批量合并策略。
2. 思考增量只作为「当前 intent 的实时状态」存在，不写入 Turn / Activity / journal，intent 结束即丢弃——这样默认历史仍与现有设计一致。
3. UI 在回复卡片内加一个可折叠的实时思考区，默认折叠，或只显示「正在思考」与耗时。

**C. 可选：思考的可观测性**

1. provider 已经会带回 reasoning token 数（`node_modules/@earendil-works/pi-ai/dist/api/anthropic-messages.js:551`，`Usage.reasoning`），可以接入用量指示器。
2. 是否提供按需「查看本次完整思考」（诊断视图而不是默认历史）——这会与既有设计决定冲突，需要先定夺。

## 方案审核（2026-09-10）

### 审核结论

前面的**现状调研基本可信**：请求没有启用 reasoning，thinking 增量没有进入主进程语义，持久化和 UI 也没有承载它。关键代码位置与 `pi-ai` 0.84.1 的行为能够互相印证。

但后面的 A/B/C 草案**不能原样作为实施方案**。它适合说明功能表面积，不足以保证 Iris 现有的 Session、工具循环、进程恢复和 provider-neutral 约束。尤其是所谓“只做 A”只能成为存活 Worker 内的演示，不能作为可发布功能：一旦 Worker 重建、应用重启或切换模型，当前 canonical history 无法恢复 provider 要求的 reasoning continuation 数据。

建议把结论改为：

| 原分层 | 审核判断 | 修订 |
| --- | --- | --- |
| A. 让模型思考 | 方向正确，但不能单独发布 | 先补 A0“能力与重放语义”，再开启请求 |
| B. 把思考送出来 | 全文传输不是首版必需，且“实时但不落盘”被低估 | 首版只传瞬时 phase，不传 thinking 文本 |
| C. 可观测性 | reasoning usage 值得做 | 放在请求正确性之后，不与全文展示绑定 |

**推荐首版范围：A0 + A1 + B-lite。** 默认关闭；只对能力已知的模型开放；显示“思考中”和耗时，不显示 thinking 全文；允许在主进程私有持久化 provider continuation，但不投影为回复卡片或用户可见历史。

### 原方案需要纠正的事实

1. `SimpleStreamOptions.reasoning` 的类型只有 `minimal | low | medium | high | xhigh | max`，**没有 `off`**（`node_modules/@earendil-works/pi-ai/dist/types.d.ts:23`、`:211`）。关闭的正确表达是“不传 `reasoning`”，Iris 自己的配置类型才需要包含 `off`。
2. 只给 `IrisAgentConfiguredModel` 增加 level 不足以启用模型。`profileModelsConfig()` 对 pi 内置目录中找不到的模型明确写入 `reasoning: false`（`src/main/agent/provider-profiles.ts:209`）。手工添加的模型和大多数兼容端点模型因此仍会被 pi 当成不支持，设置页即使显示档位也不会生效。
3. 原方案遗漏了第三个模型调用：终端监督在 `src/main/agent-worker.ts:443` 也调用 `completeSimple()`。它是否使用 reasoning 必须明确，不能由“按模型配置”意外继承。
4. 设置页当前实际只编辑上下文窗口和输出保留量（`SettingsView.tsx:1247` 起）；`maxOutputTokens`、`keepRecentTokens`、`compactTrigger` 虽然存在于数据结构中，并没有都暴露为可编辑列。原调研对 UI 现状描述不准确。
5. 档位不能固定展示七档。pi 的 `getSupportedThinkingLevels()` 只有在 `thinkingLevelMap` 明确声明时才开放 `xhigh` / `max`，不支持的档位会被 `clampThinkingLevel()` 静默夹到别的档位（`node_modules/@earendil-works/pi-ai/dist/models.js:548`）。Iris 必须显示实际支持和实际生效的档位，不能让 UI 声称使用了 `max`，请求却降成 `high`。
6. Anthropic 的 budget thinking 会和正文共享输出上限。pi 默认 `medium=8192`、`high=16384`，并且至少只给答案留 1024 token（`node_modules/@earendil-works/pi-ai/dist/api/simple-options.js:41`）。Iris 当前常见的 `maxOutputTokens` 正是 16384；直接开放 `high` 可能让正文只剩约 1K token。思考档位、provider 输出上限和 Iris 的 `reserveOutputTokens` 必须一起校验。

### 不能绕过的可靠性前置项

#### 1. Provider continuation 与“展示思考”是两件事

当前 Turn 只保存 `content + toolCalls`（`src/main/agent/session-model.ts:115`），历史重建又把 assistant 伪装成 `api: openai-responses / provider: iris-history / model: unknown`（`src/main/agent/pi-adapter.ts:1106`）。这会丢失：

- Anthropic thinking block、signature 与 redacted payload；
- OpenAI Responses reasoning item 的 `encrypted_content`；
- text signature、tool call thought signature 及其它 provider 重放元数据。

这不只是 Anthropic 问题。`pi-ai` 的 OpenAI Responses 路径在 `store: false` 下主动请求 `reasoning.encrypted_content`，并把完整 reasoning item 序列化进 `thinkingSignature` 供后续请求重放（`openai-responses.js:231`、`openai-responses-shared.js:137`、`:396`）。Iris 如果开启 reasoning 后仍只保存正文和工具调用，跨进程工具循环与后续请求都可能失去合法 continuation。

因此必须把两个产品概念拆开：

- **可见历史**：继续只保存/展示正文，不把 reasoning 投影成 Agent 回复；
- **私有 provider replay 数据**：为可靠恢复保存完成消息所需的 thinking/signature/encrypted item，但不发送到 Renderer，不进入卡片，不参与全文搜索。

如果产品决定“任何形式的 thinking 都不能落盘”，那么首版就不能承诺 Anthropic extended thinking 的跨进程恢复；必须明确降级为 Worker 存活期间有效，并在重启时中止未完成工具链。不能一边不保存 continuation，一边宣称 Session 可可靠恢复。

#### 2. 重放必须按 provider/model 边界降级

完整 continuation 只应在**同 API、同 provider、同 model**下重放。模型切换、provider 切换、消息中断、tool result 不完整时，沿用当前安全原则，只投影已显示正文并丢弃 provider 私有块。不能把 Anthropic signature 或 OpenAI encrypted reasoning 带到另一个模型。

#### 3. “实时但不落盘”需要独立瞬时通道

当前 `assistant-text-delta` 经 `commitAndEmit()` 写入 Session journal（`src/main/agent/session-manager.ts:2244`），并不存在一个天然的“只更新 UI、不提交 aggregate”的路径。原 B 方案若新增 thinking delta 后照搬正文处理，会把思考写进历史；若什么都不存，Renderer 又收不到卡片级状态。

首版更合适的是新增瞬时 phase 事件，例如 `thinking | answering | tool`：主进程只维护内存态并广播投影，完成、停止、崩溃时清除，不提交 journal。UI 据此显示“思考中 · 3.2s”，不传输 thinking 文本。

### 修订后的可执行方案

#### A0. 能力模型与安全重放（请求开启前必须完成）

1. 增加 Iris 自己的 `IrisAgentReasoningLevel = off | minimal | low | medium | high | xhigh | max`，存储默认值为 `off`，旧配置缺字段时迁移为 `off`，避免升级后成本和行为突变。
2. 模型目录对 Renderer 输出“支持的档位 + 能力来源”，不要只输出一个 `reasoning: boolean`。支持档位应由 pi 模型元数据计算；未知手工模型首版保持“不支持/未知”，不能猜测兼容端点接受哪种参数。
3. 为 `AgentTurn.assistant` 增加不向 Renderer 投影的 provider replay 数据，保存完成 assistant message 中重放所需的 JSON-safe provider 内容和原始 `api/provider/model` 身份。设置尺寸上限，禁止图片字节和请求密钥进入该字段。
4. history 投影增加两条路径：同 provider/model 使用 replay 数据；跨模型、aborted、结构不完整时使用现有 provider-safe text 降级。压缩掉的旧 Turn 可以随摘要边界丢弃 replay 数据，保留区内不能丢。
5. 为 Anthropic signature、redacted thinking、OpenAI encrypted reasoning、工具调用后重启、跨模型切换和 aborted message 增加 provider-bound payload 测试。测试必须断言最终发出的 payload，而不只断言 Pi Session 内部消息。

#### A1. 开启主 Agent 请求

1. 在每次执行开始时解析一次“请求档位”和“实际生效档位”，通过 `AgentWorkerExecutionRuntime` 显式传给 Worker；不要让 Worker 隐式读取一个可能在执行中变化的设置文件。
2. 只在 level 非 `off` 且模型能力已确认时向 `streamSimple()` 传 `reasoning`。不支持时明确降级并给出原因，不能依赖 pi 静默忽略或夹档。
3. 首版只给主 Agent 工具循环启用 reasoning。压缩摘要和终端监督继续不传 reasoning：它们是内部、短输出、成本敏感调用，不应该意外继承用户为主回答选择的高档位。
4. 设置页首版采用“按模型默认档位”；会话内临时切换以后再做。档位选择旁同时显示总输出上限及预估答案余量，budget thinking 下不足时禁用高档位或给出明确警告。
5. Context Inspector 记录“配置档位、实际档位、降级原因”，并继续用已有 payload 审计验证真正发给 provider 的 `reasoning` / `thinking` 参数。

#### B-lite. 只展示阶段与耗时

1. Worker 识别 `thinking_start/delta/end`，只上报 phase 转换，不上报 thinking 正文。
2. 主进程使用独立瞬时状态，不写 Turn、Activity 或 journal；停止、错误、Worker 重建和 intent 完成时必须清除。
3. 回复区在正文出现前显示“思考中”，正文开始后切成“生成中”；完成后不保留思考卡片。该行为与既有“不投影 reasoning”设计一致。

#### C. 后续可观测性

接入 `usage.reasoning` 是合理的，但需要明确它通常已经包含在 output token 中，不能重复计费或重复累加。首版可以只在 Context Inspector 显示；是否进入日常 UI 另行决定。不要提供“完整思考”入口：不同 provider 返回的可能是摘要、加密块或兼容端点自定义字段，把它统一标成模型真实思维既不准确，也与既有卡片设计冲突。

### 推荐决策

- **启用范围**：做，但不是原方案的“只做 A”；做 A0 + A1 + B-lite。
- **配置粒度**：首版按模型默认，默认 `off`；以后再增加会话覆盖。
- **实时可见性**：只显示状态与耗时，不显示全文。
- **历史语义**：用户可见历史不保存 reasoning；为同模型恢复允许私有保存 provider continuation。
- **内部调用**：压缩摘要和终端监督首版保持 reasoning 关闭。
- **兼容端点**：能力未知时不开放；不要通过模型名或字符串启发式猜测。

- [ ] 是否同意首版默认关闭，且只对 pi 目录中能力已确认的模型开放
- [ ] 是否同意首版只显示“思考中 + 耗时”，不展示 thinking 全文

## 产品范围补充：左上角 Logo 必须表达思考/生成阶段（2026-09-10）

用户补充要求：这不只是 provider reasoning 参数功能。Agent 面板左上角当前会转动的 Logo 和状态文字也必须区分“思考中”与“生成中”，作为用户判断 Agent 当前在做什么的主要入口。因此 B-lite 不再是可有可无的附属展示，而是首版完整链路的一部分。

### 当前实现为什么不能满足

`IrisAgentView` 只根据 `isSessionRunning(session)` 得到一个布尔值（`src/renderer/components/agent/IrisAgentView.tsx:122`）：

- Logo 只有 `data-running`，所有忙碌状态共用同一个呼吸和绕圈动画（`:340`；`src/renderer/styles/global.css:157`）；
- 状态文字只读取 `session.state`，其中 `running` 固定显示“生成中”（`IrisAgentView.tsx:1600`）；
- `starting`、provider 请求等待、thinking、正文生成以及 tool call 参数生成之间没有细分；
- 纯 thinking 阶段还没有 Reply 卡片，所以只改卡片占位文字无法解决左上角反馈。

### 状态模型：生命周期与模型输出阶段分开

不建议把现有 `IrisAgentRuntimeState.running` 直接拆成 `thinking` / `generating`。现有 state 同时承担忙碌判断、模型选择禁用、关闭确认、工具执行、重试和停止语义；把 provider 阶段塞进同一个枚举会导致所有调用方都要理解模型流事件，并容易覆盖 `waiting-tool` / `retry-wait` 等优先级更高的状态。

建议保留两层正交状态：

| 层 | 示例 | 用途 |
| --- | --- | --- |
| Session lifecycle | `starting / running / waiting-tool / retry-wait / stopping / idle / paused` | 调度、权限、按钮和会话状态机 |
| Live provider phase | `requesting / thinking / generating` | Logo 动画、左上角文字和实时耗时 |

Live phase 只在 lifecycle 为 `running` 时生效。其它 lifecycle 状态优先显示自己的明确文案，例如“工具执行中”“等待重试”“停止中”，不能被旧的 `thinking` phase 覆盖。

### 建议的阶段转换

1. 用户发送后：`starting`，Logo 显示“启动中”。
2. Worker 发起每一次 provider 请求时：lifecycle=`running`、phase=`requesting`，显示“请求中”或“准备中”。工具循环中的第二、第三次 provider 调用也必须重新进入该阶段。
3. 收到 `thinking_start` 或第一个 `thinking_delta`：phase=`thinking`，立即显示“思考中”，从此刻计算本段思考耗时。
4. 收到 `text_start` / `text_delta`：phase=`generating`，显示“生成中”。
5. 收到 `toolcall_start` / `toolcall_delta`：模型仍在产生输出，归入 `generating`；真正开始执行工具后由 lifecycle=`waiting-tool` 覆盖为“工具执行中”。
6. 工具结果返回、准备下一次模型调用时：清掉上一段 phase，重新进入 `requesting`，不能继续显示上一次的“生成中”。
7. retry、stop、error、intent 完成、Worker 退出、Session 关闭或项目切换：立即清除 live phase。

必须遵循“有事件才显示”的原则：模型配置了 reasoning，但 provider 没有发 thinking 事件时，不能凭配置猜测它正在思考；应从 `requesting` 直接进入 `generating`。兼容端点在内部产生隐藏 reasoning、却不提供流事件时，Iris 无法可靠区分。

### 传输与存储设计

Live phase 建议走独立瞬时链路，而不是写进 Turn、Activity 或 canonical Session journal：

1. Worker 增加 `assistant-phase` 事件，携带 `sessionId / intentId / workerEpoch / providerMessageId / phase / startedAt`。
2. `pi-adapter` 不能继续只转发 `thinking_delta` 和 `text_delta`；需要把 `thinking_start`、`text_start`、`toolcall_start` 或等价的首次 delta 转成稳定阶段边界，并在每次 provider 请求开始时发出 `requesting`。
3. 主进程维护按 Session 隔离的 live phase map，并通过独立 IPC 事件（例如 `IRIS_AGENT_PHASE_CHANGED`）广播，不增加 canonical revision，也不调用 `store.commit()`。
4. Renderer store 维护瞬时 phase；必须用 `intentId + workerEpoch` 拒绝迟到事件。收到 Session 非 running 状态、Session destroyed 或项目 generation 变化时主动清理。
5. 不应把 phase 硬塞进现有 `IRIS_AGENT_SESSION_CHANGED` 且复用同一 revision。当前 Renderer 投影依赖严格递增 canonical revision，同 revision 的瞬时更新会被当成陈旧数据，伪造 revision 又会破坏状态一致性。

这样可以同时满足：Logo 能实时变化；thinking 文本不进入 Renderer；阶段不污染历史；窗口刷新或应用重启后不会恢复一个已经过期的“思考中”。

### Logo 与文字表现

左上角是主状态面，状态文字必须优先于仅靠动画辨识：

- `requesting`：显示“请求中”，可使用现有轻量呼吸效果；
- `thinking`：显示“思考中 · 3.2s”，保留环绕轨迹，节奏偏慢，表达持续计算；
- `generating`：显示“生成中”，可使用较快的脉冲或现有三点动画，表达正文正在到达；
- `waiting-tool / retry-wait / stopping`：沿用“工具执行中 / 等待重试 / 停止中”，使用 lifecycle 对应表现。

Logo 容器可从单一 `data-running` 扩展为 `data-phase`，但不要仅靠颜色区分；文字是无障碍和低动效模式下的权威表达。现有 `prefers-reduced-motion` 规则必须覆盖新增动画，关闭动画后状态文字仍应完整可用。

首版不必在纯 thinking 阶段创建一张空的 Reply 卡片。那会迫使主进程建立一个尚无正文、可能最终只有 tool call 的持久化回复对象。左上角 Logo 和文字应承担正文到达前的即时反馈；Reply 卡片在正文首次出现后再按现有语义建立。

### 对前述推荐范围的修订

推荐首版仍是 `A0 + A1 + B-lite`，但 B-lite 的验收范围明确扩大为：

- provider thinking 事件能够驱动 live phase；
- 左上角 Logo、状态文字和计时从“请求中”切到“思考中”，再切到“生成中”；
- 工具执行、重试和停止状态具有更高显示优先级；
- 多轮工具循环每次 provider 调用都会重置阶段；
- phase 不写入对话历史，不创建空回复卡片，不在重启后残留。

### 新增验收项

- [ ] 左上角 Logo 和状态文字可靠区分“请求中 / 思考中 / 生成中”
- [ ] reasoning 关闭或 provider 不发送 thinking 事件时，不出现虚假的“思考中”
- [ ] thinking 先于正文到达时，无需 Reply 卡片也能立即显示状态与耗时
- [ ] thinking → text → tool execution → 下一次 provider 请求的阶段顺序正确
- [ ] retry、stop、error、Worker 重建、Session 关闭和项目切换都会清除旧 phase
- [ ] 迟到的旧 intent / 旧 worker phase 事件不会覆盖当前 Logo 状态
- [ ] `prefers-reduced-motion` 下新增动画停止，但状态文字仍准确

## 实施结果（2026-09-11）

已按首版 `A0 + A1 + B-lite` 完成一轮实现，重点覆盖“推理请求、同模型连续性、实时阶段、左上角 Logo/文字、设置页配置”这条完整链路：

- `IrisAgentReasoningLevel` 支持 `off/minimal/low/medium/high/xhigh/max`；旧配置缺少该字段时归一化为 `off`。
- 模型目录向设置页提供 `supportedReasoningLevels` 与 `reasoningMode`；未知/手工模型不声明推理能力，不会因为用户配置而强行发送 reasoning。
- 主 Agent 请求才会根据有效配置传 `reasoning`；压缩摘要和终端监督继续保持 reasoning 关闭。
- 对已完成 assistant provider message 保存受限大小的 JSON-safe replay；恢复时仅在 `api/provider/model` 三者完全一致时重放，跨模型/供应商自动退回可见文本与工具调用安全表示；失败和中止消息不保存 replay。
- provider context artifact 记录 configured/effective reasoning 及降级原因，但不记录敏感凭据。
- Worker 新增 `assistant-phase`，每次 provider 请求从 `requesting` 开始，依据真实 `thinking_start/delta`、`text_start/delta`、`toolcall_start/delta` 切换到 `thinking/generating`；阶段不写入 Session revision 或对话历史。
- Main 通过独立 `IRIS_AGENT_PHASE_CHANGED` IPC 广播瞬时阶段，按 `intentId + workerEpoch` 拒绝迟到事件，并在完成、暂停、重试、Worker 退出、Session 关闭、项目切换和 shutdown 时清理。
- 左上角 Logo 使用 `data-phase` 区分请求/思考/生成动画；“思考中”显示分段耗时；无 thinking 事件时不会凭配置伪造“思考中”；纯思考阶段不会创建空 Reply 卡片。
- 设置页新增最大输出与思考强度选择，预算型思考显示预计回答 headroom，并对只剩最小回答空间的级别禁用/警示；手工模型默认关闭推理。
