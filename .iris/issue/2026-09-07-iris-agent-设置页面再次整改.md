### 当前页面结构

1. 设置壳层是固定 14rem 左侧分类导航 + 右侧滚动内容；右侧使用 `px-10 py-10`，没有内容最大宽度或窄屏断点。
2. Iris Agent 页依次放置：启用开关、添加供应商方案、已配置方案。
3. 添加方案使用通用双列 `SettingRow`，把模板、方案名、Base URL、API Key 拆成四行；“添加”按钮塞在 API Key 行末尾。
4. 每个已配置方案内部又包含：方案身份、更新凭据、模型目录标题、模型工具栏、模型表格、保存 footer。
5. 模型表格把模型 ID、上下文窗口、输出预留和删除操作压在一行；当前工作树还把模型 ID / 上下文窗口改成了带候选菜单的输入，原有上下文预设下拉被移除。

### 主要问题

#### A. 信息架构混乱

- “启用 Iris Agent”是全局开关，“添加方案”是创建流程，“已配置方案”是资源管理，三者被连续放入同一条普通设置流，没有明确的页面级层次和任务边界。
- 供应商模板、用户方案、运行时 provider 三个概念没有在 UI 中区分；当前页面基本只消费 `profiles`，`providers` 状态没有形成可见的认证/能力说明。
- 每个方案同时承担凭据维护和模型目录维护，但没有“方案概览 → 凭据 → 模型”层级，用户难以判断当前正在编辑什么。

#### B. 对齐和密度不一致

- 通用 `SettingRow` 的固定 12.5rem 标签列不适合 Base URL、API Key 等长控件；新增按钮、显隐按钮和输入框在 API Key 行里挤成一条，视觉重心偏右。
- 方案身份是无边框文本块，凭据输入是 `max-w-xl` 横排，模型目录又变成另一套全宽表格；同一方案内出现三种不同的对齐基线。
- 方案之间主要依赖 `py-8` 留白，没有稳定的分隔线、背景层或标题锚点；多方案时容易看成一整块连续内容。
- “模型目录”工具栏左侧获取、右侧手工添加，依赖空白 flex 占位推动；在不同宽度下按钮和输入会跳动。
- API Key、模型 ID、Base URL 混用中文标签、英文术语和不同按钮尺寸，文案层级不统一。

#### C. 响应式与可用性风险

- 模型表格使用 `16rem` 和 `12rem` 的最小列宽，再叠加间距与删除列；在设置窗口较窄时会横向溢出或迫使模型列极度压缩。
- 左侧导航固定宽度且不会折叠；右侧内容没有窄屏布局，双列 `SettingRow` 在小窗口中会让标签和控件同时变窄。
- 所有方案共享一个 `busy` 状态；任一方案获取模型、保存模型或更新凭据时，其他方案的操作也被整体禁用。
- 错误只显示在设置页顶栏，并以单行截断；模型发现可能返回多条 provider 错误，用户无法在具体方案处定位失败原因。
- 已配置凭据只通过 placeholder 表示“已配置”，缺少稳定的状态徽标；空状态也只是普通灰色文字，没有明确的下一步 CTA。

#### D. 数据与编辑模型不匹配

- `IrisAgentConfiguredModel` 包含 `displayName`、`maxOutputTokens`、`keepRecentTokens`、`compactTrigger`、`enabled`、来源和校验信息，但当前界面只编辑模型 ID、上下文窗口、输出预留；用户看不到也无法修正其余会影响运行时的字段。
- 当前工作树把模型 ID 和上下文窗口改为 `InputWithSuggestions`，但模型 ID 本质上是自由文本、上下文窗口又是数值；候选菜单与数字输入组合增加了控件复杂度，同时移除了已有的上下文预设入口，交互语义不再一致。
- 模型行直接用数组 index 拼 key；编辑、删除和刷新同时发生时，行身份稳定性较弱，后续重设计应避免依赖视觉行序表达模型身份。

### 重设计方向（本轮只完成调研，不改代码）

目标是把该页从“通用设置表单”改成“Agent 供应商工作台”，保留现有 IPC、校验和持久化语义。

1. 页面壳层：保留左侧分类，但为右侧内容设置合理最大宽度；在窄窗口切换为顶部分类滚动条或可折叠导航。Iris Agent 页使用更明确的页面标题、说明和状态摘要。
2. 顶部区域：将 Iris Agent 开关独立成一个简洁的能力开关区；在其下显示“已配置方案数量 / 可用模型数量 / 最近错误”等摘要，而不是与创建表单连续堆叠。
3. 添加流程：改为独立的“添加供应商方案”面板。模板先以选择器/分段卡片确定协议，再以两列或分组字段填写方案名、Base URL、API Key；提交按钮放在面板 footer，避免塞进 API Key 行。
4. 方案列表：每个方案使用稳定的容器（轻背景或单层边框）承载身份、模板、Base URL、凭据状态和危险操作；多个方案之间用明确间距和分隔。
5. 凭据区：将 API Key 更新作为方案内独立操作，显示“已配置 / 未配置”状态，显隐按钮、输入和更新按钮共享统一高度；错误就近显示在该方案。
6. 模型区：改成可折叠的“模型目录”子区。工具栏统一为“从供应商获取 + 手工添加”；模型行在桌面端使用表格，在窄屏自动堆叠为字段组。保留并重新放置上下文窗口预设，不用候选下拉替代自由编辑。
7. 编辑范围：明确哪些字段是可编辑配置，至少补齐显示名称、上下文窗口、最大输出/输出预留、启用状态；来源、最近验证和错误作为只读元信息，避免数据结构与 UI 长期不一致。
8. 状态与操作：将 `busy` 拆成按 profile/model 操作的局部状态；保存、发现、更新凭据和删除操作分别反馈，不阻塞其他方案。
9. 视觉规范：统一控件高度、圆角、按钮尺寸和术语；减少无意义边框，但为方案容器、模型表头和状态徽标保留清晰层级；中英文术语按现有 i18n 统一。
