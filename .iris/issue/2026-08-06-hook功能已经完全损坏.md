## 2026-08-06 全链路清查

### 结论

当前不是一个单点 bug，而是两项确定性故障叠加一组架构性盲区：

1. Claude Code 的文档 hook 会成功执行，但输出被 Claude 截断。当前脚本把
   `<iris-software>` 放在最前面，仅这一段就约 5.1 KB；Claude Code 2.1.170
   实测只把超长 hook 输出的前约 2 KB 放进上下文，完整 stdout 另存临时文件。
   因而后面的 `<iris-project>`、`<iris-user>`、`<iris-focus>` 都没有送达模型。
   这从模型视角等同于注入完全失效。
2. 项目根和子工作区的 hub 会话当前必然没有动态注入。UI 传入的
   `workspacePath` 只用于会话分组；主进程在 `docPath === null` 时明确删除
   `FOCUS_DOC`，脚本又在没有 `FOCUS_DOC` 时立即零输出。Codex 显示一下
   `SessionStart hook (completed)` 后消失，正是“hook 执行成功但输出为空”的
   表现，不是随机丢包。
3. Codex 的文档会话在当前机器、当前配置下工作正常。会话记录能看到完整 Iris
   hook 上下文；用户级 hook 也已有信任记录。此前以 `[` 开头导致 Codex 把纯文本
   误判成 JSON 的旧问题已经修复，不是本轮故障。
4. 设置页的“最新 / 已配置”只是静态文件检查，不是运行时健康状态。它只能证明
   脚本字节与内置模板一致、JSON 中存在相同命令，不能证明 CLI 执行了命令，更
   不能证明 stdout 最终进入了模型上下文。
5. 当前 76 项测试全部通过，但 `agent-injection.ts`、会话 spawn 环境和任何真实
   CLI hook 交付都没有测试覆盖。因此全绿与核心功能失效可以同时成立。

### 当前架构

运行链路如下：

```text
文档/工作区的“用 X 打开”
  -> renderer/session-actions.ts
  -> front-cpu 指令 session.open
  -> IPC session:open
  -> SessionManager.createSession()
  -> 复制 Electron 进程环境并启动 node-pty
       文档会话: env.FOCUS_DOC = 文档相对路径
       hub 会话: delete env.FOCUS_DOC
       cwd: 始终为项目根
  -> pwsh/powershell 以 -Command 启动 claude/codex
  -> CLI 读取自己的用户级 hook 配置
       Claude: ~/.claude/settings.json
       Codex:  ~/.codex/hooks.json，并另有信任审核
  -> SessionStart 调用 ~/.iris/focus-context.ps1
  -> 脚本以当前 cwd 为项目根，读取 FOCUS_DOC
  -> 依次向 stdout 写 software / project / user / focus 四层
  -> 各 CLI 自己决定如何把 stdout 转成模型上下文
```

这条运行链路旁边还有一条静态兜底链：Iris 在项目入口文件中维护
`<iris-software>`；Claude/Codex 会自行读取 `CLAUDE.md` / `AGENTS.md`。所以动态
hook 失效时，模型仍可能看到软件层，容易造成“好像注入了一部分”的错觉，但项目
层、机器层和聚焦文档并没有因此送达。

安装和检测是另一条链路：

```text
设置页 Agents
  -> injectionState() 读取脚本和五家 CLI 的 JSON
  -> 用户确认后 installFocusScript() / installHook()
  -> 写 ~/.iris/focus-context.ps1
  -> 合并 CLI 用户配置并生成 .bak
```

`AgentConfig.injection = hook` 目前只是 UI 信息，不参与 spawn，也不决定是否安装、
执行或验证 hook。五家 CLI 共用同一个 PowerShell 脚本和同一种嵌套 JSON 形状，
没有 vendor 级输出适配。

### 架构问题

#### P0：没有按 CLI 定义交付契约

当前把“同一段纯文本 stdout”同时当作 Claude、Codex、Gemini、Qwen、Cursor 的
适配器。代码只适配了配置文件路径和 hook key，没有适配各家输出格式、长度上限、
信任模型和错误呈现。Claude 的 2 KB 截断已经证明这个抽象不成立。

#### P0：hub 会话上下文在数据模型中断路

`workspacePath` 从 UI 一直传到 `SessionManager`，但只写入 `SessionInfo` 供 UI
分组，未进入子进程环境。前置 issue 提出的 `IRIS_WORKSPACE_PATH` 仍只是方案，代码
中不存在。当前注释和 UI 甚至明确把 hub 定义为“无聚焦兜底”，与用户现在要求的
根目录三层注入直接冲突。

#### P1：健康检查停在配置文件层

`configured` 的判据只是 handler 类型和 command 字符串相等；Codex 是否信任、
PowerShell 是否执行、退出码、输出字节数、CLI 是否截断、模型是否收到都不可见。
因此 UI 会对 Claude 当前的确定性失败显示“已配置”。

#### P1：输出预算设计失真

只对 focus 单段设 32 KiB 上限，总 payload 没有上限，也没有把最重要的焦点元数据
放在截断前。software 本来已由 CLI 的入口文件静态加载，却又在 hook 中完整重复，
既浪费上下文，又把真正的动态内容挤出 Claude 的可见范围。

#### P1：核心路径零测试

没有测试断言文档会话设置 `FOCUS_DOC`、hub 会话携带 workspace 元数据、脚本四种
输入组合、配置合并、PowerShell 实际输出、vendor 输出预算或 Claude/Codex 端到端
送达。现有测试只间接覆盖入口文件的软件块维护。

#### P2：全局脚本存在版本和归属风险

所有 Iris 版本和所有项目共用 `~/.iris/focus-context.ps1`，脚本只在设置页手工
安装或更新，不随启动自动保证当前。hook 命令路径不变时，CLI 配置仍会显示
configured；不同 Iris 版本最后一次写入者决定全机行为，也没有版本握手。

脚本还只用通用名称 `FOCUS_DOC` 作为触发凭据，并从当前 cwd 推断项目根，没有
独立的 Iris 会话标记或显式 root。外部进程若碰巧继承/设置同名变量也会触发全局
hook；cwd 或路径不符合预期时没有结构化诊断。

### Claude Code hook 输出上限调研（2026-08-06）

根据 Claude Code 官方文档（https://code.claude.com/docs/en/hooks ）确认：

1. **硬上限 10,000 字符**。Hook output strings — 包括 `additionalContext`、
   `systemMessage` 和 plain stdout — 统一受此限制。超出后完整内容另存文件，
   只有前约 2KB 预览和文件路径进入模型上下文。
2. **结构化 JSON 不能绕过上限**。`hookSpecificOutput.additionalContext` 受同
   一个 10,000 字符限制，换 JSON 输出格式不提升容量。
3. **没有文件引用注入机制**。Hook 无法通过返回路径让 Claude Code 自动读取文
   件内容；要么内联在 stdout/additionalContext 里（受上限），要么靠模型自己
   用 Read 工具读盘。
4. **当前脚本输出约 20,057 字符**（software ~5.1KB + project ~1.1KB + focus
   ~0.8KB + 信封文本），超标一倍。其中 `<iris-software>` 已由 CLAUDE.md /
   AGENTS.md 静态加载，在 hook 中完整重复是纯浪费，把真正的动态内容挤出了
   可见范围。
5. **大 issue 问题**。即使去掉 software 层，当聚焦文档本身几十 KB 时仍会超
   限。10,000 字符是不可配置的硬上限，无法通过任何设置提升。

#### 推荐方案

将 hook 从"尽量内联所有内容"改为"轻量指针 + 模型自行读取"：

- **去掉 software 层输出**：CLAUDE.md 已静态加载，hook 不必重复。
- **保留 project / user conventions 内联**：通常 1–2KB，在预算内。
- **focus 文档只输出路径指针**，不内联内容。依赖 Iris 协议已有规则
  "If `$FOCUS_DOC` is set, read it first" 让模型第一个动作 Read 聚焦文档。
- hook 总输出稳定在 2–3KB，永远不触发截断。
- 代价：模型多一轮 Read 调用（几百毫秒），用户基本无感。

此方案尚未实施，待用户确认 Claude Code 在实际会话中是否能可靠地记得读取
`$FOCUS_DOC` 指向的文件后再决策。

### 整改方向

应把“上下文内容模型”和“CLI 交付适配器”拆开。主进程先产生明确的会话元数据：
Iris 会话标记、绝对项目根、workspace 相对路径、可选 focus 文档；各 vendor hook
再按自己的格式和预算渲染，而不是共享一份无上限 stdout。

Claude 需要先用真实 CLI 探针确认普通 stdout 与结构化
`hookSpecificOutput.additionalContext` 的实际上限，再决定是紧凑内联、优先 focus、
还是明确降级为让模型读取已知文件。不能继续假定 32 KiB 能直接内联。Codex 可保留
已验证的纯文本首字符约束，但也要有总预算和端到端测试。

hub 会话应使用独立的 `IRIS_WORKSPACE_PATH`，而不是伪造 `FOCUS_DOC`；项目根用
`.iris`，子工作区用实际相对路径。脚本在只有 workspace 时输出 software/project/
user 和 workspace 元数据，不输出 focus。普通非 Iris 终端则由独立会话标记保证零
输出。

设置页应把“配置状态”和“最近运行状态”分开：前者说明文件是否正确，后者至少记录
脚本最近执行时间、目标 vendor、输入模式、输出字节数和退出结果。最终健康度仍需
真实 CLI smoke test，不能由配置字符串推断。
