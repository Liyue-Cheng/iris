现在iris agent的分支按钮怎么还是单独的，而不是在卡片上？谈谈你的理解

## 理解与方案

当前实现中，分支按钮确实是脱离卡片的：`IrisAgentView.tsx` 在每个 `turn` 的所有活动卡片之后，额外渲染了一个右对齐的 ghost icon button。它不属于 `AgentActivityCard`，也没有传给 `CardFrame` 的 `action` 插槽。因此视觉上它是消息流中的独立控件，而不是某张卡片标题栏的一部分。

这大概反映了实现时对语义的选择：分支的对象是完整的一轮对话（`turn.id`），而不是某项「本地获取」「文件写入」或「终端操作」活动；按钮放在 turn 容器末尾可以避免误导用户以为只会从某一张操作卡片分叉。但这个技术语义不要求它在视觉上独立，当前排布损失了关联性，也让操作看起来像是悬空的附加按钮。

我认为应把入口放到该轮的最终 Agent 回复卡片（`agent-reply`）标题栏右侧，复用 `CardFrame` 的 `action` 区域：回复是用户可阅读、也最自然会希望「从这里另开一条思路」的结果锚点；按钮仍传入当前 `turn.id`，所以后端仍会复制整轮上下文，语义不变。若一轮尚未产生回复卡片，则不应为了展示入口把按钮挂到任意工具卡上；待回复卡片出现后再展示即可。

实现上可以在渲染卡片时，仅对 `card.kind === 'agent-reply' && turn.canFork` 向 `AgentActivityCard` / `AgentReplyCard` 传递 `onFork`，并将按钮作为 `CardFrame action`。随后删除 turn 末尾现有的独立按钮。这样一轮只会出现一个分支入口，且入口精确贴附于结果卡片；无须改变 `branchIrisAgent(session.id, turn.id)`、会话复制逻辑或 IPC。

- [x] 确认分支入口应附着在最终 Agent 回复卡片，而非工具活动卡片（该结论已被后续设计修正）

## 补充：回复与人工输入都提供入口

我赞同，而且这比只放在回复卡片上更完整。分支的真实语义是「以当前 turn 为上下文边界，改走另一条后续对话」，而一个 turn 同时有两个用户可感知的锚点：人工输入代表分叉的起因，Agent 回复代表当时得到的结果。两处入口都指向同一个 `turn.id`，不会造成两套分支行为。

建议如下：

- 在人工输入卡片标题行右侧加入分支图标，和已有的「查看上下文」文件图标并列；这使用户能在提出问题时立即决定从该问题处分支。
- 在该轮 `agent-reply` 卡片的 `CardFrame action` 区加入相同图标；这使用户在看完结论后能自然地探索另一种后续。
- 两处均只在 `turn.canFork` 时出现，均调用同一个 `branchIrisAgent(session.id, turn.id)` 回调，并采用相同 tooltip/无障碍标签「从本轮创建对话分支」。
- 删除当前位于整轮末尾的独立按钮，避免同一 turn 出现第三个、且语义更模糊的入口。

唯一需要明确的是进行中的 turn：现有 `canFork` 已由后端判定其是否可安全复制，因此前端不应自行根据卡片是否完成猜测；只要遵守该字段，两处入口的显示条件就能保持一致。

- [x] 确认在人工输入与 Agent 回复两个锚点均展示分支入口（仅入口位置成立；两者的复制边界不同）

## 修正：两个入口对应不同的分叉边界

你说得对；此前把两个入口都解释为复制同一个 `turn.id` 是错误的，它忽略了 turn 内「用户输入 → Agent 执行工具与生成回复」的时间顺序。入口相同不代表分叉快照相同。

### 人工输入右侧：从回复前分叉

这里表达的是「保留这条用户指令，但让另一个 Agent 从尚未执行的状态重新处理它」。新会话应复制该输入及其之前的历史，但**丢弃当前 turn 的所有后续内容**：已完成或未完成的本地获取、终端操作、文件写入、Agent 回复、关联的 provider calls / attempts、时间线和终端状态都不继承。

新分叉应以“待继续”的状态落在这条人工输入之后，用户点击「继续」才会发起新的 Agent 执行。因此它不是当前 `branchIrisAgent(session.id, turn.id)` 所实现的「通过完整 turn 复制」；需要单独的“从用户输入分叉”后端语义，或为现有 branch 接口增加明确的 fork point / inclusion mode。

### Agent 回复右侧：从回复后分叉

这里才是现有语义：复制完整 turn，包括其中已经完成的操作记录和 Agent 回复；新会话在回复之后等待用户发下一条消息。它可继续使用当前以 `turn.id` 为边界的分支实现。

### UI 与实现约束

- 两个按钮应使用不同 tooltip 与无障碍标签，分别说明「从此输入重新开始」和「从此回复创建对话分支」，避免用户误以为结果一致。
- 输入侧按钮应只在该输入可作为可重放边界时显示；即便原 turn 正在运行，也必须先安全停止/隔离原会话的后续写入，确保新会话不会带入未完成活动。
- 回复侧按钮继续只在完整回复形成、且当前 `canFork` 为真时显示。
- 为清楚表达操作后的会话状态，输入侧创建的分支应展示「继续」而非自动运行。

- [x] 明确输入侧分叉在原 turn 运行中时，对原会话的执行和后续写入采取何种隔离策略：当前仅允许 quiescent session，避免复制时与原执行竞争
- [x] 设计并实现“从用户输入分叉、丢弃该 turn 后续活动、等待继续”的会话复制语义
- [x] 为输入侧与回复侧分别实现具有不同复制边界和文案的分叉入口

## 实现细节

### 1. 将「从输入分叉」建模为独立命令

原有 `iris-agent:branch` 的行为是 `createIrisAgentBranch`：在指定 `throughTurnId` 找到完整、已 fulfilled 的 turn，深复制该 turn 及之前所有 turn，并按保留的 turn id 筛选 provider calls、provider attempts、timeline 与 transcript。因此它天生是「从回复后分叉」。

本次没有为该命令增加隐式布尔参数，而是新增了明确的 `IRIS_AGENT_BRANCH_INPUT` 通道。渲染进程的 `branchIrisAgent(sessionId, turnId, fromInput)` 根据入口选择旧通道或新通道；主进程 IPC 再分别路由至 `IrisAgentSessionManager.branch` 与 `branchFromInput`。这样协议层能够看出调用者请求的是哪种时间边界，也避免后续调用方意外把输入分叉当成完整 turn 分叉。

两个命令都沿用 session revision 前置条件和 session mutation mailbox：过期界面不能基于旧快照创建分支，同一 source session 的状态变更也会串行化。

### 2. 输入分叉快照的内容与排除项

`createIrisAgentInputBranch` 以 `throughTurnId` 定位输入所属的 turn，先创建新的空会话，再建立 `parentSessionId` 和 `forkedFromTurnId` 谱系关系。

它复制目标 turn 之前的全部 turn；这些历史 turn 的 provider calls、attempts、timeline 和 transcript 按 turn id 一并复制，所以新的 Agent 仍能获得已经发生过的历史对话。目标 turn 本身只保留其 `AgentTurn` 元数据和 user timeline activity：

- 目标 turn 的工具活动、Agent 回复活动、任何终端记录都不进入新 session 的 timeline；
- 目标 turn 不进入 provider calls、provider attempts 和 transcript 的筛选集合，因此不会携带已完成、失败或尚未完成的模型调用；
- 其可读 assembled input 标记被清除，避免将原执行的 prompt artifact 误表示为新执行的上下文；
- 目标 turn 被改为 `paused`，带有 `pauseReason: 'user'` 与「等待继续。」说明，并成为新 session 的 `currentTurnId`；session 自身也处于 `paused`。

结果是界面能显示原来的人工输入以及顶部的「继续」按钮，但不会显示原 turn 的任何执行产物。这正是「保留问题、放弃当时答案与执行路径」的快照。

### 3. 输入分叉后的「继续」为何重新创建执行 turn

原有 `retry` / `resume` 流程假定 paused turn 已经有 provider 调用、transcript 或 worker 可恢复上下文；输入分叉刻意把这些内容全部清空，不能直接向 Worker 发 `resume`。

因此 `retry` 发现 paused current turn 没有 provider call 和 transcript 时，会读取唯一保留的 user timeline 文本，删除这个仅用于展示的 paused turn 与它的 user activity，然后通过既有 `sendSession` 路径重新发送相同文本。`sendSession` 会新建一个 turn id、重新组装 prompt、保存新的 prompt snapshot、启动 Worker 并发出 `run`。这保证新分支的执行从干净状态开始，且继续沿用普通发送路径的状态迁移、错误处理和持久化逻辑。

这也意味着 lineage 上的 `forkedFromTurnId` 仍记录原始输入边界，而实际重新执行产生的 turn id 是新的；二者分别表达「从哪里分出」和「本次真正执行的请求」。

### 4. UI 入口与可用条件

`IrisAgentTurnView` 增加 `canForkFromInput` 投影字段；当前投影对每个可见 turn 置为真，所以人工输入卡片标题右侧会提供 GitBranch 图标。该入口的 tooltip / aria label 为「从此输入重新开始」。输入原本已有的「查看上下文」文件图标仍保留，两者位于同一右侧操作区。

回复侧不使用新字段：仅 `agent-reply` 卡片且原有 `turn.canFork` 为真时，通过 `CardFrame` 的 `action` 插槽渲染按钮。原有 `canFork` 仍要求目标 turn 已 fulfilled 且整个 session 不在 busy state，故回复分叉保持原有完整、稳定快照的约束。其 tooltip / aria label 为「从此回复创建对话分支」。

原来位于 turn 卡片组末尾的独立按钮已删除；分支入口现在附着于明确的时间锚点，且两种入口的文案说明了不同后果。

### 5. 并发与当前限制

`branchFromInput` 与完整回复分叉一样要求 source session quiescent；若原会话正处于 starting、running、waiting-tool、retry-wait 或 stopping，命令会拒绝，而不会复制正在变化的内存状态。paused 和 idle session 可安全创建输入分叉。

需要注意，投影目前将 `canForkFromInput` 设为真而命令会拒绝 busy source session，因此运行中输入侧按钮仍可能出现但点击后失败。这是实现与交互可用条件之间尚未收紧的一点：应将 `canForkFromInput` 与 quiescent 条件关联，或把运行中点击定义为先停止/隔离原 session 后再分叉。当前代码采用的是更保守的后端拒绝策略，尚未实现自动停止原会话。
