## 2026-09-10：测试资产盘点与判断

本节是实际跑过测试、读过测试源码后的结论。命令与结果：

* `npm test -- --run`：91 个测试文件 / 568 项全部通过，34s（vitest 1.6.1，本机 2026-09-10）。
* `npx vitest run src/main/agent src/shared`：24 个文件 / 196 项通过。
* `.iris/status/2026-09-06-Iris-Agent-领域模型与状态机.md` 里记的是“12 个测试文件、119 项”，现在已是 13 个 / 140 项。

### 一、测了什么（按层，标注替身边界）

Agent 内核 `src/main/agent`：13 个测试文件 / 140 项；源码 18 个文件 8522 行，测试 5490 行（约 0.64:1）。
用例分布：session-manager 38、compaction 24、pi-adapter 17、command-pty 13、worker-host 9、tool-host 8、session-store 8、history 7、session-model 6、trace-context 4、prompt 3、task-manager 2、supervision 1。

| 层 | 关键文件 | 替身边界 | 真实性 |
| --- | --- | --- | --- |
| 领域模型与纯函数 | session-model、session-domain、trace-context、compaction、history | 无替身 | 高 |
| 持久化 / journal | session-store | 真实 fs + 临时目录 | 高 |
| Worker 协议与执行循环 | worker-host、agent-worker | Host 侧用 `FakeWorker`；agent-worker 用真实入口 + mock `pi-adapter` | 中：两侧各自为真，接缝靠双方对同一契约的替身 |

| Session 编排 | session-manager（2536 行） | `FakeWorker` + `FakeInteractiveTerminal`，真 store，工具走真 ToolHost | 中高 |

同一链路的周边覆盖：`shared/agent-protocol`(2)、`shared/agent-context-budget`(4)；renderer 投影 `iris-agent-store`(5)、`iris-agent-actions`(2)、`lens-agent-state`(2)、`agent-status`(3)、`agent-context-usage`(6)、`session-projection`(3)；`agent-injection.ts` 没有专门测试，只在 i18n-protocol 与 terminal-session-manager 用例中被顺路引用。

非单元测试的门禁：`typecheck`、`check:async`、`metadata:check`、`licenses:check`、`agent:worker-check`（比对编译产物与源码里的协议版本，防止 Worker 产物过期）、`smoke`（主进程 5 秒存活，抓 preload-error / render-process-gone）。CI（`.github/workflows/ci.yml`，windows-2022）跑 test + typecheck + build + worker-check + smoke，**不产出覆盖率**。

### 二、确实被验证到的业务逻辑

* **状态机不变量是真断言**：`paused → superseded` 时新输入接管、Rewind 截断 Trace 且不把被截断项写成 superseded、Rewind 后把 head 恢复为 paused、Fork 不改来源 Session、从 superseded 输入 Fork 后新分支为 paused（history.test、trace-context.test、session-store.test）。
* **错误归层原则有落地验证**：工具 `ok:false` 转成 `isError=true` 的 tool result 而不是升级为暂停 Intent；provider 失败不伪造 assistant 回复；重试留在同一次 Invoke 内，多次失败才 `execution-paused`；只有上下文类 provider 错误才判定为 overflow（pi-adapter.test、worker-host.test、session-manager.test）。
* **提交顺序与原子性**：Invoke → ToolCall → ToolResult 的提交次序、Stop 期间排队 delta 不丢、durable commit 失败要 NACK 并先终止 Worker 再暴露 paused、request facts 先于 provider 请求落盘。
* **凭据边界**：provider profile 的 apiKey 不出现在 renderer 投影与模型目录（`JSON.stringify(...)` 断言不含 `sk-`）。

### 三、薄弱与空白

1. **接缝没有真实覆盖**。session-manager 看到 `FakeWorker`，worker-host 看到 `FakeWorker`，agent-worker 看到 mock 掉的 `pi-adapter`。真实链条 main → Host → agent-worker → pi-adapter → Pi SDK **从未在同一进程里跑过一次**。
2. **没有覆盖率度量**。没有 `@vitest/coverage-*`，CI 也不产覆盖率；“140 项全过”只能说明既有断言通过，不能说明哪些分支没被写到。
3. **部分模块只有间接覆盖**：`session-events.ts`（领域事务 + `assertAgentSessionTransition`）、`session-domain.ts` 的部分断言、`context-artifact.ts`（payload 清洗与凭据擦除）、`edit-diff.ts` 都没有独立测试文件，只在别的用例顺路经过，失败时定位成本高。
4. **没有端到端或契约回放**：没有真实 provider 的录制回放/金样，没有 IPC 层的集成测试；smoke 只证明“能起来”。2026-08-13 那轮手工测试实际承担的正是这部分，但它不可重复、不可回归。
5. **时间与竞态行为不对称**：超时、流量控制、串行化大量依赖真实计时（测试慢、易抖），而真正的竞争窗口（Stop 与 `agent_end` 的先后、Worker 退出与 `initialize` 的先后）只有极少数定向用例。
6. **renderer 只测投影纯函数**，发送/停止/重试/Rewind 的按钮 → store → IPC 交互链路没有测试。

### 四、我的判断

* 对**纯逻辑**（领域模型、Context 投影、compaction、edit diff、命令构造）可以算充分：断言围绕不变量写，而不是照抄实现细节。
* 对**业务逻辑整体**还不够，而且缺的正是最容易出 bug 的那一层——跨进程接缝与真实 provider 链路。现状更像“每一层各自自证”，而不是“这条业务链路能走通”。
* 最有力的证据是反面的：2026-08-15 的 `run` 早于 `ready` 竞态、2026-08-16 的持久历史从未注入 Pi Session、以及同期的 Stop 竞态，三个都能让用户直接踩到的缺陷，全部是在测试全绿的情况下漏出去的。前两个的共同形态就是“两侧契约都测了，契约之间的接线没测”。
* 还有一处**错配**：复杂度集中在 `session-manager.ts`（2536 行，占内核源码约 30%），但它只有 38 项用例，且把最复杂的对端（Worker）替身化。覆盖率分布与复杂度分布不一致。
* 所以结论不是“测得太少”，而是“测的层级选偏了”。继续堆同类单测的边际收益在下降，预算应该转向：真实 Worker 的进程内端到端链路、定向的竞态/时序用例、以及覆盖率作为防回退下限（而不是追求高数字）。
