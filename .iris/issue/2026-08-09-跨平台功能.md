## 问题理解

Iris 面向本地 AI CLI、Git 和终端用户，这一目标群体中的 macOS 和 Linux 用户占比会显著高于普通桌面软件。Windows-only 不只是少覆盖两个平台，还会让许多潜在用户在下载阶段直接离开。因此，跨平台支持不应被视为遥远的附加功能，而应进入近期产品主线。

## 结论

Iris 可以迁移到 Linux 和 macOS，无需重写。整体架构本身适合跨平台：Markdown 协议、项目扫描、文件监听、编辑器、Git、设置存储、Electron/React UI 和大部分终端渲染逻辑都没有被 Windows 锁死。内置 PTY 甚至已经存在 POSIX shell 分支，会读取 `$SHELL` 并回退到 `/bin/bash`；`node-pty` 也支持 Windows、macOS 和 Linux。

但这不是只给 `electron-builder` 增加两个 target 就能完成的工作。粗略看，约 75% 的代码天然跨平台，剩余约 25% 集中在终端启动、上下文注入、命令语法、窗口行为和发行工程等关键链路。迁移难度中等、风险可控，Linux 的公开发行相对容易，macOS 的主要成本在签名、公证和原生体验，而不是业务代码。

应把目标定义为“平台级可用”，而不只是“Electron 能生成安装包”。

## 当前跨平台基础

* Markdown 文件协议及 `.iris/` 工作区模型与操作系统无关。

* Node 文件系统、`path`、`chokidar`、`gray-matter` 等核心实现均为跨平台方案。

* Git 集成通过 `git` 可执行文件工作，各平台只需保证其位于 `PATH`。

* Electron、React、CodeMirror、Milkdown、xterm.js 等 UI 和编辑器技术均支持三平台。

* 设置目录使用 `homedir()` 和 `path.join()`，近期项目路径也已按 Windows 大小写不敏感、其他平台保留原生语义处理。

* 内置终端的宿主 shell 已区分 Windows 与 POSIX：Windows 使用 PowerShell/cmd，POSIX 使用 `$SHELL` 或 `/bin/bash`。

* xterm 的 Windows ConPTY 参数只会在 Windows 启用，其他平台不会错误套用。

* `node-pty@1.1.0` 包含 Windows 和 macOS 预构建产物；Linux 可在安装依赖时本机构建。

* 应用已经使用 Electron 的 `shell.openPath`、`showItemInFolder`、`trashItem` 等跨平台系统 API 处理打开、显示和回收站操作。

## 已确认的 Windows 耦合

### 上下文注入

SessionStart 上下文注入目前完全依赖 `~/.iris/focus-context.ps1` 和 `powershell.exe`。需要提供功能等价的 POSIX 脚本，例如 `focus-context.sh`，并让 hook 命令、脚本状态检测、安装、更新和卸载逻辑按平台选择适配器。

脚本必须继续满足当前契约：区分 `FOCUS_DOC` 与 `IRIS_WORKSPACE_PATH`、输出动态上下文、32 KiB 以上降级为路径提示、正确处理文件不存在和非 ASCII 内容，并保持普通外部终端无输出。

### Agent 默认命令

大多数基础预设命令（如 `claude`、`codex`、`gemini`）本身可跨平台，但 Aider 和 Goose 预设包含 `$env:FOCUS_DOC`、`$env:USERPROFILE`、PowerShell 子表达式和 `.ps1` 路径，在 POSIX shell 下不能工作。

预设需要按平台生成或表达为结构化模板，不能继续把 PowerShell 命令作为所有平台共享的静态字符串。用户已经保存的自定义命令应保持不变，避免迁移设置时被静默改写。

### 外部系统终端

“在系统终端中运行”目前只支持 `wt.exe`，非 Windows 平台会明确失败。

Linux 需要适配常见终端或提供用户可配置的外部终端命令；可以优先支持 `x-terminal-emulator`，再按需覆盖 GNOME Terminal、Konsole 等。macOS 需要支持 Terminal.app，iTerm2 可作为可选适配器。找不到支持的终端时，界面应隐藏或禁用该能力并给出明确原因，而不是让用户执行后才得到笼统错误。

### 文件拖入终端与 shell 转义

当前文件拖入终端的引用规则基于“Windows 文件名不能包含双引号”的假设，只给含空白的路径加双引号。POSIX 文件名允许双引号等字符，而且 Bash/Zsh、PowerShell 和 cmd 的参数转义规则不同。

文件参数序列化必须移入平台或 shell 适配层，并为 PowerShell、cmd 和 POSIX shell 分别测试空格、单引号、双引号、反斜杠、美元符号、换行和其他元字符。现有危险字符确认仍应保留，不能把引用处理误当成安全授权。

### PTY 生命周期

Windows 使用 `taskkill.exe /t /f` 结束整棵进程树；POSIX 当前只调用 `pty.kill()`。需要在 Linux 和 macOS 上验证 agent CLI 派生进程是否会残留，并根据结果使用进程组或信号策略补齐关闭、切换项目、退出和崩溃清理语义。

ConPTY 专用的 resize、防闪烁和标题过滤逻辑多数不会阻止 POSIX 运行，但必须用 Bash/Zsh 及常见全屏 TUI 做真实回归，确认没有因 Windows 经验参数造成错误状态或重绘问题。

### 窗口与桌面行为

应用使用 `frame: false` 和 Windows 风格自绘标题栏。Linux 上可以保留这种体验，但 macOS 应使用原生交通灯布局，或至少采用 Electron 支持的 macOS 标题栏方案。

macOS 还应遵循关闭最后一个窗口后应用留在 Dock、点击 Dock 图标重新创建窗口的常规生命周期。当前实现虽然监听了 `activate`，但 `window-all-closed` 会在所有平台直接退出。

还需验证菜单栏、全屏、最小化/最大化、快捷键中的 Cmd/Ctrl 差异、Finder 文件拖放、系统字体和 Retina 显示。

### 构建、原生依赖与发行

当前 `npm run dist` 固定为 `electron-builder --win --x64`，`electron-builder.yml` 只有 Windows portable 和 NSIS 配置，CI 也只运行 Windows 2022。

Linux 需要增加 AppImage 或 deb 目标、桌面分类和图标配置。`node-pty` 没有随当前安装包提供 Linux 预构建产物，因此 Linux CI/构建机需要 Python、编译器和相关构建工具，或后续采用可靠的预构建策略。

macOS 建议先支持 Apple Silicon；需要生成和检查 macOS 图标，配置 DMG/zip、应用签名、hardened runtime、entitlements 和 Apple notarization。未签名开发包可以用于内部验证，但不适合作为正式公开发行。Intel Mac 和 universal build 可以在首个 Apple Silicon 版本稳定后再决定。

构建必须在对应操作系统上完成和验证，尤其是包含 `node-pty` 这类原生模块时，不应依赖在 Windows 上交叉打出所有平台产物。

## 推荐的实现边界

不要维护三套分叉业务实现。应建立统一的平台能力层，让核心代码只表达意图：

```text
Iris 核心
  └─ Platform Adapter
       ├─ 宿主 shell 与命令语法
       ├─ Agent 预设
       ├─ 上下文脚本与 hook 命令
       ├─ 外部终端启动
       ├─ 路径参数转义
       ├─ PTY 终止策略
       ├─ 窗口生命周期与外观
       └─ 打包、签名与更新
```

平台判断应集中在适配器和能力声明中。Renderer 可以依据能力决定显示、隐藏或禁用操作，不应在组件中不断增加零散的 `process.platform` 或 `navigator.platform` 分支。

## 推荐推进顺序

1. 先抽出平台能力层，补齐 POSIX shell、命令引用、上下文脚本和进程生命周期，使 Linux 与 macOS 共享同一套 POSIX 实现。
2. 立即建立 Windows、Ubuntu、macOS 的 CI 矩阵，至少执行依赖安装、测试、类型检查和应用构建，尽早暴露大小写敏感路径、原生模块和 shell 差异。
3. 先发布 Linux x64 AppImage 或 deb beta。它的发行门槛最低，可以最快证明跨平台核心可靠。
4. 随后发布签名并 notarize 的 macOS Apple Silicon beta，补齐原生标题栏、Dock 生命周期和 Terminal.app 适配。
5. 根据真实用户需求再扩展 Intel Mac、universal build、更多 Linux 包格式和更多桌面终端适配器，避免首轮把测试矩阵扩得过大。

如果目标是最快验证技术可行性，Linux 应先发；如果目标是尽快扩大 AI 开发者用户量，macOS Apple Silicon 的商业优先级可能更高。工程上仍应先完成共享 POSIX 层，再分别收口发行。

## 工作量判断

* 做到源码在 Linux/macOS 开发环境中启动：预计数个工作日。

* 完成共享 POSIX 适配、自动测试和基本稳定性验证：预计约 1 周。

* 做到 Linux 可公开 beta：在前项基础上预计再增加 2 至 4 个工作日。

* 做到 macOS 可公开 beta：在前项基础上预计再增加 3 至 7 个工作日，另受 Apple 开发者账号、证书和公证流程影响。

* 三平台达到当前 Windows 版本相近的可靠性：建议预留约 2 至 3 周集中工作，并持续承担三平台回归成本。

以上为单人熟悉现有代码库、没有重大原生依赖阻塞时的粗略估计。真正不可压缩的部分是三平台实机测试和发行验证，而不是编写平台分支本身。

## 验收清单

* [ ] 建立集中式平台能力接口，核心业务代码不散落新增平台判断。

* [ ] 在 Bash/Zsh 下验证内置 PTY、Agent 启动、环境变量和命令退出后返回交互 shell。

* [ ] 实现并测试 POSIX `focus-context` 脚本及各 Agent CLI 的 hook 安装、检测、更新和移除。

* [ ] 按平台生成 Aider、Goose 等默认 Agent 命令，同时保留用户自定义命令。

* [ ] 为 Windows、Linux、macOS 实现或明确降级外部系统终端能力。

* [ ] 为 PowerShell、cmd、Bash/Zsh 分别测试拖入文件的参数引用和危险字符确认。

* [ ] 验证三平台关闭会话、切换项目、退出和异常崩溃后无残留 agent 进程。

* [ ] 增加 Windows、Ubuntu、macOS CI，覆盖安装、测试、类型检查和构建。

* [ ] 生成并实机安装 Linux beta 包，验证图标、启动、文件选择、回收站、Git 和终端。

* [ ] 生成、签名并 notarize macOS Apple Silicon beta，完成干净机器安装验证。

* [ ] 更新 README、系统要求、下载入口和已知平台限制。

## 最终判断

跨平台支持值得做，而且当前架构已经具备良好基础。它不是一次重写，也不是不可控的大工程；主要工作是把少数 Windows 假设提升为正式的平台抽象，再建立真实的多平台构建与测试纪律。

Linux 技术上最容易率先交付；macOS 代码迁移并不困难，但公开发行必须认真处理签名、公证和原生桌面体验。只做 Windows 会显著限制 Iris 在其核心目标用户中的覆盖面，因而跨平台应作为近期高优先级能力推进。
