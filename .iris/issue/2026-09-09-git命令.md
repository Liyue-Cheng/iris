我发现现在很多时候，AI调用是git命令会弹出pager，导致超时，这是怎么回事？这是我们终端的问题，还是AI的问题，你检查一下

## 检查结论（2026-09-09）

**不是终端坏了，也不是 git 配置写错了。是「Iris 用真 PTY 跑 AI 命令」和「git 在 TTY 下默认启用 pager」撞在一起。**
AI 侧有可自保的写法，但根因在产品侧的执行环境。

### 复现证据

在本仓库（`E:\projects\iris`，147 个 commit）实测：

| 检查项 | 结果 |
| --- | --- |
| `git var GIT_PAGER` | `less` |
| `git config --get core.pager` | 空（未配置，走 git 默认值） |
| 环境变量 `GIT_PAGER` / `PAGER` / `LESS` | 全部未设置 |
| `[Console]::IsOutputRedirected` | `False` —— stdout 是真 TTY |
| `git log --oneline -60` | 卡住；输出里出现 `:` 与 `:...skipping...`，即 less 全屏接管、等待按键 |
| `git --no-pager log --oneline -3` | 正常返回，exit 0 |
| `$env:GIT_PAGER='cat'; git log --oneline -3` | 正常返回，exit 0 |

### 根因链路

1. `src/main/agent/command-pty.ts` 用 node-pty 在 ConPTY 里起 pwsh（`-NoLogo -NoProfile -Command <cmd>`，80x24），环境只从 `process.env` 继承并剔除 `ELECTRON_RUN_AS_NODE` 等少数键，**没有设置任何 pager 相关变量**。
2. 因为是真 PTY，git 判定 stdout 是终端，于是对 `log` / `diff` / `show` / `branch` 等多屏输出自动调用默认 pager `less`。
3. `less` 是交互程序，满一屏就停在 `:` 等按键；AI 不会按键，前台 deadline 到期，命令被判定超时。

短输出通常不卡，因为 git 默认给 less 传 `FRX`（`-F`：一屏内自动退出）——所以现象是「有时弹 pager 有时不弹」。

### 影响面不止 `git log`

同一机制会让任何交互式程序挂住 AI 的终端：

- `git commit`（不带 `-m`）：本机 `git var GIT_EDITOR` = `vi`，同样等按键；
- `git add -p`、`git rebase -i`、`git config --edit`；
- 需要凭据的 `git push` / `fetch`（`GIT_TERMINAL_PROMPT` 未设置时会等输入）；
- 其它走 `PAGER` 的工具（`less` / `more`），以及 `npm init` 之类的交互提示。

### 修复方案

**A. 产品层（根治，推荐）** —— 给 AI 的命令 PTY 注入非交互默认值，且不覆盖调用方显式传入的同名变量。

在 `src/main/agent/command-pty.ts` 的 `buildSpawnEnv(...)` 之后补充：

- `GIT_PAGER=cat` —— 等价于 `--no-pager`；`cat` 随 Windows Git 自带，比设空值稳；
- `PAGER=cat` —— 兜底其它分页工具；
- `GIT_TERMINAL_PROMPT=0` —— 缺凭据时快速失败，而不是挂到超时；
- 可选 `GIT_EDITOR` / `GIT_SEQUENCE_EDITOR` —— 让 `git commit`、`git rebase -i` 在 AI 侧直接失败而不是起 vi；Windows 下没有 `true`，需要用包装命令，收益与风险需单独评估。

建议同时覆盖 `TerminalSessionManager.createCommandSession`（项目工具栏的一次性命令，同属无人值守场景）；**不要**改普通交互终端会话（`createConfiguredSession`），用户自己敲 `git log` 应该保留分页。

**B. AI 侧（自保，立刻可用）**

- 养成 `git --no-pager ...` 的习惯，或在同一条命令里前置 `$env:GIT_PAGER='cat';`；
- 需要多屏内容时用 `--no-pager` 搭配 `-n` / `--stat` 收敛输出；
- 提交一律带 `-m`，避免进入编辑器。

**C. 工具描述层（降低复发）**

`src/main/agent/pi-adapter.ts:162` 的 terminal 工具 `promptGuidelines` 里补一条：不要运行等待输入的交互式命令（pager、编辑器、凭据提示），git 请加 `--no-pager`。

### 补充：什么叫「用真 PTY 跑 AI 命令」，换成管道会怎样

**真 PTY** = node-pty 给子进程分配一个伪终端（Windows 上是 ConPTY，`command-pty.ts` 里 `name: 'xterm-256color'`）。子进程的 stdout 是一个终端设备，`isatty()` 为真。
**假的** = `child_process.spawn` + `stdio: 'pipe'`，stdout 是管道，`isatty()` 为假。

git 只在 stdout 是终端时才启用 pager，所以换管道确实能消掉这个症状。本仓库实测（同一条命令，只改 stdout 去向）：

| 写法 | stdout | 耗时 | 结果 |
| --- | --- | --- | --- |
| `git log --oneline -60` | PTY | 卡住 | less 接管等按键 |
| `git log --oneline -60 \| Select-Object -First 3` | 管道 | 0.09s | 正常返回 |
| `git log --oneline -60 > file` | 文件 | 0.05s | 正常返回 60 行 |

**但换管道要付出代价**，因为真 PTY 是这个产品的功能底座，不是随手选的实现细节：

1. **AI 命令的实时终端卡片**。`command-pty.ts:184` 的 `shown` 事件 + `TerminalMirror` 屏幕模型，让终端在跑够 3s 后在卡片里露出实时画面（`session-manager.ts:1605` 写 `terminalRevealedAt`）。管道没有屏幕语义，只能给一段纯文本。
2. **用户接管**。`session-manager.ts:897` 的 `writeTerminal`（IPC 在 `ipc.ts:1314`）允许用户往 AI 正在跑的终端里打字，活动记录还专门记了 `terminalUserInput`。管道下这个能力不存在。
3. **ANSI 渲染**。颜色、进度条、光标、synchronized output 都依赖真终端；管道拿不到这些。
4. **工具自己的承诺**。terminal 工具描述是「Execute a visible PowerShell command」（`pi-adapter.ts:165`），管道会直接违背这句。

**而且管道也治不全。** 它只解决「git 因为看到 TTY 才分页」这一类，读 stdin 的交互仍会挂或报错：`git commit`（无 `-m`，会去起 `vi`）、`read` / `Read-Host` / `pause`、`npm init`、缺凭据的 `git push`。所以方案 A 的环境变量注入即使换了管道也仍然值得做。

顺带排除两个误解：

- `useConpty: false`（退回 winpty）**没用**，winpty 同样是 PTY，`isatty()` 依然为真。
- 这不是 Iris 独有的问题，任何在 TTY 里自动跑 git 的工具都会遇到，AI 只是不会按键。

**结论**：管道能消症状但砍掉可见终端、用户接管和 ANSI 渲染；推荐保留真 PTY，只注入非交互环境变量，即方案 A。

## 实施结果（2026-09-09）

按「不换管道」的要求，保留真 PTY，只把无人值守 PTY 的交互式出口全部堵住。

### 改了什么

**1. `src/main/pty-utils.ts`** —— 新增 `NON_INTERACTIVE_ENV` 常量与 `applyNonInteractiveEnv(env)`：

| 变量 | 值 | 作用 |
| --- | --- | --- |
| `GIT_PAGER` | `cat` | 等价于全局 `--no-pager`，本次故障的直接修复 |
| `PAGER` | `cat` | 兜底其它遵守 `PAGER` 的分页器 |
| `GIT_TERMINAL_PROMPT` | `0` | 缺凭据时快速失败，不再等输入 |
| `GIT_EDITOR` | `false` | `git commit` 不带 `-m` 时退出非零 |
| `GIT_SEQUENCE_EDITOR` | `false` | `git rebase -i` 时退出非零 |
| `GIT_MERGE_AUTOEDIT` | `no` | 合并提交用默认消息，不做编辑器（成功而非失败） |

**2. `src/main/agent/command-pty.ts`** —— 在 `buildSpawnEnv(...)` 之后调用 `applyNonInteractiveEnv(env)`。这是 AI 命令的唯一入口，所有 `terminal` / `task_start` 命令都过这里。

**3. `src/main/agent/command-pty.test.ts`** —— 新增两个测试（见下）。

**没改**：`pi-adapter.ts` 工具提示（本轮要求暂缓）、普通交互终端会话（`createConfiguredSession`）、外部终端（`system-terminal.ts`）、`git-manager.ts`（它用 `child_process` 管道，本来就不分页）。

### 关键决策：为什么只改 AI 命令 PTY

项目工具栏的 `createCommandSession` 虽然也是一次性命令，但它的 shell 带 `-NoExit`，命令跑完后**留给用户继续使用**。往 spawn env 里写 `GIT_PAGER=cat` 会连带污染用户后续在这个 shell 里手敲的 `git log`。而它本身又没有 deadline，分页不会超时（用户自己按 q 就行），所以本轮不动。

### 关键决策：为什么编辑器用 `false` 而不是 `:`

实测对比（git 2.48.1.windows.1）：

| 配置 | 行为 |
| --- | --- |
| `GIT_EDITOR=false` | `error: there was a problem with the editor 'false'` + `Please supply the message using either -m or -F option.`，exit 1，0.22s |
| `GIT_EDITOR=:` | `Aborting commit due to empty commit message.`，exit 1，0.11s |
| `GIT_SEQUENCE_EDITOR=false` | rebase -i 直接报错，**无残留 rebase 状态**，0.17s |
| `GIT_SEQUENCE_EDITOR=:` | rebase -i **静默成功**，按默认 todo 重放——AI 会误以为 squash 成功 |

`false` 两处都用，因为 `GIT_EDITOR=false` 的输出直接告诉模型改用 `-m` / `-F`；而 `GIT_SEQUENCE_EDITOR=:` 会造成「假成功」，比报错更危险。即使环境里没有 `false` 这个命令，sh 也会因找不到命令返回非零，仍然是快速失败。

- **环境变量断言**：`forces non-interactive git defaults over inherited values in the spawned environment` —— 传入 `GIT_PAGER=less` / `PAGER=more` / `GIT_TERMINAL_PROMPT=1` / `GIT_EDITOR=vi`，断言 spawn 出去的值全部被覆盖为安全值。
- **真实回归测试**：`runs a real git log in a ConPTY without the pager stalling the command` —— 在真 ConPTY 里跑 `git log --oneline -50`（远超一屏）。
  - 把注入临时注掉后：`AssertionError: expected 'timeout' to be undefined`（10s 被 pager 卡死，即原故障）。
  - 恢复注入后：通过。
- **测试套件**：`npx vitest run src/main` → 40 个文件、322 个测试全过。
- **typecheck**：`tsc -p tsconfig.node.json` 只剩一条与本改动无关的既存报错：`src/main/agent/session-manager.test.ts(1760,93): Property 'revision' does not exist on type 'IrisAgentContextUsage'`（该文件在本轮之前已有 243 行未提交改动，属于上下文水位那条线的在建工作）。

### 效果

AI 侧不再需要记得加 `--no-pager`：`git log` / `git diff` / `git show` / `git branch` 直接流式输出；`git commit` 不带 `-m` 会立即报错并提示用 `-m`；`git rebase -i` 会立即报错而不是挂死；`git merge` 正常完成。工具提示未改，但即使模型不遵守也不会再超时。

### 生效范围：只影响 AI 命令，不影响手动终端

已按代码路径核实（`applyNonInteractiveEnv` 全仓库只有一处调用）：

**生效**（都走 `AgentCommandPty` → `command-pty.ts:98`）：

- `terminal` 工具调用 —— `tool-host.ts:218`
- `task_start` 后台任务 —— `task-manager.ts:123`

**不生效**（都没有调用注入）：

| 场景 | 入口 | 行为 |
| --- | --- | --- |
| 用户点开的终端会话 | `TerminalSessionManager.createSession` → `createConfiguredSession` | `git log` 仍分页，`git commit` 无 `-m` 仍起 `vi` |
| Iris Agent 会话本体（用户在里面手敲） | 同上 | 同上 |
| 项目工具栏一次性命令 | `createCommandSession` → `createConfiguredSession` | 同上（有 `-NoExit`，shell 留给用户） |
| 外部 Windows Terminal | `system-terminal.ts` | 同上 |

另一个安全边界：`buildSpawnEnv` 返回的是 `process.env` 的**副本**，`applyNonInteractiveEnv` 改的是这个副本，所以 Iris 主进程自身的环境不被污染，各会话之间也不互相影响。
