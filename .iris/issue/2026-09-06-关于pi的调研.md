## 调研记录（2026-09-06）

### 结论先行

可以移除 Pi，但不是删除一个 import 或把 `pi-adapter.ts` 改名就结束。当前 Iris 的领域模型已经独立；Pi 仍是执行层和模型供应商层的运行时依赖。准确地说：

* **可以直接移除的 Pi 外壳**：Pi 的持久化 Session、ResourceLoader、Settings、内置资源发现、Pi compact，以及 Pi 的 TUI/CLI/extension 能力。当前代码把它们全部关闭或只用内存实现。
* **仍被生产路径使用的 Pi 能力**：`createAgentSession()` 的 provider -> assistant -> tool-call 循环、自动重试和事件流；`ModelRuntime` 的模型/供应商注册、模型目录、认证凭据、OpenAI/Anthropic 请求适配和流式解析。
* **少量独立工具能力**：`generateUnifiedPatch()` 只用于文件变更展示，可以用 Iris 自己的实现或直接依赖一个小型 diff 库替换。

因此“移除 Pi 核心”有两个不同终点：

1. **移除 `pi-coding-agent`**：Iris 自己实现执行循环，但暂时直接使用 Pi 的 `pi-ai` provider runtime。这个终点能去掉 Pi 的 Agent/Session/资源/TUI 层，改动中等。
2. **完全移除 Pi 运行时**：执行循环、SSE/流式协议、模型目录、认证、Provider 适配全部归 Iris 所有。这个终点才是真正不依赖 Pi，改动较大，但与“整个 agent 领域模型都是我们自己的”最一致。

建议把第 1 个终点作为过渡批次，最终以第 2 个终点收口；不要继续在 `pi-adapter.ts` 上叠加 Iris 语义。

### 当前 Pi 实际承担的职责

| 位置 | 当前调用 | 实际职责 | 是否属于 Iris 领域事实 |
| --- | --- | --- | --- |
| `src/main/agent-worker.ts` | `createIrisPiSession()`、`session.prompt()`、`session.agent.continue()` | 执行一次或继续一次 LLM + tool loop；发出流式事件 | 否，属于执行器 |
| `src/main/agent/pi-adapter.ts` | `ModelRuntime.create/getModel/streamSimple/completeSimple` | provider 注册、模型解析、认证、HTTP 请求、流式响应 | 否，属于 provider runtime |
| `src/main/agent/pi-adapter.ts` | `SessionManager.inMemory()`、`appendMessage()` | 把 Iris `AgentHistorySnapshot` 转成 Pi message，以便下一次请求 | 否，临时转换层；Iris 已有 Trace/Context |
| `src/main/agent/pi-adapter.ts` | `DefaultResourceLoader`、`SettingsManager.inMemory()` | 满足 Pi SDK 初始化契约 | 否，当前功能已明确关闭 |
| `src/main/agent/pi-adapter.ts` | `create*ToolDefinition()` | JSON schema、参数校验、tool 结果包装 | 否，工具执行实际由 `IrisAgentToolHost` 完成 |
| `src/main/agent/tool-host.ts` | `generateUnifiedPatch()` | 生成文件 diff 展示 | 否，独立小工具 |
| `src/main/agent/provider-profiles.ts` | `ModelRuntime` 类型及模型元数据 | 将 Iris profile 映射为 Pi provider/model 结构 | 否，profile 文件和 UI 投影已经是 Iris 自己的 |
| `src/main/app-main.ts`、`src/main/ipc.ts` | `irisPiAgentDir()`、provider catalog/login/logout | 使用 Pi 的 agent 目录和凭据文件 | 目录/凭据是机器基础设施，当前还不是 Iris 自有格式 |
| `src/shared/agent-protocol.ts`、`scripts/check-agent-worker.mjs` | `piVersion` | worker 自检和可观测性版本字段 | 否，可改为 Iris executor/provider 版本 |

### 已经属于 Iris、无需重做的部分

当前 v3 Session aggregate 的事实源是 `intents`、execution-level `turns`、`invokes`、`invokeAttempts`、`timeline`、`toolOperations`、`effects`、`requestFacts`、`rewindReceipts` 和 `injection`。Trace/Context、compact、rewind、fork、artifact ownership、CAS 文件恢复都在 Iris 代码中完成。Pi 没有写入 Iris 的持久化 transcript，也没有成为 Intent/Turn/Invoke 的身份。

Worker 初始化只携带项目目录、agent 配置目录、provider profile 根目录和 shell；模型与 proxy 在每次 `run`/`resume` 临时传入。Worker 每次执行前创建 Pi session，结束后 dispose。因此 Pi session 不是跨用户操作的权威状态，替换它不会改变持久化 schema。

同时，Pi 自带的以下能力在 Iris 中已被显式禁用或绕过：

* ResourceLoader 禁止 extensions、skills、prompt templates、themes、context files，只注入 `IRIS_AGENT_PROMPT`。
* Pi compaction 通过 `SettingsManager.inMemory({ compaction: { enabled: false } })` 关闭，真正的 compact 在 `src/main/agent/compaction.ts` 调度。
* `SessionManager` 只用 `inMemory()`，历史由 Iris `history()` / `buildAgentContext()` 提供。
* Pi 的 tool 执行只负责调用包装后的定义；文件、终端、effect、artifact、权限边界均由 `IrisAgentToolHost` 和主进程负责。

这说明移除 Pi 不需要迁移 Pi session 文件，也不需要改 Iris v3 aggregate；主要是替换一次性执行适配器。

### 不能低估的耦合点

1. **执行循环不是单次 HTTP 调用。** 需要保留 assistant 流式增量、多个 tool call、tool result 回填、继续请求、用户 abort、provider 自动重试、`paused`/`settled` 边界，以及当前 worker 的 durable event ack 顺序。
2. **Provider 适配不是只有 URL。** 当前 `ModelRuntime` 覆盖 OpenAI Responses、Anthropic Messages 及兼容端点，负责请求体转换、SSE 事件解析、tool-call 参数增量拼接、thinking/usage/stopReason 归一化、错误和 retry。`normalizeIrisProviderContext()` 还会在真正发请求前清理中断 assistant、重复/孤儿 tool result。
3. **模型目录和 profile 已有双层语义。** Iris profile 文件保存 profile、凭据和手工模型配置；Pi runtime 还提供内置 provider 模型元数据、认证状态和 `getAvailable()`。完全移除时必须定义 Iris 自己的 model/provider contract，不能把 Pi 的 `Model` 类型原样搬过来。
4. **凭据存在兼容问题。** `saveIrisProviderApiKey()` / `removeIrisProviderCredential()` 当前通过 Pi 的 `auth.json` 和 login/logout 流程工作；自定义 profile 的 key 则由 Iris profile 文件保存。完整移除必须保留旧凭据读取的一次性迁移或明确放弃迁移。
5. **协议与测试有显式 Pi 名称。** `piVersion`、`IRIS_PI_VERSION`、`restoreIrisPiHistory`、`createIrisPi*`、`pi-adapter.test.ts`、worker check、prompt metadata、third-party notices 都需要一起收口，否则会留下“已移除但仍依赖 Pi”的假绿状态。

### 推荐目标结构

```text
IrisAgentSessionManager
  -> AgentExecutionRunner       # Iris-owned loop and lifecycle boundary
       -> ProviderClient         # Iris-owned provider-neutral contract
            -> OpenAIResponsesClient
            -> AnthropicMessagesClient
       -> IrisAgentToolHost      # existing side-effect boundary
       -> Trace/Context           # existing persisted facts and pure projection
```

`ProviderClient` 建议只暴露 Iris 需要的最小接口：

* `stream(request, signal, hooks)`：返回规范化的 `text_delta`、`tool_call_delta`、`message_end`、`error` 事件。
* `complete(request, signal)`：给 compact 和 terminal supervision 使用，不创建 Agent session。
* `listModels(profile)` / `verify(profile)`：模型目录和连接检查。
* `readCredential`、`writeCredential`、`removeCredential`：由 Iris 用户数据目录管理，不再依赖 `~/.pi/agent/auth.json` 的语义。

`AgentExecutionRunner` 只处理执行状态机：组装当前 Context，调用 provider，累积 assistant message，按顺序或并行执行 tool calls，把 tool result 回填 Context，并通过已有 worker 事件协议提交 Iris 事实。它不应知道 provider 的 HTTP、模型目录或 Pi message 类型。

### 分阶段迁移方案

#### 阶段 0：先把依赖边界钉死（低风险）

* 新建 Iris-owned `provider-contract.ts`、`execution-runner.ts` 的接口和事件类型。
* 将 `pi-adapter.ts` 改为唯一临时实现，禁止其他模块直接 import Pi 类型；`provider-profiles.ts` 也只依赖 Iris 类型。
* 把 `piVersion` 改成 `executorVersion` / `providerRuntimeVersion`，并保留一次协议兼容窗口。
* 把 `generateUnifiedPatch()` 移到 Iris 本地 utility。

#### 阶段 1：移除 `pi-coding-agent` 的 Agent/Session 外壳

* 用 Iris `AgentExecutionRunner` 替代 `createAgentSession()`、`SessionManager.inMemory()`、`DefaultResourceLoader`、`SettingsManager` 和 Pi tool definitions。
* 继续暂时调用 `pi-ai` 的 `streamSimple`/`completeSimple`，只把它放在 `provider-client-pi.ts` 这一处。
* 复刻当前已验证的语义：多 tool call、tool result、streaming delta、provider failure projection、abort、resume 时丢弃未提交 assistant。
* 删除 `restoreIrisPiHistory()` 和所有 `toPiHistoryMessage()`；runner 直接消费 `AgentHistorySnapshot` / `buildAgentContext()`。
* 通过后从 `package.json` 删除 `@earendil-works/pi-coding-agent`，显式声明需要的低层 provider 包（若选择过渡路线）。

#### 阶段 2：替换 provider runtime

* 以现有的 OpenAI-compatible 和 Anthropic-compatible 两种协议为第一范围，实现 fetch + SSE parser；先不扩展 Pi 当前支持的 Bedrock、Google、Mistral 等 provider。
* 将请求/响应映射固定在 adapter 内：tool schema、thinking、usage、finish reason、错误正文、retry-after、HTTP 状态和取消信号都转成 Iris contract。
* 把 provider profile 的模型发现、手工模型、连接验证、API key 保存和删除全部迁移到 Iris user data；旧 Pi `auth.json` 只做一次读取迁移，然后停止写入。
* 完全删除 `@earendil-works/pi-ai`、`pi-agent-core`、`pi-client`、`pi-protocol`、`pi-telemetry` 及其嵌套依赖和 license override。

#### 阶段 3：数据与发布收口

* 删除所有 `Pi` 命名、Pi prompt fingerprint 兼容注释和 worker check 中的 Pi 版本断言。
* 更新第三方 notices、lockfile、协议版本和诊断字段。
* 对旧 Session 做一次只读加载验证，确认没有任何持久化字段依赖 Pi message shape。
* 执行类型检查、Agent/协议专项测试、全量单 worker 测试；按项目约束不运行 build/dist 或开发服务器。

### 风险和取舍

* **最大风险是 provider 行为回归，不是领域数据迁移。** 特别是 Anthropic/OpenAI 两种 tool-call 流式格式、thinking block、错误重试和中断恢复。
* **直接使用官方 SDK 的取舍**：减少 SSE/request 代码，但会把 SDK 的类型和错误模型带入 Iris；OpenAI-compatible/Anthropic-compatible 端点仍需额外适配。使用 fetch 自实现协议更彻底，但测试量更大。
* **支持范围应先收窄。** 第一版完整移除只承诺当前 UI 已暴露的 OpenAI/Anthropic 两类 API；Pi 原本内置但 Iris 没有产品入口的 provider 不应成为迁移阻塞项。
* **不要在阶段 1 重做 compact、Trace、Context 或 tool host。** 它们已经是 Iris 自己的稳定边界，重做会扩大风险且无法帮助移除 Pi。

### 验收标准

* [ ] 生产源码（测试和脚本除外）不再直接 import `@earendil-works/pi-coding-agent`。
* [ ] `AgentExecutionRunner` 能覆盖 Send、Resume/Retry、Abort、Provider pause、多个 tool call、worker 重启恢复和 durable event 顺序。
* [ ] Trace/Context、Intent/Turn/Invoke、effect/artifact 和 rewind 的持久化结果与迁移前一致。
* [ ] OpenAI Responses 与 Anthropic Messages（含兼容端点）通过真实协议 fixture：文本流、tool call、tool result、usage、错误、超时、取消、重试。
* [ ] 旧 Pi 凭据可迁移或明确提示重新配置；新版本不再写入 Pi agent 目录。
* [ ] `npm ls` 中不存在任何 `@earendil-works/pi-*` 包；third-party notices 和 lockfile 已收口。
* [ ] `npm run typecheck -- --pretty false`、Agent/协议专项测试和全量单 worker 测试通过；不运行 build/dist 或开发服务器。

### 本轮调研判断

Pi 不是 Iris 的领域核心，当前更像一个被 Iris 包装得很薄的“执行器 + provider SDK”。因此移除是可行的，且不需要推翻前两份架构设计；真正的工作量集中在执行循环和 provider 协议兼容。推荐先完成阶段 0，再以阶段 1 的独立提交验证“没有 Pi Agent/Session 也能运行”，最后决定是否继续阶段 2 的完全去 Pi 化。当前 issue 先保持 `In Progress`，下一步应从阶段 0 的接口和现状测试基线开始，而不是直接删除依赖。

## 阶段 2 评估：彻底替换 `pi-ai` Provider runtime（2026-09-06）

### 先给结论

彻底替换 `pi-ai` 是一个 **Provider 基础设施重写**，不是一次普通依赖清理。第一终点已经解决了真正的领域架构问题：Pi 不再拥有 Iris 的 Agent、Session、Trace、Context、Intent、Turn 或 ToolHost 语义。继续移除 `pi-ai` 的收益主要是控制供应商协议、凭据、依赖链和发布节奏；它不会进一步改变 Iris 的领域模型。

按当前产品范围估算：

* **当前范围 MVP（OpenAI Responses + Anthropic Messages + 两类兼容端点）**：1 名熟悉代码的工程师约 **4-8 周**，其中 2-4 周实现，2-4 周协议 fixture、取消/重试、回归和发布收口。
* **完整复刻 Pi 的 Provider 能力**（Google、Mistral、Bedrock、OAuth、各类兼容 flags 和模型目录）：约 **8-12 周起**，之后还要持续跟随供应商协议和 Pi 上游变化。
* **内化/复用 Pi 代码但删除 `@earendil-works/pi-ai` 依赖**：当前范围约 **3-6 周**；如果同时要求删除所有官方 SDK 和代理/遥测依赖，工作量会逐渐收敛到上面的纯自研范围。

因此，除非 Iris 已经明确要长期拥有 Provider SDK 的维护责任，否则没有必要立即做完整替换。推荐先保持当前 runtime，同时把 Iris-owned Provider contract 固定下来；需要去依赖时优先评估第三方案，再决定是否把协议实现逐步改成 Iris 自研。

### 三条路线

| 路线 | 做法 | 首次工程量 | 长期成本 | 适用判断 |
| --- | --- | --- | --- | --- |
| 方案一：继续依赖 | 保持 `@earendil-works/pi-ai`，只允许 `provider-runtime-pi-ai.ts` 这一处接触它 | 0-1 周整理边界 | 低到中，受 Pi 发布节奏和依赖链影响 | 当前最稳妥的默认方案 |
| 方案二：纯自研协议 runtime | Iris 自己实现 Provider contract、请求构造、SSE、增量归一化、凭据、模型发现和重试 | 当前范围 4-8 周；完整 parity 8-12 周起 | 高，所有 Provider 行为差异由 Iris 维护 | 需要完全控制隐私、协议和供应商生命周期时采用 |
| 方案三：内化/复用 Pi 实现 | 从 Pi 源码或 source map 提取 OpenAI/Anthropic 所需模块，放入 Iris 自有目录，删掉 npm 包和未使用 Provider 分支 | 当前范围 3-6 周 | 中到高，需要自行合并上游修复并维护版权/notice | 想先去掉运行时依赖、又不想立刻重写全部协议时采用 |

### 方案二需要重写的真实边界

不能只替换 `streamSimple()`。至少需要定义并测试以下 Iris-owned contract：

* `stream(request, signal, hooks)` 和 `complete(request, signal)`，输出文本、thinking、tool-call 参数增量、usage、stop reason、最终 assistant message 和规范化错误。
* OpenAI Responses、Anthropic Messages 及兼容端点的请求体、认证头、SSE 事件和 tool-call JSON 增量拼接。
* HTTP 状态、错误正文、`retry-after`、网络失败、超时、AbortSignal 和 provider pause 的一致语义。
* 模型目录、手工模型、连接验证、上下文窗口/最大输出元数据和 profile 映射。
* API key 的读取、保存、删除；旧 `~/.pi/agent/auth.json` 的一次性迁移或明确的重新配置提示。
* provider payload capture、敏感信息脱敏以及 compact/supervision 使用的单次 `complete` 调用。

最大风险是行为回归而不是 Session 数据迁移：Anthropic/OpenAI 的 tool-call 流、thinking block、usage、取消和重试最容易出现“能调用但 durable event 不一致”的问题。验收必须使用协议 fixture 覆盖文本流、多个 tool call、tool result、错误、超时、取消、重试和 malformed stream，并验证持久化 Trace/Turn/Invoke 结果与当前实现一致。

### 方案三为什么不是简单复制

`@earendil-works/pi-ai@0.84.1` 的许可证是 MIT，当前 notices 已记录它；法律上可以复用，但必须保留版权和许可证文本。技术上 npm 包主要发布 `dist`，source map 含有 `sourcesContent`，可以提取源码；应优先从 Pi 上游源码仓库建立一个可追溯的内化快照，而不是把编译后的大 bundle 直接复制进 Iris。

内化时至少要剥离：

* Pi 的全局 Provider 注册和未使用的 Google、Mistral、Bedrock 等实现；
* OAuth、Pi credential store、Pi telemetry、CLI 和模型生成脚本；
* `pi-ai` 的 `Model`/`Context` 类型对 Iris 业务的渗透，改成 Iris-owned 类型；
* 不需要的官方 SDK、代理实现和跨 Provider 兼容分支。

内化的收益是保留已经验证过的协议解析细节，缩短第一版风险窗口；代价是 Iris 会承担一份 fork：上游修复不会自动进入，供应商协议变化需要自行 cherry-pick 或重做。若只复制 `dist` 而不建立上游版本、来源、差异和测试记录，短期看似去依赖，长期会形成不可维护的隐性分叉。

### 推荐决策与执行顺序

1. 保持当前 `pi-ai` adapter，不把 Pi 类型扩散到 `worker`、profile 或持久化层。
2. 先完成 Iris-owned `provider-contract.ts` 和协议 fixture；用当前 `pi-ai` 实现作为一个可替换后端。
3. 若目标只是减小依赖和供应链暴露，优先实施方案三：只内化当前 UI 暴露的 OpenAI/Anthropic 两类协议，并保留明确的 MIT attribution 和上游 commit 标记。
4. 若目标是完全控制协议行为、取消、重试和凭据格式，再从同一个 contract 替换为方案二的 fetch + SSE 实现；不要同时扩展 Provider 数量。
5. 只有在新 runtime 通过真实协议 fixture、Agent 回归和旧凭据迁移验证后，才删除 `@earendil-works/pi-ai` 及其嵌套依赖，并更新 lockfile/notices。

**本轮判断：** 彻底去掉 `pi-ai` 有明确的架构纯度和供应链收益，但不是当前 Iris 交付的必要条件。方案一是默认；方案三是“想去 npm 依赖但控制工程量”时的折中；方案二只在 Iris 愿意长期维护 Provider SDK 时值得投入。当前 issue 继续保持 `In Progress`，下一步应先冻结 Provider contract，而不是立即重写所有 Provider。

## 最终决策与当前成熟度（2026-09-06）

### 决策

采用 **方案一：继续使用 `@earendil-works/pi-ai@0.84.1`**。不再为替换 Provider runtime、内化 Pi 代码或清理这部分依赖安排额外工程。当前 adapter 边界已经足够，后续只有出现明确产品需求、供应链要求或 Provider 行为控制需求时，才重新打开阶段 2。

### 成熟度判断

* **Iris Agent 领域边界：高。** Agent/Session/Trace/Context/Intent/Turn/Invoke/ToolHost 已由 Iris 掌控，Pi 不再是持久化领域模型或业务状态机的所有者。
* **执行器可靠性：中高，可进入 beta。** Iris-owned runner 已覆盖 Send、Resume/Retry、Abort、多 tool call、tool result 回填、provider failure 投影和 durable event 顺序；Agent 专项 111 项测试通过。
* **Provider 能力：中高，依赖 `pi-ai` 的生产成熟度。** OpenAI/Anthropic、兼容端点、流式文本、thinking、tool-call、usage、错误、代理和凭据路径均保留现有实现；Pi 的 Provider runtime 仍是唯一外部运行时风险。
* **发布验证：接近 beta，不宣称全绿。** 类型检查通过；Pi adapter、worker-host、tool-host 定向测试 31 项通过；全量 Vitest 为 500 项中 499 项通过。唯一失败是未修改的 renderer 测试 mock 缺少 `window.removeEventListener`，与本次 Agent/Pi 改动无关，但在发布前仍应单独修复或明确隔离。

### 当前已知边界（接受为方案一的成本）

* `pi-adapter.ts` 和 `createIrisPi*` 的兼容命名仍存在，但不影响领域所有权或运行行为。
* Provider 凭据仍沿用 Pi `auth.json` 兼容格式；这是运行时实现细节，不是 Iris Session 数据格式。
* `pi-ai` 依赖链仍包含多个 Provider SDK 和 Pi telemetry；在采用方案一的前提下属于有意接受的供应链成本。
* 本次验证没有运行 build、dist 或开发服务器，符合项目约束；因此“可进入 beta”基于类型检查和测试基线，不等同于发布包验收完成。

**最终结论：** 当前成熟度足以停止 Pi Provider 迁移工作。Iris 已经完成必要的架构脱钩，继续保留成熟的 `pi-ai` Provider runtime 是成本最低、风险最小且符合当前产品目标的选择。

本节最终决策覆盖前文“保持 `In Progress`、继续冻结 Provider contract”的阶段性判断；该调研 issue 现已完成。
