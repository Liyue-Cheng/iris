## 背景

2026-08-09 对近期密集开发进行了一轮只读审计。范围为 `main` 相对
`origin/main` 多出的 31 个提交以及当时 140 个工作区变更，合计约 213 个
文件、`+23236/-5021`。

审计重点不是代码风格，而是 workaround、并发边界、数据安全和职责不清的
实现。当前结论是不宜在处理高风险项前直接合并或发布。

## 高风险问题

### 删除文档会丢弃未保存草稿

`DeleteDocDialog` 直接执行 `doc.delete`，没有调用统一的
`editorStore.flushBeforeSwitch`。文件 unlink 事件随后关闭编辑会话。关闭自动
保存、保存失败或快速确认删除时，当前草稿不可恢复。

相关位置：

- `src/renderer/components/doc/DeleteDocDialog.tsx:87`
- `src/renderer/components/doc/DocContextMenu.tsx:63`
- `src/renderer/stores/editor-store.ts:433`

### 项目设置 CAS 不具备原子并发语义

`updateProjectSettings` 执行“读取 revision、修改、临时文件 rename”，但主进程
没有按文件串行化。提示词写入和工具栏写入还使用不同的 FrontCPU 资源；不同
窗口也拥有独立 pipeline。两个写入可以同时通过相同 revision 检查，随后发生
后写覆盖先写，Windows 下也可能表现为 `EPERM`。

相关位置：

- `src/main/project-settings.ts:406`
- `src/renderer/cpu/isa/agent-isa.ts:115`
- `src/renderer/cpu/isa/project-isa.ts:105`

### 语言切换可能清空其他窗口的 WYSIWYG 草稿

语言变化会重建 Crepe 编辑器，但重建输入是 `session.originalBody`，不是当前
`bodyCurrent`。hydration 随后又把旧正文写成 baseline/current，导致 dirty 状态
和草稿一起消失。本窗口进入设置页前可能完成保存，但全局设置广播会影响仍在
编辑的其他窗口。

相关位置：

- `src/renderer/components/doc/CrepeEditor.tsx:68`
- `src/renderer/components/doc/DocView.tsx:166`
- `src/renderer/lib/editor-session.ts:58`
- `src/renderer/stores/settings-store.ts:44`

### 文档 API 的路径边界不防 symlink/junction

`ProjectManager.resolveInside` 只检查规范化字符串前缀。读、写、创建和删除文档
均未验证父目录的 realpath。若 `.iris` 或 typed folder 是指向项目外的 junction，
文档操作可能实际落到项目外，删除操作甚至可能把外部文件移入回收站。资产模块
已有 realpath 防护，说明当前边界实现不一致。

相关位置：

- `src/main/project-manager.ts:203`
- `src/main/project-manager.ts:301`
- `src/main/project-manager.ts:405`
- `src/main/project-manager.ts:739`
- `src/main/project-manager.ts:779`

### 重复关闭可以绕过编辑器 flush

窗口第一次收到 close 事件时，在 flush 完成前就设置 `flushed = true`。等待保存
期间再次触发 close，第二次事件会把“正在 flush”误当成“已经 flush”，直接进入
确认和后端清理流程。

相关位置：

- `src/main/app-main.ts:348`

### Agent hook 写入可能覆盖用户配置

安装和移除 hook 都对用户拥有的 CLI 配置执行 read-modify-`writeFile`，没有原子
替换、revision 检查或主进程锁。另一窗口或 CLI 同时修改配置时，无关设置可能被
覆盖；进程异常时也可能留下截断 JSON。现有测试只覆盖纯内存的 handler 删除。

相关位置：

- `src/main/agent-injection.ts:401`
- `src/main/agent-injection.ts:488`

## 功能正确性问题

### Git porcelain 状态模型被压成单组

当前解析器逐个 NUL 片段处理，并根据二维状态的一个字符把文件放入单一 group。
这会导致：

- `MM`、`AM` 等文件的未暂存部分不可见；
- rename/copy 的第二个 NUL 路径被误当成新的状态记录；
- unborn repo 的分支名解析错误；
- unborn repo 使用 `git reset HEAD` 无法 unstage。

相关位置：

- `src/main/git-manager.ts:80`
- `src/renderer/components/git/ResourceRow.tsx:73`

### 项目切换期间可能吞掉新项目的文件事件

`scanInFlight` 和 `scanDirty` 是跨项目模块全局变量。A 项目扫描期间切到 B 后，
B 的首个文件事件只设置 dirty；A 的过期响应因 scope 不匹配直接 return，最终不
会为 B 执行 follow-up scan。

相关位置：

- `src/renderer/stores/project-store.ts:70`
- `src/renderer/stores/project-store.ts:254`

### Git watcher 漏掉深层文件

Git watcher 固定使用 `depth: 2`，无法观察 `src/renderer/components/...` 等深层
路径。内置终端修改深层文件时窗口不会失去并重新获得焦点，Source Control 面板
可能一直保持旧状态，直到手动刷新。

相关位置：

- `src/main/git-manager.ts:38`

### 资产 Markdown URL 重写依赖脆弱字符串定位

代码已有 remark AST 节点和 offset，却仍在节点原文中使用 `indexOf(source)`。
例如 `[foo](foo)` 会首先命中链接文字而不是 URL，操作可能报告成功但 URL 未被
替换，并留下孤立的受管资产。

相关位置：

- `src/main/asset-manager.ts:434`

## 结构债务与 workaround

- `SettingsView.tsx` 接近 1900 行，同时承担全局设置、agent/hook、项目设置、
  提示词冲突治理和工具栏编辑，模块边界已经失效。
- 终端重放依赖 xterm 私有 `_core`，升级依赖时存在高回归风险：
  `src/main/session-manager.ts:655`、
  `src/renderer/components/terminal/TerminalView.tsx:576`。
- `SessionManager.reanchor` 只改变 UI anchor，不改变进程启动时注入的
  `FOCUS_DOC`，并明确依赖用户后续向 agent 解释，属于协议语义与显示状态分离的
  workaround：`src/main/session-manager.ts:422`。
- preload 注释称 IPC 能力经过白名单控制，实际 `invoke/on` 接受任意字符串；
  机器级写操作的“用户确认”目前只是 renderer UI 约定，不是主进程能力边界：
  `src/preload/index.ts:27`。
- `parseProjectRootFromArgv` 用无路径边界的 `startsWith` 排除临时目录，并把
  `PORTABLE_EXECUTABLE_DIR` 整个目录视为临时区，可能误拒绝 portable exe 同目录
  下的真实项目：`src/main/app-main.ts:72`。
