Uncaught (in promise) Error: Error invoking remote method 'session:open': ProjectError: \[ProjectManager] WriteFailed: Synchronize the participating agent entry files before starting a terminal

## 2026-08-11 排查结论

这是两个问题叠在一起，不应只当成一条报错文案来修：

1. 主进程的会话启动门禁拒绝了一个当时不满足一致性要求的项目，这是预期的保护行为。
2. renderer 没有承接这次拒绝，导致完整错误只以 `Uncaught (in promise)` 出现在 DevTools，用户点击后 UI 毫无反应。这是明确的产品缺陷。

### 这条报错实际表示什么

`session:open` 在创建 PTY 前会调用 `ProjectManager.assertProjectSettingsReady()`（`src/main/ipc.ts:679-701`、`src/main/project-manager.ts:713-731`）。对已经初始化 `.iris/` 的项目，它要求：

- `.iris/settings.json` 可读且迁移没有冲突；
- `agentContext.entries` 中每个参与入口的 `<iris-software>` 块都为 `ok`；
- 每个入口的 `<iris-project>` 块都与 `.iris/settings.json` 中的 canonical project prompt 同步。

任一入口缺失、漂移、重复或写入失败，都会被压成同一条 `WriteFailed: Synchronize...`。所以它能说明“报错发生时参与入口不健康”，却不能说明是哪个文件、哪一层、哪一种状态。这个诊断信息损失本身也是问题。

当前项目配置的参与入口是 `AGENTS.md` 和 `CLAUDE.md`。按解析器使用的“独立行首标签”规则复核当前磁盘：两边各有一个受管 software block，内容相同；两边各有一个 project block，内容也相同。`CLAUDE.md` 第 4 行的标签样文字位于引用行中，不会被 `src/main/software-prompt.ts:31-39` 的解析器识别成受管块。当前状态看起来已经同步，无法从现有通用错误反推出当时具体漂移的是哪一个入口。主进程日志也没有记录 IPC handler rejection 的状态快照。

这里还暴露出一个不同的治理风险：`CLAUDE.md:3-134` 残留了一份旧协议正文，起始标签混在引用行中，因此被解析器视为受管块之外的 foreign prose。它不是本次 `WriteFailed` 的直接原因，受管块同步也不会删除它；但 Claude 读取整份入口文件时仍可能同时收到新旧两套互相冲突的规则。也就是说，当前健康检查只证明“受管投影正确”，不能证明入口文件的实际 agent context 没有陈旧副本。

结合流程，常见触发时机是内置协议模板或 `.iris/settings.json` 已变化，而入口文件尚未来得及/未能重新投影。当前仅在项目打开或 renderer 恢复时调用一次 `offerPromptProjectionRepair()`；提示被取消、提示自身失败、或项目打开后再次漂移，都可能一直拖到用户点击“启动终端”才暴露。

### 为什么 UI 会吞掉它

调用链是：

```text
RightPane.spawn
  -> void openSession/openWorkspaceSession
  -> pipeline.dispatch('session.open')
  -> ipcExecutor
  -> window.api.invoke('session:open')
  -> main assertProjectSettingsReady() throws
  -> Promise rejection 原样返回 renderer
  -> 无 catch、无错误状态、无通知
  -> Uncaught (in promise)
```

关键位置是 `src/renderer/components/layout/RightPane.tsx:131-134` 和 `src/renderer/lib/session-actions.ts:21-80`。`front-cpu`、IPC executor 与 preload 都只是透传 rejection；代码库也没有 renderer 级 `unhandledrejection` 兜底或 React Error Boundary。因此这里不是 Electron 把错误吃掉，而是 UI 主动用 `void` 放弃了一个仍可能 reject 的 Promise。

### 全面审计结果

本次检查覆盖了 renderer 中全部 `window.api.invoke`、`pipeline.dispatch`、`catch`、floating Promise，以及 main 侧 watcher 和全局异常出口。

#### P0：用户明确操作失败但没有任何 UI 反馈

- 会话启动、关闭：`RightPane`、`LensTree` 多处 `void openSession/openWorkspaceSession/closeSession`，包括本次报错。关闭失败也会表现为点了没反应。
- issue 状态修改：`TypedHeader.tsx:124-131`、`IssuePanel.tsx:288-294` 丢弃 `setDocStatus` rejection。涉及关联终端关闭或文档 CAS 写入失败时没有反馈。
- todo 勾选：`TodoPanel.tsx:63-80` 仅用 `finally` 清 spinner，rejection 继续成为未处理 Promise，用户不知道为什么没有勾上。
- “用默认程序打开/在目录中显示”：`DocContextMenu.tsx:47-65`、`AssetPanel.tsx:250-268` 丢弃 shell verb rejection。
- 剪贴板：`clipboard.ts:11-31` 明确把异常转成 `false`/空字符串，但绝大多数调用方又忽略返回值。复制失败和“剪贴板本来为空”无法区分。
- renderer 启动：`index.tsx:15-59` 最终 `void bootstrap()`，初始化设置、bootstrap IPC 或渲染前 hydration 一旦 reject，可能直接白屏且只有控制台错误。

#### P1：应用会进入陈旧/降级状态，但用户无从知道

- 项目文件变化后的重扫失败只 `console.warn`：`project-store.ts:326-356`。树、todo、状态和编辑器投影可能停留在旧数据。
- 手动 rescan/raw tree 失败也只 `console.warn`：`project-store.ts:497-542`。
- renderer reload 后 session hydration 失败只 `console.warn`：`session-store.ts:216-232`，右栏可能暂时看不到主进程仍存活的会话。
- prompt 健康检查在 `index.tsx:49` 以 floating Promise 运行；检查或修复失败本身仍可能 `Uncaught (in promise)`。而且没有项目打开后的常驻健康状态。
- 终端文件拖入、文档拖入失败只 `console.warn`：`TerminalView.tsx:259-319`。
- 终端字体滚轮设置、主题切换直接丢弃 settings update rejection：`TerminalView.tsx:389-397`、`TitleBar.tsx:115-120`。界面可先变、持久化实际失败。
- 终端输入和 resize 直接 floating invoke：`TerminalView.tsx:615-628`、`700-711`。连续输入不适合每次弹窗，但也不能制造 unhandled rejection；至少应去重上报会话失联并触发状态自愈。
- 编辑器 watcher 对打开文档的重读失败直接返回：`editor-store.ts:427-437`。用户可能继续在过期基线上编辑。

#### P1：main 侧错误只落日志，renderer 没有状态通道

- `GitManager.open()` 创建 chokidar watcher 后没有监听 `error`（`src/main/git-manager.ts:38-43`）。本机 `~/.iris-dev/logs/main-debug.log` 和 `~/.iris/logs/main-debug.log` 在 2026-08-11 已多次记录 `.git/index.lock` 的 `EPERM` unhandled rejection。全局 `process.on('unhandledRejection')` 只写日志，不通知窗口，Git 投影可能停止刷新而 UI 不知情。
- `ProjectManager` watcher 虽有 `error` listener，但也只 `logger.warn`（`project-manager.ts:941-947`），没有向对应窗口广播 degraded 状态。
- preload 的 `invoke` 直接使用 Electron rejection（`src/preload/index.ts:27-30`）。`ProjectError.code` 等结构化字段跨边界后不可依赖，renderer 最终只能解析带有 Electron 前缀的 message；这使“重新同步”“打开设置”等针对性恢复动作无法稳健实现。

#### 可以保留静默/日志降级的场景

- 临时文件、回滚和 watcher close 的 best-effort 清理；
- `exists/stat/realpath` 用异常表达“不存在”的探测；
- Git HEAD 不可用时隐藏 freshness 比较；
- Markdown 图片读取失败后显示明确的图片失败占位；
- 终端 scrollback 回放失败后仍切到 live stream；
- 进程退出阶段的幂等清理。

这些失败不会让用户刚发出的命令无声失效，或已有可见降级，因此不应与上述 P0/P1 一刀切地全部弹窗。

### 建议的整体方案

不要在每个 `void` 后随手补一个 `alertDialog`。这会把问题从“无反馈”变成“弹窗风暴”，尤其是输入、resize、watcher 和批量操作。应建立一套明确的错误契约和展示分层。

1. **先保真传输。** IPC 统一返回或抛出可序列化的 `AppError`：至少包含 `domain`、`code`、用户可读 `message`、可选 `details`、`recoverable`、`correlationId`。main 保留原始 stack 到日志；renderer 不解析字符串。prompt 未就绪应使用专门 code，并携带不健康入口及状态。
2. **建立用户操作边界。** 提供统一 `runUserAction`/action controller，负责 pending、错误归一化、日志和展示。事件 handler 可以 `void` 调这个“保证 resolve”的边界，但不能直接 `void` 一个会 reject 的业务 Promise。
3. **按上下文展示。** 表单/编辑器写入失败用就地错误；离散命令失败用可排队、去重的 notification；阻断工作流且可恢复的错误用 action dialog；后台投影失效用持久 banner/状态指示，恢复后自动消失。现有 `alertDialog` 是单例覆盖模型，新 alert 会直接结算旧 alert，不适合作为全局错误队列。
4. **为本次场景做专门恢复。** `session.open` 收到 `PromptNotReady` 时，界面应列出具体入口和状态，并提供“全部重新同步”和“打开设置 > 软件提示词”动作；同步成功后可由用户再次启动，或明确地自动重试一次。不能只显示原始 `Synchronize...`。
5. **补全后台健康信号。** Git/project watcher、project scan、session hydration 都应有 per-window health state/event；错误去重后展示，下一次成功刷新时清除。终端高频 I/O 失败只上报一次 session disconnected，并触发 session list 自愈。
6. **最后加兜底和静态约束。** renderer 安装 `unhandledrejection`/fatal bootstrap fallback，只用于捕获遗漏并记录/显示通用故障，不能替代局部错误处理。引入 type-aware `no-floating-promises`（或同等检查）；允许 `void` 的函数必须在类型/命名上保证内部已处理 rejection。

### 建议实施顺序

- [ ] P0：为 `session.open/close` 增加结构化错误与 action dialog，覆盖当前复现路径。
- [ ] P0：给 status、todo、shell、clipboard 这些明确用户手势接入统一 action boundary。
- [ ] P0：增加 bootstrap fatal fallback，保证初始化失败不白屏。

- [ ] P1：治理终端输入/resize/drop、主题/字体持久化等高频或乐观操作，避免 unhandled rejection，并定义一次性降级反馈。
- [ ] P1：单独迁移/清理 `CLAUDE.md` 中解析器边界外的旧协议副本，并为“受管块外疑似 Iris 协议残留”增加诊断，避免健康状态与 agent 实际读取内容不一致。
- [ ] P2：补 type-aware floating Promise 检查和 renderer `unhandledrejection` 遥测兜底。
- [ ] 测试：断言上述用户手势 rejection 后 UI 有可见反馈、pending 会复位、不会产生 `unhandledrejection`。
- [ ] 测试：prompt 漂移时展示具体文件/状态，“全部重新同步”成功与失败都可恢复。
- [ ] 测试：watcher/scan/session hydration 失败进入 degraded 状态，后续成功会清除状态且不会重复刷通知。

## 2026-08-11 全面整改设计

下面是对前述清单的完整架构设计。目标不是保证“所有错误都弹出来”，而是建立一个可验证的不变量：**任何会影响用户意图或当前数据可信度的失败，都必须被分类、保真传输、记录，并在正确的 UI 上下文中可见；预期取消和无害降级则不能制造噪声。**

### 设计边界

本方案负责：

- main、preload、renderer 之间的错误契约；
- 用户命令、projection query、后台 watcher、中断和终端高频 I/O 的不同错误策略；
- 错误展示、恢复动作、健康状态、日志关联与兜底；
- 逐步迁移现有调用点，并用静态规则阻止回退。

本方案不做：

- 不把所有 `catch` 都改成弹窗；
- 不让 main 决定具体 UI 组件或按钮文案；
- 不把业务错误展示塞进 `front-cpu`；
- 不通过解析 `Error.message` 判断业务分支；
- 不把 stack、文档正文、终端输入等敏感/大体积内容发送到 renderer 或写进通用诊断。

### 总体架构

```text
renderer user gesture                     main background service
        |                                          |
        v                                          v
runUserAction / attemptAction              watcher catches locally
        |                                          |
        v                                          v
pipeline.dispatch or query                 health event + structured log
        |                                          |
        v                                          |
ipcExecutor ---- correlationId                     |
        |                                          |
        +------ window.api.invoke -----------------+
                         |
                         v
              typed IPC request envelope
                         |
                         v
                registerIpcHandler
                  |             |
               success       catch/normalize
                  |             |
                  +------ typed IPC result
                                |
                                v
                    preload validates + unwraps
                                |
                          RemoteAppError
                                |
               +----------------+----------------+
               |                                 |
        contextual action UI              health/notification store
```

职责必须保持单向：

- 领域代码产生有语义的错误；
- IPC boundary 保证字段不丢并记录一次；
- action boundary 保证 Promise 被消费并选择展示策略；
- UI 根据错误 code 和当前操作上下文提供恢复动作；
- 全局兜底只捕捉架构遗漏，不能成为正常业务错误出口。

### 一、统一错误模型

建议在 `src/shared/app-error.ts` 定义跨进程稳定契约：

```typescript
export type AppErrorDomain =
  | 'app'
  | 'settings'
  | 'project'
  | 'prompt'
  | 'document'
  | 'asset'
  | 'git'
  | 'session'
  | 'shell'
  | 'clipboard'
  | 'ipc'
  | 'internal';

export interface SerializedAppError<TDetails = unknown> {
  version: 1;
  incidentId: string;
  requestId: string;
  correlationId?: string;
  domain: AppErrorDomain;
  code: string;
  message: string;
  details?: TDetails;
  retryable: boolean;
}

export type IpcResult<T> =
  | { ok: true; value: T }
  | { ok: false; error: SerializedAppError };
```

字段约束：

- `domain + code` 是程序判断依据，发布后保持兼容；现有 `ProjectError`、`GitError` 等 code 可以先原样映射，避免第一阶段大改全部领域错误。
- `message` 是安全的用户可读 fallback，不包含 stack；标题、恢复动作和通用说明由 renderer 根据 code 本地化。
- `details` 必须按 code 定义具体类型，不能塞任意 Error 或 payload。路径、冲突 revision、异常入口列表可以传；文档内容、终端字节和密钥不能传。
- `retryable` 只表达底层操作能否安全重试，不代表 UI 必须展示“重试”。
- `incidentId` 标识一次失败，便于用户复制诊断；`requestId` 标识一次 IPC；`correlationId` 复用 front-cpu 指令上下文。
- 严重程度和展示方式不放进 remote error。相同的 `document.WriteConflict` 在自动保存中应内联，在关闭窗口时可能需要阻断对话框，决定权属于调用上下文。

main 侧提供一个基础 `AppError`，各领域错误继承或由 adapter 映射。未知异常统一归一为 `internal.Unexpected`，原始 stack 只写 main 日志。不要为了统一模型一次性删除现有领域类；先让它们实现可映射接口，再逐步收敛重复 code。

取消必须成为非错误终态：用户取消目录选择、关闭确认框、front-cpu instruction cancellation 都映射为 `cancelled` outcome，不进入 notification，也不计入错误率。超时则是错误，统一为 `operation.Timeout`，并保留 correlation 信息。

### 二、IPC 保真传输

Electron 对 thrown Error 的自定义字段保留没有可靠契约，因此不能继续依赖 `ipcMain.handle` 直接 throw。建议新增 `registerIpcHandler(channel, handler)`：

1. preload 为每次调用生成 `requestId`，把业务 payload 包进 typed request envelope；
2. `ipcExecutor` 使用 `ExecutorFn` 的第三个 `context` 参数，把 `context.correlationId` 一并传给 preload；
3. main wrapper 解包后调用现有 handler；
4. 成功返回 `{ ok: true, value }`；
5. 失败在 wrapper 中 normalize、记录一次，再返回 `{ ok: false, error }`，不让业务异常逃出 Electron handler；
6. preload 校验 result envelope，失败时抛出 renderer 可识别的 `RemoteAppError`；现有上层仍可使用 Promise rejection，但 rejection 已保留 code/details。

请求元数据与业务 payload 分离，不能往现有 payload 上偷偷增加 `__meta`，否则会污染项目 scope 校验和结构化类型。建议形态为：

```typescript
interface IpcRequest<P> {
  meta: {
    requestId: string;
    correlationId?: string;
  };
  payload: P;
}
```

迁移不要求一次性改完全部 channel。preload 在过渡期可以同时识别 envelope 与 legacy raw result；legacy rejection 统一归为 `ipc.LegacyRemoteError`，但不能提供业务恢复。main 按 domain 分批替换注册方式。迁移完成后，CI 扫描禁止 `src/main/ipc.ts` 直接新增 `ipcMain.handle`，并删除 preload 的 legacy 分支。

日志边界规则：

- domain error 构造时不记录，避免同一个错误被多层重复打日志；
- `registerIpcHandler` 是 remote request 的唯一错误日志点，记录 channel、window id、project scope、request/correlation/incident id 和 stack；
- 不记录完整 payload；可为每个 channel 声明安全摘要函数，例如只记录 `docPath` 或 session id；
- renderer 本地错误通过专用、限频的 `reportRendererError()` preload 能力发送，不能暴露任意 `ipcRenderer.send`；
- notification 展示短 incident id，并提供“复制诊断信息”，但不展示 stack。

### 三、renderer 用户操作边界

建议提供两个互补 API，而不是让每个组件手写 `try/catch`：

```typescript
type ActionOutcome<T> =
  | { status: 'ok'; value: T }
  | { status: 'cancelled' }
  | { status: 'failed'; error: UiAppError };

attemptAction<T>(operation: () => Promise<T>): Promise<ActionOutcome<T>>;

runUserAction<T>(options, operation): Promise<ActionOutcome<T>>;
```

- `attemptAction` 只归一化并保证永不 reject，供已有内联错误状态的 dialog/store 使用。
- `runUserAction` 在此基础上管理 notification/action dialog、去重、恢复动作和可选 pending callbacks，同样保证永不 reject。
- 低层 lib/store 不得直接弹 UI。它们只有两种合法语义：成功返回/失败 throw；或者把失败写进明确的 store state 并返回 outcome。`console.warn` 后假装成功不是合法语义。
- React event handler 可以 `void runUserAction(...)`，因为该函数的契约保证 Promise 已消费；不能 `void pipeline.dispatch()`、`void window.api.invoke()` 或 `void` 任意会 reject 的业务函数。
- 批量操作由最外层 action boundary 汇总失败，不能为每个元素弹一次。结果应说明成功数、失败数和首个/全部可查看错误。

`front-cpu` 继续负责指令调度、资源冲突、timeout、commit 和 correlation trace。它不知道当前 UI 是按钮、快捷键还是后台同步，因此不能承担错误展示。`ipcExecutor` 只做 transport 与 RemoteAppError 重建；真正的 surface policy 位于 `runUserAction` 调用点。

### 四、展示通道和规则

需要三种互不替代的 UI 通道：

| 场景 | 通道 | 行为 |
| --- | --- | --- |
| dialog/form 内提交失败 | inline error | 保留输入和 dialog，焦点移到错误摘要，允许重试 |
| 普通离散命令失败，如复制、打开、定位、关闭 session | notification | 非阻塞、可排队、同源去重，可带一个重试动作 |
| 阻断原始意图且存在明确恢复步骤 | action dialog | 展示原因和安全的恢复动作，例如“同步并启动” |
| 后台 projection/watcher 失效 | persistent health banner/indicator | 不因超时自动消失；成功恢复后清除 |
| 高频 session I/O 失联 | session-local disconnected state | 每个 session 只提示一次，停止继续刷相同错误并触发自愈 |
| renderer bootstrap/fatal render 失败 | fatal fallback | React 挂载前也能显示，提供重试/重载与复制 incident id |
| 预期取消、best-effort cleanup、已有可见 fallback | 无用户提示 | 需要时只记 debug/warn 日志 |

建议把当前 `confirm-dialog.tsx` 的“新请求覆盖旧请求”改成 FIFO dialog service。confirmation、alert 和 action dialog 可以共用调度队列，但使用不同 request type；任何 awaiter 都必须得到真实的用户选择，不能因为另一条错误到达而被伪装成已取消。

notification store 至少包含：`id`、`dedupeKey`、level、title、message、actions、sticky、occurrences、createdAt、incidentId。相同 `dedupeKey` 在窗口内合并计数，不重复弹出；同时最多展示少量通知，后续排队。后台健康故障不进入普通通知队列反复出现。

所有错误 UI 需要满足：

- `role="alert"` 或 `role="status"` 与正确的焦点策略；
- message 可换行、长路径可断行，不泄露 stack；
- 操作按钮使用明确动词，不能只有“知道了”；
- 一个错误最多有一个 primary recovery 和一个 secondary navigation，复杂处理进入对应设置页；
- 恢复成功后清除旧错误；恢复失败更新同一 incident UI，不叠加新弹窗。

### 五、后台健康模型

后台失败不是一次性通知，而是状态。建议新增 per-window `healthStore`，以 project scope/generation 隔离：

```typescript
type HealthDomain =
  | 'project-watcher'
  | 'project-projection'
  | 'git-watcher'
  | 'git-projection'
  | 'session-projection'
  | 'prompt-projection';

interface HealthIssue {
  key: string;
  domain: HealthDomain;
  state: 'degraded' | 'recovering';
  error: UiAppError;
  firstSeenAt: number;
  lastSeenAt: number;
  occurrences: number;
  scope: ProjectScope | null;
  retry?: () => Promise<void>;
}
```

规则：

- 第一次失败立即把内部状态标为 degraded；重复失败只更新 occurrence 和 lastSeen，不制造通知风暴。
- 对应操作下一次成功后显式 `resolve(key)`，不能依赖计时器自动消失。
- 项目切换后丢弃旧 generation 的 health event，避免 A 项目错误显示到 B 窗口。
- main watcher error 通过带 scope 的 `SERVICE_HEALTH_CHANGED` 广播；renderer 本地 scan/hydrate 错误直接写 health store。
- watcher 错误必须在源头监听，不能落到 `process.on('unhandledRejection')`。Git watcher 进入 degraded 后仍允许显式 `git status`，并以有上限的 backoff 尝试重建 watcher；成功后恢复 healthy。
- project watcher、Git watcher 与 projection query 是不同健康项：watcher 坏了表示未来可能不刷新，单次 status/scan 失败表示当前读失败，不能混成一个布尔值。
- health banner 只显示当前工作区域相关的最高优先项；标题栏提供汇总 indicator，点击可查看全部当前问题和 incident id。

### 六、本次 prompt/session 的目标流程

主进程仍是最终门禁，renderer 预检只能改善体验，不能替代 `assertProjectSettingsReady()`，否则预检和真正启动之间仍有 TOCTOU。

`assertProjectSettingsReady()` 应抛专门的 `prompt.NotReady`，details 为：

```typescript
interface PromptNotReadyDetails {
  repairable: boolean;
  issues: Array<{
    layer: 'settings' | 'software' | 'project';
    path?: string;
    state: string;
    message?: string;
  }>;
}
```

会话启动失败后的 UI：

1. action dialog 列出具体入口、层和状态；
2. `repairable=true` 时 primary action 为“同步并启动”，明确说明会重写受管块；
3. primary action 依次执行 `prompt.sync-all` 和原始 `session.open`，最多自动重试一次，并复用同一个 user action id；
4. secondary action 为“打开设置 > 软件提示词”；
5. conflict、invalid settings 或疑似受管块外协议残留时不提供自动覆盖，只导航设置页；
6. 用户取消不报错，原始 launcher 保持可再次点击；
7. 同步或重试失败时更新原 action dialog，显示新的结构化错误和 incident id。

prompt 健康状态还应在项目打开、`PROMPT_CHANGED` 和 `.iris/settings.json` 变化后持续重算。RightPane 在未就绪时可以在 launcher 附近显示简洁的阻断状态，但仍必须由 main 在启动时复核。

对于当前 `CLAUDE.md` 的旧协议残留，需要新增只读诊断：扫描受管块之外是否出现完整/高置信度 Iris 协议签名，报告 `prompt.ForeignProtocolResidue`。它只能提供 preview 和显式迁移，不能由普通 `sync-all` 自动删除 foreign prose。

### 七、bootstrap、React 和全局异常兜底

分三层处理：

1. `bootstrap().catch(renderBootstrapFailure)`：在 React mount 之前用最小静态 DOM 显示启动失败、重试和 incident id，避免白屏。
2. React Error Boundary：覆盖 render/effect 造成的组件树崩溃，保留 TitleBar 或提供整页恢复，不处理普通 Promise rejection。
3. `window.unhandledrejection` / `window.error`：归一化、限频上报并显示“未处理的内部错误”。这是 CI 应尽量归零的最后防线；不得根据这个事件恢复正常业务流程。

main 的 `uncaughtException` 继续执行 PTY 清理后退出；`unhandledRejection` 应被视为程序缺陷，记录 incident 并向相关/全部窗口广播一次 system degraded。正常 IPC handler、watcher 和 timer callback 都必须在自己的 boundary 内处理，不能依赖全局监听器。

renderer error report 必须限频和去重，避免一个 render loop 把日志写满。建议同一 `message + top stack frame` 在一分钟内合并计数。

### 九、分阶段交付

以下阶段展开前面“建议实施顺序”的任务，不新增另一套并行清单。

**阶段 0：建立基线。** 固化当前所有 invoke/dispatch/floating Promise 清单，给已确认允许静默的 catch 标注原因；为本次 `session.open` 写失败测试，先证明现状会产生 unhandled rejection 且 UI 无反馈。

**阶段 1：错误契约与 IPC wrapper。** 增加 shared error/result、main normalize/register helper、preload unwrap、renderer RemoteAppError；先迁移 prompt/session channels，打通 request/correlation/incident id。此阶段交付后立即修复当前复现路径。

**阶段 2：renderer action runtime。** 增加 `attemptAction`、`runUserAction`、notification queue 和 FIFO action dialog；迁移 session、status、todo、shell、clipboard 和 bootstrap 这些 P0 路径。

**阶段 3：后台健康。** 增加 health store/event/banner；处理 Git/Project watcher、scan、raw tree、session hydration、prompt projection；实现恢复清除和 project generation 隔离。

**阶段 4：高频与乐观 UI。** 处理 terminal input/resize/drop，主题和字体持久化失败，增加 failure latch、去重和自愈，验证不会出现通知风暴。

**阶段 5：全量 IPC 迁移。** 按 settings、project、document、asset、git、app/system 的顺序迁移剩余 channel；删除 legacy raw/rejection 兼容，CI 禁止直接注册 handler。

**阶段 6：治理收口。** 增加 type-aware floating Promise 检查、React/global fallback、renderer error report、诊断复制和文档；清理旧的裸 `console.warn`、字符串解析及覆盖式 alert 用法。

每个阶段都必须能独立发布，不能出现“错误已经不 throw，但 UI 基础设施尚未接入”这种中间状态。迁移一个 channel 时，handler wrapper、renderer normalization、具体 surface 和测试要在同一提交完成。

### 十、测试策略

单元测试覆盖：

- 每个领域 Error 到 `SerializedAppError` 的映射、unknown/cause、敏感 details 过滤；
- IPC envelope 校验、legacy 过渡、request/correlation id 贯通；
- `attemptAction`/`runUserAction` 对成功、取消、失败、恢复失败的 outcome；
- notification FIFO、去重、次数合并和 action 生命周期；
- health store 的 scope/generation 隔离、失败合并和成功清除；
- prompt.NotReady 的 repairable/conflict/invalid-settings 分支；
- terminal failure latch，确保一百次 input rejection 只产生一个状态问题。

组件测试覆盖：

- session open 失败后显示具体入口，点击“同步并启动”只重试一次；
- status/todo/shell/clipboard 失败有正确 surface，busy/pending 恢复；
- dialog queue 不会互相覆盖或伪造取消；
- bootstrap fatal fallback 与 React Error Boundary 可操作；
- health banner 恢复后消失，切换项目不串状态。

Electron 集成测试需要 fault injection，测试版 main 可按 channel 注入一次失败，禁止在生产设置中暴露。至少覆盖 main throw -> IPC envelope -> RemoteAppError -> action UI 的完整链路，以及 watcher error -> health event -> banner -> recovery。测试监听 renderer 的 `unhandledrejection`，正常业务错误场景必须为零。

### 十一、验收门禁

- [ ] 任一用户触发的异步命令都满足：成功、明确取消、可见失败三者之一，不存在“点击无反应”。
- [ ] 所有应用 IPC channel 都通过统一 wrapper；renderer 不再根据 Electron 错误字符串判断业务分支。
- [ ] `session.open` 的 prompt 未就绪错误能显示具体文件、层和状态，并提供安全恢复动作。
- [ ] 正常领域错误、超时、拒绝和后台服务错误不会触发 renderer/main 的全局 unhandled handler。
- [ ] notification、dialog 和 health 三类通道在重复失败下不会覆盖用户选择或形成提示风暴。
- [ ] watcher/projection 失败会形成可见 degraded 状态，成功恢复后自动清除，且多窗口/项目切换不串 scope。
- [ ] UI 展示和复制诊断不包含 stack、文档正文、终端输入或其他未声明 payload。
- [ ] 每个可见错误都能通过 incident/request/correlation id 在本地日志和 front-cpu trace 中关联。
- [ ] CI 启用 type-aware floating Promise 检查；所有保留的 `void Promise` 和静默 catch 都有受控 helper 或明确理由。
- [ ] 当前 `CLAUDE.md` 受管块外旧协议残留有显式诊断和人工确认迁移路径，普通同步不会擅自删除 foreign prose。

### 架构取舍

这套方案比“全局 toast + `window.unhandledrejection`”重一些，但新增抽象都对应真实边界：跨进程保真、用户操作收口、后台健康状态。它避免把错误处理继续分散到几十个组件，也避免把所有失败都粗暴地变成 modal。

不建议把 `Result` 一路传播到所有领域函数。main 内部仍可使用 typed Error 和 throw，renderer 组合业务流程也可使用 exception；只在跨 IPC 边界和 UI action boundary 转成显式 union。这样可以获得可验证的终态，又不会让整个代码库充满手工 `if (!result.ok)`。

不建议第一阶段重构全部 Error code。先保留现有领域 code，补 `domain` 和少量必须区分的新 code（尤其 `prompt.NotReady`），等调用点全部停止解析字符串后，再独立清理命名和重复类型。这样风险和收益更匹配。
