左上角有这么多图标，所有的都是有必要的吗？前四个或者三个 能不能合并？

右上角也是，那个心电图图标有意义吗？

## 2026-08-08 研究结论

结论：确实存在冗余。左上角前三个按钮属于同一个“打开项目”任务族，适合合并；第四个“新建工作区”不是同类动作，不应硬塞进项目菜单，但也没有必要长期占用全局工具栏。右上角的心电图按钮是开发期遗留的链路测试入口，对正常用户没有业务意义。

### 现有入口逐项核对

| 位置 | 图标 / 实际行为 | 判断 |
| --- | --- | --- |
| 左 1 | `FolderOpen`：选择文件夹并在当前窗口打开 | 项目切换 |
| 左 2 | `History`：列出最近项目并在当前窗口打开 | 项目切换，与左 1 高度相关 |
| 左 3 | `AppWindow`：再次选择文件夹并在新窗口打开 | 项目打开方式，与左 1、2 同组 |
| 左 4 | `FolderPlus`：在当前项目内创建子工作区 | 作用对象是工作区，不是项目切换 |
| 左侧其余 | 排序、筛选、Todo、Git | 都直接作用于当前左栏内容或切换左栏视图，保留独立入口有明确反馈 |
| 右侧 `Activity` | 调用 `app.ping`，显示 renderer → pipeline → IPC → main 的往返结果 | 纯调试能力 |
| 右侧 `Palette` | 快速切换主题 | 设置页“外观”已提供更完整的同一能力，属于重复入口 |
| 右侧 `Cog` | 打开设置页 | 应保留 |
| 最小化 / 最大化 / 关闭 | Windows 标准窗口控制 | 应保留，不能与应用操作混为一组 |

`Activity` 的定位在代码里很明确：`src/renderer/cpu/isa/app-isa.ts` 将 `app.ping` 标为 `debug`，注释说明它最初用于 M0 阶段证明整条调用链可用；`TitleBar.tsx` 目前没有开发环境判断，因此这个内部诊断按钮也出现在正常界面。底层 ping 可以继续留给自动化测试或诊断，但不应占据产品主界面。

### 建议信息架构

1. 左上角保留一个“项目”菜单，菜单内提供“打开项目...”“最近项目”和“在新窗口打开...”。最近项目直接列在菜单中，不再用第二个图标打开二级入口。
2. 将“新建工作区”放到工作区标题行的上下文菜单或省略号菜单中，并以当前工作区作为默认父级。它与工作区的关系会比放在全局工具栏中更清楚。
3. 从标题栏移除 `Activity`。保留底层 `app.ping` 指令即可；如以后需要可观测性，应放进开发者工具或专门的诊断页，而不是恢复常驻按钮。
4. 从标题栏移除 `Palette`，主题统一从“设置 → 外观”修改。当前设置页已经有全部主题、色板预览和明暗说明，比快捷下拉更完整。
5. 标题栏最终只保留“设置”以及系统的最小化、最大化、关闭按钮；左栏工具区保留项目菜单、排序、筛选、Todo 和 Git。

这样左栏在项目就绪时会从 8 个常驻图标降到 5 个，标题栏的应用按钮从 3 个降到 1 个，同时不丢失任何用户能力。

## 2026-08-08 用户决策与实施

本轮范围调整如下：

- “新建工作区”暂时保留在左栏工具区，不移动到工作区标题行。
- 主题切换暂时保留在标题栏。
- 原来的“打开项目”“最近项目”“在新窗口打开项目”三个图标已合并为一个“项目”菜单，菜单内直接提供三类入口。
- 标题栏的 `Activity` 调试 ping 已移除；底层 `app.ping` 指令仍保留供诊断使用。

本轮实际结果是左栏常驻图标从 8 个降到 6 个，标题栏应用按钮从 3 个降到 2 个。

验证结果：`npm test -- --run` 通过，共 23 个测试文件、136 项测试；`npx electron-vite build` 通过。完整 `npm run typecheck` 被当前工作区已有的 `SettingsView.tsx` / `AgentConfig.injection` 类型不一致阻塞，本次修改文件没有出现在错误列表中。
