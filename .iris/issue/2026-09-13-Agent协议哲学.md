# UCP v0.1 设计与实现说明

## 1 协议名称

**UCP** 的全称是 **Universal Capability Protocol**，中文名为**通用能力协议**。

UCP 是一种面向 Agent 的上下文能力描述协议。它把完成某类任务所需的说明、操作方法和相关材料组织成一个可获取的能力单元，并将其中的文本内容提供给模型上下文。

UCP 的核心对象不是远程服务，也不是可调用工具，而是一份类似 Skill 的能力模板。模板通常以 Markdown 为入口，可以引用同一能力单元中的其他文档、示例、资产、脚本、模型文件或可执行程序。

一个典型的 UCP 能力可以表达：

> 要完成视频解码，请使用随能力单元提供的 `bin/video-decoder.exe`。输入文件、参数、输出位置和错误处理方式如下。

模型阅读这段说明后，使用宿主已经具备的文件、命令或进程执行能力完成任务。UCP 本身不定义程序如何被统一调用，也不充当执行器。

## 2 设计目标

UCP 解决的问题是：**怎样把完成任务所需的知识和材料一起交给 Agent，使模型知道应该做什么以及如何使用这些材料。**

它适合承载以下内容：

* 面向模型的任务说明和操作步骤
* 参数约定、示例、限制和故障处理方法
* 可供模型读取的参考文档和数据文件
* 图片、音频、视频、模板等资产
* 脚本、动态库、模型权重和可执行文件
* 指向外部接口、程序或其他资源的说明

UCP 不要求所有能力被抽象成函数，也不要求所有输入和输出符合统一 schema。能力作者只需提供足够清楚的上下文，让模型能够利用宿主已有能力完成任务。

## 3 非目标

UCP v0.1 不定义以下事项：

* 统一的工具调用请求和响应格式
* JSON 输入和 JSON 输出 ABI
* 进程生命周期、RPC、会话或流式传输
* 权限模型、沙箱、签名、可信发布者或安全审查
* 对附件类型的业务语义解释
* 模型必须采用的计划或推理方式
* MCP、JTP 或其他工具协议的兼容层

UCP 协议本身不处理安全。获取方自行决定是否信任来源以及是否使用其中的材料。实现可以显示来源、文件列表和将要执行的程序，但这些信息不属于 UCP 的信任或权限机制。

## 4 能力单元

一个 UCP 能力单元至少包含一个入口文档。建议默认文件名为 `CAPABILITY.md`。

最小目录示例：

```text
video.decode/
└── CAPABILITY.md
```

包含附加材料的示例：

```text
video.decode/
├── CAPABILITY.md
├── references/
│   ├── formats.md
│   └── troubleshooting.md
├── examples/
│   └── decode-h264.json
├── assets/
│   └── default-preset.json
└── bin/
    ├── video-decoder.exe
    └── video-decoder
```

目录名和子目录名只是推荐组织方式。UCP Core 只要求能够定位入口文档以及入口文档引用的材料。

## 5 入口文档

入口文档是模型理解能力的主要上下文。建议包含：

1. 能力名称和用途
2. 何时使用以及何时不使用
3. 所需输入和预期产物
4. 操作步骤
5. 相关文件及其用途
6. 可执行程序或脚本的具体用法
7. 常见失败及处理方法
8. 平台、环境或依赖限制

视频解码能力示例：

```markdown
# 视频解码

当用户需要把受支持的视频转换为逐帧图像时使用本能力。

## 使用程序

Windows 使用 `bin/video-decoder.exe`，Linux 使用
`bin/video-decoder`。程序接受输入文件和输出目录：

    bin/video-decoder --input <video> --output <directory> --format png

先创建空的输出目录。成功时程序退出码为 0，并在输出目录写入
按时间顺序编号的 PNG 文件。诊断信息写入 stderr。

支持格式见 `references/formats.md`。如果程序报告不支持的编码，读取
`references/troubleshooting.md` 后再决定是否转换输入文件。
```

这里的命令只是提供给模型的操作知识。UCP runtime 不解析该命令，也不把它转换为某种协议调用。

## 6 获取与装载

UCP 实现可以从本地目录、压缩包或远程端点取得能力单元。无论来源如何，装载过程在逻辑上包含两个动作：

1. 取得入口文档和它可能引用的材料。
2. 将任务相关的文本提供给模型，并让宿主在需要时访问相关文件。

同步整个能力单元不等于把所有文件内容一次性放进模型上下文。实现可以先提供入口文档，再根据入口文档和当前任务按需读取参考材料。二进制资产不应被直接转换成大段上下文；模型只需知道它们的位置、用途和使用方法。

UCP v0.1 不规定具体的远程清单格式、缓存协议或更新策略。实现可以采用目录复制、归档下载、版本库或现有内容分发机制。若未来需要标准化分发，可以单独定义 UCP Distribution，而不改变 UCP 作为上下文协议的核心语义。

## 7 宿主职责

宿主负责把 UCP 能力接入 Agent，包括：

* 定位和读取入口文档
* 选择与当前任务相关的能力
* 将相关文本加入模型上下文
* 为模型提供读取附件和执行程序所需的已有能力
* 把执行结果重新提供给模型

宿主不应假定每个 UCP 能力都有可执行文件。纯写作规范、设计模板、领域知识和操作手册同样是有效的 UCP 能力。

## 8 与 Skill 的关系

UCP 把 Skill 的基本思想协议化：能力的主体是提供给模型的说明，说明可以引用完成任务所需的其他材料。

因此，UCP 能表示比传统工具调用更宽的内容。它既可以描述一个无需执行代码的工作方法，也可以告诉模型如何使用一个程序、HTTP API、JTP 工具或任何其他宿主可访问的能力。

UCP 不把这些外部能力重新包装成统一工具。它只让模型获得正确使用它们所需的上下文。

## 9 与 JTP 的边界

UCP 与 JTP 相互独立。

| 维度    | UCP            | JTP                 |
| :---- | :------------- | :------------------ |
| 核心对象  | 上下文能力模板        | 可调用工具               |
| 核心输入  | 任务相关说明和材料      | 工具 ID 与 JSON 参数     |
| 核心输出  | 提供给模型的上下文      | JSON 结果             |
| 执行语义  | 不定义            | 定义统一调用契约            |
| 内容范围  | 文档、资产、脚本、exe 等 | 已注册的执行入口            |
| 主要使用者 | 模型和 Agent 宿主   | Agent runtime 和工具实现 |

UCP 可以在文档中描述某个 JTP 工具的用法，因此从模型完成任务的角度看，UCP 可以指导实现 JTP 能实现的任意功能。但这不意味着 UCP 应依赖 JTP，也不意味着 JTP 工具必须通过 UCP 发布。

v0.1 保持两者分开：

* UCP 不规定 `tool id + JSON → JSON`。
* JTP 不读取或解释 UCP 能力模板。
* 两者可以被同一个 Agent 同时支持，但没有协议级依赖。

## 10 最小实现与验收

一个最小 UCP 实现应满足：

1. 能从一个已配置位置取得能力单元。
2. 能找到并完整读取入口 Markdown。
3. 能把入口文档提供给模型上下文。
4. 能根据文档引用定位同一能力单元中的文件。
5. 不要求附件具有固定类型或固定 schema。
6. 不把“包含 exe”误解为“UCP 自动执行 exe”。
7. 不在协议层增加权限、签名或沙箱要求。

## 11 对外介绍

> UCP 是面向 Agent 的通用能力上下文协议。一个 UCP 能力以 Markdown 模板为入口，可以同时携带参考文档、示例、资产、脚本和可执行文件。模板告诉模型何时使用这些材料以及具体怎样使用；模型再借助宿主已有的读取和执行能力完成任务。UCP 不规定统一工具调用格式，也不处理安全和信任。

## 14 JTP 全量重写方案

本次重写删除旧的工具调用抽象，不保留兼容层。模型只看到当前启用工具的结构化定义，完全不知道 JTP、Runtime、Provider、MCP 或部署方式。系统提示词只保留 Agent 通用行为、项目规则和结果表达要求；工具用途、参数、返回值、错误和限制全部属于工具描述。

### 14.1 目标结构

```text
src/main/jtp/
├── protocol.ts          # 请求、响应、错误和调用状态
├── descriptor.ts        # 工具描述与 schema 校验
├── registry.ts          # 工具注册、冲突检查、启用状态和模型投影
├── runtime.ts           # invoke、校验、路由、超时和审计
├── provider.ts          # Provider 统一接口
├── builtin-provider.ts  # 文件、终端和任务内置实现
├── mcp-provider.ts      # MCP 适配器
├── errors.ts            # 标准错误
└── result.ts            # 结果到模型内容的投影
```

`pi-adapter.ts` 只负责模型传输和消息转换；`agent-worker.ts` 只负责 Worker 消息；`session-manager.ts` 只负责会话、Invoke、审计和持久化。

### 14.2 Core 契约

请求固定为 `{ id, tool, arguments }`，响应固定为 `{ id, ok, result }` 或 `{ id, ok: false, error: { kind, code, message, retryable } }`。工具描述至少包含 `id`、`title`、`description`、`inputSchema`、`outputSchema`、`errors`、`effects` 和 provider 绑定。

### 14.3 Registry、Provider 与 Runtime

Registry 是唯一工具目录，负责注册、schema 校验、ID 冲突检查、启用状态和模型工具投影。所有实现统一为 `invoke(request, context)`；内置工具直接在 Agent Runtime 内执行，MCP Provider 在边界内完成 stdio、JSON-RPC、`tools/list` 和 `tools/call`。MCP 的 resources、prompts、sampling、elicitation、notifications 和复杂会话不得进入 Core。

Runtime 是唯一执行入口：解析请求、检查重复 ID、查询 Registry、检查启用状态、校验输入、调用 Provider、处理超时/取消/资源限制、校验输出、归一化错误并记录审计。

```text
model tool call → JTP request → JtpRuntime.invoke → Provider → JTP response → model result
```

### 14.4 Agent、设置与持久化

Worker 不再按工具名称转换旧的 `AgentToolOperationInput`；Session Manager 不再特殊分流 TaskManager 或 ToolHost。文件、终端和任务统一包装为 BuiltinProvider。设置页展示内置与 MCP 工具的描述、来源、状态及启用开关；本机和云端显示暂未支持。会话只记录通用 JTP 调用、工具 ID、参数摘要、provider、状态、结果或错误。

### 14.5 实施与验收

先建立 Core 类型、Registry、BuiltinProvider 和 Runtime，再改造 Worker、Session Manager、历史记录和 UI，之后接入 MCP，最后删除旧联合类型、旧工具 schema、旧分流和兼容代码。

验收要求：系统提示词没有工具信息；工具列表完全由 Registry 生成；所有内置工具经过同一个 Runtime；禁用工具在模型侧和 Runtime 侧都不可用；非法参数不会调用 Provider；错误类型可区分；调用 ID 可去重；MCP 可经同一路径调用且其复杂语义不进入 Core；类型检查和测试全部通过。

## 11 进一步架构判断：JTP 作为唯一工具 ABI

前述讨论进一步明确了 UCP、JTP 与 MCP 的层次关系。UCP 与 JTP 应保持独立：UCP 负责向模型提供能力说明、操作方法和相关材料；JTP 负责 Agent 内部确定的工具调用 ABI。

JTP Runtime 应成为 Agent 内部唯一理解的工具调用入口，核心流程保持为：

```text
resolve(tool_id) → execute(json) → return(json)
```

工具的具体实现由 provider 层负责，JTP Core 不区分内置函数、本地可执行程序、WASM、HTTP bridge 或 MCP bridge。MCP 因而被定位为一个兼容 provider（也可以实现为固定注册的 JTP executable），而不是与 JTP 并列的第二套 Agent 内部调用语义：

```text
Agent → JTP Runtime → JTP Provider → MCP client → MCP server
```

这种设计让 Agent 内核只维护一种 `tool_id + JSON → JSON` 契约，同时可以直接吸收现有 MCP 生态，并允许新工具逐步采用原生 JTP 实现。JTP 兼容 MCP，但不依赖 MCP。

需要冻结的边界是：MCP 的 `resources`、`prompts`、`elicitation`、`sampling`、通知和会话语义不能反向扩展为 JTP Core 对象。适配器可以自行支持这些能力，或在无法压缩为单次 JSON 请求/响应时明确报告不支持；只有能够归一化为 JTP 调用结果的部分进入核心路径。这样可以避免 JTP 因兼容 MCP 而重新长成一个复杂的 MCP。

# **JTP v0.1 设计与实现说明**

## **1 协议名称**

**JTP** 的全称是 **JSON Tool Protocol**，中文名为 **JSON 工具协议**。

JTP 是面向 Agent 的轻量工具调用协议。它把一次调用统一为：

```
工具 ID + JSON 参数 → JSON 结果
```

JTP runtime 根据工具 ID 找到宿主预先注册的执行入口，把 JSON 参数交给该入口，再把 JSON 结果返回给调用方。它不理解工具的业务语义，也不规定工具来自本地程序、进程内函数、远程下载产物还是协议适配器。

## **2 设计目标**

JTP 解决的问题是：**Agent 内部怎样通过一个稳定、最小的 ABI 调用不同实现。**

核心目标包括：

* 为 Agent 提供单一工具调用入口
* 让工具实现与模型、宿主框架和下游协议解耦
* 同时支持进程内函数和独立可执行程序
* 让 MCP 等外部协议能够作为普通适配器运行
* 把分发、更新和业务 schema 留在核心协议之外

## **3 核心模型**

每个工具至少具有：

0. 唯一工具 ID
1. 面向模型的工具说明
2. 已注册的执行入口
3. JSON 输入
4. JSON 输出

模型可以产生如下调用：

```
{
  "id": "call-001",
  "tool": "acme.orders",
  "arguments": {
    "op": "get",
    "order_id": "123"
  }
}
```

runtime 使用 `tool` 查找执行入口，并把 `arguments` 作为业务输入。模型不能通过工具 ID 临时指定任意磁盘路径、URL 或 shell 命令。

## **4 执行绑定**

对于独立进程，JTP v0.1 建议采用以下绑定：

```
stdin   一个 UTF-8 JSON 对象，写入后关闭输入
stdout  一个 UTF-8 JSON 响应对象
stderr  不属于协议结果的诊断信息
```

成功结果：

```
{
  "ok": true,
  "result": {
    "order_id": "123",
    "status": "paid"
  }
}
```

业务失败：

```
{
  "ok": false,
  "error": {
    "code": "ORDER_NOT_FOUND",
    "message": "订单不存在"
  }
}
```

退出码 0 表示程序正常返回了协议结果，不表示业务操作一定成功。程序无法启动、崩溃、超时或输出无效 JSON 属于执行层错误。

runtime 应直接启动注册表中固定的程序，并通过 stdin 传入 JSON。它不应把模型参数拼接成 shell 命令。

## **5 Runtime 职责**

JTP runtime 只负责：

* 解析调用信封
* 根据工具 ID 查询注册表
* 调用固定执行入口
* 收集结果和执行错误
* 把调用 ID 与结果关联后返回宿主

JTP runtime 不负责：

* 理解业务参数
* 为模型制定计划
* 下载或更新工具
* 管理远程服务认证
* 定义工具权限系统
* 解释 UCP 或其他上下文模板

调用超时只表示调用方未在期限内收到结果，不表示下游操作没有发生。runtime 不应自动重试具有副作用的调用。

## **6 注册与来源**

注册表维护从工具 ID 到执行入口的映射，例如：

```
system.file.read  → builtin function
acme.orders       → /opt/jtp/orders/orders-tool
compat.mcp        → /opt/jtp/adapters/mcp-adapter
```

工具可以来自内置实现、本地安装、远程取得的软件包或任何其他分发渠道。来源只影响安装和注册，不改变调用协议。

工具说明、可选 schema、平台信息和版本信息可以作为注册元数据存在，但不属于 JTP Core 的强制调用字段。

## **7 MCP 适配器**

MCP 可以作为一个普通 JTP 工具或工具提供者运行。适配器接收 JSON 参数，调用已配置的 MCP server，再把结果转换成 JTP JSON。

示例：

```
{
  "id": "call-002",
  "tool": "compat.mcp",
  "arguments": {
    "server": "configured-server",
    "tool": "target-tool",
    "arguments": {}
  }
}
```

`server` 应引用宿主已配置的别名，而不是让模型任意指定新端点。MCP 的资源、提示、采样、通知和多轮交互语义不进入 JTP Core。适配器无法压缩成单次 JSON 请求和响应的能力，应明确报告不支持或自行管理。

## **8 与 UCP 的边界**

JTP 与 UCP 是两个独立协议。

JTP 定义确定的工具调用 ABI。UCP 向模型提供完成任务所需的上下文和材料。一个 UCP 模板可以解释怎样调用 JTP 工具，但 JTP runtime 不依赖 UCP，也不读取 UCP 文档。

保持独立带来两个清晰的应用场景：

* 需要稳定、可编程、可记录的调用边界时，直接使用 JTP。
* 需要把工作方法、参考知识和任意材料交给模型时，使用 UCP。

同一个 Agent 可以分别实现两者，但不应把两者合并成一个联合协议或强制执行路径。

## **9 最小实现与验收**

一个最小 JTP 实现应满足：

0. 接受包含 `id`、`tool` 和 `arguments` 的调用。
1. 只允许调用宿主注册表中的工具 ID。
2. 能调用至少一种固定执行入口。
3. 能区分业务失败与执行层失败。
4. 能拒绝无效 JSON 和无效响应信封。
5. 不通过 shell 字符串拼接传递业务参数。
6. 不对有副作用的超时调用进行隐式重试。
7. 不依赖 UCP、MCP 或特定分发系统。

## **10 对外介绍**

> JTP 是面向 Agent 的轻量 JSON 工具调用协议。它使用“工具 ID + JSON 参数 → JSON 结果”的统一契约，把内置函数、本地程序和协议适配器纳入同一调用路径。JTP Core 只负责路由和执行，不理解业务语义，也不依赖 UCP 或任何特定工具生态。

## 11 JTP v0.1 实现方式

### 11.1 结构化工具描述

JTP 工具描述应是可解析文档（建议 `tool.json`），自然语言仅作为字段内容。最小结构：

```json
{"jtp":"0.1","id":"acme.orders.get","title":"Get order","description":"Retrieve an order by ID.","input":{"type":"object","required":["order_id"],"properties":{"order_id":{"type":"string"}},"additionalProperties":false},"output":{"type":"object"},"effects":"read","entry":{"kind":"process","command":"bin/orders-tool.exe"},"timeout_ms":10000}
```

`id` 是稳定注册键；`input`、`output` 使用 JSON Schema 子集；`effects` 区分 `read`、`write`、`external`；`entry` 必须来自受信任注册表，不能由模型提供。

### 11.2 调用情况

Runtime 按解析、注册解析、参数校验、执行、结果校验五阶段处理调用，覆盖：合法成功；请求 JSON 或信封无效；工具不存在、禁用或 provider 不可用；参数校验失败（不得启动程序）；入口启动失败；崩溃、非零退出或 provider 执行失败；超时或取消（禁止默认重试）；输出非法或不符合 schema；重复/迟到响应；并发、内存、输出大小或速率限制。

统一响应为 `{"id":"call-001","ok":true,"result":{}}`。失败使用 `{"id":"call-001","ok":false,"error":{"kind":"validation | unavailable | execution | timeout | protocol","code":"...","message":"...","retryable":false}}`。

### 11.3 Runtime 职责

Runtime 负责读取和校验描述、建立不可由模型修改的注册表；校验调用、参数和资源限制；分派 builtin、process 或 provider；以固定 argv 启动进程并通过 stdin/stdout 交换 JSON，禁止 shell 拼接参数；管理超时、取消、回收、输出大小及 stderr；校验响应、调用 ID 和 output schema；记录生命周期、版本、耗时和错误类别；保证调用 ID 去重；提供同步接口及同语义异步句柄。

Runtime 不下载工具、不解释业务字段、不替模型规划、不实现权限体系，也不解析 UCP。

### 11.4 Provider 与 MCP 适配器

Provider 抽象 `describe`、`invoke`、`cancel`、`close` 等固定动作。MCP 适配器使用宿主预配置的 server 别名和凭据，将参数转换为 MCP `tools/call`，再压缩为 JTP 响应。MCP 的 resources、prompts、sampling、notifications 和会话由适配器内部处理；无法表示为单次 JSON 调用的能力返回 `unsupported`。

### 11.5 最小部署

第一版部署 Registry、JTP Runtime、Process Provider 和 MCP Provider。工具包至少包含：

```text
acme.orders/
├── tool.json
└── bin/orders-tool.exe
```

验收：成功调用、未知工具拒绝、非法参数不启动、启动失败/超时/崩溃/非法输出可区分、重复响应不重复交付、MCP 工具可由同一 JTP 入口调用。远程 provider、取消协议、签名和完整 schema 后续扩展。


## 12 抽象层与部署形态分离

JTP Runtime 的抽象对象是“可通过工具 ID 接收 JSON 并返回 JTP 结果的执行能力”，而不是“外置工具进程”。因此内置、本地和云端工具在 JTP Core 中应保持同一调用语义：

```text
resolve(tool_id) → invoke(arguments) → JTP response
```

例如文件读写、终端执行等基础能力已经由 Agent 内核直接提供，不需要作为额外工具包安装，也不需要强行启动独立 executable。它们可以由 Runtime 直接调用内置实现；但对 JTP 来说，仍然只是注册表中的工具，拥有同样的 ID、结构化描述、输入校验、输出校验、错误分类、超时和日志关联机制。

因此，`entry.kind` 或 provider 类型表达的是实现绑定，而不是协议对象的不同种类：

* **builtin**：由 Agent Runtime 进程内直接实现，例如文件系统和终端工具。
* **local**：由本机固定程序、脚本或其他进程实现。
* **cloud/remote**：由宿主配置的远程服务或 API provider 实现。
* **mcp**：由 MCP 兼容适配器实现。

这些 provider 都实现同一套 JTP 调用接口。Runtime 不应要求所有工具都具备进程、stdin/stdout 或安装目录；Process Provider 只是众多执行绑定中的一种。

部署形态的差异应由 Agent 设置和管理界面呈现，而不是泄漏到 Agent 的工具调用逻辑中。设置页面可以分别展示内置工具的启用状态、本地工具的安装和路径、云端工具的端点与凭据、MCP 工具的 server 配置，但模型产生的调用以及 Runtime 的核心流程不因此分叉。这样既能让 Agent 把基础能力作为产品内建能力提供，也能保留本地扩展、云端服务和 MCP 生态的统一接入方式。

这意味着 JTP 的注册表至少应记录工具描述和 provider 绑定，但不把“是否需要安装”作为调用协议前提。安装、启用、配置、认证和更新属于宿主管理平面；解析、校验、执行和结果标准化属于 JTP 数据平面。

- 终端回调、输出批处理、监督和任务审计都绑定到该 Session 级执行实例，避免每次调用重复构造宿主。
- 验证：`npm run typecheck` 通过；Session Manager、NativeExecution、JTP Runtime/Registry 共 64 项测试通过。

## 2026-09-13 MCP 设置与目录

- 设置模型新增结构化 `experimental.mcpServers`，包含 stdio server 的 id/command/args/cwd/env，并加入校验与默认值。
- Agent Session Manager 从设置读取 MCP server 配置；MCP 工具发现仍在 Session Registry 建立时执行。
- `iris-agent:tools` IPC 目录现在同时返回内置工具与已配置 MCP server 的 provider 条目，Renderer store 无需判断工具类型。
- 验证：`npm run typecheck` 通过。

## 2026-09-13 Runtime 事件流收口

- 移除 Session Manager 手工补发的 JTP started/completed/failed 事件，调用生命周期事件现在只由 Session 级 `JtpRuntime` emit 并转发到 UI。
- Session Manager 仍负责把执行结果写入会话时间线与审计记录，但不再复制 Runtime 的事件语义。
- 验证：`npm run typecheck` 与 Session Manager/JTP Runtime 测试通过。

## 2026-09-13 MCP 启用策略

- 已配置 MCP server 的动态工具在 Registry 发现后自动加入启用集合；内置工具仍由 `experimental.jtpTools` 开关控制。
- `iris-agent:tools` 提供统一目录视图，Renderer 不需要判断 builtin/MCP 的调用路径。
- 验证：`npm run typecheck` 通过。

## 2026-09-13 Worker bridge 与回归修复

- Worker 工具调用的 correlation.toolCallId 现在优先使用 JTP request.id，保证模型 tool call 与 Runtime operation 一一对应。
- Pi 的 opaque operations 仅作为测试/provider bridge 类型入口，不包含工具 schema 或执行分流；生产工具目录仍来自 Registry。
- 修复后 Worker provider attempt 测试通过，`npm run typecheck` 通过。
