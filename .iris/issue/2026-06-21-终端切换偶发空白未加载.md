切换到某个终端后，偶发（低概率）出现内容没有加载出来的状态，视觉上像空白 / 未完成 replay，有时"动一下"（resize、敲键）才重新画出来。

本 issue 从《【长期跟踪】性能问题专项》拆出，便于独立处理。下面是 2026-06-19 复查 replay 链路（`RightPane` → `TerminalView` mount effect → 主进程 `getScrollbackForReplay`）后的定位。6-14 的 seq 边界修复已堵住"清屏后 redraw 被误丢"的丢包路径，但空白的根因不止那一处。

## 根因（按可疑度排序）

### 1. 结构性根因（最该改）：每次切会话都整体销毁重建

`RightPane.tsx:214` 只挂一个 `<TerminalView key={shownSession.id}>`。key 绑 sessionId ⇒ 每次切换都是完整 unmount + remount：销毁旧 xterm/WebGL/各 addon → 新建 → 请求 serialize 快照 → base64 回传 → 解码 → 分片 write → fence → reveal。这条链上任意一环抖动，用户看到的都是"切过去空白"。空白不是孤立 bug，而是"销毁-重放每次都来一遍"这个范式的故障面。

证据：

* `src/renderer/components/layout/RightPane.tsx:214` —— 单实例、`key={shownSession.id}`，无隐藏保活。

* `src/renderer/components/terminal/TerminalView.tsx` 整个 mount effect（`[sessionId]` 依赖）每次切换全量重建。

durable 修法：把切换从"销毁/重建"改成"保活/隐藏"——同一锚点下最近 N 个 `TerminalView` 常驻挂载，用 `display:none` / 绝对定位错层切换可见性，而不是 unmount。没有重放就没有重放竞态，也没有 WebGL 上下文翻动，空白面直接消失。这是最该做的一步，同时干掉下面 #2、#3。

### 2. WebGL 上下文翻动：切换频繁时新建上下文可能失败

每次 remount 都 `new WebglAddon()`（`TerminalView.tsx:466-481`），即新建一个 WebGL 上下文，unmount 时 dispose。浏览器对同时存活的 WebGL 上下文有上限（约 16 个），dispose 又非同步立即回收。频繁切换 / dev 下 StrictMode 双挂载 / 旧上下文回收滞后时，`new WebglAddon()` 可能抛错被 catch 落到 DOM 渲染——功能上能回退，但已知 xterm 在"WebGL 上下文创建失败或中途丢失"后，首帧画布可能空白，直到下一次 resize/refresh 才重绘。`onContextLoss` 里只 dispose+置 null，没有强制 `term.refresh()`。这条和现象"切过去空白、动一下才出来"高度吻合。

### 3. fence 窗口里的二次写竞态（6-14 修复的镜像问题）

headless 镜像在 `handlePtyData` 里逐 chunk 即时 `headlessTerm.write(data)`（`session-manager.ts:494`），而 replay 的 seq 边界冻结在 flush 批边界（`getScrollbackForReplay` 里 `replayLastSeq = managed.scrollbackLastSeq`，`session-manager.ts:435`）。两者粒度不一致：`await term.write('', cb)` 这段 await 期间到达的 chunk 会即时写进 headless（可能进快照），且 seq 一定 > `replayLastSeq`（一定被 renderer 当 live 补写）。是否进快照取决于 xterm `_innerWrite` 是否在同一同步批里连带解析了它——时序竞态。命中时该帧被写两遍。对 alt-buffer TUI 整屏重绘多半幂等（看不出），对行模式输出会重复行。它不直接产生纯空白，但属同一处时序裂缝。

根因一句话：headless 镜像按 chunk 即时写入，而 replay 的 seq 边界按 flush 批冻结，两者粒度不一致，fence 只能保证冻结点之前已入队的部分，盖不住 await 期间新到的 chunk。

## 建议落地顺序

1. 先用已埋好的性能监视器抓一次真实空白（零改动定性）：复现时看 `terminal.replay.serialize` 的 `ansiBytes`、`terminal.replay.ipc` 的 `base64Bytes`、`holdQueueFlushed/Filtered`、`fenceTimeout`、`replay.failed`。据此区分是"快照本身为空 / IPC 超时降级 / 有数据但没画出来（→ 指向 #2 WebGL）"。
2. 做 #1 TerminalView 保活（隐藏而非销毁），根治手段。
3. 若保活短期不做，先给 #2 兜底：`onContextLoss` 与 WebGL 创建失败回退后，reveal 时强制一次 `term.refresh(0, term.rows - 1)`；并评估把默认渲染器降为 DOM/canvas，验证空白是否消失。
4. #3 精确修法：让 headless 写入也走 seq-gated 的批（与 emit 同源推进），或在冻结 `replayLastSeq` 后、serialize 之前对 await 期间到达的 chunk 显式排除，使"进快照"和"> replayLastSeq"严格互斥。

## 2026-06-25 复盘：现象升级 + 推翻"负载论" + 当前理解

这一轮（与 AI 结对排查）现象比之前严重得多，已从"偶发空白"变成"高概率卡几秒"，且把之前的多条根因推断都推翻了。**本节结论性事实来自用户实测，AI 的中途推断（主进程被刷屏/扫描压满）已被证伪，勿再沿用。**

### 决定性新事实（用户实测）

* **空闲也卡**：三个**完全没动**的终端之间来回切，或**新建一个**终端，照样卡、照样等几秒。

* **此时没有任何输出**（agent 没在刷屏），**也没有任何 md / 文件在变**（扫描没被触发）。

* 即：**零负载下，每次开/切终端都要等差不多固定的几秒。**

### 被证伪的推断（不要再走这些方向）

* ❌「多个 agent 输出把主进程 headless 解析压满」——空闲终端没输出，照样卡。

* ❌「chokidar 扫描 `.iris` 与终端抢主线程」——没有 md 在变，扫描没触发，照样卡。

* ❌「主进程忙不过来 / 单线程饱和」——空闲的主进程没有理由卡；这跟忙不忙无关。

* 结论：**这不是性能 / 并发 / 负载问题。** 之前关于"搬 worker、并行化、给扫描减负、降阈值"的方向都是错的。

### 当前理解：固定延迟只可能是两类（均与负载无关）

零负载却每次固定等几秒，逻辑上只能是：

* **A. 某个超时在到点放行。** 代码在等一个信号（回放快照 / 某个回调），而该信号**根本没送到**（不是慢，是没来）。终端一直空白，直到 \~5s 安全兜底计时器（`REPLAY_FAILSAFE_MS`）到点把终端硬显示出来。"几秒"是**等一个不来的东西然后超时**，是接线 / 逻辑 bug，不是负载。

* **B. 某个步骤本身固定就要几秒。** 例如切换时**每次把整个终端连渲染器从零重建**（`RightPane.tsx` 的 `key={shownSession.id}` 全量 remount + `new WebglAddon()` + replay），或新终端等 shell/agent 进程启动。固定开销，空闲也一样。

### 下一步唯一需要的观察（先别再猜）

判 A / B 只需一个事实：**那个"等几秒"是不是每次都几乎一样长（像被固定时长卡住）？**

* 每次都差不多、像卡固定 5 秒 → **A（在等超时 / 信号没送到）**：去查"那个信号为什么没送达 / 为什么显示非要等它"。

* 时长有长有短、跟着别的东西变 → **B（某步骤实打实在耗）**：去查"为什么切一下要把终端整个重建 / startup 多久"。

正确的根治方向（无论 A/B，方向一致）：**让终端的"显示"不再依赖那趟"先向主进程要快照、拿到才显示"的握手**——终端开出来就该立刻可见、实时流式渲染，历史快照只是后台补上的附加品，永远不当显示门槛。这样无论主进程在做什么，终端都秒出。配套仍是**真正的保活**（切回不重建、不再请求 scrollback）。

### 本轮代码改动状态

本轮 AI 尝试过的改动（保活：`RightPane` 错层挂载 + `display:none`；`ThreePane` 稳定挂载；`backgroundThrottling:false`；主进程 fence 加 `REPLAY_FENCE_CAP_MS` 上限；`REPLAY_FAILSAFE_MS` 5000→2000；以及在性能面板加「终端事件」端到端追踪 tab）**均已被用户撤销，仓库现处基线状态。** 其中"终端事件"端到端追踪（点击→渲染完毕逐阶段计时）这个**工具**值得重做——它能一眼看出几秒卡在哪一段，是判 A/B 的最快手段。

### 与 Marina 对比（为什么原项目不卡）

`E:\projects\terminal`（Marina）的 `getScrollbackForReplay` 与回放栅栏**逐行相同**，所以差异不在回放代码本身。Marina 是纯终端，主进程只有 PTY + headless 镜像；Iris 多了文档项目层（chokidar + scan + 投影）。但**鉴于本轮证实"空闲也卡"**，对比的价值不在"负载差异"，而在：同样的回放握手，为什么在 Iris 里这趟握手（或重建）会稳定地耗到兜底——这才是要查的。

## 2026-06-25 续：empty-string fence 假说——源码已证实、已实现、但仍卡（证伪为主因）

接上一轮（与 Claude/Opus 结对），沿「A 类：等一个不来的信号然后超时」这条线深挖到一个**确凿的真实 bug**，实现了修复，但实测**仍卡**——因此它不是「零负载也固定卡几秒」的主因。完整记录如下，供后续不要再走回头路。

### 假说与源码证据（这条 bug 是真的）

回放链路上有两处用空字符串写作 xterm 的 parser-drain 栅栏：

* 主进程 `getScrollbackForReplay`：`await term.write('', cb)`（旧 `session-manager.ts:437`）。

* renderer `finishReplay` 揭开前：`term.write('', cb)`（旧 `TerminalView.tsx:699`）。

xterm 两条出队路径对空串行为不一致（已读源码 `node_modules/@xterm/xterm/src/common/input/WriteBuffer.ts`）：

* `_innerWrite`（正常异步，`:224`）用 `while (this._writeBuffer.length > this._bufferOffset)` 判定——空串能正常处理、callback 照常触发。

* `flushSync`（`term.resize()` 会调它，`:71`）用 `while (chunk = this._writeBuffer.shift())` 出队——`''` 是 falsy，被当成**队尾哨兵**，该 chunk 连同它的 callback 一起被丢弃且**不调用**（`:84`），随后 `_callbacks.length = 0` 清空。

⇒ 只要栅栏 `write('', cb)` 还在写队列里时撞上一次 resize/fit（→`flushSync`），callback 永不触发：主进程 IPC promise 永挂 → renderer `Promise.race` 等到 `REPLAY_FAILSAFE_MS`(5s) 才兜底揭开。完全吻合「固定卡 \~5s、与负载无关」（即上一节的 A 类）。

node 复现（已实测）：

```JavaScript
const t = new (require('@xterm/headless').Terminal)({ cols: 80, rows: 24 });
let called = false;
t.write('', () => { called = true });
t.resize(81, 24);            // → flushSync()
setTimeout(() => console.log(called), 20);   // false
// 换成 t.write(new Uint8Array(0), cb)：resize 后 callback 正常触发
```

### 已落地改动（保留——这是真 bug）

* `src/main/session-manager.ts`：栅栏改 `term.write(new Uint8Array(0), cb)`（truthy 对象，`flushSync` 会正常处理并回调）；新增 `REPLAY_FENCE_CAP_MS = 250ms` 兜底——超时则序列化「晚一拍」的镜像并打 `terminal.replay.fenceCapped` 计数 + warn，绝不再把 IPC 挂到 renderer 的 5s。

* `src/renderer/components/terminal/TerminalView.tsx`：`finishReplay` 揭开栅栏同改 `new Uint8Array(0)`；头部 / SCROLL-1 注释里过时的 `write('',cb)` 措辞一并更正。

* `npx tsc --noEmit` 通过。

### 决定性结果：仍卡 ⇒ 此假说被证伪为主因

* 用户实测：上述改动后**照样卡**。

* 结论：empty-string fence 丢回调是一个**真实存在、值得保留修复**的 bug，但**不是**「零负载每次开/切都固定等几秒」的（唯一 / 主要）原因。**后续不要再把「卡几秒」归因到这条 fence 上**——它已堵死，现象仍在。

* 旁证：现 repo 已含保活脚手架（`TerminalView` 带 `active` prop + keep-alive 注释，`RightPane`/`ThreePane` 有改动），即「切回不重建」这条 durable 修法看起来也在场，却**仍卡**——指向问题在「首次开 / 切到尚未保活的会话」那趟，或在 reveal/可见性切换、或主进程别处的同步阻塞，而**不在回放栅栏本身**。

### 下一步（回到上一节的唯一正确手段，先别再猜）

* [ ] 重做「终端事件」端到端逐阶段计时工具（点击 → mount → resize IPC → scrollback IPC → decode → write → fence → reveal），抓一次真实「卡」的 trace，看那几秒**到底落在哪一段**。在拿到这个 trace 之前，继续推断栅栏 / 握手都是浪费。

* [ ] 复现一次「卡」，确认 `terminal.replay.fenceCapped` 是否 > 0（若为 0，说明根本没走到 fence 兜底，卡在更早的环节）。

* [ ] 确认保活是否**真的生效**：切回一个已挂载会话时，是否仍触发 `SESSION_SCROLLBACK` IPC？若仍触发 → 保活没接上，问题回到「每次都重放」；若不触发却仍卡 → 卡在显示 / 可见性切换或主进程别处。

## 2026-06-25 再续：本帖历轮「实测仍卡 / 证伪」是在错的二进制上得出的

**决定性事实**：之前每一轮「改完→实测仍卡→判定证伪→回退」，跑的根本不是改后的码。`npm run dev` 因单实例锁 / userData 时序错配从没真正活下来，窗口一直加载安装版 asar 里的旧 bundle（详见《2026-06-25-开发版与安装版实例隔离》）。修好 dev / 安装版隔离、dev 第一次真正跑上当前源码后，**所有卡顿 / 切换空白全部消失。**

由此**必须修正本帖几处既有结论**：

* 上一节「empty-string fence 假说……证伪为主因」中的关键证据「上述改动后照样卡」——那次「照样卡」是在**没有该改动的旧构建**上测的，因此**不能据此判它证伪**。这条 fence（`write(new Uint8Array(0), cb)` + `REPLAY_FENCE_CAP_MS`）是确凿真 bug、已修、应保留；它到底贡献了多少，得在「确实跑着新码」的前提下重测才算数。

* 同理，「保活脚手架在场却仍卡 → 指向问题不在重建」这条旁证也站不住：保活那版也没真正运行过。

* 「零负载也固定卡几秒」之所以诡异、性能 / 并发 / 负载所有方向都对不上——因为现象不来自被排查的源码，而来自一个**谁都没在跑的旧 bundle**。这不是性能问题的判断没错，但「在跑的码 ≠ 改的码」才是它查不动的根。

## 2026-06-25 续二：切走再切回——排版混乱（保活下 WebGL 在 display:none 期间渲染坏掉了 atlas）

dev 跑上真码后暴露的**新**、可稳定复现的 bug：切到另一个终端再切回来，回放不完整、**排版混乱**（不是空白）。这是保活范式自己引入的，Marina 没有——因为 Marina 销毁/重放，从不让终端在隐藏态继续渲染。

### 根因

`RightPane` 的保活把非活动终端留在 `display:none` 下（`RightPane.tsx:263`）。但隐藏的 xterm **仍在收 live PTY 输出、仍在跑 WebGL 渲染循环**——`requestAnimationFrame` 对 `display:none` 元素照常触发（只有整个文档/标签页隐藏才会暂停 rAF）。于是这些写入被画进一个**没有布局盒子**的 GPU canvas / texture atlas，atlas 状态被写坏。

切回时原 reveal 路径（`TerminalView.tsx` 的 `[active]` effect）只做 `fit()` + `scrollToBottom()` + `term.refresh(0, rows-1)`。但 `refresh()` 只是把行从**当前（已损坏的）atlas** 重刷一遍，**不重建 atlas**——所以照样花。这正是 xterm 已知的「display:none 后渲染变花」失效模式，其官方解药是 `WebglAddon.clearTextureAtlas()`（「清空 texture atlas 并触发重绘」），而旧 reveal 路径从没调它。

### 已落地改动（待用户实测验证）

* `src/renderer/components/terminal/TerminalView.tsx`：新增 `webglRef` 持有 WebGL addon（DOM 渲染回退 / GPU context loss 时置 null）；切回的 `[active]` reveal effect 在 `scrollToBottom` 前先 `webglRef.current?.clearTextureAtlas()` 重建 atlas（其本身即触发整屏重绘，已覆盖随后的 `refresh`）。DOM 渲染器下为 null-op（该路径不会有此损坏）。

* `npx tsc --noEmit` 通过。

> 这是**按机理推断的定向修复**，尚未亲眼验证（GUI 复现在用户侧）。若仍花：说明损坏不止 atlas（如隐藏期间 0 尺寸把 cell 度量写坏 / reflow），下一步改为**根治**——隐藏态不要用 `display:none` 渲染坏掉，改成「隐藏但保持布局尺寸」（如 `visibility:hidden` / 移出视口）让隐藏终端始终在正确尺寸下渲染，从源头消除 0 盒子渲染。
