## 巡检结论（2026-08-05）

本轮检查以当前未提交工作树为准，只做调研，没有修改业务代码。`npm test -- --run` 的 67 个测试全部通过，`npm run typecheck` 通过；但文档选择、焦点协调器和性能面板目前没有自动化测试。

### P0：后台保存失败会静默丢失编辑

`project-store.ts` 的 `flushInBackground()` 不等待保存，`selectRoot()`、`selectWorkspace()` 等路径紧接着关闭编辑会话。`editor-store.ts` 的保存失败只在当前会话路径仍匹配时写入 `saveError`，一旦页面已经切走，错误既不可见，也没有重试入口，用户刚才的编辑会随旧会话一起丢失。

建议：把“允许立即切换 UI”和“保证旧文档写入结果可追踪”分开。保存任务应拥有独立于当前编辑会话的错误状态和重试能力；关闭项目或窗口前必须等待未完成写入。至少补充“切换后写入失败”和“窗口关闭时仍在写入”的测试。

### P1：快速 A→B→A 会接受过期读取结果

`project-store.ts:210-245` 只用 `state.selectedPath === path` 判断 `DOC_READ` 响应是否过期。若第一次 A 较慢，用户依次选择 B、A，第一次 A 的旧响应仍会通过判断，并可能覆盖第二次 A 的新内容。路径相等不代表请求仍是最新请求。

建议：给每次选择分配单调递增的 request token，提交响应时同时核对 token 和 path；补充乱序完成的 A→B、A→B→A 测试。

### P1：焦点协调器把“调用过”当成“获得焦点”

`use-claim-focus.ts:22-29` 在调用 `claim()` 后无条件执行 `markClaimed()`，而 `claim` 返回 `void`，无法表达目标未挂载、被禁用或 `focus()` 未生效。这样 `lastClaimed` 可能记录一个实际未获得焦点的区域，窗口重新激活时又恢复到错误目标。焦点策略还分散在 `project-store`、`session-actions`、`App`、两个编辑器和终端组件中，行为缺少可独立验证的状态转换。

建议：让 claim 返回成功布尔值，或传入目标元素并在调用后核对 `document.activeElement`；只有成功才消费 token 和更新 `lastClaimed`。把 request/claim/restore 的纯状态机抽出并覆盖“未就绪、失败、重挂载、窗口恢复、设置为 auto”场景。

### P2：Markdown 编辑器状态职责过密

`editor-store.ts` 369 行内同时处理 frontmatter 字节保真、WYSIWYG/source 双基线、dirty 计算、保存合并队列、文件监听回声去重、外部冲突和 React 订阅。当前仅有 2 个 store 测试，主要覆盖连续保存；模式切换、frontmatter 与正文并发变化、外部冲突、失败重试、unlink、checkbox 自动保存均无覆盖。这里不是单纯“文件太长”，而是多个一致性协议共享可变模块状态，修改任一协议都容易破坏其他协议。

建议：先补状态转移测试，再拆为纯 `compose/rebase` 逻辑、按路径保存队列、编辑会话状态三层；不要先做机械拆文件。`CrepeEditor.tsx:157-162` 的右键编辑动作依赖两层定时器，且卸载时不取消，快速切换后可能把 cut/paste 发给新的焦点目标，应改为可取消任务或基于菜单关闭事件后的确定性聚焦。

### P2：性能面板同时是采集器、诊断模型和 UI

`PerfPanel.tsx` 484 行，包含全局开关 store、事件合并、终端 trace/replay 分组、五个视图和导出/清空。标题栏反向从面板组件导入 `openPerfPanel()`，使 shell 控制依赖具体视图。面板关闭时主进程轮询会停止，但 renderer 的 long-task observer 和 5 秒 heap 定时器从启动后永久运行；每个事件还会复制整个 ring snapshot。500 条上限下暂时不是严重性能瓶颈，但性能工具本身缺乏启停、采集成本度量和测试，长期扩展指标后会反噬被测对象。

建议：将 open state 移到独立 store，将事件选择/分组变成纯函数，将各 tab 拆成视图；采集器提供一次性安装和 dispose/enable 开关，开发版默认开启、发行版按需开启。轮询增加 in-flight 防重入，面板测试至少覆盖跨进程合并、clear、replay 分组和卸载停止轮询。

### P3：大文件与测试分布暴露维护风险

除本次点名模块外，`SettingsView.tsx` 1424 行、`TerminalView.tsx` 1092 行、`session-manager.ts` 770 行、`project-manager.ts` 580 行。终端组件包含多组 timer、DOM 监听、replay、resize、selection、paste 和焦点逻辑，是下一轮最值得单独巡检的区域。当前 67 个测试主要集中在 scanner、初始化和 markdown 工具，renderer 交互状态的覆盖明显不足。

## 建议处理顺序

1. 修复并测试后台保存失败与文档读取竞态。
2. 收紧焦点 claim 契约，给焦点状态机补测试。
3. 为 editor store 的一致性协议补测试后再分层。
4. 拆分性能面板并使采集可启停、可测量。

## Markdown 滚动与跳转专项补查（2026-08-05）

这部分不是一个孤立的“滚动条样式问题”。当前代码没有统一的编辑器视口状态：焦点、光标、滚动位置、链接目标和历史导航分别由不同模块隐式决定，最终落点依赖异步时序。

### P1：滚动恢复与“聚焦到文末”直接竞争

`CrepeEditor.tsx:68-76` 在编辑器 ready 后把选区强制设为文末，并调用 `scrollIntoView()`；`SourceEditor.tsx:30-38` 也把 CodeMirror 光标强制设到全文末尾并滚入视口。与此同时，两个编辑器在创建后调用 `attachScrollMemory()` 恢复旧 `scrollTop`。

因此重新进入一篇读到中部的长文档时，恢复器试图回到旧位置，焦点 claim 又试图跳到文末。两者都经异步生命周期触发，谁最后执行谁获胜。这也解释了滚动位置“有时恢复、有时跳走”的非确定性。普通“查看文档”和“创建新文档后立即输入”被错误地共用同一套光标策略。

建议：导航意图必须携带显式落点，例如 `preserve`、`start`、`end`、`heading(id)`、`sourceRange`。普通选文档默认恢复视口且不改选区；只有新建文档或明确的“继续写作”动作才跳到文末。恢复过程完成前不得再由 focus claim 改写滚动位置。

### P1：Markdown 文档内跳转实际上没有实现

项目内没有针对编辑器链接的 click handler、heading id 生成、hash 解析或目标定位逻辑。兼容性文档已经包含 `[跳转到表格](#7-表格)` 这样的目录链接，但 `CrepeEditor` 只监听 `markdownUpdated`。应用级代码只为终端链接配置了 `window.open`/外部浏览器处理，并不构成 Markdown 编辑器导航。

结果是 `#heading`、相对 `.md` 链接和“从待办跳到来源文档的具体任务”都没有可靠语义：最多只能打开整篇文档，不能定位块；相对链接还可能落入 Chromium/Electron 默认导航行为。

建议：建立统一的 Markdown link resolver。外部 `http(s)` 明确交给系统浏览器；`#fragment` 在当前文档解析 heading/block id 并定位；相对 `.md[#fragment]` 先规范化为项目相对路径，再通过 `projectStore.selectDoc()` 导航并在编辑器 ready 后消费 fragment；非法或越界路径必须拒绝。标题 slug 规则需固定并测试中文、重复标题、标点和显式锚点。

### P1：不存在文档导航历史

所有入口最终直接调用 `projectStore.selectDoc(path)`，状态只保存当前 `view` 和 `selectedPath`，没有 back/forward 栈，也没有记录进入前的视口位置与选区。用户从目录、待办或文档链接跳走后，无法按原路径返回原阅读位置；左栏再次点回只是碰巧依赖全局 `positions` Map。

建议：引入独立 navigation store，每条 history entry 至少包含 view、doc path、mode、viewport anchor、selection 和可选 fragment。文档切换、集合跳转、Markdown 链接共用一个 navigate 命令，back/forward 只重放 entry，不重新猜测焦点。

### P2：滚动恢复器靠猜 DOM 和像素值，稳定条件不成立

`scroll-memory.ts:50-100` 不持有确定的滚动容器，而是把同一个 `scrollTop` 写给内容节点向上最多 8 层的所有可滚动祖先。恢复以 `scrollHeight` 连续 3 帧不变作为布局稳定，但这通常约 50ms 就会结束；图片、Mermaid、代码编辑器和字体可能随后才完成布局，导致同一个像素值不再对应原来的段落。

此外，保存的是绝对像素而非内容锚点。编辑器宽度、分栏宽度、字体、主题、BlockEdit 开关或文档外部修改引起换行变化后，旧像素位置会漂移到另一段。`positions` 是无上限的进程内 Map，不随项目关闭清理，也不持久化，跨窗口/重启行为与当前会话内行为不一致。

建议：让编辑器适配器明确返回唯一 scroller，不再扫描祖先。阅读位置保存为“顶端可见文档位置 + 像素偏移”，WYSIWYG 可用 ProseMirror position/DOM mapping，source 模式可用 CodeMirror line/selection；异步媒体布局后再次校正。缓存按项目命名空间并设上限，是否跨重启持久化需要明确产品决策。

### P2：WYSIWYG 与源码模式是两套互不相通的进度

滚动 key 被刻意分成 `wysiwyg:${path}` 和 `source:${path}`。这避免了像素单位直接复用，却意味着模式切换不会保持用户正在看的语义位置；首次切到另一模式时又因 focus claim 直接跳到全文末尾。模式切换因此不是同一文档的等价视图切换，而是一次位置丢失的重新打开。

建议：切换前记录语义位置。WYSIWYG→source 将 ProseMirror position 映射到 Markdown offset/line，source→WYSIWYG 做反向近似映射；无法精确映射时至少以当前段落文本或最近 heading 为锚点，不能默认跳到文末。

### P2：滚动条布局约束散落且过度耦合

`.crepe-host` 自己通过 `overflow-y-auto` 成为预期 scroller，`global.css:366-368` 又用 `scrollbar-gutter: stable both-edges` 预留两侧空间；`TypedHeader.tsx:245-256` 手工使用 `px-2.5` 假定滚动条宽度为 10px来对齐正文。滚动条宽度、header padding 和正文居中由三个文件人工同步，任何主题、缩放或容器调整都可能重新产生错位。源码模式使用 CodeMirror 自己的 scroller，没有同一套 gutter/列宽协议，切模式时视觉进度条和正文位置会跳变。

建议：由一个 editor viewport shell 同时承载 header 与 body，并通过共享 CSS 变量定义 gutter；WYSIWYG 与 source adapter 只提供内容和 scroller。不要让 header 猜滚动条宽度。需要分别验证 100%/125%/150% 缩放、窄分栏、短文/长文、滚动条出现临界点和三个主题。

### P2：专项测试完全缺失

当前没有 `scroll-memory`、链接解析、文档 history、heading slug、模式切换位置或焦点/恢复竞争测试。此前关于滚动条和滚动记忆的 issue 虽记录了实现过程，但现有测试套件无法防止这些行为回归。

建议优先补以下自动化场景：长文档切走再返回；A→B→A 且异步读取乱序；恢复期间 editor ready/focus 到达顺序互换；图片与 Mermaid 延迟增高；WYSIWYG/source 往返；中文及重复 heading；相对文档链接带 fragment；back/forward 恢复原段落；窗口缩放和分栏宽度变化。

## 调整后的优先级

1. 先停止普通选文档时强制跳到文末，消除 focus 与 scroll restore 的竞争。
2. 修复后台保存失败和文档读取 token 竞态。
3. 定义统一 navigation intent、link resolver 与 history 模型。
4. 用明确 scroller 和语义锚点替换祖先扫描及绝对像素恢复。
5. 再统一两种编辑模式的 viewport shell、滚动条布局和位置映射。

## 临时下线结果（2026-08-05）

按当前决策，焦点协调、滚动记忆和性能监控三套功能已从代码中完整删除，等待未来统一设计后重新实现。

已删除的范围：

- 键盘焦点 intent store、claim hook、窗口恢复逻辑、编辑器/终端/集合面板自动聚焦、文档聚焦策略设置及校验。
- WYSIWYG 与 CodeMirror 的滚动位置缓存、DOM 祖先扫描和恢复逻辑。
- renderer/main 性能 ring buffer、long-task 与 heap observer、性能面板、IPC channel、项目扫描和终端 replay 埋点。
- 仅服务于性能面板的 terminal trace、replay correlation id 和事件分组入口。

刻意保留：

- Iris 协议的 `FOCUS_DOC`。它表示 agent 会话绑定的文档，不是键盘焦点管理。
- 控件完成自身交互所需的局部 focus，例如终端搜索、粘贴或菜单关闭后恢复输入。这些不是跨区域焦点协调功能。
- 终端 replay、滚动到底、分片写入和超时保护。这些是终端正确性机制，不是性能监控。
- 滚动条主题和 gutter 样式。它们是视觉布局，不包含阅读位置记忆。

验证结果：`npm run typecheck` 通过；`npm test -- --run` 通过，7 个测试文件、67 个测试全部成功。全库检索确认不存在已删除模块、设置字段、IPC channel、trace 或埋点的残留引用。

## 前端与终端第二轮巡检（2026-08-05）

本轮按当前工作树复查了 renderer、preload、IPC 和 main 的 session manager。没有修改业务代码。终端的基本分层是清楚的：

- `SessionManager` 在 main 持有 PTY、会话生命周期、8ms 输出聚合和 headless xterm 镜像。
- `wireBroadcasts` 把生命周期事件和输出事件推到对应窗口；preload 只暴露 `invoke/on` 白名单桥。
- renderer 的 `session-store` 只保存生命周期投影，`TerminalView` 直接消费输出并管理 xterm。
- `RightPane` 只挂当前 session 的一个 xterm；切换 session 会卸载旧实例，再走 `SESSION_RESIZE → SESSION_SCROLLBACK → seq 去重 → fence → reveal` 重建。
- 离散动作走 front-cpu instruction，键盘输入、resize、output 走直接 IPC。这种 CQRS 偏离有理由，但目前没有独立的 typed terminal adapter 来收拢协议。

### P1：切换项目不会回收旧项目的 PTY，会话投影可能跨项目泄漏

`PROJECT_OPEN` 只调用 `projectManager.open()` 和 `gitManager.open()`（`src/main/ipc.ts:80-93`）。`ProjectManager.open()` 会关闭旧 watcher 并替换 `projectRoot`，但没有通知同一 `WindowContext` 的 `SessionManager`；后者直到窗口关闭才在 `disposeWindowContext()` 中 `shutdown()`（`src/main/app-main.ts:133-145`）。因此在同一窗口打开项目 B 后，项目 A 的 PTY 仍以旧 cwd 和旧 `FOCUS_DOC` 运行，`SESSION_LIST` 仍会返回它们，且 renderer 只按 `docPath/workspacePath` 过滤，遇到同名文档时可能显示或操作错项目的会话。

这是会话所有权边界缺失，不是 UI 小问题。打开项目前应由 main 原子地关闭或迁移旧项目会话，并让 session projection 带项目代际/根路径；至少要补“打开 B 后 A 的会话不可见、不可输入、可明确关闭”的测试。

### P1：异步粘贴和文档拖入没有绑定发起时的 session

`pasteText()` 在确认框或剪贴板 IPC 返回后，使用的是当时的 `termRef.current`（`TerminalView.tsx:151-219`）。`handlePaste()`、`handleDocDrop()` 以及 `handleFileDrop()` 都允许在 `await` 期间切换 session；其中文档拖入读取完成后会把快照贴到“当前”终端，文件拖入则始终用闭包里的旧 `sessionId` 发送（`TerminalView.tsx:234-285`）。快速切换时，用户在 A 发起的内容可能落到 B，或旧会话收到已经不再可见的输入。

所有异步输入操作都应捕获 `{ sessionId, term }`，在每个 await 后验证仍是当前实例；失效时取消，不应依赖全局 `termRef`。危险路径确认后还应按目标 shell 正确转义，而不是只确认后原样拼接 shell 元字符。

### P1：React StrictMode 会让重建副作用执行两次

入口用 `React.StrictMode`（`src/renderer/index.tsx:40-44`）。`TerminalView` 的 effect 在开发环境会 setup/cleanup/setup，但 cleanup 只能标记 `disposed`，无法取消已经发出的 `SESSION_RESIZE(forceRedraw)` 和 `SESSION_SCROLLBACK`（`TerminalView.tsx:686-783`）。旧 effect 仍会在 main 侧触发一次 PTY 双 resize、headless serialize 和 IPC 回传；这会放大 Codex 等 alternate-screen TUI 的重绘和乱码窗口，也会让开发环境的性能与发行版不一致。

重建协议需要可取消/可识别的 mount generation；main 端也应在 replay 请求中携带 generation，过期请求不再执行强制 redraw 或 serialize。至少补 StrictMode 双挂载、快速 A→B→A 和卸载中 replay 返回的测试。

### P2：`forceRedraw + 50ms` 是有效实验，不是稳定协议

当前为绕过 ConPTY 同尺寸 resize 的 early return，main 先把 rows 调一格再恢复（`session-manager.ts:396-410`），renderer 固定等待 50ms 后才请求 snapshot（`TerminalView.tsx:689-704`）。IPC 返回只代表 `pty.resize()` 调用了，不代表 TUI 已重绘；50ms 在负载、后台窗口、不同 shell 下没有确定性保证。该 workaround 还会制造两次 reflow 和额外输出。

短期可保留为诊断开关，但最终应优先稳定挂载 terminal；若继续重建，必须定义“resize 已完成/收到 redraw”的可观测确认，而不是依赖固定 sleep。

### P2：renderer 端输入和 resize 错误被全部丢弃

`onData`、`term.onResize` 和文件拖入都以 `void window.api.invoke(...)` 或只 `console.warn` 结束（`TerminalView.tsx:571-575, 641-650, 256-264`）。main 已经返回 `session-not-found`、`pty-exited`、`pty-write-failed`，但用户看不到任何状态，也没有重试或停止输入的策略。窗口关闭、项目切换和 PTY 半关闭时，这会表现为“终端偶尔不响应”。应增加一个按 session 的 transport 状态，并把不可接受结果转为一次性可见提示或结束输入通道。

### P2：输出聚合使用重复 `Buffer.concat`，高吞吐时是 O(n²)

`SessionManager.queueEmit()` 每收到一段 PTY 输出就复制整个 pending buffer（`session-manager.ts:532-543`）。编译、日志或 agent 流式输出在一个 8ms 窗口内出现很多 chunk 时，CPU 和临时内存会按累计长度反复复制。应改为 `Buffer[] + totalBytes`，flush 时只 concat 一次，并为单批和单会话增加上限/背压策略。

### P2：终端组件仍是跨层 workaround 集合，且注释已出现漂移

`TerminalView.tsx` 约 929 行，同时负责 xterm 创建、WebGL/Search/WebLinks addon、IME 私有 API patch、剪贴板安全策略、OS/文档拖放、ResizeObserver、字号持久化、replay、seq 去重和 UI 搜索栏。文件头仍写着“visibility:hidden + inert”“focus now intent-driven”（`TerminalView.tsx:15-20, 107-118`），但当前实现使用 `opacity: 0` 且焦点协调器已删除；这类迁移残留会误导下一次修复。

建议先建立可测试的 `terminal-transport`、`terminal-replay-controller`、`terminal-input-policy` 和 `terminal-viewport` 边界，再拆 React 组件。不要继续在组件 effect 中叠加定时器和私有 `_core` 访问；IME workaround 应隔离到版本适配层，并在 xterm 升级时有契约测试。

### P2：切换 session 的全量销毁/序列化/重建仍是主要复杂度来源

`RightPane` 只挂一个 keyed `TerminalView`（`RightPane.tsx:209-221`），每次切换都要把最多 5000 行 headless 状态完整序列化、base64 传 IPC、renderer 再解码和分片写入（`session-manager.ts:440-498`、`TerminalView.tsx:718-741`）。这保护了 alt-buffer，但并不等价于 TUI 自身状态，且 line length 没有上限；输出很多或单行很大时，切换会产生明显内存和卡顿峰值。稳定挂载并保留有限个实例是首选；若资源不允许，应把 replay 做成有大小上限、可取消、可观测的协议，而不是继续增加固定延时。

### 其他确认到的维护风险

- Ctrl+滚轮的 120ms 持久化 timer 在卸载时只被清除，注释所说的“flush”并未发生（`TerminalView.tsx:788-793`）；用户缩放后立即切换 session，字号可能丢失。
- WebGL context loss 只 dispose addon，没有显式 `term.refresh()` 或重建 atlas（`TerminalView.tsx:491-500`）；GPU 丢失后可能一直空白，直到下一次 resize。
- `lastTerminalDims` 是 renderer 进程级单一值（`session-store.ts:166-180`），没有按项目、窗口或布局分区；从窄的文档终端切到全宽根终端时，新 PTY 仍按旧列数启动，再触发一次 reflow。
- 终端、session manager、settings 和 collection 交互目前没有专门测试；现有 67 个测试无法覆盖上述时序协议。

## 第二轮重构判断

当前不建议做“大拆文件”式重构。优先级应是先修复会话所有权和异步输入目标，再把重建协议改成可取消/可观测，随后以纯状态机和适配器为边界拆分。推荐顺序：

1. 在 main 建立 project/session 代际边界，打开项目时原子回收旧会话。
2. 引入 session-bound transport token，所有 paste/drop/replay/resize await 都校验 token；错误结果进入可见的 transport 状态。
3. 为 replay、输入、resize、StrictMode 双挂载补单测和最小集成测试；先记录 replay bytes、hold queue、resize/redraw 时间，不恢复已删除的全局性能面板。
4. 评估有限保活的 xterm 实例；若仍使用全量 replay，增加大小上限、取消和 backpressure。
5. 最后拆 `TerminalView`，把 xterm 私有 API 和 UI 控件移到适配层，并删除失真的 Marina 历史注释。
