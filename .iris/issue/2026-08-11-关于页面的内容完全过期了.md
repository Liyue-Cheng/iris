## 2026-08-11 现状核查

- `SettingsView.tsx` 仍显示“版本号、构建形态和数据目录信息等待 IPC 支持”和“无版本元数据”，没有读取运行中的应用信息。
- 页面写死 `AGPL-3.0`，但 `package.json`、仓库根 `LICENSE`、README、打包配置和第三方声明链路均已采用 MIT。这是必须优先消除的法律信息错误。
- 页面仍使用设置页的 `Palette` 图标代替 Iris 品牌标记；仓库已有 `IrisMark`、`build/mark.svg` 和 `build/wordmark.svg`。
- 产品描述仍是早期的功能标签，未采用 README 当前的产品定义：“一个以持久项目记忆为核心的本地优先人机协同开发工作空间”。
- 主进程已经拥有 `app.getVersion()`、`app.getPath('userData')`、`getBuildType()`、平台/架构和 Electron/Chromium 版本，但 shared protocol 中没有只读的应用信息契约。
- `LICENSE` 与 `THIRD_PARTY_NOTICES.txt` 已进入 Windows 发布包，页面却没有查看入口；源码、Releases 和问题反馈也没有产品级入口。
- 目前没有关于页或产品元数据一致性测试，未来改版本、许可证、发布形态或品牌文案时仍可能再次漂移。

## 治理目标

关于页应成为“当前正在运行的 Iris 是什么、从哪里来、把本机数据放在哪里、依据什么许可证分发”的可信产品界面，而不是发布说明、功能清单或调试信息堆放处。

治理完成后应满足四条原则：

1. 运行时事实来自主进程，renderer 不猜测版本、构建形态或路径。
2. 产品静态元数据有明确真相源，并由自动检查阻止跨文件漂移。
3. 法律声明和外部链接使用受限的产品级动作，不开放任意路径或任意 URL 能力。
4. 开发版、portable 和安装版均显示真实信息，并在缺失或失败时给出明确降级状态，绝不恢复为占位文案或错误常量。

## 页面信息架构

关于页保持设置页的安静、紧凑风格，不做营销落地页，也不增加嵌套卡片。

### 产品身份

- 使用现有 `IrisMark`，不再借用 `Palette`。
- 主标题固定为 `Iris`。
- 中文描述采用 README 当前定义：“一个以持久项目记忆为核心的本地优先人机协同开发工作空间。”英文使用等义的正式译文。
- 在标题附近直接显示 `v<version>` 与本地化后的发行形态：`开发版`、`便携版`、`安装版`。

### 运行信息

使用普通设置分组展示以下字段：

| 字段 | 展示规则 | 权威来源 |
| --- | --- | --- |
| 版本 | `v0.1.0-beta.5` 形式，不手写版本号 | `app.getVersion()` |
| 发行形态 | 开发版 / 便携版 / 安装版 | 现有 `getBuildType()` |
| 运行平台 | 例如 `Windows x64` | `process.platform`、`process.arch` |
| 运行环境 | Electron 与 Chromium 版本；Node 版本仅进入诊断副本，不占常规页面 | `process.versions` |
| 数据目录 | 可读路径，提供“复制”和“在文件管理器中显示”图标按钮 | `app.getPath('userData')` |

长路径必须在窄窗口中截断或换行，按钮尺寸保持稳定，并以 tooltip 和无障碍名称解释图标。增加“复制诊断信息”命令，复制固定、可审阅的纯文本字段；默认不包含当前项目路径、最近项目、终端内容、用户名或其他项目数据。数据目录只在页面本地展示，不进入日志或遥测。

### 法律与项目入口

- 显示 `MIT License`，提供查看 Iris 自身许可证的命令。
- 提供查看 `Third-party software notices` 的命令。
- 提供源码仓库、Releases、问题反馈三个外部入口；文案和 URL 来自产品元数据，不散落在 JSX 与翻译资源中。
- 显示规范化版权信息。作者名称以 `LICENSE` 的法律主体为准，并同步修正 npm manifest 与 electron-builder 元数据中的缺失或别名表达。

“文件契约”不是应用版本或法律信息，不应继续占据关于页。若未来要展示 `.iris` 协议版本，应先建立独立、可读取的协议版本契约，再作为明确命名的字段加入；本次直接移除当前无数据支撑的行。

## 数据与权限设计

### 只读应用信息契约

在 shared types 中增加稳定的 `AppInfo`，建议形状如下：

```ts
interface AppInfo {
  name: 'Iris';
  version: string;
  buildType: 'dev' | 'portable' | 'installed';
  platform: NodeJS.Platform;
  arch: string;
  electronVersion: string;
  chromiumVersion: string;
  nodeVersion: string;
  userDataPath: string;
  license: 'MIT';
  copyright: string;
  links: {
    source: string;
    releases: string;
    issues: string;
  };
}
```

`APP_INFO` 是 machine-level 只读 query，由 main 组装并一次返回；不经过 FrontCPU 指令管线，也不依赖当前项目是否已打开。renderer 在 AboutPanel 挂载时读取并缓存结果，处理 loading、error 和 retry 三种状态。失败时显示“无法读取应用信息”，保留重试动作，不用静态假值掩盖故障。

### 受限动作

新增产品级动作并只接受枚举 ID：

- `APP_OPEN_LEGAL_DOCUMENT` 只接受 `license | thirdPartyNotices`。main 在开发态从仓库应用根解析，在打包态从 `process.resourcesPath` 解析，并检查目标存在后调用 `shell.openPath()`。
- `APP_OPEN_EXTERNAL_LINK` 只接受 `source | releases | issues`。main 从已验证的产品链接表解析 HTTPS URL 后调用 `shell.openExternal()`；renderer 不能提交任意 URL。
- `APP_REVEAL_USER_DATA` 不接收路径参数，只显示 main 自己读取的 `userData` 目录。不要借此扩大现有通用 shell IPC 的权限面。

preload 仍保持现有通用 `invoke` 白名单桥接方式，不暴露 Electron、Node、文件读取或 shell 对象。

## 元数据真相源与防漂移

`package.json` 作为版本、产品名、许可证、作者和项目 URL 的机器可读真相源，补齐规范的 `author`、`homepage`、`repository` 和 `bugs` 字段。运行时版本继续通过 Electron `app.getVersion()` 读取，确保它反映实际启动的包而非源码工作树。

增加产品元数据一致性检查脚本，并纳入 CI 与 `npm run dist`。检查至少覆盖：

- `package.json` 与 `package-lock.json` 根版本一致。
- manifest 的许可证为 `MIT`，仓库存在 MIT `LICENSE`，electron-builder 的 NSIS license 与 extraResources 指向同一文件。
- 产品名、作者/版权主体、仓库 URL 在 manifest、builder 配置和关于页运行时结果中一致。
- `LICENSE` 与 `THIRD_PARTY_NOTICES.txt` 均存在且会进入打包 resources。
- i18n 中不再出现旧占位文案、`AGPL-3.0` 或 JSX 手写版本号。

README 可以描述发布线而不绑定每个补丁版本；精确当前版本只由 manifest、lockfile、发布产物和运行时关于页承载。这样日常发版无需人工在多处替换同一版本字符串。
