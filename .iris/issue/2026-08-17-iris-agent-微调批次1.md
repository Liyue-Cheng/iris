## Iris Agent 当前信息展示与数据结构评审（2026-08-18）

### 结论

当前 Iris Agent 的**数据底座设计明显强于展示层设计**。它已经不是把聊天文本临时放在 Renderer 的原型：main 持有 canonical Session，Session 以 revision、worker epoch、turn、message、tool event、request facts、file effect、artifact cleanup 等事实组成可恢复状态；Renderer 只接收投影并用 revision 拒绝旧快照。这套分层对 Stop、重试、分支、Worker 重建和重启恢复是正确且专业的。

但 UI 仍基本是“聊天记录 + 少量调试按钮”的 MVP。它能显示发生过什么，却没有把新结构里最有价值的**因果、状态、边界和证据**组织成用户能快速理解的工作面。尤其 Agent 的工具、副作用、模型身份、上下文证据和分支，当前大多只是被压扁为文本或藏在图标/下拉框里。因此总体判断是：**底层工程设计 8/10；信息架构与交互呈现约 5.5/10；两者的配合约 6/10。**

### 当前实际展示方式

Agent 被嵌入右栏，并与普通终端共享同一个 session switcher：

1. 右栏顶部用 Bot 图标识别 Agent，标题显示 `Iris Agent` / Session displayName；同一 anchor 下的 Terminal 和 Agent Session 按创建时间混排在一个下拉列表中。
2. Agent 自身 header 显示运行状态、固定的“当前版本尚不具备自举资格”说明、provider/model 下拉框，以及依状态变化的 Stop、Retry、Undo 图标按钮。
3. 正文按 turn 线性排列：user/assistant 各自使用消息卡片；tool event 插在两者之间，显示工具名、状态、路径、摘要、错误和可选 diff。
4. 每条 user/assistant 卡片右上可出现文件图标，打开该 turn 的 provider context 或 legacy assembled input；每个已结束 turn 底部有 Fork 图标；turn error 单独显示警告块。
5. 底部是两行 textarea 和发送按钮。模型不可用或运行中时输入被禁用。

这套布局的优点是学习成本低：用户把它当作“挂在 Issue/Workspace 上的聊天会话”即可使用；停止、重试、撤销、分支也都没有脱离对话上下文。

### 与最新数据结构的匹配情况

#### 配合良好的部分

* **Session 与 anchor 的归属明确。** `IrisAgentSessionInfo.anchor` 与右栏按文档/工作区过滤的机制一致；同一个 anchor 下的多个 Agent Session 可以选择，Fork 成功后也能切换到新 Session。这一点与“会话属于工作对象，而非全局聊天”的产品模型匹配。
* **turn 是展示主轴，符合用户心智。** `turns + messages` 足以稳定渲染“我提出请求 -> Agent 输出”的阅读顺序；`providerOnly` 消息不渲染，避免工具循环中的内部 assistant envelope 造成重复聊天卡片。
* **运行态和命令语义有基本映射。** `starting/running/waiting-tool/stopping` 映射为 header 文案，Stop/Retry/Undo 的可用性主要由 turn/session 状态决定；这与 main 的 command serialisation、expected revision 和 worker epoch 不冲突。
* **工具事实未被伪装成聊天文本。** `toolEvents` 有独立结构，UI 也独立渲染，至少保住了“工具调用是执行证据，不是 Agent 自述”的边界。`diff`、path、error 已有承载位置。
* **敏感上下文没有穿过 Renderer。** Provider context 只以 `providerContextAvailable/providerCallCount` 等能力标记投影，Renderer 用 session/turn 标识请求 main 打开 artifact；这与 app-owned artifact、脱敏和路径授权的安全模型吻合。
* **模型选择使用 Session canonical state。** Header 的 provider/model 控件读取 `session.model`，而不是浏览器本地状态；不可用方案保留为“不可用”，不会静默替换。这很好地对应了 v4 的 profile + model 设计。

#### 配合不足的部分

* **结构信息大量存在却没有可见语义。** Session 的 `revision`、`workerEpoch`、`parentSessionId`、`forkedFromTurnId`、`requestFacts`、`fileEffects`、`pendingArtifactCleanupTurnIds`、`lastError`、turn 的 requestId/retryOfTurnId/artifact 能力等，几乎完全不在 UI 中表达。不是要求把内部 ID 全贴出来，而是应转译为用户问题：这轮从哪里重试？这个分支源自哪里？哪些文件已经改变？证据是否仍可打开？当前内容是否是恢复后的会话？
* **同一 turn 的事实被拆成松散垂直块。** 现在的顺序是 user card -> 所有 tool cards -> assistant card -> Fork -> error；它不能呈现工具调用与具体回答段落、失败、重试的关系。对多工具/多 provider call 的 turn，用户只能看到一串平铺日志，无法判断“Agent 做了什么、结果支撑了哪句结论、是否还在执行”。
* **`toolEvents` 的表达过度摘要化。** `inputSummary/resultSummary`、diff 和 path 能用于排错，却缺少展开层次、完整命令输出、退出码、真实 terminal correlation、耗时和变更数量。数据模型已有 `terminalId`、状态和 file effect 基础，UI 却没有形成“可验证执行记录”。这会使用户误把 Agent 的最终文字当作唯一证据。
* **artifact 入口的命名与位置仍偏开发者。** 同一个文件图标既可能代表 provider context、legacy assembled input 或本轮 assembled input，差异只在 tooltip；而 provider context 的 call 数只是标题中的数字。对普通用户来说“打开上下文文件”不是自然的任务，也看不到它与当前消息/模型/历史恢复的关系。
* **分支是底层已成立、上层几乎不可发现的能力。** 数据结构已有 lineage，UI 只在每个结束 turn 右下放一个无文字 GitBranch 图标；分支创建后，列表中也只显示同名 `Iris Agent Branch N`。没有来源提示、分支点、会话关系或“仅复制对话、不复制世界状态”的说明，用户很容易把它误解为工作区快照或普通重试。
* **状态展示不够可信。** header 将 `ready`、`idle` 区分为“就绪/空闲”，但用户并不知道这是否意味着 Worker 存活、已恢复历史、模型可用或仅是没有运行中的 turn；`failed` 只变成一个短文案，具体错误散落在某轮卡片。底层已经非常强调 lifecycle correctness，前台却没有给出与之匹配的可信状态解释。
* **顶层信息密度失衡。** “尚不具备自举资格”长期占据最高可见位置，但当前 anchor、来源分支、模型方案、最近一次执行结果、未处理错误等任务相关信息更重要。它像产品内部阶段标签，而不是用户此刻完成 Issue 的操作信息。

### 设计水平评价

#### 底层数据设计：良好，且方向正确

v4 Session 的核心优点是把三类东西拆开：

* 对话投影：`turns`、`messages`；
* 执行与副作用事实：`toolEvents`、`fileEffects`、`requestFacts`；
* 生命周期/一致性/持久化事实：revision、epoch、stop intent、undo receipt、artifact cleanup、model 和 lineage。

这比常见的“一个 messages 数组塞入 UI、provider 原文和工具日志”的做法成熟得多。main-owned store、按 turn 的 artifact、Worker protocol identity 与 Renderer 的受控投影，也给未来审计和恢复留下了正确边界。需要注意的是，当前 `IrisAgentSessionInfo` 同时承担 domain state、IPC DTO 和 Renderer view model 三种职责；字段继续增长后，建议保持内部 canonical schema 与更小的 renderer projection 分离，避免 UI 为了一个摘要而长期接触过多运行时字段。

#### 展示设计：可用 MVP，但尚未形成 Agent 工作台

现有界面遵循了传统聊天产品的“最小可用”范式，视觉上克制，布局也与右栏尺寸相适配；对于一轮纯问答，它足够好。但 Iris Agent 的价值不只是回答，而是围绕 Issue 读取、执行、改文件、验证和写回。此时聊天应该是叙事层，不应该承担全部事实层。当前把执行记录压在消息流中，导致：简单任务显得正常，真实工程任务则很快变成不可扫描的长列表。

更准确地说，当前不是视觉设计差，而是**对象模型已经进入 Session/Turn/Effect/Artifact 阶段，界面仍停留在 Message/Log 阶段**。这正是数据结构和信息展示之间最大的代差。

### 建议的展示收口方向（不在本次直接改代码）

1. **保持时间线，但将 turn 升级为可折叠“工作单元”。** Turn 头部应一眼给出请求摘要、状态、模型、耗时、工具数、文件变更数、provider 调用数；展开后再呈现用户消息、过程、最终回答、错误和证据。这样继续沿用现有 `turns/messages/toolEvents/fileEffects/providerCallCount`，不需要另造状态真相源。
2. **将执行事实收敛为明确的 Evidence 区。** 每个 turn 下分为“文件”“命令/终端”“上下文”三类可展开证据。文件使用 `fileEffects` 显示路径、edit/write、diff 与是否仍仅保留外部副作用；命令关联 `terminalId`、退出码、输出和错误；上下文显示 provider/model、调用数、artifact 可用性。卡片内不应仅靠一个文件图标承担这些含义。
3. **把 lineage 变成可读信息。** 分支 Session 显示“从 <源 Session> 的第 N 轮分出”，分支点在时间线上可跳转；Fork 操作改为带文字或菜单的显式动作，并在确认/说明中强调它不复制工作区和外部副作用。
4. **将状态改为任务语言。** 例如“正在生成”“正在执行 2/3 个工具”“已停止，保留 992 字草稿”“失败：provider 超时，可重试”“已恢复历史（共 14 条）”。内部 revision/epoch 放在可选诊断详情中，而不消失或直接暴露技术术语。
5. **建立紧凑摘要与深入诊断的两层，而非把所有内容常驻。** 右栏适合摘要、当前 turn 和最近结果；完整 provider payload、完整命令输出、raw diff、request fingerprint 等放进展开 Drawer/Inspector 或默认程序打开的 artifact。这样能维护右栏的可读性，又不牺牲可观测性。
6. **重新排序 header 信息。** anchor/会话名称和 provider/model 是常用上下文；运行状态与可执行动作次之；“自举资格”应降到 Session metadata/实验开关处。若没有模型可用，应在输入区附近说明原因和下一步，而非只禁用 textarea。

### 优先级建议

若只做一轮展示迭代，优先做“Turn 工作单元 + 文件/命令/上下文证据摘要 + 可展开详情”。它能直接消费现有结构，且会同时改善工程任务的可读性、验证能力和错误定位。之后再补 Session lineage 与更丰富的状态语言。不要先做大而全的 Inspector；否则容易再次制造一套与聊天时间线脱节的平行界面。

- [ ] 由产品确认 Iris Agent 的主界面定位：轻量对话侧栏，还是以 Turn/Evidence 为核心的 Issue 工作台。
- [ ] 若选择工作台方向，为 `IrisAgentSessionInfo` 定义独立且最小化的 Renderer view projection，明确 turn 摘要、执行证据、lineage 和诊断详情各自所需字段。
- [ ] 以包含工具调用、文件修改、Stop/Retry 与 Fork 的真实 Issue 验证信息层级，而不是只用纯聊天流程验收。

## 真相之源、传输对象与渲染表示的关系（2026-08-18）

### 先给判断

现在的关系是**正确的单向数据流，但中间层不够明确，因而还谈不上特别优雅**：

```text
main 内存 / 持久化 Session canonical state
  -> IPC 返回与 sessionChanged 事件
  -> Renderer 的 irisAgentStore（按 scope、revision 做接收与选择）
  -> IrisAgentView 直接以 IrisAgentSessionInfo 渲染
```

它的优点是没有第二个可写业务真相源：Renderer 不自行推进 turn、不能编造工具结果、不能选择任意 artifact 路径；所有改变都以 `commandId + expectedRevision` 回 main，经 main 的 Session command chain、store 落盘和事件回推。对一个有 Worker、工具副作用、Stop、重启恢复的 Agent，这是非常重要的正确性基础。

但中间两段实际上把同一个 `IrisAgentSessionInfo` 同时用作：

1. canonical domain aggregate；
2. 持久化 JSON schema；
3. main -> Renderer IPC DTO；
4. React 的直接 view model。

这四种角色的边界尚未拆开。当前的“中间表示”不是一个真正被设计过的 IR，而是 canonical object 的近乎原样复制。因此我的评价是：**方向合理，当前阶段可接受，但随着功能增加必须演进；否则显示层会反向绑架 domain schema。**

### 当前哪些层已经分得很好

#### 1. Worker protocol 不等于 Session 真相源

`AgentWorkerRequest/AgentWorkerEvent` 已经是一个相对清晰的边界协议：它带 protocol version、correlation、worker epoch、request/turn/tool ID，并且只表达初始化、run、abort、tool request/result、stream、runtime state 等跨线程事实。

这是好的设计。Worker 不是 Session 的所有者；它不能直接写持久化文件，也不能把一次 `agent_end` 自己解释为“这个 turn 已完成”。main 收到 event 后，仍要用 active turn、requestId、workerEpoch、stop intent 和 domain reducer 判断其是否有效。这避免了把不可靠的异步事件误当成真相。

也就是说，Worker protocol 是 **event/effect protocol**，Session 是 **aggregate state**；两者没有混同。

#### 2. Provider 原始形态不等于用户对话形态

`IrisAgentMessage.providerMessage`、`providerOnly` 和 UI 的 `message.content` 已经体现出一层很有价值的双投影：

* provider message 用于恢复合法模型上下文；
* user-facing message 用于阅读；
* 工具循环中的 assistant envelope 可被保留为 `providerOnly`，却不会渲染成重复回答；
* stopped assistant 的 provider-safe 投影可以丢掉未完成 thinking/tool metadata，同时保留显示给用户的 partial text。

这不是简单的字段冗余，而是承认“模型协议语义”和“用户阅读语义”不同。此前 Stop 后继续的修复，也正是靠这条边界避免把 provider 的 `aborted` 直接当作可重放历史。此处设计是成熟的。

#### 3. artifact 不等于 Session 内嵌 payload

Provider context 的完整 payload 仍留在 main-owned 文件 artifact；Session/Renderer 仅持有 `providerContextAvailable`、`providerCallCount`、schema version 等能力和摘要。这也很对：它控制 IPC 体积、避免敏感内容进入 Renderer，并保持 artifact 的独立完整性和 hash 校验。

因此，真正的问题不是所有东西都被塞进 `IrisAgentSessionInfo`；问题是剩下仍在其中的对象，尚未区分“领域必要事实”与“本屏渲染需要的摘要”。

### 当前不够优雅的具体点

#### 1. aggregate 与 projection 的形状完全相同

Renderer 收到 `IrisAgentSessionInfo` 后，`IrisAgentView` 自己做：

* 按 turn 扫描 `messages`；
* 过滤 `providerOnly`；
* 再按 turn 扫描/分组 `toolEvents`；
* 从 turn 的多个 artifact boolean 推导图标含义；
* 从 Session state 和最后一个 turn 推导按钮状态；
* 从完整 session 列表按 anchor 推导选中 Session。

这不是错误，但意味着 React 组件知道了太多 aggregate 内部归一化方式：message 和 tool event 是平行数组、assistant 是否应隐藏取决于 `providerOnly`、artifact 有 legacy/assembled/provider-context 的兼容优先级。这类知识一旦分散到多个组件，未来 schema 迁移会很痛苦。

更好的关系不应是：

```text
canonical arrays -> React component 临场 join/filter -> DOM
```

而应是：

```text
canonical aggregate -> pure projection builder -> AgentSessionViewModel -> React DOM
```

注意这里的 projection builder 不是新真相源，只是一个确定性的、只读的函数。它可以在 main 构造后经 IPC 发出，也可以短期先在 shared pure module 中由 Renderer 构造；关键是把“如何阅读 aggregate”从 JSX 中拿出来，并有独立测试。

#### 2. `IrisAgentSessionInfo` 同时包含三种时间尺度

同一对象中混合了：

* **长期审计事实**：`fileEffects`、`undoReceipts`、`requestFacts`；
* **当前会话叙事**：turn/message/tool event；
* **瞬态控制状态**：`state`、`activeTurnId`、`stopRequestedTurnId`、`workerEpoch`、`revision`、`pendingArtifactCleanupTurnIds`。

它们都可以是 canonical state，但不应该自动拥有相同的 Renderer 生命周期和刷新频率。流式 text delta 或 tool state 更新会令整个深层 Session snapshot 经 IPC 重新发送；随着历史、diff、file effect 增长，这会让“一个字符到达”携带越来越大的历史对象。现在规模尚小，逻辑上却已经出现了 O(完整 Session) 的投影刷新模式。

更重要的是，长期审计事实的语义不总是“当前 timeline 的子集”。例如 Undo 会删掉 message/turn/tool event，却刻意保留 `fileEffects`，并通过 `undoReceipts.externalEffectsRetained` 表示副作用仍真实存在。这是正确的 domain 决策，但若 view 层只把所有数组当成同一段聊天历史，就会自然产生误读。

#### 3. 状态机没有显式投影为 UI 状态机

domain 层的 `state + activeTurnId + stopRequestedTurnId + latest turn status + running tool events` 联合决定真实状态；UI 再用另一套条件推导 `running`、`latestRetryableTurn`、`canUndoLatestTurn`。两者目前大体一致，但这是隐式重复，而非显式契约。

例如 `ready`、`idle`、`failed` 是 Session runtime state，`completed/stopped/failed` 是 Turn terminal state；某个按钮是否可点还要依赖模型目录可用性和 revision。它们应被收敛为一个展示态，如：

```ts
type AgentSessionPresentationState =
  | { kind: 'ready-to-send'; model: 'available' | 'unavailable' }
  | { kind: 'generating'; turnId: string }
  | { kind: 'executing-tool'; turnId: string; runningToolCount: number }
  | { kind: 'stopping'; turnId: string }
  | { kind: 'retryable'; turnId: string; reason: 'stopped' | 'failed' }
  | { kind: 'failed'; message: string };
```

这不是把 domain 状态压扁或丢失，而是让视觉逻辑只消费其真正需要的联合结果。现在 JSX 直接理解 domain state，未来很容易在新状态添加时漏掉一处。

#### 4. ID 关联完备，关系投影却不完备

数据中已有可靠关联：`turnId`、`requestId`、`toolCallId`、`terminalId`、`retryOfTurnId`、`parentSessionId/forkedFromTurnId`。这是正确的 normalized design。但目前只有 `turnId` 真正被 UI join 使用；其余多半停在 domain 中。

从架构角度，这不是“UI 没展示字段”这么简单，而是 projection 没有定义关系对象。比如一个 turn 的投影理应已经含有：

```ts
interface AgentTurnView {
  turn: TurnSummary;
  request: UserMessageView;
  activity: Array<ToolActivityView | AssistantProgressView>;
  answer: AssistantMessageView | null;
  evidence: TurnEvidenceSummary;
  retry?: { sourceTurnId: string };
  actions: { canStop: boolean; canRetry: boolean; canUndo: boolean; canFork: boolean };
}
```

这样 `fileEffects` 可以明确归入 source turn，即使该 turn 已从 timeline 被 Undo，projection 也可以在审计区表达“来自已撤销对话的已保留副作用”，而非让组件到处猜测数组关系。

### 是否应该完全拆成事件溯源？不应该急着做

当前已有 append-like 的 messages/tool events、turn status 和 undo receipt，容易让人想把它彻底改成 event sourcing。我的看法是**暂不值得**。

原因是 Session 需要的不是任意时点重演所有内部过程，而是：

* 快速恢复一份当前可运行的 canonical state；
* 将合法历史注入 provider；
* 对 Stop/Retry/Rewind 等命令做原子、可验证的变换；
* 保留有限的审计证据。

现有 aggregate + reducer + artifact 已能满足这个目标。全面 event log 会引入 schema 演进、replay、snapshot、compaction 与 artifact 关联的额外复杂度，反而会稀释当前正在收口的可靠性工作。正确的演进是增加**读模型/projection**，不是重写写模型。

### 我建议的目标分层

```text
A. Domain / write model（main-only，canonical）
   IrisAgentSession aggregate
   - turn/message/tool/effect/lineage/state
   - reducer、invariant、revision、durability

B. Runtime event protocol（Worker <-> main）
   AgentWorkerEvent / AgentWorkerRequest
   - 不可信的异步事实，必须由 A 校验和归约

C. Persistence / artifact model（main-only）
   session JSON + provider-context artifact + terminal output
   - 可恢复、可校验、权限与脱敏边界

D. Renderer projection（IPC DTO，只读）
   IrisAgentSessionView
   - session header summary
   - ordered AgentTurnView[]
   - explicit actions/capabilities
   - evidence summaries / lineage summary
   - 不含 provider payload、密钥、原始大输出和不必要的内部状态

E. Renderer local UI state（短暂、不可作为业务真相）
   selected session、折叠状态、滚动位置、临时输入草稿、打开的详情 tab
```

A 到 D 应是单向、确定性的；E 只能影响“怎样看”，不能改变“发生了什么”。命令仍从 E 发起，但必须携带 D 提供的 revision/precondition 回到 A。这保留当前系统最重要的并发正确性特性。

### 过渡方案：不需要立刻大拆

可以分三步演进，且每步不改变 canonical 真相源：

1. **先抽纯 projection 函数。** 输入完整 `IrisAgentSessionInfo` 与 model availability，输出按 turn 分组的视图对象和 action capability。当前 IPC 仍传 `IrisAgentSessionInfo`，但 `IrisAgentView` 不再自己 join/filter/推导。这一步主要解决逻辑重复与可测试性。
2. **再定义 IPC read DTO。** 由 main 在 `list/open/sessionChanged` 处输出 `IrisAgentSessionView`，保留命令所需的 revision 和 ID，删除 Renderer 不应依赖的 providerMessage、完整 before/after file content、request fingerprint、cleanup queue 等内部字段。需要诊断时按受控 action 请求摘要或 artifact，而不是常驻下发。
3. **最后按刷新频率拆投影。** Session header/turn summary 走小而频繁的 patch 或 snapshot；展开某个 turn 的 diff、完整 output、artifact index 时按需读取。不要在流式 delta 时反复克隆/跨 IPC 传输整个历史。

这里最关键的准则是：**projection 不是 domain 的镜像，而是用户任务的读模型；但每一项可见事实都必须能追溯回 canonical state 或不可变 artifact。**

### 最终评价

当前架构已经避免了更危险的两种反模式：Renderer 成为业务真相源，以及 provider/Worker 事件直接驱动 UI 真相。因此它在正确性上是合理的。

不够优雅之处在于“domain aggregate 原样泄露为 view model”。这在 MVP 可以节省实现，但会让领域字段、持久化兼容字段、并发控制字段和视觉需求相互耦合。只要下一步不是继续在 JSX 中堆条件，而是补一个显式、只读、可测试的 projection 层，我认为这套底座能平稳演进为很干净的 Agent 架构。
