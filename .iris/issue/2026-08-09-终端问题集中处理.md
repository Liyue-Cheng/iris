## 初步调研（2026-08-09）

这轮先做只读调查，没有修改终端代码。当前结论是：几个表面不同的 bug 并不是都来自同一处，但它们共享同一个结构性放大器，即终端的数据面、协议仿真、replay、视口、输入策略和 React 生命周期没有形成明确的所有权与背压边界。

### 已由当前代码确认的风险

* `TerminalView.tsx` 约 43 KB、1069 行。它同时创建 xterm 和 addons，处理 replay、seq 去重、resize、WebGL、IME 私有 API、搜索、剪贴板、确认框、文件/文档拖入、字号设置和 React UI。异步操作依赖可变 ref，session/runtime lifetime 没有统一 token。

* `SessionManager` 约 40 KB、1079 行。它同时承担 PTY 生命周期、输出合批、active/idle 推断、headless xterm、replay 事务、resize/redraw、序列化、标题解析和进程树回收。生命周期状态机与字节流状态机混在一个对象中。

* main 会把每个 session 的输出广播给 renderer；当前只有可见 `TerminalView` 真正消费，但不可见 session 的字节仍经过 base64、Electron IPC 和 renderer 事件分发。多会话同时输出时存在确定的无效数据搬运。

* main 的 headless xterm 与可见 browser xterm 都直接调用 `write()`，没有按 write callback 确认消费进度，没有 pending bytes 上限，也没有 PTY `pause()` / `resume()` 背压。xterm 当前版本的 `WriteBuffer` 源码明确写明：积压超过约 500 KB 时通常已经无响应，50 MB 才会抛弃数据并报错。当前代码没有在到达这两个阈值前采取动作。

* 每个 PTY 字节至少经过 main headless parser 和可见 browser parser 两次。main 还会同步执行最多 5000 行的 serialize 和 base64 编码。用当前依赖做的本机基线中，约 734 KB / 6500 行输入的 headless parse 为 47 ms，生成约 568 KB replay 的 serialize 为 59 ms。该数值不是产品性能结论，但足以说明这些工作不能继续没有预算、队列深度和退让点。

* OSC 10/11 颜色查询证明“终端协议回复”目前没有稳定所有者：headless mirror 不能回答，browser xterm 会通过 `onData` 回答，但它只在可见和 replay 完成后可靠存在。协议查询、普通用户按键和粘贴最终都走同一个 `SESSION_INPUT` 入口。

* 当前自动化测试主要覆盖 main 会话生命周期、8 ms 合批和一个 Codex 风格 replay 用例；没有覆盖 `TerminalView` runtime、背压、renderer 消费停滞、用户滚动期间的 live redraw、OSC 查询所有权及异步输入跨 session lifetime。

### 对“完全卡死”的当前判断

目前最强的代码级候选不是一个永久 pending 的 Promise，而是无背压的数据面把 xterm parser、Electron IPC 或 renderer 主线程压入持续积压。它能同时解释“不再输出”和“点击也不响应”。replay 的同步 serialize、base64 和集中 flush 会放大停顿，但现有 250 ms / 500 ms / 5 s 超时意味着它们单独更像有界卡顿，不足以解释所有完全失去响应的情况。

现有 main 日志没有出现 `render-process-gone`、OOM、replay fence capped 或 replay redraw capped，因此还不能判断卡死发生在 main、renderer、GPU 还是 ConPTY。没有日志不等于这些路径正常，只说明当前日志只擅长记录崩溃和少数超时，不能记录事件循环饥饿、xterm pending bytes、IPC backlog 或最后成功消费的 seq。

### 旧性能监视器审计

不恢复 6 月删除的旧性能面板，也不采信它给出的阶段耗时。已确认的测量错误包括：

* `terminal.replay.write` 在调用 `term.write()` 后就结束，只测到了 enqueue 和人为 `setTimeout(0)`，没有等待 xterm parser callback。

* `terminal.replay.totalToReveal` 在 `scrollToBottom()` 和 RAF 之前结束，不代表用户已经看到完成帧。

* `terminal.replay.ipc` 混合了 IPC 排队、main 的 resize、等待 TUI redraw、parser fence 和 serialize，却在 UI 中作为单一 IPC 阶段展示。

* main / renderer 事件使用各自的时钟和独立 ring，再按 wall clock 合并；高频事件会挤掉真正需要的异常上下文。面板本身还会复制快照、通知 React 和每秒轮询 main，可能改变被测路径。

后续如加入观测能力，应是终端专用 flight recorder，而不是先做用户可见的通用性能面板：只记录状态转移、seq、水位、暂停时长和异常前后的有界窗口；每个阶段必须用同进程单调时钟测量，并以 xterm write callback 作为 parser 完成边界。renderer 卡死时不能指望 renderer 自己展示或导出数据，异常快照应由 main 的窗口 `unresponsive` 事件、renderer heartbeat 中断或队列高水位触发并低频落盘。记录器本身需要校准测试，证明注入已知延迟后读数一致。

### 建议的目标边界

1. `terminal-domain`：纯 reducer 和不变量，描述 session lifetime、attachment epoch、replay/live/history-frozen/resync/disposed 状态，以及 seq/ack/watermark 转移；不依赖 Electron、React 或 xterm。
2. `terminal-protocol`：跨 chunk 的 OSC/CSI 解析与所有权分配。main/worker 回答 OSC 10/11 并从下游显示流中消费查询，避免 browser xterm 迟到或重复回答。暂不把 Codex 的 ED2/DECSTBM 做无状态字符串过滤。
3. `terminal-output-pump`：main 数据面。只向已 attach 的可见/保活 runtime 发送输出，使用二进制 MessagePort、消费 ACK 和高低水位；任一必要消费者积压时暂停 PTY，降到低水位再恢复。生命周期命令不与字节流共用此队列。
4. `terminal-mirror-worker`：把 headless xterm parse、serialize 和协议查询检测移出 Electron main event loop。`node-pty` 本身保持在 main，因为依赖明确说明它不是 thread-safe；worker 只拥有纯字节状态和快照生成。
5. `terminal-session-runtime`：renderer 中脱离 React 的 runtime，拥有 browser xterm、transport port、attachment epoch、write ACK、replay/resync 和 dispose。React 只负责 host、搜索栏和上下文菜单。
6. `terminal-viewport`：负责 fit/resize、是否位于底部、用户查看历史时冻结可见 runtime，以及回到底部后的原子 resync。冻结期间 main mirror 和 PTY 继续运行，不缓存无上限的中间动画。
7. `terminal-input-policy` 与 `terminal-input-operation`：纯函数决定大文本、ESC、多行、路径元字符和 quoting；operation 在开始时捕获 sessionId、runtime instance 与 epoch，每个 await 后统一校验，失效即取消。
8. FrontCPU 只承载控制面命令和可观测的恢复动作，如 open/close/reanchor/recover；按键、PTY 输出、xterm write ACK 不进入现有业务流水线。真正耗 CPU 的 headless parse/serialize 使用 worker thread，而不是把高频字节伪装成 FrontCPU instruction。

### 建议实施顺序

- [ ] 先建立终端专用 flight recorder 与可重复压力 harness，并用已知延迟、已知字节数和 xterm callback 校准；记录 renderer heartbeat、main event-loop lag、每 session 输入/输出速率、mirror pending bytes、renderer in-flight bytes、PTY pause/resume 和最后 ACK seq。

- [ ] 提取纯 `terminal-domain`、replay ordering、input policy 和 lifetime token，先用 fake ports/fake clock 锁住现有行为，不在同一阶段改变 IPC 协议。

- [ ] 建立 attach/detach 的定向二进制输出通道，停止向 renderer 广播不可见 session 输出；加入 ACK 水位和 PTY 背压，并做 renderer 停止 ACK、worker 停止 ACK、端口断开和 50 MB 前永不触发 xterm discard 的故障注入测试。

- [ ] 将 headless mirror 与 serialize 迁到 worker，main 只保留 node-pty、session registry 和流量控制；worker 崩溃时会话不退出，进入 degraded 状态并可重建 mirror。

- [ ] 把 OSC 10/11 等终端回复的所有权迁到 main/worker，补全跨任意 chunk 边界、renderer 未挂载、replay、隐藏和切换场景。

- [ ] 引入 renderer runtime 状态机并收薄 `TerminalView`；同时修复异步粘贴/拖入 lifetime。评估有上限的 warm runtime LRU，隐藏实例必须保持稳定尺寸并暂停渲染，不能重用曾导致 WebGL atlas 损坏的 `display:none + live render`。

- [ ] 最后实现 history-frozen/resync，并用真实 Codex 控制序列 fixture 覆盖用户向上滚动、DEC 2026 跨 chunk、DECSTBM 未复位、ED2/ED3、输入触发回底和 session 切换。

### 仍需继续确认

- [ ] 用当前真实开发版复现一次完全卡死，并确认运行的确是当前源码；同时采集 Windows 任务管理器中的 main/renderer/GPU CPU 与内存、窗口是否触发 `unresponsive`、PTY 子进程是否仍存活。

- [ ] 做 renderer browser xterm 的持续输出压力测试，而不只测 headless；找出本机从正常交互到明显输入延迟、窗口无响应和 xterm 50 MB discard 的实际水位。

- [ ] 验证 `node-pty.pause()/resume()` 在当前 Windows bundled ConPTY DLL 路径的行为、恢复后字节完整性和对子进程阻塞语义，再确定正式高低水位。

- [ ] 对比 DOM 与 WebGL 在同样输入速率和用户滚动下的失效模式；WebGL context loss、renderer hang 与协议 buffer 错乱必须分开归因。

## 方向校正：以结构治理为主（2026-08-09）

用户补充确认：完全卡死很少见，不应成为本轮重构的主轴。本轮首要目标是建立清晰、可验证、能继续承载终端问题排查的代码结构。卡死、Codex viewport、OSC 颜色回复和异步粘贴都是新结构建立后的行为课题与验收样本，不以任何一个低概率现象反向决定全部架构。

因此，上文“建议实施顺序”中的二进制 MessagePort、PTY 背压、worker thread 和 flight recorder 不作为第一阶段必做项。它们是目标边界允许的后续演进方向，只有在结构拆分完成、测量边界可信且真实数据证明需要时才实施。第一阶段保持当前 IPC、base64、单可见 xterm 和 main headless mirror 的外部行为不变。

## 结构治理目标

治理不是把两个千行文件机械切碎，而是做到以下几点：

* 每份可变状态只有一个所有者，其他层只能通过事件或命令读取其投影。

* React 组件不编排终端协议；main facade 不直接实现所有 PTY、mirror、replay 和活动状态细节。

* 纯决策与副作用分离。纯逻辑输入完整事实、输出明确 decision/transition；计时器、IPC、xterm、DOM 和对话框通过窄端口执行。

* 每个异步流程拥有明确 lifetime/epoch，所有 await 返回后都能判断结果是否仍属于当前 session 和 runtime。

* `active/idle` 产品活动状态、PTY 进程生命周期、renderer runtime 阶段和输出流状态使用不同类型，不能继续都隐含在 `ManagedSession` 的字段组合里。

* 保持分阶段可合并。每一步都应能独立通过测试和类型检查，不能依赖一次性替换整个终端栈。

## 状态所有权

| 状态 / 事实 | 唯一所有者 | 对外形态 |
| --- | --- | --- |
| PTY 进程、PID、退出与关闭 | main session lifecycle | `SessionInfo` 生命周期投影与事件 |
| 用户语义上的 active / idle | main activity classifier | `SessionInfo.state`，内部不与进程状态混用 |
| 输出 seq、合批边界 | main output pump | 有序 `SessionOutputPayload` |
| 可脱离 renderer 存活的终端状态 | main terminal mirror | replay snapshot |
| 同一 session 的 replay 串行事务 | main replay coordinator | 一次 request/response，不暴露内部锁 |
| 可见 xterm、addons、parser write queue | renderer session runtime | runtime command/query facade |
| replay/live/history/resync 阶段 | renderer runtime reducer | 只读 runtime snapshot |
| cols/rows、fit debounce、底部/历史视口 | renderer viewport controller | viewport event/decision |
| paste/drop 的安全判断 | shared pure input policy | decision，不直接弹框或发送 |
| 一次异步 paste/drop 的有效性 | renderer input operation | 捕获的 sessionId + runtime epoch |
| 搜索文字、菜单开关等短期界面状态 | React UI | component state |
| 当前 anchor 与每个 anchor 的选中 session | 现有 project/session stores | 不进入 terminal runtime |

需要特别拆开的概念：

* `processState`: `spawning | running | exited | closing | disposed`。

* `activityState`: `active | idle`，只在 process running 时存在。

* `runtimePhase`: `created | attaching | replaying | live | history-frozen | resyncing | degraded | disposed`。

* `outputState`: `flowing | paused | closed`。第一阶段可以只有类型和 reducer，不必立即实现 pause/resume。

公开的 `SessionInfo.state` 暂时保持兼容；main 内部先拆开，facade 再把 `processState + activityState` 投影为现有 `active | idle | exited`。

### shared terminal domain

`runtime-reducer.ts` 只表达事件是否合法、下一阶段是什么、应产生哪些 effect request。例如 `ATTACH`、`SNAPSHOT_RECEIVED`、`REPLAY_DRAINED`、`USER_LEFT_BOTTOM`、`RESYNC_FAILED`、`DISPOSE`。reducer 不调用 xterm，不启动 Promise，不读取时间。

`replay-ordering.ts` 负责 snapshot boundary、hold queue、seq 去重和释放顺序。输入是 `{lastSeq, queuedPayloads}`，输出是 `{accepted, filtered, nextLastSeq}`。当前散落在 `TerminalView` 的循环应先以 characterization test 锁住，再迁入。

`input-policy.ts` 负责文本字节数、ESC、多行、bracketed paste 和危险路径分类，输出一个有序确认计划；`shell-quoting.ts` 只负责明确 shell flavor 下的 quoting。二者都不能引用翻译、confirm dialog、xterm 或 Electron。

现有 `terminal-keybindings.ts` 已符合纯模块方向；IME 两个 helper 也已可注入测试。治理时只调整归属和通过 `xterm-compat` 统一接入，不重写已验证逻辑。

### main terminal service

`session-service.ts` 是现有 `SessionManager` 的最终 facade，保留 `create/list/get/sendInput/resize/prepareReplay/close/shutdown` 这组稳定 API。IPC 仍只依赖 facade，不认识内部模块。

`session-record.ts` 定义 main 内部记录，替代当前不断扩张的 `ManagedSession`。记录只组合各 owner 的 handle/snapshot，不让任意方法随意修改所有字段。

`session-lifecycle.ts` 负责 spawn、PTY disposables、exit、close 和 process tree；`process-tree.ts` 隔离 Windows `taskkill` 与超时。生命周期代码不处理 ANSI、replay 或 active/idle 判断。

`session-activity.ts` 用纯 transition 管理 startup/resize/input quiet window 和 idle deadline。PTY 输出只向它发送事实事件；它返回是否需要广播状态变化。

`output-pump.ts` 负责 UTF-8 bytes、seq、8 ms batching 和 flush-on-exit。headless mirror 与 renderer broadcast 都从同一个 batch/seq 事实派生，避免边界语义分叉。第一阶段保持现有广播协议；背压和定向 attach 是它未来可替换的 transport policy。

`terminal-mirror.ts` 是 `@xterm/headless` 与 SerializeAddon 的唯一直接使用点，提供 `write/fence/resize/snapshot/dispose/title` 窄接口。其他 main 模块不访问 headless `_core`。

`replay-coordinator.ts` 只负责编排同 session 串行、alt-buffer resize/redraw、quiet wait、mirror fence 和 snapshot。所有超时由注入 clock/timer 管理，测试不依赖真实 500 ms。

`terminal-title.ts` 收纳 `sanitizeTitle` 和 startup garbage 判断；绝大部分为纯函数，现有测试可以直接迁移。

### renderer terminal runtime

`terminal-runtime.ts` 是一个 session 对应一个实例的非 React orchestrator。它组合 transport、replay、viewport、input 与 xterm adapter，公开 `mount(host)`、`focus()`、`paste(intent)`、`search(command)`、`setOptions()`、`dispose()` 等命令，并提供只读 snapshot/事件给 UI。

runtime 创建时获得不可变 `sessionId`、`ProjectScope` 和递增 `epoch`。异步操作只持有 runtime handle；dispose 或重新 attach 会使旧 epoch 失效。组件不再依赖 `termRef.current` 判断一个异步结果属于谁。

`terminal-runtime-registry.ts` 决定 runtime 是否随 React unmount 销毁。第一阶段可以继续“一次只保留可见 runtime”，但策略被隔离后，未来才能安全评估 bounded warm LRU，而不用再次改写 `TerminalView`。

`terminal-transport.ts` 是 renderer 中唯一可见 `window.api`、`CHANNELS` 和 `EVENTS` 的位置。它负责 scope、订阅取消、payload codec 和 IPC 错误规范化，不负责 seq、replay 或 xterm。

`replay-controller.ts` 执行 reducer 给出的 replay effects：先订阅、请求 snapshot、最多一次尺寸重试、写 snapshot、释放 live queue、parser fence 和降级。写入完成必须以 xterm callback 为边界，不能再用“调用过 `write()`”代表完成。

`viewport-controller.ts` 组合 ResizeObserver adapter、trailing debounce、最小尺寸、replay gate、输入前 flush 和 bottom/history 判断。它产生 `FIT` / `SEND_RESIZE` / `ENTER_HISTORY` 等 decision，不直接访问 IPC。

`input-controller.ts` 执行 pure input policy 给出的确认计划。clipboard/doc read/dialog 都是注入端口；每次 await 后统一检查 runtime epoch，再由 xterm adapter paste 或 transport send。

`xterm-adapter.ts` 是 `Terminal`、Fit/Search/WebLinks/WebGL addon 的唯一创建和直接调用点；`xterm-compat.ts` 集中 `_core` feature detection、IME patch、DECSTBM/cursor serializer compatibility 和安全降级。普通 controller 只依赖最小 `TerminalPort`，不 import xterm 类型。

### React UI

`TerminalView.tsx` 最终只负责获取 runtime、提供 host、把 runtime snapshot 映射到 UI，并连接 DOM drag/paste/wheel 入口。它不应直接出现：

* `window.api`、`CHANNELS`、`EVENTS`。

* replay queue、`lastSeq`、snapshot timeout。

* `ResizeObserver`、fit debounce。

* xterm `_core`。

* 大文本/ESC/多行/路径安全规则。

`TerminalSearchBar` 与 `TerminalContextMenu` 只保留展示和明确用户命令；它们不获取 terminal ref，不自行做 IPC。

```text
        +----> main adapters (node-pty / headless xterm / process tree)
        |
        +----> pure shared terminal domain
```

禁止反向依赖：shared 不 import renderer/main；controller 不 import React；main IPC 不访问 session record；UI 不 import protocol channel；xterm private API 不越过 compat adapter。

## 状态机契约

renderer runtime 的基础转移：

```text
created -> attaching -> replaying -> live
                     \-> degraded
live -> history-frozen -> resyncing -> live
                         \-> degraded
created/attaching/replaying/live/history-frozen/resyncing/degraded -> disposed
```

关键不变量：

* `disposed` 后任何 Promise、timer、RAF、ResizeObserver 或 xterm callback 都不能产生外部 effect。

* 同一 epoch 只有一个 replay/resync 在提交；旧请求可以完成，但结果必须被忽略。

* `live` 前到达的输出只能进入有上限、可统计的 hold queue；snapshot 内与 live queue 中的 seq 不能同时被应用。

* parser fence 完成前不能宣称 replay 完成；UI reveal 与 focus 是 replay 完成后的独立 effect。

* `history-frozen` 不等于 PTY 暂停，也不等于 main mirror 暂停。

main process 的基础转移：

```text
spawning -> running -> exited -> closing -> disposed
                   \-> closing -> disposed
spawning -> failed
```

关键不变量：

* session registry 只有 lifecycle 能插入/移除 record。

* exit 前先 flush 最后输出；renderer 观察顺序永远是 output -> exited -> state patch。

* close 幂等，重复调用共享同一个 Promise。

* activity timer 不能让 exited/closing session 回到 active/idle。

* replay 失败不能改变 PTY 生命周期；mirror 失败与进程退出是不同故障域。

## 测试治理

测试分四层，不用一开始 mock 整套 React + browser xterm：

1. 纯函数测试：reducer transition table、非法事件、seq ordering、paste decision、shell quoting、activity quiet windows、title sanitize。
2. controller 契约测试：fake transport、fake terminal port、fake clock、fake dialog，覆盖 dispose/epoch、超时、失败降级和调用顺序。
3. main adapter 集成测试：fake PTY + 真实 headless xterm，覆盖 split control sequence、snapshot、resize redraw、exit causal order。
4. 少量真实 browser/Electron 场景：xterm mount、WebGL/DOM fallback、真实 ResizeObserver、用户滚动和首帧。它们验证适配层，不承担所有状态组合。

每个已知 bug 都转成边界测试，而不是继续堆到大组件测试中：

* Codex DEC 2026 / ED2 / DECSTBM -> mirror/replay integration fixture。

* OSC 10/11 迟到回复 -> terminal protocol ownership test。

* 确认框期间切 session -> input controller epoch test。

* 用户向上滚动时局部刷新 -> viewport/runtime transition test + browser integration。

* renderer 停止消费 -> output pump 的未来背压 contract test。

## 执行步骤（人话版）

一句话概括：先用测试记住终端现在应该怎么工作，再把两个千行大文件按职责逐步拆开，等每块代码都有明确主人和测试后，再修具体 bug。前几步不改用户看到的终端行为，也不一上来就换通信方式或上 worker。

### 第 0 步：先把现状记清楚

- [ ] 列出几种真正要支持的使用场景：普通 shell、持续大量输出、全屏 TUI、Codex 这类行内 TUI、已经退出的会话。对每种场景记录打开、切换、缩放、滚动、粘贴和关闭时应该发生什么。

- [ ] 把当前关键行为写成自动测试，尤其是重放顺序、窗口尺寸变化、active/idle 切换、粘贴安全检查，以及会话销毁后晚到的异步结果不能再写入终端。

这一步不是修 bug，而是给后面的重构加“护栏”。完成标准是：后面拆代码时，只要行为被意外改掉，测试就会立刻报错。

### 第 1 步：先把“怎么决定”从大文件里拿出来

- [ ] 把“输出按什么顺序显示”、“粘贴前是否要确认”、“会话何时算 active/idle”、“标题怎样清理”等规则拆成小型纯函数。

- [ ] 用一个小状态机记录终端正在挂载、恢复历史、实时运行还是已销毁，但暂时仍由现有 `TerminalView` 调用它。

- [ ] 把 xterm 私有 API 和 IME 兼容处理集中到一个隔离层，其他代码不再到处摸 xterm 内部字段。

完成后，这些规则可以不启动 Electron、不渲染界面就直接测试。终端外观和用法不应变化。

### 第 2 步：把后台的大管家拆成几个专职模块

- [ ] 保留 `SessionManager` 现有对外接口，但在它内部依次拆出：进程启停、active/idle 判断、输出合并与排序、后台终端镜像、历史重放。

- [ ] 明确规定每份状态只能由一个模块修改。例如，进程退出由进程生命周期模块管，输出序号由输出模块管，不再让任意方法都能改整个 session 对象。

这一步只整理后台代码，不换 IPC、不换 base64 传输、不把 xterm 迁到 worker。完成标准是：上层调用方式和对用户的表现保持不变，每个新模块都有自己的测试。

### 第 3 步：给前台终端建一个独立“运行时”

- [ ] 新建一个不依赖 React 的 terminal runtime，让它统一管理 xterm、IPC 订阅、历史重放、窗口尺寸、定时器和销毁。

- [ ] 每个 runtime 固定绑定一个 session 和一个世代号。切换或销毁后，旧任务即使晚点完成，也能识别自己已经过期并停止操作。

- [ ] 等 runtime 真正接管这些责任后，再从 `TerminalView` 删掉对应编排代码。

完成后，`TerminalView` 应主要负责把终端放到页面上和显示界面状态，不再自己维护整套终端流程。

### 第 4 步：把粘贴、拖入和界面操作从大组件里移出

- [ ] 把搜索栏和右键菜单拆成纯界面组件，它们只向 runtime 发送“搜索”、“粘贴”等命令。

- [ ] 把读取剪贴板、读文档、弹确认框和处理拖入统一交给 input controller。每次异步等待返回后，都重新确认用户还在原来的 session。

这一步会直接堵住“确认框弹出后切换会话，内容却粘到新会话”这类错误。验收时不只看 `TerminalView` 变短了没有，而要看它是否真的不再掌管 IPC、replay 队列、resize 定时器、xterm 私有 API 和粘贴安全规则。

### 第 5 步：在新边界上逐个修真正的问题

- [ ] 先修终端颜色查询的回复归属，确保它不再依赖当前可见的 browser xterm 碰巧回复。

- [ ] 再修“用户向上翻看历史时，实时刷新把画面搞乱”。用户离开底部后暂停更新可见画面，回到底部时再用一份完整快照对齐。

- [ ] 然后加入能定位“完全卡死”的最小观测数据，测出到底是 main、renderer、GPU 还是输出队列堵住。

- [ ] 只有当压力测试证明当前传输或解析确实是瓶颈时，再分别评估背压、定向 MessagePort、worker thread 或少量隐藏会话保活。每项性能改造单独立项，不和基础拆分混在一次改动里。

完成这一步后，每个 bug 都应能明确落到某一个模块，并有对应测试；不再需要进入一个千行文件同时理解所有事情。

### 每一步都怎么验收

- [ ] 一次只做一类调整，能单独提交、单独回退，不要等到所有终端代码都改完才集中验收。

- [ ] 现有测试、新模块的直接测试和三套 TypeScript 检查全部通过。

- [ ] 除非当前任务就是修某个用户可见的 bug，否则重构前后的界面、IPC 数据和事件顺序必须保持一致。

- [ ] 任何定时器、订阅或异步任务都必须有明确的销毁方式，并有“销毁后晚到结果不再生效”的测试。

以下“渐进迁移计划”是上述步骤的技术版清单，实际执行时以这份人话版的目标和顺序为准。

## 渐进迁移计划

### Phase 0：行为清单与 characterization

- [ ] 为现有 replay ordering、resize gate、activity quiet windows、input safety 和 dispose 后不写入建立 characterization tests。

- [ ] 建立终端行为矩阵：普通 shell、normal-buffer 连续输出、alternate-screen TUI、Codex inline TUI、exited session；打开、切换、resize、滚动、粘贴、关闭分别记录当前预期。

- [ ] 只加能证明测试边界的最小 hooks，不恢复旧性能面板，不先改变 IPC 或 runtime 生命周期。

### Phase 1：先提纯逻辑

- [ ] 提取 replay ordering、input policy、activity transition、title sanitize；让每个模块在 Node Vitest 中独立通过。

- [ ] 建立 runtime phase/epoch reducer，但先由现有 `TerminalView` 调用，保持 UI 和协议不变。

- [ ] 建立 `xterm-compat`，把 `_core` 探测与 IME attach 从 `TerminalView` 移出。

### Phase 2：拆 main，保持 facade

- [ ] 从 `SessionManager` 依次提取 process tree、activity、output pump、mirror、replay coordinator；每次提取后 `SessionManager` 的公开 API 和 IPC payload 不变。

- [ ] 把 `ManagedSession` 改为组合明确 owner handle 的 `SessionRecord`，禁止跨模块直接改字段。

- [ ] 保留现有 headless xterm 所在线程和 base64 transport，避免结构迁移与性能架构迁移同时发生。

### Phase 3：建立 renderer runtime

- [ ] 先引入 `terminal-transport` 和 `xterm-adapter`，把 IPC/xterm 直接依赖从组件移出。

- [ ] 将 replay controller 和 viewport controller 接入 runtime；用同一批 characterization tests 比较迁移前后事件顺序。

- [ ] runtime 完整接管 timer、RAF、observer、disposable 和 epoch 后，再收薄 `TerminalView`。

### Phase 4：拆 UI 与输入操作

- [ ] 提取 SearchBar/ContextMenu，命令只调用 runtime facade。

- [ ] 把 clipboard、doc read、confirm 和 drop 迁入 input controller，修复所有 await 后的 session/runtime 校验。

- [ ] 验收 `TerminalView` 中不再出现上述禁止依赖；行数只作信号，不作唯一指标。

### Phase 5：在新结构中逐项修行为

- [ ] 先解决 OSC 查询所有权，因为它能明确检验 protocol/main/renderer 边界。

- [ ] 再实现 history-frozen/resync，因为它检验 viewport/runtime/replay 协作。

- [ ] 之后处理卡死观测与背压；先在 output pump/terminal port 的现成边界上测量，再决定是否升级定向通道。

- [ ] bounded keep-alive、MessagePort、worker thread 均单独立项，以数据和故障模型决定，不与基础治理捆绑。

## 每阶段完成标准

* `npm test -- --run`、三套 TypeScript typecheck 全部通过。

* 新模块拥有直接测试，不能只由 `SessionManager.test.ts` 间接碰到。

* 没有为了拆文件同时改变 replay 协议、渲染策略或用户可见行为；行为变化必须单独提交并引用对应测试。

* 新旧实现短暂并存时只有一个生产入口，不能留下双状态源或 feature flag 长期分叉。

* 所有 async owner 都有 `dispose()`，并有“dispose 后晚到结果无 effect”的测试。

* main/renderer/shared 的依赖方向可从 import 直接看出，不依赖注释维持。

## 明确不做

* 不把 PTY 字节、每次按键或 xterm ACK 送进 FrontCPU。

* 不先恢复旧性能监视器或用不可信数据决定 worker/keep-alive。

* 不在一个阶段同时引入 worker、MessagePort、保活、replay 重写和 viewport 新策略。

* 不以“文件变短”代替状态所有权治理，也不创建只有一层转发、没有测试价值的抽象。

* 不让 renderer 的可见 xterm 继续承担会话级终端协议回复的唯一所有权。
