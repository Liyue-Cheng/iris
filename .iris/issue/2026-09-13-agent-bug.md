content.filter is not a function

## 排查结果（2026-09-13）

根因在 Agent 历史恢复到 Pi provider 上下文的类型转换：

- 持久化历史中的 `tool` 消息允许 `content` 是字符串（当前 Trace/历史数据大量使用这种形式）。
- `src/main/agent/pi-adapter.ts` 的 `toPiHistoryMessage()` 将 `tool` 消息映射为 `role: 'toolResult'`，但直接复用了 `toPiContent()`。
- `toPiContent()` 对字符串原样返回；因此传给 Pi 的 `toolResult.content` 可能是字符串。
- Pi 的 provider 适配层按协议假定 `toolResult.content` 一定是内容块数组，并调用 `msg.content.filter(...)`，于是字符串上没有 `filter`，触发 `content.filter is not a function`。

这不是某个具体模型返回异常，而是“历史消息格式（字符串）”与“Pi toolResult 协议（数组）”之间的边界转换遗漏。新产生的工具结果通常已经是数组，所以更容易在恢复旧会话、切换模型或重启 Agent 时暴露。

建议修复：仅对 `role: 'toolResult'` 使用专用转换，字符串包装为 `[{ type: 'text', text: content }]`；图片/文本数组继续按现有逻辑转换。并补一个回归测试，验证字符串形式的历史 tool 消息经过 `toPiHistoryMessage()` 后传给 provider 的 `content` 始终为数组。

- [ ] 修复 tool 历史消息的 content 类型转换并补回归测试

## 复现日志核对（2026-09-13）

刚刚复现的会话日志进一步确认了触发时机：

- 会话使用 `gpt-5.6-sol`，第一个 intent 共产生 16 次 provider call，全部正常完成。
- 第一个 intent 结束后，第二个 intent 在 `starting` / `running` 之后立即暂停，日志中没有第二个 intent 的 provider-context call，错误直接是 `content.filter is not a function`。
- `snapshot.json` 中第一个 intent 的每个工具结果（`turns[].toolResults[]`）的 `content` 都是字符串；例如 read/terminal 结果均为字符串。
- 第一个 intent 的 assistant replay 则保留为 GPT Responses 的结构化 `content` 数组（含 `thinking`、`toolCall` 或 `text`）。

因此错误不是 GPT-5.6 Sol 返回了坏数据，而是第二个 intent 重建 provider 上下文时首次走“持久化历史 → Pi 消息 → OpenAI Responses”路径：

1. `toPiHistoryMessage()` 把历史 `tool` 记录转成 `toolResult`。
2. 历史工具结果的字符串被 `toPiContent()` 原样返回。
3. `openai-responses` 适配器的 `convertToolResultOutput()` 对 `toolResult.content` 直接调用 `.filter()`。
4. GPT Responses 路径因此在发出第二个请求前同步抛错，`onProviderPayload` 尚未触发，所以日志里看不到第二个 provider call。

更正：不能说换成 DeepSeek 后能继续是因为它走了 OpenAI Completions 路径。实际记录显示，DeepSeek 会话的 provider-context 日志同样标记为 `api: "openai-responses"`，并且连续产生了 35 次正常请求。因此“DeepSeek 走 Completions、GPT 走 Responses”的解释不成立。

这也解释了为什么第一条 intent 正常、第二条稳定复现：第一条使用的是新建内存中的数组型 tool result；第二条才加载第一条已经持久化成字符串的历史。

## 综合治理方案（不兼容历史数据）

治理原则：不读取、不转换、不迁移旧历史格式。从当前版本开始，工具结果协议收敛为单一形态；不符合新协议的数据在 Iris 边界立即失败并给出明确诊断。

### 1. 收紧领域模型

- `tool` 消息的 `content` 统一为内容块数组，不再允许字符串联合类型。
- 文本结果统一表示为 `[{ type: 'text', text: '...' }]`；图片结果表示为文本块加图片块。
- Trace、Session history、Worker 消息和 Pi `ToolResultMessage` 共用同一套内容块定义。
- 用户消息仍可保留字符串快捷格式，但工具结果不得复用该快捷格式。

### 2. 统一转换边界

- `toPiHistoryMessage()` 对 `tool` 只接受规范数组，直接构造 Pi `toolResult`。
- 将用户消息转换和工具结果转换拆成不同函数，禁止一个 `toPiContent()` 同时承担两种协议。
- provider 适配器不增加字符串兼容逻辑，避免协议错误继续向下游扩散。
- history 组装完成后增加断言：所有 `toolResult.content` 必须是数组；失败信息包含 session、intent、toolCallId 和实际类型。

### 3. 从写入端消除错误形态

- 工具执行结果落库前统一经过唯一构造函数。
- read、edit、write、terminal、task、异常结果、中断结果和图片结果全部走该构造函数。
- Provider 返回的工具结果在写入 Iris 域模型时立即归一为数组；域模型不保存 provider 私有形状。
- 删除所有手写字符串型 tool result 的调用方式，让 TypeScript 在编译期阻止新代码写入错误形态。

### 4. 失败策略

- 非法内容在 Iris 边界暂停当前 intent，错误改为明确的 `tool result content must be an array`，不再暴露底层 `content.filter`。
- 错误附带 provider、model、sessionId、intentId、toolCallId 和检测边界。
- 不自动换模型、不自动重试同一份非法上下文；DeepSeek 能继续不能作为验收标准。

### 5. 测试矩阵

- 单元测试覆盖文本、图片、错误、空结果的统一构造函数。
- 转换测试保证 history → Pi 后每个 `ToolResultMessage.content` 都是数组。
- 集成回归：GPT-5.6 Sol 连续执行两个 intent，第二个 intent 必须实际发出 provider call 并完成。
- Provider 矩阵覆盖 `openai-responses` 和 `openai-completions`，两者接收相同的 Iris tool result 形状。
- 负向测试注入字符串 tool result，验证在 Iris 边界被拒绝，而不是兼容通过。
- Worker 重建测试覆盖首个 intent 完成后销毁/重建 Worker 再发送第二个 intent。

### 6. 观测与发布闸门

- provider 请求前记录脱敏后的消息形状摘要：角色、content 类型、块类型和数量，不记录正文。
- 将协议断言失败单独归类，和网络错误、HTTP 错误分开统计。
- 发布闸门必须包含类型检查、相关单测、Worker 测试和 GPT-5.6 Sol 双 intent 回归。
- 手工验收标准是：GPT-5.6 Sol 连续两个 intent 均成功，且日志中出现第二个 intent 的 provider-context call。

### 7. 实施顺序

1. 收紧工具结果领域类型并建立唯一构造函数。
2. 修改所有写入端，禁止产生字符串型 tool result。
3. 修改 history → Pi 转换并加入边界断言。
4. 补齐双 intent、双 provider、负向和 Worker 重建测试。
5. 增加错误分类与脱敏形状日志，完成 GPT-5.6 Sol 手工验收。

### 记录校正

- GPT 会话：`model: gpt-5.6-sol`、`api: openai-responses`，第一个 intent 16 次请求，第二个 intent 在首个 provider call 前抛错。
- DeepSeek 会话：`model: deepseek-v4-flash`、`api: openai-responses`，同样使用 Responses 请求格式，并在多个 intent 中持续成功。
- 因此当前已知差异不是 API 家族（Responses / Completions），而应继续比较两种模型在同一 Responses 适配器下的模型元数据、请求 payload 约束以及 replay 消息中 `thinking` / `toolCall` / `responseId` 等字段的组合。
- 不能把问题归因于“DeepSeek 的 Completions 适配器绕过了 `.filter()`”；该结论已被实际日志否定。

## 最终根因（2026-09-13）

继续对比 `pi-ai` 的实际转换代码后，已经可以解释为什么 GPT 稳定报错而 DeepSeek 能继续。真正的根因是两个缺陷叠加，其中第二个缺陷决定了不同模型的表象不同：

### 缺陷一：Iris 送入 Pi 的 toolResult 违反协议

`toPiHistoryMessage()` 把持久化的 `tool.content` 通过通用 `toPiContent()` 转换。字符串会原样返回，因此恢复历史后得到的是：

```ts
{ role: 'toolResult', content: '...', ... }
```

但 Pi 的 `ToolResultMessage.content` 协议是内容块数组。第一个 intent 运行在内存中，工具执行器产生的是数组；第二个 intent 重建 Worker、从 Trace 投影历史时，字符串才重新进入 provider 转换链。

### 缺陷二：`transformMessages()` 按 `model.input` 走出两种结果

`openai-responses-shared.ts` 在调用 `convertToolResultOutput()` 前会执行 `transformMessages()`：

1. 当 `model.input` 包含 `image`（GPT-5.6 Sol 的实际路径）时，`downgradeUnsupportedImages()` 不处理 `toolResult`。字符串继续传给 `convertToolResultOutput()`，后者执行 `content.filter(...)`，同步抛出 `content.filter is not a function`。因此请求尚未发出，也没有第二个 provider-context call。
2. 当 `model.input` 只有 `text`（本次 DeepSeek profile fallback 的实际路径）时，`downgradeUnsupportedImages()` 会对 `toolResult` 调用 `replaceImagesWithPlaceholder()`。该函数假定 content 是数组，却收到字符串；`for ... of` 会逐字符遍历，结果变成“字符数组”。随后 converter 对这些字符执行 `c.type` 检查，找不到 text/image block，最终返回 `(no tool output)`，所以请求继续但输出被丢弃。

因此 DeepSeek 并不是走了 OpenAI Completions，也不是证明字符串 tool result 合法；它只是被“非视觉模型的图片降级分支”意外把非法字符串清空了。这个路径还会静默丢失真实工具输出，是比直接报错更隐蔽的数据完整性问题。

### 因果链收敛

```text
工具执行结果（数组）
  -> Trace 持久化为字符串
  -> 第二个 intent 恢复历史
  -> toPiHistoryMessage 保留字符串 toolResult.content
  -> transformMessages 按 model.input 分叉
       ├─ GPT（含 image）：字符串原样到 convertToolResultOutput
       │                  -> content.filter is not a function
       └─ DeepSeek（fallback 仅 text）：字符串被逐字符“图片降级”成字符数组
                          -> (no tool output)，继续请求但丢失工具结果
```

所以“字符串 tool result”是跨模型都存在的协议违规；“GPT 报错 / DeepSeek 能继续”由 `model.input` 能力分支对该违规的不同处理造成。`api: openai-responses` 在两边完全一致，已排除 Completions 绕过解释。

### 对治理方案的影响

- 不能只修 `toPiHistoryMessage()` 的 GPT 报错；否则 DeepSeek 仍可能在其他入口继续静默丢工具输出。
- Iris 新协议必须让 `toolResult.content` 从写入、Trace、History 到 Pi 全链路始终是数组；非法类型在 Iris 边界直接拒绝，不做旧数据兼容或自动转换。
- Pi 的 `replaceImagesWithPlaceholder()` 也应增加类型前置校验，禁止把字符串当数组迭代；遇到非法 tool result 应明确报协议错误，而不是生成空结果。
- 回归验收不能只看“请求是否继续”。必须同时断言：GPT 路径不抛异常、DeepSeek 路径不会把工具输出变成 `(no tool output)`，并且两种 `model.input` 能力收到完全相同的规范数组。

## 对“视觉模型 / 实际图片”的校正（2026-09-13）

上一节把 `model.input` 直接解释为“模型是否是视觉模型”，这个表述不准确，现更正如下：

- 两份失败/成功请求的实际 provider payload 都没有图片块：`imageBlocks=0`。本次复现没有使用图片。
- `model.input` 是 Pi model metadata 的能力声明，适配器据此选择转换分支；它不是对当前请求内容的检测，也不能单独证明供应商模型的真实多模态能力。
- GPT-5.6 Sol 在内置 OpenAI catalog 中存在，元数据为 `input: ['text', 'image']`。
- DeepSeek V4 Flash 本身可以是多模态模型，但本次 Iris profile 使用的是 `openai-compatible` 模板，`profileModelsConfig()` 以 OpenAI 内置 catalog 查找该 model id。找不到 `deepseek-v4-flash` 时走 fallback，fallback 硬编码为 `input: ['text']`。因此日志里的 `['text']` 是“未知模型 fallback 元数据”，不是 DeepSeek 实际能力结论。

这反而把根因进一步收窄为**元数据驱动的错误分支 + 非法字符串输入**：

1. `toolResult.content` 是字符串，违反 Pi 的数组协议。
2. GPT 的 `input` 元数据包含 `image`，`downgradeUnsupportedImages()` 直接跳过，字符串到达 `convertToolResultOutput()` 后触发 `.filter()` 异常。
3. DeepSeek 的 `input: ['text']` 只是 fallback 元数据，于是进入 `downgradeUnsupportedImages()`；该函数把字符串当可迭代数组处理，逐字符遍历后得到空数组，输出 `(no tool output)`。

因此这里不能说“GPT 是视觉模型、DeepSeek 不是”，也不能说“因为请求中有/没有图片”。准确说法是：**同一非法字符串经过 Pi 的 capability metadata 分支被分别暴露为异常或被静默清空；本次请求实际没有图片。** 即使把 DeepSeek 的元数据正确标成 `['text', 'image']`，它也会复现 GPT 的 `.filter()` 异常；反过来，任何被错误 fallback 成 `['text']` 的模型都可能复现 DeepSeek 式的静默丢结果。
