## 现状

Iris Agent 消息区在两个 issue 之间切换时出现新的严重回归：

1. 从 issue A 切到 issue B，再切回 issue A，右侧消息区滚动条会先发生明显闪动。
2. 切回后没有可靠地回到底部，反而停在离开 A 时的历史位置。
3. 即使离开前正在接收 Agent 流式回复，切回后的视口也可能不是最新消息底部。
4. 该行为与用户期望的终端式滚动不一致：只有用户主动上滚查看历史时才应保持历史位置；处于底部时切换回来必须继续贴底。

本 issue 专门处理本次滚动回归。不要继续修改原“agent 第三批问题统一处理” issue，也不要借此调整 `RightPane` 外层顶栏、身份区或标签页视觉结构。

## 稳定复现步骤

* [ ] 打开一个存在 Iris Agent Session 的 issue A，等待已有消息或发送一条会产生流式回复的消息。

* [ ] 确认 A 的消息区位于底部，然后切换到 issue B。

* [ ] 再切回 issue A，观察右侧消息区首帧、滚动条位置和最终停留位置。

* [ ] 重复一次：在 A 中向上滚动一段距离，切到 B，再切回 A，确认是否应恢复历史位置且不被新消息抢回。

* [ ] 在 A 仍处于流式回复时快速切换 A/B 数次，观察是否出现跳动、停在旧位置或最终不贴底。

## 当前实现与上一轮修复

上一轮原实现位于 `IrisAgentView`：

```ts
useEffect(() => {
  if (!followMessagesRef.current) return;
  const frame = requestAnimationFrame(() => {
    viewport.scrollTop = viewport.scrollHeight;
  });
  return () => cancelAnimationFrame(frame);
}, [session.turns]);
```

它的问题是挂载后异步滚动，首帧可能先显示错误位置；同时 `followMessagesRef` 只存在于组件实例中，切换 issue 后会丢失。

上一轮整顿新增了 `src/renderer/lib/session-viewport.ts`：

* 以 `SessionKey` 为键在 renderer 内存中保存 `mode`、`scrollTop`、`scrollHeight` 和 `clientHeight`。

* `mode` 分为 `follow-bottom` 和 `free`。

* `IrisAgentView` 通过同构 layout effect 创建 `SessionViewportController`，尝试在首次 paint 前恢复位置。

* `ResizeObserver` 监听 viewport/content 尺寸，在 `follow-bottom` 模式下重新锚定底部。

* 底部进入阈值为 24px，退出阈值为 32px。

* 消息 viewport 设置了 `overflow-anchor: none`，避免浏览器原生锚定与应用锚定同时生效。

* `RightPane` 仍只挂载当前 `SessionProjection`，切换 issue 会卸载旧的 `IrisAgentView`，回来时重新挂载。

## 当前架构中的关键链路

```text
issue/anchor 切换
  -> sessionViewStore 选择新的 SessionKey
  -> RightPane 只渲染当前 ProjectedSessionView
  -> 旧 IrisAgentView unmount，SessionViewportController.dispose()
  -> dispose() capture 当前 scrollTop/mode
  -> 切回后重新 mount
  -> controller 从全局 memory 恢复 mode/scrollTop
  -> ResizeObserver / scroll / RAF 继续参与位置修正
```

Agent projection 更新链路仍然是：

```text
main session-manager emitChanged
  -> renderer irisAgentStore.handleProjectionUpdate
  -> 新的 turns/card projection
  -> React 重绘消息内容
  -> content ResizeObserver 回调
```

领域 Session、`SessionProjection`、Session 选择和 viewport 记忆必须继续分层；不要把滚动位置写入 Agent 持久化 Session，也不要让 `IrisAgentSessionManager` 感知 DOM 滚动。

## 初步判断

这次“停在上次离开的位置”本身可能是 viewport memory 按 `free` 模式恢复的结果，但当前实现没有可靠证明这个 `free` 是由用户主动上滚产生的。重点排查以下竞态：

1. controller 在恢复或底部锚定时写入 `scrollTop`，随后产生的 `scroll` 事件是否被当成用户滚动处理。
2. 首次 mount 时内容高度、viewport 高度或滚动条尺寸尚未稳定，导致当时距底部超过 32px，错误切换为 `free`。
3. `dispose()` 捕获时是否正好处于一次尚未完成的 RAF/ResizeObserver 修正之前，把临时位置写进了 Session memory。
4. 切换回来后，`follow-bottom` 与 `free` 恢复是否发生在不同的绘制阶段，造成“先闪动，再恢复旧位置”。
5. 流式 patch 导致 content 反复改变尺寸时，旧 controller 的 observer/RAF 是否仍能在卸载后触发，或迟到回调写入错误的 Session memory。
6. `overflow-anchor: none`、浏览器滚动事件时序和应用自己的底部锚定是否存在相互覆盖。
7. 多个 Session 是否可能因为 `SessionKey` 构造、销毁或 scope 切换错误而共享或污染 viewport memory。

不要先把“切回恢复上次位置”当成正确行为。正确行为必须由离开前的用户意图决定：用户在底部时恢复底部，用户明确上滚时才恢复历史位置。

## 治理要求

* [ ] 为 viewport controller 建立可观测的状态转换记录：`mount`、`restore`、`user-scroll`、`programmatic-scroll`、`resize`、`anchor`、`dispose`，至少包含 SessionKey、mode、scrollTop、scrollHeight、clientHeight 和距底部距离。

* [ ] 明确区分用户滚动与程序性滚动。任何恢复、锚定、布局补偿产生的 scroll 事件都不能单独改变 `mode`。

* [ ] 将“是否跟随底部”和“上次滚动位置”视为两个相关但不同的状态；不能通过一次 mount 时的默认值或一次 scroll 事件推断用户意图。

* [ ] 切换前保存必须是稳定状态：取消/合并待执行的 RAF，完成必要的尺寸采样，再决定保存 bottom anchor 还是 free position。

* [ ] 切回恢复必须是单一事务：首帧不可见错误位置，恢复期间不能被旧 observer、旧 RAF 或新一轮 scroll 回调覆盖。

* [ ] `follow-bottom` 下内容高度变化必须持续贴底；`free` 下内容高度变化不得抢回视口，也不得把一个暂时不可恢复的位置永久写成 0。

* [ ] Session 销毁、项目 scope 切换和 projection 替换后，所有迟到回调必须失效，不能污染新 Session 或同 anchor 的其他 Session。

* [ ] 普通终端继续使用自己的 xterm replay/history-freeze 机制；本 issue 统一 Session 视口边界和状态语义，不把 DOM 消息滚动强行改造成 xterm buffer。

## 验收标准

* [ ] 底部状态下切换 A/B/A：首个可见帧没有滚动条闪动，A 最终精确贴底。

* [ ] A 上滚后切换 B/A：A 恢复原历史位置，不自动跳底；持续收到新消息时位置保持稳定。

* [ ] A 回到底部后再收到新消息：自动跟随恢复，且不会在 24px/32px 边界抖动。

* [ ] 流式 token 高频更新期间快速切换多个 issue：不存在旧 RAF/observer 造成的跨 Session 写入、跳动或错误停留。

* [ ] Markdown 长文本、代码块、图片或卡片高度延迟变化时，底部模式仍贴底，自由模式仍保持用户视口。

* [ ] Session 已销毁或项目已切换后，迟到的 scroll/resize/RAF 回调不会重新创建或修改其 viewport memory。

* [ ] 增加 controller 状态机测试、切换生命周期测试、程序性 scroll 过滤测试和动态高度测试；不能只依赖静态 React markup 测试。

* [ ] 在真实 Electron 中完成手工复现矩阵，记录首帧是否闪动、离底部距离、切换次数、Agent 是否仍在流式输出以及最终 mode。

## 完成定义

只有当 Session 级 viewport 状态能够稳定表达用户意图，并且切换、流式 patch、动态布局和销毁竞态都经过自动测试与 Electron 手工验收后，本 issue 才能关闭。单纯把 `scrollTop` 再写一次、增加更长的 timeout 或默认强制滚到底部，都不算完成。

## 治理重设计（2026-09-03 追加）

### 为什么推翻旧模型，而不是继续加补丁

上一个实现把两个本质不同的问题揉在一个会自激的信号链上，这是它每次修完都复发的根因：

1. **用户意图由滚动位置推断。** `onScroll` 每次滚动都量 `distanceFromBottom`，用 24px/32px 阈值推出 follow/free。流式输出时内容在涨、程序性贴底的 RAF 还没执行，离底部距离会**瞬时**超过 32px → 系统把一次程序性滚动误判成"用户上滚了" → 永久切到 `free` → 切回来停在旧位置。阈值判断位置永远存在这个竞态，因为它用位置反推动机。
2. **freeze 位置用绝对像素记忆。** `scrollTop` 本身在流式下没有稳定参照；`dispose()` 采样到的还可能正好是"贴底前的一瞬"。恢复时写回这个已经过期的绝对值，自然停在旧位置。

### 新核心不变式

* **`mode`（`follow-bottom`** **/** **`free`）只在用户真正交互期间改变**，判断依据是"交互中的位置"，而非"任何 scroll 事件的位置"。`scroll` 监听器只做一件事：`capture()` 存当前状态，**永不**改变 `mode`。

* **交互门控** **`interacting`**：由 `wheel` / `touchstart` / `pointerdown` / 滚屏 `keydown` 这些只可能来自用户的事件置位，由 `pointerup` / `touchend` 以及 120ms 无手势超时复位。只在 `interacting === true` 期间才允许在滚动里做 follow↔free 判定。任何我们自己写的滚动（贴底、恢复、布局补偿）都不会被当成用户滚动 → 自激循环从根上消除。

* **freeze = 锚定视口顶部** **`scrollTop`（顶部锚）**。配合已有的 `overflow-anchor: none`，内容追加在底部时浏览器不会动 `scrollTop`，用户正在读的位置保持稳定——这正是终端 `freezeHistory` 的语义（通过固定的 buffer 索引锚定）。流式在底部增长时顶部锚是唯一正确的解；底部锚会在增长时把用户读的内容往上顶，反而不符合直觉。

  * **已知局限**：内容在冻结视口**上方**增长这一极端形状，顶部锚和底部锚都扛不住，需要 DOM 节点锚定。列为后续增强，不在本次范围。

* **follow 无条件贴底**：content 尺寸一变，同帧用 RAF 写 `scrollTop = maxScrollTop`，且不触发任何意图改变。

* **切换是一次事务**：`dispose()` 取消待定 RAF、断连 observer、置 `disposed` 使所有迟到回调失效，并 capture 稳定态。restore 在 `useLayoutEffect` 首帧前用当前 layout 恢复位置，freeze 位置 clamp 到 `[0, maxScrollTop]`，**不写 0、不丢意图**。
