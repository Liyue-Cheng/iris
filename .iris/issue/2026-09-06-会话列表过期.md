## 后续防护方案

当前 v1 -> v2 的处理能避免本次损坏数据阻塞启动，但后续版本应把“清空”升级为可恢复迁移，避免格式变更再次造成不可逆丢失：

- [ ] 为每个持久化根目录建立明确的 schema/generation manifest，升级前先执行兼容性检查；发现更高版本数据时只读并提示，不允许旧版本覆盖或删除。
- [ ] 将升级清理改为 quarantine：把旧的 agent 根目录按时间戳原子重命名到备份目录，再创建新目录；保留最近若干份，确认新版本稳定后再由用户显式删除。
- [ ] 将会话加载改为逐 session 隔离。单个 journal hash chain 损坏时标记该 session 为 `corrupt` 并显示恢复/删除入口，不能让整个会话列表加载失败。
- [ ] 为 journal 增加启动前校验和迁移演练：覆盖旧版本 fixture、断尾写入、乱序/断链、快照锚点失效、升级中途退出和重复启动。
- [ ] 在发布检查中强制要求：manifest 版本变更必须同时提交迁移策略、回滚策略和跨版本测试；禁止仅通过改常量触发批量删除。
- [ ] 提供显式的“导出 agent 数据 / 清理 agent 数据”操作，把破坏性清理从隐式启动行为变成用户可确认的动作，并在清理前显示备份位置。
