### 结论

确实存在注入丢失，但不是首次注入晚于用户消息。点击“开始”组装的首次请求包含软件规则、项目规则及聚焦文档；该请求发生 TLS 连接建立前的 `ECONNRESET`。恢复执行走历史重建路径，只还原用户原始指令，没有恢复注入层，导致真正成功返回回答的请求缺少 issue 和项目规则。用户追问产生新意图后，系统重新组装注入层，所以模型此时才看到文档。

### 点击“开始”的具体行为

1. `src/renderer/components/agent/IrisAgentView.tsx` 的 `submitDraft` 允许文档会话在没有历史意图时提交空输入。

### 代码原因

- `src/main/agent/session-manager.ts:2504` 附近在 provider attempt 开始时即创建 Turn，因此“存在 Turn”不等于模型已成功生成过回答。
- `src/main/agent/session-manager.ts:1082` 附近的 `retry` 只有在意图完全没有 Turn 时才重新组装完整 prompt 并发送 `run`；已有 Turn 时发送 `resume`，仅携带 history/runtime。
- `src/main/agent/trace-context.ts:97` 的历史投影只保存 `intent.content`，没有原来的组装输入。
- `src/main/agent-worker.ts:171` 附近恢复 runtime 后直接 `agent.continue()`；适配器默认 system prompt 只有基础规则。原来只放在 user 消息里的注入内容于是全部消失。

## 2026-09-19 追加排查：bad_response / timeout 与恢复入口

用户报告：`bad_response: stream ended with reason timeout (request id: 202609191411162983762318268d9d65bjY06OI)`，询问含义、为何不能恢复以及 provider 错误是否统一处理。本轮完成代码与实际 journal 核对，未新增产品代码修改或运行测试。

### 错误含义与实际状态

这是上游调用的流式响应以 timeout 原因结束；request id 用于上游排查。仅凭现有记录不能进一步确定超时由模型服务、代理网关还是其内部链路触发，也不能据此认定是本地命令的执行超时。

该错误对应此前同一会话中的意图 `d580422d-1f5f-4af7-b7e5-0b8a1242619d`（“可以的，全部实现”），Invoke 为 `ab002a4f-8761-4a67-a891-065074ca02de`。失败 attempt 从 22:11:13.693 持续到 22:13:20.690，约 127 秒。

实际 journal 记录表明该错误没有漏进恢复状态：

| 本地时间 UTC+8 | journal revision | 事实 |
| --- | --- | --- |
| 22:13:20.825 | 1170 | session 和当前意图均进入 `paused`，`pauseReason: provider`。 |
| 22:14:41.511 | 1171 | 收到新用户消息“继续”，创建意图 `cb423660-cdd0-4bdd-bf3e-a0b5b7a98e1e`；旧意图变为 `superseded`。 |

该失败 Invoke 只有一次 attempt，没有原 Invoke 被继续重试的记录。之后的新“继续”意图完成了剩余工作。记录可以证明收到的是新消息及其状态转移，不能反推出用户当时看到的界面、点击位置或是否遇到显示异常。

### 为什么看起来不能恢复

当前有两种不同操作：

- 顶部暂停栏的“继续”调用 `resumeIrisAgent` → `IRIS_AGENT_RETRY` → `retry`，恢复当前暂停意图。`IrisAgentView.tsx` 在 `session.pause` 存在时显示该入口，不按具体 provider 错误文字禁用。
- 输入框发送“继续”仍是普通 `send`。`session-manager.ts` 遇到暂停意图时会先将其 `superseded`，再创建新意图。旧意图随后不再满足 `retry` 的“当前且暂停”条件。

另外，失败回复卡片调用 `AgentReplyCard` 时写死了 `canRetry={false}` 和 `onRetry={noop}`。虽然卡片组件实现了重试按钮，该入口始终不可见。顶部暂停栏和错误卡片的恢复体验确实没有统一。不能把所有历史失败卡片都直接开放重试：被后续任务替代的旧意图需要单独设计恢复/分支语义。

### Provider 错误治理现状

- 传输抛异常与 provider 返回 `stopReason=error` 均汇合到 worker 的 `execution-paused`，再映射为会话暂停。这条 timeout 已成功命中该通道。
- 错误分类目前依赖 `providerPauseReason` 中的文本正则：认证关键字归 auth，HTTP/网络/timeout 等归 provider，未命中归 runtime。没有完整的结构化错误分类契约。
- Iris 执行循环在错误后退出并暂停，尚无统一的、有次数和退避上限的自动重试策略。底层 provider transport 是否自行重试需要分别确认；不能把 `provider-exhausted` 这个事件名理解为 Iris 已执行多轮重试。
- 上一版修复针对的是“已经触发恢复后，重新构建的请求丢失上下文”，没有统一错误分类或打通错误卡片的重试按钮。

### 建议的下一步

把当前暂停意图的失败卡片与顶部暂停栏接到同一个恢复命令；明确旧意图的不可直接恢复状态。Provider 错误以来源和结构化信息分类，分别标注能否重试、是否需要用户处理；超时、连接中断、429/5xx 可以制定有限自动重试规则，认证、参数和协议错误不盲目重复请求。所有恢复入口继续复用已经修复的上下文重建路径。
