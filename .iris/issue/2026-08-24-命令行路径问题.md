用户投诉说，安装了codebuddy之后，出现了一个很严重的问题，就是命令行检测不到，在windows terminal中，输入codebuddy可以显示，但是在iris中，就是找不到命令，这是怎么回事？

谈谈你对这个问题的理解

## 2026-08-24 调研记录

### 当前判断

这不是 xterm 的显示问题，也不是 ConPTY 自己做命令查找的问题。命令最终由
Iris 创建的 PowerShell/cmd 解释，能否找到 `codebuddy` 取决于该 shell 收到的
环境变量、加载的 profile 以及命令实际安装形式。

代码已确认：普通 Iris 终端在 `src/main/session-manager.ts:282` 调用
`buildSpawnEnv(process.env, ...)`，而 `src/main/pty-utils.ts:13` 的
`buildSpawnEnv` 只是复制 Electron 主进程现有环境，不会读取 Windows 注册表，
也不会合并用户级和机器级 Path。Iris Agent 的命令终端在
`src/main/agent/command-pty.ts:66` 也采用同样做法；Iris Agent 的 shell 选择甚至在
`src/main/agent/session-manager.ts:120` 构造 manager 时就从 `process.env` 固定下来。
项目中没有发现监听 `WM_SETTINGCHANGE` 或主动刷新 Windows 环境的实现。

因此，一个确定存在的产品缺口是：Iris 只能看到其父进程传入的环境快照，无法保证
它与用户此刻在 Windows Terminal 中看到的环境一致。

### 为什么“重启 Iris”仍可能无效

用户已补充：完全重启 Iris 后依然找不到。这降低了“只是旧 Iris 进程没刷新”的概率，
但还不能排除环境继承问题：重新启动的 Iris 通常仍由长期存活的 Explorer 创建；若
CodeBuddy 安装器或安装命令没有广播环境变化，Explorer 仍可能把旧 Path 交给新的
Iris。Windows Terminal 里的 shell 则可能来自不同的父进程、已手动刷新过环境，或在
profile 中补过路径。

另一个必须核实的差异是 shell。Iris 在 Windows 上固定按
`pwsh.exe -> powershell.exe -> cmd.exe` 的顺序选择宿主
（`src/main/session-manager.ts:172`），而 Windows Terminal 使用用户自己的默认
profile。若外部终端实际是 cmd/Windows PowerShell，而 Iris 使用 PowerShell 7，
两边可能加载不同 profile；如果 `codebuddy` 是 alias/function，或路径只在某个
profile 中追加，就会出现稳定的“一边有、一边没有”。PowerShell 的脚本执行策略也
可能让 npm 生成的 `codebuddy.ps1` 失败，但这种情况通常会报告“禁止运行脚本”，不应
笼统归为“命令不存在”。

腾讯 CodeBuddy CLI 的 npm 包 `@tencent-ai/codebuddy-code` 已确认注册
`codebuddy`、`cbc`、`codebuddy-code` 和 `cbc-prewarm` 四个 bin。若它是用
`npm install -g` 安装，真正需要比较的是 `npm prefix -g` 及该目录中的
`codebuddy.cmd`/`codebuddy.ps1`，而不能只比较肉眼看到的 Path 文本。

### 目前不能直接下的结论

当前开发机没有安装 CodeBuddy，`Get-Command codebuddy` 和 `where codebuddy` 均无
结果，所以尚未在本机复现投诉。仅凭“Windows Terminal 能运行、Iris 不能运行”还
不能判断究竟是 Iris 收到旧 Path、shell/profile 不同，还是 PowerShell 执行策略问题。
现场输出可以在一轮内把三者分开。

### 现场采集

请分别在“能够运行 CodeBuddy 的 Windows Terminal”和“找不到命令的 Iris 终端”中
执行同一组命令，并保留完整输出：

- [ ] 在两边执行 `$PSVersionTable.PSVersion; $Host.Name; Get-Command codebuddy -All | Format-List Name,CommandType,Source,Definition`。
- [ ] 在两边执行 `where.exe codebuddy` 和 `npm prefix -g`。
- [ ] 在两边执行 `[Environment]::GetEnvironmentVariable('Path', 'Process')`，并对比是否包含 `npm prefix -g` 的结果。
- [ ] 若 Iris 报的是脚本执行策略错误而非 command-not-found，在两边执行 `Get-ExecutionPolicy -List`。
- [ ] 做一次系统注销后重新登录，再启动 Iris 验证；这一步能排除 Explorer 持有旧环境快照。

### 结果判读

1. 两边 shell 相同，Iris 的进程 Path 缺少 CodeBuddy 所在目录：环境继承/刷新问题，
   Iris 应在创建子进程前取得可靠的最新 Windows 用户级与机器级 Path。
2. 两边 Path 相同，但 `Get-Command` 类型不同或只有外部终端能看到 alias/function：
   shell profile 差异，需先确认 Iris 是否应该允许用户选择默认 shell，而不是把问题误修
   成 Path 拼接。
3. 两边都能定位 `codebuddy.ps1`，Iris 报执行策略错误：不是查找失败；应保留诊断信息，
   并优先执行可用的 `.cmd` shim 或提示真实策略错误。
4. 注销登录后 Iris 恢复：可确认是父进程环境快照问题，但产品仍应考虑自动刷新，不能把
   注销系统当成正常解决方案。

### 后续修复边界

如果现场证明确为 Path 刷新问题，修复不能只落在普通终端。至少需要让
`SessionManager`、Iris Agent 的 `AgentCommandPty`/命令 shell 解析，以及
`launchSystemTerminal` 共用同一个可测试的 Windows 环境解析器；同时保留 Iris 注入的
`FOCUS_DOC`、`IRIS_WORKSPACE_PATH` 和终端提示变量。合并用户 Path 与机器 Path 时要按
Windows 的大小写不敏感语义去重，并明确注册表读取失败时回退到 `process.env`。
