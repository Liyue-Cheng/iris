title: 命令行路径问题
status: In Review
---
用户投诉说，安装了codebuddy之后，出现了一个很严重的问题，就是命令行检测不到，在windows terminal中，输入codebuddy可以显示，但是在iris中，就是找不到命令，这是怎么回事？

谈谈你对这个问题的理解

## 2026-08-24 调研记录

### 当前判断

这不是 xterm 的显示问题，也不是 ConPTY 自己做命令查找的问题。命令最终由
Iris 创建的 PowerShell/cmd 解释，能否找到 `codebuddy` 取决于该 shell 收到的
环境变量、加载的 profile 以及命令实际安装形式。

代码已确认：普通 Iris 终端在 `src/main/session-manager.ts:282` 调用
`buildSpawnEnv(process.env, ...)`，而 `src/main/pty-utils.ts:13` 的
`buildSpawnEnv` 只是复制 Electron 主进程现有环境，不会读取 Windows 注册表，
也不会合并用户级和机器级 Path。Iris Agent 的命令终端在
`src/main/agent/command-pty.ts:66` 也采用同样做法；Iris Agent 的 shell 选择甚至在
`src/main/agent/session-manager.ts:120` 构造 manager 时就从 `process.env` 固定下来。
项目中没有发现监听 `WM_SETTINGCHANGE` 或主动刷新 Windows 环境的实现。

因此，一个确定存在的产品缺口是：Iris 只能看到其父进程传入的环境快照，无法保证
它与用户此刻在 Windows Terminal 中看到的环境一致。

### 为什么“重启 Iris”仍可能无效

用户已补充：完全重启 Iris 后依然找不到。这降低了“只是旧 Iris 进程没刷新”的概率，
但还不能排除环境继承问题：重新启动的 Iris 通常仍由长期存活的 Explorer 创建；若
CodeBuddy 安装器或安装命令没有广播环境变化，Explorer 仍可能把旧 Path 交给新的
Iris。Windows Terminal 里的 shell 则可能来自不同的父进程、已手动刷新过环境，或在
profile 中补过路径。

另一个必须核实的差异是 shell。Iris 在 Windows 上固定按
`pwsh.exe -> powershell.exe -> cmd.exe` 的顺序选择宿主
（`src/main/session-manager.ts:172`），而 Windows Terminal 使用用户自己的默认
profile。若外部终端实际是 cmd/Windows PowerShell，而 Iris 使用 PowerShell 7，
两边可能加载不同 profile；如果 `codebuddy` 是 alias/function，或路径只在某个
profile 中追加，就会出现稳定的“一边有、一边没有”。PowerShell 的脚本执行策略也
可能让 npm 生成的 `codebuddy.ps1` 失败，但这种情况通常会报告“禁止运行脚本”，不应
笼统归为“命令不存在”。

腾讯 CodeBuddy CLI 的 npm 包 `@tencent-ai/codebuddy-code` 已确认注册
`codebuddy`、`cbc`、`codebuddy-code` 和 `cbc-prewarm` 四个 bin。若它是用
`npm install -g` 安装，真正需要比较的是 `npm prefix -g` 及该目录中的
`codebuddy.cmd`/`codebuddy.ps1`，而不能只比较肉眼看到的 Path 文本。

### 目前不能直接下的结论

当前开发机没有安装 CodeBuddy，`Get-Command codebuddy` 和 `where codebuddy` 均无
结果，所以尚未在本机复现投诉。仅凭“Windows Terminal 能运行、Iris 不能运行”还
不能判断究竟是 Iris 收到旧 Path、shell/profile 不同，还是 PowerShell 执行策略问题。
现场输出可以在一轮内把三者分开。

### 现场采集

请分别在“能够运行 CodeBuddy 的 Windows Terminal”和“找不到命令的 Iris 终端”中
执行同一组命令，并保留完整输出：

- [ ] 在两边执行 `$PSVersionTable.PSVersion; $Host.Name; Get-Command codebuddy -All | Format-List Name,CommandType,Source,Definition`。
- [ ] 在两边执行 `where.exe codebuddy` 和 `npm prefix -g`。
- [ ] 在两边执行 `[Environment]::GetEnvironmentVariable('Path', 'Process')`，并对比是否包含 `npm prefix -g` 的结果。
- [ ] 若 Iris 报的是脚本执行策略错误而非 command-not-found，在两边执行 `Get-ExecutionPolicy -List`。
- [ ] 做一次系统注销后重新登录，再启动 Iris 验证；这一步能排除 Explorer 持有旧环境快照。

### 结果判读

1. 两边 shell 相同，Iris 的进程 Path 缺少 CodeBuddy 所在目录：环境继承/刷新问题，
   Iris 应在创建子进程前取得可靠的最新 Windows 用户级与机器级 Path。
2. 两边 Path 相同，但 `Get-Command` 类型不同或只有外部终端能看到 alias/function：
   shell profile 差异，需先确认 Iris 是否应该允许用户选择默认 shell，而不是把问题误修
   成 Path 拼接。
3. 两边都能定位 `codebuddy.ps1`，Iris 报执行策略错误：不是查找失败；应保留诊断信息，
   并优先执行可用的 `.cmd` shim 或提示真实策略错误。
4. 注销登录后 Iris 恢复：可确认是父进程环境快照问题，但产品仍应考虑自动刷新，不能把
   注销系统当成正常解决方案。

### 后续修复边界

如果现场证明确为 Path 刷新问题，修复不能只落在普通终端。至少需要让
`SessionManager`、Iris Agent 的 `AgentCommandPty`/命令 shell 解析，以及
`launchSystemTerminal` 共用同一个可测试的 Windows 环境解析器；同时保留 Iris 注入的
`FOCUS_DOC`、`IRIS_WORKSPACE_PATH` 和终端提示变量。合并用户 Path 与机器 Path 时要按
Windows 的大小写不敏感语义去重，并明确注册表读取失败时回退到 `process.env`。

## 复核（2026-11-24）

**结论：问题仍然存在。** 从 2026-08-24 到现在，造成问题的代码机制没有变化，只是文件位置随平台层重构发生了迁移。

### 当前代码证据

- 普通终端：`src/main/terminal-session-manager.ts:263` 仍是 `buildSpawnEnv(process.env, SPAWN_ENV_SKIP)`。`src/main/pty-utils.ts` 的 `buildSpawnEnv` 只做过滤和复制，不会读取注册表，也不会刷新 Path。
- shell 选择：`src/main/platform/shell.ts` 的 `windowsShell` 也只拿同一份 `env.PATH` 查找 `pwsh.exe → powershell.exe → cmd.exe`。顺序固定，用户无法选择。
- 系统终端：`src/main/platform/system-terminal.ts` 默认使用 `process.env`；`ipc.ts:625` 调用时没有传入新的 env。
- Git：`src/main/git-manager.ts:185` 同样直接展开 `process.env`。
- 全项目找不到任何读取 `HKCU\Environment`、`HKLM\...\Session Manager\Environment` 或监听 `WM_SETTINGCHANGE` 的代码。

### 比原分析多出的一个放大因素：单实例 + 多窗口

`index.ts` 使用 `requestSingleInstanceLock`。再次启动 Iris 时，`app-main.ts:113` 的 `second-instance` 处理只会在**原主进程**里开一个新窗口；`app-main.ts:593` 要等到最后一个窗口关闭才退出。

所以，只要还有任意一个 Iris 窗口开着，"关掉再重新打开 Iris"拿到的仍是主进程第一次启动时的环境快照。用户以为已经重启，主进程其实一直没换。对于平时开着多个项目窗口的用户，这一点很可能比 Explorer 的旧快照更常见。

### 判断

- 这种情况下必然出问题：安装器修改了用户或系统的 Path（独立安装程序、winget、scoop 首次安装、`setx` 等），然后用户在 Iris 主进程不退出的前提下新建终端。
- 这种情况下一般不会出问题：`npm install -g` 新装一个 CLI，而 npm 全局目录早已在 Path 中。
- 原 issue 列出的另外两种可能（shell/profile 差异、执行策略）仍无法从代码排除，现场采集清单依然有效。

### 修复方案（未实施）

1. 新增 `src/main/platform/windows-env.ts`。每次创建子进程前，从注册表读取机器级和用户级的 `Path`，按 Windows 规则拼接（机器在前、用户在后，展开 `%VAR%`），再与 `process.env.Path` 做大小写不敏感的去重合并，最后把进程里额外的条目追加到末尾，这样 Iris 自身注入的路径不会丢。读取失败时回退到 `process.env`。
2. 普通终端、系统终端、Git 统一走这个解析器。Iris 注入的 `FOCUS_DOC`、`IRIS_WORKSPACE_PATH`、`TERM*` 变量继续在它之后覆盖。
3. 读取方式：优先用 `reg query`，或者用一个轻量的 PowerShell `[Environment]::GetEnvironmentVariable(..., 'User'/'Machine')`，可以短时间缓存（例如 2 秒），避免每次开终端都卡顿。
4. 单测覆盖：去重、大小写、`%VAR%` 展开、读取失败时的回退。
5. 可选：在设置里允许选择默认 shell，以对应结果判读第 2 类（profile 差异）。

## 实施（2026-11-25）

用户确认必须修复。按上节方案实施，Iris Agent（实验功能）不在本次范围内。

### 改动

- 新增 `src/main/platform/child-env.ts`：
  - 用 `reg export` 读取 `HKLM\...\Session Manager\Environment` 与 `HKCU\Environment`。导出文件是 UTF-16LE，中文路径不会乱码；`reg query` 按控制台代码页输出，会乱码，所以没有用它。
  - 按 Windows 规则构建注册表环境：先机器后用户，Path 为机器 Path 拼接用户 Path，`REG_EXPAND_SZ` 展开 `%VAR%`。
  - **追加式合并**：继承的 Path 条目顺序不变，只在末尾追加新出现的目录（比较时忽略大小写和末尾斜杠）；只补充进程里缺少的变量，已有的值一律不覆盖。这样对现有行为的影响最小。
  - `refresh()` 是异步的：并发调用会合并成一次，1 秒内的重复调用直接跳过；它永远不会 reject，读取失败时沿用上一次成功的快照，从未成功过则直接使用 `process.env`。`resolve()` 是同步的。非 Windows 平台上两者都直接透传。
- `terminal-session-manager.ts`：spawn 时的环境改为 `childEnvironment.resolve(process.env)`（新增可注入的 `spawnEnv` 选项）。shell 选择也基于这份新环境，所以新装的 pwsh 也能被选中。
- `ipc.ts`：`SESSION_OPEN` 和 `PROJECT_COMMAND_RUN` 在创建会话前先 `await childEnvironment.refresh()`；系统终端启动时显式传入合并后的环境。
- `git-manager.ts`：git 子进程使用合并后的环境（只读缓存，不在每次 git 调用时读注册表）。
- `app-main.ts`：`browser-window-focus` 时在后台预刷新。用户在别处装完 CLI 回到 Iris，焦点一切回来缓存就会更新。

### 验证

- 新增 `src/main/platform/child-env.test.ts`，10 项：覆盖解析（续行 hex、中文、转义、忽略 dword 和子键）、展开、追加合并、不覆盖已有值、并发去重与节流、失败回退、非 Windows 透传，以及一次真实 `reg.exe` 读取。全部通过。
- `npm run typecheck`（含异步边界检查）通过。
- 全量 `npx vitest run`：129 个文件，976 项通过、1 项跳过。
- 本机真实注册表探针（临时测试，已删除）：刷新耗时 38ms；58 个 Path 条目顺序完全保留；发现注册表中有、当前进程环境中没有的用户变量 `MARINA_EXE`，这就是本问题的现成实例；把 `nodejs` 目录从 Path 中移除模拟过期快照后，合并结果能把它补回。
- 按项目约定，没有运行 build/dist，也没有启动开发服务器截图。
