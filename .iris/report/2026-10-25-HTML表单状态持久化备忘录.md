## 问题

HTML 单文件里的复选框、输入框、下拉框等表单控件，用户操作后的状态能否在 Iris 中持久化？

相关 issue：[支持HTML](../issue/2026-10-25-支持HTML.md)

## 结论

**现在不能，按《支持HTML》issue 中已确定的第一版方案落地后也仍然不能。**

1. Iris 当前还不识别 `.html`：`src/main/iris-scanner.ts` 只收 `.md`，代码里也还没有 `iris-doc://` 协议或 iframe 预览。HTML 文档目前在 Iris 中看不到，自然谈不上保存表单状态。
2. 第一版方案（沙箱 iframe、默认不执行脚本、永不加 `allow-same-origin`）从结构上就不提供任何持久化通道。
3. 在 Iris 里需要"勾选并保存"的场景，本来就是 issue（md）里 GFM checkbox 的职责。HTML 定位为以阅读为主的报告，第一版不做持久化是合理的。

## 为什么第一版方案下状态存不住

### 1. 默认不执行脚本

沙箱 iframe 的 `sandbox` 属性为空值时，用户仍然能点复选框、能在输入框里打字，这是浏览器原生行为。但没有任何脚本能观察到这些变化：页面自己不能，Iris 宿主也不能（iframe 与宿主跨源，宿主读不到它的 DOM）。刷新或重新打开后，状态全部丢失。

### 2. 表单状态只在内存里，不在源码里

| 控件 | 用户操作改变的 | 源码 / `outerHTML` 中的 |
| --- | --- | --- |
| `<input type="checkbox">` | `checked` **property**（DOM 属性值） | `checked` **attribute**（HTML 标记），不随勾选变化 |
| `<input type="text">` | `value` property | `value` attribute，不随输入变化 |
| `<textarea>` | `value` property | 标签内的文本，不随输入变化 |
| `<select>` | `selectedIndex` / `value` | `<option selected>`，不随选择变化 |

所以即使把当前 DOM 序列化回文件，也拿不到用户操作后的状态。这和 issue 中"不能把运行时 DOM 写回源码"的原因是同一个：序列化 DOM 既会丢失表单状态，也会把脚本对 DOM 的运行时修改写进源码。

### 3. 开了脚本，页面自己也存不住

方案规定永远不加 `allow-same-origin`，因此 iframe 是不透明源（opaque origin）。在不透明源下：

* `localStorage`、`sessionStorage`、`IndexedDB` 一访问就抛出 `SecurityError`；
* `document.cookie` 不可用。

很多 agent 生成的"一次性小工具页"正是用 `localStorage` 记住状态的。这类页面在 Iris 里要么丢状态，要么脚本因为未捕获的异常直接中断，页面功能不完整。

> 这一点在《支持HTML》issue 第 5 节"风险与未验证项"中没有写到，属于遗漏的风险。

## 如果以后要做持久化：可选方案

| 方案 | 原理 | 优点 | 代价 |
| --- | --- | --- | --- |
| **A. 写回源码** | 宿主注入一段桥接脚本，监听 `change` / `input` 事件，通过 `postMessage` 报给宿主。宿主按元素的 `id` / `name` 在源码中定位标签（例如用 parse5 的 `sourceCodeLocationInfo` 拿到源码偏移），只对这个标签加或删 `checked`、改 `value=`、替换 `<textarea>` 文本、移动 `<option selected>`。做法和 `<meta name="iris:*">` 写回一样，是最小文本修改，不做 DOM 序列化。 | 状态就在 HTML 文件里：agent 读源码能看到勾了什么，git diff 看得清，换机器、用浏览器直接打开都还在 | 必须开脚本；没有 `id` / `name` 的元素定位不到；脚本动态生成的表单无法映射回源码；和 agent 同时改文件时要走现有的外部修改冲突提示；写回频率需要防抖 |
| **B. 旁路状态文件** | 状态存到 `<name>.assets/form-state.json`，按 `id` / `name` 记录；打开文档时由桥接脚本恢复 | 不动源码，实现简单 | agent 和浏览器都看不到这份状态；源码结构一变，状态就可能对不上；会在 assets 目录里产生 Iris 私有文件 |
| **C. 模拟 storage** | 往页面注入一个 `localStorage` 的替代实现，数据经 `postMessage` 由宿主落盘 | 依赖 `localStorage` 的现成页面不用改就能用 | 数据藏在 Iris 内部，最不透明，最难向用户和 agent 解释；离开 Iris 后状态不存在 |
| **D. 不做持久化，靠导出** | 页面自己提供"复制结果 / 导出"按钮，用户把结果贴回给 agent，由 agent 写入 md 或改 HTML | 零实现成本；与 Thariq 文章中的用法一致 | 依赖人手动操作；不是真正的持久化 |

### 倾向

* **第一版：D。** 不做持久化，在协议文本里引导 agent：需要人勾选、跟踪的事项写进 issue（md）；HTML 里的交互控件只用于临时操作，结果通过导出带回。
* **以后确实需要时：A。** 理由是它最符合 Iris"文件即唯一真相"的思路，状态对人、agent、git 都可见。建议的限定条件：
  * 只在用户对该文档"信任并运行脚本"后启用；
  * 只支持带 `id` 或 `name` 的 `<input>`、`<textarea>`、`<select>`；
  * 定位不到源码位置的控件不写回，并在界面上给出提示，而不是静默丢弃；
  * 桥接脚本由宿主（自定义协议响应）注入，不依赖页面作者配合。
* **C 不建议做。** 它让状态脱离文件存在，和 Iris 的文档模型冲突。

### 对第一版方案的补充建议

* 在风险项里补上：带脚本且依赖 `localStorage` / `IndexedDB` / cookie 的页面，在不透明源下会报 `SecurityError`，可能导致页面功能失效。
* 可以考虑在"信任并运行脚本"模式下注入一个**只做兜底的空实现** storage（不落盘，仅在内存中，关闭即失），让这类页面至少不因异常而中断。这不属于持久化，只是兼容性处理，是否做需要权衡。

## 未验证项

本文是基于代码阅读和 Web 平台规范的分析，**没有写原型，也没有实测**。

* [ ] Electron 43 下，`sandbox` 不含 `allow-same-origin` 的 iframe 访问 `localStorage` 时的实际表现（预期抛出 `SecurityError`）
* [ ] 宿主通过自定义协议响应注入桥接脚本，与按文档下发的 CSP 能否共存（注入脚本需要被 CSP 放行，例如用 nonce 或 hash）
* [ ] parse5 源码位置信息在畸形 HTML（agent 常写出未闭合标签等）上的可靠性
