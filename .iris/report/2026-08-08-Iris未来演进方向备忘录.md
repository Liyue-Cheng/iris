本文记录 2026-08-08 关于 Iris 后续产品演进的讨论，重点覆盖结构化 Agent 运行环境、
代码与 diff 查看能力，以及多人使用后的 issue 管理。判断以当前代码和已经明确的产品原则为准，
不是实施方案或排期承诺。

## 总体判断

三个方向并非相互独立的功能堆叠，而是在闭合三条 Human-Agent 工作回路：

1. 结构化 Agent 环境闭合“意图 -> 执行 -> 人类介入 -> 结果写回”。
2. 代码与 diff 查看器闭合“任务 -> 代码改动 -> 人类审查”。
3. 多人 issue 管理闭合“个人项目事实 -> 团队共同事实”。

前两个方向直接强化 Agent Development Environment 的定位。第三个方向可能把 Iris 从本地工作环境
进一步推向团队协作平台，涉及身份、同步、权限和共同事实源，产品与工程跨度明显更大。

## 一、基于 Pi RPC 的结构化 Agent 环境

### 已明确的产品原则

- [x] 结构化模式不引入 Iris 自己的审批系统、命令 allowlist 或沙箱。
- [x] Agent 继承当前操作系统用户权限，使用风险由用户自行承担。
- [x] 不选择会静默改变命令行为的安全层；执行忠实性高于形式上的安全包装。
- [x] 普通 CLI 和 PTY 继续保留，结构化后端不取代通用终端能力。

这项原则改变了此前候选后端的权重。Codex app-server 的审批和沙箱闭环不再是优势；当目标是
不干预地承载多 provider Agent，并由 Iris 提供自己的交互体验时，Pi RPC 更符合产品方向。
Codex 仍可作为普通 CLI 通过 PTY 使用，但不再优先作为唯一结构化后端。

### Iris 实际要拥有的部分

近期目标不是自己重新实现模型循环和工具系统，而是让 Iris 成为 Pi 的原生 Host：

| Iris 负责 | Pi 负责 |
| --- | --- |
| 文档/workspace 会话锚定 | Agent loop |
| 进程与会话生命周期 | 模型与 provider |
| 结构化事件归一化和 UI 投影 | 工具调用与实际命令执行 |
| `FOCUS_DOC` 和 Iris 上下文注入 | 会话历史、压缩与重试 |
| 结果、文件改动和文档写回追踪 | RPC 原始事件 |

使用 Pi RPC 意味着 Iris 拥有交互宿主和产品体验，但 Pi 仍然拥有运行内核。只有未来确实需要修改
Agent loop、工具协议或上下文策略时，才需要评估 Pi SDK、扩展或更深层的运行时所有权。

### 右栏的目标体验

“结构化”不能只是把终端替换成聊天记录。右栏应默认压缩信息密度，只突出：

- 当前目标和正在执行的动作。
- Agent 向用户提出的问题。
- 已修改文件和关键 diff。
- 测试、构建和检查结果。
- 最终结论及 `.iris/` 写回状态。

完整消息、原始命令、工具参数、输出和 exit code 应可按需展开。少文字意味着减少重复叙述和默认
噪声，不意味着隐藏执行事实。Iris 不拦截或重写命令，也不能在 RPC 故障时静默切换执行方式。

建议在应用内部建立协议无关的 session/run 模型，至少区分 `pty` 与 `structured` 两种 backend。
Pi 事件先转换为 Iris 自己的运行状态、问题、动作和 artifact 投影，避免 Pi 的协议类型渗透整个
renderer。原始事件和会话映射属于可重建的机器本地状态，项目的长期事实仍写入普通文件。

### 待验证

- [ ] 做 Pi RPC 只读 spike：启动、恢复、单轮请求、流事件、正常完成和取消。
- [ ] 验证 Pi 进程崩溃、Iris 重启和 RPC 断线后的会话恢复行为。
- [ ] 验证 Windows 下实际 Bash、cwd、环境变量和直接运行 Pi 时是否一致。
- [ ] 定义未知事件、扩展事件和 Pi 版本不兼容时的显式降级策略。
- [ ] 设计紧凑投影与原始事件视图，确保任何命令和输出都可追溯。
- [ ] 明确结构化会话的本地持久化位置和清理策略，不把聊天历史混入项目事实。

## 二、代码查看器与 diff 查看器

### 当前事实

当前 Iris 没有代码查看器，也没有 diff 视图。现有 raw tree 只用于查看 `.iris/` 的裸文件结构，
非 Markdown 文件不可打开；Git 面板提供的是状态、暂存和提交等最小操作，不能承担代码审查。

因此 Agent 完成代码修改后，用户仍需离开 Iris 才能查看实际改动。这是当前 Human-Agent 闭环中的
明显断点，不能把未来方向描述成对已有 diff 能力的小幅增强。

### 产品定位

第一阶段应做“面向 Agent 工作验收的代码阅读能力”，而不是缩小版 VS Code。优先级建议为：

1. 查看工作树、暂存区以及单次 Agent run 产生的 diff。
2. 从 Agent 动作、文件变更或最终结果直接跳到对应文件和行。
3. 浏览完整项目文件树，以只读方式查看源码并提供语法高亮和行号。
4. 搜索文件名和代码正文，复制稳定的文件/行引用。
5. 在用户已有 IDE 中打开当前文件或定位到指定行。

diff 比通用代码浏览更接近 Iris 的核心工作流，应作为 MVP 核心而不是后续附加项。暂不进入代码
编辑、LSP、调试器、插件市场等领域，避免把 Iris 推向与成熟 IDE 正面竞争。

交互上也不宜先做割裂的“IDE/ADE 模式”。代码或 diff 可以成为中栏的新视图，但查看代码时，
右栏仍应保持原 issue 或 workspace 的会话锚点。源文件是当前工作的 artifact，不应因为被打开就
取代 issue 成为 Agent 会话的长期工作单元。

### 待设计与实施

- [ ] 定义代码树、单文件查看和 diff 三类视图的最小信息架构。
- [ ] 明确第一版 diff 范围：工作树、暂存区、提交，以及能否可靠归因到单次 Agent run。
- [ ] 选择只读源码高亮方案，并验证大文件、二进制文件和编码异常的降级行为。
- [ ] 设计从结构化工具事件、Git 资源和 Markdown 文件引用跳转到 `file:line` 的统一协议。
- [ ] 设计“在外部 IDE 打开”的 Windows 集成和用户配置。

## 三、多人使用后的 issue 管理

“issue 很多”和“用户很多”是两种不同的扩展问题。

大量 issue 主要考验本地投影：列表性能、搜索、分组、过滤、排序、批量操作和保存视图。Iris 当前
已经具备其中一部分，后续可以通过虚拟列表和可重建索引扩展，不必因此引入服务器。

多人协作的核心则会转向：

- 身份、负责人和责任边界。
- 并发编辑、冲突合并与离线同步。
- 通知、关注和需要人处理的事件。
- 审查、关闭权限和操作记录。
- 团队以哪个副本作为共同事实。

简单增加 `assignee`、`priority`、`due` 等 frontmatter 字段只能改善分类，不能解决多人协作。
Iris 应继续坚持分层：Markdown 文件是永久事实源；本地索引可以随时重建；初期团队传输继续依赖
Git；未来如有 Iris Team 服务，它更适合负责同步、身份、通知和索引，而不应以服务器数据库取代
磁盘文件。

在协议字段中，稳定文档 ID 可能比更多项目管理字段更基础。目前路径实际承担文档身份；一旦出现
重命名、跨人引用、依赖关系、远端同步和 structured thread 映射，稳定 ID 能同时服务多个方向。
是否引入 ID 及其他字段仍应由真实多人使用反馈驱动，不能仅凭对 Jira 功能的想象扩展协议。

### 待观察与决策

- [ ] 用真实团队 dogfood 区分“列表规模问题”和“协作人数问题”。
- [ ] 记录 Git 协作中实际出现的 frontmatter 冲突、正文冲突和文档重命名问题。
- [ ] 评估稳定文档 ID 是否已成为会话恢复、diff 归因或跨人引用的共同前置条件。
- [ ] 根据真实查询需求决定 owner、priority、milestone、dependencies 等字段，而不是一次性扩充 schema。
- [ ] 在考虑团队服务前，先定义 Markdown、Git 与服务端投影之间唯一且可解释的事实归属。

## 建议演进顺序

从产品战略看，结构化 Agent 环境的价值最高；从交付风险看，代码和 diff 查看器更容易先形成完整、
可验证的用户价值。建议顺序如下：

1. 先交付只读代码与 diff 查看 MVP，补上 Agent 改动无法在 Iris 内验收的断点。
2. 同期做 Pi RPC 只读 spike，并建立协议无关的 structured session/run 模型。
3. 结构化投影稳定后开放完整工具执行；不增加审批或沙箱，但保证执行和降级行为透明可追溯。
4. 继续以 Git 为多人协作基础，通过 dogfood 收集问题，再决定协议字段和团队服务。

最终目标不是把 Iris 做成“小型 IDE + 小型 Jira + 聊天窗口”，而是让文档定义工作、Agent 执行
工作、代码与 diff 视图帮助人类审查工作，并在确有需要时由团队层让这些事实可靠地在人之间流动。
