## 结论

Iris 的实际开发并不是单 Agent 串行工作，也不是以 Git worktree 隔离为默认前提。多个 Agent 经常同时在同一个工作树中处理不同的低风险任务，完成后的修改立即进入其他 Agent 可见的共享现实，最后由人统一验证并形成一个交付提交。

这是一种由意图分解驱动的乐观并发模型：并行的基本单位是相互独立的意图，而不是 Agent、分支或 worktree。人的主要职责是判断任务之间是否存在语义依赖，并据此决定并行、等待或隔离。

Git 历史中的零 merge commit 因而不能证明开发是串行的，只能证明并行没有被编码为分支拓扑。部分大提交也不是单个 Agent 一次生成大量代码，而是多个低风险任务在共享工作树中汇合后的交付批次。

## 两种并发假设

Orca 一类 worktree-native ADE 采用接近悲观并发的假设：任务默认可能相互干扰，因此先隔离执行，再通过 diff 和 merge 汇合。

Iris 的实际工作方式采用语义上的乐观并发：先由人判断任务是否独立，独立任务共享工作树并行执行；存在硬依赖的任务按时序等待；只有物理覆盖或试验隔离风险足够高时才引入 worktree。

| 维度 | 默认 Worktree 隔离 | Iris 共享工作树 |
| --- | --- | --- |
| 默认判断 | 任务可能冲突 | 大部分小任务可以按语义拆开 |
| 并发边界 | 分支和目录 | 意图、模块和时序依赖 |
| 集成时机 | 各自完成后 merge | 修改落盘后立即进入共享现实 |
| 主要收益 | 防止工作过程中的文件覆盖 | 避免环境复制、rebase 和事后集成成本 |
| 主要风险 | 延迟暴露语义不一致 | 同文件覆盖、陈旧读取和破坏性命令 |
| 正确性来源 | 仍然依赖契约、测试和审阅 | 仍然依赖契约、测试和审阅 |

## Worktree 能保证什么

Worktree 能隔离目录、分支、暂存区和未提交修改，使失败尝试可以整体丢弃，也能阻止两个 Agent 在工作过程中直接覆盖同一份文件。

它不能保证两个实现合并后正确，不能保证两个 Agent 对接口、状态模型或验收条件的理解一致，也不能消除任务间的先后依赖。两个 Agent 可以在各自 worktree 中基于同一个旧基线独立通过测试，却在 merge 后暴露出互不兼容的设计假设。

因此 worktree 解决的是物理干扰，不是语义正确性。它可能消除即时覆盖，也可能把真正的集成问题推迟到 merge 阶段。

## 时序依赖优先于执行隔离

如果任务 B 依赖任务 A 定义的新接口或真相源，那么合理顺序通常是：

```text
A 确定并实现基础模型
→ 修改成为共享工作树中的新现实
→ B 读取新现实并继续实现
```

让 B 在隔离 worktree 中提前基于旧接口工作，并不会消除依赖，只会把等待成本换成之后的 rebase、重新理解和重新验证成本。只有在双方先冻结了明确接口契约时，才可能安全地并行推进；此时保证正确性的仍然是契约，而不是 worktree 本身。

## 共享工作树成立的条件

Iris 当前的模式能够工作，依赖以下条件：

- 由一个人承担最终产品判断和任务调度。
- Agent 任务通常较短，范围明确，修改区域大多不同。
- 高风险基础设施和数据模型变更会主动串行。
- Agent 尊重盘上已有修改，不把共享工作树当作自己的独占空间。
- 所有 Agent 读取同一个持续更新的代码现实。
- 测试、人工验收和 Git 提交在交付边界上验证组合后的整体结果。
- Issue 保存任务意图、决定和结果，Git commit 保存人确认后的项目现实；两者都不承担 Agent 身份档案的职责。

这套模型更适合单人主导、Agent-native、短任务密集的开发。它不是无条件安全：当多个任务会重写同一核心模块、运行破坏性仓库级命令、持续时间较长或需要保留多个互斥方案时，共享工作树的乐观假设就不再可靠。

## Worktree 的合理边界

Worktree 应是按风险升级的工具，而不是每个 Agent 的默认容器。适合使用的场景包括：

- 两个 Agent 必须同时修改相同核心文件或进行跨仓库重构。
- 需要比较多个互斥实现，并确保失败方案能整体丢弃。
- 长时间实验不能污染当前可运行环境。
- 任务会升级依赖、执行迁移或产生大范围生成文件。
- Agent 或脚本的修改范围无法可靠约束。

即使使用 worktree，最终仍必须在合并后的真实项目上重新运行测试和验收。隔离成功不等于集成正确。

## 对 Iris 产品设计的含义

Iris 不应把 worktree 提升为最高层工作单元。最高层仍然是意图及其依赖关系：Issue 描述问题，Agent 临时领取任务，共享工作树承载正在形成的现实，Git 固化经人确认的结果。

未来若增加并发支持，更值得强化的是任务依赖、风险和注意力表达，而不是默认制造更多分支。产品可以在检测到同文件并发修改、长时间未刷新基线或高风险命令时提供轻量警告，并把 worktree 作为显式的隔离升级路径。

在这个模型中，Agent 不拥有分支，也不拥有代码，只暂时拥有一个任务。并发安全主要来自意图分解和语义调度；Worktree 负责必要时的物理隔离；最终正确性始终来自共享约束、测试证据和整体审阅。

## 近期开发的实证观察

2026 年 8 月 8 日至 9 日这一轮密集开发共有 27 条 Issue，其中 17 条已经完成并实际涉及代码修改。9 条没有修改 Iris 产品源码，主要是调研、审计、重构设计、品牌与公开素材工作；排除刚创建、尚未实际开展的 Pi Agent 条目后，是 26 条实质工作中的 8 条，约占 31%。这部分任务天然适合与代码实现并行，几乎不产生文件竞争。

同期提交涉及 147 个代码文件和 230 次提交级文件触碰，其中 71 个文件出现在不止一个提交中。重复触碰主要集中在多语言、协议治理、设置页、项目生命周期、Markdown 编辑器、终端以及 `ipc`、`protocol`、`types` 等横切区域。文件被多个提交修改只能说明它是热点，不能证明 Agent 在工作过程中发生了编辑冲突。

从现存 Issue 记录、Git 历史和实际开发者经验看，长期同时运行四到五个 Agent，至今可以确认的 Agent 编辑覆盖、冲突标记或修改丢失仍为零。能够确认的跨任务干扰是四类临时改动使其他任务无法完成全量类型检查，例如未使用导入、JSX 未闭合、类型不一致和测试参数缺失。同一个临时问题曾被多条 Issue 重复记录，因此不能按记录次数重复计数；这些干扰也没有造成修改丢失。

近期审计发现的数据安全、CAS、异步生命周期和状态所有权问题是真实的集成风险，但它们主要是实现本身的正确性问题，不是多个 Agent 互相覆盖代码的结果。共享工作树没有消除软件缺陷，Worktree 同样不能把这些缺陷自动变正确。

## 物理冲突与语义冲突

Agent 并发中的“冲突”需要分成两类：

- 物理冲突：两个 Agent 同时改写相同代码，发生覆盖、冲突标记或修改丢失。
- 语义冲突：任务 B 的接口、状态模型或验收前提必须建立在任务 A 完成后的新现实上。

Iris 实际开发中更常见、也更重要的是第二类。例如一个核心模块必须先完成重构，之后才能基于新模型开发功能。这是一条因果依赖：

```text
A 完成基础重构
→ A 的修改成为共享工作树中的新现实
→ B 重新读取当前代码
→ B 基于新模型开始实现
```

把 B 提前放进独立 Worktree，并不能消除这条依赖。B 仍会基于旧模型工作，最后即使 Git 可以无冲突合并，接口假设和测试基线也可能已经失效。Worktree 只是把当前的等待成本推迟成之后的 rebase、重新理解、返工和重新验证成本。

因此，语义冲突不能靠物理隔离解决，只能靠排序、冻结明确契约或重新规划任务。共享工作树在这里反而有直接价值：A 完成后，新的项目现实立刻对所有 Agent 可见，天然形成一道语义执行屏障。

这套调度可以概括为：

```text
独立意图         → 共享工作树并行
存在语义依赖     → 设置执行屏障，按顺序推进
必须保留互斥方案 → Worktree 隔离实验
不可控物理覆盖   → Worktree 作为风险升级
```

并发开发的核心问题因而不是如何合并多个 Agent 的代码，而是如何安排多个意图进入同一个不断变化的项目现实。Worktree 管理多个物理现实；Iris 管理多个意图如何有序地塑造同一个现实。

## 高带宽人类控制回路

Iris 的核心产品价值可以进一步表述为：把人的产品判断转化为一个持久、低损耗、可并行执行和可快速纠偏的开发控制回路。它不是以人退出回路为目标，而是放大有限的人类判断力。

```text
发现问题
→ 写成可持久的 Issue
→ Agent 读取完整意图并执行
→ 代码、测试和实施记录写回共享现实
→ 人检查结果并纠偏
→ Issue 保留决定与后续事项
→ Git 固化已经接受的项目现实
```

2026 年 8 月 9 日，开发者输入超过 1.5 万字，同时有 25 条 Issue 被触碰。即使按每分钟 60 个中文字符持续输出，也需要四个多小时；技术判断和产品反馈的实际表达速度通常更低。这说明当前产出不是 Agent 脱离人的自治，而是人持续承担问题发现、任务拆分、产品判断、时序安排、反馈和验收形成的高带宽控制。

如果没有 Issue 体系，这些内容会散落在多个终端和聊天记录中。并发越多，人越需要在脑中维护每个会话的目标、历史、依赖和完成状态，最终被上下文恢复和重复解释拖垮。Issue 把一次性对话变成可寻址、可恢复和可继续执行的任务状态：原始意图不会被 Agent 输出淹没，调研、决定、实现记录和验收留在同一工作记录中，新 Agent 也不需要继承旧 Agent 的私有记忆。

因此，1.5 万字不只是大量 Prompt。它们经过 Issue 体系后获得了复用和放大能力：一次判断可以约束当前实现、后续审计、人工验收和未来重新接手。Iris 提升的不是人的原始打字速度，而是判断的有效带宽，即减少信息损失、缩短反馈延迟并提高同一判断的复用次数。

在这个控制回路中，各对象承担不同职责：

| 对象 | 控制回路职责 |
| --- | --- |
| Issue | 保存任务意图、过程决定、依赖和验收状态 |
| Status | 提供与当前代码和 Git HEAD 对应的系统状态镜像 |
| Report | 跨任务综合、审计和形成较长期判断 |
| Todo | 把等待人处理的动作聚合为注意力队列 |
| Terminal | 承载人与 Agent 的即时交互 |
| 共享工作树 | 承载正在形成并持续更新的共同现实 |
| Git | 固化人已经接受的项目现实 |

由此，Iris 更准确的定位不是传统 PM 工具或 Agent 启动器，而是 Agent-native 开发中的人类控制面：它把人的产品判断组织成持久、可并行执行、可验证和可恢复的开发意图。

## 进一步的产品含义

未来的并发支持应优先增强语义调度，而不是默认给每个 Agent 创建 Worktree。值得表达和检测的对象包括任务的 `blocks` / `blocked by` 关系、基础模型重构形成的执行屏障、Agent 启动后是否出现关键基线变化、任务之间的文件重叠与设计真相依赖，以及需要升级为隔离实验的高风险操作。

同时，超过 1.5 万字的人类输入也构成产品约束。它证明这套系统能够承载高强度调度，但不应把持续的大量手工解释当作永久前提。Iris 应减少其中重复说明任务边界、依赖关系、当前现实和验收状态的部分，让同样的产品判断以更少的重复表达约束更多 Agent 和更多阶段。

目标不是追求无人化开发，而是让人继续掌握最终产品判断，同时降低维持控制所需的认知和表达成本。共享工作树提供统一现实，Issue 提供持久意图，语义调度决定执行顺序，Agent 提供并行执行能力；这四者共同构成 Iris 能够达到当前开发速度的基础。

## 完整历史的补充观察

### 核心价值不是事后归纳

Iris 在 2026 年 6 月 11 日建立项目骨架，第二天第一次真实 dogfood 就已经得出“作为需求捕获与人-Agent 协作媒介价值最大”的判断。当时形成了 10 条 Issue、7 个实现提交和一份迭代报告，并记录了一场从用户口述、Agent 代录、待决定事项到分批实现的完整 PRD 协商。

这说明“高带宽人类控制回路”不是看到后期高产出后才附加的产品叙事。它在产品第一次使用自身时就已经出现，之后两个月的开发是在不断补强这个早期成立的核心闭环。

### Git 低估了实际并行

当前 `main` 有 77 个提交，Git 作者始终只有一人，没有 merge commit；其中 55 个提交带有 Agent 的 `Co-Authored-By` 记录。提交时间还显示出八次明显的批量汇合：多轮开发都在一到三分钟内连续提交三至八个按模块拆分的结果。

这些批次不可能代表对应功能在几分钟内被串行开发完成。它们说明多个任务先在共享工作树中并行形成结果，再由人按架构层、文档和发布边界整理成提交。Git 保存的是交付拓扑，不保存完整执行拓扑；单一作者、线性历史和零 merge commit 都不能据此推出单 Agent 串行开发。

Issue 与 Git 因而承担不同职责：Issue 是意图、决定和执行过程的工作账本，Git 是人确认后项目现实的交付账本。要求两者一一对应，反而会损失这种分层。

### Issue 是长期运行的控制状态

当前历史保留 111 条 Issue，其中 88 条已经完成；69 条包含明确实施或修复记录，25 条包含独立调研或审计，至少 25 条记录了显式用户决定，58 条拥有三个以上阶段性章节，共收集 369 个任务 checkbox。

这些数据说明 Issue 不是“发出任务、完成后关闭”的一次性票据。它更接近一个任务级状态机和事件日志：原始意图、调查、方向校正、实现、用户反馈、二次处理和验收可以在同一对象中持续演进。Agent 可以更换，终端可以结束，提交可以批量形成，但任务的因果链仍然保留。

### 控制回路同时提供时间带宽

主线 77 个提交实际集中在 12 个自然日完成。2026 年 6 月 27 日至 8 月 5 日之间项目暂停了 39 天；恢复开发后，仍有 8 条 6 月 Issue 被重新读取、复核和更新。

Iris 降低的不只是同一时刻维护多个 Agent 的横向协调成本，也降低了项目中断后恢复上下文的纵向成本：

```text
横向带宽：同时维护多个 Agent 的任务、依赖和反馈
纵向带宽：跨会话、跨人员、跨长时间中断恢复原有判断
```

如果任务状态只存在聊天记录和人的短期记忆里，39 天后的恢复接近重新调研；当原始问题、历次决定和实施证据都保留在 Issue 中，恢复可以从已有因果链继续，而不是从零重建上下文。

### 实现后删除是产品学习而非冲突

完整历史中存在多条“认真实现、真实使用、发现模型不成立、随后删除或重构”的路径：标签、优先级和样式映射曾被实现后移除；性能监视器因测量边界不可信被删除；Focus store 被更直接的项目与会话投影取代；提示词治理、编辑器保存和终端 replay 也经历了多轮真相源与所有权调整。

这些变化不是 Agent 编辑冲突，而是产品假设经 dogfood 后发生的语义修正。代码可以删除，Issue 仍保留当初为什么实现、实际观察到了什么以及后来为什么放弃。Iris 因而不只提高代码产量，也提高“提出假设、实现、验证、推翻并保留理由”的产品学习速度。

从这个角度看，更值得衡量的不是单位时间生成了多少代码，而是形成了多少经过真实反馈验证的产品判断，以及这些判断在被修正后是否仍有可追溯的理由。

### 隔离分支的唯一例外符合风险边界

当前有效拓扑中，除 `main` 外只有一条 `special/configurable-proc-name` 分支，保留三个未合并的独有提交，用于可配置进程名和 Python 文件 IO 等特殊评估。历史还记录过另一条评估分支在方案放弃后被删除。

这类特殊发行实验、互斥方案比较和需要整体保留或丢弃的尝试，正是分支或 Worktree 隔离有价值的场景。普通功能与修复长期共享工作树、特殊实验显式隔离，实际历史与“按风险升级隔离”的模型一致。

## 更完整的产品定义

结合完整历史，Iris 的价值不只是 Agent-native 开发中的人类控制面，也是一套产品认知的持久化与恢复系统。它优化的不是单纯的并发代码量，而是人能够持续提出、执行、验证、修正和复用多少有效判断。

共享工作树让所有 Agent 面对同一个当前现实；Issue 记录为什么要改变现实、改变到哪里以及哪些决定仍然成立；Git 固化哪些改变已经被人正式接受。零编辑冲突是这套机制的一个结果，更重要的结果是：即使大量并行、频繁推翻旧设计并经历长时间中断，项目的意图链条仍然没有断裂。
