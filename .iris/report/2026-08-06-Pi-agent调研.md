## 2026-08-06 调研结论

结论：**应该支持，但当前只做“终端级一等支持”，不做 RPC/SDK 深度集成。**

Pi 与 Iris 不是竞争关系。Pi 是可扩展的 coding-agent harness，Iris 是文档和终端驱动的 PM 壳。Pi 原生加载 `AGENTS.md`，Iris 已经通过环境变量提供 `FOCUS_DOC`，因此二者现有契约天然兼容。近期最合理的投入是把 Pi 加入 agent 预设、检查 Windows 的 Bash 前置条件，并用真实会话做一次兼容性验收。

RPC/SDK 很完整，但接入后 Iris 需要解析 agent 事件、管理模型与认证、重做会话 UI，直接跨过当前“终端是界面、文件是契约、不解析 agent 输出”的产品边界。现阶段收益不足以覆盖耦合和维护成本。

### Pi 是什么

这里的 Pi 指 Mario Zechner 发起的项目，原仓库 `badlogic/pi-mono` 目前会重定向到 `earendil-works/pi`，官方 npm 包也已使用 `@earendil-works/*` 命名空间。

它不是单一 CLI，而是一个 TypeScript monorepo：

| 包 | 职责 |
| --- | --- |
| `pi-coding-agent` | 交互式 coding-agent CLI，也提供 print、JSON、RPC 和 SDK 模式 |
| `pi-agent-core` | 工具调用、消息状态和 agent loop |
| `pi-ai` | Anthropic、OpenAI、Google 等多 provider 的统一流式 API |
| `pi-tui` | 差量渲染的终端 UI |
| `pi-telemetry` | vendor-neutral telemetry 契约与适配器 |

默认模型只有 `read`、`write`、`edit`、`bash` 四个工具。高级工作流主要通过 TypeScript Extensions、Skills、Prompt Templates、Themes 和可分发的 Pi Packages 组合，而不是固化在核心里。官方刻意不内置 sub-agent 和 plan mode，但仓库提供相应扩展示例。

### 工程化评估

| 维度 | 观察 | 判断 |

| 采用度 | GitHub 约 84.7k stars、10.5k forks；新命名空间的 CLI 包近 30 天约 562 万次下载 | 已形成显著用户和生态规模 |
| 活跃度 | 当天仍有多位贡献者提交；最近 15 个 release 分布在约 6 周内 | 极活跃，但变化速度也很高 |
| 发布 | 当前 `v0.84.0`，release 非 prerelease；提供 npm 安装、安装脚本和独立二进制 | 交付链完整，但仍是 `0.x` |
| 测试与 CI | 仓库约 515 个测试文件、134 个 coding-agent 示例文件；主干和 PR 的近期 CI 有成功记录 | 覆盖和示例都明显超过早期玩具项目 |
| 供应链 | 直接依赖精确锁版、发布包带 shrinkwrap、CI 使用 `--ignore-scripts`、有 npm audit/signature、release smoke 和校验和 | 工程纪律强 |
| 扩展性 | Extensions 可注册工具/命令/provider、拦截生命周期、修改 system prompt/context、实现 UI；可热重载 | 核心能力成熟，也是主要差异点 |
| 程序化接口 | RPC 使用严格 JSONL，覆盖流式消息、工具事件、队列、模型、会话树、压缩、重试和扩展 UI；SDK 暴露 `AgentSession` 等类型化 API | 足以支撑 IDE 或自定义客户端 |
| 平台 | 官方支持 Windows，但要求 Git Bash、Cygwin、MSYS2 或 WSL 中的 Bash | 对 Windows-first 的 Iris 是真实接入门槛 |
| 安全 | project trust 只控制项目资源加载；没有内置 permission system 或 sandbox，工具和扩展继承启动用户权限 | 需明确告知，不应把 trust 描述成沙箱 |
| 稳定性 | 高频发布、仍为 `0.x`，文档中已有兼容入口未来移除等迁移提示 | CLI 表面可用，深层 API 需要持续跟版 |

综合判断：**工程化成熟度高，已可生产使用；接口稳定性和安全边界仍需要调用方自己治理。** “成熟”不等于“适合嵌入”，尤其是一个快速演进的 `0.x` SDK。

### 与 Iris 的实际兼容性

Pi 启动时会从全局、父目录和当前目录加载 `AGENTS.md` 或 `CLAUDE.md`。Iris 已经做到：

1. cwd 固定为项目根。
2. 启动进程带有相对路径形式的 `FOCUS_DOC`。
3. 根 `AGENTS.md` 中包含 Iris 协议和“先读取 `FOCUS_DOC`”的规则。

因此把 agent 命令设为 `pi` 后，Pi 在收到用户第一条指令时就能按协议读取聚焦文档，不需要 Iris 理解 Pi 的会话格式，也不需要 API key 进入 Iris。

有三个兼容性注意点：

- Pi 在 Windows 上实际依赖 Bash。Iris 从 PowerShell 启动 `pi` 没问题，但需要提前检测 Git Bash/WSL，否则用户只会在终端里看到启动失败。
- 如果项目根存在 `AGENTS.override.md`，Pi 会用它替代同目录的 `AGENTS.md`。这可能绕过 Iris 的协议块，应纳入验收或文档提示。
- Pi 没有 Iris 当前支持的 JSON `SessionStart` hook 形态。没有 hook 不影响正确性，只是聚焦文档要等首条用户指令后由模型主动读取，而不是在模型调用前预展开。

### 支持层级决策

| 层级 | 内容 | 现在是否做 | 原因 |
| --- | --- | --- | --- |
| 通用兼容 | 用户手工添加 `{ command: "pi" }` | 已经可用 | 现有 PTY、cwd、`FOCUS_DOC` 和 `AGENTS.md` 足够 |
| 内置预设 | Agents 页加入 `pi` 预设，`command: "pi"`、`injection: "none"` | **建议现在做** | 改动小、可发现性高，符合 agent-agnostic 定位 |
| 启动诊断 | 检测 `pi` 和 Windows Bash，给出明确缺失信息 | **建议随预设做** | Windows 是 Iris 的首要平台，也是 Pi 最明确的前置条件 |
| Pi 原生扩展 | 经用户确认安装全局 Iris extension，在第一次 `before_agent_start` 时注入焦点快照 | **暂缓，按需 spike** | 可实现近似零轮次注入，但会向用户目录安装可执行 TS，维护面明显扩大 |
| RPC 子进程 | Iris 渲染 Pi 的结构化消息和工具状态 | **不做** | 会产生第二套会话/聊天 UI，违背“不解析 agent 输出”和“终端即界面” |
| 同进程 SDK | 直接嵌入 `AgentSession`、模型和认证 | **不做** | 产品边界冲突最大；Pi 要求 Node `>=22.19`，Iris 当前基线是 Node `>=20`；还会引入凭据、依赖和版本耦合 |

### 为什么不因 RPC 很强就立刻接入

RPC 确实能给 Iris 当前 PTY 启发式拿不到的信息，例如精确区分运行/等待、结构化工具调用、token/cost、模型切换、取消、会话分叉和压缩。但是这不是一个小 adapter：

1. Iris 需要新增非 PTY 会话类型和一套协议生命周期。
2. 右栏需要从通用终端变成 Pi 专属聊天客户端，并复刻输入队列、工具卡片、扩展交互等体验。
3. 会话所有权会在 Iris 锚定模型和 Pi 的 JSONL 树之间重叠。
4. Pi 的升级会变成 Iris 的兼容性责任，削弱其他 agent 的对等地位。
5. 文件写回才是 Iris 的长期记忆；结构化终端输出并没有改善核心文档契约。

只有当产品方向明确改为“统一 agent 客户端”，并且至少两种 agent 都有可维护的结构化协议时，才值得重新评估 RPC。SDK 则应更晚。

### 建议实施范围

第一阶段控制在很小的改动面：

1. 在 Agents 页的快捷预设中增加 `pi`，先不放进所有用户的默认 agent 清单。
2. 增加启动前诊断：命令是否存在；Windows 下是否能找到官方支持的 Bash。
3. 验收项目根、普通 issue、子 workspace 三类会话的 `FOCUS_DOC` 和写回作用域。
4. 单独覆盖存在 `AGENTS.override.md` 时的行为，避免误称“已完整注入”。
5. 观察实际用户是否在意首条指令才读取焦点；只有出现明确需求，再做全局 Pi extension 的小型 spike。

### 待确认与验收

## 2026-08-07 补充评估：如果 RPC 永远只选一个

新增产品约束：Iris 不追求给每个 agent 实现 RPC。未来即使增加结构化后端，也只选一个；其余 agent 继续使用原生 CLI 和 PTY。

这个约束使前文“至少两种 agent 都有可维护协议才重新评估 RPC”不再成立。新的结论是：

> **唯一 RPC 后端应选择 Codex app-server，不选择 Pi RPC。**

这里选的是 `codex app-server` 子进程协议，不是 Codex SDK，也不是直接调用 OpenAI API。Codex 的原生 CLI 仍应保留为逃生舱，其他 agent 的 CLI 地位不变。

### 为什么唯一选择是 Codex app-server

如果只维护一套结构化集成，最重要的不是 provider 数量，而是这个后端能否完整承担“富客户端宿主”的责任。Codex app-server 在这件事上明显领先：

1. **协议就是为富客户端设计的。** 官方明确将它定义为给自有产品做深度集成的接口，Codex VS Code 扩展也使用这一层，而不是从终端输出倒推状态。
2. **安全闭环最完整。** 协议原生包含审批请求；Codex 本身有文件系统/网络沙箱、权限 profile 和命令规则。Iris 只需正确呈现并回复审批，不必自己发明 agent 权限系统。
3. **会话模型与 Iris 能对齐。** `Thread -> Turn -> Item` 可映射为“文档锚定会话 -> 一次用户请求 -> 消息/工具/文件改动”，并支持 start、resume、fork、steer、interrupt、archive 和精确状态通知。
4. **认证可由后端拥有。** app-server 支持读取账户状态、ChatGPT managed login、device code、API key、登出和 rate-limit 状态。Iris 不必接触或复制用户 token。
5. **版本治理比其他候选强。** 协议区分稳定 API 与显式 opt-in 的 experimental API；CLI 能生成与当前版本严格匹配的 TypeScript/JSON Schema。未来仍需兼容矩阵，但不会靠手抄事件类型维护。
6. **Windows 契合度最高。** Codex 有原生 Windows/ConPTY 路径和 Windows 沙箱；Pi 则明确要求额外 Bash。对 Windows-first 的 Iris，这是长期维护成本差异。
7. **stdio 足够。** 默认 JSONL/stdio 就能满足本地 Electron 子进程集成。WebSocket 目前被官方标为 experimental/unsupported，Iris 没必要碰它。

### 候选排序

| 排名 | 候选 | 优点 | 没有成为唯一选择的原因 |
| --- | --- | --- | --- |
| 1 | **Codex app-server** | 富客户端专用 JSON-RPC；认证、审批、真实沙箱、线程历史、流事件、schema、Windows 支持完整 | 绑定 Codex agent 语义，provider 中立性较弱；但“只选一个”的前提已经接受这种非对称 |
| 2 | **OpenCode server** | TUI 本身就是 server client；HTTP + SSE；发布 OpenAPI 3.1；多 provider、session、diff、permission API 很完整 | 本地 HTTP server 生命周期和认证面比 stdio 更重；已确认有 permission 交互，但安全边界不等同于 Codex 的原生 OS 沙箱契约 |
| 3 | **Pi RPC** | JSONL 简洁；多 provider；session tree、流式工具事件、扩展 UI、压缩和重试都很完整 | 官方明确没有内置 permission system/sandbox；Windows 依赖 Bash；高频 `0.x` 变化且没有 Codex 那样清晰的稳定/实验协议分层 |
| 4 | **Gemini CLI ACP** | 开放 ACP 标准；JSON-RPC/stdio；支持认证、session、prompt、cancel、approval mode 和客户端代理文件系统 | 标准公共面偏 IDE 最小公分母，Gemini 的实现能力面不如 Codex app-server 丰富；若 Iris 不准备借 ACP 再接多个 agent，标准化红利也被削弱 |
| 5 | **Claude Agent SDK** | Claude Code 能力可编程化，Node 18+，官方维护 | 它首先是 SDK，不是语言无关的稳定本地 RPC 宿主；已有从 Claude Code SDK 到 Agent SDK 的 breaking migration，且受 Anthropic Commercial Terms 约束 |

### 为什么不是 Pi RPC

Pi 是很好的 CLI 和 agent harness，但“适合作为多 provider 工具”与“适合作为唯一 GUI 后端”不是同一个判断。

Pi 的最大优势是同一套 agent loop 可切换大量 provider，甚至复用多个订阅登录。如果 Iris 的战略目标是做 provider-neutral agent client，这会让 Pi 成为首选。但 Iris 当前的战略目标仍是文档/终端 PM 壳；唯一 RPC 的价值应该是获得一套**最完整、最安全、最少需要 Iris 补基础设施**的结构化体验。

Pi 缺少内置权限和沙箱后，Iris 至少要在以下方案中选一个：自己实现审批层、强制容器化、安装第三方安全扩展，或接受 agent 以用户完整权限运行。前三者都扩大了 Iris 的职责，最后一个不适合包装成更“原生”的 GUI 体验。多 provider 的收益不足以抵消这一点。

### 为什么 OpenCode 仍排在 Pi 前面

OpenCode 的核心架构就是 client/server：TUI、IDE 插件和外部客户端共享同一服务端，OpenAPI 3.1 是公开契约，SSE 是公开事件流，session、diff、permission 和 provider auth 都是一等 API。它比 Pi RPC 更接近“可直接承载产品 UI 的后端”。

如果未来产品战略改成“唯一 RPC 必须同时覆盖尽可能多的模型/provider”，应把选择改成 **OpenCode server**，而不是 Pi RPC。当前之所以仍选 Codex，是因为 Windows、安全隔离、审批闭环和稳定/实验 API 分层权重更高。

### 实现时的边界

即使未来选定 Codex app-server，也不应立即把整个右栏替换成聊天 UI。建议按以下边界做：

1. 新增独立的 `structured` session kind，与现有 `pty` session 并存；不要让 Codex 特例污染通用会话模型。
2. 每个 Iris 项目管理一个 app-server 子进程，文档锚定到 Codex thread；进程崩溃不能影响文档编辑和普通终端。
3. 第一版只使用 stdio 和稳定 API，不设置 `experimentalApi`，忽略未知 notification 以便前向兼容。
4. 固定并检测最低/已验证 Codex CLI 版本，维护小范围兼容矩阵；构建时保存对应 schema 和协议 fixtures。
5. 第一版复用用户已有 Codex 登录，不保存 token；登录 UI 可以后做。
6. 必须实现审批请求、取消、断线恢复和沙箱状态展示后，才允许执行写操作；不能只做“消息能流出来”的演示版。
7. `FOCUS_DOC`、Iris 协议和文档快照通过 thread/turn 的结构化上下文注入，但长期结果仍以 `.iris/` 文件写回为准。
8. Codex 原生 CLI 始终保留；RPC 故障、版本不兼容或用户不想用结构化 UI 时可直接回退 PTY。

### 决策建议

- [ ] 确认未来唯一结构化后端优先选择 Codex app-server，Pi、OpenCode、Gemini、Claude 继续保留 CLI 原生支持。
- [ ] 真正立项前先做只读 spike：`initialize -> thread/start -> turn/start -> streamed items -> turn/completed`，并验证 Windows 下断线恢复和版本拒绝策略。
- [ ] spike 通过后再评审审批/沙箱闭环；未完成该闭环前不进入写文件阶段。
